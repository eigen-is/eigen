# Backend Code Review: Contacts

## Summary

The Contacts domain is a relatively compact module consisting of five files: a domain class
(`contacts.ts`), schema (`schema.ts`), database config (`db-config.ts`), SSE event builders
(`sse-events.ts`), and a route layer (`routes/contacts.ts`). It also has a dedicated test file
(`test/contacts.test.ts`). The module manages per-user contact storage with labels, avatar uploads,
and a self-contact (the "me" contact tied to the authenticated user).

Overall the code is functional and reasonably well-structured. However, the review uncovered one
critical bug, several important issues affecting correctness and security, and a number of minor
quality issues.

## Architecture Compliance

**Mostly compliant.** The module follows the established patterns:

- Domain class owned by `Home` singleton -- **yes** (`UserHome` creates `Contacts` in constructor).
- DB config with versioned migrations -- **yes** (`CONTACTS_DB_CONFIG` in `db-config.ts`).
- Routes in `apps/api/src/routes/contacts.ts` with `{auth: true}` -- **yes**.
- SSE event builders in `sse-events.ts` -- **yes**.
- `ManagedDatabase` via `home.getLocalDatabase()` -- **yes**.

**Deviations:**

- No `index.ts` barrel file in `apps/api/src/lib/contacts/`. Other domains have one; contacts does
  not. The route file imports directly from `contacts.ts`.
- No shared validation schemas in `packages/lib/src/validation/` for contacts. Email, phone, and
  other field validation is absent entirely.

## Issues Found

### Critical

#### 1. `getMe()` returns `null` after creating the self-contact (bug)

**File:** `apps/api/src/lib/contacts/contacts.ts`, lines 363-371

When a user's "me" contact does not yet exist, `getMe()` calls `addYourself()`, which returns
`user.id` (the auth user UUID). It then calls `this.getContactById(addedId)` with that user ID.
However, `getContactById` looks up by `schema.contacts.id` (the contact row UUID, generated by
`uuidv4()` inside `addContact`), not by `eigenId`. Since `user.id` will never match a contact row
`id`, the lookup returns `null`.

```
public async getMe() {
    ...
    } else {
        const addedId = await this.addYourself();   // returns user.id, NOT the contact row id
        return this.getContactById(addedId);         // looks up by contacts.id -- always null
    }
}

private async addYourself() {
    ...
    await this.addContact({...});   // addContact generates and returns the real contactId
    return user.id;                 // but addYourself discards it and returns user.id instead
}
```

**Impact:** The `/me` endpoint returns `null` on the very first call for any user. The second call
works because by then `addYourself` has already inserted the row and the `found` branch in `getMe()`
is taken. In practice the `init()` method also calls `addYourself()` during Home initialization, so
this path is rarely hit -- but it can occur in race conditions or if `init()` is called with existing
contacts but the "me" contact was deleted.

**Fix:** `addYourself` should return the contact ID from `addContact`, not `user.id`.

### Important

#### 2. `ownerId` route parameter is completely ignored -- no authorization check

**File:** `apps/api/src/routes/contacts.ts`, all routes

Every route includes `:ownerId` in the path (e.g., `/contacts/:ownerId/contacts`), but the parameter
is never read. All handlers call `getContacts(user)` which uses the authenticated `user.id`
regardless of the `ownerId` in the URL. This means:

- A user can supply any `ownerId` and still get their own contacts (confirmed by the
  "ownerId spoofing" test at lines 189-202 in `contacts.test.ts`).
- The `ownerId` parameter serves no purpose and creates a misleading API surface. Other domains
  (e.g., Drive) use `ownerId` to select between user/team/org scopes. Contacts ignores it
  entirely.

This is not a security vulnerability (it silently returns the authed user's data), but it is
architecturally misleading and inconsistent with other routers.

#### 3. Path traversal in avatar download

**File:** `apps/api/src/lib/contacts/contacts.ts`, line 318
**File:** `apps/api/src/routes/contacts.ts`, line 98

The `downloadAvatar(filename)` method passes the `filename` parameter directly to
`this.storage.read('avatars/' + filename)`. While `LocalFilesystem.getFilePath` uses `path.join`,
`path.join` does not prevent path traversal -- `path.join('/base', '../etc/passwd')` resolves to
`/etc/passwd`.

If a client calls `GET /contacts/:ownerId/avatar/../../eigen.contacts/contacts.db`, the
`LocalFilesystem` would attempt to read from outside the `avatars/` directory. Elysia may
percent-decode the URL parameter, making `..%2F..%2F` a viable traversal vector.

**Impact:** Potential read access to the user's contacts database file or other files within their
home directory.

**Fix:** Validate that `filename` contains no path separators or `..` sequences before passing it to
storage. Alternatively, use `path.basename(filename)` to strip any directory components.

#### 4. Avatar stored in JSON `data` but also declared as a separate column -- dual storage

**File:** `apps/api/src/lib/contacts/schema.ts`, line 11
**File:** `apps/api/src/lib/contacts/contacts.ts`, lines 29-45 and 136-144

The `contacts` table has a dedicated `avatar` column (line 11 of `schema.ts`), but
`extractContactData` puts the avatar URL into the `data` JSON blob (line 40 of `contacts.ts`). The
`addContact` method does not set the `avatar` column at all. Meanwhile, `getContactById` and
`getContacts` spread the `data` JSON (which includes `avatar`) over the result, effectively ignoring
the dedicated `avatar` column.

The `data` JSON type explicitly excludes `avatar` from its Omit type
(`Omit<Contact, 'id' | 'firstName' | 'lastName' | 'eigenId' | 'labels' | 'avatar'>`), yet the
`extractContactData` function includes it in the JSON anyway.

**Impact:** The `avatar` column in SQLite is always `null`. Avatar data is only stored in the JSON.
The schema type disagrees with actual storage. If someone queries the DB directly or builds an index
on the `avatar` column, they will find nothing.

#### 5. `updateContact` does not update `eigenId`

**File:** `apps/api/src/lib/contacts/contacts.ts`, lines 177-184

The `updateContact` method updates `firstName`, `lastName`, `data`, and `updatedAt`, but never
updates the `eigenId` field. If an API client sends a different `eigenId` in the PUT body, it is
silently ignored. While this might be intentional (eigenId should be immutable once set), it is not
validated or documented.

More concerning: the `ContactSchema` in `routes/contacts.ts` line 28 allows `eigenId` as an
optional string in the body, suggesting the client could attempt to set it.

#### 6. `deleteLabel` deletes junction rows after deleting the label -- redundant but order-dependent

**File:** `apps/api/src/lib/contacts/contacts.ts`, lines 232-237

```typescript
await this.db.delete(schema.labels).where(eq(schema.labels.id, id));
await this.db.delete(schema.contactsToLabels).where(eq(schema.contactsToLabels.labelId, id));
```

The schema defines `ON DELETE CASCADE` on the `labelId` foreign key in `contacts_to_labels`, so
deleting from `labels` should automatically cascade to the junction table. The explicit second delete
is redundant. However, this depends on `PRAGMA foreign_keys = ON` being set, which `ManagedDatabase`
does handle. The redundancy is harmless but misleading -- it suggests the cascade is not trusted.

#### 7. `cleanupAvatarImages` and `uploadAvatar` fire-and-forget during `init()`

**File:** `apps/api/src/lib/contacts/contacts.ts`, lines 106, 297

In `init()` at line 106, `cleanupAvatarImages()` is called without `await`. Similarly, in
`uploadAvatar()` at line 297, cleanup is called without `await`. Since these methods modify the
filesystem, running them concurrently with the rest of initialization or avatar upload could cause
race conditions (e.g., a newly uploaded avatar being deleted by a concurrent cleanup that hasn't
seen the updated contact data yet).

#### 8. `init()` missing `await` on `this.addContact` for the hardcoded Reinder contact

**File:** `apps/api/src/lib/contacts/contacts.ts`, line 89

```typescript
this.addContact({...});  // no await
```

The `addContact` call for the hardcoded "Reinder" contact is not awaited. This means the database
insert runs concurrently with the `cleanupAvatarImages()` call on line 106 and the function returns
before the contact is actually inserted. In most cases this is harmless, but it means `init()` can
resolve before all seed data is written.

#### 10. Hardcoded developer contact in `init()`

**File:** `apps/api/src/lib/contacts/contacts.ts`, lines 87-103

Every new user gets a hardcoded "Reinder Nijhoff" contact added on first init. This is development
convenience that should not ship to production. The name is hardcoded even though the user record
has a `name` field, and the domain lookup (`reinder@${getDomain()}`) will fail silently on instances
where no such user exists (handled by the `if (reinder)` check, but still unexpected behavior for a
contacts module).

#### 11. `updateLabel` has a useless try/catch that re-throws

**File:** `apps/api/src/lib/contacts/contacts.ts`, lines 213-230

```typescript
try {
    ...
    return updatedLabel;
} catch (error) {
    throw error;
}
```

The `catch` block just re-throws the error with no logging or transformation. This is dead code.

#### 12. `updateLabel` queries the updated label but the result is unused in some paths

**File:** `apps/api/src/lib/contacts/contacts.ts`, line 222

After updating, the method queries `SELECT * FROM labels WHERE id = ?` and returns the result. This
is fine for the route layer (the PUT handler returns it), but the query could be avoided since the
caller already knows the new values.

#### 13. `getContacts()` N+1 query pattern

**File:** `apps/api/src/lib/contacts/contacts.ts`, lines 266-293

For each contact, a separate query fetches its label associations. With N contacts, this results in
N+1 queries. For a local SQLite database this is acceptable performance-wise, but a single JOIN
query would be cleaner and more efficient.

#### 14. `getContactById` return type spread inconsistency

**File:** `apps/api/src/lib/contacts/contacts.ts`, line 261

The spread type cast is `Omit<Contact, 'id' | 'firstName' | 'lastName' | 'labels'>`, which does not
exclude `eigenId`. This means if the `data` JSON happened to contain an `eigenId` field, it would
overwrite the `eigenId` set on line 260. The schema type for `data` excludes `eigenId`, but the
runtime spread does not enforce this.

#### 15. No email format validation

**File:** `apps/api/src/routes/contacts.ts`, line 19

The `ContactSchema` defines `email` as `t.Array(t.String())`. There is no format validation -- any
string is accepted as an email address. Similarly, `phone` accepts any string, `birthday` accepts
any string (no date format check), and `color` on `LabelSchema` accepts any string (no hex color
validation).

#### 16. `downloadAvatar` returns `null` but route creates `new Response(null)`

**File:** `apps/api/src/routes/contacts.ts`, lines 98-106
**File:** `apps/api/src/lib/contacts/contacts.ts`, lines 317-323

When the avatar file does not exist, `downloadAvatar` returns `null`. The route handler then
executes `new Response(null)` with status 200 and `Content-Type: image/webp`. The client receives
an empty response with image headers. The `catch` block only catches exceptions, not the `null`
return. The handler should check for `null` and return 404 explicitly.

## Robustness

- **Race conditions in init:** The `init()` method does not guard against being called twice
  concurrently. However, the `Home.init()` parent method has initialization guards
  (`initializationStarted` + waiters pattern at lines 57-76 of `home.ts`), so this is protected
  at the Home level.
- **No transaction usage:** `addContact`, `updateContact`, `deleteContact`, and `setContactLabels`
  all perform multiple database operations (insert contact + insert labels) without wrapping them in
  a transaction. A failure between the contact insert and the label insert would leave the database
  in an inconsistent state.
- **Fire-and-forget async in init:** Both `cleanupAvatarImages()` (line 106) and the Reinder contact
  `addContact` (line 89) are called without `await`, meaning errors in these operations are silently
  swallowed.
- **`enforceAvatarUpload` uses hardcoded `'default'` mount:** The enforcement function
  (`enforcement.ts` line 46) resolves quotas using the `'default'` mount ID, which may not exist if
  the user's Home hasn't been fully initialized. This could throw during avatar upload.

## Test Coverage

The test file (`apps/api/src/test/contacts.test.ts`) covers:

- **Contact CRUD**: Create, list, get by ID, update, delete -- **good coverage**.
- **Label CRUD**: Create, list, update, delete -- **good coverage**.
- **Cross-user isolation**: Verifies separate contact stores per user -- **good**.
- **ownerId spoofing**: Confirms the ownerId parameter is ignored -- **good, but tests a weakness
  rather than correct behavior**.
- **Me endpoint**: Get own profile, spoofing protection, self-delete prevention -- **good**.
- **Whitespace trimming**: Create test uses padded names to verify trimming -- **good**.

**Missing test coverage:**

- Avatar upload and download (no tests at all).
- Path traversal on avatar download endpoint.
- Label assignment to contacts (`setContactLabels` is never tested via the API).
- Contact-label relationship (creating a contact with labels, verifying labels appear on the
  contact, removing a label and verifying it's removed from associated contacts).
- Empty/missing required fields (what happens with empty `firstName`?).
- Concurrent operations.
- `getMe()` when no "me" contact exists yet (the critical bug path).
- Error cases (invalid contact ID on update, invalid label ID on update).
- The `size()` method for quota calculations.

## Recommendations

1. **Fix the `getMe` / `addYourself` bug** -- `addYourself()` should return the contact ID from
   `addContact()`, not `user.id`.

2. **Add path traversal protection on avatar download** -- sanitize `filename` with
   `path.basename()` or reject inputs containing `/`, `\`, or `..`.

3. **Add `await` to fire-and-forget calls in `init()`** -- both the Reinder contact `addContact`
   (line 89) and `cleanupAvatarImages` (line 106) should be awaited.

4. **Handle `null` return from `downloadAvatar` in the route** -- check for `null` before creating
   the `Response` and return 404 explicitly.

5. **Fix avatar dual-storage** -- either remove the `avatar` column from the schema (and the type
   exclusion), or populate it during `addContact`/`updateContact` and stop storing it in the JSON.

6. **Remove the hardcoded Reinder contact** or make the seed data configurable.

7. **Translate the Dutch comment** to English.

8. **Remove the useless try/catch** in `updateLabel`.

9. **Wrap multi-step writes in transactions** -- particularly `addContact` (insert + labels) and
   `updateContact` (update + labels).

10. **Add basic field validation** -- at minimum, email format validation in the route schema, and
    hex color validation for labels.

11. **Add avatar-related tests** to the test suite.
