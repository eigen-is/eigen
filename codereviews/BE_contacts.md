# Backend Review: Contacts

**Scope:** `apps/api/src/lib/contacts/`, `apps/api/src/routes/contacts.ts`
**Reviewed:** 2026-03-18

The contacts domain is a compact module: domain class (`contacts.ts`), schema (`schema.ts`),
database config (`db-config.ts`), SSE event builders (`sse-events.ts`), and route layer
(`routes/contacts.ts`). It manages per-user contact storage with labels, avatar uploads, and a
self-contact ("me" contact tied to the authenticated user).

Architecture compliance is good: domain class owned by `Home` singleton (via `UserHome` constructor),
`ManagedDatabase` via `home.getLocalDatabase()`, versioned migrations in `CONTACTS_DB_CONFIG`, routes
with `{auth: true}`, SSE builders in `sse-events.ts`. Two deviations: no `index.ts` barrel file
(other domains have one), and no shared validation schemas in `packages/lib/src/validation/`.

---

## Critical Issues

### 1. `getMe()` returns `null` when creating the self-contact

**File:** `apps/api/src/lib/contacts/contacts.ts:363-371`

When no self-contact exists, `getMe()` calls `addYourself()`, which returns `user.id` (the auth user
UUID). It then calls `this.getContactById(addedId)` -- but `getContactById` looks up by
`schema.contacts.id` (the contact row UUID generated by `uuidv4()` inside `addContact`), not by
`eigenId`. The user's auth ID will never match a contact row's primary key, so the lookup always
returns `null`.

```
addYourself():
  await this.addContact({...});   // addContact returns the new contact row UUID
  return user.id;                 // discards it, returns user.id instead

getMe():
  const addedId = await this.addYourself();   // user.id
  return this.getContactById(addedId);        // looks up by contacts.id -- null
```

**Impact:** The `/me` endpoint returns `null` on the first call if the self-contact doesn't exist.
In practice, `init()` (line 85) calls `addYourself()` during `Home` initialization, so the self-
contact is normally created before any API call reaches `getMe()`. The bug path triggers only if the
self-contact is deleted after init, or under a race condition where `getMe()` is called before
`init()` completes.

**Fix:** `addYourself()` should capture and return the contact ID from `addContact()`:
`const contactId = await this.addContact({...}); return contactId;`

**Previous review:** Correctly identified this bug. Analysis confirmed -- no changes to severity or
description.

## Important Issues

### 2. `updateContact` with omitted `labels` silently strips all labels from the contact

**File:** `apps/api/src/lib/contacts/contacts.ts:187`
**File:** `apps/api/src/routes/contacts.ts:27`

The route schema declares `labels` as `t.Optional(t.Array(t.String()))`. When a client sends a PUT
request without a `labels` field, `extractContactData` destructures `labels` as `undefined`. Then
`updateContact` calls `setContactLabels(id, labels || [])`, which passes `[]`. Inside
`setContactLabels`, the first operation is
`DELETE FROM contacts_to_labels WHERE contactId = ?` -- wiping all existing label associations.

**Impact:** Any contact update that doesn't explicitly include the full labels array will destroy the
contact's label associations. This is a data-loss bug. The client must always send the complete
labels array on every update to preserve existing assignments.

**Fix:** Skip `setContactLabels` when `labels` is `undefined`:
`if (labels !== undefined) await this.setContactLabels(id, labels);`
Apply the same guard in `addContact` at line 147.

**Previous review:** Not identified. This is a new finding.

### 3. Path traversal in avatar download

**File:** `apps/api/src/lib/contacts/contacts.ts:317-318`
**File:** `apps/api/src/routes/contacts.ts:96-98`

`downloadAvatar(filename)` passes the filename directly to `this.storage.read('avatars/' + filename)`.
`LocalFilesystem.getFilePath` uses `path.join(baseDir, filePath)`, which resolves `..` segments. If
`filename` contains `../`, the resolved path escapes the `avatars/` directory.

The storage base is `{homeDir}/eigen.contacts`. A filename like `../contacts.db` would resolve to
`{homeDir}/eigen.contacts/contacts.db`, leaking the user's contacts database. A filename like
`../../eigen.mail/mail.db` would leak the mail database.

Elysia's `:filename` route parameter typically matches a single path segment (no literal slashes),
which limits the attack surface for un-encoded input. However, `..` without slashes still escapes
one level (the `avatars` directory itself), and behavior with percent-encoded slashes (`%2F`) depends
on the HTTP server's decoding policy. The risk is confined to the authenticated user's own home
directory since the storage is scoped to their home.

**Impact:** Authenticated users could potentially read arbitrary files within their own home directory
tree via the avatar endpoint. Severity is moderate -- the attacker can only access their own data,
but they could extract raw database files that the API would not normally expose.

**Fix:** Sanitize with `path.basename(filename)` before passing to storage, or reject any filename
containing `/`, `\`, or `..`.

**Previous review:** Correctly identified. I've refined the severity assessment -- the traversal is
scoped to the user's own home directory, and Elysia's single-segment matching limits practical
exploitability.

### 4. Avatar stored in JSON `data` contradicts schema type and leaves the `avatar` column always NULL

**File:** `apps/api/src/lib/contacts/schema.ts:11-12`
**File:** `apps/api/src/lib/contacts/contacts.ts:29-41, 136-144`

The schema declares `avatar` as both a dedicated column (line 11) and explicitly excludes it from the
`data` JSON type: `Omit<Contact, 'id' | 'firstName' | 'lastName' | 'eigenId' | 'labels' | 'avatar'>`.
Despite this, `extractContactData` (line 40) includes `avatar` in the `data` object. `addContact`
never sets the `avatar` column. `getContactById` and `getContacts` spread the JSON `data` over the
result, so the avatar value comes from the JSON -- not the column.

**Impact:** The `avatar` column is always `NULL` in the database. The TypeScript type for `data`
disagrees with its runtime content. Direct database queries on the `avatar` column return nothing.

**Fix:** Either remove the `avatar` column from the schema and the type exclusion (store it only in
JSON), or populate the column during insert/update and remove it from the JSON blob. The former is
simpler.

**Previous review:** Correctly identified. No changes.

### 5. `updateUser` not awaited in `updateContact` -- fire-and-forget auth DB write

**File:** `apps/api/src/lib/contacts/contacts.ts:167`

When updating the self-contact ("me"), `updateUser(this.home.user, ...)` is called without `await`.
This function is async -- it writes to the auth database (`users` table) to update the user's display
name and avatar image. Errors from this write are silently swallowed. If it fails, the contact is
updated but the auth user record is stale.

**Impact:** Silent failure when syncing the self-contact name/avatar to the auth database. The user
sees updated contact info but their auth profile (visible in other contexts like the topbar, shared
documents, etc.) retains the old values.

**Fix:** `await updateUser(...)`.

**Previous review:** Not identified. This is a new finding.

### 6. `ownerId` route parameter is ignored -- no authorization check

**File:** `apps/api/src/routes/contacts.ts`, all routes

Every route includes `:ownerId` in the path but no handler reads it. All handlers call
`getContacts(user)` which resolves the authenticated user's contacts regardless of the URL. A user
can supply any `ownerId` and get their own data (confirmed by the spoofing test at
`contacts.test.ts:189-202`).

**Impact:** Not a security vulnerability (returns the authed user's data regardless), but
architecturally misleading. Other domains use `ownerId` for user/team/org scope selection.

**Previous review:** Correctly identified. No changes.

### 7. Fire-and-forget calls in `init()` -- unwaited `addContact` and `cleanupAvatarImages`

**File:** `apps/api/src/lib/contacts/contacts.ts:89, 106`

Two async operations are not awaited:
- Line 89: `this.addContact({...})` for the hardcoded Reinder contact -- database insert runs
  concurrently with the rest of init. Errors are silently swallowed.
- Line 106: `this.cleanupAvatarImages()` -- filesystem operations (listing files, deleting orphans)
  run concurrently. If a new avatar is uploaded before cleanup finishes, the cleanup could delete it
  (it reads the contacts list before the contact is updated with the new avatar URL).

**Impact:** Init resolves before seed data is fully written. Cleanup can race with avatar uploads.
Errors in either operation are silently lost.

**Fix:** `await` both calls.

**Previous review:** Correctly identified as two separate issues (items 7 and 8). Consolidated here
since the root cause (missing `await` in init) is the same.

### 8. No uniqueness constraint on `eigenId` -- duplicate self-contacts possible

**File:** `apps/api/src/lib/contacts/schema.ts:10`
**File:** `apps/api/src/lib/contacts/db-config.ts:15`

The `eigenId` column has no UNIQUE constraint or index. `getMe()` (line 365) uses
`.where(eq(schema.contacts.eigenId, user.id)).get()` which returns the first match. If duplicate
contacts with the same `eigenId` exist (e.g., from a race in `addYourself`), the user would have
multiple self-contacts, and `getMe()` would arbitrarily pick one.

**Impact:** Potential data integrity issue. Also, `getMe()` does a full table scan on every call
since there's no index on `eigenId`.

**Fix:** Add a unique index on `eigenId` (for non-empty values) in the migration, or at minimum add
a regular index for query performance.

**Previous review:** Not identified. This is a new finding.

## Minor Issues

### 9. `deleteLabel` explicitly deletes junction rows that are already cascade-deleted

**File:** `apps/api/src/lib/contacts/contacts.ts:234-235`

```typescript
await this.db.delete(schema.labels).where(eq(schema.labels.id, id));
await this.db.delete(schema.contactsToLabels).where(eq(schema.contactsToLabels.labelId, id));
```

The schema defines `ON DELETE CASCADE` on `contactsToLabels.labelId`. With `PRAGMA foreign_keys = ON`
(set by `ManagedDatabase`), deleting the label automatically cascades. The second delete is
redundant. It executes against an already-empty set (the cascade already ran), which is harmless but
misleading.

**Previous review:** Correctly identified. No changes.

### 14. `downloadAvatar` returns `null` but route returns 200 with image/webp headers

**File:** `apps/api/src/routes/contacts.ts:96-106`
**File:** `apps/api/src/lib/contacts/contacts.ts:317-323`

When the avatar file doesn't exist, `downloadAvatar` returns `null`. The route handler creates
`new Response(null)` with status 200 and `Content-Type: image/webp`. The `catch` block only catches

**Fix:** Check for `null` before `new Response(...)` and return a 404.

### 15. No input validation on email, phone, birthday, or label color

**File:** `apps/api/src/routes/contacts.ts:15-35`

`email` is `t.Array(t.String())` -- any string is accepted. `phone` likewise. `birthday` accepts

### 16. `ContactSchema` accepts `id` in the body for both create and update

**File:** `apps/api/src/routes/contacts.ts:16`

The same `ContactSchema` is used for POST (create) and PUT (update). It includes
`id: t.Optional(t.String())`. The `addContact` method ignores any supplied `id` (generates its own
UUID). The `updateContact` method takes `id` from URL params. Client-supplied `id` in the body is
silently discarded in both cases. Using separate schemas for create vs update would be cleaner.

**Previous review:** Not explicitly identified. New finding (minor).

### 17. `updateContact` returns void; inconsistent with `updateLabel`

**File:** `apps/api/src/lib/contacts/contacts.ts:165-190`
**File:** `apps/api/src/routes/contacts.ts:52-59`

`updateLabel` queries and returns the updated label. `updateContact` returns nothing. The PUT
response for contacts is an empty body. The PUT response for labels is the updated entity. This is
an API inconsistency.

**Previous review:** Not identified. New finding (minor).

### 18. Spread type cast in `getContactById` does not exclude `eigenId`

**File:** `apps/api/src/lib/contacts/contacts.ts:261`

```typescript
...data as Omit<Contact, 'id' | 'firstName' | 'lastName' | 'labels'>,
```

The cast does not exclude `eigenId`. If the JSON `data` blob contained an `eigenId` field, it would
overwrite the `eigenId` from line 260. The schema type for `data` excludes `eigenId`, but
`extractContactData` does not enforce this at runtime (it stores whatever `contactData` contains
minus only `labels`). Since the `Contact` type has `eigenId?: string` (optional), and
`extractContactData` builds the data object by explicitly listing fields (lines 33-40), `eigenId`
is actually not included in `data`. So this is a theoretical risk only -- the cast is overly broad
but no actual overwrite occurs.

**Previous review:** Correctly identified. Refined analysis: the current `extractContactData`
implementation explicitly lists fields and does not include `eigenId` in `data`, so this is
type-safety concern only, not a runtime bug.

### 19. No transaction wrapping for multi-step writes

**File:** `apps/api/src/lib/contacts/contacts.ts:136-147, 177-187`

`addContact` and `updateContact` each perform a write to `contacts` followed by
`setContactLabels` (which deletes then inserts into `contactsToLabels`). These are not wrapped in
a transaction. A failure between the contact write and the label write leaves the database
inconsistent. For local SQLite this is low-probability but still a correctness gap.

**Previous review:** Mentioned in the Robustness section. Elevated to a numbered minor issue for
completeness.

## Observations

- **Test coverage** (`apps/api/src/test/contacts.test.ts`): Good coverage of CRUD operations,
  cross-user isolation, ownerId spoofing, me endpoint, and self-delete prevention. Missing: avatar
  upload/download, label-contact associations via the API, path traversal, empty/invalid fields,
  error cases (invalid IDs), the `size()` method, and the `getMe()` null-return bug path.

- **Race condition protection in init:** `Contacts.init()` itself has no re-entrancy guard, but
  `Home.init()` (lines 54-61 of `home.ts`) uses `initializationStarted` + waiters pattern, so
  `init()` is only called once.

- **`enforceAvatarUpload` resolves quotas via the `'default'` mount:** At
  `apps/api/src/lib/config/enforcement.ts:46`, `resolveQuotas(userId, userId, 'default')` calls
  `home.drive.getMountConfig('default')`. This should work since `Home.init()` creates the default
  mount before contacts init, but the coupling is implicit and undocumented.

- **`size()` only counts avatar files:** The contacts `size()` method at line 109 sums avatar file
  sizes but does not include `contacts.db`. The database file could be significant for users with
  many contacts. The quota system (via `enforceAvatarUpload`) uses this method to check
  `mailAndContactsMax`, so the quota check slightly undercounts actual usage.

- **SSE events** (`sse-events.ts`): Clean implementation. Templates cover all six event types. The
  `as SSEvent` cast on the return type (lines 67, 79) works but could be replaced with explicit
  type annotations for better type safety.

- **`cleanupAvatarImages` uses loose `includes()` matching** (line 335): Checks
  `c.avatar?.includes(file)` where `file` is a bare filename like `{uuid}.webp` and `c.avatar` is
  a path like `contacts/{userId}/avatar/{uuid}.webp`. This works because filenames are UUID-based
  and unique, but the pattern is fragile. A direct comparison with `path.basename(c.avatar)` would
  be more robust.
