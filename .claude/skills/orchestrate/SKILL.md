# Orchestrate

How feature work runs here, each step sized by its measured cost and yield. Scale it to the job: a one-line fix needs none of it, a feature most, a program all. Reviewers are held to [REVIEW-STANDARD.md](../../../docs/REVIEW-STANDARD.md), code to [CODE-STANDARDS.md](../../../docs/CODE-STANDARDS.md). On measured programs every real defect came from the spec's design review, the browser pass, reviews of judgment-heavy units and the closing passes, while a third of the tokens went to onboarding, which is why the standards docs stay lean and a brief carries every exact value.

**Review at checkpoints, not after every step.** A unit gets its own cold review only when it touches a **risk seam**: an ACL check, a lock, a persisted format, a cross-home call, a parser or a route that serves untrusted bytes, a shared helper with callers outside the diff. Every other unit merges on its tests plus the orchestrator's read of the diff, and the next checkpoint covers it: every fourth or fifth unit, and the last.

**A cheap-wins round takes three seats.** A row qualifies only when its fix is obvious and small: no new route, stored format, mechanism or UI choice. Rows are often LLM-written, so a row's fix is a hint, not a spec, and the owner sees the triaged list before any dispatch. One implementer per task on its own commit, no per-task review, then one whole-branch review (step 8), one fix wave, one scoped re-review, one `bun run check`. A task on a lock, an ACL check, a persisted format or a cross-home seam keeps its own review.

**Models.** Every subagent is `subagent_type: "general-purpose"` on the cheapest model that can do the job, with effort set on every dispatch: `effort: "medium"` by default, reviewers, hunters and judgment-heavy implementers included, and `effort: "high"` only where medium has proved not to be enough. `model: "opus"` for implementers of an ordinary unit, researchers and every review that needs judgment: the design review, unit reviews, the whole-branch pass, the standards audit and the hunt (Opus beat Fable on all three closing passes at 2.5× less per token). `model: "sonnet"` for screenshots and comparing them, scripted browser passes, a fixed probe or mutation set, a pointer-drift check, reading a render, a scoped re-review of a small fix wave. `model: "haiku"` for collecting outputs, counting, a lookup across files. `model: "fable"` falsifies: once a root-cause or design hypothesis forms, or a plan, sequencing or set of rulings takes shape, sure or not, a Fable seat gets the raw evidence and the claim labeled unproven, argues against it and names alternatives before you present it as settled or the owner signs off. An architectural decision (a choice between designs, a redesign's shape, where a rule or fact lives) always goes to a Fable seat at `effort: "medium"` first, the owner's standing rule. Fable at `effort: "medium"` also writes an architecture plan and implements the hard units: a complex implementation, a cleanup, refactor or simplification, and a fix to code that already carries a pile of earlier fixes (the owner, 2026-11-12). Other Fable seats only when the judgment warrants the cost. A cold agent is a fresh dispatch, never a fork, which inherits the session's findings and rulings.

**Keep the orchestrator's context small.** It plans, briefs, rules and merges; reading, implementing, reviewing and verifying run in subagents. Never read large source files or subagent transcripts, but read [ARCHITECTURE.md](../../../docs/ARCHITECTURE.md) and CODE-STANDARDS.md before the first brief, or it names the wrong concept. Cap reports at about 800 words and keep the program state in a local `STATE.md` so a fresh session can resume. Past about 70% context, or whenever a clean one would help, tell the owner and hand over a resume prompt.

**Another session in the tree** (files you never touched in `git status`, several `claude` processes, `develop` moving under you): run no global check, never stash or revert its files, stage by path, re-read `git status` right before staging, and leave the full check to the owner once both are done. The PostToolUse `bun run lint:fix` hook formats the whole repo on every edit, so your edits touch its files too.

1. **Evidence first, sign-off before code.** An audit on real data (a gap matrix with measured counts), then a written spec with explicit decision points, signed off BEFORE implementing. Before the first dispatch, the best return per token of the run: one cold review of spec and plan, a pointer-drift check of every `file:line` the plan cites, and a check of every file location it names against ARCHITECTURE.md, since a plan naming the wrong layer overrides "read the siblings". A proposal in `docs/proposals/` names files and symbols, never line numbers, and an implementer verifies its claims. Local-only artifacts (specs, audits, screenshots, the ledger, `STATE.md`) live in gitignored `docs/superpowers/` and `.superpowers/`; never commit them, even when a skill says to. A ruling that changes the spec mid-program dispatches its code task at once: a spec line with no task is drift. Before proposing a ROADMAP row as next work, run `git log --oneline -i --grep=<keyword>` and grep `docs/superpowers/` and `.superpowers/`; if it is done, fix the stale row.
2. **Own branch per unit, mechanical ones batched.** Merge `--no-ff` to an integration branch once a unit is verified; `develop` gets it only after `bun run check` AND the browser pass (step 7) are green and the owner says where it lands; reviewed plus scoped tests is not verified. Never push without an explicit go. A chain of moves, renames or re-exports is ONE unit with one implementer and one review (three `git mv` units cost 700k tokens for two corrected doc lines). Units with disjoint files, and any parallel multi-file sweep, run in parallel worktrees, since the lint hook makes agents in one tree fight; commit dispatched output right away. Run everything independent in parallel; nothing waits on a lock or queue it doesn't need. Corpus byte gates take no lock (two or three fit in memory; an xlsx gate peaks near 6 GB), and a seat gates only the formats its change can reach. Only `bun run check` and the Docker suites run alone. `bun run check` runs once per wave for mechanical units and once per merge for the rest: it keeps every core busy for about four minutes, so a suite beside it flakes on timeouts, and its isolated API workers ([TESTING.md](../../../docs/TESTING.md)) fail a test that leans on an earlier file. Docker suites run one at a time (two can pick the same subnet), each its own timestamped background job, since a job dies at its two-hour cap and a slow chain gets cut off with a log that reads like a hang. `isolation: "worktree"` cuts from main as of session start, not HEAD: give a worktree agent absolute paths into the main checkout for this session's commits; it has no `node_modules` (`bun install --frozen-lockfile`), and its branch name is in the notification's `<worktree>` block. After merging a new dependency, `bun install` before `bun run check`. Git refuses a branch `x/y` while `x` exists.
3. **TDD, red first.** A failing test before the implementation, always. Tests pin the CONTRACT (full round-trips, output-level assertions), never library internals. A test green on its first run proves nothing until a deliberate mutation of the implementation makes it fail.
4. **Delegate with complete briefs.** A brief carries required reading (CODE-STANDARDS.md, the [source-file skill](../source-file/SKILL.md), 2–3 siblings in the target dir; not AGENTS.md or the owner's memory, which every Claude agent already has), exact file pointers, encodings and values, scoped test commands, and the hard rules: stay strictly in scope (a revert reproduces the exact prior state; check each diff against the plan's file list); report a bug found outside it, which the orchestrator dispatches in the same program unless AGENTS.md makes it a row; diagnose failures by reading source, never blind-retry; never `git push` or `git stash` (stashes are shared across worktrees); no new casts or `!`; stop every process it started (a vite, an API, a bench) before it reports, since a parallel run keeps the machine at load 25 to 50. It asks for every source-file step, 1 to 11 and Verify, on the whole of every non-test file touched, a one-line or comment-only edit included, with the skill's per-file table in the report; a brief that only names the skill gets headers and nothing else. A follow-up brief carries the same instruction. Never resume a large-context implementer for a few one-line residuals (a resume re-bills its context): dispatch a fresh small agent, and make a file-local nit (a comment, a log line, an import) yourself, since onboarding costs more than the edit; the next checkpoint covers it. Keep a ledger of every ruling made on the owner's behalf with its cost if wrong; the closing message lists them all. A product, UI, limit or stored-format choice goes to the owner as a plain question with a recommendation, and an LLM's answer (a Fable check included) is not the owner's ruling. Recommend the cleanest fix at the cause, never the cheaper patch, its cost beside it. A new API route or migration gets its own question right before the dispatch that builds it (AGENTS.md). A subagent's claim about code it did not write ("X does not exist" included) enters the ledger or plan only once verified in the code. Never dispatch UX-changing security hardening without asking, and check design intent (docs, tests) before adding a guard. Behavior from a mature upstream library (ProseMirror, Tiptap) is presumed deliberate: look up its purpose before calling it a bug, and a fix keeps it. Every persisted-format or runtime-state change gets a report line on what breaks for existing data; a brief never asks to keep an old name or shape working while CODE-STANDARDS § Code Philosophy forbids backward compatibility.
5. **Independent review before merge, sized to the risk.** A unit on a risk seam gets a cold reviewer that did NOT write it, held to the Review Standard; a mechanical or UI-only unit waits for the checkpoint. It asks spec compliance and quality (bugs, edge cases, absences, conventions); two reviewers when the contract is long enough that one would skim. Every cold brief also asks whether it is over-engineered, clean, consistent and "Eigen", with simpler alternatives at `file:line`, and, when setup, env or startup code changed, whether a fresh clone plus `bun run serve` still works. Every review brief says that clean is a result: a review that finds nothing real says so, and never invents or inflates a finding. A fix wave on a risk seam or past about two hundred lines gets a scoped re-review of its diff; the orchestrator reads a smaller one and any docs- or comment-only fix under ten lines. A reviewer's "simplifying" removal is proven in the running app first (dropping y-websocket's `resyncInterval` broke idle tabs). **Rule on a finding at its cause**: a fix that adds a mechanism (a cache, memo, queue, cap, counter, flag, retry, fallback or second code path) treats a symptom, so change the design choice behind it or ask the owner with the root-cause option first; a reviewer's suggested fix is a hint, not a spec. When a second finding in one module needs a mechanism, redesign the module (one redesign deleted about 1,300 lines four fix waves had added). A rare edge case is accepted per CODE-STANDARDS, and the ledger names it.
6. **Standards audit at checkpoints and before merge.** A cold reviewer briefed with nothing but CODE-STANDARDS.md, ARCHITECTURE.md and the Review Standard grades every touched non-test file better / neutral / worse, a finding per slip: comments, philosophy (single-use helpers, test-only options, casts, `interface`, a second source of truth), layering (thin routes, logic and types in the layer ARCHITECTURE names, shared handlers reused) and broken windows left behind, pre-existing slop in a touched file included. It asks whether every touched file meets the written bar, not whether the code is right; "worse" or "neutral with findings" blocks the merge. Run it at every checkpoint, the first included, and over the whole branch at the close, never per unit: drift such as one fact spelled in two units' files only shows across units. `bun scripts/check-standards.ts` gates the mechanical half.
7. **Real-world verification is mandatory, before the whole-branch reviews.** Dispatch it the moment the last UI unit merges: drive the running dev app headless against REAL documents with a throwaway test user and read the screenshots; verdicts come from pixels plus behavioral probes (scroll, click, reload-persistence), not data-shape assertions. It finds user-facing bugs many review rounds cleared, and replaces the frontend half of step 8. Cover every storage backend the feature touches from the first pass (a local MinIO for S3: `scripts/s3-local/`), because the suite's fakes never preflight CORS, idle a queue or surface a real client's error shape. Data pipelines verify as closed round-trips with feature counts; files for external software (xlsx, ics, eml, tar, …) are spot-opened in the real consumer. A byte-identical pixel gate is only for render-path changes. The verification agent reports facts; the orchestrator rules. Recipe: the [verify-in-browser skill](../verify-in-browser/SKILL.md).
8. **One closing fan-out, then one fix wave.** After the last unit and the browser pass, dispatch in parallel: the whole-branch review of backend seams and locks (Opus, also triaging the ledger's deferred minors), the correctness review, the step 6 audit (Opus), the two step 9 hunters (Opus), the step 10 efficiency (Sonnet) and simplicity (Opus) seats, and the step 11 docs claim check (Sonnet). Every finding ruled for a fix goes into ONE fix wave, split by area into two small parallel implementers, which also runs the source-file skill over every non-test file the branch touched, with its table. This closing fix wave always gets one scoped re-review of its diff (a per-unit fix wave follows step 5). Then stop: a re-review finding that can crash or block the server, lose data or leak access gets a small fix the orchestrator reads, and everything else becomes a SHEETS-TODO or ROADMAP row, never another wave. The program's aim is the simplification, not a branch with nothing left to find (the owner, 2026-11-11). Never run these passes as sequential rounds: they found the same findings at three times the cost. Each fix wave reports the net lines of the modules it touched; one that grows a module more than its fixes need gets a simplicity read before the next.
9. **Cold adversarial hunt, in the fan-out.** Two fresh Opus agents, independently, with only the repo, the branch, the ops doc and one sentence: "something in this mechanism is broken; find it". No narrative, findings or rulings: a reviewer told a bug exists searches instead of grading, and one found a cross-home path traversal after some thirty ordinary passes. Scope it to the one riskiest mechanism; after steps 1, 5, 7 and 8 its yield is low, so a clean result is assurance. Its findings are ruled like any other: a rare interleaving that can't crash, block, lose data or leak access is accepted, the rest join the fix wave.
10. **Simplify inside the fan-out.** Only the efficiency angle runs as a closing seat; reuse, simplification and altitude overlap about 80% with the standards audit. The orchestrator's own read of the accretion spots (an options bag, a labels prop, a flag threaded through layers) comes first. An efficiency finding adds no mechanism without a measurement at a real size. One simplicity seat reads each new module whole, not its diff: what is the simplest design that keeps this rule, and what can be deleted? Apply what's worth it in the fix wave and re-gate with the same tests.
11. **Docs in the same cycle**, via the [domain-doc skill](../domain-doc/SKILL.md): the domain doc and any status or backlog, before the work is done; a docs unit gets its own cold review of every claim against the code. A change a user sees also corrects the affected articles under `apps/index/src/data/support/`, minimally, via the [support-article skill](../support-article/SKILL.md) and [SUPPORT-STYLE-GUIDE.md](../../../docs/SUPPORT-STYLE-GUIDE.md); nothing type-checks an article.
12. **Design changes go in small rounds.** One or two visual changes at a time, screenshots first, a human verdict before merge. "Like X does it" means copy X's choices (icon, component, label, interaction); build the match first and flag a better idea separately, never substitute silently. Default to subtle, such as `color-mix(in oklab, X 14%, var(--background))` over a Tailwind -100 tint and small padding and type tweaks; a big move (background tokens, a component swap, tinted icon tiles) needs its own go.
