# Orchestrate

How feature work runs in this repo, with every step's cost and yield measured on real programs. Scale it to the job: a one-line fix needs none of this, a feature needs most of it, a program of changes needs all of it. Reviewers are held to [REVIEW-STANDARD.md](../../../docs/REVIEW-STANDARD.md); code style is [CODE-STANDARDS.md](../../../docs/CODE-STANDARDS.md).

**Where the tokens go, and where the bugs are.** On the vCard program six rounds found every real defect for about 1M tokens: the cold design review of the spec (177k: a Node `Buffer` in the browser bundle, a wrong quota assumption, a prop shape that would have failed its own pixel gate), the browser verification pass (457k: three user-facing bugs nine review rounds had missed), three per-unit reviews of judgment-heavy units, and the backend whole-branch pass. A third of the total went to onboarding: every agent reads the standards docs and two or three siblings before it starts. The rest was ceremony around mechanical units.

**Review at checkpoints, not after every step.** On the file-subject program (about forty-five agent seats over fourteen units and fix waves) the design review, the per-unit reviews of the judgment-heavy units, the owner's browser round and the closing passes found every real bug; eight scoped re-reviews of fix waves found two regressions and otherwise nits, and running the closing passes as sequential rounds, each with its own fix wave and re-review, cost about a third of the program for what one parallel fan-out finds. So a unit gets its own cold review only when it touches a **risk seam**: an ACL check, a lock, a persisted format, a cross-home call, a parser or a route that serves untrusted bytes, a shared helper with callers outside the diff. Every other unit merges on its tests plus the orchestrator reading the diff, and the next checkpoint covers it. A checkpoint is every fourth or fifth unit, or the last one.

**A cheap-wins round scales it down to three seats.** A batch of small, independent broken-window fixes (the ROADMAP § Cheap wins rows) gets one implementer per task on its own commit, no per-task review loop, then one whole-branch review (step 8), one fix wave, one scoped re-review, one `bun run check`. The per-task loop on one round cost seventeen sequential agent seats for four tasks and found only comment length and test hygiene; the one bug that mattered, a fourth gate the fix never reached, came from the whole-branch review. Keep the per-task review only for a task that touches a lock, an ACL check, a persisted format or a cross-home seam.

**Models.** Every subagent is `subagent_type: "general-purpose"` with `model: "opus"`: implementers, researchers and browser verification. The design review, the judgment-heavy unit reviews and the backend whole-branch pass go to the most capable model: Fable on a Fable main session; on an Opus main session they may run on Opus. Fable (`model: "fable"`) is for the one closing adversarial hunt per branch (step 9) and for falsifying a theory: once a root-cause or design hypothesis forms, send a Fable agent the raw evidence and the hypothesis labeled unproven, ask it to falsify it and name alternatives, and don't present the theory as settled before it returns. The same goes for the orchestrator's own decisions, sure or not: once a plan, a sequencing or a set of rulings takes shape, a Fable seat gets the decisions and the evidence and argues against them before the owner signs off. Other Fable seats only when the judgment warrants the cost; a unit expected clean returned "clean" three times for 265k tokens on the most capable model. A cold agent is a fresh dispatch, never a fork: a fork inherits the session's findings and rulings.

**Keep the orchestrator's context small.** It plans, briefs, rules and merges; reading, implementing, reviewing and verifying each run in their own subagent. Never read large source files or subagent transcripts yourself, cap reports at about 800 words, and keep the program state in a local `STATE.md` so a fresh session can resume. Past about 70% context, or whenever a clean context would help, tell the owner and hand over a resume prompt.

**Another session in the tree.** Files you never touched in `git status`, several `claude` processes, or main moving under you mean another session is working. Then run no global check, never stash or revert its files, stage by path only, re-read `git status` right before staging, and leave the full check to the owner once both are done. The PostToolUse `bun run lint:fix` hook formats the whole repo on every edit, so your edits touch its files too.

1. **Evidence first, spec sign-off before code.** Start with an audit on real data (a gap matrix with measured counts, not assumptions), then a written spec with explicit decision points, and get sign-off BEFORE implementing. Before the first dispatch run one cold review of the spec and plan, a cheap pointer-drift check of every `file:line` the plan cites against the current code, and a check of every file location it names against [ARCHITECTURE.md](../../../docs/ARCHITECTURE.md), because a plan that names the wrong layer overrides "read the siblings"; these are the best return per token of the whole run. Local-only artifacts (specs, audits, screenshots, the ledger, `STATE.md`) live in gitignored `docs/superpowers/` and `.superpowers/`; never commit them, even when a skill says to. A ruling that changes the spec mid-program dispatches its code task in the same breath: a spec line with no task behind it is drift, and only the final whole-branch review will notice.
2. **Own branch per unit of work, but batch the mechanical ones.** Merge `--no-ff` to an integration branch when the unit is verified. Main gets it only after `bun run check` AND the browser pass (step 7) are green and the owner has said where it lands; reviewed plus scoped tests is not verified. Never push without an explicit go. A chain of moves, renames or re-exports is ONE unit with one implementer and one review: three `git mv` units with their own reviews and re-reviews cost 700k tokens for two corrected doc lines. Units with disjoint files run in parallel worktrees, and so does any parallel multi-file sweep, since the lint hook makes agents in one tree fight; commit dispatched output right away. The full `bun run check` runs once per wave for mechanical units and once per merge for the rest, alone, because two suites on one machine produce timeout flakes that look like regressions. `isolation: "worktree"` cuts from main as of session start, not HEAD, so give a worktree agent absolute paths into the main checkout for anything committed this session; a worktree has no `node_modules` (`bun install --frozen-lockfile` is fast), and the real branch name is in the notification's `<worktree>` block.
3. **TDD, red first.** A failing test before the implementation, always. Tests pin the CONTRACT (full round-trips, output-level assertions), never library internals; they are the committed regression net. A test that went green on the first run proves nothing until a deliberate mutation of the implementation makes it fail.
4. **Delegate with complete briefs.** Every brief carries: required reading ([CODE-STANDARDS.md](../../../docs/CODE-STANDARDS.md) + 2–3 sibling files in the target dir; AGENTS.md and the owner's memory are already in every Claude agent's context, so naming them loads them twice), exact file pointers and encodings, scoped test commands, and the hard rules: stay strictly in scope (a revert reproduces the exact prior state; check each diff against the plan's file list), diagnose failures by reading source (never blind-retry), never `git push`, never `git stash` (stashes are shared across worktrees). Onboarding is the largest single cost, so the standards doc stays lean and the brief carries every exact value. Never resume an implementer that holds a large context for a handful of one-line residuals: a resume re-bills the whole context (300k tokens for five one-liners); dispatch a fresh small agent with only the residuals. Keep a ledger of every ruling made on the owner's behalf, with what it costs if wrong; the closing message lists them all. A subagent's claim about code it did not write, an explorer's "X does not exist" included, enters the ledger or the plan only after someone verified it in the code. Never dispatch UX-changing security hardening without asking, and check design intent (docs and tests) before adding any guard.
5. **Independent review before merge, sized to the risk.** A cold reviewer that did NOT write the code, held to the Review Standard, for a unit on a risk seam; a mechanical or UI-only unit waits for the checkpoint. Two questions, spec compliance and quality (bugs, edge cases, absences, conventions); one reviewer for a small unit, two for a unit whose contract is long enough that one would skim it. Every cold brief also asks for an opinion: is this over-engineered, is it clean, consistent and "Eigen", with simpler alternatives at `file:line`; when setup, env or startup code changed, does a fresh clone plus `bun run serve` still work. A fix wave on a risk seam, or one past about two hundred lines, ends with a scoped re-review of the fix diff only: fixes bring regressions of their own, and the scoped pass has caught a leading menu separator and a test that did not exercise its fix. A smaller fix wave, and any docs- or comment-only fix under ten lines, is read by the orchestrator.
6. **Standards audit at checkpoints and before merge.** A cold reviewer briefed with nothing but [CODE-STANDARDS.md](../../../docs/CODE-STANDARDS.md), [ARCHITECTURE.md](../../../docs/ARCHITECTURE.md) and the Review Standard grades every touched non-test file better / neutral / worse, with a finding per slip: comments (why only, one line, neighbor density, pre-existing slop in a touched file), philosophy (no single-use helpers, no test-only options on production signatures, no casts, `type` over `interface`, one source of truth), layering (thin routes, logic and types in the layer ARCHITECTURE names, shared handlers reused), and broken windows left behind. It asks not "is this right" but "does every touched file now meet the written bar". A "worse" or "neutral with findings" blocks the merge until fixed. Run it at every checkpoint, the first included, and over the whole branch in the closing fan-out, never per unit: per-unit audits mostly re-litigate helper extraction, while the real drift (a fact spelled in two files by two units, a module the plan itself put in the wrong layer) only shows across units. `bun scripts/check-standards.ts` in `bun run check` gates the mechanical half for free.
7. **Real-world verification is mandatory, and it runs before the whole-branch reviews.** Drive the running dev app headless against REAL documents with a throwaway test user, and read the screenshots: verdicts come from pixels plus behavioral probes (scroll, click, reload-persistence), not from data-shape assertions alone. Dispatch it the moment the last UI unit merges: on the vCard program it found the three user-facing bugs (a `data:` avatar prefixed with the API host, an SSE burst tripping the rate limiter in a second tab, a live button on an over-cap file) that nine review rounds had cleared, and it replaces the frontend half of step 8. Cover every storage backend the feature touches from the first pass (a local MinIO for S3, see `scripts/s3-local/`), because the API suite's fakes never preflight a CORS request, never idle a queue, and never surface a real client's error shape. Data pipelines verify as closed round-trips with feature counts; files consumed by external software (xlsx, ics, eml, tar, …) get spot-opened in the real consumer. A byte-identical pixel gate is only for render-path changes (rules in the skill below). The verification agent reports facts; the orchestrator rules on them. Recipe: the [verify-in-browser skill](../verify-in-browser/SKILL.md).
8. **One closing fan-out, then one fix wave.** After the last unit and the browser pass, dispatch together, in parallel: the whole-branch review of the backend seams and locks, the four simplify angles (reuse, simplification, efficiency, altitude), the correctness review, the standards audit of step 6, the adversarial hunt of step 9 on the riskiest mechanism, and the docs claim-by-claim check of step 11; each gets the ledger's deferred minors to triage. All findings go into ONE fix wave, split by area into two small parallel implementers rather than one large one; the orchestrator reads that wave, and residuals surface to the owner. Do not run these as rounds: on the file-subject program the same six real findings came from passes run one after another, each with its own fix wave and re-review, at three times the cost. Per-unit reviews catch local issues; this pass catches cross-cutting drift, a spec ruling nobody implemented, and a ledger entry that was never true.
9. **Cold adversarial hunt, as part of the fan-out.** On every branch that gets a closing fan-out, dispatch a fresh Fable agent with no context beyond the repo, the branch, the ops doc and one sentence: "something in this mechanism is broken; find it". No narrative, no findings history, no rulings. A reviewer told that a bug exists searches instead of grading. This has found a cross-home path traversal and a crash-recovery hole after some thirty ordinary review passes had cleared the same code; on a branch that already went through steps 1, 5, 7 and 8 its expected yield is low, so scope it to the one riskiest mechanism and treat a clean result as the assurance it is. Its findings join the closing fix wave.
10. **Simplify inside the fan-out.** The four angles run as four of the closing reviewers; apply what's worth it in the same fix wave and re-gate with the same tests. The orchestrator's own critical read of the accretion spots (an options bag, a labels prop, a flag threaded through layers) comes first: on the file-subject program that read removed more than the four agents did.
11. **Docs in the same cycle.** Update the domain doc and any status/backlog before calling the work done, via the [domain-doc skill](../domain-doc/SKILL.md). A docs unit gets its own cold review that checks every claim against the code. If the work changed anything a user sees, the help center is docs too: correct the affected articles under `apps/index/src/data/support/` in the same cycle, minimally, via the [support-article skill](../support-article/SKILL.md) and [SUPPORT-STYLE-GUIDE.md](../../../docs/SUPPORT-STYLE-GUIDE.md). Nothing type-checks an article, so this drift is silent.
12. **Design changes go in small rounds.** One or two visual changes at a time, screenshots first, a human verdict before merge.
