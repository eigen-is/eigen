# Orchestrate

How feature work runs here. Scale it to the job: a one-line fix needs none of it, a feature most, a program all. Every agent loads AGENTS.md; a brief names [REVIEW-STANDARD.md](../../../docs/REVIEW-STANDARD.md) and [CODE-STANDARDS.md](../../../docs/CODE-STANDARDS.md), which hold the rest of the rules, so this skill adds only what an orchestrator does. Onboarding took a third of the tokens on measured programs, so a brief carries every exact value.

**Models.** Every subagent is `subagent_type: "general-purpose"` with `model` and `effort` set on each dispatch. Effort is `medium`, and `high` only where medium has proved too little. Pick the cheapest model that can do the job:

- `opus`: implementers, researchers, every review that needs judgment (spec and plan, units, the whole branch, the standards audit, simplicity, the hunt) and second opinions. Opus beat Fable on all three closing passes at 2.5× less per token.
- `sonnet`: screenshots and comparing them, scripted browser passes, a fixed probe or mutation set, a pointer-drift check, reading a render, the efficiency seat, the docs claim check.
- `haiku`: collecting outputs, counting, a lookup across files.
- `fable`: three seats only. The second opinion on a choice between designs the owner is asked to make, one seat per choice. The fix at the root of a mechanism about to take its third patch ([REVIEW-STANDARD.md § A patch is a finding](../../../docs/REVIEW-STANDARD.md)). A unit the owner names for Fable. When Fable is out of budget, the same seat runs on Opus, with a ledger line and no question.

**Second opinion.** Before you present a root cause, a design or a plan as settled, or the owner signs off on it, one fresh seat gets the raw evidence with the claim labeled unproven, argues against it and names alternatives. One Opus seat per claim a unit builds on or the owner decides, not per passing hypothesis; step 1's cold review is the plan's. Only a choice between designs put to the owner goes to Fable (Models). A cold seat is a fresh dispatch, never a fork, which inherits the session's findings and rulings. An LLM's answer is never the owner's ruling.

**Keep your context small.** You plan, brief, rule and merge; subagents read, implement, review and verify. Read [ARCHITECTURE.md](../../../docs/ARCHITECTURE.md) and CODE-STANDARDS.md before the first brief, or it names the wrong concept, but never large source files or transcripts. Reports cap at about 800 words. Program state lives in a local `STATE.md` so a fresh session can resume; past about 70% context, hand the owner a resume prompt. The PostToolUse `bun run lint:fix` hook formats the whole repo on every edit, so with another session in the tree your edits touch its files too: never revert them, and re-read `git status` right before staging.

**Review at checkpoints.** A unit gets its own cold review only on a **risk seam**: an ACL check, a lock, a persisted format, a cross-home call, a parser or a route that serves untrusted bytes, a shared helper with callers outside the diff. Other units merge on their tests plus your read of the diff, and a checkpoint covers them: every fourth or fifth unit, and the last.

**A cheap-wins round** takes only rows whose fix is obvious and small: no new route, stored format, mechanism or UI choice. Rows are often LLM-written, so a row's fix is a hint, and the owner sees the triaged list before any dispatch. One implementer per task on its own commit, then one whole-branch review, one fix wave, one scoped re-review and one `bun run check`. A task on a risk seam keeps its own review.

1. **Evidence first, sign-off before code.** An audit on real data (a gap matrix with measured counts), then a spec with explicit decision points, signed off before implementing. Before the first dispatch, the best return per token of the run: one cold review of spec and plan, a pointer-drift check of every `file:line` the plan cites, and a check of every location it names against ARCHITECTURE.md, since a plan naming the wrong layer overrides "read the siblings". A proposal in `docs/proposals/` names files and symbols, never line numbers, and an implementer verifies its claims. Specs, audits, screenshots, the ledger and `STATE.md` live in gitignored `docs/superpowers/` and `.superpowers/`, never committed, even when a skill says to. A ruling that changes the spec dispatches its code task at once. Before proposing a ROADMAP row as next work, run `git log --oneline -i --grep=<keyword>` and grep both folders; a row that is done gets fixed.
2. **A branch per unit, mechanical ones batched.** Merge `--no-ff` to an integration branch once a unit is verified; `develop` gets it only after `bun run check` and the browser pass are green and the owner says where it lands. Reviewed plus scoped tests is not verified. A chain of moves, renames or re-exports is one unit with one implementer and one review (three `git mv` units cost 700k tokens for two corrected doc lines). Disjoint units and parallel multi-file sweeps run in their own worktrees, since the lint hook makes agents in one tree fight; commit dispatched output right away. Run everything independent in parallel:
   - Corpus byte gates take no lock (two or three fit in memory; an xlsx gate peaks near 6 GB), and a seat gates only the formats its change can reach.
   - `bun run check` runs once per wave for mechanical units and once per merge for the rest. Other work may run beside it, but never a second check at the same moment: two fill every core and both flake. A timing test that fails under that load and passes alone is a flake: rerun its workspace.
   - Docker suites run one at a time (two can pick the same subnet), each as its own timestamped background job: a job dies at its two-hour cap with a log that reads like a hang.
   - `isolation: "worktree"` cuts from main as of session start, not HEAD, so give the agent absolute paths into the main checkout for this session's commits. It has no `node_modules` (`bun install --frozen-lockfile`), and its branch is in the notification's `<worktree>` block.
   - After merging a new dependency, `bun install` before `bun run check`. Git refuses a branch `x/y` while `x` exists.
3. **TDD, red first.** A failing test before the implementation. Tests pin the contract (full round-trips, output-level assertions), never library internals. A test green on its first run proves nothing until a mutation of the implementation makes it fail.
4. **Complete briefs.** A brief carries the required reading (CODE-STANDARDS.md, the [source-file skill](../source-file/SKILL.md), 2–3 siblings in the target dir; not AGENTS.md, which every agent has), exact file pointers, encodings and values, and scoped test commands. It asks for the source-file skill on the whole of every non-test file touched, with the skill's per-file table in the report; a brief that only names the skill gets headers and nothing else. A follow-up brief says so too. Its hard rules: stay in scope (a revert reproduces the exact prior state), diagnose a failure from the source, never by blind retry, and no new `!`. Check each diff against the plan's file list. Never resume a large-context implementer for one-line residuals (a resume re-bills its context): dispatch a fresh small agent, or make a file-local nit yourself. A subagent's claim about code it did not write ("X does not exist" included) enters the plan only once verified in the code. Every persisted-format or runtime-state change reports what breaks for existing data.
5. **Review and rule, sized to the risk.** A unit on a risk seam gets a cold reviewer, briefed with REVIEW-STANDARD.md, that did not write it; two when the contract is long enough that one would skim. The brief asks for spec compliance, bugs, edge cases and absences, whether it is over-engineered or un-Eigen, with simpler alternatives at `file:line`, and, when setup, env or startup code changed, whether a fresh clone plus `bun run serve` still works. A fix wave on a risk seam or past about two hundred lines gets a scoped re-review of its diff; you read a smaller one. A reviewer's "simplifying" removal is proven in the running app first (dropping y-websocket's `resyncInterval` broke idle tabs). Keep a ledger of every ruling made on the owner's behalf with its cost if wrong, and list them all at the close. A product, UI, limit or stored-format choice goes to the owner as a plain question with a recommendation. Recommend the cleanest fix at the cause, never the cheaper patch, its cost beside it. A reviewer's fix is a hint, not a spec. When a second finding in one module needs a mechanism, redesign the module (one redesign deleted about 1,300 lines that four fix waves had added). Behavior from a mature upstream library (ProseMirror, Tiptap) is presumed deliberate: look up its purpose first, and a fix keeps it. Never dispatch UX-changing security hardening without asking.
6. **Standards audit at every checkpoint and at the close.** A cold reviewer briefed with nothing but CODE-STANDARDS.md, ARCHITECTURE.md and the Review Standard grades every touched non-test file better, neutral or worse, with a finding per slip: comments, philosophy, layering and broken windows, pre-existing slop in a touched file included. It asks whether each file meets the written bar, not whether the code is right; "worse" or "neutral with findings" blocks the merge. Never per unit: one fact spelled in two units' files only shows across units. `bun scripts/check-standards.ts` gates the mechanical half.
7. **Real-world verification is mandatory, before the closing fan-out.** Dispatch it the moment the last UI unit merges, by the [verify-in-browser skill](../verify-in-browser/SKILL.md). It replaces the frontend half of the closing review. The agent reports facts; you rule.
8. **One closing fan-out, one fix wave, one re-review.** After the last unit and the browser pass, dispatch in parallel: the whole-branch review of backend seams and locks (also triaging the ledger's deferred minors), the correctness review, the step 6 audit, the two step 9 hunters, the step 10 efficiency and simplicity seats, and a cold check of every docs claim against the code. Never as sequential rounds: those found the same findings at three times the cost.
   - **The fix bar.** A finding is fixed only when it prevents data loss, a security hole or a crash, makes the code smaller, or is a visible UX polish the owner would want. One whose fix only makes a message or a check more precise is accepted, with no row: the program shrinks code and roadmap alike.
   - **One fix wave** takes every finding over the bar, split by area into two small parallel implementers, which also run the source-file skill over every non-test file the branch touched and re-gate with the same tests. It reports the net lines of the modules it touched; a module that grew more than its fixes need gets a simplicity read.
   - **One scoped re-review** of that wave's diff, then stop. A re-review finding that can crash or block the server, lose data or leak access gets a small fix you read; one over the fix bar becomes a SHEETS-TODO or ROADMAP row; the rest is accepted. Never another wave: the aim is the simplification, not a branch with nothing left to find.
9. **Cold adversarial hunt, in the fan-out.** Two fresh agents, independently, with only the repo, the branch, the ops doc and one sentence: "something in this mechanism is broken; find it". No narrative, findings or rulings: a reviewer told a bug exists searches instead of grading, and one found a cross-home path traversal after some thirty ordinary passes. Scope it to the riskiest mechanism. After steps 1, 5 and 7 its yield is low, so a clean result is assurance.
10. **Simplify inside the fan-out.** Two closing seats, efficiency and simplicity; reuse and altitude get none, since they overlap about 80% with the standards audit. Your own read of the accretion spots (an options bag, a labels prop, a flag threaded through layers) comes first. An efficiency finding adds no mechanism without a measurement at a real size. The simplicity seat reads each new module whole, not its diff: what is the simplest design that keeps this rule, and what can be deleted?
11. **Docs in the same cycle**, per AGENTS.md § Done means; a docs unit gets a cold review of every claim against the code.
12. **Design changes go in small rounds.** One or two visual changes at a time, screenshots first, a human verdict before merge. "Like X does it" means copy X's choices (icon, component, label, interaction); build the match first and flag a better idea separately, never substitute silently. Default to subtle, such as `color-mix(in oklab, X 14%, var(--background))` over a Tailwind -100 tint and small padding and type tweaks; a big move (background tokens, a component swap, tinted icon tiles) needs its own go.
