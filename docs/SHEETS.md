# Sheets

> **TLDR:** Sheets is Eigen's spreadsheet: a workbook of tabs that several people edit at once, with formulas, number formats, validation and xlsx import and export. The grid, its state and the formula engine are `packages/sheet` (`@workspace/sheet`), our own fork of the open-source fortune-sheet, itself based on luckysheet. `apps/sheets/` is the app around it. A workbook is stored as a snapshot plus a log of edits.

A workbook is a `.eigensheets` file. It holds one or more sheets, the tabs. A sheet is a grid of cells. A cell holds its value (`v`), the string the grid shows (`m`), its formula (`f`), its number format, its style and its link. What belongs to a grid position rather than to the cell, such as borders and merges, sits in maps beside the grid, keyed `"r_c"` (row and column, counted from 0). Row heights and column widths are keyed by the row or column index alone. The maps under a sheet's `config` (merges, borders, row and column sizes, hidden rows and columns) are its config collections. Rules that cover ranges hang off the sheet with those ranges: conditional formats and validation rules. Floating images and charts hang off the sheet too.

In the browser the fork keeps the whole workbook as one plain object, the context, and changes it only through immer. An edit is a recipe, a function that changes a draft of the context, and immer reports the change as patches: small records of a path and a value.

A workbook is a collab document ([COLLAB.md](COLLAB.md)), but its Yjs document holds no Yjs grid. It has two roots: `state`, a map whose `snapshot` key holds the whole workbook encoded as one value, and `ops`, a Yjs array of op batches. An op is an immer patch in a form a peer can apply, and a batch holds the ops of one edit. So an edit travels like this. The recipe runs on the local context, its patches become one batch, the batch is pushed onto `ops`, Yjs carries it to the other browsers, and each applies it to its own context. A browser that opens the workbook decodes the snapshot and replays the batches on top. Yjs gives every copy of the array the same order, and every tab applies the batches in that order, so every tab ends as a browser that opens the workbook fresh. No tab writes the snapshot. When the workbook closes, a minute after its last tab left, the server folds the head of the log into a fresh snapshot.

The op log is the idea the design rests on. Writing the whole snapshot on every edit would make the last writer win for the whole workbook, while two ops on different cells merge cleanly, and two ops on one cell end with the later one in the log.

The server reads workbooks for export, the Drive preview and the search index. `packages/sheet/src/engine/` is the half without the DOM, and the API imports it: the formula parser and evaluator, the op replay and recalc, the pass that recomputes formula values. So the browser and the server read a workbook and compute a formula with the same code.

The sections run from storage (ops, their order, config collections, borders, the snapshot codec, the compaction, undo) through the engine and formulas to the painted glyphs, comments and export. Five things in them surprise people:

- A peer's batch can land in the log before batches a tab already applied, and the tab then applies the log again from an earlier state, which empties its undo ([§ Every tab applies the batches in the log's order](#every-tab-applies-the-batches-in-the-logs-order)).
- A sheet's config collections always exist, because creating one ships it whole ([§ Creating a collection ships it whole](#creating-a-collection-ships-it-whole-so-every-collection-exists)).
- The snapshot moves only through one codec ([§ The snapshot is interned](#the-snapshot-is-interned-and-written-only-through-the-codec)).
- Undo is per tab. A peer's batch ends your newest row, column or sheet step, or a paste that grew the grid, and everything below it, and an undo skips a cell a peer changed since ([§ Undo is per tab, and a peer's batch ends your structural steps](#undo-is-per-tab-and-a-peers-batch-ends-your-structural-steps)).
- An edit carries the formula values it computed, but a sheet, row or column op carries none, so every reader recomputes after one ([§ The editor computes on write](#the-editor-computes-on-write-the-server-only-what-nobody-computed), [§ A sheet, row or column op recomputes on every reader](#a-sheet-row-or-column-op-recomputes-on-every-reader)).

## `packages/sheet` is a fork we own

The whole upstream library (UI components, state runtime, formula parser) lives in `packages/sheet/`, with no external fortune-sheet dependency. `src/engine/` is the DOM-free half the server imports, `src/state/` the workbook context and its immer reducers, `src/components/` the React UI. How the canvas and the DOM overlays stack is in [RENDERING.md](../packages/sheet/RENDERING.md).

We own the code, so sheet code you touch gets simplified and its broken windows fixed, in small steps a reviewer can follow. A sheet dialog draws its own `FormDialog`, as `ResizeDialog` and `CustomSort` do, and opens through the sheet's `useDialog` into the one slot `ModalProvider` holds. The link dialog does too: Insert link and the link card's pencil mark `ctx.linkCard` editing, and the card opens `LinkEditDialog` in the slot in its own place. When a dialog closes, the focus goes back to the grid's cell input, since a sheet dialog has no trigger for Radix to return it to. Three in the slot stay outside `FormDialogForm`: the range picker (`CellRangeDialog`), which is non-modal so the grid stays usable to pick on, and gets a shell the slot draws; `ManageRules`, a `FormDialog` shell around a list of rules; and the notice (`showNotice`), a `FormDialog` shell with nothing to submit. The filter popover is no dialog in the slot: it opens at its column's header button. The slot exposes `pickerOpen`, read from what it holds, which the cell editor and the link card read, and a picker's Cancel or Escape opens its opener's dialog again. A bespoke positioned card-dialog moves to `FormDialog` when someone touches it, while hover popovers and toolbars may stay positioned. The link card is a Radix popover on an anchor in its cell's overlay region, so it follows a scroll and flips or shifts to stay inside the cell area; it is keyed by its cell, because Radix places a card again only for a new anchor element. The validation card hangs the same way, and both hang from `CellAnchor`, a box over the cell's whole rectangle: Radix's `hideWhenDetached` counts an anchor with no width at the cell area's left edge as clipped, which hid every card in column A. A benchmark runs with immer's `autoFreeze` on, as the app does: turning it off misstates what an edit costs. The op batch is the exception: `applySheetsBatch` applies a batch's patches through an `Immer` of its own with `autoFreeze` off, since it copies what it changes and nothing reads its sheets as frozen. Freezing every sheet after each batch cost a long replay a fifth of its time, and the editor's recipe freezes what it takes in anyway.

## An edit is an op in a Y.Array

`use-sheet.ts` (`apps/sheets/src/components/sheets/hooks/`) pushes each local batch to `ops`. A peer applies it with `applyOp()` (`components/Workbook/api.ts`), which patches the context in place. The Workbook mounts once and loads its sheets in its `useState` initializer, so the grid holds them from its first render. `useSheet` remembers the snapshot and the batches those sheets hold, and an effect catches the mounted grid up with what arrived meanwhile: while the doc still starts with that snapshot and those batches, it applies the batches after them, and after any other change it loads the doc again ([§ A new snapshot loads into the mounted grid](#a-new-snapshot-loads-into-the-mounted-grid)).

A tab applies its own batch at once and a peer's when it arrives, which is not always the order the log holds; [§ Every tab applies the batches in the log's order](#every-tab-applies-the-batches-in-the-logs-order) says how a tab ends as the log says anyway.

A tab rename is one op, `renameSheet`, as a row insert is one marker. Every reader runs it through the engine (`applySheetRename` in `engine/sheet-name.ts`), which rewrites the text naming the sheet on every sheet it holds: formulas, formula rules, list sources and links (`renameSheetTexts`). Writing those cells instead would ship them whole, and land at stale rows after a peer's row op. A chart ref names its sheet by id and needs nothing. A rewritten reference reads the same cell, so its value stays, and the recompute after a rename reaches a formula that named the new name and read no sheet until now ([§ A sheet, row or column op recomputes on every reader](#a-sheet-row-or-column-op-recomputes-on-every-reader)). A name `isSheetName` (`engine/a1-notation.ts`) refuses fails its whole batch, since one long name would be written into every formula naming the tab. Of two renames to one name, the later in the log fails on every reader, since a delete or rename of one namesake would break or repoint the formulas reading the other. Of two adds of one name, such as two tabs pressing + at once, the later takes the next free name, such as `Sheet4 (2)`, by the rule an import names its sheets by (`legalSheetNames` in `applySheetsBatch`), so nothing its author typed is lost. A formula that named it by its first name reads the earlier sheet, on every reader alike.

A joiner decodes the snapshot and replays the pending ops through `replaySheetsOps` (`engine/replay-ops.ts`). The API's document reader calls the same function, so every consumer agrees on what snapshot plus ops means. Every op names its sheet by id, so the snapshot decoder refuses a sheet with no id or a taken one as corrupt (`decodeSheetsWorkbook` in `packages/lib/src/sheets/snapshot-codec.ts`), and the tab opens read-only, because an id one reader minted is one no other reader has. A batch with an op the workbook refuses is rolled back and skipped, so one bad op never makes the doc unreadable, and a cell or field write whose parent is gone is skipped alone ([§ A write whose parent is gone is skipped alone](#a-write-whose-parent-is-gone-is-skipped-alone)). A row or column op whose value is not whole rows or columns on the grid, or an insert past the sheet's size limit, rolls its whole batch back too (`rowColOf`), since the batch's other ops were written for the rows it would have moved. The replay also syncs every sheet's stored cells from its matrix after the last batch, outside any batch's rollback, so `opToPatchOnSheets` drops a write that would leave a matrix or one of its rows no array, and `dataToCelldata` skips such a row: one op could otherwise make the workbook unreadable for every export, preview and joiner. It also drops a plain write of a sheet's `id` or `name`: a second sheet with one id makes the next snapshot undecodable, and a name that is no text breaks every later row or sheet op, while a rename travels as its checked `renameSheet` op. Both apply each batch through one function, `applySheetsBatch` (`engine/replay-ops.ts`): the sheet and row or column ops first, then the cell and field writes, one by one on the sheets those ops left, then the recompute those ops ask for, whole or not at all. The editor runs it too (`applyBatch` in `state/modules/apply-ops.ts`), on the plain sheets outside immer, and one recipe then writes what changed into the context and moves the view. The recipe (`writeSheets`) pairs the sheets by id, and a sheet the batch deletes is replaced, not written into, even when the batch adds its id back: the tab then holds the added sheet last, as the replay does. Reading every cell of every sheet through immer drafts, and immer finalizing each one, makes a row op on a heavy workbook take more than a second; on plain sheets it takes under half that. A peer's batch, a replay of the log, every structural undo or redo and the author's own row or column op, sheet add, delete or rename go through it, so the tab that sends a batch, the tabs that take it and a joiner agree. An op the shape check refuses throws before the recipe writes anything, and `applyOpBatch` then skips the batch. Every sheet the editor holds has its matrix, because `initSheetData` gives it one where it enters, at the mount or an add. The formula graph lives outside immer. The batch shifts it through a row or column op and has it follow the cell patches, a batch that renames, adds or deletes a sheet builds it again, and a batch that fails to apply drops it, since it may have followed part of the batch ([§ A reader holds its formula graph across batches](#a-reader-holds-its-formula-graph-across-batches)). `packages/sheet/src/test/components/Workbook/api.test.ts` pins the batch shapes against the replay, and `packages/sheet/src/test/state/modules/apply-ops.test.ts` runs one tab through random runs of its own edits, a peer's batches, undos and replays, checking after each step that the tab holds the replay of its log and that an undo and a redo cancel. The tests' joiner (`join` in `packages/sheet/src/test/state/factories/collab.ts`) decodes the stored snapshot, stored cells and no matrix, as a real joiner does: one that kept a live tab's matrices would hide a row op that leaves another sheet's stored formulas at the old rows. A Yjs update that writes a new snapshot and pushes batches at once loads the snapshot into the grid, and that load replays those batches too ([§ A new snapshot loads into the mounted grid](#a-new-snapshot-loads-into-the-mounted-grid)).

## A log entry that is no batch reads as an empty batch

A peer can store anything as an entry of `ops`: a number, text, an op with no path. So `sheetsOpLog` (`packages/lib/src/sheets/yjs-state.ts`) hands out the entries untyped, and every reader takes its batches through `readSheetsLog` or `sheetsBatchOf`: the tab's observer before it asks `commutes`, the tab's and the server's replay, the compaction and Import… before they send the log to the transform process as JSON, and the media sweep. An entry is a batch when it is an array of well-formed ops (`isOpBatch` in `packages/lib/src/sheets/types.ts`): each a known kind, its sheet id text, its path text and numbers, and no BigInt anywhere in its value, which a Yjs update carries and JSON does not. Any other entry reads as an empty batch, whole, even when only one of its ops is bad. It changes nothing on any reader, and it keeps its place, so the indexes the tab's anchors, the fold's count and `sheetsLogStartsWith` go by stay those of the log. The next fold deletes it with the batches around it. The checks behind it trust this one: `opToPatchOnSheets` and `commutes` read `op.path` as an array of keys. `packages/lib/src/test/sheets/yjs-state.test.ts` pins the shapes.

## A write whose parent is gone is skipped alone

A batch's cell and field ops are immer's patches, and every reader applies them one by one through `applySheetWrites` (`packages/lib/src/sheets/yjs-ops.ts`), each on what the writes before it left. A write applies when everything above it is there. One into a field of a cell a peer cleared, into an image, chart or filter a peer deleted, below a plain value such as `images/<id>/x/y`, or at a row or column its array lacks, is skipped alone, and the rest of its batch applies. So a cell or field write is not all-or-nothing with its batch. Only a sheet, row or column op the workbook refuses, or a batch that would leave no sheet shown, rolls the whole batch back, because the batch's other ops were written for the rows that op would have moved.

- **An array** takes a `replace` or a `remove` at an index it holds and an `add` at any index, which puts the value in there, or last when the array is shorter. So no write leaves a hole in a matrix. It also takes a `length` that cuts it, which is how immer writes the undo of an array that grew, and never one that grows it. No writer removes the matrix, one of its rows or a cell's place in a row, so `opToPatchOnSheets` drops such a `remove`.
- **A record** takes an `add` or a `replace` under any key but `__proto__`, and a `remove` of a key it holds. A `replace` needs no key to be there: immer writes one for a key its base held with no value, which a stored snapshot drops, so a joiner would skip what a live tab applied.
- **The caps stay at the write**, since a peer's op is untrusted: a conditional format past `MAX_CONDITIONAL_FORMATS` or a validation rule past `MAX_VALIDATIONS` is skipped, counted on the sheet as the batch's earlier writes left it, and so is a `replace` of a rule that is gone ([§ A validation rule is stored once over its ranges](#a-validation-rule-is-stored-once-over-its-ranges)). A write of a sheet's `row` or `column` is skipped the same way when the two would name a grid no sheet may hold ([§ A sheet's grid is bounded where it enters](#a-sheets-grid-is-bounded-where-it-enters)). The shape checks sit one step earlier, in `opToPatchOnSheets`, which also drops a write below a chart's field.

A skip reads only the sheets and the write, never when the batch arrived, so a tab, a joiner and the server's fold skip the same writes of every batch an editor sends. One forged edge is accepted: a snapshot keeps a matrix as its cells and the sheet's `row` and `column`, not its size, so after a forged `length` that cuts a matrix or a row below those, a live tab skips a write past the cut that a joiner from the snapshot applies. Undo and redo apply their entry's patches through the same function, and its result is the tab's next sheets and the batch they send (`patchStep` in `state/modules/history.ts`). The applier writes on copies of the objects along a write's path and shares the rest, so a batch costs what it writes. immer's `applyPatches` is not the applier for two reasons: it fails a whole batch at the first path that does not resolve, so every such case would need a filter that predicts it, and on sheets that are not frozen it walks every cell of the workbook per batch, 39 ms for one cell write on 10,000 rows where the applier takes 0.01 ms. `packages/lib/src/test/sheets/yjs-ops.test.ts` pins the rules and `packages/sheet/src/test/engine/replay-ops.test.ts` the replay.

## Every tab applies the batches in the log's order

The log's order is the truth: a joiner and the server replay it, so a tab that applied batches in any other order would show what nobody else has. Two tabs typing into one cell would each end with the other's value. A peer's batch can land before batches the tab already applied: two edits sent at once land in either order, and an offline peer's batches land where its tab pushed them. `handleOps` in `use-sheet.ts` reads where each new batch sits from the Yjs event, and handles a transaction's batches at once. A late batch takes one of two paths:

- **It commutes** with the batches it overtook, the ones the tab applied that come after it in the log (`commutes`, `packages/sheet/src/state/utils/commute.ts`): no batch on either side adds, deletes, renames or moves sheets, rows or columns, and no op on one side writes a path the other writes, or one inside or above it. A sheet's `hide` counts as one path for every sheet, since which of two hides applies depends on their order. A formula's recomputed value is a write too, so two edits to the inputs of one total don't commute. Two formulas typed in different cells write different paths, so they do. The batch then applies on top, and the undo stacks stay.
- **It doesn't.** The tab puts the grid back to an anchor and applies the log again from there (`replayOps` in `components/Workbook/api.ts`). An anchor is the sheets the grid showed once it held the log's first n batches. The tab keeps one every `ANCHOR_EVERY` batches, at most `MAX_ANCHORS`, the oldest dropped first; an anchor shares every row nobody changed since, so it is cheap to keep. On a sheet of 300,000 cells a batch applied again costs about 12 ms on average over a mixed log, a cell edit well under a millisecond and a row insert or delete about 150 ms, so twenty batches between anchors keep a rollback near a quarter second for a log of mostly cell edits; ten anchors hold about 2 MB there, and a rollback from the oldest applies some two hundred batches again, a few seconds. A batch that lands before the oldest anchor, such as one before the batches the tab replayed at load, loads the snapshot and the whole log again, in place. The replay empties both undo stacks, because their entries were recorded against an order that is gone. It also empties the formula engine, which learns the formulas again once the browser is idle, or at the first batch in the log with a sheet, row or column op. A kept map would still hold the formula of a batch of the tab's own that the log's order rejects, and the next edit of a cell that formula reads would write it back.

A throw while the tab applies a batch, or the log again from an anchor, loads the snapshot and the whole log in place as a new snapshot does (`reset`), because the grid may hold part of a batch and the next anchor would keep it. A throw in that load locks the workbook read-only, as a snapshot it can't decode does ([§ An undecodable snapshot](#an-undecodable-snapshot-locks-the-editor-and-never-overwrites)). A batch the workbook refuses is no throw: the grid skips it whole, as the replay does.

Only the batches new to the tab move its view, since the ones it applied before moved it once. A peer's row or column op on the current sheet moves the open cell editor and the selection with their cells, and on a sheet the tab left it moves the selection kept for it. A delete of the editor's cell closes it without writing, drops the selection and takes the focus off the grid, so the keys typed next write nowhere until a click selects a cell again, rather than overwrite the cell that took its place. Without an open editor, a selection the delete takes whole stays at that position, on what took its place or on the new last row or column, with its focus and its whole-row or whole-column mark, and one it takes part of shrinks, as in Google Sheets and Excel for the web. So the arrows go on from there and typing overwrites that cell with no warning. A focus that lands inside a merge takes the merge's head, with the box over the merge, as a click does, since text in a covered cell never shows. A delete never takes a sheet's last row or column: when two tabs deleting at once ask for every line, the last one stays on every reader (`rowColOf` in `engine/replay-ops.ts`), because a stored sheet reads no rows as the default size and a fold would part from the replay. So the selection always has a cell to land on. One function decides it for your own delete, a peer's, an undo and a redo alike (`followView` in `state/modules/rowcol.ts`), and it moves the selection kept for a sheet the tab left the same way. Each row or column op of a batch moves the view on the grid that op left, so a batch that deletes the last row and inserts one at the top lands the selection where the two ops one by one would. The peer who deleted sees your cursor where it landed, since a landing reports the selection the host publishes. Two cases are accepted: a landing on a hidden row refuses typing until an arrow moves off it, and two selections that land on one cell count twice in the status bar. When a new batch that moves rows on the current sheet lands ahead of an applied one that does too, the tab can't tell where its editor and selection went: the editor closes without writing, the selection clears and the grid gives up the focus, so a keystroke writes nowhere. On a sheet the tab left, the kept selection goes, and a tab the same replay lands on that sheet, because a fresh batch hid or deleted its own, has no selection there and gives up the focus too (`replayOps` decides both in one pass after the batches applied). `apps/sheets/src/test/components/sheets/hooks/use-sheet-order.test.tsx` pins these cases over real `Y.Doc`s.

Two things are accepted. Ops are not transformed, so a batch recorded before a peer's row insert that lands after it in the log writes at the rows it recorded ([SHEETS-TODO.md](SHEETS-TODO.md#sync-and-undo)). And a batch of cell edits recalculates nothing where it applies, on a live tab or in a replay: a formula whose input a late batch changed keeps the value its author computed, on every tab and for a joiner alike. Only a sheet, row or column op recomputes ([§ A sheet, row or column op recomputes on every reader](#a-sheet-row-or-column-op-recomputes-on-every-reader)).

## Creating a collection ships it whole, so every collection exists

immer records the creation of a key as one `add` carrying the whole new value. So the first write to a config collection that doesn't exist yet ships the entire collection, and it overwrites a peer's. And a granular write into a collection the base lacks finds no parent, so every reader skips it and the edit is lost.

`normalizeSheetConfig` (`engine/sheet-config.ts`) therefore materializes every config collection where a sheet enters a consumer: `initSheetData` at the mount and an add, the replay base, its `addSheet` ops and `createDefaultSheets`. Its `SHEET_CONFIG_COLLECTIONS` list has an exhaustiveness assert, so a new collection fails the build instead of reopening the hole. It also materializes `images`, `charts`, `conditionalFormats` and `dataValidations`, the maps outside `config` written key by key, as the snapshot decode does. So `opToPatchOnSheets` drops a peer's write that removes one of them or `config` whole, or leaves it no map: a joiner gets the map back and would apply the writes into it that the live tab skips.

There is no `ctx.config` or `ctx.filter` shortcut. Read a sheet's config with `getSheetConfig` (`state/context.ts`) and write through `ctx.sheets[i].config`, and read and write a filter on the sheet. immer names a patch after the path its draft was reached through, so a second route to the config emits patches at a root `filterPatch` drops, and assigning it back replaces the whole config. A mirror of the filter would go stale at a peer's filter edit, and the next local one would strand the rows it hid. `packages/sheet/src/test/state/events/concurrent-config.test.ts` pins it through the real op pipeline: one client merges cells, another drags a row taller, and the drag must not undo the merge.

`state/modules` find a sheet through `getSheet` (`state/api/common.ts`): the current sheet, or the one an id names. A bad id throws instead of handing back `undefined`, so a path that may name a sheet that is gone, such as a peer's row op, checks `getSheetIndex` first and returns.

`filterPatch` (`state/utils/patch.ts`) keeps what sits under `sheets` and nothing else. So what belongs to one tab stays off the sheets: its cursor and scroll on each sheet sit in `sheetViewRecord` on the context, and reach neither a peer nor the snapshot.

A write on a path that then rejects the operation still ships an op and costs the user an undo entry. `packages/sheet/src/test/state/rejected-writes.test.ts` is the table-driven gate; add a row to it when you add a writer.

## `borderInfo` holds each cell's own sides

`config.borderInfo` maps an `"r_c"` key to that cell's sides. `applyBorder` (`state/modules/border.ts`) expands a toolbar layout per cell at write time. `border-none` deletes the key and clears the facing side of each outside neighbor, so the shared edges go blank. Paste, move, fill and the format painter carry borders through `carrySides`, which deletes the destination's key when the source cell has no border, the Excel and Google overwrite rule. Order carries nothing, so two clients bordering different cells converge (`packages/sheet/src/test/state/modules/border-convergence.test.ts`).

A border belongs to the cell it was drawn on. The painter draws each cell's own sides at coordinates that coincide with the neighbor's, so the pixels match without a mirror. A shared edge never creates the neighbor's key, because that would be the whole-object `add` of [§ Creating a collection ships it whole](#creating-a-collection-ships-it-whole-so-every-collection-exists). A neighbor entry that already exists gets its facing side overridden, so the edge just drawn wins on screen. One result a user can see: copying B1 alone does not pick up A1's right edge. When two neighbors disagree on a shared edge, as after many xlsx imports, the higher-index one wins (B1's left over A1's right), so the color can't flip with the viewport's walk order.

A header click selects a whole axis, so it is clipped to the used extent first (`clipToUsedExtent`); one click must not write a key for every row. Cells filled in later rows show no border, an accepted divergence from Excel and Google. Merges are a read-time filter. `mergeEdgeSides` (`packages/lib/src/sheets/borders.ts`) is the one predicate. The canvas calls it per cell. The HTML export calls it on each stored key of a merge and folds the sides onto the merge's first shown cell, because the HTML has one `<td>`, so a side stored on a hidden edge row or column still draws. When several cells of a merge write the same outer edge, the last one folded wins. The xlsx export writes each cell its own sides, as Excel stores them. Storage stays raw, so an unmerge shows the sides again.

Only the canvas border pass skips hidden rows and columns. Every carry (paste, cut, move, fill, the format painter) reads the merge-filtered sides through `getBorderInfoCompute`, which keeps them, so a drag-fill from a hidden source keeps its border. The copied table folds a merge's sides through `mergedBorderSides` and keeps hidden tracks' too. A row or column insert clones the borders of the row or column at the insert index onto the new ones (`applySheetsInsertRowCol` in `engine/rowcol.ts`). So inserting above the top row of a bordered block repeats that row's top edge.

## Position-bound properties live beside the cell

Everything that is the cell (value, formula, number format, colors, font, rotation, rich-text runs, link) lives on the `Cell` in the matrix, and overwriting the cell overwrites all of it in one op. A link is `cell.link`, so whatever moves the cell moves it: a cut, a fill, a sort, a row op, undo and the op log need no code of their own, and two peers' links on two cells can't collide. A link's kind is `webpage`, `cellrange` or `sheet` (`CellLinkType`), and a peer's write of another kind, or of an address that is no text, is dropped (`opToPatchOnSheets`), as no reader could follow it. Typing over the cell keeps the link, and a table pasted from another program removes it, as such a paste writes a new cell. A rich-text cell keeps its text in its runs alone, with no `v` or `m`, and every reader takes it from there through `richText`, `cellValue` for a value that is the runs' text or `v`, or `cellDisplay` for the text the grid shows, the runs' text or `m` or `v` (`engine/format.ts`), except find and replace, which skips rich-text cells for now ([SHEETS-TODO.md](SHEETS-TODO.md), "Sheets: find and replace inside rich-text cells"). A writer that writes plain text over a rich cell drops its runs with `dropRuns`: they would otherwise outrank the value it wrote. Delete drops only the contents (`deleteSelectedCellText` in `state/modules/selection.ts`): the value, the formula, the runs and a link with its blue underline go, and the colors, font, alignment, number format and comments stay, as in Excel and Google Sheets. Removing the format is **Clear formatting** (`handleClearFormat`). What is bound to the grid position lives in a map beside the matrix:

| Property | Home | Why not on the cell |
|---|---|---|
| Borders | `config.borderInfo` | A border outlives deleted content, and a separate key keeps "A types, B draws a border" from clobbering |
| Merges | `config.merge` | A merge spans cells |
| Data validation | `sheet.dataValidations`, each rule over its ranges ([§ A validation rule is stored once over its ranges](#a-validation-rule-is-stored-once-over-its-ranges)) | The rule outlives the value it validates |
| Row and column geometry | `config.rowlen`, `columnlen`, `rowhidden`, `colhidden` | Keyed by axis, not by cell |

`parseCellKey` is the one `"r_c"` parser. Insert and delete re-key borders through `shiftCellKeyed` (`engine/rowcol.ts`); merges have their own shifter. A track nobody resized stores no size and falls back to its sheet's `defaultColWidth` and `defaultRowHeight`, or to `SHEET_DEFAULT_COL_WIDTH` and `SHEET_DEFAULT_ROW_HEIGHT` on a sheet without them. Only the xlsx import sets a sheet's own, so an Excel sheet keeps Excel's pitch. The editor, the importer and the export all read them through `sheetDefaultColWidth` and `sheetDefaultRowHeight` (`packages/lib/src/sheets/defaults.ts`), so screen and export share one pitch. The export and the xlsx import's chart anchors walk tracks to pixels through `sheetColumnsWidth` and `sheetRowsHeight` beside them, a hidden track counting none. A track's size counts its gridline, which the editor paints on the track's last pixel, as Excel counts it. So a column is as many pixels on screen as in Excel and the export, and a floating image, stored in pixels from A1, covers the same cells in all three.

Conditional formats and validation rules are stored the same way: `sheet.conditionalFormats` and `sheet.dataValidations` are records from an id to a rule, and each rule holds its `ranges` and an `order`, a fractional key as an image's or a chart's `index` is (`packages/lib/src/sheets/range-rules.ts`). The order is the priority, Excel's model: `orderedRules` reads a record first to last, ties by id, and the last rule over a cell wins it, so a new rule takes the key after the last (`nextRuleOrder`) and the newest rule wins. An edit names a rule by its id: an add, a delete, a row or column shift and a carry each write one key, so two rules added at once both stay and a delete or an edit made on another order still hits its own rule. Only the undo of a sheet delete writes a sheet's rules whole (`rewrittenByDelete` in `state/modules/history.ts`), and a peer's first batch ends that entry. A new rule from the editor gets a `crypto.randomUUID()` id; the importer and the demo seed number theirs `format-1` and `validation-1` in order, with the keys `nextRuleOrder` gives, so an import never depends on randomness. A sheet holds at most `MAX_CONDITIONAL_FORMATS` and `MAX_VALIDATIONS` (1,024 each) rules and a rule at most `MAX_RULE_RANGES` (8,192) ranges. No reader converts what an older build stored: a `conditionalFormatRules` list is not read, and a validation rule without an `order` is dropped where it is decoded, as any rule that is not well formed. An older log's write of the whole list lands as a `conditionalFormatRules` field no reader reads, and its write into the list by index lands in that field or, with no list written before it, finds no parent and is skipped alone. `packages/sheet/src/test/state/modules/range-rules.test.ts` pins these on two tabs and a joiner.

## The snapshot is interned and written only through the codec

`encodeSheetsSnapshot` and `decodeSheetsSnapshot` (`packages/lib/src/sheets/snapshot-codec.ts`) are the only way in or out of `state.snapshot`. A real 340k-cell workbook was 56 MB as plain JSON, because 224 style combinations and about 110 border payloads repeated per cell. The v2 envelope interns both into workbook-global dictionaries and is about 4.5 times smaller. The codec runs only where the snapshot is serialized: the in-memory `Sheet[]`, the ops and the replay don't know it exists.

- The dense `data` matrix folds into the cell list at encode and is never stored.
- The envelope's `computed` flag says whether the stored values were computed, which is what the server's recalc gate reads ([§ The editor computes on write](#the-editor-computes-on-write-the-server-only-what-nobody-computed)).
- A sheet's `row` and `column` are written at least as large as its dense matrix, which a row op or a paste can grow past them. A reader builds its grid from those two, and a write recorded in a row the reader lacks is skipped.
- `images` and `charts` ride verbatim, since there is nothing to intern. An `images` array, the form before images became a map, decodes as no images: sheets keep no backward compatibility, and no per-image write could resolve on an array. `opToPatchOnSheets` drops the whole-array write a tab still open on that build sends, for the same reason.

Only the server writes the snapshot: a replacing import, a version restore and the compaction at close ([§ The server folds the log](#the-server-folds-the-log-into-the-snapshot-when-the-workbook-closes)). The editor writes none, because a tab's state equals the log's replay only while the tab got everything right, and a snapshot it wrote would store any divergence for good. A workbook has no snapshot until its first compaction, and its first ops are recorded against the default sheets. `decodeOrDefault` (`engine/defaults.ts`) is that one decision for the editor, the server's reads and the compaction. The media sweep's reader (`document/references.ts`) only collects names, which the defaults don't hold, so it reads a missing snapshot as nothing.

## A sheet's grid is bounded where it enters

Every reader builds a sheet's matrix whole, at its `row` by `column` and out to its farthest stored cell (`gridSize`, `celldataToData`). One forged `row` of four billion would fail every later open, and a million rows by 16,384 columns would take its memory. So `sheetFitsGrid` (`packages/lib/src/sheets/defaults.ts`) is asked at the three places a size enters: a write of `row` or `column` (`applySheetWrites`, on the sheet as the batch's earlier writes left it, so two writes that fit only apart land the first), an `addSheet` value (`isNewSheet`, its stored cells' places included) and the snapshot decoder, which throws as for any corrupt snapshot. The editor's two growers ask it before they grow, since an imported sheet is taller or wider than their own limits: a row or column insert (`applySheetsInsertRowCol`, a `RowColError`, so every reader skips the batch) and a paste that runs past the grid (`roomFor` in `state/events/paste.ts`), each with a notice. A sheet fits when both counts are whole numbers within Excel's grid (`REFERENCE_ROW_COUNT`, `REFERENCE_COLUMN_COUNT`), every stored cell sits at an index on it, and the rows by the columns stay within `MAX_GRID_SLOTS`, 110 million. That is the cap the xlsx reader charges a whole file against, so no imported sheet reaches it: a sheet as tall as Excel's with 104 columns fits, and so does one as wide with 6,713 rows. It is a bound on what one op can cost, not a comfortable size: a million-row sheet still takes seconds and hundreds of megabytes to open ([SHEETS-TODO.md](SHEETS-TODO.md#performance)).

One edge is accepted: a row or column insert and a paste grow the matrix by their own limits (`MAX_SHEET_ROW_COUNT`, `MAX_SHEET_COLUMN_COUNT`), not by this one, and the encoder writes a sheet's size as large as its matrix. So a sheet imported within a few percent of the cap and then grown past it would be stored at a size the decoder refuses. A browser can hardly open such a sheet, let alone grow it.

## The server folds the log into the snapshot when the workbook closes

A collab document lingers a minute after its last socket leaves, or after an open that no socket joins ([COLLAB.md](COLLAB.md#a-document-lingers-after-the-last-unsubscribe)). At the end of the linger, a workbook with at least one batch in its log is compacted before it closes (`closeAfterLinger` in `apps/api/src/lib/collab/collab-document.ts`, the policy in `apps/api/src/lib/document/sheets-compaction.ts`). The main thread reads the snapshot and the log from the live doc and hands them to the transform process as JSON text, a `compact` job ([DOCUMENT-TRANSFORMS.md](DOCUMENT-TRANSFORMS.md)). There `compactSheetsSnapshot` (`apps/api/src/lib/document/sheets.ts`) decodes, replays with the editor's own replay and encodes. Without it the log of a workbook edited for months would grow without end, and every open and every server read would replay all of it.

**A close folds as much of the log as fits in its run.** A structural batch holds a row or column op or a sheet's add, delete or rename (`isStructuralBatch` in `packages/lib/src/sheets/types.ts`, the batches `seedsOf` recomputes for). Such an op ships no values, so the replay rewrites the formulas it moves and recomputes what it can affect, where a cell edit costs next to nothing. On a real 136,000-cell tab one costs the fold about 0.5 to 0.8 s, most of it the shift and the rewrite, and a row inserted above a 10,000-row running total reads 50 million cells, about 11 s: the reads cost 2 to 5 million cells a second as the formulas go. A run that fails closes the document with its whole log, so a log too long to fold would only grow and fail at every close, while every browser that opens the workbook replays all of it. So the fold has one bound, the run's own deadline. The runner hands the child the wall-clock time it kills it at (`deadlineAt` in `ChildRequestEnvelope`), and `compactSheetsSnapshot` turns it into the child's own clock once and stops `FOLD_MARGIN_MS` (5 s) before it, for the encode and the reply, 0.5 s for the 26 MB reference workbook, and for the part of the last batch no check reaches. The recompute checks the deadline where it checks its memory budgets, at each formula the graph lists and each cell its walk visits, and between two formulas it evaluates (`assertBeforeDeadline` in `engine/formula-engine.ts`), so a graph rebuilt after a sheet's add, rename or delete stops at the deadline too. A batch that runs past it is a skipped recompute like one past a budget: the fold drops it, stores every batch before it, and the next close starts with it under the whole deadline. A batch the deadline passes before it starts is not started. Only a first batch that alone needs more than the deadline fails the fold, which is accepted. A row op's copy of the sheets and its formula rewrite, the graph's move of the formulas the op didn't rewrite and the list of cells on a moved line check nothing, so the last batch can run past the deadline by them, which the margin holds: 0.7 s on the owner's largest tab. A fold can so hold the one transform child for nearly its whole deadline, which is accepted, and the runner prices a running compaction at all of it (`TRANSFORM_LIMITS.compact.admissionCostMs`). The fold has no cell budget, since time is what it is bounded by: three 10,000-row running totals read 150 million cells at a row insert and fold in about 40 s. The bound is time, not a count of batches or of cells, because one batch costs anything from a millisecond to most of the run: a count low enough for the heaviest workbook leaves a light one's long log to many closes, and one high enough for a light one fails the heaviest at every close. The main thread hands the child the whole log at each close, and the child returns how many of its first batches it folded, which the swap deletes. The fold reads the replay a batch at a time (`replaySheetsSteps` in `engine/replay-ops.ts`), which `replaySheetsOps` runs too, so every reader's replay stays the one the fold runs, and browsers and the editor replay with no deadline. A batch leaves the sheets it was given as they were, so the fold keeps the sheets before the stopped batch for free, and a time never reaches a stored value.

The main thread swaps the result in only while the log still opens with the batches it folded, the same objects in the same order (`sheetsLogStartsWith` in `packages/lib/src/sheets/yjs-state.ts`). A batch that arrived after them, from a socket that came and went during the run or a server writer such as Import…, stays in the log, and the swap deletes only the folded batches. A batch that landed among them, such as an offline tab's, or a new snapshot since the read, such as a replacing import, makes the result stale: the document lingers again and the next close tries again. A socket that connects during the run reattaches to the open document, and while it is connected nothing is swapped and the document stays open. A socket that came and left during the run holds every batch the fold read, so the swap goes ahead. The swap writes the snapshot and deletes the folded batches in one transaction, under an origin of its own that moves no Modified time. `apps/api/src/test/collab/collab-close-compaction.test.ts` pins each case.

- **It keeps the `computed` flag and runs no recalc of its own.** Its replay recomputes after each sheet, row or column op, as every reader's does, under the server's memory budgets and the fold's deadline. A batch past one is never stored, because a browser computes values the fold would store stale: the fold ends before it, and when it is the first the fold fails, the log stays, every tab recomputes it on open, and after three failures the server stops trying until it restarts ([§ A sheet, row or column op recomputes on every reader](#a-sheet-row-or-column-op-recomputes-on-every-reader)). An export, a preview and a search extract read the values the replay has. A workbook nobody computed, such as an import whose recalc failed, stays not computed, so its exports keep paying the recalc ([§ The editor computes on write](#the-editor-computes-on-write-the-server-only-what-nobody-computed)). The flag stays false until a replacing import or a version restore gives the workbook new content, and a formula typed in the meantime doesn't change it. A tab an Import… adds from a file whose recalc failed keeps the values the file held. A recalc here would hold the one transform child at every close, and delay the version and the swap, for a workbook whose recalc may fail every time.
- **A batch that fails the replay is dropped**, as every reader drops it, and the server logs how many.
- **A version keeps the log before the swap.** The swap deletes the folded batches, and a version the close takes would come after it, so a short session's raw log would be in no version. So the main thread first saves a version, as a replacing import does (`drive.saveVersion`). It holds no lock at that point, so the version waits for the container lock and copies data.db from its open handle, like a manual save. A version that fails stops the swap, and the document closes with its log, as after a failed run. A version that keeps failing leaves the log uncompacted, and the next close tries again: such a failure doesn't count toward the three that stop it. The check covers the version too: a batch that lands among the folded ones during it drops the result, one after them stays in the log, and a socket connected at its end stops the swap. After a swap the close takes no version of its own (`skipFinalSnapshot`): the version holds every batch the swap deletes, and a batch that came in since stays in the log, for the next session's version. So the copy of the log is the session's one version, and the history gets one entry per session, not two. It ages like any other version under retention.
- **Three failed runs in a row stop it** for that workbook until the API restarts (`MAX_COMPACTION_FAILURES`), so a workbook too large for the transform process doesn't hold the one child at every close. A busy runner, a canceled run and a shutdown say nothing about the workbook and don't count. A replacing import or a version restore gives the workbook new content, and the count starts over.
- **The wait is bounded.** A run is queued behind the work the one child has, then runs under its own deadline. Under load that queue can be long, and every workbook that waits in it stays open in memory. So the whole of it, queue included, has one budget (`COMPACTION_BUDGET_MS`, an export's deadline plus the run's own); past it the document closes without the compaction. A run that waited so long that the budget ends inside its fold is killed before the fold's own stop and stores nothing, and the next close does the work again, which is accepted. A destruct, such as a trash or a shutdown, aborts the run, because a closed document has nowhere to put the result, and the run would hold the child for nothing.
- **A snapshot in an older format is left as it is.** The compaction can't read it, and the editor opens it read-only ([§ An undecodable snapshot](#an-undecodable-snapshot-locks-the-editor-and-never-overwrites)).

Every close with a non-empty log compacts, and a workbook some tab always has open never does ([SHEETS-TODO.md](SHEETS-TODO.md#sync-and-undo)). A workbook that closes with batches still in its log, past the fold's deadline or arrived during the run, folds them at its next close, once a tab or a server writer such as an import opens it again.

## A new snapshot loads into the mounted grid

The server writes a new snapshot in three cases: the compaction at close, a version restore and a replacing import. It compacts only while no socket is connected, so the tab that receives a compaction is one that was away longer than the linger, such as a laptop that slept or a phone tab in the background.

On a transaction that changes `state`, the tab decodes the snapshot, replays the whole log on top as a joiner does, and hands the sheets to the grid in place (`reset` in `use-sheet.ts`, through `replayOps` with no batches). The Workbook never remounts, so the selection, the scroll position, the sheet on screen and the peers' cursors stay, and a selection keeps its row and column even where a folded batch moved the rows. A snapshot without the sheet on screen, such as a replacing import, whose sheets have new ids, puts its first sheet on screen with the cursor on A1. The grid gives up the focus only when the snapshot leaves it no selection, a smaller grid on the same sheet, so after an import the keys still reach it and undo shows its notice (`packages/sheet/src/test/components/Workbook/undo-peer-notice.test.tsx`). Both undo stacks empty, which is accepted: a tab that slept through a compaction loses its undo steps. Keeping them would need a mark in the doc that tells a compaction of what the tab holds from any other new snapshot, a judge of every transaction against it and two server writers that stamp it.

Nothing of the tab's own is lost or applied twice, because the grid's new state is the doc's and nothing else. A fold deletes only the batches it read, so a batch the tab wrote offline is still in the log and in the replay, and a batch of the tab's that the fold did read is in the snapshot and gone from the log. A transaction that deletes batches from the log without writing a new snapshot loads the same way. Yjs runs the log's and the map's observers in no fixed order, so the log's observer leaves a transaction that changed `state` to the map's. `apps/sheets/src/test/components/sheets/hooks/use-sheet.test.tsx` pins these cases.

A workbook stored by an older build can still hold a `base` key in `state`. Nothing reads it.

## An undecodable snapshot locks the editor and never overwrites

Anything that is not a v2 envelope throws, and so does a dictionary index past its table or a sheet whose grid no sheet may hold ([§ A sheet's grid is bounded where it enters](#a-sheets-grid-is-bounded-where-it-enters)). How `use-sheet.ts` reacts depends on when. On the initial load it opens read-only on blank defaults, and the `loadedRef` gate keeps it from sending an op built on them (`handleOp`). On a new snapshot it can't read mid-session, it keeps the workbook already on screen and arms the same lock, because local state may now diverge from the wire. Either way a persistent banner in `editor.tsx` says so, because a blank read-only sheet with no lasting explanation looks like data loss.

Version history keeps snapshots in older encodings. Restoring one answers 409 and changes nothing (`apps/api/src/lib/versioning/restore.ts`), because every connected editor would lock.

## Undo is per tab, and a peer's batch ends your structural steps

Undo is the tab's own pair of stacks of immer patch entries (`globalCache.undoList`/`redoList`, kept by `components/Workbook/index.tsx`). The steps are functions in `state/modules/history.ts`: `undoEntry` and `redoEntry` take the context and an entry and return the next context and the batch to send. An undo is broadcast as an ordinary op batch, so peers see an edit. A peer's batch is never undoable locally. A late peer batch that makes the tab apply the log again empties both stacks ([§ Every tab applies the batches in the log's order](#every-tab-applies-the-batches-in-the-logs-order)), and so does a new snapshot ([§ A new snapshot loads into the mounted grid](#a-new-snapshot-loads-into-the-mounted-grid)). So does a peer's rename that applies: an entry holds formula text naming tabs, and bringing back `=One!B1` after `One` became `Two` would read `#REF!` for every reader. A rename is rare, so no machinery rewrites the entries.

**Any peer batch that applies removes your newest structural entry and everything below it, on both stacks** (`dropStructuralEntries` in `state/modules/history-shift.ts`). A structural entry is a row or column op, a sheet's add, copy or delete, a rename, or an edit that changes a list's length, such as a paste that grew the grid (`isStructural`). A conditional format or a validation rule added or taken out is one key written, so it is an ordinary entry and a peer's batch leaves it on your stack. The first kinds record the workbook they found and left, as whole fields and matrices or as a sheet's old name. An edit that changes a list's length records a write of that `length`, which would cut off what a peer appended and which no check against a target can skip. So it can only step on that workbook, and each entry below it fits the workbook as it leaves it. A structural step always finds the grid as it left it, and never merges a peer's edits or has to refuse. Entries newer than it stay, and working alone nothing changes. A peer is any other tab, the same user's included.

**A press that finds nothing left because a peer took it says so.** `setStacksAfterPeer` (`components/Workbook/api.ts`) marks a stack in `globalCache.cutByPeer` when a peer's batch shortens it, by the drop, a shift that drops an entry, a rename or a replay. Each stack has its own mark, because a cut of your undos says nothing about your redos. The tab's next own edit clears both, so once that edit is undone an empty stack is silent again, even with older entries cut. `stepHistory` (`components/Workbook/index.tsx`) reads the mark only when its stack is empty, and shows the notice through `ctx.warnDialog`, so a stack that was empty all along stays silent. The Edit menu keeps a marked row enabled, as a disabled row can't be pressed. An undo whose every write was skipped ([§ Undo skips a cell a peer changed since](#undo-skips-a-cell-a-peer-changed-since)) still uses up its press with no notice.

An entry names its sheet by id, `['sheets', id, field, …]` (`recordEntry`), so a peer adding or deleting another sheet doesn't misplace it, and a write to a sheet that is gone is dropped. A peer's row or column op then shifts what is left through `shiftEntries` (`state/modules/history-shift.ts`), as it shifts the live cells: cell paths, which carry a cell's link, the `"r_c"` keys of merges and borders, the ranges of conditional formats and validation rules (`shiftRules`), the row and column size maps on the op's axis, `mc` references, and formula text on every sheet that points at the moved rows, through the same `functionStrChange` the engine uses. An entry the op makes meaningless is dropped instead: one that writes inside deleted rows or columns, a rule a delete takes whole, a conditional format with a formula, whose text the op rewrites on its own sheet and on any sheet where the formula names the op's sheet, or one that cuts through a merge, a whole `config` or config map, or a range-valued field on that sheet (filter, frozen panes), and a chart's data on a chart that reads that sheet. A write of a chart's style, a slice color among them, stays, since a point keeps its index through a row op. Your own ops never shift your stacks, because last in, first out already fits them. The undo stack keeps its newest 200 entries, and of the row, column and sheet entries, which may hold whole matrices, only the newest ten (`pushEntry`). Past those limits only the oldest entries go, since an entry dropped from the middle would misplace the ones below it.

The drop and the shift happen in `applyOp`, once the batch applied: `applyOpBatch` reports the row and column ops it applied with the sheets it applied each to, so a skipped batch moves nothing, and a second batch shifts against the sheets the first left. **Every write applies at its call, not when React renders.** The Workbook keeps the workbook in a ref (`contextRef` in `components/Workbook/index.tsx`). An edit's recipe, its undo entry and its `onOp` batch, an undo or redo, and a peer batch with its shift all run on that ref before the call returns, and React then gets the result as a plain value. So the ref and the stacks change once per call, in call order, however React schedules its renders. A React updater runs at render, not at the call, so an edit's batch pushed from one could reach the op log behind a peer batch that arrived after the edit. A read outside render, such as the host's `getFlowdata`, a paste, or a menu that builds a row op, reads the ref through `getContext`, so it sees an edit made just before (`packages/sheet/src/test/components/Workbook/eager-context.test.tsx`).

## Undo skips a cell a peer changed since

Before an undo writes a cell or field back, it checks that the target still holds what the entry wrote there, and skips it otherwise, as Google Sheets does; redo checks against what the undo restored (`stillWritten`). The check writes the entry's other side again, once and in order, through the applier every reader uses, and a target that comes out as it is holds. So a write a reader would skip is skipped in the check too, and a merged gesture's edit of an object it then deleted does not read as a peer's change. For a formula cell it compares what a person wrote, not the value, display text or value type the engine computed, so a formula whose precedent a peer changed still undoes. A merge and its cells' `mc` pass or skip together, so an undo never leaves half a merge. A skipped patch is not sent. The check runs only on the client that undoes, so two peers undoing at once, or an offline tab rejoining, settle by the log's order ([§ Every tab applies the batches in the log's order](#every-tab-applies-the-batches-in-the-logs-order)). An undo or redo sends no value or display text the entry recorded for a formula cell, since a peer may have changed its inputs or the formula itself, unless this build can't evaluate that formula, whose number then stays as a recompute keeps it (`withoutComputedValues`). The filter is not only a saving: when a peer changed every input the entry wrote, the recorded totals are all that is left of it, and without the filter they would go out as a batch that changes nothing, ends the peers' structural undos and leaves the entry to redo. It recalculates the formulas it wrote and every formula that reads a cell it wrote, as an edit does, and sends those results. A recompute writes a result whenever the cell's value, value type or display text differs from what the result gives in the cell's format (`holdsFormulaResult` in `engine/format.ts`), not only when the value changed, so the undo of a date format on `=A1*2` gives back `10` typed as a number, and a type the entry brought back that no longer fits the value is written over.

## A structural undo applies exactly the ops it sends

An undo or redo that adds or deletes a sheet, rows or columns, or renames a sheet, builds a batch of ops and applies that batch through `applyOpBatch`, as its peers will. Applying the entry's own patches would differ from the wire: a row op records whole fields, `data` among them, while peers only take the marker.

- A sheet add, copy or delete keeps the sheet in the entry's options. Bringing it back is an `addSheet` op with that value plus the order ops, which also gives the restored sheet its `data`. Taking it away is a `deleteSheet` op by id plus the order ops. `addSheetOps` and `deleteSheetOps` (`state/utils/patch.ts`) build these batches for the edit, its undo and its redo alike: a joiner's replay appends or removes the sheet and moves no other, so the batch carries the orders the op left. A peer takes those orders as they come too, and only the author's own edit moves the other sheets (`shiftSheetOrders` in `state/modules/sheet.ts`): two batches sent at once would each move them again. The batch carries exactly the orders that changed, compared sheet by sheet before and after the edit, wherever they sit. Two tabs adding a sheet at once leave two sheets on one order, and two deleting at once leave a gap, which every reader holds alike. A copy then renumbers every sheet from 0 (`setSheetOrder`), sheets before it included, and an order left out of the batch would part the author from its peers and a joiner; an order sent unchanged would undo a peer's move sent at the same time. A delete moves only the sheets past it, so a sheet on the same order keeps its place and the delete's undo puts the sheet back before it. Which of two sheets on one order comes first is their place in the list, and an undo puts a deleted sheet back first, so after a delete and undo of the second the two swap (`history.test.ts`, "sheet orders after two tabs change the sheet list at once"). The add ships no recomputed cells, which would replace the sheet on a receiver and lose a peer's edit the log put first. Adding a tab with a cell open commits that edit as an undo step of its own, so the two undo apart.
- A delete rewrites what names the sheet on the sheets it leaves, so its entry also records their matrices, rules and validations as they were (`rewrittenByDelete`), and its undo ships what the marker did not bring back after the `addSheet`, cell by cell, as a row undo does.
- A rename keeps the sheet's two names in the entry's options, and its undo and its redo are a `renameSheet` op to one or the other.
- So an undo rewrites formulas it never recorded, as Excel does for the same edit: undoing an add or a copy is a delete, and a formula a peer wrote naming that sheet reads `#REF!`; undoing a rename renames back, so a peer's `=Renamed!A1` becomes `=Two!A1`. Accepted by the owner on 11 Nov 2026: no data is lost, and recording the rewrite as a delete does would be more undo machinery for a race.
- A row or column undo is the inverse marker plus what the marker did not bring back (`undoRowCol`). Since no peer batch landed, the grid is as the entry left it, so what the entry recorded is the state to go back to, on any sheet and in any field: it ships each recorded write the marker didn't make, such as a deleted row's height or link or a formula rule a delete made `#REF!`, and keeps the rest off the wire. A receiver then keeps its own shift of a batch on its way. The config maps, images, charts, conditional formats and validation rules are recorded one entry at a time (`WRITTEN_BY_ENTRY` in `state/modules/apply-ops.ts`), so none ships whole: the undo of a delete sends `config/rowlen/4`, never `config`, and a column width or border a peer set meanwhile on another key stays. The config goes back entry by entry to what the entry found (`configOps`), so the undo also removes an entry the marker made that the delete never took, such as a border an inserted row takes from the row beside it. A deleted merge comes back as its `config/merge` entry and its cells' `mc` in the one batch. A tab that writes a map entry by entry holds its keys in another order than a joiner, so the engine shifts and stamps merges in key order (`shiftMerges` in `engine/rowcol.ts`): overlapping merges, which two tabs merging at once leave, would otherwise stamp differently per reader.
- The cells go one by one: `repairOps` ships a `replace data/r/c` for each cell where the recorded matrix differs from what the marker left, such as the rows a delete took or a formula it made `#REF!` or shrank. Every reader then recomputes after the whole batch, seeded with those cells too, so a formula on a sheet the entry never recorded comes back with them.
- A row or column redo is the edit's own marker again, so an entry records only its undo side.
A step that applies nothing sends nothing, and its entry leaves both stacks (`stepNewestEntry`): an imported sheet past the row limit can delete a row but can't insert it back, and a redo left on the stack would delete the next row. That undo does nothing and says nothing; accepted by the owner on 11 Nov 2026.

`packages/sheet/src/test/state/modules/history.test.ts` runs every case on two tabs and a joiner, and pins the shifter's paths. Whether to move to Yjs structures and `Y.UndoManager` is answered in [PROPOSAL_SHEETS_YJS_WORKBOOK.md](proposals/PROPOSAL_SHEETS_YJS_WORKBOOK.md): only with stable row and column ids, and not first.

## Every sheet switch goes through `changeSheet`

Tab clicks, the sheet list, search, hyperlinks, the API and the current sheet going away all call `changeSheet` (`state/modules/sheet.ts`). When the current sheet is hidden or deleted, locally, by a peer or by an undo, `settleCurrentSheet` lands on the first visible sheet in tab order. A hidden target is refused, and so is hiding or deleting your last visible sheet, with a notice (`lastShownSheetRefusal`). `hideSheet` and `deleteSheet` check it when they run, not when the menu opened, since a peer's delete can make the sheet the last one shown while its delete confirm is open. When two tabs at once each hide or delete one of the last two sheets shown, the later batch in the log does nothing on every reader, as a row delete keeps a sheet's last line, and so does an undo or redo that would hide the last one (`hidesEverySheet` in `engine/replay-ops.ts`).

A switch closes the cell editor and any formula range selection, so Enter can never commit into a sheet a peer switched you to. It also derives everything the grid paints (`applySheetView`) inside the same recipe, and a sheet with no cursor yet opens on A1, since a key does nothing without one. Any other commit on the same sheet goes through `deriveView` in the Workbook's commit, an edit, an undo and a peer's batch alike, which works out the geometry again only when the grid's size, its first row, a track or merge map, the filter range or the edit rights changed. The first frame after a commit paints before any effect runs, so anything left to an effect would draw a frame on the old geometry, such as the selection above a row a peer just inserted. `freezeOf` reads the frozen panes off the sheet and the geometry of the same context, so they hold no state of their own to go stale (`packages/sheet/src/test/components/Workbook/view-derivation.test.tsx`).

## The engine is the half the server imports

`packages/sheet/src/engine/` holds the parser and evaluator, the dependency graph, recalc, row and column shifts, the op replay and the conditional-format evaluator. The editor and the server run the same code. `engine/` imports nothing from `state/` and nothing from the DOM. It evaluates through one `CellResolver`, `createArrayResolver` (`engine/cell-resolver.ts`), over the editor's sheets or the server's replayed `Sheet[]`. Orchestration that needs the context lives in `state/modules/formula-exec.ts`: `execFunctionGroup` after an edit. A sheet, row or column op recomputes inside `applySheetsBatch` through `recomputeAfter`, in the editor as in the replay. Both call the engine's walk and pass `FormulaGraph.affected` (`engine/formula-graph.ts`) and `evaluateFormulas` (`engine/recalc.ts`), which keeps its computed values in a local map (`withComputedValues`), so a recompute holds nothing between edits that could shadow a cell. `execFunctionGroup` takes the cells that changed as its argument and writes the changed values before it returns.

`apps/api` imports only the `@workspace/sheet/engine` subpath, and two of its leaf modules: `engine/a1-notation` and `engine/format`, which a docx or pptx chart reads its ranges and number formats through, since the barrel evaluates the whole formula engine, formulajs included (632 modules). The `./engine` entries in `packages/sheet/package.json` point at the TypeScript source, not a build, so the API's own type check covers the engine under its stricter options: no DOM lib, `verbatimModuleSyntax`, `noUnusedParameters`. A DOM or state import in the engine fails the API build.

The functions come from `@formulajs/formulajs`, behind a parser inherited from the fortune-sheet fork. A function neither formulajs nor the engine has (LET, FILTER) evaluates to `#NAME?`. An error is a value, not a throw: an operator's or a function's error, and an error typed into a formula such as `#N/A`, becomes formulajs's own error object (`toFormulaError` in `engine/parser/error.ts`), because formulajs's functions, such as `ISNA` and `IFNA`, compare errors by identity. So does an error another cell holds: a cell stores its error as text, such as `#DIV/0!`, and `getCellValue` in `engine/formula-engine.ts` turns it back into the object for every cell and range read, so `IFERROR(B1,"none")`, `SUM(A1:A3)` over an error and a `VLOOKUP` landing on one behave as in Excel. A cell that holds such text as text stays text: `ct.t: 's'`, as a leading apostrophe makes it, or a rich-text cell. An error typed into a text-formatted (`@`) cell is stored as text, as in Excel (`setCellValue` in `state/modules/cell.ts`). A formula's result sets its cell's `ct.t` at every write, in the editor and in the server's recalc alike, through one writer (`writeFormulaResult` in `engine/format.ts`), and leaves `ct.fa`, the format a person chose. An empty-text result is `v: ''`, from the editor as from an import, so the cell shows blank and `=B1+1` over it is 1 ([§ Values follow Excel's grid and calendar](#values-follow-excels-grid-and-calendar)). A blank result holds no `v`. A reader goes by `ct.t`, so a type left from the last result would read the text `005` as the number 5. Applying a number format, from the menu or the format painter, writes the result the same way (`updateFormatCell`, `pasteHandlerOfPaintModel`), as does a formula pasted as text, so `=IF(A1>1,"005",5)` under Number shows `005` until it gives the number, then `5.00`, as in Excel, and `fa` stays throughout. The format painter changes what a constant shows, not what it is: a number takes its type from the painted format, and text or a boolean keeps its own, so `'005` under `0.00` stays the text `005`. Any function handed an error, as an argument or a cell of a range, returns the first one, as nearly every Excel function does: `callFunction` checks before the call, so `CONCAT`, `TEXTJOIN` or `STDEV` over a range with an error is that error, which `IFERROR` traps. An operator does the same, a range operand included: `C2:C3&"a"` over a #N/A is #N/A. `READS_ERRORS` in `evaluate-by-operator.ts` names the arguments a function reads errors in itself: those of the IS functions, `ERROR.TYPE` and `TYPE`, the value `IFERROR` and `IFNA` inspect, `COUNT` and `COUNTA`, every argument of the `*IF` family, a lookup's table or arrays, the range `UNIQUE`, `FLATTEN` or `TRANSPOSE` reshapes, and `AGGREGATE`'s references, whose options 2, 3, 6 and 7 drop their errors. A lookup's options are not among them: `VLOOKUP("c",B1:C3,2,D1)` with #N/A in D1 is #N/A, as in Excel. The `*IF` family matches an error cell by its text, and an error criterion too, so `COUNTIF(A1:A9,"#N/A")` and `COUNTIF(A1:A9,NA())` count the #N/A cells. `IFS` and `SWITCH` test in order, as Excel does, so they hand on an error they reach and not one past the value they return. formulajs has no object its `ISERROR` knows for `#SPILL!`, `#CALC!` or `#ERROR!`, so the engine's own `ISERR`, `ISERROR`, `IFERROR` and `ERROR.TYPE` (`engine/parser/functions/`) recognize every error a cell can show by its message, not by identity (`isFormulaError` in `engine/parser/error.ts`). An unknown name is `#NAME?` the same way, and so is a function Excel doesn't know either, such as the typo `FILTRE`, so `IFERROR` traps it, as in Excel. A real Excel function the engine lacks is not, because a fallback would read as the answer Excel computed: `callFunction` returns `UNSUPPORTED_FUNCTION` (`engine/parser/error.ts`), an error that reads `#NAME?` but is not formulajs's, and hands it on through every function, so `IFERROR(FILTER(…),"x")`, `ISERROR(FILTER(…))` and `ERROR.TYPE(FILTER(…))` are `#NAME?`. Handed a `#REF!`, it hands that on instead, so `=FILTER(#REF!,1)` is `#REF!`. A `#NAME?` another cell holds reads as `UNSUPPORTED_FUNCTION` too. The cell can't say whether a typo or such a function made it, and one cell away a fallback would read as Excel's answer just the same. The cost is a typo's `#NAME?`, which Excel would trap one cell away and the engine hands on. It is no throw, because the grammar evaluates every argument before the call, where Excel evaluates only the branch taken: `IF(FALSE,FILTER(…),1)` and `CHOOSE(1,5,FILTER(…))` must stay a value. So `BRANCHES` in `evaluate-by-operator.ts` names the arguments `IF`, `CHOOSE`, `IFS`, `SWITCH`, `IFERROR` and `IFNA` choose their result among, and only those may hold it; the function returns the one it takes. A condition, an index or the value `IFERROR` inspects never may. Every `IFS` condition and `SWITCH` match value counts as one, even past the one that holds, which Excel would not evaluate, so there the cell shows `#NAME?` where Excel has a value. `isExcelFunction` (`@workspace/formula/names`) holds every Excel function name, from Microsoft's alphabetical list; formulajs is no source for it, because it registers Google Sheets' functions too. The engine overrides `VALUE`, which rejects a number, and `TEXT`, which formulajs leaves unimplemented, so it formats through the same numfmt masks the grid renders with, and an empty mask gives empty text. It overrides `CONCATENATE` and `CONCAT`, which join a number with JavaScript's `toString` and a Date with `Date.toString()`. It overrides `INDEX`, which reads a row_num or column_num of 0, empty or blank as 1, where Excel gives the whole column or row as an array: `SUM(INDEX(A1:C2,,1))` sums column A. A lone index into a one-row range picks along the row, as Excel's does: `INDEX(A1:C1,2)` is B1. The engine has no reference form of `INDEX`, so no area_num. `FIND` and `SEARCH` read a start_num below 1 as 1, where Excel's is `#VALUE!`, and `NUMBERVALUE` answers NaN for text it can't read, which shows as a blank; overrides make both `#VALUE!`. It overrides `AGGREGATE`, which reads only its first reference and ignores its options. It adds `XLOOKUP`, `XMATCH`, `TEXTJOIN`, `MAXIFS` and `MINIFS`, which formulajs 2.9.3 lacks, and replaces `IFERROR`, `IFS`, `SWITCH`, `ISERR`, `ISERROR`, `ERROR.TYPE`, `AVERAGEIF`, `AVERAGEIFS`, `MATCH`, `VLOOKUP`, `HLOOKUP`, `ROWS` and `COLUMNS`, from `engine/parser/functions/`, one file per family: `FUNCTIONS` in `formula-function.ts` registers them, and a function added there may return a blank, which an override can't, since its `undefined` falls through to formulajs. `MAXIFS` and `MINIFS` test their criteria with formulajs's own `lib/utils/criteria-eval`, the test its `SUMIFS` and `COUNTIFS` run, so all of them match the same cells (`src/test/engine/parser/functions/statistical.test.ts`). That test is case-sensitive and knows no wildcard but a lone `*`, unlike Excel's; the gap is open in [SHEETS-TODO.md](SHEETS-TODO.md#formula-engine).

`XLOOKUP` and `XMATCH` take each of Excel's match modes (exact, next smaller, next larger, wildcard) and search modes (first to last, last to first, binary over ascending or descending data), so an imported `XLOOKUP(2.5,A1:A5,C1:C5,,-1)`, the shape Excel writes for a mode with no if_not_found, finds the next smaller row. A lookup lands only on a value of its own kind, as in Excel: 5 never matches `"5"`, so a binary search steps over a column's trailing blanks. An exact match is the first of its duplicates in every mode, the row a linear search finds (`src/test/engine/parser/functions/lookup.test.ts`). `MATCH` searches the same way, because formulajs's reads its text as a regular expression, matches part of a cell and throws on a number or a blank in the range, which makes `MATCH("Real (Central)",O14:Q14,0)` `#ERROR!`. Its match_type 0 is an exact match with wildcards, and 1 and -1 a binary search that lands on the last of a run of duplicates, as Excel's does. A blank lookup value is 0, so it finds no blank cell. `VLOOKUP` and `HLOOKUP` search their table's first column or row as `MATCH` does, a range_lookup of TRUE as match_type 1, because formulajs's compare text case-sensitively, know no wildcard and find a blank lookup value in a blank cell, so `IFNA(VLOOKUP(C13,…,2,FALSE),"")` over an empty C13 would be 0 where Excel gives `""`.

Excel's dotted names (`STDEV.S`, `NORM.S.DIST`, `NETWORKDAYS.INTL`) are properties formulajs nests under a function or a namespace, so `resolveFormula` walks into both. `DOTTED_FUNCTIONS` in `formula-function.ts` lists the ones the engine registers, by hand, because formulajs's aliasing leaves nested paths Excel doesn't know (`STDEVS.P`, `CEILINGMATH.MATH`). `T.DIST`, `T.TEST` and `F.TEST` are left out: formulajs computes something else under those names, and `#NAME?` lets an imported cell keep Excel's number through a recompute ([Recalc keeps what it can't improve](#recalc-keeps-what-it-cant-improve)). So are the names `LEFT_OUT` lists (`engine/parser/supported-formulas.ts`): the ones formulajs registers as a stub that throws "not implemented" (`FIXED`, `PRICE`, `CELL`), and `ROW` and `COLUMN`, which it reads as Google's `(matrix, index)` forms. Each is the `#NAME?` no function traps. The function list that autocomplete and Insert function read (`state/modules/function-list.ts`) offers only names the engine registers and evaluates, which `src/test/state/modules/function-list.test.ts` checks. Overrides fill in an omitted significance of 1 for the `CEILING.*` and `FLOOR.*` variants, which formulajs reads as 0, and make `ERF.PRECISE` and `ERFC.PRECISE`, which formulajs leaves unimplemented, `ERF` and `ERFC` of one argument. The xlsx writer stores each dotted name with the `_xlfn.` prefix except `ERROR.TYPE` and `ISO.CEILING`, which the 2007 file format already defines; `apps/api/src/test/ooxml/spreadsheetml.test.ts` checks every registered name against that list.

The grammar is `engine/parser/grammar-parser/grammar-parser.ts`, a jison parser converted to TypeScript and edited by hand since, its parse table included. `grammar-parser.jison` beside it is the readable copy: the same lexer rules and productions in the same order, with a header naming what only the TypeScript holds. Nothing generates from it, and regenerating would lose the hand edits, so a grammar change edits both files and regenerates neither. A function name may be one letter (`T`, `N`), and `%` follows any expression, so a row delete's `=#REF!%` still parses. A text past Excel's 8,192 characters doesn't parse (`MAX_FORMULA_LENGTH`, `engine/parser/parser.ts`), so it shows `#ERROR!`, or keeps its number: every reader evaluates what a recompute reaches, a forged formula could otherwise hang a browser, and a browser has no deadline.

An empty argument, as in `SUM(1,,2)` or `SUBSTITUTE(A1," ",)`, is a slot of its own, because Excel writes `,,` into its files. The grammar gives it the `OMITTED` marker (`engine/parser/omitted.ts`), and Excel's rule depends on the parameter: an empty number is 0 and an empty text is `""`, so `LEFT("abc",)` is `""` and `VLOOKUP`'s empty range_lookup is FALSE, an exact match. formulajs can't be handed the slot as `undefined`, which it reads as not supplied (`LEFT("abc",)` would be `"a"`). So `formula-function.ts` hands it `""` at the text parameters `TEXT_PARAMETERS` lists for the text functions, and 0 everywhere else, which is Excel's answer for `SUM`, `ROUND`, `IF` and `VLOOKUP`. A function in `FUNCTIONS` gets the marker itself and reads it as Excel reads that parameter: an empty `XLOOKUP` if_not_found is not supplied, an empty mode its default. `PI()` stays a call with no arguments, not one empty one.

formulajs carries one patch, `patches/@formulajs%2Fformulajs@2.9.3.patch`, listed in `patchedDependencies` in the root `package.json`. Its `flattenShallow` (`lib/utils/common.js`, the only build the engine loads: `main` is `index.js`, which requires `lib/`) concatenated onto a `reduce` accumulator, copying it per row, so flattening a range was quadratic in its rows: 100,000 rows took 2.1 s, one `SUMIFS` over 208,681 rows 305 s. The patch is the same flatten as a loop, with the same output, and it no longer pushes into its input. 4.6.0 has the old code. Once a release fixes it, delete the file and the `patchedDependencies` entry and run `bun install`. Keep `src/test/engine/formulajs-flatten.test.ts`, which pins the output and the time. Both Dockerfiles copy `patches/` with the manifests, because the install applies it.

## Values follow Excel's grid and calendar

- A Date result (`DATE`, `EOMONTH`, `NOW`) is stored as its Excel serial, taken from the Date's local calendar fields, because formulajs builds its Dates at local midnight. `dateToSerial` in `engine/parser/helper/number.ts` is the engine's conversion, with the Lotus leap day from 1900-03-01. The cell keeps its format mask, so a mask-less cell shows the serial.
- Every range is clamped to the sheet grid, because an unclamped `A1:XFD1048576`, a shape real xlsx files carry, is 17 billion cells. So `ROWS(A1:A100)` on a two-row grid is 2 (`packages/sheet/src/test/engine/formula-engine.test.ts`), a range past the grid is empty, and an `INDEX` past the grid is `#REF!`.
- One deliberate departure from Excel: an empty text counts as 0 in arithmetic, Google Sheets' rule, for every file. So `=""*5` is 0, and so is `=E1*5` where E1 is `=IFNA(VLOOKUP(…),"")`, where Excel gives `#VALUE!`. It is the owner's ruling, because a workbook made in Google Sheets multiplies such a lookup's `""` fallback and expects 0. The rule lives once, where the operators `+ - * / ^` take their operands (`ARITHMETIC` in `evaluate-by-operator.ts`), and the grammar's unary minus and plus are those operators applied to 0, and `%` is a division by 100, so `-""` and `""%` are 0 too. Only the empty text: `"abc"*5` and `" "*5` stay `#VALUE!`, numeric text such as `"3"*2` is 6, and `&`, the comparisons and the functions read `""` as before, so `""=0` is FALSE and `SUM` skips it. On a file Excel computed, a recompute of such a cell replaces Excel's cached `#VALUE!` with a number.
- The engine has no spill. An array result (a bare range, `TRANSPOSE`, an `XLOOKUP` returning several columns) shows its top-left value, the value Excel's spill anchor holds, and an empty top-left cell shows 0, as a bare reference to one does, so `=INDEX(O20:Q20,,2)` over an empty P20 is 0, so a recalc of an imported anchor lands on Excel's cached value. Inside another function the whole array passes, so `SUM(XLOOKUP(...))` sums the matched row. Spill is open in [SHEETS-TODO.md](SHEETS-TODO.md#formula-engine).
- formulajs parses an ISO date string as UTC (`DATEVALUE("2026-01-05")`), so the result is off by the zone offset outside UTC. `DATE(...)` is built in local time and is right everywhere. The fix is open in [SHEETS-TODO.md](SHEETS-TODO.md#formula-engine).

The dependency graph has two limits:

- A reference cycle never errors: the visited set in `getCalculationOrder` breaks the walk, and the cycle's cells evaluate in visit order.
- `OFFSET` and `INDIRECT` build a reference their text doesn't hold, which Excel answers by making them volatile: they recalc on every edit. formulajs 2.9.3 has neither, so both evaluate to `#NAME?` whatever their inputs, and the graph records only the references in their arguments: `=OFFSET(A1,1,1)` recalcs when A1 changes, `=INDIRECT("B2")` never. Once the engine computes them they need that recalc on every edit, which the editor has for no function yet ([SHEETS-TODO.md](SHEETS-TODO.md#formula-engine)).

A formula reads every reference in its text, a function's arguments included, as Excel lists a cell's precedents (`list` in `engine/formula-graph.ts`). So `INDEX` needs no special case: the reference it returns lies inside its range argument, and `=INDEX(A1:B3,2,1)` and `=SUM(A1:INDEX(A1:B3,2,2))` both read A1:B3. The engine can't evaluate a range that ends on a call yet, so the second is `#ERROR!` ([SHEETS-TODO.md](SHEETS-TODO.md#formula-engine)). A whole column or row, on the formula's sheet or another (`=SUM(Data!A:A)`), runs to Excel's last row or column (`resolveCellRange` in `engine/formula-utils.ts`). The walk reads no matrix, so a formula that reads a sheet nobody opened follows it, and a grid that grows moves nothing. A sheet name reads its sheet in any case, as in Excel: `=data!A1` reads the sheet named Data, in the walk, the evaluation, a row or column shift and a rename alike (`findSheetByName` in `engine/parser/helper/cell.ts`). Two names are compared by `sheetNameKey`, which folds each character to its uppercase on its own, so the Greek final ς matches σ, and ß, whose uppercase is SS, never matches ss. A tab rename refuses a name another sheet holds in any case, with a notice that says so, but a workbook can still hold Data and data, such as one stored before that rule, or two tabs two peers added at once. Then a name reads the sheet of exactly that name first, so `=data!A1` and `=Data!A1` each read their own sheet, and `=DATA!A1` reads the first of the two. A row or column op on one of them moves only its own references, in the editor, the op replay and the undo stack's shift alike, because each reads a reference's name against the workbook's sheets in `functionStrChange`. A walk that reads many names, such as the recalc, a row or column shift and Import…'s renames, reads them through `sheetFinder`, whose maps are built once per walk, so a reference to a sheet no sheet holds costs no walk of the sheets. The dependency index (`engine/dependency-index.ts`) lists a range by its shape (`layoutOf`). One to the grid's last row, or a long one from the top of its sheet, is listed once per column, and likewise along the rows, so a whole column costs the graph one entry whatever its sheet holds. Any other range is listed in each 64 × 16 block it meets.

## The editor computes on write, the server only what nobody computed

The editor's dependent recompute of an edit runs inside the recipe that emits the op, so recomputed `v` and `m` persist as ordinary ops. A doc edited in a browser is already fresh when the server reads it, once its replay has recomputed what its sheet, row and column ops affect ([§ A sheet, row or column op recomputes on every reader](#a-sheet-row-or-column-op-recomputes-on-every-reader)).

So `readSheetsFromDoc` runs `recalcSheets` only on the export read. Preview and the search extract pass `{ recalc: false }` and serve the replayed values, and a formula cell with no value stays blank. A never-computed workbook costs an unbounded recalc (about 39 s measured), past the 30 s transform deadline of a preview, so every preview of such a doc would fail. An export recomputes under its 120 s deadline, because a deliverable with blank formula cells is wrong output.

Even on export, `recalcSheets` runs only when the envelope says `computed: false` ([the codec](#the-snapshot-is-interned-and-written-only-through-the-codec)). The compaction passes the flag on and runs no recalc ([§ The server folds the log](#the-server-folds-the-log-into-the-snapshot-when-the-workbook-closes)), so a workbook stored as not computed pays the recalc at every export. The xlsx importer runs `recalcSheets` once in its transform and writes `computed: true`, or `false` when its recalc failed, so that export recomputes. Any recalc failure falls back to the replayed values: an export never fails because recalc did.

`recalcSheets` trusts a file's numbers, since they are Excel's. It evaluates only a formula with no stored value or a stored error, reading every other cell as stored, so one guard is all it takes to keep a number, with no flag on the cell. A text formula with an empty `<v>` holds the empty text Excel computed, so `=IF(A1,"",1)` is a stored value too. A stale number in a file stays until an edit reaches it, and the file's recalc-on-open setting isn't read.

The server's recalc, at import and at export, runs under a budget, `SERVER_RECALC_BUDGET` (`document/sheets.ts`). It counts the entries the dependency index lists the ranges in, each range cut to the cells its sheet holds: only a formula cell is ever looked up, so `SUM(A1:XFD1048576)` on a small sheet costs the few blocks or columns the sheet spans. Past the budget `recalcSheets` throws before it evaluates, a recalc failure like any other. A replay in the transform process passes the same budget to each recompute, and past it the values stay as they were, the op stands and the replay reports the skipped recompute. The links between formulas, one for each formula and each formula cell it reads, have a budget of their own (`maxDependencyEdges`), because a whole column costs the index one slot however many formulas in it read it: 20,000 `=COUNT(A:A)` cost 20,000 slots but make 400 million links. The walk over the graph (`affected` in `engine/formula-graph.ts`) counts each formula's links as it makes them and stops past the budget, so such a workbook fails fast, where building the links took minutes and gigabytes. A lookup scans every range listed near its cell, one that covers the cell or not, so the entries it visits have a budget too (`maxDependencyVisits`, from `lookupVisits` in the index), counted without a scan as a formula joins the walk: `recalcSheets` walks every formula, so all of them join before the first scan. The slots are counted as the index lists and unlists them, so a graph a replay holds across batches stays inside the slot budget as it changes. A recompute counts the visits and links its own walk makes, not the whole workbook's: it pays for what its op reaches. Without it, 51,200 formulas reading ranges in the lower halves of their blocks made no link and took 20 s to count. Evaluation is charged each cell a range read covers, cut to its sheet (`maxCellsRead`), and stops at the formula after the one that passed it. The numbers come from the 1,062-file corpus: no workbook needs more than 68.8 million slots (3.3 s), the largest that recalcs needs 43.2 million visits and 21 million links, and the most one reads in under 10 s is 30 million cells (9.9 s). The slot budget is four times the most, the visit and link budgets twice, and the cell budget, 32 million cells, sits just above the most. An export's, a preview's or an extract's replay charges it per batch, so a heavy batch keeps its older values inside a preview's 30 s deadline instead of getting the job killed. The fold has no cell budget, only its deadline ([§ The server folds the log](#the-server-folds-the-log-into-the-snapshot-when-the-workbook-closes)). Two workbooks need 121 and 285 million visits and now fail before any link is counted, and 43 million links took 7 GB, where 2,000 COUNTIFs over `A1:Z1048576` fail the cell budget.

## Recalc keeps what it can't improve

`recalcSheets` and `recomputeAfter` (`engine/recalc.ts`) walk the formula graph ([§ A reader holds its formula graph across batches](#a-reader-holds-its-formula-graph-across-batches)) for the formulas to compute, each after what it reads, and evaluate them with the shared `FormulaEngine` in `evaluateFormulas`, the pass the editor's edits run too. What a formula reads is listed in one place, the graph's `list`, so the editor and the server agree on it. It takes the references from `walkFormulaRefs` (`engine/formula-shift.ts`), the one walker that shifts and renames them too, so what a formula reads and what a row op moves can't disagree, and resolves each through `resolveCellRange` in `engine/formula-utils.ts`. The graph finds a sheet by the names and ids it was built with, so a sheet's add, copy, delete or rename builds it again, since a name may read another sheet then. It keeps the references it resolved by their text. A row or column op clears them, because it rewrote the references it moved, so the ones resolved before it are seldom read again.

Every recompute, in the editor and on the server alike, follows these rules:

- A formula keeps whatever its cell holds, a number, an error or empty text, when this build can't evaluate the formula's own text (`FormulaEngine.cantEvaluate`): a parse failure, a function it lacks in the branch taken, an operator over a range or a name it can't resolve. `evaluateFormulas` holds the one guard. That turns no value from Excel into an error nobody computed, and the readers of the cell read that value. Any other error is an answer and is stored, on an edit too, and a result of `#REF!` always is. So after a delete `=A2*2` shows `#REF!`, where it would otherwise keep a number nothing backs. A text holding `#REF!` that evaluates to `#NAME?` or `#CALC!` first keeps its number, such as `=FILTER(A1:A3,1)+#REF!`. The value can drift from its inputs, and that is the owner's choice over destroying it.
- A sort and a cut move a formula with its value, and the same pass decides from there, so they keep it too. A paste copy and a fill write a new formula in another place, which may read other cells, so its source's number is no answer of its own: they compute it, and one this build can't evaluate shows `#NAME?` or `#CALC!`. A paste and a fill land the copy with no value and seed the recompute with it, so formulas that read each other compute in order and each answer takes its own type, in the number format that came with the copy. A copy landing on its own cell is left as it is.
- A clock or a random number (`NOW`, `TODAY`, `RAND`, `RANDBETWEEN`) keeps its stored value in a recalc and in the recompute after a sheet, row or column op, the way Excel reads a closed file, so an export is deterministic and every tab agrees. The recompute of an edit does compute one, because its author sends the value.
- A function Excel has and this build lacks can't evaluate even inside `IFERROR` or `ISERROR`, because they hand its `#NAME?` on rather than trap it ([The engine is the half the server imports](#the-engine-is-the-half-the-server-imports)). So `=IFERROR(FILTER(…),"none")` keeps its number instead of computing `none`, while `=IF(A1>0,A1+1,FILTER(…))` recalculates, since the branch it takes is one the engine can compute. A `#NAME?` read from another cell is that cell's answer, so `=IFERROR(B1,"none")` over such a cell stores `#NAME?` over its number.
- A formula that uses a name the engine can't resolve keeps its stored value even when its result is no error. The import writes each defined name into the formulas that use it, and one it can't stays as written ([EXPORT.md](EXPORT.md#an-xlsx-defined-name-is-inlined-into-the-formulas-that-use-it)). The engine has no names, so `IFERROR` traps that name's `#NAME?` and computes a fallback Excel didn't. `cantEvaluate` asks the parser about each name `inlineNames` finds, the walker the import inlines names with, so a name shaped like a cell past column XFD, such as `RhoCO2`, counts too.
- An operator applied to a range or another array, as in `SUMPRODUCT(A1:A3*B1:B3)`, `-A1:A3` or `IF(A1:A3>0,1,0)`, has no answer, because the operators are scalar. It evaluates to `UNSUPPORTED_ARRAY_OPERATION` (`engine/parser/error.ts`), which reads `#CALC!`, Excel's word for what its calculation engine doesn't support, and which no function traps, so `IFERROR` around it computes no fallback. `cantEvaluate` takes it as no answer, so a stored value stays through a recompute and an edit, and a formula typed with no value to keep shows `#CALC!`. A `#CALC!` read from another cell is that cell's. A broken reference the operator itself reads makes it `#REF!`, as in `=#REF!*A1:A3`. One elsewhere in the text does not, so `=SUM(A1:A3*2,#REF!)` is `#CALC!` and keeps its number. A function handed a range in a scalar parameter, such as `SUMPRODUCT(ISNUMBER(A1:A3))`, is not caught: it answers `#VALUE!` or a scalar ([SHEETS-TODO.md](SHEETS-TODO.md#formula-engine)).

Every cell is guarded, so one poisoned formula never aborts the pass. A result that is no finite number, which many of formulajs's functions answer, such as `STDEV(5)`, is `#NUM!` (`evaluateCompiled`), because JSON turns NaN into null and a tab and a joiner would hold different cells.

## A reader holds its formula graph across batches

At mount the Workbook materializes each sheet's `data` and evaluates nothing. Displayed values come straight from the stored workbook, and an edit recomputes only the affected sub-graph (`execFunctionGroup`), so its cost follows the edit, not the workbook.

The formula graph (`FormulaGraph` in `engine/formula-graph.ts`) holds which cells hold a formula and, through the dependency index, which formulas read each cell. The editor keeps one in `ctx.formulaCache.graph`, built from an idle callback, so the first edit on a large workbook doesn't pay a multi-second build. Whichever comes first, the idle build, an edit or a paste, builds it whole by scanning each sheet's `data` for `f`, the one record of which cells hold a formula (`isFormula`), from a plain `current()` snapshot, because reading every formula through an immer draft is slow. The replay builds one at the first batch that recomputes and keeps it across batches, until a batch adds, deletes or renames a sheet or a step passes a budget. There is one graph mechanism, and the editor, the replay and so the compaction all use it.

Once built, the graph follows every change, so a batch costs what it touches:

- **A formula's key is not its place.** Each formula gets a key when it is listed and keeps it while row and column ops move its cell, so a move rewrites no list in the index. `formulaAt` finds a formula by its cell.
- **A row or column op shifts the graph** (`shift`): the formulas on its sheet move with their cells, one on a deleted line goes, and only a formula whose text the op rewrote lists its references again. The text is the one truth of what a formula reads, so no second rule says where a reference goes.
- **A range is cut to the cells its sheet holds and the line past them**, where a delete of the sheet's last rows or columns seeds the formulas that read them, and the graph keeps, per sheet, the formulas a cut shortened. When a sheet's size changes, such as after an insert or a paste past the last row, those list again at the next walk (`affected`). A sheet with no matrix, such as a copy nobody opened, has no size, so a formula reading it lists it once it has one.
- **Cell patches update it cell by cell** (`followPatches`): local writers through `setFormulaCellInfo`, and undo, redo and a peer's batch through their `data` patches, because every formula change carries one. A patch that writes a whole row or matrix, or adds or removes a cell and so moves the ones after it, reads that sheet again. No patch writes a sheet's id or name, which the graph keys on: the batch drops such a write.
- **A sheet's rename, add or delete builds it again**, on the next use in the editor and at the next recompute in the replay, since a name may read another sheet then.

A shift, a patch or a recompute past a server budget may leave the graph short, so the replay drops it, and the next batch that recomputes builds a new one. A recompute past one leaves the batch's values as they were, its ops stand, and the replay reports a `SkippedRecompute` to its `onDropped`. The editor logs one as a warning, as the replay does by default. `packages/sheet/src/test/engine/held-graph.test.ts` applies random batches of row, column, cell and sheet ops on several sheets and checks, after each, that the editor's graph reaches what a fresh build reaches, and that the replay's and the editor's values are a fresh recalc's. Under a slot budget it checks that the held graph skips the recomputes, and computes the values, that a graph built for each batch does.

## Number display strings go through `numberDisplay`

`numberDisplay(value, fa)` (`@workspace/formula/format`, the one wrapper of `numfmt` that charts share) turns a number into its `m`. Typed entry, paste, sort, autofill, the toolbar format change, the format painter, recalc and the xlsx importer all call it. A mask renders the exact value. General is Excel's General at default width, so float noise hides (`0.1+0.2` shows `0.3`), long values cut to 11 characters and large or tiny values go scientific. A malformed format, which an xlsx file can carry, falls back to General. numfmt rounds a number as its 15-digit decimal, a half away from zero, as Excel does, so `1.005` under `0.00` is `1.01`. It carries one patch, `patches/numfmt@4.1.3.patch`, listed in `patchedDependencies` in the root `package.json`: the weekday of a day before day 0 (`dddd` of -7) came out empty, or as the next day's name when the number had a time, because `runPart` took it from the truncated number with a remainder that goes negative. The patch takes it from the day the date is written from, in both builds the package ships (`dist/index.js` and `dist/index.cjs`). Once a release carries the fix, delete the file and its `patchedDependencies` line. The input parser (`parseCellInput`) still formats on its own.

A typed number is stored as a number in `v`, unless the cell is text-formatted. Pasted plain text goes through the same `setCellValue` parse as typing. A formula's text result stays text (`=TEXT(5,"000")` is `"005"`). A date's value reads as the date it shows (`getCellValue`), for a copy or a dropdown, but its formula is still its formula, so the bar and the editor open on it. Copying a General number writes 15 significant digits (`copiedNumberText`), not the 11-character display, so a paste elsewhere keeps the precision. A formula that joins a number into text (`&`, `CONCATENATE`, `CONCAT`, `TEXTJOIN`) writes it the same way, through `numberText` (`engine/format.ts`), at Excel's 15 significant digits: `(0.1+0.2)&""` is `"0.3"`, and a number past 15 digits is E notation (`1E+21`).

A cell without its own horizontal alignment takes Excel's General alignment by its value (`generalAlign` in `engine/format.ts`, read through `normalizedCellAttr` in `state/modules/cell.ts`): a number or a date right, a boolean or an error centred, text left. The painter, the text layout, the overflow and the HTML and PDF export read it there. A tick box is the exception: it sits where the cell's own alignment puts it, and centred without one, as in Google Sheets, so a ticked, an unticked and an empty cell's box sit in one place (`checkboxAlign`, which the painter and the click share).

## A copy puts the cells on text/plain as TSV

A range copy writes three flavors: the HTML table with the cells' styles, the Eigen clipboard payload, and TSV on `text/plain` with tabs between cells and newlines between rows. `copy` (`state/modules/clipboard.ts`) builds the table and the TSV in one pass over the same cells, each cell's display text with General numbers at 15 digits. A cell holding a tab, a line break or a leading quote is quoted and its quotes doubled, as Google writes it, through `cellsToTsv` in `@workspace/lib/clipboard`; a quote inside text stays as it is, so `12" pizza` pastes as typed. The Eigen text item carries the same cells unquoted, tabs and newlines between them, because Docs reads it as text rather than as TSV. The HTML table writes a cell's font size in pt, the unit every font size on the clipboard is in ([CLIPBOARD.md](CLIPBOARD.md#a-font-size-crosses-in-pt)), and the table paste reads a size in pt as pt and in px at 96 dpi. A collaborator or an xlsx can store any value, so the table writes a color only as a hex color, a border's else transparent, a row height, column width or merge span only as a finite number, else the default, and escapes every style attribute. The plain text is what a paste into a text field, a chart's Edit data grid or another app without an HTML reader gets, so it has to keep the grid's shape. The plain-text paste in Sheets itself splits on tabs and newlines and doesn't unquote, so a quoted multi-line cell pasted as plain text lands split ([SHEETS-TODO.md](SHEETS-TODO.md#bugs)).

## A copy carries hidden rows and columns, but not a filter's rows

A copy, a cut, a drag move and the format painter carry every row and column of the range, hidden ones included, as Excel does: the hidden cells' values, formats, borders, validation rules, links and merges land too. The destination's rows and columns keep the hidden state they had. Excel pastes into consecutive rows and leaves the target's row and column settings alone, so a block pasted over a hidden row fills it and the row stays hidden. The one exception is a filter. Excel copies only what a filter shows, so a copy, and the format painter, which takes what a copy would, leave out the rows an active filter hides and close the block up. A cut or a drag moves every cell of its range, and such a row would land out of sight or stay behind, so it refuses with a notice and writes nothing (`movedLines`). A merge a filter's row straddles can't close up, so a carry that touches one refuses too. A paste and the format painter ask again as they land, since a filter can arrive after the copy.

A cut or a drag moves a formula by Excel's rule (`moveFormulaRefs` in `engine/formula-shift.ts`): a ref wholly inside the moved block follows its cells, `$` or not, and any other ref still means the cell it meant. So `=A1*2` cut from One to Two becomes `=One!A1*2`, while `=B1` where B1 moved too reads the moved cell, unqualified, on the new sheet. A move therefore changes a formula's value only through the cells it reads, so it recomputes the dependents of the vacated and the landed cells and evaluates nothing else (`packages/sheet/src/test/state/events/cut-across-sheets.test.ts`). A formula outside the block that reads a moved cell doesn't follow yet ([SHEETS-TODO.md](SHEETS-TODO.md#bugs)). A paste that covers a merge whole replaces it, on every path, as in Excel, and one that would land on part of a merge is refused with a notice (`roomFor` in `state/events/paste.ts`).

`carriedLines` (`state/modules/carry.ts`) lists the rows and columns a carry takes, and `carryCells` lands them for a paste, a cut, a drag move, a fill and the format painter. It keys every side table by the source cell it came from, so in a closed-up copy the borders and rules stay with their cells. A source cell without a rule takes the destination's away, as in Excel, one cell at a time, so a paste can leave a hole in a rule (`C1:C3` becomes `C1,C3`), and a peer's rule elsewhere survives. Only a rule that changes is written, on its own. What of the cell itself lands, its link among it, each path says through `carryCells`' callback: a paste and a fill land the cell with its link, so a source cell without a link takes the destination's away, and the format painter leaves the destination's value and link. A row is filter-hidden when an entry of the sheet's `filter` lists it and `rowhidden` still holds it. A row the user hides by hand while a filter is on is carried. A filter adds and removes only the rows it hides itself (`saveFilter` and `clearFilter` in `state/modules/filter.ts`), so a row hidden by hand stays hidden when a filter is applied, changed or cleared. A hand-hidden row the filter hides too is listed in its entry, though, and shows again when the filter stops hiding it. An imported xlsx has no filter entries ([SHEETS-TODO.md](SHEETS-TODO.md), "Filter criteria don't round-trip"), so its filtered rows are carried like hand-hidden ones. The clipboard's TSV and table use the same list, so another tab or app gets the cells a paste in this tab lands. Excel writes only the visible cells for another application. Eigen writes the hidden ones too, so a paste in another tab, which reads the table, lands what a same-tab paste lands. `packages/sheet/src/test/state/hidden-carry.test.ts` pins it.

## A sort moves a cell's contents and leaves the sheet's rules where they are

A sort (`sortDataRange` in `state/modules/sort.ts`) moves a cell's contents, its cell formats and its link, and leaves borders, validation and conditional-format ranges where they are, as Excel does. So it goes around the carry and writes no rule, and neither a row that stays nor a cell landing on its twin is written. A formula is shifted to the row it lands on with the value it holds, and the recompute after the sort evaluates it there in one pass, even when no cell it reads moved. Only the cells it writes seed that recompute, so a formula in a row that stays, hidden or not, keeps a stale number or a random one until an edit reaches it. So does one landing on its twin, and a formula elsewhere that reads no written cell.

A hidden row stays where it is, hidden by hand or by a filter, and a sort reads and lands only the rows that show, as in Excel for the web. `rowhidden` holds rows by index, so a row moved into a hidden one would vanish and the row moved out of it would show.

## Enter and Tab commit an edit and move on

While a cell is open, Enter commits it and moves down, and Tab commits and moves right, Shift+Tab left, as in Google Sheets. Both go through `commitEdit` (`state/events/keyboard.ts`), which writes the cell and collapses the selection to it before the move. A visible formula suggestion takes Tab first and stops it, so Tab picks the function instead of committing.

The open editor's cell is `ctx.editingCellPosition`, and every commit path writes there. A row or column op on the current sheet, a peer's or the tab's own, moves it with its cell (`followView`), and the selection with it, so Enter writes where the person was typing, not into the row that slid under the editor. The editor keeps what was typed through that move, because every opener goes through `openCellEditor` (`state/modules/cell-editor.ts`), which sets the position, the text and the caret in the opener's recipe, and nothing loads the cell after that. Text an opener brings, such as Insert function's or autosum's, goes to the formula bar there too, also over an open edit, so no opener syncs the bar itself. An opener with no text leaves the bar alone: it already shows the cell, and a click in the bar holds its caret there. A delete of that cell closes the editor without writing and drops the selection, so the keys typed next write nowhere.

## The cell editor edits rich text as runs

A rich-text cell keeps its text as runs in `ct.s`, each a piece of text with its own weight, slant, decoration, color, size and font. While the cell is open, the in-cell editor shows the same runs as spans, and `state/modules/inline-string.ts` is the one model between the two. The editor's DOM reads into runs, a toolbar format applies to the selected characters (`formatEditorSelection`), the runs go back as spans (`runsHtml`) and the selection comes back by character offset. `updateCell` commits what `committedRuns` reads, so the cell gets what the editor shows. The reader takes whatever markup the editor holds: our spans, the browser's own `<b>`, `<br>` or `<div>`, and bare text typed beside a span. Offsets count text, not HTML, so an `&` or a `<` can't shift a format, and a `<br>` or a block counts as the one line break it reads as, both ways. A run it reads is whole, all seven style keys, with the color as hex and the font as a name, as the xlsx import stores runs. Stored runs come from a collaborator or an xlsx, so `runStyleOf` checks them before `runsHtml` writes CSS: a color that isn't hex, a size that isn't a number, or a font name with `;`, `(`, a quote, a backslash or a control character falls back to the default (`cellFontName`, `packages/lib/src/sheets/fonts.ts`). So a real name with an apostrophe, such as O'Neill, draws in the default too and exports to xlsx as Inter. The editor box and the copied table's HTML read a cell's own font keys through the same `runStyleOf` (`getFontStyleByCell`), so the box and the runs typed in it agree on a legacy string size, and a cell-level color, fill or font, or a conditional format's colors, that isn't a plain value writes no CSS there either (`hexColor`). The canvas and the format toolbar read a style through `runStyleOf` too, so a run that leaves out its size or color draws, edits and shows in the toolbar at the default, 10 pt in black, and its underline is as thick as its glyphs are large. Every size, a plain cell's included, goes through `cellFontSize` in `@workspace/lib`, which keeps Excel's 1 to 409 pt without rounding, so the canvas, the editor and the xlsx, HTML and PDF exports draw and write the one size a file brought in; only the toolbar's size box steps and caps at 400, as Docs' does.

A paste while the editor is open is its plain text, as in Google Sheets (`onPaste` in `InputBox`): it types as typed text would. A paste onto a closed cell goes to the grid as before. One handler owns each paste: the Workbook's document `paste` listener returns while a cell is open, so the text lands once and no image, chart or rows land on the grid.

Text outside any styled element has the cell's own style, which the editor box shows: `getStyleByCell` styles the box for a rich cell too. A span states only where its run differs from the cell, so a word un-bolded in a bold cell reads back as not bold. Text all in the cell's style commits plain, so a format undone before Enter leaves no runs. A format while the editor holds a formula goes to the cell, as before.

⌘B, ⌘I and ⌘U while the editor is open on text go to the toolbar's handlers (`InputBox`), so the browser never writes its own `<b>`. They match through `SHEET_HOTKEYS`, as the grid's do ([§ Every shortcut is defined once](#every-shortcut-is-defined-once-in-sheet_hotkeys)). A format on a bare caret waits for the next `beforeinput` and types that text in its style, as Google and Excel do, and a caret that moves drops it. Text typed over a selection takes the style of its first character, as in Google Sheets and Docs: the browser drops a span whose text is all selected and types plain, so `typeStyledText` types over a selection that starts in a styled run itself and leaves one that starts in the cell's own style, or a formula, to the browser. A toolbar control that takes the focus, such as the size box or the color popover, formats the selection the editor last had: `InputBox` keeps it on every `selectionchange` (`rememberEditorSelection`) and forgets it, with a waiting caret format, when the editor closes. As a menu or popover of the menu bar or a tab's menu closes, the size box blurs to nowhere, or a sheet dialog closes, `useCellEditorRefocus` gives the focus and that selection back to the editor: Radix would focus the menu's trigger, where the next keys type nothing. It reads whether a cell is open as the control closes, so the editor that Insert function's OK opens gets its caret back after the bracket. Whatever took the focus as the menu closed keeps it, as in Docs' `keepEditorFocus`: a dialog the menu opened, such as Data validation, or an input a press outside landed on ([LAYOUT.md](LAYOUT.md#the-app-bars-menus-are-one-radix-menubar)). The size box drops Enter's own action, which would otherwise type a line break over the editor's selection once the focus is back. While a cell is open, the format toolbar shows the run at the caret (`useEditorSelectionStyle`). The menu bar reads it once, on one listener, and hands it to the toolbar and the Format menu. A caret that moves inside one run keeps the same style object, so neither re-renders. That style is state set on `selectionchange`, never a DOM read during render: the app's React Compiler memoizes such a read, and a moved caret changes none of its inputs, so the toolbar would stay on its first answer while a unit test, which runs without the compiler, passes.

The canvas wraps a rich cell between words, inside a run too, and the runs on one line share its baseline (`getCellTextInfo`, `state/modules/text.ts`). It splits runs into words only when the cell wraps, and keeps the line's width as it goes, so a long cell lays out in one pass: the painter lays out every cell it draws, with no cache of the layout. The words of one style on a line join into one piece before they are placed, so right-to-left text reads in its own order and the canvas kerns across spaces. Runs of different styles on one line still go left to right. Wrap, a size from the Format menu or the toolbar's box, and a commit grow the row to the wrapped lines (`growRowToFit`), laid out at the painter's text box, so the row holds every line the painter draws. Such a caller passes no cell height, and `getCellTextInfo` then lays out every line of a plain cell, where the painter stops at the lines that fit the row. The HTML, PDF and preview export still draw a rich cell in its own style ([SHEETS-TODO.md](SHEETS-TODO.md#bugs)). `packages/sheet/src/test/state/modules/inline-string.test.ts` pins the editor model through the toolbar handlers and the commit.

A formula in the editor is colored spans, which `handleFormulaInput` rebuilds from the text on every key. The caret goes back as one offset into the whole text, read before the rebuild and placed after it (`selectionTextOffsets` and `selectTextOffsets` in `state/modules/cursor.ts`), and F4's reference cycling uses the same pair. A span number with an offset inside it doesn't survive the rebuild: a string literal or a line break splits the text into other spans than before the key, and the caret then landed in front of what was typed.

## Every shortcut is defined once, in `SHEET_HOTKEYS`

`SHEET_HOTKEYS` (`state/events/keyboard.ts`) holds each sheet shortcut as one TanStack hotkey string, such as `Mod+B`. The grid's `handleWithCtrlOrMetaKey`, the Workbook's undo and redo, the open cell editor's ⌘B, ⌘I and ⌘U and the focus lock all match a keydown against it with `matchesKeyboardEvent`, and the Format menu shows it with `formatForDisplay`, ⌘\\ on Clear formatting included. The Edit menu is the shared `EditMenu`. Its Undo, Redo and clipboard rows show lib's shared constants, such as `CUT_HOTKEY`, and the table takes those keys from the same constants. So a menu row can't name a key that doesn't work, and `Mod` reads ⌘ on a Mac and Ctrl elsewhere, as in Docs. Find and Find and replace show the find bar's own `FIND_HOTKEY` and `FIND_REPLACE_HOTKEY`. The screen-reader shortcut list in the Workbook reads the same table with `formatWithLabels`. `src/test/components/Workbook/hotkeys.test.tsx` and `src/test/state/events/keyboard.test.ts` spell every key out, so a changed definition fails a key test and a label test.

The matcher takes the letter the layout types, else the physical key, so ⌘B still bolds on a Russian layout. The physical key also matches when the layout types another Latin letter, so the order of the checks matters: the grid checks ⌘X before ⌘B and ⌘C before ⌘I, because Dvorak types x on the B key and c on the I key. The collisions that remain are a known bug ([SHEETS-TODO.md](SHEETS-TODO.md#bugs)).

While a cell is open, ⌘Z, ⇧⌘Z and ⌘Y belong to the browser, which undoes the typing in the editor, as Google Sheets does. The Workbook runs the sheet's undo only while no cell is open. Otherwise one ⌘Z would undo the typing and the sheet's last edit at once.

A key during an IME composition is the IME's, in the grid's handler, the cell editor and the formula bar alike (`imeOwnsKey`), so the Enter that confirms a composition keeps the cell open and the next one commits it. That is `isComposing`, or keyCode 229 in an open cell, because Safari fires that Enter just after `compositionend`. On a closed cell a 229 with `isComposing` false is the key that starts typing, as an IME's first key and an Android keyboard send it, and it opens the cell.

Keys with a name rather than a letter, such as Enter, Tab, the arrows, F2, Escape and Delete, still dispatch on `e.key` in `handleGlobalKeyDown`, and so does Ctrl+Shift+; for the date and time: a hotkey string can't name the shifted punctuation a layout types there.

## Conditional formats evaluate headless

`evaluateConditionalFormat(rules, data, options?)` (`engine/conditional-format.ts`) returns the `"r_c"`-keyed style map the canvas paints, and the HTML export calls it too ([§ The export paints conditional formats with the grid's evaluator](#the-export-paints-conditional-formats-with-the-grids-evaluator)). Without an evaluator, formula rules are skipped. Both callers pass the same one, `createCfFormulaEvaluator`.

Every rule scans only the materialized matrix, because Excel writes a whole-column rule as `A1:A1048576`. Overlapping rules layer per style property in rule order, so a later rule's fill never erases an earlier rule's text color. `textContains` ignores case and `duplicateValue` skips blank cells, both as in Excel.

## A formula rule is anchored at its first range's corner

That is Excel's anchor: every cell of every range evaluates the formula at its offset from the top-left of the first range. `createCfFormulaEvaluator` compiles each formula once and evaluates it at that offset. It shares `offsetCoordinate` and `offsetRange` with `functionCopy`, the text shifter paste and autofill use, so shifted text and a compiled offset read the same cells. The xlsx importer keeps a rule with all its ranges, and the exporter writes one multi-range `sqref`.

Every rewrite of a rule's ranges (a carry, a row or column delete, the preview's clip) goes through `withCfRanges`. When the first range starts somewhere new, it re-expresses the formula from the new corner, so every cell keeps the relative formula it had. A carry joins the landed ranges behind the rule's first range and keeps its corner (`joinedRanges`), so only a hole in that range, a cut of it or a landing on its corner moves the corner: moved up, the formula could run off the sheet. An insert moves corner and references together, so it doesn't re-anchor.

One edge stays. A formula that reads above or left of its corner (`=A4>0` on `A5:A10`) can't be re-expressed from a corner nearer the sheet edge than it reaches, because A1 text has no row 0. `functionCopy` writes `#REF!` and the rule stops matching, as it does for a rule cut whole to near the top ([SHEETS-TODO.md](SHEETS-TODO.md#xlsx-round-trip-fidelity)).

## A dialog value typed with `=` is stored as a formula rule

In the conditional formatting dialog, a value that starts with `=` names one cell, such as `=A1` or `=Data!$A$1`, as in Excel and Google Sheets. The engine's comparison rules, such as `greaterThan` and `between`, compare against a literal, so they can't read a cell. `addConditionRule` (`state/modules/condition-format.ts`) stores such a rule as a `formula` rule instead, with the formula Excel writes for it, anchored at the selection's top-left: Greater than `=A1` over B2:C3 becomes `=B2>A1`. That is the shape the xlsx import gives a `cellIs` rule whose operand is a reference (`apps/api/src/lib/import/sheets/rules.ts`), so the rule reads the cell each time it paints, and a change to A1 repaints the range. Manage rules then lists it as Custom formula, not as Greater than. A value without `=` stays the literal, even one that looks like a cell, such as `FY2024` or `A1`: Equal to and Text contains compare it as text, and a number rule refuses it. A range or a list after `=` is refused, since a comparison reads one value. `packages/sheet/src/test/state/modules/condition-format.test.ts` pins these cases.

## Row and column shifts rewrite every sheet's formulas

`applySheetsInsertRowCol` and `applySheetsDeleteRowCol` (`engine/rowcol.ts`) shift the cells with their links, geometry, merges, borders, conditional-format rules, validation rules, frozen pane and filter of the changed sheet, and stamp every merge's cells again, so the `mc` on each cell agrees with `config.merge` on a live tab and in the replay alike, and formula text and chart refs in every sheet. Only references that resolve to the changed sheet move: unqualified ones on it, `Sheet!`-qualified ones anywhere. So a formula on another sheet whose text holds no spelling of the sheet's name, in any case or quoting, skips the walk (`mayShiftOffSheet` in `engine/formula-shift.ts`), which on a large workbook is most of them. The walk writes back only the references the op moves and copies every other character as typed, newlines, tabs and the spaces beside a colon included (`walkFormulaRefs`), so a formula no ref of which moves keeps its text byte for byte, on every sheet. A range whose legs name two sheets, `A!A1:B!B2`, is `#VALUE!` to the engine, so no op or rename changes it; Excel's reference across sheets, `A:B!A1`, names no sheet the engine knows, so it is `#VALUE!` too and stays as written. The undo stacks skip the same formulas when a peer's op moves them (`shiftEntries` in `state/modules/history-shift.ts`). A sheet without a matrix, in the replay any sheet a batch doesn't name, has its stored cells' formulas moved instead, so the live tabs, a joiner, the server's read and the next snapshot agree. A tab rename walks the same text (`rewriteSheetFormulas` in `engine/formula-shift.ts`). A reference wholly inside a deleted band becomes `#REF!`, and a whole-row or whole-column range keeps both legs. A delete of the whole frozen band ends the freeze on that axis on every reader (`shiftFrozen`), and the undo entry's recorded field brings it back. A filter's criteria stay with their column, as in Excel: a row delete moves the rows an entry hides and keeps the entry when none is left, a column delete takes the entry on that column, and a delete of the header row removes the filter (`shiftFilter`). The rows a removed entry or a removed filter hid show again, by the rule clearing the filter by hand uses (`showFilterRows`), so a row hidden by hand stays hidden, and the undo of the delete brings back the filter and its hidden rows. A `row_focus` of -1 an older build stored stays until someone unfreezes or freezes anew: nothing moves it, and `freezeOf` pins the top row for it. A selection the delete takes whole lands on the row or column that took its place, or the new last one, whoever deleted it ([§ Every tab applies the batches in the log's order](#every-tab-applies-the-batches-in-the-logs-order)). The functions are generic over the sheet type, so the editor's wider sheet flows through with its extras.

A forward row or column op ships its marker and nothing else (`patchToOp` in `state/utils/patch.ts`), since every receiver's engine makes the same writes. The author's copy of a field would land on a receiver's own shift of a peer's edit sent at the same time, and the tabs and a joiner would part ways. So a peer's rename, freeze, filter, rule, link or chart edit sent at the same time survives, and the op moves it. An edit that also writes a sheet field in the same recipe as the op, such as a row height set beside an insert, keeps that write on the author's tab alone: every receiver drops it. Such a write goes in an edit of its own.

## A sheet, row or column op recomputes on every reader

A row or column op, a sheet's add or delete and a rename ship no values. So every reader recomputes what the op can affect once the whole batch applied, through `recomputeAfter` (`engine/recalc.ts`) at the end of `applySheetsBatch`. That is how `=A2*2` over a deleted row shows `#REF!` and `=SUM(A1:A3)` follows a shrunk range, on the author, a peer, a joiner and the server alike. Values on the wire would land on a receiver's own shift of a peer's edit, and writing every formula one op changes costs the wire what the marker saves.

`seedsOf` (`engine/replay-ops.ts`) names what a batch can affect: the lines the op opened or closed, moved through any later row or column op of the batch as the cells on them move, the cells the batch's own patches wrote, every formula holding `#REF!`, and every formula naming a sheet the batch added or renamed. Deleting a tab turns a formula naming it into `=#REF!*2`, as a row delete does, and a list source or a link naming it reads `#REF!` too, so a new tab with the old name heals none of them (`applySheetDelete`). A batch with no such op recomputes nothing, since an edit carries its own values.

The recompute runs per batch, not once per replay, because a later batch is a delta against a state that includes the recompute: one pass at the end gives wrong values. In the transform process each one runs under `SERVER_RECALC_BUDGET`, the fold's with its deadline in place of the cell budget, and past it the values stay as they were, the op stands and the compaction ends before that batch ([§ The server folds the log](#the-server-folds-the-log-into-the-snapshot-when-the-workbook-closes)). `packages/sheet/src/test/state/modules/structural-recompute.test.ts` pins these on two tabs and a joiner.

## Images and charts are floating records in one paint order

`Sheet.images` and `Sheet.charts` map an id to a `SheetImage` or a `SheetChart`, both a `SheetFloatingObject`: a box in grid pixels from A1, an `angle` in degrees clockwise about its center (absent reads as 0), and an `index`, a fractional key that orders images and charts together for painting, ties broken by id. Two maps rather than one with a kind field, so the chart-only paths (ref shifts, the row and column write-back) stay chart-only. `floatingItems` (`packages/lib/src/sheets/floating.ts`) is the one answer to which objects a sheet holds and in what order; the editor's overlay, the export and a z-order move read it. `nextFloatingIndex` puts an insert above both kinds, and a z-order move goes through `zOrderKeys` over both, so neither throws on the tied keys two peers inserting at once leave behind. Both repair a tied or malformed key on the record and write the repair with their own write, because a malformed key such as `zz` sorts above any key an insert could take. An image's id is a uuid, because two peers must never write one key.

A file or a peer can store any box, a string included, and a side in the billions overflows the painter's stack, so `sheetFloatingBox` clamps every box wherever one is written or drawn: the xlsx import, insert, paste, move, resize and rotate, `renderSheetChartSvg` and the export. A side is at most `CHART_MAX_SIDE`, the 2112 px Docs caps a chart at, the corner lies on Excel's grid at the default track sizes, and an angle that is no finite number is 0. An inserted image larger than that is scaled down whole, so it keeps its aspect. Copying a sheet gives its images and charts fresh ids.

Each writer writes one object of the current sheet under its own key, field by field: the shared ones in `state/modules/floating.ts`, a chart's spec, range and look in `chart.ts`, an image's insert and media name in `image.ts`. A move writes `x` and `y`, a first rotate adds `angle`, a spec edit writes the parts it changes, each one string, a look edit writes only the look fields it changes, and none ever replaces a whole existing object. So two people editing different objects merge, and a write into an object a peer deleted finds no parent, so it is skipped on every client and in the replay instead of bringing the object back, while the rest of its batch applies: an insert whose batch repairs a tied key on an object a peer deleted keeps its insert ([§ A write whose parent is gone is skipped alone](#a-write-whose-parent-is-gone-is-skipped-alone)). A write into an object applies when the object is there as the batch's earlier writes leave it. An object's fields are plain values, a chart's part one string, so `opToPatchOnSheets` drops a write below a chart's field and the apply skips one below any plain value. Undo and redo skip the same writes of their entry (`patchStep` in `state/modules/history.ts`), so the undo of a merged gesture that edited and then deleted an object, which puts the object back and then its field, ends the same everywhere. What writes a whole object, redoing its insert or undoing its delete, brings back one a peer deleted only when the delete comes first in the log, on every tab and in the replay alike ([§ Every tab applies the batches in the log's order](#every-tab-applies-the-batches-in-the-logs-order)). `packages/sheet/src/test/state/modules/floating.test.ts` pins both kinds on the author, a peer and a joiner.

The selected object is `ctx.activeObject`, an image or a chart and whether a chart's editor is open, per client, so `filterPatch` drops it.

## A pending upload's name is swapped on every sheet and in the undo stack

An image inserted from an upload carries a `pending:` name until the upload settles ([MEDIA-REFERENCES.md](MEDIA-REFERENCES.md)). `replaceImageMediaName` and `removeImageByMediaName` walk every sheet, because the user may have switched tabs since the insert, and the zombie sweep collects pending names from every sheet too. The swap records no undo step, so the entry that inserted the image still holds the pending name, and a redo, or the undo of a delete, would bring back an image that never resolves. `replaceMediaNameInHistory` renames it in the undo and redo stacks as well, in a patch on the image, on its sheet's images map or on the whole sheet, a copied or deleted sheet's included (`packages/sheet/src/test/components/Workbook/image-undo.test.tsx`, `packages/sheet/src/test/state/modules/floating.test.ts`).

## A chart is a floating record whose refs name sheets by id

A chart stores its spec as the eight JSON strings a canvas chart element and a doc's chart node store, a field per part, `specChart` to `specData`, beside its look ([CHARTS.md](CHARTS.md#a-spec-is-eight-parts-each-a-record)). Only `readChartSpec` (`packages/lib/src/charts/`) reads them, and `setChartSpec` (`state/modules/chart.ts`) applies a change onto them as stored and assigns the parts whose text it changed (`chartSpecWrites`), so immer ships one replace per changed part ([CHARTS.md](CHARTS.md#an-edit-is-a-change-applied-onto-the-spec-as-stored)). A part is the merge unit: two peers who edit two parts, a title and a series color, both keep their edit, and of two edits of one part, two series' colors, the later one in the log stands. An undo of a style edit does nothing once a peer has since written that part. A part that is no string reads as missing and takes its defaults. So a chart an older build stored with `specAxes`, `specPlots`, `specSeries` and `specPoints` as records draws with its type, title, legend, data, box and look, and without its axis settings, stacking, series styles and slice colors, and the next edit of such a part stores a string. A range ref in the spec names its sheet by id, so renaming a sheet moves nothing. Copying a sheet points its charts' refs to the copied sheet at the copy, as Excel and Google do. An xlsx import brings a chart Excel anchors on a worksheet in as one of these records over the same cells, and a chart sheet as a sheet holding its chart ([EXPORT.md](EXPORT.md#an-xlsx-chart-comes-in-over-the-cells-excel-draws-it-over)). The import reads an anchor's box only, so an imported chart stores angle 0.

## Chart refs shift with rows and columns, and an undone delete ships them

A row or column insert or delete shifts every ref to the edited sheet, on every sheet's charts, inside the engine, so the editor, a peer and the replay all run it. The rule is Excel's, and it is one function for every holder of a row or column index, `mapSpan` with `mapIndex` for a single line (`@workspace/formula/text`): an insert at or before a range moves it, inside grows it, right after leaves it, and a delete shrinks it. Chart refs, conditional formats, validation rules and the filter call it through `shiftRange` (`engine/rowcol.ts`), which leaves a range over the whole axis as it is, so a whole-column rule or ref stays `A:A` under any row op, as in Excel. Merges and the frozen pane call it on their own, so a row inserted right below a one-row merge is not merged, a merge an op cuts to one cell is removed with that cell's `mc` (a one-cell merge an import stored only moves), and a row height or border an insert pushes past the grid's last line goes. Deleting all of a values or categories ref makes it null, and a deleted name cell leaves the series unnamed. A point's style, such as a pie's slice color, stays at its index, as in Google Sheets, so after an insert or a delete inside the categories the slice at that place has it ([CHARTS.md](CHARTS.md#a-spec-is-eight-parts-each-a-record)). An insert stops a ref's end at the grid's last row or column, because `parseChartSpec` refuses a ref past it and the chart would never read again, and a ref it pushes off the grid whole is gone, as one a delete takes.

`writeSheets` (`state/modules/apply-ops.ts`) writes every field the op changed into the context, its charts one at a time and a chart field by field, so an undo of the op carries a replace of each shifted chart's `specData`, on the edited sheet and on any other. The op itself ships no chart write: every receiver's engine shifts the charts as the author's did, and the author's write would land on a receiver that also took a peer's row op sent at the same time, a row off. A peer's move or delete of a shifted chart, its title, or its recolour of a slice, at once or later, survives on every client and in the replay: the box stays the peer's, and a part write into a deleted chart is dropped. A recolour names its slice by index, which the op doesn't move, so it lands on that index whichever comes first in the log. A row op moves no image. `packages/sheet/src/test/state/modules/floating.test.ts` pins it on the author, a peer and a joiner.

An undo needs those writes because its marker alone would differ from what the entry recorded: an undone delete ships as an insert, and an insert never grows a shrunk or nulled ref back; and an undone insert never shrinks a ref the insert stopped at the grid's edge. A receiver runs the marker first and then the writes. `packages/sheet/src/test/state/modules/chart.test.ts` pins these on the author, a peer and a joiner.

Conditional formats and validation rules are written the same way: `writeSheets` writes each rule the op moved or dropped under its own id, never the `conditionalFormats` or `dataValidations` record whole. The op ships none of them, and its undo ships the ones the marker did not bring back ([§ A structural undo applies exactly the ops it sends](#a-structural-undo-applies-exactly-the-ops-it-sends)). So a rule a peer added or deleted while the op was on its way keeps the peer's state, on every tab and in the replay. Every receiver's engine also stamps the merges again, so the op ships no stamp a peer's row op could leave without its cell. `packages/sheet/src/test/state/modules/rowcol-ops.test.ts` pins the marker for inserts and deletes of rows and columns.

## A range chart reads the grid's own values and labels

`resolveRangeChartData` (`engine/chart-data.ts`) turns a range chart into the categories and series the layout draws, through a `CellResolver`, so the editor and the server read the same cells. A value is the cell's computed `v` when it is a finite number and a gap otherwise. A label or series name is the cell's display text `m`, the string the grid shows, or a rich-text cell's runs joined, since one made in the editor has neither `m` nor `v`. A name ref reads its first cell. A chart with no categories counts them 1, 2, … up to its longest series.

A series whose values ref is null, deleted with its rows or columns, is left out and the rest draw, as Google does; it keeps its id, so its style stays in the spec and an undo brings it back as it was. The layout resolves an automatic color by the series' place in the spec, so the series after a deleted one keep the colors the editor shows them in. No series left, or a ref that names a missing sheet or spans several rows and several columns at once, is a `'ref'` error, which the chart shows as Excel's #REF. More points than `MAX_CHART_POINTS` is `'too-many-points'`. Both are decided from the refs before a cell is read, so selecting a whole column costs nothing. Hidden rows and columns are read like visible ones, while Excel and Google skip them by default ([CHARTS-TODO](CHARTS-TODO.md)).

`renderSheetChartSvg` (same file) is the chart the editor's overlay and the export both draw: the box, the look the record stores, the resolved data, and value ticks through `numberDisplay` in the axis's own format or else the first value cell's, Google's "From source data", so a percent column gets percent ticks.

## A chart's Setup is a block of cells, derived to refs and read back from them

The spec stores a ref per series, so a row insert can shift each one the way Excel shifts a chart's series. Google's Setup instead describes one block of cells: series down its columns or along its rows, and whether its first row and first column hold names. That block is a `ChartRange` (`engine/chart-range.ts`). `chartRangeData` derives the refs from it, and `chartRangeOf` reads it back by deriving both orientations and comparing with the stored refs. Refs no block derives, an imported chart's or one a deleted row nulled, have no Setup to show until a range is typed. The flags name the block's own first row and column, so Switch rows/columns keeps them: a text first row names the series down columns and the categories along rows.

Insert → Chart and a typed data range set a block up the same way (`suggestChartRange`): text in the first row or first column makes it names, the corner cell counting for neither, and series run down the columns unless the block has more data columns than rows. Insert also charts the table around a single selected cell (Excel's current region, `currentRegion`), titles the chart after its series ("North, South and East"), names the horizontal axis after the corner cell when that heads the categories, and places a 600 × 371 column chart below the block, selected, so its panel shows. `setUpChartRange` refuses a block of more than `MAX_CHART_SERIES` series, which `parseChartSpec` would read back as null, and one of more values than `MAX_CHART_POINTS`, which the chart would only draw as too much data. The values are counted from the refs, the fewest a block can hold before its cells set it up, so a typed whole column reads nothing. `currentRegion` grows each edge as far as it goes before trying the next and stops past `MAX_CHART_POINTS`, so a cell in a 10,000-row table reads a few thousand cells and is refused. Insert says why in an alert and the panel under the field, one message per reason (`CHART_RANGE_REFUSALS`).

## Images and charts share one frame on the grid

`FloatingObjects` (`components/FloatingObjects/`) draws the current sheet's images and charts in `floatingItems` order, so the DOM order is the paint order, each in one `FloatingObjectFrame` at its `sheetFloatingBox`. The kind supplies only its content, an `<img>` or the chart's drawing, so both kinds select, move, resize, rotate and open their menu through the same code and cannot drift apart. The frame is an unrotated positioned box and the content turns inside it, so a hit follows the turned shape. Selecting an object keeps its place in that order: every frame sits at one z-index, and the selected one's `ObjectTransform` ring renders through a portal into a layer after every frame, so its grips draw above the objects stacked over it.

A click selects the object and focuses its frame, so the workbook's keydown sees Delete, which goes through `clearSelectedContents`. Escape is the frame's own keydown. A drag moves it, and the `ObjectTransform` grips resize and rotate it, each gesture one write of the fields it changed. The preview clears on `onGestureEnd`, because a gesture cancelled by Escape or one that never moved commits nothing. Clicking a cell, a header or another sheet's tab deselects through `deselectFloatingObject`, and `changeSheet` drops the selection too, because the object belongs to the sheet left behind.

Touch follows Google Sheets on a phone: only the selected object is `touch-none`, so a finger on any other one pans the grid, the tap that follows selects it, and a drag on it then moves it. A `pointercancel`, the browser taking a touch for a pan, ends a move without writing it. `packages/sheet/src/test/components/FloatingObjects/floating-objects.test.tsx` runs every case for both kinds.

## A floating object's menu, keys and aspect lock are Vector's

Right-click, and a long press on touch, select the object and open the shared `ObjectContextMenu` ([LAYOUT.md](LAYOUT.md#menus-draw-their-rows-in-one-order)), so its rows read as a canvas object's do: Cut, Copy, Duplicate, Order, the download, Delete. The app passes it to the workbook as `aspectLocked`, so the corner grips and the panel's checkbox follow one setting, and Shift inverts it while dragging. Delete is the menu's, the Delete key's and Edit › Delete's, as in Vector and Slides, so the panel has no Delete button.

## A chart on the grid redraws only when a cell matrix it reads changes

Every component under the workbook context re-renders on every context change, a selection or a drag included, so `sheetChartSvg` (`state/modules/chart.ts`) keeps one drawing per chart record and the `data` matrices of the sheets its refs name. immer replaces the matrix whose cells an edit touched, so an edit feeding a chart redraws it on the next render and nothing else does. The key is the matrix, not the sheet, so a write to another field of the sheet redraws nothing. A rotate or a move keeps the drawing. A resize scales it to the preview box while the grip is held, its text stretching with it, because a large sketched chart takes tens of milliseconds to draw, and its commit draws it once at the new size. `packages/sheet/src/test/components/FloatingObjects/chart-content.test.tsx` counts the redraws.

Download image draws the chart as a copy carries it, through the canvas image writer: its ranges read into inline data and its look carried (`sheetChartClipboardItem`), on white, with the faces its labels use embedded ([EXPORT.md](EXPORT.md#a-drawing-downloads-its-own-svg-and-prints-as-layers)). A chart that draws #REF! or too much data has no inline data, so its menu has no Download image. The value ticks draw in the number format the copy writes on the axis, as in the grid ([CHARTS.md](CHARTS.md#a-chart-copies-between-apps-with-its-numbers-inline)).

## A selected chart copies itself, not the cells behind it

Selecting a chart or an image leaves the cell selection as it was, and the object takes the focus, so ⌘C and ⌘X reach the workbook's keydown with the cells still selected. The keydown skips the cell copy while a chart or an image is selected, so the cells get no copy border, and the Workbook's `copy` listener writes the chart instead: one chart item ([CLIPBOARD.md](CLIPBOARD.md#a-chart-travels-as-its-spec-with-the-numbers-inline)) carrying the chart's look, whose parts are the chart's with its ranges read into inline data (`inlineChartSpec`, `engine/chart-data.ts`), since no other app can read a range. Every part the copy doesn't touch goes as the text it stores. `sheetChartClipboardItem` (`state/modules/chart.ts`) builds it, for the copy and Download image alike. Ticks drawn "From source data" take the first value cell's format onto the axis, so they keep it. An automatic color stays automatic unless a deleted series before it would shift its index. A chart that draws `#REF!` or too much data copies nothing. ⌘X writes the same item and deletes the chart, one undo step, as Google's does, and an image the same way; a viewer's ⌘X only copies. The object menu's Cut and Copy and Edit › Cut and Copy reach the same listener through the clipboard event `execCommand` fires (`copyActiveObject`, `state/modules/clipboard.ts`), so a menu writes what the keys write. The listener reads the chart from `ctx.sheets`, not through the editable current sheet, so a viewer can copy. It stands down while the focus is in a text field, such as the chart panel's title, which copies its own text; a selected image's copy does the same.

⌘V works with a chart or an image focused, since the paste gate takes a focused object of this workbook as well as the cell input. A pasted chart lands on the selected cell at its copied size, selected. The workbook keeps the chart it last copied beside the inline copy it wrote (`copiedChart` on the global cache), so a paste of parts equal to that copy here stores the chart's own eight parts and the duplicate stays linked to its cells, as Google's does. Anywhere else, another workbook or another tab of this one, it stores the inline copy, a part the item lacks as an empty string (`newChartSpecParts`). Duplicate is a spread of the chart's record under a new id. `packages/sheet/src/test/components/Workbook/chart-clipboard.test.tsx` pins each case.

## A selected chart's panel is a canvas chart's, and a typed edit is one undo step

Selecting a chart shows one panel, in the order Vector and Slides show a chart's: Transform, the shared chart and look sections (`ChartSections`, [CHARTS.md](CHARTS.md#one-chart-editor-edits-a-spec-and-the-host-writes-it)), then Arrange. There is no Edit chart step, so a chart's rows are one click away in every app. A phone shows no panel, as Slides and Vector show none ([MOBILE.md](MOBILE.md#a-phone-views-canvas-documents-never-edits-them)). Google's Setup, the data range and its three boxes (`ChartPanelSections`), sits at the end of the Chart section, where an inline chart has Edit data, because the range is how a sheet chart edits its data. The Workbook reports the selected chart through `onChartPanelChange`, as it reports the selected object through `onActiveObjectChange`, and the app mounts `ChartPanelSections` inside the object's panel. A viewer gets the Transform read-out only. The Workbook holds the app's hooks in a ref, read at call time, so a host render fires no report, and both states are memoized on what they read, so the app's `setState` bails out when nothing changed. The panel writes through the Workbook API: `setChartSpec`, `setChartLook` for the paint rows, and `setChartDataRange` for a typed range, which needs the cells to set the block up.

The shared editor writes a typed title on every keystroke inside a gesture ([CHARTS.md](CHARTS.md#one-chart-editor-edits-a-spec-and-the-host-writes-it)). The Workbook's `beginGesture` opens `undoGesture`, and `setContextWithProduce` merges every write made under it into the last undo entry, so one ⌘Z takes the whole title back while peers still see it as it is typed. A write that replaces the field the entry's last write replaced overwrites that patch and adds no inverse, so the entry holds the first old title and the latest new one, not one per keystroke. The caret stays in the field, outside the Workbook's keydown, so the object's panel hands the Workbook's undo and redo to its fields (`PropertyHistoryContext`, `floating-object-panel.tsx`), as the Docs chart panel does. Left to the browser, ⌘Z there would be the field's own undo, each step written back as an edit and an undo entry of its own (`apps/sheets/src/test/components/sheets/floating-object-panel.test.tsx`).

## A validation rule is stored once over its ranges

A sheet keeps its validation rules in `dataValidations`: a record from an id to a rule, the ranges it covers and its order key, as it keeps its conditional formats ([§ Position-bound properties live beside the cell](#position-bound-properties-live-beside-the-cell); `SheetValidation` in `packages/lib/src/sheets/types.ts`). A rule over a whole column costs one entry, so it runs to the grid's last row, as Excel stores `B:B`, and keeps working past the rows that hold data. The dialog names a column header's selection `B:B` (`validationRange`), and the importer keeps `B1:B1048576` as the file has it. Only a tick box's seeding stops where the sheet's cells stop, since it writes a value into each empty cell.

- **One key per rule.** A new rule from the editor gets a `crypto.randomUUID()` id and the order key after the last rule's. Every sheet carries the record, empty if need be (`normalizeSheetConfig`), so two peers editing different rules write different keys and neither overwrites the other ([§ Creating a collection ships it whole](#creating-a-collection-ships-it-whole-so-every-collection-exists)).
- **A changed rule is written whole.** `clearValidations` and `addValidation` (`state/modules/validation-rules.ts`) replace `['dataValidations', id]`, never a write into its `ranges`: `opToPatchOnSheets` drops a write into a rule's fields, which could leave the rule malformed. A whole write over a rule a peer deleted is skipped (`withinCap` in `packages/lib/src/sheets/yjs-ops.ts`): immer writes `add` for an id its base lacked, so a `replace` means the writer saw the rule, and the delete wins on every tab and in the replay.
- **A cell has one rule.** Putting a rule on cells takes them out of every other rule, through `rangeWithout`, and drops a rule left with none. Two peers putting rules on one cell at once, or an xlsx file, can still leave a cell in two rules. Then the last rule in order wins on every tab (`validationAt`), which is the newest, and of an import's overlapping rules the last in the file.
- **Rows and columns move rules as they move conditional formats.** The engine shifts the ranges through `shiftRange` (`shiftRules` in `engine/rowcol.ts`, the one shifter for both kinds of rule), so a live tab, a peer and the replay agree. An insert inside a rule grows it, one at or before it moves it, and one right below a bounded rule leaves it alone, so the new rows get no rule. An insert stops every range's end at the grid's last row or column, and a range it pushes off the grid whole goes as a deleted one does. A row op ships no rule, since every receiver's engine moves them: the author's write would land on a receiver's own shift of a peer's edit sent at once, and two inserts sent at once would leave a rule a row off its cells. Its undo ships each rule the marker did not bring back under its id, and its redo is the marker alone.
- **A carry replaces the destination's rules.** A paste, a cut, a move, a fill and the format painter first take the cells they land on out of every rule, as Excel does, then land the source's rules on the cells their source cells landed on (`carryCells` and `landedRanges` in `state/modules/carry.ts`). On the source's sheet the landed ranges join the source rule, and on another sheet they join a rule that says the same, or become a rule of their own. A sort stays out of this ([§ A sort moves a cell's contents](#a-sort-moves-a-cells-contents-and-leaves-the-sheets-rules-where-they-are)). `addValidation` coalesces the ranges it lands with the rule's own (`coalescedRanges` in `packages/lib/src/sheets/range-rules.ts`): ranges of one width that touch join, and duplicates go. So one validated cell pasted down 10,000 rows adds one range, not 10,000. The source's rules land first to last, so where two of them overlap, each landed cell takes the rule its source cell shows. A rule a cut moves whole becomes the sheet's last rule.
- **The painter looks rules up once per pass.** `validationLookup` lays the rules over the window `drawMain` paints out into a grid of its cells once, first to last so the last rule wins, and a cell then costs one read. 100 rules of 100 cells in view cost a frame about a millisecond, where checking each rule's ranges per cell took about 50. A cell outside the window, which the text overflow asks about, is looked up in full once a pass.
- **A rule reads the cell's value.** A number, length or date rule reads the value, which a number format doesn't change, and a date rule compares serials. A list rule reads what the cell shows, because a list holds the text its source cells show (`cellPassesRule` in `state/modules/data-validation.ts`). A commit from the editor passes when its text is what the editor opened with, and any other text is written to a copy of the cell and checked as a cell (`inputPassesRule`).
- **A rule's fields are text whatever its type.** `DataValidationRule.type` is `dropdown`, `checkbox`, `number`, `number_integer`, `number_decimal`, `text_content`, `text_length` or `date`, and `type2` the comparison, such as `between`, `notBetween`, `equal`, `include` or `earlierThan` (`''` where there is none). `value1` holds a dropdown's items, comma-separated, or its range, the number of a number or length check, a date check's YYYY-MM-DD date and a tick box's checked value; `value2` holds a between check's upper bound and a tick box's unchecked value. A tick box stores no checked flag: the cell's value says it (`isCheckboxChecked`). `hintShow` and `hintValue` make the prompt a selected cell shows, and `prohibitInput` refuses a value that fails the check (`updateCell`).
- **A rule's shape is checked where it arrives.** A peer can store anything under an id, and every reader walks a rule's ranges. So the snapshot decoder and `normalizeSheetConfig` keep only well-formed rules (`wellFormedValidations` and `wellFormedConditionalFormats` in `packages/lib/src/sheets/range-rules.ts`), and `opToPatchOnSheets` drops a write that would leave one malformed, or that writes into a rule's fields. A rule's order must be a fractional key of at most 128 characters (`isValidFractionalIndex`), since a new rule's key is made from the last one, character by character, and a key of 40,000 would overflow the stack of every later add. A conditional format is checked the same way, its `textColor` and `cellColor` included, so the painter and the exports trust a stored rule's type. A rule under the id `__proto__` is dropped where rules arrive whole, since a write by id never reaches that key and the rule could not be deleted. Every field of the rule is checked, the optional ones such as `hintValue` and `prohibitInput` included, so a reader such as the xlsx export or the hint card can trust its type. A rule holds at most `MAX_RULE_RANGES` (8,192) ranges, and one with more is dropped before its ranges are walked. A sheet holds at most `MAX_VALIDATIONS` (1,024) rules: past it the decoder keeps the first in order, and a write that adds a rule is dropped. Why the caps sit where they do is beside them in `range-rules.ts`. The importer coalesces a sqref's ranges, and counts a rule still over a cap as a dropped validation. The xlsx export cuts each rule out of the cells of every later rule, finding the ranges near each one rather than checking every pair, then joins what it cut, and drops and counts a rule the cuts left past the range cap, which the importer would drop. The editor's writers keep inside both caps, because a rule past one would live on the author's tab alone. Past a cap the edit stands and the rule forgets: `addValidation` leaves a rule that would grow past the range cap as it was and a new rule on a full sheet out, and `clearValidations` drops a rule a cut would split past it. So a paste of one validated cell over every other row of a long column lands all its cells, and those past the cap have no rule.

## A tick box is a validation rule, and the value is its state

Tick boxes, list chevrons and the three corner marks are canvas paint, not DOM. A tick box's and a chevron's model and geometry live in `state/modules/data-validation.ts`, which of them takes a press in `cell-glyph.ts`, and the paint, with the corner marks' geometry, in `state/render/cells.ts`. Which rule covers a cell is `validationAt` (`state/modules/validation-rules.ts`), and the painter takes its lookup once per pass ([§ A validation rule is stored once over its ranges](#a-validation-rule-is-stored-once-over-its-ranges)).

`Insert → Tick box` and the cell context menu both call `insertCheckbox`, which writes a `checkbox` rule with the values `TRUE` and `FALSE`. That is Google's model: a tick box is data validation, not a cell format. The context-menu entry exists because the common intent is converting an existing TRUE/FALSE column.

There is no checked flag on the rule. `isCheckboxChecked` compares the cell's display value with the rule's checked value, ignoring case. So an imported, pasted, typed or formula-produced `TRUE` renders ticked. Applying a rule seeds the unchecked value into empty cells only, so a tick box over an existing column loses nothing. A formula cell is a read-only tick, because a toggle would replace the formula with a literal. The rule dialog (`confirmMessage`) refuses a tick box with either value empty, and a list with no options, so the editor never writes a rule the painter can't draw.

A tick box draws the box alone, the way Google does, with custom values too: the formula bar says whether a ticked box holds "Yes". A cell holding a value the rule names neither of fails the rule (`validateCellData`): it paints as ordinary text with the invalid mark and no box, and neither a click nor Space toggles it (`isCheckboxClick`, `checkboxChange`), so a tick box laid over a column of prose never paints the data away. Empty cells in the range pass and draw the plain unchecked box, so the range reads as one column.

A header click is clipped to the used extent, as for borders (`clipToUsedExtent` in `state/utils/index.ts`). A dragged range applies exactly as selected, which is how a checklist over empty rows gets its boxes.

## A list chevron is painted on every cell its rule covers

A `dropdown` rule paints a chevron on every cell it covers, empty ones included (`renderDropdownChevron`, called from `cellRender` and `nullCellRender`). Most list-validated cells are empty, and without the chevron a blank validated cell looks like a free-text one. Keyboard users and read-only viewers see it too.

It overlays the cell text rather than reserving width, because reserving would reflow every validated column. Its color is the cell's own `fc` at 55% alpha, since real workbooks put list rules on dark fills that a fixed gray would vanish into.

Clicking the chevron opens the list, and a click anywhere else in the cell selects. A viewer sees the chevron but gets no list. The `#sheet-validation-list-anchor` element is only an invisible anchor for the portaled menu.

## The grid redraws whole when a font slice loads

The grid measures and draws text on its canvas, and a canvas measures a character in a fallback until the font slice that draws it has loaded ([TYPOGRAPHY.md](TYPOGRAPHY.md#a-canvas-waits-for-the-slices-of-its-text)). Drawing a cell starts that fetch, so a Chinese cell's first frame can draw in the system's font. So one font watcher per page, `watchFontFaces` (`state/modules/text.ts`), listens to the `loaded` promise of every face in `document.fonts` that hasn't loaded yet, and each mounted grid subscribes to it with a listener (`components/Sheet/index.tsx`). When a face settles, the watcher waits for `document.fonts.ready`, clears the text measure and line-height caches once (`clearMeasureTextCache`), and calls every listener, which redraws its whole grid, as a cached width would keep the fallback's.

The grid doesn't listen for `loadingdone`, because WebKit fires none for the slices a canvas draw fetches: the grid would keep Apple's colour emoji and the system's Chinese face until a scroll redrew it. A face's `loaded` promise and the set's `ready` settle in Chromium, Firefox and WebKit alike. The faces are declared in `fonts.css`, so every one exists when the first grid mounts, and each subscribe rescans the set for a face added since. The watcher chains one reaction per face for the whole session and lives at module scope: most faces, such as the CJK slices, never load in a session, so a reaction chained per grid would keep every workbook the page ever opened in memory. A grid that unmounts unsubscribes, and nothing holds on to it. A face that fails to load settles too, once, so a slice that never arrives can't redraw the grid on every frame. The slices one frame needs arrive over several frames, and waiting for `ready` redraws once for all of them: a cold load in Firefox draws the grid three times, the first frame included, not once per slice.

The measure itself loads nothing, and `getMeasureText` stays a cache lookup. Asking `document.fonts.load` for the measured text would fetch too much: in Chromium and Firefox it loads every emoji slice that holds a character of the text, so a `⚠️` (U+26A0 and the emoji selector U+FE0F) fetches all nine emoji slices, about 774 KB, where drawing it fetches one or two.

A redraw can't heal a stored height. A wrapped cell's row height is measured once, as the cell commits on any path, on the one lazy context those commits share (`measuringContext` in `state/modules/text.ts`), and written to `cfg.rowlen`, which syncs to peers and reaches every export. So the cell editor and the formula bar load the cell's font for the text as it is typed (`loadCellFont`), and the commit, which stays synchronous and one undo step, measures the real face. A commit faster than the slice's fetch, or a rich-text run in another family, still stores the fallback's height ([SHEETS-TODO.md](SHEETS-TODO.md#bugs)).

## Text spills into empty neighbours

A text cell overflows into the cells beside it as in Google Sheets and Excel: by default, unless its wrapping is Clip (`tb: '0'`) or Wrap (`tb: '2'`). No `tb` means overflow, so imported and typed cells spill without a setting. Left-aligned text spills right, right-aligned left, centred both ways. It runs over any neighbour without a value, whatever that neighbour's style, and stops at the first one with a value, a space or a formula included, or at a merge. Text spills once it comes within 4 px of its cell's edge, the 2 px the painter lays it in plus the 2 px of grid line its clip gives up. Numbers, tick-box cells and text that fits never spill (`rowOverflowSpans` in `state/render/overflow.ts`, recomputed for the visible rows on every draw).

A source scrolled off-screen still spills into view. Past each edge of the view only the first cell with a value can reach in, since it blocks everything behind it, so each row walks out at most `OVERFLOW_REACH_COLUMNS` (256) empty columns per side to find it. Text from a source further away clips at the edge of the view. The HTML, PDF and preview render doesn't overflow at all: every cell clips ([SHEETS-TODO.md](SHEETS-TODO.md#bugs)).

## Painter and hit test read one rect

Each glyph that takes a click has one geometry function that both the painter and the mousedown hit test call: `checkboxRect` and `dropdownChevronRect`. It means a glyph and its click target cannot drift apart. The filter button works the same way: `createFilterOptions` (`state/modules/filter.ts`) gives each `filterOptions` item its rect, which `drawFilterUI` paints and `getFilterButtonAtPosition` hit-tests. The button is 20×15 on the column's right edge, and in a column narrower than 20px it is as wide as the column, so it never overlaps its neighbor's. The tick box gets its bounds from `cellTextBox` on both sides, and `cellGlyphAt` (`state/modules/cell-glyph.ts`) is the one place that builds that box for a press, for the mousedown and the selection's handles alike. It passes the painter's edges in sheet pixels: the painter's box starts a pixel right of the cell's sheet edge and reaches a pixel lower, since the canvas shows a sheet pixel one to the left and one up and its rows start a pixel higher. The box is stroked inside its rect, so its 10 px are the pixels that take the press. `packages/sheet/src/test/state/render/validation-paint.test.ts` paints with the real painter at the headers' offsets and presses every pixel in and around each box. Only the box toggles; Space or Enter toggles the focused cell. The chevron's click strip is wider than the glyph but built from the same rect, and both drop out below a minimum column width.

## Nothing toggles while a cell edit is open

Clicking a tick box while composing `=IF(` inserts the cell's reference and nothing else. A toggle would write the cell and kick a recalc behind the half-typed formula. The chevron is gated the same way, since its list would open over the formula, and so is the keyboard path (`state/events/mouse-cell.ts`, `keyboard.ts`).

## Three corner marks share one painter

A comment (top-right), an invalid value and a forced string (top-left) are all drawn by `drawCellIndicator` at `cellIndicatorRect`. The size is `CELL_INDICATOR_SIZE` in `packages/lib/src/constants/comment-indicator.ts`, which the canvas apps' `CommentIndicator` reads too, so a comment mark looks the same in every app. Filled and empty cells reach the same painter. A comment triangle takes its card's color from the Workbook's `commentCards` prop, and red when the card has none.

The grid's colors are light-only CSS variables in ui's `globals.css`, read by the canvas and by the chart Edit data grid; the canvas's other colors are hardcoded light, because the grid is paper and doesn't re-theme ([RENDERING.md](../packages/sheet/RENDERING.md#theming-the-light-pinned-surface)).

## A glyph outranks the selection handles

The selection carries two invisible DOM hit targets over the canvas: the move band on its border and the fill handle at its corner. Without a precedence rule, a press on a chevron at the fill corner starts a fill drag. `cellGlyphAt` (`state/modules/cell-glyph.ts`) says whether a chevron or a tick box sits under a point, from the painter's rects. Both handles ask it first, and on a hit they start no drag, so the press reaches the cell area, which opens the list or toggles the box. A corner mark claims nothing, as in Google Sheets: a press on one at the selection's border starts a move, and one inside the cell a range select. `packages/sheet/src/test/components/SheetOverlay/handle-precedence.test.tsx` pins both.

The hover path writes the same answer to `context.cellGlyphHover`, which shows a pointer over a chevron or tick box and stands the handles' own cursors down. Row and column resize never compete, because those handles live in the headers.

## The validation card follows the focus cell

One React card, `components/DataValidation/HintCard.tsx`, shows a validated cell's prompt or, when its value fails the rule, why. `getValidationHint` derives it from the focus cell on every render. So it follows keyboard navigation, never strands over the previous cell, and renders a collaborator's or an xlsx file's prompt as text, never as markup. It is a Radix popover on an anchor spanning the cell, as the link card is, so at the grid's edge it flips above the cell or shifts left instead of hanging past the cell area.

A rejection outranks a prompt, since it is the more urgent message. The card stands down while the list is open, because both hang over the same corner. The copy is assembled by `describeValidationRule`, which also words the `prohibitInput` dialog, so both ways a rejected value is reported say the same thing.

## Comments are Eigen comment cards

A cell anchors comments through `commentCardIds` on the `Cell`. The context menu, the panel and the card dialogs are the shared components from [COMMENTS.md](COMMENTS.md). Only adding and deleting a cell's anchor and reporting a hover stay sheet-specific hooks. Which cards are in use and the delete both read every sheet (`apps/sheets/src/components/sheets/comment-anchors.ts`), because a card on a tab that is not open is still in use: the pane lists it, and a delete takes it off every cell that holds it, in one undo step. A delete that left the id on another tab would keep the card in the pane.

The [hover card](COMMENTS.md#a-hover-shows-a-comments-card-and-the-host-draws-it) is the host's. The grid's `document` mousemove calls `commentHoverAt` on every frame and hands the answer to `hooks.onCommentHover`, outside the `setContext` recipe, because a host's report sets its state. `getCellRowColumn` finds the cell from coordinates alone, so `commentHoverAt` first checks that the event's target is the grid's own surface: `.sheet-cell-table` or the selection's drag and fill handles (`CELL_SURFACE`). Without that gate a pointer over a floating image, a chart or the portaled card itself would read the cell under it.

On mobile the comments pane takes the whole width, so `editor.tsx` hides the workbook instead of unmounting it. `Sheet` keeps a `ResizeObserver` on its container and skips 0×0 boxes, so the canvas re-measures when the workbook shows again. App code may rely on that.

## The full export styles cells by class

The server renders a workbook to HTML, PDF and xlsx in `apps/api/src/lib/export/sheets/`, from the `Sheet[]` that `readSheetsFromDoc` returns. The transform, the route and the xlsx writer are in [EXPORT.md](EXPORT.md#a-sheet-export-recalcs-and-xlsx-carries-cells-charts-and-pictures).

`renderSheetsHtml` interns every style it emits (cell, row height, column width, data bar, rotation, image) into a workbook-global registry of classes and returns `{ html, css }`. The document builders put the rules in a body `<style>` element, which goes through `sanitizeExportHtml` with the markup.

A real workbook repeats a few hundred styles across hundreds of thousands of cells. DOMPurify on jsdom CSS-parses every inline `style` attribute it sanitizes, but passes class attributes and style-element text through as strings. With inline styles a real workbook's export was 82 MB and took 104 s, mostly CSS parsing.

The preview (`renderSheetsPreviewHtml`) keeps inline styles, because its body fragment embeds without a `<head>` ([PREVIEWS.md](PREVIEWS.md)). Its bytes are golden-pinned in `apps/api/src/test/preview/sheets-preview.test.ts`.

The table sets an unsized cell's font size to `SHEET_DEFAULT_FONT_SIZE` pt, the grid's own default, so a cell without a size prints at the size the grid draws it.

## The stylesheet is guarded in two places

Cell values are schemaless CRDT strings, and stylesheet text is a different escaping context from a style attribute. Two guards keep it inert, each where every field passes through rather than per field:

- `serializeStyleRules` strips what is structural in CSS text from every declaration. `<` and `>` would end the `<style>` element, and DOMPurify keeps what follows, so an `<svg><image href>` becomes a fetch in the HTML download. `{` and `}` open rule blocks. `\` starts a CSS escape, which spells `url(` or `@import` invisibly to the sanitizer. `/*` opens a comment that would swallow every later rule, so one odd cell would unstyle the rest of the workbook.
- Numeric fields are coerced, not escaped. Row heights and column widths go through the `Number()` guard in `sheetColumnsWidth` and `sheetRowsHeight`, and an image's or chart's box through `sheetFloatingBox`, which the `@page` rule's size reads too.

Colors are checked, not escaped. A cell's `fc` and `bg`, a rule's colors, a border's and a data bar's reach the CSS, in the export and the preview alike, only as a hex, `rgb()` or transparent value `document/colors.ts` reads, or as a bare keyword such as `red`, which can't add a declaration. Any other string, such as `red;position:fixed;inset:0`, would add declarations of its own and fetch nothing, so the sanitizer would let it through. `cssColor` (`export/sheets/render.ts`) drops it, and a border or a bar draws transparent.

Other values are still `escapeHtml`'d on the way in, and the font family is too in a style attribute, but not in the stylesheet, which decodes no entities and would draw `Bell MT & Co` as `Bell MT &amp; Co`. There the stack goes in as it is: `cellFontName` refuses a name holding `;`, `(`, a quote, a backslash or a control character, so a name can't leave its declaration. The sanitizer's data-URI rule and `@import` strip cover style-element text too ([EXPORT.md](EXPORT.md#the-sanitizer-keeps-only-data-references-because-a-browser-fetches)).

## The export paints conditional formats with the grid's evaluator

`render.ts` calls `evaluateConditionalFormat` per sheet and merges its colors into each cell's style, so an export shows what the canvas shows. For formula rules it builds one `FormulaEngine` and one `createArrayResolver` over all loaded sheets, so a cross-sheet rule like `=Sheet2!A1>10` resolves. The pass reads `cell.v` and never recomputes the sheet's own formulas. Those values are already fresh, because `readSheetsFromDoc` ran the [gated recalc](#the-editor-computes-on-write-the-server-only-what-nobody-computed).

A data bar is an absolutely positioned `<div>` inside a `position:relative` cell, with geometry mirrored from the canvas painter. Negative bars are red, as on the canvas.

## Floating images and charts are an overlay on the table

A sheet with images or charts wraps its table in a `position:relative` box, and `renderFloatingObjects` (`export/sheets/render.ts`) draws them over it in their one paint order: each at its clamped box, rotated about its center. That is the box and the order the editor lays out, because both read the same fields.

The stored coordinates are grid pixels from A1, while the table starts at the used range. So the overlay subtracts the rows and columns above and left of that window. An object above or left of the used range pulls the window back to where it starts, so the offset never goes negative and the page covers it. The page size, the window's origin and the preview's clip all count the box an object covers as it turns (`getElementBounds`), so a rotated object stays on the page. One that turns past A1 tucks under the editor's headers, but a page has none, so the export moves it right or down until it starts on the page. The overlay's box reaches the farthest one, so the next sheet and the preview's truncated notice start below them, and the preview clips the box to its budget window. `apps/api/src/test/export/sheets-pdf.test.ts` reads a rotated chart off WeasyPrint's pixels; it skips where WeasyPrint or a rasterizer is missing, as on CI.

An image's name is a media reference ([MEDIA-REFERENCES.md](MEDIA-REFERENCES.md)), looked up in a map the transform prepared: `data:` URIs for an export, preview URLs for a preview. A name that resolves to nothing renders nothing. The xlsx export writes charts as chart parts ([CHARTS.md](CHARTS.md#a-chart-goes-to-office-as-a-cchartspace-that-reads-back-as-the-same-spec)) and images as pictures over the same cells, turned as they turn ([EXPORT.md](EXPORT.md#an-xlsx-picture-is-anchored-as-excel-places-a-turned-one)). The import reads both back in one paint order, each picture's file a new media name, so a round trip keeps an image's box, angle and stacking but not its name.

## Charts draw in the overlay as inline SVG

A chart is `renderSheetChartSvg`, the editor's own drawing, in a white box, so the gridlines stop at it as they do on screen. Its ranges read through the render's resolver over every loaded sheet, so a chart on one tab can chart another. The export reads them after the gated recalc and the preview from the stored values. The SVG is plain shapes and text, which the sanitizer keeps and WeasyPrint draws ([CHARTS.md](CHARTS.md#the-painter-draws-each-shape-with-its-own-kind-and-the-labels-as-svg-text)).

## An imported tab arrives as an addSheet op, renamed as Duplicate names a copy

File › Import… can add an xlsx's sheets as new tabs ([EXPORT.md § A replace saves a version first](EXPORT.md#a-replace-saves-a-version-first)). The transform process builds them as one batch of `addSheet` ops (`addSheetsBatch` in `apps/api/src/lib/document/sheets.ts`), which the main thread pushes after the workbook's own, never as a new snapshot. An open tab applies the batch as it applies a peer's new tab, so it keeps its undo, where a new snapshot would empty every tab's undo stacks ([§ A new snapshot loads into the mounted grid](#a-new-snapshot-loads-into-the-mounted-grid)).

The reader repairs a name the tab bar would refuse, such as one past 31 characters or holding a `:`, and a second sheet of one name (`legalSheetNames` in `engine/sheet-name.ts`, which the writer uses too), and what names a repaired sheet follows it. Otherwise a rename's undo would fail on the old name, and retyping it would be refused. An `addSheet` whose name breaks the rule or is taken gets the same repair on every reader, a live tab and the replay alike (`applySheetsBatch`). A forged name can do no more than a legal one, and a name stored before the reader repaired names keeps its break in its copy's name, so the tab menu's Duplicate of `Q1: Sales` lands as `Q1_ Sales(Copy)`.

Every imported sheet takes a fresh id: the importer numbers its sheets `sheet-0` and on, which a workbook's own ids can match. A sheet whose name the workbook holds is renamed by `copySheetName` (`engine/sheet-name.ts`), the rule the tab menu's Duplicate uses, so `Data` comes in as `Data(Copy)`. The names are compared ignoring case, as Excel and a rename in the tab bar compare them. What the file says about its own sheets follows the new names and ids, so its formulas still read the cells they read in Excel:

| Reference | Names a sheet by | Rewritten through |
|---|---|---|
| A formula, a formula conditional format, a list validation's source, a `cellrange` link | Name, `'Data(Copy)'!A1` | `renameSheetTexts` (`engine/sheet-name.ts`), which a tab rename runs too |
| A `sheet` link | Name | `renameSheetTexts` |
| A chart's series and categories | Id ([§ A chart is a floating record](#a-chart-is-a-floating-record-whose-refs-name-sheets-by-id)) | `mapChartRefs` |

Defined names need nothing: the reader has already written each into the formulas that use it as the range it names ([EXPORT.md](EXPORT.md#an-xlsx-defined-name-is-inlined-into-the-formulas-that-use-it)), so its refs are renamed like any other.

The reader bounds each file alone ([EXPORT.md](EXPORT.md#zip-guards-run-before-the-parser-inflates-anything)), so repeated inserts could grow one workbook past what any single import may. An insert weighs the file with the workbook against the same `MAX_CELLS` and `MAX_TEXT` and refuses past either with the import's 413 "This spreadsheet is too large to import" (`assertInsertFits` in `apps/api/src/lib/import/sheets/limits.ts`). Both sides are weighed by `sheetsWeight` in one unit: the stored cells, and the characters of each cell's value, display, formula, number format and rich-text runs. The transform weighs the file as the reader read it, and the workbook as a tab opening it shows it, so a sheet an earlier insert added, which stays an `addSheet` op until the workbook's next compaction, counts too. The reader charges those same fields and more, so a file a replace accepts always fits an empty workbook. What Insert doesn't count: the recalc grid's slots (`MAX_GRID_SLOTS`), and what the reader charges beyond the cells' own text, such as borders, merges and the text of links and rules ([SHEETS-TODO.md](SHEETS-TODO.md)).

The main thread reads the workbook's snapshot and log from the live doc and hands them to the job as JSON text, as a compaction does, and the transform replays them under the server's recalc budget: every structural batch recomputes, and on the main thread the replay of an 8,000-row running total with three row inserts in the log held the event loop for 23 s. The insert's replay and the file's parse share the import's deadline and the child's memory, so a large open workbook with a long log and a modest file can together fail the insert, out of memory as "too large" and past the deadline as a failed import. The weigh runs once, in the transform, before the pictures are saved, so a refused insert leaves none in the media folder. The main thread pushes the batch it gets back as built, whatever changed in the workbook during the transform. Two cases are accepted. A peer who adds a tab of the same name in those seconds makes the imported tab come back renamed, such as `Sales (2)`, on every reader, while the formulas in the Insert's other tabs still name `Sales` and read the peer's tab. And two inserts at once can together take a workbook one import past the caps.

## Some xlsx round-trip drifts are decisions

These are deliberate. Where a test pins one, it is in `apps/api/src/test/export/sheets-export.test.ts`. Hyperlinks:

- A `sheet` link re-imports as a `cellrange` link at `'Name'!A1`, because the location names a cell. A `sheet` link to a name no sheet holds is a defined name's, as the import reads a location without a cell, and keeps its location. A bare ref gains its own sheet's quoted prefix.
- Imported link cells keep Excel's font, while the link dialog sets blue and underline. Forcing the dialog style at import would clobber theme-styled link cells.

Column widths and row heights:

- A width counts the file's default font's widest digit ([TYPOGRAPHY.md](TYPOGRAPHY.md#the-xlsx-export-makes-inter-the-workbooks-default-font)), so a column imports at the pixels Excel for Windows draws it at: a Calibri 11 column stored as 9.140625 is 64 px. `maxDigitWidth` (`apps/api/src/lib/ooxml/spreadsheetml.ts`) holds Excel's digit for the Office defaults by face and size, because Excel draws GDI's hinted digit, not the outline's: Calibri 11 and Arial 10 are 7 px, Arial 11 and Cambria 11 are 8. A face it doesn't list counts 7. `columnWidthToPx` and `pxToColumnWidth` are ECMA-376's conversion both ways. The writer truncates to a 256th of a digit and the reader rounds half a 256th up, so every pixel width survives the round trip.
- A height or width that draws no pixel, a custom 0 or a 0.05 pt row, comes in as a hidden row or column, which every renderer draws as none and the writer writes back as `hidden="1"`. A stored length of 0 would draw at the default in the editor and as nothing elsewhere.
- An unsized column takes the sheet's default width, read by the same digit. `sheetFormatPr`'s `defaultColWidth` counts its padding already. Without it Excel pads `baseColWidth` (8 when absent) by 5 px and rounds up to a multiple of 8 px, so Excel's default is 64 px. The default row height is points to pixels, and Excel's 15 pt when the file names none.

Rules and comments:

- Top or bottom, above-average, duplicate-value and data-bar rules export as Excel's own (`top10`, `aboveAverage`, `duplicateValues`, `dataBar`), which Excel and Eigen read and Google Sheets doesn't show. `duplicateValue` exports as Excel's `duplicateValues` or `uniqueValues` rule and re-imports as itself. `occurrenceDate` is editor-only and is not exported.
- The xlsx writer (`export/sheets/xlsx/rules.ts`) quotes a rule's exotic numeric literals (`1e5`, `+5`) as text. The engine compares with `Number()`, so rendering is unaffected.
- The data-validation exporter always writes `allowBlank: true`, Excel's UI default.
- Tick boxes are editor-only. The cells export their values and the rule is dropped: OOXML has no cell tick box, and a `"TRUE,FALSE"` list would re-import as a dropdown, a different feature.
- Excel comments and notes are not imported, because Eigen has its own comment cards.
