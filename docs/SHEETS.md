# Sheets

> **TLDR:** Sheets is Eigen's spreadsheet: a workbook of tabs that several people edit at once, with formulas, number formats, validation and xlsx import and export. The grid, its state and the formula engine are `packages/sheet` (`@workspace/sheet`), our own fork of the open-source fortune-sheet, itself based on luckysheet. `apps/sheets/` is the app around it. A workbook is stored as a snapshot plus a log of edits.

A workbook is a `.eigensheets` file. It holds one or more sheets, the tabs. A sheet is a grid of cells. A cell holds its value (`v`), the string the grid shows (`m`), its formula (`f`), its number format and its style. What belongs to a grid position rather than to the cell, such as borders, merges, validation rules and hyperlinks, sits in maps beside the grid, keyed `"r_c"` (row and column, counted from 0). Row heights and column widths are keyed by the row or column index alone. The maps under a sheet's `config` (merges, borders, row and column sizes, hidden rows and columns) are its config collections. Conditional-format rules, floating images and charts hang off the sheet too.

In the browser the fork keeps the whole workbook as one plain object, the context, and changes it only through immer. An edit is a recipe, a function that changes a draft of the context, and immer reports the change as patches: small records of a path and a value.

A workbook is a collab document ([COLLAB.md](COLLAB.md)), but its Yjs document holds no Yjs grid. It has two roots: `state.snapshot`, the whole workbook encoded as one value, and `ops`, a Yjs array of op batches. An op is an immer patch in a form a peer can apply, and a batch holds the ops of one edit. So an edit travels like this. The recipe runs on the local context, its patches become one batch, the batch is pushed onto `ops`, Yjs carries it to the other browsers, and each applies it to its own context. A browser that opens the workbook decodes the snapshot and replays the batches on top. An editor that closes while connected and alone, with no other client open on the workbook, viewers included, writes a fresh snapshot and empties the log.

The op log is the idea the design rests on. Writing the whole snapshot on every edit would make the last writer win for the whole workbook, while two ops on different cells merge cleanly.

The server reads workbooks for export, the Drive preview and the search index. `packages/sheet/src/engine/` is the half without the DOM, and the API imports it: the formula parser and evaluator, the op replay and recalc, the pass that recomputes formula values. So the browser and the server read a workbook and compute a formula with the same code.

The sections run from storage (ops, config collections, borders, the snapshot codec, undo) through the engine and formulas to the painted glyphs, comments and export. Four things in them surprise people:

- A sheet's config collections always exist, because creating one ships it whole ([§ Creating a collection ships it whole](#creating-a-collection-ships-it-whole-so-every-collection-exists)).
- The snapshot moves only through one codec ([§ The snapshot is interned](#the-snapshot-is-interned-and-written-only-through-the-codec)).
- Undo is per tab, but it follows a peer's row, column and sheet changes and skips a cell a peer changed since ([§ Undo is per tab and follows a peer's rows and sheets](#undo-is-per-tab-and-follows-a-peers-rows-and-sheets)).
- The editor computes formula values as it writes, so the server recalculates only a workbook nobody computed ([§ The editor computes on write](#the-editor-computes-on-write-the-server-only-what-nobody-computed)).

## `packages/sheet` is a fork we own

The whole upstream library (UI components, state runtime, formula parser) lives in `packages/sheet/`, with no external fortune-sheet dependency. `src/engine/` is the DOM-free half the server imports, `src/state/` the workbook context and its immer reducers, `src/components/` the React UI. How the canvas and the DOM overlays stack is in [RENDERING.md](../packages/sheet/RENDERING.md).

We own the code, so sheet code you touch gets simplified and its broken windows fixed, in small steps a reviewer can follow. A dialog is the shared centered `Dialog`, opened through the sheet's `useDialog` and `ModalProvider` as `ResizeDialog` and `CustomSort` are; a bespoke positioned card-dialog moves to it when someone touches it, while hover popovers and toolbars may stay positioned. A benchmark runs with immer's `autoFreeze` on, as the app does: turning it off misstates what an edit costs.

## An edit is an op in a Y.Array

`use-sheet.ts` (`apps/sheets/src/components/sheets/hooks/`) pushes each local batch to `ops`. A peer applies it with `applyOp()` (`components/Workbook/api.ts`), which patches the context without remounting the grid. A batch that arrives while a grid mounts, on first load or on a remount for a new snapshot, waits in a queue that `loadSnapshot` opens and an effect in `useSheet` drains into the grid that mounted. The Workbook seeds its sheets in its own effect, which runs before the host's, so the queued batches land on the seed. Handing them to the grid on its way out would lose them at the remount, and handing them to a grid not yet seeded would apply them to an empty workbook.

Two clients editing the *same* cell still diverge, because each applies its own op optimistically. Applying batches in array order would close that ([the proposal](proposals/PROPOSAL_SHEETS_YJS_WORKBOOK.md#what-to-do-first)).

A joiner decodes the snapshot and replays the pending ops through `replaySheetsOps` (`engine/replay-ops.ts`). The API's document reader calls the same function, so every consumer agrees on what snapshot plus ops means. A batch that can't apply is rolled back and skipped, so one bad op never makes the doc unreadable. `applyOpBatch` (`state/modules/apply-ops.ts`) applies a batch in the editor the same way: the sheet and row or column ops first, then the cell and field patches, resolved against the sheets those ops left, whole or not at all, on a copy of the context it commits only when every op applied. A peer's batch, the queued batches and every structural undo or redo go through it, so the tab that sends a batch, the tabs that take it and a joiner agree. A sheet nobody opened, such as a fresh copy, holds only its stored cells, so a cell or row op on it first gives it a matrix, as the replay does. The formula map lives outside immer, so it learns an added or newly filled sheet's formulas only once the batch applied. `packages/sheet/src/test/components/Workbook/api.test.ts` pins the batch shapes that once disagreed against the replay. The tests' joiner (`join` in `packages/sheet/src/test/state/factories/collab.ts`) decodes the stored snapshot, stored cells and no matrix, as a real joiner does: one that kept the base's matrices hid that a row op left another sheet's stored formulas at the old rows. A Yjs update that writes the snapshot and pushes batches at once is applied through the snapshot reload alone, which replays those batches too.

## Creating a collection ships it whole, so every collection exists

immer records the creation of a key as one `add` carrying the whole new value. So the first write to a config collection that doesn't exist yet ships the entire collection, and it overwrites a peer's. And a granular patch against a base that lacks the collection fails to resolve, so `replaySheetsOps` rolls back the whole batch and the edit is lost.

`normalizeSheetConfig` (`engine/sheet-config.ts`) therefore materializes every config collection where a sheet enters a consumer: `initSheetData`, the replay base, `addSheet` ops, `createDefaultSheets` and the Workbook's seeding effect. Its `SHEET_CONFIG_COLLECTIONS` list has an exhaustiveness assert, so a new collection fails the build instead of reopening the hole. It also materializes `images` and `charts`, the two maps outside `config` written key by key, and leaves out a chart past `MAX_CHART_SPEC_ENTRIES`, as the snapshot decode does ([§ A chart is a floating record](#a-chart-is-a-floating-record-whose-refs-name-sheets-by-id)). `withNormalizedSheet` does the same for `calcChain`, which also lives outside `config`: the first formula a user types emits `add ['calcChain', 0]` in the same batch as the cell.

There is no `ctx.config` shortcut. Read a sheet's config with `getSheetConfig` (`state/context.ts`) and write through `ctx.sheets[i].config`. immer names a patch after the path its draft was reached through, so a second route to the config emits patches at a root `filterPatch` drops, and assigning it back replaces the whole config. `packages/sheet/src/test/state/events/concurrent-config.test.ts` pins it through the real op pipeline: one client merges cells, another drags a row taller, and the drag must not undo the merge.

`state/modules` find a sheet through `getSheet` (`state/api/common.ts`): the current sheet, or the one an id or index names. A bad id throws `sheetNotFound` instead of handing back `undefined`, so a path that may name a sheet that is gone, such as a peer's row op, checks `getSheetIndex` first and returns.

`filterPatch` and `sheetMetadataOps` (`state/utils/patch.ts`) decide what goes on the wire, and both read one list of per-client `Sheet` fields, `PER_CLIENT_SHEET_FIELDS`. With two lists, a row insert would broadcast state the op path drops.

A write on a path that then rejects the operation still ships an op and costs the user an undo entry. `packages/sheet/src/test/state/rejected-writes.test.ts` is the table-driven gate; add a row to it when you add a writer.

## `borderInfo` holds each cell's own sides

`config.borderInfo` maps an `"r_c"` key to that cell's sides. `applyBorder` (`state/modules/border.ts`) expands a toolbar layout per cell at write time. `border-none` deletes the key and clears the facing side of each outside neighbor, so the shared edges go blank. Paste, move, fill and the format painter carry borders through `carrySides`, which deletes the destination's key when the source cell has no border, the Excel and Google overwrite rule. Order carries nothing, so two clients bordering different cells converge (`packages/sheet/src/test/state/modules/border-convergence.test.ts`).

A border belongs to the cell it was drawn on. The painter draws each cell's own sides at coordinates that coincide with the neighbor's, so the pixels match without a mirror. A shared edge never creates the neighbor's key, because that would be the whole-object `add` of [§ Creating a collection ships it whole](#creating-a-collection-ships-it-whole-so-every-collection-exists). A neighbor entry that already exists gets its facing side overridden, so the edge just drawn wins on screen. One result a user can see: copying B1 alone does not pick up A1's right edge. When two neighbors disagree on a shared edge, as after many xlsx imports, the higher-index one wins (B1's left over A1's right), so the color can't flip with the viewport's walk order.

A header click selects a whole axis, so it is clipped to the used extent first (`clipToUsedExtent`); one click must not write a key for every row. Cells filled in later rows show no border, an accepted divergence from Excel and Google. Merges are a read-time filter. `mergeEdgeSides` (`packages/lib/src/sheets/borders.ts`) is the one predicate. The canvas calls it per cell. The HTML export calls it on each stored key of a merge and folds the sides onto the merge's first shown cell, because the HTML has one `<td>`, so a side stored on a hidden edge row or column still draws. When several cells of a merge write the same outer edge, the last one folded wins. The xlsx export writes each cell its own sides, as Excel stores them. Storage stays raw, so an unmerge shows the sides again.

Only the canvas border pass skips hidden rows and columns. Every carry path (cut, move, fill, the format painter, copy as HTML) reads the merge-filtered sides through `getBorderInfoCompute`, which keeps them, so a drag-fill from a hidden source keeps its border. A row or column insert clones the borders of the row or column at the insert index onto the new ones, as validation rules do (`shiftCellKeyedForInsert` in `engine/rowcol.ts`). So inserting above the top row of a bordered block repeats that row's top edge.

## Position-bound properties live beside the cell

Everything that is the cell (value, formula, number format, colors, font, rotation, rich-text runs) lives on the `Cell` in the matrix, and overwriting the cell overwrites all of it in one op. A rich-text cell keeps its text in its runs alone, with no `v` or `m`, and every reader takes it from there through `richText`, `cellValue` for a value that is the runs' text or `v`, or `cellDisplay` for the text the grid shows, the runs' text or `m` or `v` (`engine/format.ts`), except find and replace, which skips rich-text cells for now ([ROADMAP.md](ROADMAP.md), "Sheets: find and replace inside rich-text cells"). A writer that writes plain text over a rich cell drops its runs with `dropRuns`: they would otherwise outrank the value it wrote. Delete drops only the contents (`deleteSelectedCellText` in `state/modules/selection.ts`): the value, the formula, the runs and a link with its blue underline go, and the colors, font, alignment, number format and comments stay, as in Excel and Google Sheets. Removing the format is **Clear formatting** (`handleClearFormat`). What is bound to the grid position lives in a map beside the matrix:

| Property | Home | Why not on the cell |
|---|---|---|
| Borders | `config.borderInfo` | A border outlives deleted content, and a separate key keeps "A types, B draws a border" from clobbering |
| Merges | `config.merge` | A merge spans cells |
| Data validation | `sheet.dataVerification` | The rule outlives the value it validates |
| Hyperlinks | `sheet.hyperlink` | The link outlives edits to its text |
| Row and column geometry | `config.rowlen`, `columnlen`, `rowhidden`, `colhidden` | Keyed by axis, not by cell |

`parseCellKey` is the one `"r_c"` parser. Insert and delete re-key borders, validation and hyperlinks through `shiftCellKeyedForInsert`/`Delete` (`engine/rowcol.ts`); merges have their own shifter. A track nobody resized stores no size and falls back to its sheet's `defaultColWidth` and `defaultRowHeight`, or to `SHEET_DEFAULT_COL_WIDTH` and `SHEET_DEFAULT_ROW_HEIGHT` on a sheet without them. Only the xlsx import sets a sheet's own, so an Excel sheet keeps Excel's pitch. The editor, the importer and the export all read them through `sheetDefaultColWidth` and `sheetDefaultRowHeight` (`packages/lib/src/sheets/defaults.ts`), so screen and export share one pitch. The export and the xlsx import's chart anchors walk tracks to pixels through `sheetColumnsWidth` and `sheetRowsHeight` beside them, a hidden track counting none. A track's size counts its gridline, which the editor paints on the track's last pixel, as Excel counts it. So a column is as many pixels on screen as in Excel and the export, and a floating image, stored in pixels from A1, covers the same cells in all three.

`conditionalFormatRules` and `alternateFormatRules` stay arrays, because order is rule priority (Excel's model, exported as xlsx priorities). Two clients appending a rule at once can disagree on that order, visible only where rules overlap ([the proposal](proposals/PROPOSAL_SHEETS_YJS_WORKBOOK.md#what-diverges-today)).

## The snapshot is interned and written only through the codec

`encodeSheetsSnapshot` and `decodeSheetsSnapshot` (`packages/lib/src/sheets/snapshot-codec.ts`) are the only way in or out of `state.snapshot`. A real 340k-cell workbook was 56 MB as plain JSON, because 224 style combinations and about 110 border payloads repeated per cell. The v2 envelope interns both into workbook-global dictionaries and is about 4.5 times smaller. The codec runs only where the snapshot is serialized: the in-memory `Sheet[]`, the ops and the replay don't know it exists.

- The dense `data` matrix folds into the cell list at encode and is never stored. `selections`, a per-client cursor, is stripped.
- `calcChain` is never stored. The envelope's `computed` flag tells the decoder to seed it, which is the signal the server's recalc gate reads ([§ The editor computes on write](#the-editor-computes-on-write-the-server-only-what-nobody-computed)).
- `images` and `charts` ride verbatim, since there is nothing to intern. An `images` array, the form before images became a map, decodes as no images: sheets keep no backward compatibility, and no per-image write could resolve on an array. `opToPatchOnSheets` drops the whole-array write a tab still open on that build sends, for the same reason.

The editor writes a fresh snapshot and clears the op log on unmount and on `beforeunload`, but only when it is connected and alone: no other client in the document's awareness, viewers included (`flushSnapshot` in `use-sheet.ts`). A flush reaches every open tab as a new snapshot, and that tab remounts its grid on it, which throws away its undo stacks; so closing one tab must not cost the others their undo. A flush with no pending ops is skipped, because every edit is an op. So the log grows while any tab stays open, a tab closed offline flushes nothing, and two tabs that close together each see the other and leave the log for the next close. Nothing is lost: a joiner and the server replay the log ([ROADMAP.md](ROADMAP.md), "Sheets: fold the op log while editors are connected" and "Sheets: a tab closed offline leaves the op log for the next close").

## An undecodable snapshot locks the editor and never overwrites

Anything that is not a v2 envelope throws, and so does a dictionary index past its table. How `use-sheet.ts` reacts depends on when. On the initial load it opens read-only on blank defaults, and the `loadedRef` gate keeps it from ever flushing them over the stored snapshot or sending an op built on them. On a peer's flush it can't read mid-session, it keeps the workbook already on screen and arms the same lock, because local state may now diverge from the wire. Either way a persistent banner in `editor.tsx` says so, because a blank read-only sheet with no lasting explanation looks like data loss.

Version history keeps snapshots in older encodings. Restoring one answers 409 and changes nothing (`apps/api/src/lib/versioning/restore.ts`), because every connected editor would lock.

## Undo is per tab and follows a peer's rows and sheets

Undo is the tab's own pair of stacks of immer patch entries (`globalCache.undoList`/`redoList`, kept by `components/Workbook/index.tsx`). The steps are functions in `state/modules/history.ts`: `undoEntry` and `redoEntry` take the context and an entry and return the next context and the batch to send. Only a redone sheet delete changes its entry: it keeps the sheet as the redo found it, so the next undo brings back a peer's edits made since the first delete. An undo is broadcast as an ordinary op batch, so peers see an edit. A peer's batch is never undoable locally.

An entry names its sheet by id, `['sheets', id, field, …]` (`recordEntry`), so a peer adding or deleting another sheet moves nothing, and a write to a sheet that is gone is dropped. A peer's row or column op shifts both stacks through `shiftEntries` (`state/modules/history-shift.ts`), as it shifts the live cells: cell paths, the `"r_c"` keys of merges, borders, links and validation, the row and column size maps on the op's axis, `mc` references, and formula text on every sheet that points at the moved rows, through the same `functionStrChange` the engine uses. That formula text includes a whole matrix your own row op recorded on another sheet, a deleted sheet's stored cells and a copy a redo adds back. A whole matrix or map on the op's sheet, such as a sheet's first link, moves as one. An entry the op makes meaningless is dropped instead: one that writes inside deleted rows or columns or cuts through a merge, a whole `config` or a range-valued field on that sheet (conditional formats, filter, frozen panes), a chart's data or points on a chart that reads that sheet, and your own row or column op on that sheet. So a peer's row op on the sheet of your own row op still empties that undo, and a conditional-format edit on it too. A linked cell's `hl` keeps the place the link was made, which no row op moves, so a write finds the link under the cell's own key. Your own ops never shift your stacks, because last in, first out already fits them. That breaks once a peer's op drops your own row or column entry: the entries below it on the undo stack were recorded without that op, and those below it on the redo stack expect it redone, so they first take its move, or on the redo stack its inverse. `calcChain` entries move with their cells but are never checked: the chain is the tab's recalc list and is never stored. Overwriting one formula records the whole list, so a whole list loses the cells a peer's delete takes instead of dropping the entry. The undo stack keeps its newest 200 entries, and of the entries that hold whole matrices, a row, column or sheet change, only the newest ten (`pushEntry`). Only the oldest entries are ever dropped, since an entry dropped from the middle would misplace the ones below it.

The shift happens in `applyOp`'s updater, once the batch applied: `applyOpBatch` reports the row and column ops it applied with the sheets it applied each to, so a skipped batch or a refused op moves nothing, and a second batch before the next render shifts against the sheets the first left. `handleUndo` and `handleRedo` move their entry between the stacks in their updater too, so the two happen in the order they were called. React may run an updater twice, so each does its bookkeeping once. A few rare cases slip ([ROADMAP.md](ROADMAP.md), "Sheets: apply every edit to one eager context"). A ⌘Z can overtake a peer batch still waiting to render, because the keydown renders at a higher priority than the WebSocket's batch. React then runs the undo updater again on top of the peer batch: the guard stops a second pop, but the entry it took is applied again unshifted, and its batch is sent twice. An async local edit, such as a paste, still in flight when a peer batch arrives misses that batch's shift.

## Undo skips a cell a peer changed since

Before an undo writes a cell or field back, it checks that the target still holds what the entry wrote there, and skips it otherwise, as Google Sheets does; redo checks against what the undo restored (`stillWritten`). For a formula cell it compares what a person wrote, not the value, display text or value type the engine computed, so a formula whose precedent a peer changed still undoes. A merge and its cells' `mc`, and a link and its cell, pass or skip together, so an undo never leaves half a merge. A skipped patch is not sent. The check runs only on the client that undoes, so two peers undoing at once, or an offline tab rejoining, still settle by arrival order ([§ An edit is an op in a Y.Array](#an-edit-is-an-op-in-a-yarray)). An undo or redo sends no value or display text the entry recorded for a formula cell, since a peer may have changed its inputs or the formula itself. It recalculates the formulas it wrote and every formula that reads a cell it wrote, as an edit does, and sends those values.

## A structural undo applies exactly the ops it sends

An undo or redo that adds or deletes a sheet, rows or columns builds a batch of ops and applies that batch through `applyOpBatch`, as its peers will. Applying the entry's own patches would differ from the wire: a row op records whole fields, `data` among them, and a sheet delete records the whole sheet list, so a local undo would put back the old matrix or workbook over every peer edit since while peers only took the marker.

- A sheet delete keeps the deleted sheet in the entry's options. Its undo is an `addSheet` op with that value plus the order ops, which also gives the restored sheet its `data`. Its redo, and the undo of an add or a copy, is a `deleteSheet` op by id plus the order ops. `addSheetOps` and `deleteSheetOps` (`state/utils/patch.ts`) build these batches for the edit, its undo and its redo alike: a joiner's replay appends or removes the sheet and moves no other, so the batch carries the orders the op left.
- A row or column entry ships its marker, the edited sheet's fields and a repair of the cells. The fields ship whole, as the op's own do, but they are what the marker makes of the live sheet, so a peer's width, merge or formula since survives. Where the entry recorded a field and the marker alone would not bring its value back, such as a deleted row's height, merge, link or validation, the entry's value goes in, key by key in a map and `config` one level deeper, unless a peer changed that key since (`restoredFields`). The recalc list takes the entry's formula cells the marker would not bring back. A field that is no map, such as the conditional formats or the frozen panes, takes the entry's value only when no peer changed it.
- The marker alone would not bring back a formula a delete made `#REF!` or shrank, on any sheet, or the cells a delete took, so the batch also carries a repair: a `replace data/r/c` for each cell where the entry's matrix differs from what the marker makes of the matrix the op left, unless a peer changed that cell since (`repairOps`). A sheet nobody opened, such as a copy, has no matrix, so the entry recorded its stored cells and the repair reads those. The repair lands before the merge stamps, which need the cells. The repaired cells hold the values the entry recorded, so the step then recalculates them and every formula that reads them, as a cell undo does, and sends those values too. The marker's trial runs that `restoredFields` compares each get a formula map of their own, since the map and the open editor's range state live outside immer.

`packages/sheet/src/test/state/modules/history.test.ts` runs every case on two tabs and a joiner, and pins the shifter's paths. Whether to move to Yjs structures and `Y.UndoManager` is answered in [PROPOSAL_SHEETS_YJS_WORKBOOK.md](proposals/PROPOSAL_SHEETS_YJS_WORKBOOK.md): only with stable row and column ids, and not first.

## Every sheet switch goes through `changeSheet`

Tab clicks, the sheet list, search, hyperlinks, the API and the current sheet going away all call `changeSheet` (`state/modules/sheet.ts`). When the current sheet is hidden or deleted, locally, by a peer or by an undo, `leaveCurrentSheet` lands on the first visible sheet in tab order, with `force` skipping the `beforeActivateSheet` veto. A hidden target is refused, and so is hiding your last visible sheet.

A switch closes the cell editor and any formula range selection, so Enter can never commit into a sheet a peer switched you to. It also derives everything the grid paints (`applySheetView`) inside the same recipe. The first frame after the commit paints before any effect runs, so anything left to an effect would draw the new sheet on the old sheet's geometry for one frame.

## The engine is the half the server imports

`packages/sheet/src/engine/` holds the parser and evaluator, the dependency graph, recalc, row and column shifts, the op replay and the conditional-format evaluator. The editor and the server run the same code. `engine/` imports nothing from `state/` and nothing from the DOM. It evaluates through a `CellResolver`: the editor's resolver reads the workbook context, the server's (`createArrayResolver`) reads a replayed `Sheet[]`. Orchestration that needs the context, such as `execFunctionGroup` and `groupValuesRefresh`, lives in `state/modules/formula-exec.ts`.

`apps/api` imports only the `@workspace/sheet/engine` subpath, and two of its leaf modules: `engine/a1-notation` and `engine/format`, which a docx or pptx chart reads its ranges and number formats through, since the barrel evaluates the whole formula engine, formulajs included (632 modules). The `./engine` entries in `packages/sheet/package.json` point at the TypeScript source, not a build, so the API's own type check covers the engine under its stricter options: no DOM lib, `verbatimModuleSyntax`, `noUnusedParameters`. A DOM or state import in the engine fails the API build.

The functions come from `@formulajs/formulajs`, behind a parser inherited from the fortune-sheet fork. A function neither formulajs nor the engine has (LET, FILTER) evaluates to `#NAME?`. An error is a value, not a throw: an operator's or a function's error, and an error typed into a formula such as `#N/A`, reaches `ISERROR`, `ERROR.TYPE` and `IFERROR` as formulajs's own error object (`toFormulaError` in `engine/parser/error.ts`), because those functions compare errors by identity. An unknown name is `#NAME?` the same way, and so is a function Excel doesn't know either, such as the typo `FILTRE`, so `IFERROR` traps it, as in Excel. A real Excel function the engine lacks is not: `callFunction` throws its `#NAME?`, so no `IFERROR`, `IFNA` or `ISERROR` traps it and the whole formula is `#NAME?`, because the fallback would read as the answer Excel computed. `isExcelFunction` in `packages/lib/src/sheets/excel-functions.ts` holds every Excel function name, from Microsoft's alphabetical list; formulajs is no source for it, because it registers Google Sheets' functions too. The engine overrides `VALUE`, which rejects a number, and `TEXT`, which formulajs leaves unimplemented, so it formats through the same numfmt masks the grid renders with, and an empty mask gives empty text. It overrides `CONCATENATE` and `CONCAT`, which join a number with JavaScript's `toString` and a Date with `Date.toString()`. It overrides `INDEX`, which reads a row_num or column_num of 0, empty or blank as 1, where Excel gives the whole column or row as an array: `SUM(INDEX(A1:C2,,1))` sums column A. A lone index into a one-row range picks along the row, as Excel's does: `INDEX(A1:C1,2)` is B1. The engine has no reference form of `INDEX`, so no area_num. `FIND` and `SEARCH` read a start_num below 1 as 1, where Excel's is `#VALUE!`, and `NUMBERVALUE` answers NaN for text it can't read, which shows as a blank; overrides make both `#VALUE!`. It adds `XLOOKUP`, `XMATCH`, `TEXTJOIN`, `MAXIFS` and `MINIFS`, which formulajs 2.9.3 lacks, from `engine/parser/functions/`, one file per family: `FUNCTIONS` in `formula-function.ts` registers them, and a function added there may return a blank, which an override can't, since its `undefined` falls through to formulajs. `MAXIFS` and `MINIFS` test their criteria with formulajs's own `lib/utils/criteria-eval`, the test its `SUMIFS` and `COUNTIFS` run, so all of them match the same cells (`src/test/engine/parser/functions/statistical.test.ts`). That test is case-sensitive and knows no wildcard but a lone `*`, unlike Excel's; the gap is open in [SHEETS-TODO.md](SHEETS-TODO.md#formula-engine).

`XLOOKUP` and `XMATCH` take each of Excel's match modes (exact, next smaller, next larger, wildcard) and search modes (first to last, last to first, binary over ascending or descending data), so an imported `XLOOKUP(2.5,A1:A5,C1:C5,,-1)`, the shape Excel writes for a mode with no if_not_found, finds the next smaller row. A lookup lands only on a value of its own kind, as in Excel: 5 never matches `"5"`, so a binary search steps over a column's trailing blanks. An exact match is the first of its duplicates in every mode, the row a linear search finds (`src/test/engine/parser/functions/lookup.test.ts`).

Excel's dotted names (`STDEV.S`, `NORM.S.DIST`, `NETWORKDAYS.INTL`) are properties formulajs nests under a function or a namespace, so `resolveFormula` walks into both. `DOTTED_FUNCTIONS` in `formula-function.ts` lists the ones the engine registers, by hand, because formulajs's aliasing leaves nested paths Excel doesn't know (`STDEVS.P`, `CEILINGMATH.MATH`). `T.DIST`, `T.TEST` and `F.TEST` are left out: formulajs computes something else under those names, and `#NAME?` lets an imported cell keep Excel's cached value ([Recalc keeps what it can't improve](#recalc-keeps-what-it-cant-improve)). The function list that autocomplete and Insert function read (`state/modules/function-list.ts`) offers only names the engine registers and evaluates, so not the ones formulajs registers as a stub that throws "not implemented" (`FIXED`, `PRICE`, `CELL`), which `src/test/state/modules/function-list.test.ts` checks. Overrides fill in an omitted significance of 1 for the `CEILING.*` and `FLOOR.*` variants, which formulajs reads as 0, and make `ERF.PRECISE` and `ERFC.PRECISE`, which formulajs leaves unimplemented, `ERF` and `ERFC` of one argument. The xlsx writer stores each dotted name with the `_xlfn.` prefix except `ERROR.TYPE` and `ISO.CEILING`, which the 2007 file format already defines; `apps/api/src/test/ooxml/spreadsheetml.test.ts` checks every registered name against that list.

The grammar is `engine/parser/grammar-parser/grammar-parser.ts`, a jison parser converted to TypeScript and edited by hand since, its parse table included. `grammar-parser.jison` beside it is the readable copy: the same lexer rules and productions in the same order, with a header naming what only the TypeScript holds. Nothing generates from it, and regenerating would lose the hand edits, so a grammar change edits both files and regenerates neither.

An empty argument, as in `SUM(1,,2)` or `SUBSTITUTE(A1," ",)`, is a slot of its own, because Excel writes `,,` into its files. The grammar gives it the `OMITTED` marker (`engine/parser/omitted.ts`), and Excel's rule depends on the parameter: an empty number is 0 and an empty text is `""`, so `LEFT("abc",)` is `""` and `VLOOKUP`'s empty range_lookup is FALSE, an exact match. formulajs can't be handed the slot as `undefined`, which it reads as not supplied (`LEFT("abc",)` would be `"a"`). So `formula-function.ts` hands it `""` at the text parameters `TEXT_PARAMETERS` lists for the text functions, and 0 everywhere else, which is Excel's answer for `SUM`, `ROUND`, `IF` and `VLOOKUP`. A function in `FUNCTIONS` gets the marker itself and reads it as Excel reads that parameter: an empty `XLOOKUP` if_not_found is not supplied, an empty mode its default. `PI()` stays a call with no arguments, not one empty one.

formulajs carries one patch, `patches/@formulajs%2Fformulajs@2.9.3.patch`, listed in `patchedDependencies` in the root `package.json`. Its `flattenShallow` (`lib/utils/common.js`, the only build the engine loads: `main` is `index.js`, which requires `lib/`) concatenated onto a `reduce` accumulator, copying it per row, so flattening a range was quadratic in its rows: 100,000 rows took 2.1 s, one `SUMIFS` over 208,681 rows 305 s. The patch is the same flatten as a loop, with the same output, and it no longer pushes into its input. 4.6.0 has the old code. Once a release fixes it, delete the file and the `patchedDependencies` entry and run `bun install`. Keep `src/test/engine/formulajs-flatten.test.ts`, which pins the output and the time. Both Dockerfiles copy `patches/` with the manifests, because the install applies it.

## Values follow Excel's grid and calendar

- A Date result (`DATE`, `EOMONTH`, `NOW`) is stored as its Excel serial, taken from the Date's local calendar fields, because formulajs builds its Dates at local midnight. `dateToSerial` in `engine/parser/helper/number.ts` is the engine's conversion, with the Lotus leap day from 1900-03-01. The cell keeps its format mask, so a mask-less cell shows the serial.
- Every range is clamped to the sheet grid, because an unclamped `A1:XFD1048576`, a shape real xlsx files carry, is 17 billion cells. So `ROWS(A1:A100)` on a two-row grid is 2 (`packages/sheet/src/test/engine/formula-engine.test.ts`), a range past the grid is empty, and an `INDEX` past the grid is `#REF!`.
- The engine has no spill. An array result (a bare range, `TRANSPOSE`, an `XLOOKUP` returning several columns) shows its top-left value, the value Excel's spill anchor holds, so a recalc of an imported anchor lands on Excel's cached value. Inside another function the whole array passes, so `SUM(XLOOKUP(...))` sums the matched row. Spill is open in [SHEETS-TODO.md](SHEETS-TODO.md#formula-engine).
- formulajs parses an ISO date string as UTC (`DATEVALUE("2026-01-05")`), so the result is off by the zone offset outside UTC. `DATE(...)` is built in local time and is right everywhere. The fix is open in [SHEETS-TODO.md](SHEETS-TODO.md#formula-engine).

The dependency graph has two limits:

- A reference cycle never errors: the visited set in `getCalculationOrder` breaks the walk, and the cycle's cells evaluate in visit order.
- `INDEX` produces references the dependency graph can't see statically. `isFunctionRange` special-cases it, together with `INDIRECT` and `OFFSET`; keep that logic when you touch the graph. formulajs 2.9.3 has no `INDIRECT` or `OFFSET`, so both evaluate to `#NAME?`.

## The editor computes on write, the server only what nobody computed

The editor's dependent recompute runs inside the recipe that emits the op, so recomputed `v` and `m` persist as ordinary ops. A doc edited in a browser is already fresh when the server reads it.

So `readSheetsFromDoc` recomputes only on the export read. Preview and the search extract pass `{ recalc: false }` and serve the replayed values, and a formula cell with no value stays blank. A legacy never-computed workbook costs an unbounded recalc (about 39 s measured), past the 30 s transform deadline of a preview, so every preview of such a doc would fail. An export recomputes under its 120 s deadline, because a deliverable with blank formula cells is wrong output.

Even on export, `recalcSheets` runs only when `sheetsNeedRecalc` finds a sheet with formula cells and an empty `calcChain`. The decoder leaves the chain empty unless the envelope says `computed: true`, which every editor flush writes ([the codec](#the-snapshot-is-interned-and-written-only-through-the-codec)). The xlsx importer runs `recalcSheets` once in its transform and writes `computed: true`, or `false` when its recalc failed, so that export recomputes. Any recalc failure falls back to the replayed values: an export never fails because recalc did.

The server's recalc, at import and at export, runs under a budget, `SERVER_RECALC_BUDGET` (`document/sheets.ts`). The dependency index lists a range in every 64 × 16 block it meets, cut to the cells its sheet holds: only a formula cell is ever looked up, so `SUM(A1:XFD1048576)` on a small sheet costs the few blocks the sheet spans. Past the budget `recalcSheets` throws before it evaluates, a recalc failure like any other. Evaluation is charged each cell a range read covers, cut to its sheet (`maxCellsRead`), and stops at the formula after the one that passed it. Nothing bounds the parent edges, one per formula cell and formula reading it ([ROADMAP.md](ROADMAP.md)).

## Recalc keeps what it can't improve

`recalcSheets` (`engine/recalc.ts`) materializes each sheet's `data`, finds formula cells by scanning it rather than trusting `calcChain`, orders them through the dependency graph and evaluates them with the shared `FormulaEngine`. Its graph builder is a port of the state layer's `setFormulaCellInfo`, because the engine can't import `state/` ([SHEETS-TODO.md](SHEETS-TODO.md#code-debt) tracks removing the copy). The INDIRECT, OFFSET and INDEX walker inside it, `isFunctionRange`, is one function in `engine/formula-utils.ts` that both call.

Four rules keep a passive export honest:

- Volatiles (`NOW`, `TODAY`, `RAND`, `RANDBETWEEN`) keep their cached value, the way Excel reads a closed file, so an export is deterministic.
- An engine error never overwrites a cached value that is not an error. A function this build lacks would otherwise turn Excel's correct result into `#NAME?` at import. Downstream cells then read the cached value too.
- A function Excel has and this build lacks is such an error even inside `IFERROR` or `ISERROR`, because the evaluator fails the whole formula rather than hand them a `#NAME?` to trap. So `=IFERROR(FILTER(…),"none")` keeps Excel's value instead of computing `none`.
- A formula that uses a name the engine can't resolve keeps such a cached value even when its result is no error. The import writes each defined name into the formulas that use it, and one it can't stays as written ([EXPORT.md](EXPORT.md#an-xlsx-defined-name-is-inlined-into-the-formulas-that-use-it)). The engine has no names, so `IFERROR` traps that name's `#NAME?` and computes a fallback Excel didn't. The guard asks `FormulaEngine.isKnownName` about each name `inlineNames` finds, the walker the import inlines names with, so a name shaped like a cell past column XFD, such as `RhoCO2`, counts too.

Every cell is guarded, so one poisoned formula never aborts the pass.

## The editor builds its formula map when idle

At mount the Workbook materializes each sheet's `data` and `seedCalcChain` records the formula cells without evaluating them. Its `data` prop takes the stored sheets, whose `id` is optional, and the mount gives a sheet without one an id, so the editor's own `Sheet` type (`state/types.ts`) requires it. Displayed values come straight from the stored workbook, and an edit recomputes only the affected sub-graph (`execFunctionGroup`), so recalc cost follows the edit, not the workbook.

The dependency map (`ctx.formulaCache.formulaCellInfoMap` and its reverse `dependencyIndex`) is built from an idle callback, so the first edit on a large workbook doesn't pay a multi-second rebuild. It is all or nothing: whichever comes first, the idle build, an edit or a paste, builds the whole map, from a plain `current()` snapshot, because reading every formula through an immer draft is slow.

Once built, the map is kept current cell by cell. Local writers register what they write through `setFormulaCellInfo`. Undo, redo and a peer's ops go through `updateFormulaCache`, which reads only `data` patches, because every formula change carries one. A structural patch or a row or column insert or delete sets the map to `null` for a lazy rebuild. The `calcChain` patch that rides along is ignored, because re-registering from it cost a whole sheet per edit. The known gap, a copied sheet's formulas, is in [SHEETS-TODO.md](SHEETS-TODO.md#bugs).

## Number display strings go through `numberDisplay`

`numberDisplay(value, fa)` (`engine/format.ts`) turns a number into its `m`. Typed entry, paste, sort, autofill, the toolbar format change, the format painter, `setCellFormat`, recalc and the xlsx importer all call it. A mask renders the exact value. General is Excel's General at default width, so float noise hides (`0.1+0.2` shows `0.3`), long values cut to 11 characters and large or tiny values go scientific. A malformed format, which an xlsx file can carry, falls back to General. The input parser (`parseCellInput`) and autofill's date series still format on their own.

A typed number is stored as a number in `v`, unless the cell is text-formatted. Pasted plain text goes through the same `setCellValue` parse as typing. A formula's text result stays text (`=TEXT(5,"000")` is `"005"`). Copying a General number writes 15 significant digits (`copiedNumberText`), not the 11-character display, so a paste elsewhere keeps the precision. A formula that joins a number into text (`&`, `CONCATENATE`, `CONCAT`, `TEXTJOIN`) writes it the same way, through `numberText` (`engine/format.ts`), at Excel's 15 significant digits: `(0.1+0.2)&""` is `"0.3"`, and a number past 15 digits is E notation (`1E+21`).

A cell without its own horizontal alignment takes Excel's General alignment by its value (`generalAlign` in `engine/format.ts`, read through `normalizedCellAttr` in `state/modules/cell.ts`): a number or a date right, a boolean or an error centred, text left. The painter, the text layout, the overflow and the HTML and PDF export read it there. A tick box is the exception: it sits where the cell's own alignment puts it. Else a box drawn alone is centred, as in Google Sheets, so a ticked, an unticked and an empty cell's box sit in one place, and a box with a label beside it sits left, so the label keeps the cell's width; a rule with its own values labels every box, an empty one's included, so its column stays one (`checkboxAlign`, which the painter and the click share).

## A copy puts the cells on text/plain as TSV

A range copy writes three flavors: the HTML table with the cells' styles, the Eigen clipboard payload, and TSV on `text/plain` with tabs between cells and newlines between rows. `rangeValueToClipboard` (`state/modules/selection.ts`) builds the table and the TSV in one pass over the same cells, each cell's display text with General numbers at 15 digits. A cell holding a tab, a line break or a leading quote is quoted and its quotes doubled, as Google writes it, through `cellsToTsv` in `@workspace/lib/clipboard`; a quote inside text stays as it is, so `12" pizza` pastes as typed. The Eigen text item carries the same cells unquoted, tabs and newlines between them, because Docs reads it as text rather than as TSV. The HTML table writes a cell's font size in pt, the unit every font size on the clipboard is in ([CLIPBOARD.md](CLIPBOARD.md#a-font-size-crosses-in-pt)), and the table paste reads a size in pt as pt and in px at 96 dpi. A collaborator or an xlsx can store any value, so the table writes a color only as a hex color, a border's else transparent, a row height, column width or merge span only as a finite number, else the default, and escapes every style attribute. The plain text is what a paste into a text field, a chart's Edit data grid or another app without an HTML reader gets, so it has to keep the grid's shape. The plain-text paste in Sheets itself splits on tabs and newlines and doesn't unquote, so a quoted multi-line cell pasted as plain text lands split ([SHEETS-TODO.md](SHEETS-TODO.md#bugs)).

## Enter and Tab commit an edit and move on

While a cell is open, Enter commits it and moves down, and Tab commits and moves right, Shift+Tab left, as in Google Sheets. Both go through `commitEdit` (`state/events/keyboard.ts`), which writes the cell and collapses the selection to it before the move. A visible formula suggestion takes Tab first and stops it, so Tab picks the function instead of committing.

The open editor's cell is `ctx.editingCellPosition`, and every commit path writes there. A peer's row or column op on the current sheet moves it with its cell (`followEditor` in `applyOpBatch`), so Enter writes where the person was typing, not into the row that slid under the editor. A peer's delete of that cell closes the editor without writing.

## The cell editor edits rich text as runs

A rich-text cell keeps its text as runs in `ct.s`, each a piece of text with its own weight, slant, decoration, color, size and font. While the cell is open, the in-cell editor shows the same runs as spans, and `state/modules/inline-string.ts` is the one model between the two. The editor's DOM reads into runs, a toolbar format applies to the selected characters (`formatEditorSelection`), the runs go back as spans (`runsHtml`) and the selection comes back by character offset. `updateCell` commits what `committedRuns` reads, so the cell gets what the editor shows. The reader takes whatever markup the editor holds: our spans, the browser's own `<b>`, `<br>` or `<div>`, and bare text typed beside a span. Offsets count text, not HTML, so an `&` or a `<` can't shift a format, and a `<br>` or a block counts as the one line break it reads as, both ways. A run it reads is whole, all seven style keys, with the color as hex and the font as a name, as the xlsx import stores runs. Stored runs come from a collaborator or an xlsx, so `runStyleOf` checks them before `runsHtml` writes CSS: a color that isn't hex, a size that isn't a number, or a font name with `;`, a quote, a bracket or a line break falls back to the default (`cssFontName`). The editor box and the copied table's HTML read a cell's own font keys through the same `runStyleOf` (`getFontStyleByCell`), so the box and the runs typed in it agree on a legacy string size, and a cell-level color, fill or font, or a conditional format's colors, that isn't a plain value writes no CSS there either (`hexColor`). The canvas and the format toolbar read a style through `runStyleOf` too, so a run that leaves out its size or color draws, edits and shows in the toolbar at the default, 10 pt in black, and its underline is as thick as its glyphs are large. Every size, a plain cell's included, goes through `cellFontSize` in `@workspace/lib`, which keeps Excel's 1 to 409 pt without rounding, so the canvas, the editor and the xlsx, HTML and PDF exports draw and write the one size a file brought in; only the toolbar's size box steps and caps at 400, as Docs' does.

A paste while the editor is open is its plain text, as in Google Sheets (`onPaste` in `InputBox`): it types as typed text would. A paste onto a closed cell goes to the grid as before. One handler owns each paste: the Workbook's document `paste` listener returns while a cell is open, so the text lands once and no image, chart or rows land on the grid. A ⌘V on the grid sets `selectionCache.isPasteAction` and `handlePaste` takes it; a paste the listener handles without `handlePaste`, such as a chart or an svg, clears it, or the next paste would run as a grid paste.

Text outside any styled element has the cell's own style, which the editor box shows: `getStyleByCell` styles the box for a rich cell too. A span states only where its run differs from the cell, so a word un-bolded in a bold cell reads back as not bold. Text all in the cell's style commits plain, so a format undone before Enter leaves no runs. A format while the editor holds a formula goes to the cell, as before.

⌘B, ⌘I and ⌘U while the editor is open on text go to the toolbar's handlers (`InputBox`), so the browser never writes its own `<b>`. They match through `SHEET_HOTKEYS`, as the grid's do ([§ Every shortcut is defined once](#every-shortcut-is-defined-once-in-sheet_hotkeys)). A format on a bare caret waits for the next `beforeinput` and types that text in its style, as Google and Excel do, and a caret that moves drops it. Text typed over a selection takes the style of its first character, as in Google Sheets and Docs: the browser drops a span whose text is all selected and types plain, so `typeStyledText` types over a selection that starts in a styled run itself and leaves one that starts in the cell's own style, or a formula, to the browser. A toolbar control that takes the focus, such as the size box or the color popover, formats the selection the editor last had: `InputBox` keeps it on every `selectionchange` (`rememberEditorSelection`) and forgets it, with a waiting caret format, when the editor closes. As a menu or popover of the menu bar closes, or the size box blurs to nowhere, `useCellEditorRefocus` gives the focus and that selection back to the editor: Radix would focus the menu's trigger, where the next keys type nothing. Whatever took the focus as the menu closed keeps it, as in Docs' `keepEditorFocus`: a dialog the menu opened, such as Data verification, or an input a press outside landed on ([LAYOUT.md](LAYOUT.md#the-app-bars-menus-are-one-radix-menubar)). The size box drops Enter's own action, which would otherwise type a line break over the editor's selection once the focus is back. While a cell is open, the format toolbar shows the run at the caret (`useEditorSelectionStyle`). The menu bar reads it once, on one listener, and hands it to the toolbar and the Format menu. A caret that moves inside one run keeps the same style object, so neither re-renders. That style is state set on `selectionchange`, never a DOM read during render: the app's React Compiler memoizes such a read, and a moved caret changes none of its inputs, so the toolbar would stay on its first answer while a unit test, which runs without the compiler, passes.

The canvas wraps a rich cell between words, inside a run too, and the runs on one line share its baseline (`getCellTextInfo`, `state/modules/text.ts`). It splits runs into words only when the cell wraps, and keeps the line's width as it goes, so a long cell lays out in one pass: the painter lays out every cell it draws, with no cache of the layout. The words of one style on a line join into one piece before they are placed, so right-to-left text reads in its own order and the canvas kerns across spaces. Runs of different styles on one line still go left to right. Wrap and a size from the Format menu or the toolbar's box grow the row to the wrapped lines (`updateFormatCell`). Such a caller passes no cell height, and `getCellTextInfo` then lays out every line of a plain cell, where the painter stops at the lines that fit the row. The HTML, PDF and preview export still draw a rich cell in its own style ([SHEETS-TODO.md](SHEETS-TODO.md#bugs)). `packages/sheet/src/test/state/modules/inline-string.test.ts` pins the editor model through the toolbar handlers and the commit.

## Every shortcut is defined once, in `SHEET_HOTKEYS`

`SHEET_HOTKEYS` (`state/events/keyboard.ts`) holds each sheet shortcut as one TanStack hotkey string, such as `Mod+B`. The grid's `handleWithCtrlOrMetaKey`, the Workbook's undo and redo, the open cell editor's ⌘B, ⌘I and ⌘U and the focus lock all match a keydown against it with `matchesKeyboardEvent`, and the Edit and Format menus show it with `formatForDisplay`. So a menu row can't name a key that doesn't work, and `Mod` reads ⌘ on a Mac and Ctrl elsewhere, as in Docs. Find and Find and replace show the find bar's own `FIND_HOTKEY` and `FIND_REPLACE_HOTKEY`. The screen-reader shortcut list in the Workbook reads the same table with `formatWithLabels`. `src/test/components/Workbook/hotkeys.test.tsx` and `src/test/state/events/keyboard.test.ts` spell every key out, so a changed definition fails a key test and a label test.

The matcher takes the letter the layout types, else the physical key, so ⌘B still bolds on a Russian layout. The physical key also matches when the layout types another Latin letter, so the order of the checks matters: the grid checks ⌘X before ⌘B and ⌘C before ⌘I, because Dvorak types x on the B key and c on the I key. The collisions that remain are a known bug ([SHEETS-TODO.md](SHEETS-TODO.md#bugs)).

While a cell is open, ⌘Z, ⇧⌘Z and ⌘Y belong to the browser, which undoes the typing in the editor, as Google Sheets does. The Workbook runs the sheet's undo only while no cell is open. Otherwise one ⌘Z would undo the typing and the sheet's last edit at once.

Keys with a name rather than a letter, such as Enter, Tab, the arrows, F2, Escape and Delete, still dispatch on `e.key` in `handleGlobalKeyDown`, and so does Ctrl+Shift+; for the date and time: a hotkey string can't name the shifted punctuation a layout types there.

## Conditional formats evaluate headless

`evaluateConditionalFormat(rules, data, options?)` (`engine/conditional-format.ts`) returns the `"r_c"`-keyed style map the canvas paints, and the HTML export calls it too ([§ The export paints conditional formats with the grid's evaluator](#the-export-paints-conditional-formats-with-the-grids-evaluator)). Without an evaluator, formula rules are skipped. Both callers pass the same one, `createCfFormulaEvaluator`.

Every rule scans only the materialized matrix, because Excel writes a whole-column rule as `A1:A1048576`. Overlapping rules layer per style property in rule order, so a later rule's fill never erases an earlier rule's text color. `textContains` ignores case and `duplicateValue` skips blank cells, both as in Excel.

## A formula rule is anchored at its first range's corner

That is Excel's anchor: every cell of every range evaluates the formula at its offset from the top-left of the first range. `createCfFormulaEvaluator` compiles each formula once and evaluates it at that offset. It shares `offsetCoordinate` and `offsetRange` with `functionCopy`, the text shifter paste and autofill use, so shifted text and a compiled offset read the same cells. The xlsx importer keeps a rule with all its ranges, and the exporter writes one multi-range `sqref`.

Every rewrite of a rule's ranges (cut, copy, paste format, drag-move, row or column delete, the preview's clip) goes through `withCfRanges`. When the first range starts somewhere new, it re-expresses the formula from the new corner, so every cell keeps the relative formula it had. Autofill only appends a range and an insert moves corner and references together, so neither re-anchors.

One edge stays. A formula that reads above or left of its corner (`=A4>0` on `A5:A10`) can't be re-expressed from a corner nearer the sheet edge than it reaches, because A1 text has no row 0. `functionCopy` writes `#REF!` and the rule stops matching.

## Row and column shifts rewrite every sheet's formulas

`applySheetsInsertRowCol` and `applySheetsDeleteRowCol` (`engine/rowcol.ts`) shift the cells, geometry, merges, borders and conditional-format rules of the changed sheet, and formula text and chart refs in every sheet. Only references that resolve to the changed sheet move: unqualified ones on it, `Sheet!`-qualified ones anywhere. A sheet without a matrix, such as a copy nobody opened or any sheet a joiner's batch doesn't name, has its stored cells' formulas moved instead, so the live tabs, a joiner, the server's read and the next snapshot agree. A reference wholly inside a deleted band becomes `#REF!`, and a whole-row or whole-column range keeps both legs. The functions are generic over the sheet type, so the editor's wider sheet flows through with its extras. `state/modules/rowcol.ts` then shifts the editor-only fields: filter, frozen panes, validation, hyperlinks, `calcChain`.

## Images and charts are floating records in one paint order

`Sheet.images` and `Sheet.charts` map an id to a `SheetImage` or a `SheetChart`, both a `SheetFloatingObject`: a box in grid pixels from A1, an `angle` in degrees clockwise about its center (absent reads as 0), and an `index`, a fractional key that orders images and charts together for painting, ties broken by id. Two maps rather than one with a kind field, so the chart-only paths (ref shifts, the row and column write-back) stay chart-only. `floatingItems` (`packages/lib/src/sheets/floating.ts`) is the one answer to which objects a sheet holds and in what order; the editor's overlay, the export and a z-order move read it. `nextFloatingIndex` puts an insert above both kinds, and a z-order move goes through `zOrderKeys` over both, so neither throws on the tied keys two peers inserting at once leave behind. Both repair a tied or malformed key on the record and write the repair with their own write, because a malformed key such as `zz` sorts above any key an insert could take. An image's id is a uuid, because two peers must never write one key.

A file or a peer can store any box, a string included, and a side in the billions overflows the painter's stack, so `sheetFloatingBox` clamps every box wherever one is written or drawn: the xlsx import, insert, paste, move, resize and rotate, `renderSheetChartSvg` and the export. A side is at most `CHART_MAX_SIDE`, the 2112 px Docs caps a chart at, the corner lies on Excel's grid at the default track sizes, and an angle that is no finite number is 0. An inserted image larger than that is scaled down whole, so it keeps its aspect. Copying a sheet gives its images and charts fresh ids.

Each writer writes one object of the current sheet under its own key, field by field: the shared ones in `state/modules/floating.ts`, a chart's spec, range and look in `chart.ts`, an image's insert and media name in `image.ts`. A move writes `x` and `y`, a first rotate adds `angle`, a spec edit writes the parts and entries it changes, a look edit writes only the look fields it changes, and none ever replaces a whole existing object. So two people editing different objects merge, and a write into an object a peer deleted, a path immer can't resolve, is dropped on every client and in the replay instead of bringing it back, while the rest of its batch applies: an insert whose batch repairs a tied key on an object a peer deleted keeps its insert. One rule decides it, `floatingWriteFilter` (`packages/lib/src/sheets/floating.ts`): a write into an object applies when the object is there as the batch's earlier writes leave it, else as it stood before the batch. A chart's entry write applies only below a field that is a record, and nothing below an entry, which is a string; a write that would leave a chart past `MAX_CHART_SPEC_ENTRIES` is dropped, a whole chart, map or sheet carrying one too. `opToPatchOnSheets` runs it on every client and in the replay, and undo and redo run it on their entry (`withoutDeletedFloatingEdits`), so the undo of a merged gesture that edited and then deleted an object, which puts the object back and then its field, ends the same everywhere. What writes a whole object, redoing its insert or undoing its delete, brings back one a peer deleted only where the delete arrived first, the replay following the log's order; a client that takes the delete after it drops the object, so the two can end apart ([SHEETS-TODO.md](SHEETS-TODO.md#bugs)). `packages/sheet/src/test/state/modules/floating.test.ts` pins both kinds on the author, a peer and a joiner.

The selected object is `ctx.activeObject`, an image or a chart and whether a chart's editor is open, per client, so `filterPatch` drops it.

## A pending upload's name is swapped on every sheet and in the undo stack

An image inserted from an upload carries a `pending:` name until the upload settles ([MEDIA-REFERENCES.md](MEDIA-REFERENCES.md)). `replaceImageMediaName` and `removeImageByMediaName` walk every sheet, because the user may have switched tabs since the insert, and the zombie sweep collects pending names from every sheet too. The swap records no undo step, so the entry that inserted the image still holds the pending name, and a redo, or the undo of a delete, would bring back an image that never resolves. `replaceMediaNameInHistory` renames it in the undo and redo stacks as well, in a patch on the image, on its sheet's images map or on the whole sheet, a copied or deleted sheet's included (`packages/sheet/src/test/components/Workbook/image-undo.test.tsx`, `packages/sheet/src/test/state/modules/floating.test.ts`).

## A chart is a floating record whose refs name sheets by id

A chart stores its spec as a field per part (`SheetChartSpecParts`): `specChart`, `specTitle`, `specLegend` and `specData` one JSON string each, and the keyed parts `specAxes`, `specPlots`, `specSeries` and `specPoints` a record from each entry's key (`'y'`, `'column'`, `'s-1'`, `'s-1/3'`) to its JSON. Only `readChartSpec` (`packages/lib/src/charts/`) reads them, and a write applies a change onto them as stored ([CHARTS.md](CHARTS.md#an-edit-is-a-change-applied-onto-the-spec-as-stored)). The keyed parts are records from the chart's insert, import or paste on, and `writeSheetChartSpec` (`engine/chart-data.ts`) only ever sets or deletes their entries: a recipe that assigned a record would ship it whole, so two peers' edits of two series, axes, plot types or slices would collide, and an entry write below a record made in the same moment would fail a joiner's batch. A read stops measuring at the byte limit but still lists a record's keys, so the entries a chart can hold are capped at `MAX_CHART_SPEC_ENTRIES` where a write, a snapshot or a whole sheet comes in: a chart a build writes holding more is past the byte limit anyway, and forged two-byte entries, about 32,000 of which fit under it, stop at the cap. A range ref in the spec names its sheet by id, so renaming a sheet moves nothing. Copying a sheet points its charts' refs to the copied sheet at the copy, as Excel and Google do. An xlsx import brings a chart Excel anchors on a worksheet in as one of these records over the same cells, and a chart sheet as a sheet holding its chart ([EXPORT.md](EXPORT.md#an-xlsx-chart-comes-in-over-the-cells-excel-draws-it-over)). The import reads an anchor's box only, so an imported chart stores angle 0.

## Chart refs shift with rows and columns, and an undone delete ships them

A row or column insert or delete shifts every ref to the edited sheet, on every sheet's charts, inside the engine, so the editor, a peer and the replay all run it. The rule is Excel's, and conditional formats and alternate formats share it through `shiftRangeForInsert` and `shiftRangeForDelete` (`engine/rowcol.ts`): an insert at or before a ref moves it, inside grows it, right after leaves it, and a delete shrinks it. Deleting all of a values or categories ref makes it null, and a deleted name cell leaves the series unnamed. A chart's points, a pie's slice colors among them, go by index along the categories, or along the first series' values without them, so they follow the cells: a delete drops the deleted points and moves the ones after it down, and an insert inside moves the ones after it up, leaving the new points automatic. Every stored series' points move, each whole, in a chart this build can't draw too. An insert stops a ref at the grid's last row or column, because `parseChartSpec` refuses a ref past it and the chart would never read again.

`writeBackSheets` (`state/modules/rowcol.ts`) writes every sheet the op changed back field by field and its charts one at a time, a keyed part an entry at a time, so the op, its undo and its redo each carry a replace of each shifted chart's `specData` and the point entries it moved, on the edited sheet and on any other. A peer's move or delete of that chart, its title, or its recolour of a slice the op doesn't move, at once or later, survives on every client and in the replay: the box stays the peer's, and a part write into a deleted chart is dropped. A recolour of a slice the op moves or deletes settles by arrival order, as two edits of one cell do ([§ An edit is an op in a Y.Array](#an-edit-is-an-op-in-a-yarray)): a client that takes it after the op paints it at its old index, which now names another point, and one that takes it first loses it, so live clients can differ until they reload. A row op moves no image. The rest of the edited sheet's metadata rides the op as authoritative replaces (`sheetMetadataOps` in `state/utils/patch.ts`), but never its `images` or `charts` map whole: that would overwrite a peer's insert, delete or move of another object on the sheet, and an undo would bring back what a peer deleted since. `packages/sheet/src/test/state/modules/floating.test.ts` pins it on the author, a peer and a joiner.

A receiver runs the engine shift first and then the writes, last writer wins, since its shift can differ from the author's write-back: an undone delete ships as an insert, and an insert never grows a shrunk or nulled ref back; and an undone insert never shrinks a ref the insert stopped at the grid's edge. Every row or column undo and redo ships the edited sheet's `calcChain` for the same reason. `packages/sheet/src/test/state/modules/chart.test.ts` pins these on the author, a peer and a joiner.

The other fields are written back whole, `data` above all, and those writes stay off the wire: of immer's own writes a row batch keeps only those into one image or chart (`writesOneFloatingObject` in `state/utils/patch.ts`). The editor-only shifts in `state/modules/rowcol.ts` write their fields whole too, `frozen` included, because the undo entry is immer's own inverse: a write inside a field a peer just removed, as an unfreeze removes `frozen`, would not resolve, and the undo would throw. `packages/sheet/src/test/state/modules/rowcol-ops.test.ts` pins both for inserts and deletes of rows and columns. A field shipped whole settles a race by arrival order, not per entry: a peer's concurrent unfreeze, or its write into `config` (row heights, column widths, hidden rows and columns, merges), conditional formats or validation, survives on a client that takes the row op first and is overwritten on one that takes it last, so live clients can end with different frozen panes or config until they reload ([SHEETS-TODO.md](SHEETS-TODO.md#bugs)).

## A range chart reads the grid's own values and labels

`resolveRangeChartData` (`engine/chart-data.ts`) turns a range chart into the categories and series the layout draws, through a `CellResolver`, so the editor and the server read the same cells. A value is the cell's computed `v` when it is a finite number and a gap otherwise. A label or series name is the cell's display text `m`, the string the grid shows, or a rich-text cell's runs joined, since one made in the editor has neither `m` nor `v`. A name ref reads its first cell. A chart with no categories counts them 1, 2, … up to its longest series.

A series whose values ref is null, deleted with its rows or columns, is left out and the rest draw, as Google does; it keeps its id, so its style stays in the spec and an undo brings it back as it was. The layout resolves an automatic color by the series' place in the spec, so the series after a deleted one keep the colors the editor shows them in. No series left, or a ref that names a missing sheet or spans several rows and several columns at once, is a `'ref'` error, which the chart shows as Excel's #REF. More points than `MAX_CHART_POINTS` is `'too-many-points'`. Both are decided from the refs before a cell is read, so selecting a whole column costs nothing. Hidden rows and columns are read like visible ones, while Excel and Google skip them by default ([ROADMAP](ROADMAP.md)).

`renderSheetChartSvg` (same file) is the chart the editor's overlay and the export both draw: the box, the look the record stores, the resolved data, and value ticks through `numberDisplay` in the axis's own format or else the first value cell's, Google's "From source data", so a percent column gets percent ticks.

## A chart's Setup is a block of cells, derived to refs and read back from them

The spec stores a ref per series, so a row insert can shift each one the way Excel shifts a chart's series. Google's Setup instead describes one block of cells: series down its columns or along its rows, and whether its first row and first column hold names. That block is a `ChartRange` (`engine/chart-range.ts`). `chartRangeData` derives the refs from it, and `chartRangeOf` reads it back by deriving both orientations and comparing with the stored refs. Refs no block derives, an imported chart's or one a deleted row nulled, have no Setup to show until a range is typed. The flags name the block's own first row and column, so Switch rows/columns keeps them: a text first row names the series down columns and the categories along rows.

Insert → Chart and a typed data range set a block up the same way (`suggestChartRange`): text in the first row or first column makes it names, the corner cell counting for neither, and series run down the columns unless the block has more data columns than rows. Insert also charts the table around a single selected cell (Excel's current region, `currentRegion`), titles the chart after its series ("North, South and East"), names the horizontal axis after the corner cell when that heads the categories, and places a 600 × 371 column chart below the block, selected, so its panel shows. `setUpChartRange` refuses a block of more than `MAX_CHART_SERIES` series, which `parseChartSpec` would read back as null, and one of more values than `MAX_CHART_POINTS`, which the chart would only draw as too much data. The values are counted from the refs, the fewest a block can hold before its cells set it up, so a typed whole column reads nothing. `currentRegion` grows each edge as far as it goes before trying the next and stops past `MAX_CHART_POINTS`, so a cell in a 10,000-row table reads a few thousand cells and is refused. Insert says why in an alert and the panel under the field, one message per reason (`CHART_RANGE_REFUSALS`).

## Images and charts share one frame on the grid

`FloatingObjects` (`components/FloatingObjects/`) draws the current sheet's images and charts in `floatingItems` order, so the DOM order is the paint order, each in one `FloatingObjectFrame` at its `sheetFloatingBox`. The kind supplies only its content, an `<img>` or the chart's drawing, so both kinds select, move, resize, rotate and open their menu through the same code and cannot drift apart. The frame is an unrotated positioned box and the content turns inside it, so a hit follows the turned shape. Selecting an object keeps its place in that order: every frame sits at one z-index, and the selected one's `ObjectTransform` ring renders through a portal into a layer after every frame, so its grips draw above the objects stacked over it.

A click selects the object and focuses its frame, so the workbook's keydown sees Delete, which goes through `clearSelectedContents`. Escape is the frame's own keydown. A drag moves it, and the `ObjectTransform` grips resize and rotate it, each gesture one write of the fields it changed. The preview clears on `onGestureEnd`, because a gesture cancelled by Escape or one that never moved commits nothing. Clicking a cell, a header or another sheet's tab deselects through `deselectFloatingObject`, and `changeSheet` drops the selection too, because the object belongs to the sheet left behind.

Touch follows Google Sheets on a phone: only the selected object is `touch-none`, so a finger on any other one pans the grid, the tap that follows selects it, and a drag on it then moves it. A `pointercancel`, the browser taking a touch for a pan, ends a move without writing it. `packages/sheet/src/test/components/FloatingObjects/floating-objects.test.tsx` runs every case for both kinds.

## A floating object's menu, keys and aspect lock are Vector's

Right-click, and a long press on touch, select the object and open the shared `ObjectContextMenu` ([LAYOUT.md](LAYOUT.md#menus-draw-their-rows-in-one-order)), so its rows read as a canvas object's do: Cut, Copy, Duplicate, Order, the download, Delete. A chart adds Download image, and a viewer gets the download row only. Like a canvas chart's, the menu has no Edit chart row, since selecting the chart already shows everything that edits it. Sheets objects take no comments, which hang off cells, so the menu has no Add comment. ⌘[ and ⌘] step the selected object down and up, with Shift to the back and front, through Vector's `useZOrderHotkeys`.

Keep aspect ratio is the app's `useAspectLock`, on by default for an image, whose photo distorts when stretched, and off for a chart, which redraws to any box. The app passes it to the workbook as `aspectLocked`, so the corner grips and the panel's checkbox follow one setting, and Shift inverts it while dragging. The app's panel (`apps/sheets/src/components/sheets/floating-object-panel.tsx`) shows X, Y, W, H and the angle, then Arrange, for both kinds, and a chart's own sections between them ([§ A selected chart's panel](#a-selected-charts-panel-is-a-canvas-charts-and-a-typed-edit-is-one-undo-step)). Delete is the menu's, the Delete key's and Edit › Delete's, as in Vector and Slides, so the panel has no Delete button.

## A chart on the grid redraws only when a cell matrix it reads changes

Every component under the workbook context re-renders on every context change, a selection or a drag included, so `sheetChartSvg` (`state/modules/chart.ts`) keeps one drawing per chart record and the `data` matrices of the sheets its refs name. immer replaces the matrix whose cells an edit touched, so an edit feeding a chart redraws it on the next render and nothing else does. The key is the matrix, not the sheet: the API's `setSelection` and a sheet switch write the per-client `selections` onto the sheet object. A rotate or a move keeps the drawing. A resize scales it to the preview box while the grip is held, its text stretching with it, because a large sketched chart takes tens of milliseconds to draw, and its commit draws it once at the new size. `packages/sheet/src/test/components/FloatingObjects/chart-content.test.tsx` counts the redraws.

Download image draws the chart as a copy carries it, through the canvas image writer: its ranges read into inline data and its look carried (`sheetChartClipboardItem`), on white, with the faces its labels use embedded ([EXPORT.md](EXPORT.md#a-drawing-downloads-its-own-svg-and-prints-as-layers)). A chart that draws #REF! or too much data has no inline data, so its menu has no Download image. The value ticks draw in the number format the copy writes on the axis, as in the grid ([CHARTS.md](CHARTS.md#a-chart-copies-between-apps-with-its-numbers-inline)).

## A selected chart copies itself, not the cells behind it

Selecting a chart or an image leaves the cell selection as it was, and the object takes the focus, so ⌘C and ⌘X reach the workbook's keydown with the cells still selected. The keydown skips the cell copy while a chart or an image is selected, so the cells get no copy border and no stale `copyState`, and the Workbook's `copy` listener writes the chart instead: one chart item ([CLIPBOARD.md](CLIPBOARD.md#a-chart-travels-as-its-spec-with-the-numbers-inline)) carrying the chart's look, whose parts are the chart's with its ranges read into inline data (`inlineChartSpec`, `engine/chart-data.ts`), since no other app can read a range. Every part the copy doesn't touch goes as the text it stores, a keyed part its entries joined, and a newer build's part goes too. `sheetChartClipboardItem` (`state/modules/chart.ts`) builds it, for the copy and Download image alike. Ticks drawn "From source data" take the first value cell's format onto the axis, so they keep it. An automatic color stays automatic unless a deleted series before it would shift its index. A chart that draws `#REF!` or too much data copies nothing. ⌘X writes the same item and deletes the chart, one undo step, as Google's does, and an image the same way; a viewer's ⌘X only copies. The object menu's Cut and Copy and Edit › Cut and Copy reach the same listener through the clipboard event `execCommand` fires (`copyActiveObject`, `state/modules/clipboard.ts`), so a menu writes what the keys write. The listener reads the chart from `ctx.sheets`, not through the editable current sheet, so a viewer can copy. It stands down while the focus is in a text field, such as the chart panel's title, which copies its own text; a selected image's copy does the same.

⌘V works with a chart or an image focused, since the paste gate takes a focused object of this workbook as well as the cell input. A pasted chart lands on the selected cell at its copied size, selected. The workbook keeps the chart it last copied beside the inline copy it wrote (`copiedChart` on the global cache), so a paste of parts equal to that copy here stores the chart's own fields and the duplicate stays linked to its cells, as Google's does. Those fields are every key that starts `spec`, a newer build's too, each record copied (`copySheetChartSpec`), as Duplicate copies them, so no two charts share a record. Anywhere else, another workbook or another tab of this one, it stores the inline copy, a keyed part split back into entries and one the item lacks an empty record (`newSheetChartSpecParts`). `packages/sheet/src/test/components/Workbook/chart-clipboard.test.tsx` pins each case.

## A selected chart's panel is a canvas chart's, and a typed edit is one undo step

Selecting a chart shows one panel, in the order Vector and Slides show a chart's: Transform, the shared chart and look sections (`ChartSections`, [CHARTS.md](CHARTS.md#one-chart-editor-edits-a-spec-and-the-host-writes-it)), then Arrange. There is no Edit chart step, so a chart's rows are one click away in every app. A phone shows no panel, as Slides and Vector show none ([MOBILE.md](MOBILE.md#a-phone-views-canvas-documents-never-edits-them)). Google's Setup, the data range and its three boxes (`ChartPanelSections`), sits at the end of the Chart section, where an inline chart has Edit data, because the range is how a sheet chart edits its data. The Workbook reports the selected chart through `onChartPanelChange`, as it reports the selected object through `onActiveObjectChange`, and the app mounts `ChartPanelSections` inside the object's panel. A viewer gets the Transform read-out only. Both states are memoized: the app passes a fresh `hooks` object on every render, which re-fires the reporting effect, and a fresh state each time would re-render the app without end. The panel writes through the Workbook API: `setChartSpec`, `setChartLook` for the paint rows, and `setChartDataRange` for a typed range, which needs the cells to set the block up.

The shared editor writes a typed title on every keystroke inside a gesture ([CHARTS.md](CHARTS.md#one-chart-editor-edits-a-spec-and-the-host-writes-it)). The Workbook's `beginGesture` opens `undoGesture`, and `setContextWithProduce` merges every write made under it into the last undo entry, so one ⌘Z takes the whole title back while peers still see it as it is typed. A write that replaces the field the entry's last write replaced overwrites that patch and adds no inverse, so the entry holds the first old title and the latest new one, not one per keystroke. The caret stays in the field, outside the Workbook's keydown, so the object's panel hands the Workbook's undo and redo to its fields (`PropertyHistoryContext`, `floating-object-panel.tsx`), as the Docs chart panel does. Left to the browser, ⌘Z there would be the field's own undo, each step written back as an edit and an undo entry of its own (`apps/sheets/src/test/components/sheets/floating-object-panel.test.tsx`).

## A tick box is a validation rule, and the value is its state

Tick boxes, list chevrons and the three corner marks are canvas paint, not DOM. Their model and geometry live in `state/modules/data-verification.ts` and `cell-glyph.ts`, the paint in `state/render/cells.ts`.

`Insert → Tick box` and the cell context menu both call `insertCheckbox`, which writes a `checkbox` rule with the values `TRUE` and `FALSE`. That is Google's model: a tick box is data validation, not a cell format. The context-menu entry exists because the common intent is converting an existing TRUE/FALSE column.

There is no checked flag on the rule. `isCheckboxChecked` compares the cell's display value with the rule's checked value, ignoring case. So an imported, pasted, typed or formula-produced `TRUE` renders ticked. Applying a rule seeds the unchecked value into empty cells only, so a tick box over an existing column loses nothing. A formula cell is a read-only tick, because a toggle would replace the formula with a literal. The rule dialog (`confirmMessage`) refuses a tick box with either value empty, and a list with no options, so the editor never writes a rule the painter can't draw.

A default rule draws the box alone, the way Google does. A rule with custom values also draws its label, the only way to tell "Yes" from "No". So does a cell holding a value the rule names neither of (`showsCheckboxLabel`), so a tick box laid over a column of prose never paints the data away. Empty cells in the range draw the plain unchecked box, so the range reads as one column.

A header click is clipped to the used extent, as for borders (`clipToUsedExtent` in `state/utils/index.ts`). A dragged range applies exactly as selected, which is how a checklist over empty rows gets its boxes.

## A list chevron is painted on every cell its rule covers

A `dropdown` rule paints a chevron on every cell it covers, empty ones included (`renderDropdownChevron`, called from `cellRender` and `nullCellRender`). Most list-validated cells are empty, and without the chevron a blank validated cell looks like a free-text one. Keyboard users and read-only viewers see it too.

It overlays the cell text rather than reserving width, because reserving would reflow every validated column. Its color is the cell's own `fc` at 55% alpha, since real workbooks put list rules on dark fills that a fixed gray would vanish into.

Clicking the chevron opens the list, and a click anywhere else in the cell selects. A viewer sees the chevron but gets no list. The `#sheet-dataVerification-dropdown-btn` element is only an invisible anchor for the portaled menu.

## Text spills into empty neighbours

A text cell overflows into the cells beside it as in Google Sheets and Excel: by default, unless its wrapping is Clip (`tb: '0'`) or Wrap (`tb: '2'`). No `tb` means overflow, so imported and typed cells spill without a setting. Left-aligned text spills right, right-aligned left, centred both ways. It runs over any neighbour without a value, whatever that neighbour's style, and stops at the first one with a value, a space or a formula included, or at a merge. Text spills once it comes within 4 px of its cell's edge, the 2 px the painter lays it in plus the 2 px of grid line its clip gives up. Numbers, tick-box cells and text that fits never spill (`rowOverflowSpans` in `state/render/overflow.ts`, recomputed for the visible rows on every draw).

A source scrolled off-screen still spills into view. Past each edge of the view only the first cell with a value can reach in, since it blocks everything behind it, so each row walks out at most `OVERFLOW_REACH_COLUMNS` (256) empty columns per side to find it. Text from a source further away clips at the edge of the view. The HTML, PDF and preview render doesn't overflow at all: every cell clips ([SHEETS-TODO.md](SHEETS-TODO.md#bugs)).

## Painter and hit test read one rect

Each glyph has one geometry function that both the painter and the mousedown hit test call: `checkboxRect`, `dropdownChevronRect` and `cellIndicatorRect`. It is the same split as the filter button's `FILTER_BUTTON_WIDTH`/`HEIGHT`, and it means a glyph and its click target cannot drift apart. The tick box gets its bounds from `cellTextBox` on both sides. Only the box toggles; Space or Enter toggles the focused cell. The chevron's click strip is wider than the glyph but built from the same rect, and both drop out below a minimum column width.

## Nothing toggles while a cell edit is open

Clicking a tick box while composing `=IF(` inserts the cell's reference and nothing else. A toggle would write the cell and kick a recalc behind the half-typed formula. The chevron is gated the same way, since its list would open over the formula, and so is the keyboard path (`state/events/mouse-cell.ts`, `keyboard.ts`).

## Three corner marks share one painter

A comment (top-right), an invalid value and a forced string (top-left) are all drawn by `drawCellIndicator` at `cellIndicatorRect`. The size is `CELL_INDICATOR_SIZE` in `packages/lib/src/constants/comment-indicator.ts`, which the canvas apps' `CommentIndicator` reads too, so a comment mark looks the same in every app. Filled and empty cells reach the same painter. A comment triangle takes its card's color, and red when the card has none.

The grid's colors are light-only CSS variables in ui's `globals.css`, read by the canvas and by the chart Edit data grid; the canvas's other colors are hardcoded light, because the grid is paper and doesn't re-theme ([RENDERING.md](../packages/sheet/RENDERING.md#theming-the-light-pinned-surface)).

## A glyph outranks the selection handles

The selection carries two invisible DOM hit targets over the canvas: the move band on its border and the fill handle at its corner. Without a precedence rule, a press on a chevron at the fill corner starts a fill drag. `cellGlyphAt` (`state/modules/cell-glyph.ts`) says which glyph sits under a point, from the painter's rects. Both handles ask it first, and on a hit they start no drag, so the press reaches the cell area, which opens the list, toggles the box or selects. `packages/sheet/src/test/state/events/mouse-cell.test.ts` pins the chevron at the fill corner and a mark under the band.

The hover path writes the same answer to `context.cellGlyphHover`, which shows a pointer over a chevron or tick box and stands the handles' own cursors down. Row and column resize never compete, because those handles live in the headers.

## The validation card follows the focus cell

One React card, `components/DataVerification/HintCard.tsx`, shows a validated cell's prompt or, when its value fails the rule, why. `getValidationHint` derives it from the focus cell on every render. So it follows keyboard navigation, never strands over the previous cell, and renders a collaborator's or an xlsx file's prompt as text, never as markup.

A rejection outranks a prompt, since it is the more urgent message. The card stands down while the list is open, because both hang over the same corner. The copy is assembled by `describeValidationRule`, which also words the `prohibitInput` dialog, so both ways a rejected value is reported say the same thing.

## Comments are Eigen comment cards

A cell anchors comments through `commentCardIds` on the `Cell`. The context menu, the panel and the card dialogs are the shared components from [COMMENTS.md](COMMENTS.md). Only adding and deleting a cell's anchor stay sheet-specific hooks.

On mobile the comments pane takes the whole width, so `editor.tsx` hides the workbook instead of unmounting it. `Sheet` keeps a `ResizeObserver` on its container and skips 0×0 boxes, so the canvas re-measures when the workbook shows again. App code may rely on that.

## The full export styles cells by class

The server renders a workbook to HTML, PDF and xlsx in `apps/api/src/lib/export/sheets/`, from the `Sheet[]` that `readSheetsFromDoc` returns. The transform, the route and the xlsx writer are in [EXPORT.md](EXPORT.md#a-sheet-export-recalcs-and-xlsx-carries-cells-charts-and-pictures).

`renderSheetsHtml` interns every style it emits (cell, row height, column width, data bar, rotation, image) into a workbook-global registry of classes and returns `{ html, css }`. The document builders put the rules in a body `<style>` element, which goes through `sanitizeExportHtml` with the markup.

A real workbook repeats a few hundred styles across hundreds of thousands of cells. DOMPurify on jsdom CSS-parses every inline `style` attribute it sanitizes, but passes class attributes and style-element text through as strings. With inline styles a real workbook's export was 82 MB and took 104 s, mostly CSS parsing.

The preview (`renderSheetsPreviewHtml`) keeps inline styles, because its body fragment embeds without a `<head>` ([PREVIEWS.md](PREVIEWS.md)). Its bytes are golden-pinned in `apps/api/src/test/preview/sheets-preview.test.ts`.

The table sets an unsized cell's font size to `SHEET_DEFAULT_FONT_SIZE` pt, the grid's own default, so a cell without a size prints at the size the grid draws it.

## The stylesheet is guarded in two places

Cell values are schemaless CRDT strings, and stylesheet text is a different escaping context from a style attribute. Two guards keep it inert, each where every field passes through rather than per field:

- `serializeStyleRules` strips what is structural in CSS text from every declaration. `<` and `>` would end the `<style>` element, and DOMPurify keeps what follows, so an `<svg><image href>` becomes a fetch in the HTML download. `{` and `}` open rule blocks. `\` starts a CSS escape, which spells `url(` or `@import` invisibly to the sanitizer. `/*` opens a comment that would swallow every later rule, so one odd cell would unstyle the rest of the workbook.
- Numeric fields are coerced, not escaped. Row heights and column widths go through the `Number()` guard in `sheetColumnsWidth` and `sheetRowsHeight`, and an image's or chart's box through `sheetFloatingBox`, which `getSheetContentSize` reads for the `@page` rule too.

Colors are checked, not escaped. A cell's `fc` and `bg`, a rule's colors, a border's and a data bar's reach the CSS, in the export and the preview alike, only as a hex, `rgb()` or transparent value `document/colors.ts` reads, or as a bare keyword such as `red`, which can't add a declaration. Any other string, such as `red;position:fixed;inset:0`, would add declarations of its own and fetch nothing, so the sanitizer would let it through. `cssColor` (`export/sheets/render.ts`) drops it, and a border or a bar draws transparent.

Other values are still `escapeHtml`'d on the way in, except the font family: entity encoding would corrupt a real name like `Bell MT & Co`, so its quotes and backslashes are dropped instead. The sanitizer's data-URI rule and `@import` strip cover style-element text too ([EXPORT.md](EXPORT.md#the-sanitizer-keeps-only-data-references-because-a-browser-fetches)).

## The export paints conditional formats with the grid's evaluator

`render.ts` calls `evaluateConditionalFormat` per sheet and merges its colors into each cell's style, so an export shows what the canvas shows. For formula rules it builds one `FormulaEngine` and one `createArrayResolver` over all loaded sheets, so a cross-sheet rule like `=Sheet2!A1>10` resolves. The pass reads `cell.v` and never recomputes the sheet's own formulas. Those values are already fresh, because `readSheetsFromDoc` ran the [gated recalc](#the-editor-computes-on-write-the-server-only-what-nobody-computed).

A data bar is an absolutely positioned `<div>` inside a `position:relative` cell, with geometry mirrored from the canvas painter. Negative bars are red, as on the canvas.

## Floating images and charts are an overlay on the table

A sheet with images or charts wraps its table in a `position:relative` box, and `renderFloatingObjects` (`export/sheets/render.ts`) draws them over it in their one paint order: each at its clamped box, rotated about its center. That is the box and the order the editor lays out, because both read the same fields.

The stored coordinates are grid pixels from A1, while the table starts at the used range. So the overlay subtracts the rows and columns above and left of that window. An object above or left of the used range pulls the window back to where it starts, so the offset never goes negative and the page covers it. The page size, the window's origin and the preview's clip all count the box an object covers as it turns (`getElementBounds`), so a rotated object stays on the page. One that turns past A1 tucks under the editor's headers, but a page has none, so the export moves it right or down until it starts on the page. The overlay's box reaches the farthest one, so the next sheet and the preview's truncated notice start below them, and the preview clips the box to its budget window. `apps/api/src/test/export/sheets-pdf.test.ts` reads a rotated chart off WeasyPrint's pixels; it skips where WeasyPrint or a rasterizer is missing, as on CI.

An image's name is a media reference ([MEDIA-REFERENCES.md](MEDIA-REFERENCES.md)), looked up in a map the transform prepared: `data:` URIs for an export, preview URLs for a preview. A name that resolves to nothing renders nothing. The xlsx export writes charts as chart parts ([CHARTS.md](CHARTS.md#a-chart-goes-to-office-as-a-cchartspace-that-reads-back-as-the-same-spec)) and images as pictures over the same cells, turned as they turn ([EXPORT.md](EXPORT.md#an-xlsx-picture-is-anchored-as-excel-places-a-turned-one)). The import reads both back in one paint order, each picture's file a new media name, so a round trip keeps an image's box, angle and stacking but not its name.

## Charts draw in the overlay as inline SVG

A chart is `renderSheetChartSvg`, the editor's own drawing, in a white box, so the gridlines stop at it as they do on screen. Its ranges read through the render's resolver over every loaded sheet, so a chart on one tab can chart another. The export reads them after the gated recalc and the preview from the stored values. The SVG is plain shapes and text, which the sanitizer keeps and WeasyPrint draws ([CHARTS.md](CHARTS.md#the-painter-draws-each-shape-with-its-own-kind-and-the-labels-as-svg-text)).

## An imported tab arrives as an addSheet op, renamed as Duplicate names a copy

File › Import… can add an xlsx's sheets as new tabs ([EXPORT.md § A replace saves a version first](EXPORT.md#a-replace-saves-a-version-first)). `appendSheetsToYjs` (`apps/api/src/lib/document/sheets.ts`) pushes them as one batch of `addSheet` ops after the workbook's own, never as a new snapshot. An open tab applies the batch as it applies a peer's new tab, so it keeps its view and its unflushed ops, where a snapshot write would remount every tab and clear them ([§ An edit is an op in a Y.Array](#an-edit-is-an-op-in-a-yarray)).

Every imported sheet takes a fresh id: the importer numbers its sheets `sheet-0` and on, which a workbook's own ids can match. A sheet whose name the workbook holds is renamed by `copySheetName` (`engine/sheet-name.ts`), the rule the tab menu's Duplicate uses, so `Data` comes in as `Data(Copy)`. The names are compared exactly, as a rename in the tab bar compares them. What the file says about its own sheets follows the new names and ids, so its formulas still read the cells they read in Excel:

| Reference | Names a sheet by | Rewritten through |
|---|---|---|
| A formula, a formula conditional format, a list validation's source, a `cellrange` link | Name, `'Data(Copy)'!A1` | `renameSheetRefs` (`engine/formula-shift.ts`) |
| A `sheet` link | Name | The rename map |
| A chart's series and categories | Id ([§ A chart is a floating record](#a-chart-is-a-floating-record-whose-refs-name-sheets-by-id)) | `mapChartRefs` |
| A link cell's `hl` and the calc chain | Id | The new id |

Defined names need nothing: the reader has already written each into the formulas that use it as the range it names ([EXPORT.md](EXPORT.md#an-xlsx-defined-name-is-inlined-into-the-formulas-that-use-it)), so its refs are renamed like any other. A range written with its sheet on both ends (`'Data'!A1:'Data'!B2`) gets the new name on its first end only, as the formula walker hands the second end's prefix back untouched; Excel writes a range's sheet once.

## Some xlsx round-trip drifts are decisions

These are deliberate. Where a test pins one, it is in `apps/api/src/test/export/sheets-export.test.ts`. Hyperlinks:

- A `sheet` link re-imports as a `cellrange` link at `'Name'!A1`, because the location names a cell. A `sheet` link to a name no sheet holds is a defined name's, as the import reads a location without a cell, and keeps its location. A bare ref gains its own sheet's quoted prefix.
- Imported link cells keep Excel's font, while the link dialog sets blue and underline. Forcing the dialog style at import would clobber theme-styled link cells.

Column widths and row heights:

- A width counts the file's default font's widest digit ([TYPOGRAPHY.md](TYPOGRAPHY.md#the-xlsx-export-makes-inter-the-workbooks-default-font)), so a column imports at the pixels Excel for Windows draws it at: a Calibri 11 column stored as 9.140625 is 64 px. `maxDigitWidth` (`apps/api/src/lib/ooxml/spreadsheetml.ts`) holds Excel's digit for the Office defaults by face and size, because Excel draws GDI's hinted digit, not the outline's: Calibri 11 and Arial 10 are 7 px, Arial 11 and Cambria 11 are 8. A face it doesn't list counts 7. `columnWidthToPx` and `pxToColumnWidth` are ECMA-376's conversion both ways. The writer truncates to a 256th of a digit and the reader rounds half a 256th up, so every pixel width survives the round trip.
- A height or width that draws no pixel, a custom 0 or a 0.05 pt row, comes in as a hidden row or column, which every renderer draws as none and the writer writes back as `hidden="1"`. A stored length of 0 would draw at the default in the editor and as nothing elsewhere.
- An unsized column takes the sheet's default width, read by the same digit. `sheetFormatPr`'s `defaultColWidth` counts its padding already. Without it Excel pads `baseColWidth` (8 when absent) by 5 px and rounds up to a multiple of 8 px, so Excel's default is 64 px. The default row height is points to pixels, and Excel's 15 pt when the file names none.

Rules and comments:

- Top or bottom, above-average, duplicate-value and data-bar rules export as Excel's own (`top10`, `aboveAverage`, `duplicateValues`, `dataBar`), which Excel and Eigen read and Google Sheets doesn't show. `duplicateValue` exports as Excel's `duplicateValues` or `uniqueValues` rule and re-imports as itself. `occurrenceDate` is editor-only and is not exported.
- The xlsx writer (`export/sheets/xlsx/rules.ts`) quotes a rule's exotic numeric literals (`1e5`, `+5`) as text. The engine compares with `Number()`, so rendering is unaffected.
- The data-validation exporter always writes `allowBlank: true`, Excel's UI default.
- Tick boxes are editor-only. The cells export their values and the rule is dropped: OOXML has no cell tick box, and a `"TRUE,FALSE"` list would re-import as a dropdown, a different feature.
- Excel comments and notes are not imported, because Eigen has its own comment cards.
