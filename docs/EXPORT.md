# Document Export and Import

> **TLDR:** One route downloads a doc as docx, PDF or HTML, a sheet as xlsx, PDF or HTML, a deck as pptx, PDF or HTML and a drawing as SVG or PDF (`apps/api/src/lib/export/`). Import turns an xlsx into a sheet, a docx into a doc and a pptx into slides (`lib/import/`). Every format but xlsx, docx, pptx and SVG is one HTML document, and PDF is that document through WeasyPrint. xlsx, docx and pptx each have a writer of their own, and the docx writer takes its look from the same stylesheet the editor draws with. An import writes nothing until the transform succeeds.

A user exports from the file menu of the docs, sheets, slides and drawing editors, or from a Drive item's menu. Import is a row of the same file menu in docs, sheets and slides (**Import docx file…**, **Import xlsx file…**, **Import slides…**). A doc or sheet import replaces the open document; a slides import adds the file's slides after the deck's own. Convert to Sheet, Convert to Document and Convert to Slides are file actions on an xlsx, docx or pptx, and make a new document from it. Which extension converts to which type is one table, `CONVERT_SOURCES` (`packages/lib/src/types/drive.ts`), that the file action, the route and the import picker's Drive rows all read, by the file's extension: Drive stores the MIME an upload claimed, and an Office file often arrives as `application/octet-stream`. Every document that exports is a collab document, so its content is the Yjs state stored in its container's `data.db` ([COLLAB.md](COLLAB.md)), and an export renders that state. The heavy work runs in a one-shot transform process ([DOCUMENT-TRANSFORMS.md](DOCUMENT-TRANSFORMS.md)).

The editor, quick look, the HTML download and the PDF draw a doc from one stylesheet, `eigen-prose.css`, so they lay it out block for block alike. The docx writer reads its sizes, spacing and colors from that stylesheet too. The rest of this doc covers how each format is built and kept safe. Three things surprise people: WeasyPrint opens only `data:` URIs, through a fetcher of Eigen's own ([§ WeasyPrint fetches only data: URIs](#weasyprint-fetches-only-data-uris)); every body keeps only `data:` references, so an HTML download fetches nothing either ([§ The sanitizer](#the-sanitizer-keeps-only-data-references-because-a-browser-fetches)); and an import checks write access again as its last step ([§ An import writes nothing](#an-import-writes-nothing-until-the-transform-succeeds)).

## A type's format list is both the menu and the gate

`EIGEN_DOC_TYPE_INFO[type].exportFormats` (`packages/lib/src/types/drive.ts`) lists what a type offers, in menu order. The file menu and the drive item menu read it through `exportFormatsFor`. The route checks the same list, and `offers()` in `export-document.ts` narrows each entry to a literal. So a format added to a type without a transform envelope fails to compile instead of reaching a user as a 400.

Export and import both dispatch on the container type, not the mime type. A mime type is caller-controlled on upload, so a plain file wearing an Eigen mime is a 400 rather than a transform over data it does not have. The export route resolves the file through `SharedDrive`, so the ACL check is the drive's; export is not a `Drive` method.

## The transform process renders and the main thread prepares

`runDocumentExport` is the one main-thread entry. It asks the runner for admission first, so a refused job does not pay for its media. Then `collectExportMedia` (`export/media.ts`) prepares every media child: the screen preview for HTML and PDF, a fresh PNG or JPEG for a docx or pptx ([§ An Office image](#an-office-image-is-a-png-or-jpeg-made-from-its-source)). That is Mount I/O plus the capped thumbnail path, so it stays on the main thread. The prep spends from the export's 120 s transform deadline, so an export is one deadline end to end: once it is spent the prep queues no more media and the job fails as a timed-out one does. The xlsx export skips it, because the writer carries cells only.

The one-shot transform process ([DOCUMENT-TRANSFORMS.md](DOCUMENT-TRANSFORMS.md)) materializes the captured Yjs blobs, then renders and sanitizes the HTML, or writes the docx, pptx or xlsx. The docx and pptx writers and ExcelJS load lazily, so an HTML export evaluates none of them. A blob that fails to decode is skipped with a `corrupt-blobs-skipped` warning, as on a live read. WeasyPrint stays on the main thread: it is already a separate process.

| Outcome | Status |
|---|---|
| WeasyPrint not installed, older than 68 or its import past 5 s (PDF only) | 501 naming the minimum and how to install it |
| WeasyPrint past its 60 s timeout, or exits non-zero | 504, or a bare 500 with its traceback in the log. A SIGSEGV, which WeasyPrint 68 hits now and then in a glib thread while renders run side by side, renders once more in what is left of the 60 s, unless the first took over half |
| Transform runner saturated | 503, never a main-thread fallback |
| Empty deck or empty drawing | 400 |

## A transform route exempts itself from the idle timeout

The response is silent while the job queues and its transform runs. Queue wait plus the 120 s transform deadline plus 60 s of WeasyPrint can outlast any server-wide `idleTimeout`, which Bun caps at 255 s. So the export, import and convert routes call `server.timeout(request, 0)`. Without it Bun closes the silent connection, which aborts the signal and kills the job mid-transform. `request.signal` still fires on a real disconnect, and the runner then drops the queued job or kills its child process.

## Every format but xlsx, docx, pptx and SVG is one HTML document

`html` and `pdf-html` render one document from one renderer, so WeasyPrint prints what the HTML download serves, but for what differs on paper. There is one document per type to get right, not one per format. Each type's entry (`renderEigendocExport`, `renderEigensheetsExport`, `renderEigenslidesExport`) decides once which one it renders: a sheet's page fits its widest and tallest sheet, a deck's pages leave the fit box, and a doc fakes small caps where the font has none ([DOCS.md](DOCS.md#the-pdf-fakes-small-caps-where-the-font-has-none)) and draws its equations as SVG ([§ The PDF draws an equation as the SVG MathJax makes of it](#the-pdf-draws-an-equation-as-the-svg-mathjax-makes-of-it)). A doc's PDF also places its bands as running elements before the body, with the stylesheet that prints them in the margins and numbers the pages, where the download shows page 1's header above the body and the footer below it, a page number as its `#` ([§ The PDF prints the bands](#the-pdf-prints-the-bands-as-running-elements-placed-before-the-body)). A doc's `<title>` keeps the extension (`Report.eigendoc`) while the docx title drops it; that output is pinned in `apps/api/src/test/export/document-export-route.test.ts`.

A doc's page is the one it stores ([DOCS.md](DOCS.md#a-doc-stores-its-page-in-a-page-map-beside-its-content)), read beside the body by `readEigendocPage`: the HTML's screen page and the PDF's `@page` from `pageStylesheet` (in `printExtras`, `export/doc/transform.ts`), and the docx's page size, margins and text column from `pageTwips`. A margin change rewrites no figure, so a figure wider than the column writes at the column's width, as the editor draws it at `max-width: 100%`.

A doc's header and footer ([DOCS.md](DOCS.md#a-header-and-a-footer-are-fragments-of-their-own-beside-the-body)) reach every export through `readEigendocBands` (`document/doc.ts`): a band with content only, page 1's only when the page differs, and without the nodes a band's schema leaves out, which only a forged peer writes. Each renders through `renderDocHtml`, as the body does, and its media resolves as the body's.

The document is self-contained, because WeasyPrint and a downloaded file have no app to fetch from. One builder writes it for every type, `exportHtmlDocument` (`export/html-document.ts`): the doctype, the policy `<meta>`, the title and the fonts, around the stylesheet and body each type renders. Only the canvas document asks for the viewport `<meta>`, which the deck's fit box needs to scale a page to a phone. Fonts are WOFF2 files base64'd into `@font-face` rules (`export/fonts.ts`). A doc embeds `eigen-prose.css`, flattened once at load by `document/prose-css.ts`: WeasyPrint does not read CSS nesting, so nesting is expanded, `.dark` rules are dropped and theme variables become values, so no `var()` survives. The font weights come from `font-weights.css`, rounded to the nearest multiple of 100 because WeasyPrint accepts no other weight: Heading 1 to 4 and table headers print at 500, Heading 5 and 6 at the body's 400, and bold at 600.

The doc node renderers (`export/doc/render.ts`) are pure and shared with the preview: `renderDocHtml` renders a body for both, with one node mapping, so quick look draws a list's start and type as the export does. They highlight with the backend's one lowlight (`document/lowlight.ts`), which the docx writer and reader share, so the main thread imports them lazily. A figure resolves its media name to a `data:` URI and, with none, keeps its `src`, so an image pasted as a `data:` URI draws; a missing image renders no `<img>`, and an external `src` is stripped by the sanitizer. So a figure with only an external `src` exports empty, with no warning, an open [ROADMAP](ROADMAP.md) row. A task item is rendered by hand, because the static renderer drops `checked`.

## The PDF prints the bands as running elements placed before the body

The PDF's HTML places every band before the body as a WeasyPrint running element (`position: running(header)`), and the head's CSS shows them in the `@top-center` and `@bottom-center` margin boxes over the text column, 1.27 cm from the paper's edge or at a narrower margin's, page 1's under `@page :first` when the page differs (`bandsCss`, `export/doc/transform.ts`). Before the body, because `element()` takes the element placed on its page or the last one placed before it: a footer placed after the body would print on the last page only. The `element()` rules stay in the head, which the sanitizer never sees: it strips `element(` from a body's CSS as a fetch. A page number renders empty there, and the head's `::after` draws `counter(page)` or `counter(pages)`, so the PDF numbers its pages and its count.

A margin box pushes nothing, so a band taller than its margin would print over the body, where Word and the editor move the body down. So `weasyprint-render.py` first lays out a probe of the bands alone (`band_margins`): the doc's HTML under a user stylesheet that hides the body and forces a second page, so page 1's bands and the other pages' both lay out, on two near-empty pages. A band needs its distance from the edge plus its height, as the editor's margin measures it; its last block has no space after (`PAGE_BAND_CLASS`, [DOCS.md](DOCS.md#a-header-and-a-footer-are-fragments-of-their-own-beside-the-body)), so a one-line header fits the 2 cm margin. The doc's one render then takes a user stylesheet that grows `@page :first` to page 1's need and `@page` to the other pages', `!important` because a user rule loses to the document's own, so a short letterhead keeps page 1's body high and a page that page 1's growth spills onto still clears its own header. The growth stops where the margins would leave the body less than half the page: a band taller than that runs over the body rather than leaving it a line per page. A doc without bands pays for no probe, as the script looks for `PAGE_BAND_CLASS` first. The probe reads WeasyPrint's layout boxes, which are not its public API, so an `AttributeError` or `ImportError` there grows no margin: a WeasyPrint upgrade that moves them prints a tall band over the body rather than failing every PDF export, docs, sheets and decks alike. Over the 257 corpus docx files whose import gets a band, each doc lays out once, where 187 laid out twice before the probe; the total time stays within 3 % (885 s to 907 s), as the probe costs about what the second layout cost a small doc, and the longest render stays near 33 s, inside the 60 s timeout. Seven print a band over the body, each one whose bands are taller than half the page, which without the cap stretched the worst from 44 pages to 64.

Browsers ignore `running()`, so the HTML download places the bands where the long page shows them: page 1's header before the body and the other pages' footer after it, a page number as its `#`.

## The PDF prints a note at its page's foot, and the screen lists the notes after the body

A footnote ([DOCS.md](DOCS.md#a-footnote-is-an-inline-node-that-holds-its-notes-paragraphs)) renders two ways from `renderDocHtml`. The PDF writes it in place as the editor's spans (`pageFootnotes`), and the head's CSS (`PAGE_FOOTNOTES_CSS`, `export/doc/transform.ts`) floats it with WeasyPrint's `float: footnote` to the foot of the page its reference falls on, as Google prints notes: a superscript number in the text and at the note, the notes at 10 pt (`FOOTNOTE_LOOK`) under a 2-inch rule. The note inherits from its reference's paragraph, so its paragraphs and its marker set its look, and the note's own font sets no line, so a note in a title adds no title-sized line to the foot. The call keeps the size of the text it sits in. The rule is an SVG background, because WeasyPrint draws a footnote area's background at the image's own size and reads no `background-size`.

Browsers ignore `float: footnote`, so the HTML download and the drive preview write each reference as a superscript number linking to its note in a list closing the body (`section.footnotes`), each note linking back, as Google's HTML download does. Both forms number the notes in document order, the order `footnotesInOrder` reads, and a nested note renders as its text (`flattenNestedFootnotes`). Only a doc with notes gets either stylesheet. A band holds no note: `readEigendocBands` drops one a peer forged.

## The doc renderers write the DOM the editor holds

A figure is an inline node, so it renders as a `span.figure` with a `span.figcaption`, which a paragraph can hold. A `<figure>` inside a `<p>` closes it in every HTML parser, the sanitizer's and WeasyPrint's, and the paragraph split around it gains margins the editor never draws. `span.figure` parses back with its caption and layout; the `<figure>` rule stays, because the editor's own copy still writes one. Both draw from the shared `.figure` box ([DOCS.md](DOCS.md#the-node-view-and-the-export-draw-one-figure-box)). A chart takes the same box with inline SVG in place of the image, never an `<img>`, because an SVG image can't reach the page's `@font-face` and its labels would fall back to another font ([CHARTS.md](CHARTS.md#a-docs-chart-draws-flat-at-its-own-size)).

`withTrailingBreaks` (`export/doc/render.ts`) gives a paragraph, heading or code block the trailing `<br>` the editor has, in the export and the preview alike ([DOCS.md](DOCS.md#the-node-view-and-the-export-draw-one-figure-box)).

The static renderer nests a text's marks the other way round from the editor: it wraps the first mark innermost, where ProseMirror draws it outermost. Rendered as is, a link's own color would sit outside its `<a>`, and `.eigen-prose a` would draw the link color over it. `inEditorMarkOrder` (`document/doc-schema.ts`) hands the renderer the doc over a schema whose marks rank in reverse, so the export and the preview nest marks as the editor does: the `<a>` outermost, its color inside it.

## The PDF draws an equation as the SVG MathJax makes of it

The HTML download and the preview draw an equation as the MathML the editor holds, in the editor's span, without its LaTeX annotation, which no screen draws. WeasyPrint draws no MathML, so the PDF draws each one as an SVG that MathJax 4 (`@mathjax/src`) makes from that same MathML string. `renderEigendocExport` (`export/doc/transform.ts`) runs an async pass before the render: it walks the equations in document order, parses each distinct one and has `mathmlToSvg` (`export/math-svg.ts`) draw it once, and hands `renderDocHtml` the drawings keyed by stored string and display. The `equation` mapping looks each equation up by its own key, so a subtree the render skips, an equation the schema refuses in a code block, a figure or another equation but a Yjs update can hold, moves no drawing onto another equation.

- MathJax loads on the first equation, once per Worker, so an export with none never evaluates it. It loads a font range the first time a character needs one, so every equation goes through the promise API.
- Every glyph is a path of its own (`fontCache: 'none'`). A glyph cache would write each glyph's id in every equation's `<defs>`, and one HTML document would hold the same id many times. An inline equation is one SVG: MathJax's inline line breaks would split it into several around an element the sanitizer drops.
- The SVG goes through `sanitizeExportHtml` with the rest of the body, which keeps all of it but `focusable`. MathJax's `vertical-align` puts an inline one on the text's baseline. A displayed one (`span.math-svg[data-display]`, `printExtras`) takes its line as in the editor: a full-width box, centred, on the bottom of the line the paragraph's trailing `<br>` holds, so no empty line follows it. Hiding that `<br>` instead would hide a user's own break after text that follows the equation, since CSS's `+` skips text. MathJax breaks no equation into lines, so one wider than the column scales down to it, where Word and Google Docs wrap it.
- **Every render bounds its equations by element, every copy counted, because the sanitizer's jsdom and WeasyPrint pay per element, not per byte.** The bands and the body spend one budget (`renderEquations`), in the order the export writes them, so a header's equations print on every page as SVG too. jsdom runs in the Worker, which shares the API's address space ([DOCUMENT-TRANSFORMS.md](DOCUMENT-TRANSFORMS.md#one-worker-runs-at-a-time)). The PDF draws at most 50,000 elements and 10 MB of SVG (`SVG_LIMIT`, `export/math-svg.ts`). 44,000 elements of empty fences are 1.2 MB, and take the Worker 0.56 GB and WeasyPrint 9 s; 6 times as many, which fit 10 MB, take 1.9 GB and 51 s. Glyph paths run about 390 bytes an element, so there the bytes bind first. One equation at the math bounds draws up to 4.1 MB of SVG, a row of 1,999 `⨌`, so the budget holds two. The HTML download and the preview, which a viewer's open runs, write at most 50,000 elements of MathML (`MATHML_LIMIT`, `export/doc/render.ts`), at 3 to 5 KB of jsdom each: one paragraph of 294,000 elements is 1.6 GB of preview, and 4.9 million elements 16 GB of download.
- A 1,000-equation paper of the 108 corpus equations draws about 21,700 SVG elements and 4.2 MB, in 8 s of WeasyPrint, and writes about 10,900 MathML elements, so it shows every equation. The PDF's pass stops calling MathJax at the first equation that does not fit, so it holds at most the budget plus that one drawing. `MAX_SVG_EQUATIONS` (1,000) bounds the MathJax calls, at 1 to 2 ms each over the corpus after about 0.12 s to load (measured on a warm file cache), and up to 0.6 s for a tree at the math bounds. From the first equation past a bound, the rest print as their linear text, `readStoredEquation`'s `text`, typed or from Word alike, as the search index reads them ([DOCS.md](DOCS.md#an-equations-text-is-its-linear-form-and-the-find-bar-skips-it)). Text costs no element.

The tests are in `apps/api/src/test/export/math-svg.test.ts`, the equations blocks of `doc-export.test.ts`, the preview's budget in `preview/eigendoc-render.test.ts`, and the WeasyPrint block of `document-export-route.test.ts`, which prints an equation through the Worker.

## An ordered list draws its first number and its marker inline

WeasyPrint reads `<ol start>` and `<ol type>` only as presentational hints, and the PDF render takes no hints, so every list would print from 1 in decimals. A stylesheet can't stand in for `type`: HTML matches the attribute case-blind, so `[type="a"]` matches an `A` list too, and Chrome reads no `s` flag to tell them apart. So the schema's ordered list (`EigenOrderedList`, `packages/lib/src/docs/eigendoc/nodes/ordered-list.ts`) writes both into its own `style`: `counter-reset: list-item <start − 1>` on a list that starts elsewhere, and `list-style-type` for a lettered or Roman one. The editor, quick look, the HTML and the PDF all render it, and it keeps `start` and `type`, which a paste reads back.

## A doc's docx is written from its JSON, with the editor's CSS values

`eigendocToDocx` (`export/doc/to-docx.ts`) writes the WordprocessingML by hand from the JSON `readEigendocFromDoc` returns, and zips it with `writeZip` (`core/zip.ts`), the way xlsx is written from the workbook and not from HTML. Fed the export HTML, a converter kept a doc's structure and lost almost every visual property ([PROPOSAL_DOCX.md](proposals/PROPOSAL_DOCX.md)). Every size, margin, color and border comes from `eigen-prose.css` through `proseValue` (`document/prose-css.ts`), so the editor's look lives in one file and the docx keeps the editor's spacing. `proseValue` throws when the CSS sets no such value, so a renamed rule fails the export tests instead of drifting.

No schema checked the CRDT's JSON, so the writer checks attrs where it uses them and never fails on structure: inline content where a block belongs is wrapped in a paragraph, and a nested block is hoisted out. A node or mark it has no mapping for throws, as the HTML export does, and `apps/api/src/test/export/doc-docx.test.ts` exports a doc holding every node and mark of the schema, so a new node fails a test instead of vanishing from the docx. A comment mark writes nothing and its text stays: comments are not exported, an open [ROADMAP](ROADMAP.md) question. A page number writes Word's `PAGE` field and a page count its `NUMPAGES` field (`PAGE_NUMBER_FIELDS`, `document/wordml.ts`) as a complex field, `w:fldChar` runs around the instruction and the result, as Word and LibreOffice write it: Google Docs leaves a `w:fldSimple` `PAGE` in the body blank. The field's runs take no marks (the editor keeps none on a page number) and the result caches 1, which Word, LibreOffice and Google Docs replace as they lay out the pages; the docx reader reads the field back as the node. Every zip entry carries the DOS epoch as its date, so one doc always exports to the same bytes.

An equation is Word's own math: the `m:oMath` that `writeOmml` writes from the tree `readStoredEquation` reads, beside the paragraph's runs rather than inside one. A displayed one is wrapped in `m:oMathPara` in a paragraph of its own, as Word's Change to Display leaves it, so it splits its paragraph as a block figure does: the pieces share the paragraph's margins, a heading's later pieces stay out of the navigator, and a list item's number stays on the first. LibreOffice draws an `m:oMathPara` that shares its paragraph with text inline. An empty equation stays an empty `m:oMath`, and the typed LaTeX stays behind, because OMML has no slot for it ([DOCS.md](DOCS.md#an-equation-is-an-inline-node-that-stores-its-mathml)).

A code block's language rides a hidden paragraph style of its own, `Code Block (<language>)` based on `Code Block` (`codeBlockStyle` in `apps/api/src/lib/document/wordml.ts`), written only for a language lowlight knows. Word keeps a paragraph's style on a re-save, and LibreOffice keeps its name, so the reader reads the language back from the name. The style is `w:semiHidden` without `w:unhideWhenUsed`, which keeps it out of Word's style gallery once used. Google Docs drops every custom style, so a doc that went through it comes back with no language.

## A band is a docx part with relationships of its own

The header and the footer are parts of their own, `header1.xml` and `footer1.xml`, written by the body's block writer in the body's column, and page 1's beside them when the page differs, with `w:titlePg` in the section; a page-1 band the doc lacks is an empty part, as Word writes one. A part resolves the `r:id`s it uses through its own relationships part (`relsPathOf`, `core/opc.ts`), so a header's image or link has its own relationship, while the image file is written once for the package. The `Package` walk carries the relationships of the part it writes (`pkg.part`), and drawing ids stay the package's, so no two collide. A part's root declares the document's namespaces, `m:` included, as a band may hold an equation. The section's header and footer distance is the bands' 1.27 cm (`BAND_DISTANCE_MM`), or a narrower margin. A band's last block is written with no space after, as the editor and the PDF draw it (`PAGE_BAND_CLASS`) and as Word's Header and Footer styles have none, so a one-line footer stands one line high.

## A note is a footnote in Word's notes part

A footnote writes Word's `w:footnoteReference` run in the FootnoteReference style where it stands, and its note goes to `footnotes.xml`, numbered 1, 2, 3 as the body meets them, the order `footnotesInOrder` reads. The part opens with Word's two separators, notes -1 and 0, which `w:footnotePr` in the settings names, as Word writes them; a doc without notes writes neither. Each note is written by the body's block writer in the body's column, in the FootnoteText style, through the part's own relationships as a band is ([§ A band is a docx part](#a-band-is-a-docx-part-with-relationships-of-its-own)), so a link or an image in a note resolves; its first paragraph opens with Word's `w:footnoteRef` number and a space. A nested note is its text (`flattenNestedFootnotes`). FootnoteText is Word's own, 10 pt, single spaced with no space after (`FOOTNOTE_LOOK`, the PDF's note size), and FootnoteReference is superscript.

## Caps cross the docx as Word's toggles

The writer puts a `textStyle`'s caps on the run as `w:caps` or `w:smallCaps`, and the reader turns them back into the attribute, so the letters stay as typed both ways ([DOCS.md](DOCS.md#caps-are-an-attribute-of-the-fonts-mark-drawn-over-the-letters-as-typed)). Both are toggle properties (ECMA-376 §17.7.3), read as bold and italic are: a character style flips the paragraph style's, and the run's own setting wins. No node draws capitals, so a style's caps, a Title's say, become the mark on its runs.

## The docx embeds the faces a doc uses, its 600s in the Bold slot

The writer puts a `textStyle`'s font size on the run as `w:sz` and `w:szCs` in half points. The reader keeps a run's size where it differs from the one its node draws: the docx's own body size (Normal over the document defaults) or a heading's or a title's style. So a Word file with a 12 pt body, a quarter of the corpus, imports without a size on every run, and its body draws at the doc's 11 pt, as its headings draw at the doc's heading sizes. Small is written as its look, 9 pt and a little spaced, and reads back as a 9 pt size. Both ways go through `readFontSize`, so a hostile `w:sz` lands in 1 to 400 pt ([DOCS.md](DOCS.md#a-font-size-is-a-number-in-points-on-the-fonts-mark)).

Word has four slots per family (Regular, Bold, Italic, Bold Italic) and reads no variable font, so the writer embeds static TrueType files that sit beside the variable WOFF2s in `packages/ui/src/assets/fonts/` (`DOCX_FONT_FILES` in `export/fonts.ts`). The editor draws bold at 600. So Inter's and JetBrains Mono's Bold slots hold their 600 files, renamed to Bold so the family stays one name that Word, an import and Google Docs all find. Source Serif 4's holds its 700, and Excalifont has a Regular only, from which Word synthesizes the rest.

Only the faces a doc's runs resolve to are embedded, with the body's Regular always among them, each whole and not subset, so a reader can type new characters. Each is obfuscated as ECMA-376 requires, its first 32 bytes XORed with a GUID key hashed from the face, so the bytes stay stable. MS Gothic, which draws the task checkboxes, joins the font table only with a task list and is not embedded.

## The docx line is a multiple of each font's own line height

CSS sets a line as a multiple of the font size. Word's `auto` line is a multiple of the font's own line height, `(usWinAscent + usWinDescent) / unitsPerEm` from its OS/2 table, and `atLeast` would be read as single spacing by Google Docs. So `autoLine` divides the CSS pitch by that height, and every style's line is the editor's pitch in Word. Word also scales an `auto` line with the tallest face in it, by that face's own line height, while the editor's unitless `line-height` scales with the largest size alone. So a larger size in the paragraph mark's family keeps the style's line, and a paragraph whose runs all draw in one family other than its paragraph mark's gets its line rescaled by that family's height (`familyLine`) when the runs' line is taller than the mark's, so Source Serif 4, JetBrains Mono and Excalifont keep the editor's pitch. Each family's height is measured once from its TTF (`fontLineHeight`, `export/fonts.ts`), which the docx reader shares.

A paragraph's own format ([DOCS.md](DOCS.md#a-paragraphs-format-is-six-numbers-on-its-textblock)) goes on top of its style's and its container's: its line spacing as an `auto` line through `autoLine`, which comes to 240ths of the multiple for Inter, before and after in twips outside a list, quote or cell, which own the spacing of what they hold, and its indents as `w:ind`, the left one counted from the container's text, a negative first line as `w:hanging`. A list item's first paragraph takes its indent from the numbering level, so an indent set on it stays in the editor. Normal is Eigen's declared look, line spacing 1.4 (an `auto` 336) and 11 pt after, read from `.eigen-prose p` like every other style.

## An Office image is a PNG or JPEG made from its source

Word and PowerPoint for the web and Google Docs show no WebP, so a docx or pptx never takes the WebP screen preview. `prepareOfficeMedia` (`export/media.ts`) re-encodes each image from its source file in the thumbnail Worker, by the rules of `encodeOfficeImage` (`export/office-image.ts`): at most 2560 px on the long side (`OFFICE_IMAGE_MAX_SIZE`), PNG for a lossless source (PNG, GIF, a VP8L WebP), JPEG for the rest, and PNG again for a source with alpha. The re-encode drops EXIF, GPS included. It is uncached and runs on the thumbnail semaphore uploads and previews share, which allows 4 workers. `collectExportMedia` loops over the images in sequence, so one export takes one image at a time and queues no more once the client disconnects. The Worker's width and height size a docx drawing, because a figure stores only its width, and place a pptx picture its box covers or contains.

An SVG goes in as itself, an `asvg:svgBlip` that Word, PowerPoint and LibreOffice draw, beside a PNG fallback for a reader without SVG. `withSvgFallbacks` (`export/office-image.ts`) draws that PNG in the transform process from the sanitized XML the `svgBlip` carries ([§ The sanitizer](#the-sanitizer-keeps-only-data-references-because-a-browser-fetches)), so the docx or pptx shows what the PDF shows. sharp loads only for a docx or pptx that holds an SVG, or a docx with a pasted image. One librsvg cannot read leaves the file, a docx keeping its caption, and so does one it cannot draw within 30 s. That timeout is sharp's own, so a slow SVG costs its image and not the export: a 310-byte filter chain held the one transform slot for 90 s. sharp reads physical units (`in`, `cm`, `mm`, `pt`, `pc`) at 72 dpi, so `cssSize` scales a side the root `<svg>` gives in one by 96/72, the size the HTML export draws.

A figure pasted with a `data:` src has no media file, and the main thread never reads the doc ([DOCUMENT-TRANSFORMS.md](DOCUMENT-TRANSFORMS.md)), so the transform process decodes each such src once (`pastedFigureMedia`, `export/doc/to-docx.ts`). A raster goes through `encodeOfficeImage` and the thumbnail Worker's own `sharpResize`, so it drops its EXIF and shrinks as a media file does; an SVG goes through `sanitizeExportMedia` and `withSvgFallbacks`. The writer names the item by its `src` (`figureMediaKey`), which no media name can equal, since a media name holds no `/`. Only a `;base64` src is read; a percent-encoded one writes only the caption.

Observed in Word's render on 2026-10-08: a 1204×4 px divider drew 466.5 pt wide until its height became whole twips. So the writer rounds the height to whole twips itself. A figure with no media, an external `src` (a docx fetches nothing) or a media item without a size or fallback writes only its caption, and so does a chart, until the writer writes Word charts.

## A wrapped figure is a floating one-cell table

A figure wrapped left or right becomes a borderless floating table of one cell holding the image and its caption, placed before its paragraph, its distances from the text the figure's float margin in `eigen-prose.css`. It is the one wrap that keeps the caption under the image in every reader, and its row cannot split, or Google Docs moves the caption to the next page. In a list or quote a left float starts at the container's text edge, clear of the bullet and the bar.

## The docx writes a figure's margin inside its paragraph's spacing

In the editor a paragraph's own margins collapse with its neighbours', and a figure's 0.75em margin sits inside the paragraph and never collapses. Word and LibreOffice collapse adjacent spacing to the larger, as CSS does, and have no inside margin. So `to-docx.ts` carries the figure's margin as an inset on its paragraphs, and `withInsets` writes the whole gap on the inset paragraph's side: the neighbour's inset, the two spacings collapsed, its own inset. The pieces a figure splits a paragraph into share its margins, the first taking the one above and the last the one below. A paragraph that holds only a wrapped figure keeps its line, as the editor's trailing break does. In a quote, a paragraph whose style isn't Quote (a figure's, its caption's, an item's clearing Spacer, a done task) draws the quote's bar itself at the quote's indent, so the bar runs unbroken past it.

A list item that holds a wrapped figure ends in a clearing break (`w:br w:clear="all"`) on a single-spaced Spacer paragraph, so the next item starts below the float, as in the editor. A nested item clears its own floats, so the item around it writes no second break. On an exact-height Spacer, LibreOffice was observed to ignore the clear. Google Docs ignores the clear too, so the next item draws beside the float there (observed 2026-10-08), while Word and LibreOffice honour it. The cases are pinned in `apps/api/src/test/export/doc-docx.test.ts`.

## Bullet lists share one numbering definition, and each ordered list has its own

Each ordered list gets its own `w:abstractNum` with its start in all nine levels, so two adjacent lists count separately. A bullet counts nothing, so bullet lists at one indent share one definition, which keeps `numbering.xml` small, and a bullet has no counter to restart. Word has nine levels, so a list or quote deeper still indents no further.

## A docx keeps every page break

A page break is a paragraph holding `w:br w:type="page"` wherever it stands, at the top level or in a list item, a task item, a quote or a table cell.

## Every export points root-relative links at the instance

A link's root-relative `href` means nothing outside Eigen, so the docx, the HTML and the PDF prefix it with the public origin (`getPublicOrigin`, none on a `localhost` dev server), and a protocol-relative one gets `https:`, since a downloaded file would open it as `file:`. One rule serves all three: `absoluteHref` in `apps/api/src/lib/export/doc/render.ts`, which the docx writer calls per link and `withAbsoluteLinks` applies to the JSON before the HTML render. The docx import reverses it, so an export edited in Word comes back with its links into Eigen: the import job carries the public origin, and `rootRelativeHref` (`apps/api/src/lib/import/doc/runs.ts`) turns a link into the instance root-relative again. It returns a path only when one `/` follows the origin, so `https://<origin>//other.host` stays absolute instead of becoming a protocol-relative link that leaves the instance.

## WeasyPrint fetches only data: URIs

PDF is the HTML document through WeasyPrint, run by `export/weasyprint-render.py` through its Python API rather than its CLI. That script hands WeasyPrint a URL fetcher that opens `data:` URIs and refuses everything else: http(s), `file:`, a plain or relative path, any other scheme. Export embeds every resource it needs as a `data:` URI, so any other reference came from a collaborator's CRDT string, and WeasyPrint would fetch it from the API host while it renders. WeasyPrint's default fetcher opens every one, from a nested `<image href>` in a `data:` SVG to an `<a rel="attachment">`, whose response, or the server file a plain path names, it embeds in the PDF. The fetcher is the boundary for the PDF; the sanitizer is not relied on for it, and `export-pdf-ssrf.test.ts` renders raw hostile bodies to prove it.

- `htmlToPdf` runs the script with the Python that imports WeasyPrint 68 or later: the one the `weasyprint` launcher's shebang names (a pip venv's, Homebrew's own, through `env` or `env -S` too), else `python3`. A pip launcher whose venv path is long or holds a space starts `#!/bin/sh`, so it counts as naming none. When neither imports a recent enough one, a PDF export answers 501. The probe is cached; a spawn that finds the cached interpreter gone, as after a Homebrew upgrade, probes once more. An import that runs past 5 s is killed, because the export routes set no request timeout, and is not cached, so the next export probes again.
- It runs under `python -I`, so a module in the working directory or on `PYTHONPATH` cannot load in its place. That also drops the user site, so a `pip install --user` WeasyPrint is not found: install it system-wide, in a venv or from the OS package.
- The script subclasses `URLFetcher`, which WeasyPrint 68 introduced, rather than pass `allowed_protocols={'data'}`: 68.0 takes the text before `://` as the scheme, so it refuses every `data:` URI.
- The Docker image pins WeasyPrint 70.0 from PyPI in a venv at `/opt/weasyprint`, so it renders with the engine development does. `docker/api/weasyprint-requirements.txt` pins every dependency by hash, for the amd64 and arm64 wheels, and its first line is the command that regenerates it. The build renders a one-line PDF through `weasyprint-render.py`, so a system library the image lacks fails the build instead of every PDF export. Debian 13 ships 62.3, which ignores flex `align-items` and width on the `.figure` box and prints a centred figure left-aligned, its caption squeezed beside it.
- The document has no base URL, so a relative link stays relative in the PDF instead of becoming a `file://` URL of the server's working directory.

## The sanitizer keeps only data: references, because a browser fetches

`sanitizeExportHtml` (`export/sanitize.ts`) is DOMPurify plus one rule. Every CSS `url(`, every `src`, `poster` and `background`, and every SVG `href` must open a `data:` URI with no fragment. A `url(` may also be fragment-only (`#id`), a reference into the same document, and so may an `href` on the elements that reference with one: `use`, the gradients, `pattern`, `filter`, `textPath` and `mpath`. An `image` or `feImage` loads its `href` as a file, so a fragment there names the document itself. `srcset` is dropped. A `url(` that opens anything else costs the whole attribute it is in, and in a `<style>` element the statement it is in. So do `@import`, the string forms of `image-set()`, `image()`, `cross-fade()` and `element()`, which fetch with no `url(`, and `attr()`, which can read an attribute as a URL: WeasyPrint fails the whole export on `attr(name url)`.

A browser that opens an HTML download fetches what the document names, from the reader's machine, which tells whoever wrote the reference who read it. A preview body is live DOM in the drive hero, the same beacon at every viewer ([PREVIEWS.md](PREVIEWS.md)). So the restriction runs inside the transform process on every assembled body, and every format inherits it: `exportHtmlDocument` sanitizes the body of every HTML and PDF document, and keeps a link's `target`, so a downloaded link opens in a new tab as it does in the editors. WeasyPrint ignores `target`. A `data:` URI passes as it came, whatever its type or payload: a browser fetches nothing from an SVG drawn as an image, librsvg draws one from its bytes, and WeasyPrint's fetcher opens nothing but `data:`. The exception is a fragment. Firefox loads a `data:` SVG named with one (`mask:url(data:…#m)`, `fill="url(data:…#p)"`, `<pattern href="data:…#g">`) as a document, not an image, and fetches what that document names, such as its `@import`. So a `data:` URI holding a `#` is refused wherever it stands. A real one never has one: export media is base64, and a `#` in a percent-encoded payload ends it anyway.

- The rule reads the `url(` token, in any case, never a `url(…)` pair. A quoted URL can hold a `)` or a quote, so a pair regex ends early on `url('http://host/a)')` and the CSS parser fetches it. Its function tokens and its statement split come from the mail rules (`packages/lib/src/core/mail/remote-content.ts`). The `url(` admissions differ: a message keeps only a raster image its parser inlined, an export any `data:` URI without a fragment, a same-document fragment and the preview's own URLs.
- Every attribute value is scanned, not only `style`: an SVG `fill`, `filter`, `mask`, `clip-path` or `marker-*` is CSS too.
- Backslashes go from `style` and `<style>` text before the scan. A CSS escape spells `url(` or `@import` invisibly to a regex (`\75 rl(`), but not to the parser that fetches. Any other attribute holding both a backslash and a `(` is dropped: an escape spells `url(` (`\75 rl(`) or a fragment (`url(data:…\23 p)`), and every fetch needs the literal `(` that opens a function.
- `<a href>` keeps its target, because docs and sheets carry real links and a browser follows one only on a click. A link is not inert to WeasyPrint: one with `rel="attachment"` is fetched and embedded in the PDF, which only the fetcher stops. jsdom names an SVG `<a>` in lowercase and an HTML one in uppercase, so the check ignores case.
- DOMPurify drops every `<use>`. A profile that admits `<svg>` keeps one whose every `href` is fragment-only, because matplotlib draws its text with `<use href="#glyph">`; any other `<use>` goes. Written as XML (`toXmlDocument`: SVG media and a drawing's own SVG), a `<use>` also needs every target to exist and hold no `<use>` of its own. Each reference draws its target again, so nested ones multiply: 1.2 KB of six levels of ten runs WeasyPrint into its 60 s kill. One level is what glyphs need, and it ends every cycle.
- DOMPurify's MathML profile drops `<none>`, the empty slot of a prescript, which breaks the `<mmultiscripts>` it is in. `KEEP_MATHML` keeps it for every HTML and PDF document and the doc preview; the namespace check still drops one outside a `<math>`.
- Only the whitespace a URL or CSS parser trims counts as whitespace. A non-breaking space before `#` or `data:` makes a relative path of the rest.
- Every token pattern runs in one pass, because a collaborator's string sizes the scan. Two whitespace runs that could trade characters around an empty match cost their square: 256 KB of spaces after a `url(` costs 26 s.
- The hooks are added and removed around each synchronous call, so they never leak to another DOMPurify user.
- A media preview serves an SVG as uploaded. A docx carries it as a part of its own, and WeasyPrint and librsvg draw its every `<use>`, so the transform process takes every `image/svg+xml` media item through `sanitizeExportMedia` before any arm embeds it, and writes it as XML, without the characters XML can't hold; a file with no `<svg>` in it is dropped. The main thread hands over the inlined bytes as they are, because sanitizing a big drawing holds jsdom for seconds. Every format takes any size: the export deadline, sharp's pixel limit and the PNG fallback's timeout ([§ An Office image](#an-office-image-is-a-png-or-jpeg-made-from-its-source)) bound the work.

A browser backs the rule up: every export response carries `EXPORT_CSP` (`export/sanitize.ts`), which allows `data:` images and fonts and inline styles and nothing else, and `exportHtmlDocument` writes it into every HTML download as a `<meta>` too, so it holds once the file is saved.

Previews pass the same function the exact set of their own preview URLs ([PREVIEWS.md](PREVIEWS.md)). The tests are in `apps/api/src/test/export/export-pdf-ssrf.test.ts`.

## A sheet export recalcs, and xlsx carries cells only

Export is the one read that recalcs a workbook nobody computed ([SHEETS.md § The editor computes on write](SHEETS.md#the-editor-computes-on-write-the-server-only-what-nobody-computed)), so an import whose recalc failed still exports values. A recalc failure exports the replayed values with a `recalc-failed` warning. A legacy workbook whose recalc outlasts the 120 s deadline fails the export, an accepted residual.

`to-xlsx.ts` reverses the importer with the same library. A merge's border perimeter is folded onto its master by `mergedBorderSides`, because ExcelJS keeps one style across a merge. Webpage links pass `resolveWebLink`, the editor's gate. Internal links are written in Excel's own `location` form. Inter is the workbook's default font ([TYPOGRAPHY.md](TYPOGRAPHY.md#the-xlsx-export-makes-inter-the-workbooks-default-font)). Floating images are dropped, an open [ROADMAP](ROADMAP.md) row. The class-styled HTML and the round-trip drifts: [SHEETS.md](SHEETS.md).

## Canvas pages are the boxes the live canvas draws

A deck's HTML and PDF and a drawing's PDF are pages of compositor layers (`export/canvas/render.ts`), which the canvas previews share. It restates no geometry: `layerBoxCss`, `layerPrintCss`, `layerInnerHtml` and `backgroundCss` come from `packages/lib`, and each screen layer gets the box `element-layer.tsx` gives it live, each printed layer the same box laid out where it prints. So what a user sees is what prints. A screen page holds the scene at 1:1 and scales it once, because a layer's body is authored in scene pixels. A non-text layer sits in an `overflow="visible"` `<svg>`, because roughjs overshoots its box.

`canvasHtmlDocument` (`export/canvas/transform.ts`) wraps all three, with one `@page` rule, font block and reset, so they cannot drift. It embeds `canvas-text.css` for the list and link rules an inline style cannot reach.

Before layout, `sanitizeSceneHtml` filters every text box to `LIGHT_EDITOR_TAGS` (`packages/lib/src/core/html.ts`), the set the canvas mounts a body with. A `<table>` or `<style>` a peer wrote would otherwise be invisible live yet print. The document cannot forbid `<style>` instead, because it carries its own `@font-face` block.

## A deck prints each frame at half scale

A frame is the page, at the deck's slide size, and an overhanging element is clipped as the canvas clips it. Every frame is 1920 wide, so the page prints at 0.5: 960 by 540 px for 16:9 and 960 by 720 px for 4:3, which is 254 × 142.875 mm and 254 × 190.5 mm, Google's PDF sizes. The PDF document lays each slide out at 1:1 on a 1920 px `@page`, and `htmlToPdf` hands WeasyPrint a zoom of 0.5 (`DECK_SCALE`) that prints it at 960. The HTML download wraps each page in a `.page-fit` box that scales it to the viewport, so a deck reads on a phone, with a `@media` ladder first for a browser that cannot divide `100cqw` by a length. The PDF has no fit box, because WeasyPrint has no viewport. The `.page-fit` rules mirror `packages/ui/src/styles/globals.css`, since a standalone file cannot import it.

## A deck's pptx is written from the scene, one DrawingML shape per element

`eigenslidesToPptx` (`export/slides/to-pptx.ts`) writes the PresentationML by hand, the way the docx is written from the JSON: a converter fed the export HTML would keep the text and lose the canvas's geometry. One frame is one slide, at PowerPoint's 16:9 or 4:3, whichever is nearer the frame's aspect, so the frame's width sets the EMU per pixel. Each element becomes the shape that draws it: a preset for a rectangle, ellipse, diamond or pie, a connector for a two-point line or arrow, a custom path for a path element's own commands, for more points and for a freehand stroke's outline, a picture with its cover or contain fit, and a text body for rich text, with its runs, lists and links. Every shape writes its own colors and fonts, so the theme only has to be valid. A gradient writes the nine OKLab samples the canvas paints from (`gradientStops`, `packages/lib/src/background/gradient.ts`), so a reader that blends in sRGB still draws Eigen's ramp. A link keeps its text's color, as `canvas-text.css` draws it.

`renderEigenslidesExport` (`export/slides/transform.ts`) runs `sanitizeSceneHtml` before it writes a pptx, the filter the HTML export runs ([§ Canvas pages](#canvas-pages-are-the-boxes-the-live-canvas-draws)). It is what keeps a `javascript:` link a peer wrote out of the file, because a pptx hyperlink is a relationship target the writer copies as it is. The pictures come from the Office media prep ([§ An Office image](#an-office-image-is-a-png-or-jpeg-made-from-its-source)). `apps/api/src/test/export/slides-pptx.test.ts` pins the writer, and `slides-export.test.ts` a whole export.

## A pptx draws what DrawingML can, and loses the rest

DrawingML has no sketch, no hatch and no paragraph border, so a few looks change on the way out:

- A hatched or rough fill is solid, and a rough outline is the plain one.
- A quote keeps its indent and its fade, but not its bar.
- An elbow arrow's rounded bends are square.
- An arrow label hides the shaft under it with a box in the slide's color, where the canvas cuts the shaft out. On a gradient or picture background there is no such color, so the shaft runs under the text, and over another shape the box covers that shape too.
- A pie's gradient spans the whole ellipse's box at its angle, where the canvas paints it across the slice's own box.
- A chart is the shapes Convert to shapes makes (`convertToShapes`), not a chart PowerPoint can edit: there is no chart part writer yet, an open [ROADMAP](ROADMAP.md) row.
- Fonts are written by name (Inter, Source Serif 4, JetBrains Mono, Excalifont) and not embedded, while the docx embeds them ([§ The docx embeds the faces](#the-docx-embeds-the-faces-a-doc-uses-its-600s-in-the-bold-slot)). PowerPoint for the web substitutes all four; Google Slides has the first three and substitutes Excalifont. Embedding them is an open [ROADMAP](ROADMAP.md) row.

## A drawing downloads its own SVG and prints as layers

The `svg` arm is `sceneToSvg` (`packages/lib/src/vector`) with the used `@font-face` blocks and `canvas-text.css` spliced in. The sanitizer allows `<foreignObject>` as an HTML integration point, or it would drop the rich-text `<div>`. The result is re-serialized as XML, because an XML parser reads an `.svg` and one unclosed `<br>` from a text box would blank the drawing.

The `pdf` arm is a single compositor page sized to the content plus 10 px on each side, the margin `sceneToSvg` leaves for roughjs's overshoot. Rich text prints because it is an HTML div; WeasyPrint ignores `<foreignObject>`. A transparent drawing prints on white paper, because WeasyPrint has no canvas behind the page. The page is capped at 19,200 px a side (`MAX_PDF_PAGE_PX`, `export/weasyprint.ts`), the PDF's 200-inch limit, so a far-out element cannot make WeasyPrint lay out an unbounded sheet. Artwork past it is cut off. A sheet's PDF page has the same cap, and a taller sheet continues on the next page.

## WeasyPrint dictates how a layer references its paint

A gradient (`fill="url(#…)"`) or an image clip (`clip-path="url(#…)"`) stays an SVG attribute pointing at the element's own `<defs>`. WeasyPrint resolves `url(#id)` only within the same `<svg>`.

No transform sits above a PDF layer, and a layer's only transform is its rotation: `renderPrintPage` lays each layer out where it prints, its box minus the page's origin as `top` and `left` (`layerPrintCss`, beside the live canvas's `layerBoxCss`), and a deck scales through WeasyPrint's zoom, never a CSS `scale`. WeasyPrint 68 lays a page out ignoring transforms and cuts every line whose layout box passes the `@page` height, and it clips a translucent element to the page as its parent's transform maps it. A layer laid out at the scene origin and moved by a `translate` would lose a text box's lines wherever its layout box passed the page bottom: in a slide's lower half under a scale of 0.5, in a text box starting above a slide, in a drawing drawn above or left of the scene origin (`canvas-pdf.test.ts`).

An arrow's shaft is hidden under its label by a `<mask>`, because WeasyPrint ignores `clip-rule="evenodd"`. WeasyPrint applies a mask after drawing a node's children, so the reference goes on each shaft `<path>`, never a wrapping `<g>`. See `labelMask` and `maskShaft` in `packages/lib/src/vector/kinds/arrow-render.ts`.

## An import writes nothing until the transform succeeds

`importIntoDocument` imports into an open document (`/import`, `/import-from-drive`) and `convertToDocument` (`/convert`) creates one beside the source, both in `import/import-document.ts`. The transform converts bytes only and never sees an owner, mount or path. So a failed transform creates no document and mutates no Yjs state, and its 400 or 413 crosses the boundary unchanged. An xlsx comes back as snapshot JSON, committed without parsing; a docx as a ready Yjs update, its page and images; a pptx as a ready Yjs update plus images. A convert refuses a file on its extension before it reads it, so a `.pptm` or a `.potx` never reaches the reader.

The route checks write before it buffers, but the job can queue for minutes, long enough for a share to be revoked. So `importIntoDocument` checks write again as the last await before the synchronous Yjs write, and a revoked writer gets a 403. `convertToDocument` checks write on the destination folder before it reads the source, so a reader pays for no transform, and needs no recheck, because `SharedDrive.create` checks write. A convert that fails after its create (a picture's name taken, quota another write spent) trashes the new document through `Drive.deletePath` and answers the failure; the trashed document sits in the owner's Trash, counted against quota, until it is purged ([SOFT-DELETE.md](SOFT-DELETE.md)). It takes no abort signal either: a page reload must not kill a minute of conversion, and the file appears through the drive SSE refresh.

## Zip guards run before the parser inflates anything

The upload bound limits compressed bytes, while ExcelJS inflates the whole package, and an out-of-memory inside it ends the transform process instead of refusing the file. So the xlsx import opens the package with `openZip` (`core/zip.ts`), which refuses a declared total past the byte cap, and reads every entry once before ExcelJS sees it: a read inflates no further than its entry declares, so a forged directory that declares a small size is refused too. ExcelJS then loads those reads, stored in a package `writeZip` builds, never the upload, so its own zip reader sees only bytes `openZip` checked. A sheet also has a cell cap. A dense, styled sheet at that cap peaks at about 5 GB to convert, and the byte cap alone holds about 7.5 million valued cells, so the cap is checked twice: on the cells the parts hold before ExcelJS loads, and on the grid they span after. A large job is part of why one transform runs at a time.

ExcelJS also expands ranges cell by cell while it loads, before the cell cap can count anything. A merge becomes its cells, and each merge is checked against every earlier one. A validation's `sqref` becomes one key per cell, a defined name's range one entry per cell, and a `<col>` one column object per column up to its `min` or `max`. One such element in a 1.5 KB file held the transform past its deadline at several GB. So while `repackXlsx` (`import/sheets/from-xlsx.ts`) reads each entry, it searches the bytes of every part for merges, validations and columns, and of every sheet part for cells and rows, by the unprefixed name ExcelJS matches (a calculation chain's `<c>` is no cell), and counts each range with ExcelJS's own `Range`, which reads a missing row or column as 1. The search reads attribute values raw, while ExcelJS's XML parser reads a raw tab, CR or LF in one as a space, and in XML 1.1 a NEL or U+2028 too. So the bytes ExcelJS gets are made to read the same: a part declaring an XML version other than 1.0 is a 400, which Excel never writes, and a raw tab, CR or LF inside a searched tag is written as a space. The scan mirrors ExcelJS 4.4.0's parser, the names it matches and the `Range` it counts with, which `from-xlsx.ts` imports from ExcelJS's internals, so `apps/api/package.json` pins that exact version: re-check the scan on any upgrade. Past a cap the import is a 413 Spreadsheet too large:

- Cells, and merged cells, count against the cell cap, because ExcelJS builds a model for each. Past it the 413 says Spreadsheet has too many cells.
- `MAX_ROWS` bounds the rows in the sheets, two full sheets' worth, because ExcelJS builds a model per row even when it is empty: 30 million empty rows fit in under 1 MB and cost 17 GB. Real workbooks hold under 1.1 million.
- `MAX_MERGES` bounds the merges in the workbook, because the pairwise check is quadratic: 10,000 merges take 2.4 s, 30,000 take 27 s.
- `MAX_VALIDATION_KEYS` bounds validated cells. A key costs about 300 bytes, so the cap costs about what a million ordinary cells do, and four column-wide validations fit.
- A `<col>` may not reach past column XFD.
- `MAX_SHEETS` bounds the sheet parts, because a sheet holds a column object per column up to its last, about 3 MB at XFD. Real workbooks hold under 50 sheets.
- `MAX_SHEET_ID` bounds a sheet's id, because ExcelJS's sheet list walks every id up to the largest. Real ids stay under 33,000.
- `MAX_ELEMENTS` bounds the elements past the cell grid in the sheets, the shared strings and the styles, because ExcelJS builds a model of up to 270 bytes for each: a rich-text run, a format, a rule, a selection. The grid's own names (`c`, `v`, `f`, `t`, `is`, `row`) don't count, since the cell and row caps bound them and a flood of them inside one cell costs what its bytes do. Real files hold under 70,000.

Defined names never reach ExcelJS, because Eigen drops them. Real workbooks carry big ones: a filter range over a whole table, or names over external workbooks that cover hundreds of millions of cells. ExcelJS reads a `definedNames` element by its exact name at any depth, so `repackXlsx` renames every `<definedNames` and `</definedNames` in every part to `ignoredNames`. A rename needs no parse: comments, CDATA, attributes and nesting stay as they are, and the XML stays well-formed.

After the load, the cell cap is checked on what the conversion walks. A row past row 1,048,576 holds no cell for the cell cap to count, yet every walk to the last row visits each row number, so it is a 413 Spreadsheet has too many cells. Next the columns each row reaches add up against the cell cap, because counting the grid's width and converting a row both walk every column up to the row's last cell: one cell in column XFD makes a row of 16,384. Last comes the grid the rows and columns span, the dense matrix recalc builds.

The conversion bounds the text it writes. A cell takes a shared string by reference, so a 1 MB string in a thousand cells is a gigabyte of snapshot, and a rich one is a copy per cell. Past `MAX_TEXT` characters of values and displays the import is a 413 Spreadsheet too large; real workbooks write under 120 million. The location hyperlinks read each sheet part once, however many sheet entries name it, under the name ExcelJS gives it, the last. Of 516 public workbooks (150 GOV.UK statistics files and 366 Apache POI test files), the caps refuse one real file, POI's 50,000-merge stress file, and POI's shared-string bomb (`poc-shared-strings.xlsx`), whose 12,000 cells would write 25 billion characters. The GOV.UK workbook whose names cover 614 million cells imports in about a second, where ExcelJS would spend 14.6 GB on its names. `apps/api/src/test/import/sheets/limits.test.ts` pins the bounds.

The docx reader opens its package with `openPackage` (`apps/api/src/lib/core/opc.ts`), so it reads only through `openZip` too. It parses only the parts it needs (the content types, the document, its styles, numbering, theme, font table and notes, the final section's headers and footers, the settings when an even page's band is named, their relationships, and a chart's or SmartArt's own parts), never `webSettings.xml` or `comments.xml`, each once. A parsed XML tree costs many times its text (`apps/api/src/lib/core/xml.ts` gives the measured ratios) and per element, so 16 MB of empty paragraphs is 2.8 million elements and 3.5 GB, while the largest real document met holds 611,000 tags. So `openPackage` charges every part the reader parses, a chart's or SmartArt's included, against the package's parse budget before it inflates and before it parses ([DOCUMENT-TRANSFORMS.md](DOCUMENT-TRANSFORMS.md#a-packages-parts-have-a-parse-budget-before-the-memory-limit)). A part past it makes the whole import 413 Document too large, and the transform process's memory limit is the backstop past the budget. The budget's worst case is dear: 1.48 million empty paragraphs, just under its tags, peak at 2.2 GB in the reader before the output's weight refuses them. What the reader builds has caps of its own: `MAX_DOCX_PIECES` for the text pieces a run splits into past its first, about 600 bytes each before the output is weighed, so 4 million of them from 5.7 MB of XML cost 2.5 GB; `MAX_INLINE_NODES` per paragraph and the output's weight and text (below). The structural bounds (columns, table and quote nesting, list starts, style chains) sit beside the code they bound in `apps/api/src/lib/import/doc/`; a thousand nested tables overflowed a Worker thread's stack before the nesting cap. Past a cap the import is a 413 Document too large, and the import maps a stack overflow, in the reader or the Yjs conversion, to the same 413, as the transform process answers an import that runs out of memory ([DOCUMENT-TRANSFORMS.md](DOCUMENT-TRANSFORMS.md#out-of-memory-is-the-jobs-not-the-servers)); any other `RangeError`, as ProseMirror's schema and table checks throw, is a reader slip, logged and 400. `apps/api/src/test/import/doc/limits.test.ts` pins the bounds.

## An imported sheet is stored as computed

The transform runs `recalcSheets` and encodes the snapshot as computed, so no later read recalcs it. A recalc failure stores the parsed values uncomputed with a warning, and the first export recalcs them. The importer keeps three rules:

- `ct.fa` is always paired with `ct.t`, `'General'` when Excel reports no number format. Without an `fa`, date serials and percents render as raw numbers.
- A formula cell's `f` keeps its leading `=` (`=SUM(A1:A3)`), the form a sheet stores; the xlsx writer strips it.
- Internal links in `location` form are read from the raw worksheet XML, because ExcelJS drops them on read.

## A docx import replaces the document

`readDocx` (`apps/api/src/lib/import/doc/from-docx.ts`) reads the WordprocessingML straight into a doc of the schema, with no HTML between, in the transform process; `docxToPmJson` gives the same doc as JSON, for the audit and the tests. An HTML converter between the file and the schema loses most of what Word shows (alignment, color, fonts, list numbers, image widths) and needs a sanitizer after it; reading the XML into the schema keeps the looks and leaves nothing to sanitize. The reader resolves styles through their chain and runs Word's list counters in document order, so a list keeps the numbers Word draws. A property Eigen has no home for (cell fill) leaves its text and drops its look: the gaps are a [ROADMAP](ROADMAP.md) row. Word comments are not read, and their text stays. Tracked changes come in accepted. The reader also recognises the writer's looks (`document/looks.ts`, which both share), so an export that Google Docs re-saved, which flattens Eigen's styles into direct formatting, still comes back with its quotes, code blocks, captions and done tasks. Heading 5 and 6 draw Google Docs' grey, and 6 its italic, so the reader drops that grey from their runs, as it drops a quote's. Word's Title and Subtitle styles, a name Word, LibreOffice and Google Docs share, become the title and the subtitle, which the writer writes in those built-in styles. The node draws their size, and the subtitle its grey, which the reader drops; a style's bold or italic stays a mark, as the title and subtitle draw neither. An italic mark in Heading 6 draws upright, as in Google Docs and Word, so the writer writes it as `<w:i w:val="0"/>` and the reader makes a run Word draws upright there the mark, and one Word draws italic plain text. Word's own Heading 6 style is not italic, so its plain runs come in as the mark. A Word page break splits its paragraph on the way in ([DOCS.md](DOCS.md#a-word-page-break-splits-its-paragraph-on-import)). Word's math comes in as equations: each `m:oMath` is an `equation` node holding `writeMathml(readOmml(…))` where it stands among the runs, and each `m:oMath` of an `m:oMathPara` a displayed one; an equation past a bound of the package comes in as the text of its `m:t`, Word's neighbouring runs one word and each object a word of its own, as Word cuts runs by style, and one in a code block or a caption is its linear text there, `readStoredEquation`'s `text`.

Word's notes come in as footnotes ([DOCS.md](DOCS.md#a-footnote-is-an-inline-node-that-holds-its-notes-paragraphs)): each `w:footnoteReference` becomes a `footnote` node holding its note's paragraphs, read where the reference stands (`readNote`, `import/doc/paragraphs.ts`) through the notes part's own relationships, as a band's are, so a link or an image in a note resolves. An endnote is a footnote too, numbered among them in document order, as Google Docs has no endnotes. The separators and the continuation notice no reference names are no notes, Word's number at the note and the space or tab after it go, and a note's heading, list, table or code comes in as its paragraphs, as the node holds paragraphs only. A note's paragraph draws in its style's look, as a heading does in its own, so Word's FootnoteText, 10 pt and single spaced, gives its runs no size mark and its paragraphs no format. A custom mark (`w:customMarkFollows`) keeps its text, a `*` say, beside the numbered note: Eigen numbers every note, so the reference shows both. A note is read once however often it is referenced, and each reference holds a copy, charged past the first as the pieces no tag counts are (`chargePiece`). A note referenced inside a note is its text there (`flattenNestedFootnotes`), read at most two deep, and a reference back to a note being read goes.

The JSON is checked against the schema block by block. A block the schema refuses keeps its text and equations as paragraphs, so a reader slip never fails an import.

The doc's page is the body's last `w:sectPr`, Word's document-level section, its size and margins read through `readPageSetup`, so a hostile `w:pgSz` clamps as a peer's write does. A size the section leaves out is the default A4, a margin Word's 1 in, so the page and the anchors placed in its column match what Word draws. A doc has one page, so an earlier section with another size or margins is dropped with a warning. `w:orient` is not read: Word draws the page `w` by `h` whatever it says. Images and tables import no wider than that page's text column.

The header and footer are the final section's: its default parts, and page 1's when the section has `w:titlePg`, which turns Different first page on. A reference a section leaves out is the one an earlier section named, as Word inherits it. Each part is charged against the package's parse budget and read as the body is, through its own relationships, so a header's logo resolves. A doc has one header, so even pages' bands, which Word draws only with `w:evenAndOddHeaders` on, are dropped with a warning. A reference counts only through a header's or a footer's relationship. A band isn't paged, as a note isn't, so a page break in it goes; a space after on its last block goes, as a band's last block draws none; an anchored picture in it is a block figure, as a band holds no float, with a warning; and a node a band's schema leaves out is its text, with the body's flattening warning. What would cover or swamp the page drops, with a warning of its own: a picture anchored behind the text (`behindDoc`, a full-page letterhead or a background) and a VML picture, Word's picture watermark, which as block figures pushed whole pages of body away. A note reference in a band drops too, as a band's schema holds no note. `PAGE` and `NUMPAGES` fields, complex or simple and whatever their switches, become the page number node, in the body too, and their cached digits go. The bands are weighed with the body, checked block by block as it is, and ride in the update in their own roots, each as its editor leaves it on open.

`commitEigendocImport` (`document/doc.ts`) clears the body and the header and footer fragments, applies the update and sets every page key in one transaction, so an import replaces rather than appends and leaves no header or page of the doc before it. The page keys are set on the live doc, never in the update: a key the transform's own doc sets is concurrent with the live one, and Yjs keeps whichever client id orders last.

Each image part becomes one media file, named `image-1.png`, `image-2.wmf`, … in the order met, its extension from the part's content type. Only the image types in `IMAGE_EXTENSION_BY_MIME` (`import/doc/drawings.ts`) are stored, so a part declared as anything else never reaches the container. WMF, EMF and BMP are kept under their own name though sharp reads none of them (`UNSHOWN_IMAGE_TYPES`). A browser draws a BMP, but the editor and quick look load every image through its sharp preview (`/file/:pathId/preview`), so all three show as a broken image with its alt text, which the user can delete, and the HTML, PDF and docx exports, which re-encode through sharp too, leave the picture out and keep its caption. The images are written through Drive as an upload is, with its write check, drive event and thumbnail, and before the update that names them: an open tab looks each name up once, as the update arrives, and redraws a changed picture on its drive event. A repeat import overwrites each deterministic name in place, since a create would rename the collision to a name the update doesn't hold. The images count toward the mount's quota at their inflated size, which the zip cap bounds, not the upload's: `saveDocImages` charges their total through `enforceMountQuota` before the first is written, credited the files a repeat import overwrites, and a conversion checks before it creates the document, so a 507 leaves nothing behind. A linked picture lives outside the file, so only its alt text comes in. A SmartArt graphic keeps its text, one paragraph per shape, and a chart its title.

The import returns warnings beside the update: `blocks-flattened`, `images-unshown`, `graphics-dropped`, `section-pages-dropped`, `even-bands-dropped`, `band-images-unanchored` and `band-content-dropped`, each with a count (`TransformWarning`, `document/transform/protocol.ts`). The runner logs them on the job's line, and the user sees none ([ROADMAP](ROADMAP.md)).

A file the reader can't read is a 400 "Not a valid docx file", whether the zip is broken, the XML malformed or the reader slipped. An encrypted docx is an OLE file holding an `EncryptedPackage` stream, and gets its own 400, "This document is password-protected. Remove the password in Word and import it again." A cap is a 413 ([§ Zip guards](#zip-guards-run-before-the-parser-inflates-anything)).

## A docx paragraph keeps what it sets apart from its Normal

Most Word files set their body's line spacing and spacing in Normal: 583 files of the corpus have a 1.15 Normal, and Google Docs writes the same values again on every paragraph. Read as they stand, every paragraph would get a format and draw unlike typed text. So the reader (`readParagraph` in `import/doc/paragraphs.ts`) compares a paragraph with its docx's Normal (docDefaults and the default paragraph style), and a heading, a title or a quote with its own style, whose look is the node's, and sets a value only where it differs. A line spacing is an `auto` line as its multiple; `exact` and `atLeast` are heights in points, which read differently at each size, so they give none.

The writer writes the container's look as direct spacing: an item's and a quote's after, a table's margin on the block below it, no space above the first block. So the reader takes spacing only on a block outside any list, quote or cell, and drops a space above that is no larger than the one Eigen draws there anyway (`formatOf` in `assemble.ts`). The writer also rescales the line of a paragraph all in one other family (`familyLine`), which the reader undoes with the same line heights, so an Eigen doc's paragraphs read back with no format. A paragraph a Word page break splits ([DOCS.md](DOCS.md#a-word-page-break-splits-its-paragraph-on-import)) keeps its space before on the first half and its space after on the last, where Word draws them. Indents are structure first: an indent nests a paragraph into a list item or a quote ([§ A docx import replaces the document](#a-docx-import-replaces-the-document)), so only the indent past the item's text is the paragraph's, an item's own indent holds its number, and a quote's paragraph keeps none. Every value is bounded through `readParagraphFormat`, as a peer's is.

## An imported doc is stored as the editor leaves it on open

The editor repairs some content the moment it loads: prosemirror-tables pads a row short of its table's columns, and on the next pass gives the new cells their column's width, and StarterKit's TrailingNode appends an empty paragraph to a doc that ends in anything else. Each repair is a Yjs update nobody typed, and two people opening a fresh import together write it twice. So the reader writes well-formed tables (`import/doc/tables.ts`): a row Word draws short of the grid ends in a cell over the columns it misses, with their widths, and a merge stops where a row leaves it out, so `fixTables` finds nothing to repair. A row stops at Word's 63 columns, its last cell holding the text of any past them: the widest row sets every row's width in the TableMap the editor builds for each table, and one row of 20,000 cells over 5,000 more cost 2.3 GB. A table that merges is split into tables of `MAX_MERGED_ROWS` (2,000) rows, a merge across the split starting again in the next: `findWidth`, under every TableMap, rescans the rows above each row after a rowspan, so 49,000 rows took 27 s to open, and a part now costs at most 0.9 s. Repairing them afterwards is no option on untrusted input: `fixTables`' transaction keeps a copy of the table for every repair, so 20,000 rows with one bad width each cost 3.4 GB and 6 s. `asOpened` (`import/doc/transform.ts`) is the safety net: it refuses a table whose repairs times rows pass `MAX_TABLE_REPAIRS` before any repair runs, runs `fixTables` once, refuses with a 413 a table a second pass would still repair (a repair can leave another, and the reader writes tables that need none), and ends the doc in a paragraph before `importDocxToEigendocUpdate` encodes the update. `apps/api/src/test/import/doc/tables.test.ts` expects `fixTables` to find nothing on ragged, colliding and mismatched tables, and `transform.test.ts` opens the stored doc with the editor's plugins and expects no change.

## A docx import is weighed by what it emits

The Yjs update costs memory per node and per mark, not per XML tag: 720,000 tags of marked tabs and breaks emit 3.6 million nodes and marks and cost 4.4 GB in the transform, which every import's limit has to hold. So after the reader walks the document and before anything is built from it, `sizeOf` (`import/doc/from-docx.ts`) counts each node and mark as one, a string attribute as one per 512 characters (the update spells a link's href out for every text node it marks) and every table's area, the slots its TableMap holds, as one per 64 (a slot costs about 16 bytes, which a span or a padded row fills at no node's cost). The same pass counts the text's characters and every string attribute's: one `w:t` compresses a gigabyte into a small upload, a link's href is spelled out again for every text node it marks, and the update holds every character, which a client opens in one WebSocket message of at most 128 MB. Past `MAX_DOCX_WEIGHT`, or past `MAX_DOCX_TEXT` characters (16 million, the corpus's most 511,898), the import is 413 Document too large. An equation's MathML is charged at the same rate as the reader writes it (`chargeMathml`, `import/doc/package.ts`), not at the weigh: a space in `m:t` writes 26 characters of MathML, so a 22 KB upload of spaces in equations would hold 400M characters by the time the weigh refuses it. The parse itself, which the weighing comes too late for, has the package's XML budget.

## A pptx import adds slides and leaves a box where it can't draw

`readPptx` (`apps/api/src/lib/import/slides/from-pptx.ts`) reads the PresentationML into the canvas's own elements in the transform process, and `importPptxToSlidesUpdate` (`import/slides/transform.ts`) encodes them as a Yjs update of frames and elements. One slide is one frame. A Convert makes the deck in the slide size nearest the file's `p:sldSz`, `SLIDE_SIZES[nearestSlideSize(cx, cy)]` (`packages/lib/src/vector/frames.ts`), and the update's `meta.slideSize` says which, so a 4:3 file makes a 4:3 deck and a 16:10 or A4 one is letterboxed, centred, into the nearer size. Import slides… passes the open deck's frame, read from its `meta` with `readSlideSize`, and a file of another size is letterboxed into it; the deck's `meta` stays as it was. A Convert writes the update into a new deck with `writeSlidesUpdateToYjs`, its `meta` included; Import slides… appends it after the deck's last slide with `appendSlidesUpdateToYjs`, under fresh ids, so nothing in the open deck is rewritten and its undo and comments stay valid ([SLIDES.md](SLIDES.md#the-deck-writer-appends-and-never-rewrites-the-deck)). Hidden slides come in too; speaker notes do not.

What the canvas has a kind for comes in as that kind: a rectangle, rounded rectangle, ellipse, diamond and pie, a straight line or connector (an arrow where it has a head), a PNG, JPEG, GIF or SVG picture, and each text body as a rich text box with its runs' fonts, sizes and colors. A layout's and master's shapes are copied beneath every slide that shows them, and groups are flattened. Any other shape comes in as editable paths ([§ A shape no kind draws is a path](#a-shape-no-kind-draws-is-a-path-from-its-drawingml-geometry)). A chart comes in as an Eigen chart through `readChart` (`core/ooxml-chart.ts`), from the values the file caches: a column, bar, line or pie chart, a 3-D one drawn flat, with its series colours through the slide's colour map, or the chart's own where it overrides that, and its text in the chart's own text colour or else that map's text colour, so it reads on a dark theme. A chart the spec can't draw as the file does (area, scatter, doughnut, radar, bubble, stock, surface, pie of pie, a combo, a stacked line, a secondary, log or reversed value axis) leaves a box naming its kind as PowerPoint's Insert Chart does (`readChart`'s name) and its title. A chart the reader's work budget can no longer cover leaves the plain "Chart not imported" box, which costs only that graphic. A table, SmartArt graphic, embedded object or unreadable picture leaves a box saying what was there too, at its place, so the slide shows the gap instead of hiding it. Every box is see-through, a dashed outline and its label in the slide's text colour, so a title it overlaps stays readable. A pattern fill becomes its foreground color, a gradient keeps its first and last stop, and a picture fill on a shape is left out. These gaps are [ROADMAP](ROADMAP.md) rows.

Each loss is counted once per source shape, so a master's background is one loss however many slides show it, and Import slides… answers with one summary of the counts, which the hook toasts ("2 tables and 1 SmartArt graphic were not imported; 5 shapes were simplified."). A Convert, of any format, answers only the new document's path and opens it without a summary: the placeholder boxes on its slides show what is missing. `importSummary` (`import/messages.ts`) phrases it. A file with no slides converts to a deck with none, which the Slides editor seeds on first open as it does a new one; Import slides… of such a file adds nothing and answers "This presentation has no slides".

The pictures are named with a random prefix per import, so a second import of the same file into one deck overwrites none of the first's. An Import that fails after its pictures are saved, a revoked write or a closed tab, leaves them in the deck's media folder, counted against quota, as Eigen keeps a document's unused media. Untrusted bytes are bounded as for a docx: the reader parses only the presentation, slides, layouts, masters, themes, their relationships and the content types, never notes, diagrams or embeddings, and a chart's part reached only by a chart relationship under `ppt/charts/`, never its own relationships, each part it parses spending the package's one parse budget (`openPackage`, [DOCUMENT-TRANSFORMS.md](DOCUMENT-TRANSFORMS.md#a-packages-parts-have-a-parse-budget-before-the-memory-limit)), and caps the slides, the elements, the reader's work (one budget over the children it scans, the colours it resolves, the text it reads, the shapes it walks, each geometry's guides, commands, arcs, nesting outlines and simplifying passes, and each chart part's elements and the points its caches declare, for every colour map it is painted with), the pictures (by count, and by bytes at the upload cap the job carries) and the update's weight. Past a cap the import is a 413 "This presentation is too large to import". The caps live in `import/slides/`. A macro deck, template or slideshow saved under `.pptx` is refused by its content type with a message to save it as a `.pptx`.

## A shape no kind draws is a path from its DrawingML geometry

A pptx shape's outline is a preset, one of ECMA-376's 187 named shapes with adjust values, or a `custGeom`, its own path list, both written in DrawingML's guide formulas. The few presets a canvas kind draws, rectangle, rounded rectangle, ellipse, diamond and their flowchart twins, come in as that kind (`PRESET_KINDS`, `import/slides/preset-geometry.ts`), so they keep their corners and binding; a pie keeps its angles. Every other shape becomes canvas paths ([CANVAS.md](CANVAS.md#a-path-is-stored-in-its-unit-box)) at the shape's box, so a star, a block arrow, a map outline or a freeform drawing stays editable and recolorable. `customGeometry` (`custom-geometry.ts`) turns a `custGeom`, and `presetGeometry` a preset through its definition in Ecma's `presetShapeDefinitions.xml`, committed unchanged beside them with its NOTICE, into one path per way the geometry paints. `guides.ts` evaluates the formulas without `eval`, every result finite. The file is the spec's own, read once per process, so every preset draws as the spec defines it; upArrow, which the file lacks, is a named override in code.

The paths follow how PowerPoint and LibreOffice paint them. A shading path (`darken`, `lighten` and their `Less` forms, a can's top or a cube's side) fills in the shape's fill blended toward black or white, by LibreOffice's fractions. A filled path left open fills as if closed and strokes open, so it becomes a closed fill and an open line. Each subpath winds by how deep it nests among its path's others, so a contour inside another is a hole, as LibreOffice's even-odd fill draws it, on the canvas's nonzero fill and under its even-odd hatch alike. Its depth is found from a point on its first segment's curve, tested against the others' outlines, each curve cut into chords within 0.1% of the box, so a thin ring such as a donut's is still a hole: a chord's middle lies inside its curve, and ends and middles alone make a circle an octagon 7.6% inside it. Filled paths painting alike become one path element only while their boxes don't overlap: the export writes an element as one `a:path`, which LibreOffice fills even-odd, so a firewall's bricks concatenated onto its wall would come back as holes. Overlapping ones are elements of their own at the shape's box, in the file's order; a shape is 32 geometries at most, so 64 path elements at most with an open fill's line apart: past them an alike path concatenates overlapping or not, and one painting a new way leaves the shape only its text, counted as simplified. A flipped shape's points are mirrored across its box as they are read, before the caps measure the path, since a path, unlike a picture, can carry its mirror. The shape's text sits on top in a transparent box. One conversion is kept per geometry and size, so a layout's shape converts once for every slide that shows it.

A geometry past the canvas's path caps is simplified, dropping each point that lies within 0.1 to 0.4% of the box of the line its neighbours draw, and past them still, or past the reader's work budget, the shape keeps only its text and counts as simplified. Each stage, the arcs, the nesting and each simplifying pass, asks the budget before it begins, so a geometry it can't cover costs the deck nothing more. An open path's arrowheads, a bent or curved connector's, an arc's or an open freeform's, are lost and counted, since a path draws none; PowerPoint draws none on a closed one. Shadows, glows and 3-D are dropped as on every shape.
