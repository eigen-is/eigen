# Document Export and Import

> **TLDR:** One route downloads a doc as docx, PDF or HTML, a sheet as xlsx, PDF or HTML, a deck as pptx, PDF or HTML and a drawing as PDF (`apps/api/src/lib/export/`); a drawing's SVG is the editor's own, drawn by the browser. Import turns an xlsx into a sheet, a docx into a doc and a pptx into slides (`lib/import/`). Every format but xlsx, docx and pptx is one HTML document, and PDF is that document through WeasyPrint. xlsx, docx and pptx each have a writer of their own, and the docx writer takes its look from the same stylesheet the editor draws with. An import writes nothing until the transform succeeds.

A user exports from the file menu of the docs, sheets, slides and drawing editors, or from a Drive item's menu. **Import…** is a row of the same file menu in docs, sheets and slides. After the user picks a file, one dialog (`DocumentImportPicker`) says how it comes in before anything is written: a deck inserts the file's slides after the current one or replaces all its slides, a workbook inserts the file's sheets as new tabs or replaces the spreadsheet, and a doc is only replaced, with a warning. Every replace saves a version first ([§ A replace saves a version first](#a-replace-saves-a-version-first)). Convert to Sheet, Convert to Document and Convert to Slides are file actions on an xlsx, docx or pptx, and make a new document from it. Which extension converts to which type is one table, `CONVERT_SOURCES` (`packages/lib/src/types/drive.ts`), that the file action, the route and the import picker's Drive rows all read, by the file's extension: Drive stores the MIME an upload claimed, and an Office file often arrives as `application/octet-stream`. Every document that exports is a collab document, so its content is the Yjs state stored in its container's `data.db` ([COLLAB.md](COLLAB.md)), and an export renders that state. The heavy work runs in a one-shot transform process ([DOCUMENT-TRANSFORMS.md](DOCUMENT-TRANSFORMS.md)).

The editor, quick look, the HTML download and the PDF draw a doc from one stylesheet, `eigen-prose.css`, so they lay it out block for block alike. The docx writer reads its sizes, spacing and colors from that stylesheet too. The rest of this doc covers how each format is built and kept safe. Three things surprise people: WeasyPrint opens only `data:` URIs, through a fetcher of Eigen's own ([§ WeasyPrint fetches only data: URIs](#weasyprint-fetches-only-data-uris)); every body keeps only `data:` references, so an HTML download fetches nothing either ([§ The sanitizer](#the-sanitizer-keeps-only-data-references-because-a-browser-fetches)); and an import checks write access again as its last step ([§ An import writes nothing](#an-import-writes-nothing-until-the-transform-succeeds)).

## A type's format list is both the menu and the gate

`EIGEN_DOC_TYPE_INFO[type].exportFormats` (`packages/lib/src/types/drive.ts`) lists what a type offers, in menu order. The file menu and the drive item menu read it through `exportFormatsFor`. The route checks the same list, and `offers()` in `export-document.ts` narrows each entry to a literal. So a format added to a type without a transform envelope fails to compile instead of reaching a user as a 400.

Export and import both dispatch on the container type, not the mime type. A mime type is caller-controlled on upload, so a plain file wearing an Eigen mime is a 400 rather than a transform over data it does not have. The export route resolves the file through `SharedDrive`, so the ACL check is the drive's; export is not a `Drive` method.

## The transform process renders and the main thread prepares

`runDocumentExport` is the one main-thread entry. The runner admits the job before anything is read. Once the transform process has read the document, it names the media files the document holds, and `collectExportMedia` (`export/media.ts`) prepares those and no others, one at a time: the screen preview for HTML and PDF, a fresh PNG or JPEG for a docx, pptx or xlsx ([§ An Office image](#an-office-image-is-a-png-or-jpeg-made-from-its-source)). That is Mount I/O plus the capped thumbnail path, so it stays on the main thread. What the export sends past 200 MB in all makes it a 413, before any read when the named SVGs alone pass it ([DOCUMENT-TRANSFORMS.md](DOCUMENT-TRANSFORMS.md#an-exports-media-is-prepared-inside-its-job)). The prep runs inside the export's 120 s transform deadline, so an export is one deadline end to end: once it is spent, or the client is gone, the prep reads no more media and the job fails as a timed-out or canceled one does.

The one-shot transform process ([DOCUMENT-TRANSFORMS.md](DOCUMENT-TRANSFORMS.md)) materializes the captured Yjs blobs, then renders and sanitizes the HTML, or writes the docx, pptx or xlsx. The docx, pptx and xlsx writers load lazily, so an HTML export evaluates none of them. A blob that fails to decode is skipped with a `corrupt-blobs-skipped` warning, as on a live read. WeasyPrint stays outside the runner, since it is already a separate process, but it takes the transform child's treatment: one render at a time (`htmlToPdf`, `export/weasyprint.ts`), because a render can hold gigabytes as a child can, under the child's Linux limits (`limitedCommand`, [DOCUMENT-TRANSFORMS.md](DOCUMENT-TRANSFORMS.md#a-child-runs-under-the-machines-memory)), and killed by the request's signal when the client goes, or dropped from the queue if it goes while the render waits its turn. Four renders may wait, about the foreground exports the runner admits behind a running one; past that a PDF export answers the runner's 503.

| Outcome | Status |
|---|---|
| WeasyPrint not installed, older than 68 or its import past 5 s (PDF only) | 501 naming the minimum and how to install it |
| WeasyPrint past its 60 s timeout, or exits non-zero | 504, or a bare 500 with its traceback in the log. A SIGSEGV, which WeasyPrint 68 hits now and then in a glib thread, renders once more in what is left of the 60 s, unless the first took over half |
| The prepared media past 200 MB in all, the named SVGs' declared sizes, or one Office source | 413 |
| Transform runner saturated, or four PDF renders already waiting | 503, never a main-thread fallback |
| Empty deck or empty drawing | 400 |

## A transform route exempts itself from the idle timeout

The response is silent while the job queues and its transform runs. Queue wait plus the 120 s transform deadline plus the wait for WeasyPrint and its 60 s can outlast any server-wide `idleTimeout`, which Bun caps at 255 s. So the export, import and convert routes call `server.timeout(request, 0)`. Without it Bun closes the silent connection, which aborts the signal and kills the job mid-transform. `request.signal` still fires on a real disconnect, and the runner then drops the queued job or kills its child process, as `htmlToPdf` kills its render.

## Every format but xlsx, docx and pptx is one HTML document

`html` and `pdf-html` render one document from one renderer, so WeasyPrint prints what the HTML download serves, but for what differs on paper. There is one document per type to get right, not one per format. Each type's entry (`renderEigendocExport`, `renderEigensheetsExport`, `renderEigenslidesExport`) decides once which one it renders: a sheet's page fits its widest and tallest sheet, a deck's pages leave the fit box, and a doc fakes small caps where the font has none ([DOCS.md](DOCS.md#the-pdf-fakes-small-caps-where-the-font-has-none)) and draws its equations as SVG ([§ The PDF draws an equation as the SVG MathJax makes of it](#the-pdf-draws-an-equation-as-the-svg-mathjax-makes-of-it)). A doc's PDF also places its bands as running elements before the body, with the stylesheet that prints them in the margins and numbers the pages, where the download shows page 1's header above the body and the footer below it, a page number as its `#` ([§ The PDF prints the bands](#the-pdf-prints-the-bands-as-running-elements-placed-before-the-body)). A doc's `<title>` keeps the extension (`Report.eigendoc`) while the docx title drops it; that output is pinned in `apps/api/src/test/export/document-export-route.test.ts`.

A doc's page is the one it stores ([DOCS.md](DOCS.md#a-doc-stores-its-page-in-a-page-map-beside-its-content)), read beside the body by `readEigendocPage`: the HTML's screen page and the PDF's `@page` from `pageStylesheet` (in `printExtras`, `export/doc/transform.ts`), and the docx's page size, margins and text column from `pageTwips`. A margin change rewrites no figure, so a figure wider than the column writes at the column's width, as the editor draws it at `max-width: 100%`. The doc's Normal is read beside them by `readEigendocStyle`: the custom properties on `.page`, the font the PDF's small caps are faked by, and the docx's defaults.

A doc's header and footer ([DOCS.md](DOCS.md#a-header-and-a-footer-are-fragments-of-their-own-beside-the-body)) reach every export through `readEigendocBands` (`document/doc.ts`): a band with content only, page 1's only when the page differs, and without the nodes a band's schema leaves out, which only a forged peer writes. Each renders through `renderDocHtml`, as the body does, and its media resolves as the body's. The PDF prints a band up to `MAX_BAND_BLOCKS` (200 blocks, counted inside tables and lists) and `MAX_BAND_TEXT` (20,000 characters), the block that passes them cut inside to what fits, so a band keeps its first lines, with a `band-blocks-cut` warning on the job's log line (`printedBands`, `export/doc/transform.ts`). WeasyPrint lays a running element out again on every page, so a 2,000-paragraph header took a 400-paragraph PDF 22.6 s and a 4,000-paragraph one ran past the 60 s timeout; cut, the 4,000 take 4.3 s. Half an A4 page holds about 60 lines of 6 pt text, and a band taller than half the page prints over the body anyway ([§ The PDF prints the bands](#the-pdf-prints-the-bands-as-running-elements-placed-before-the-body)), so the cut leaves what prints clear of the body. The docx and the HTML download keep every band whole.

The document is self-contained, because WeasyPrint and a downloaded file have no app to fetch from. One builder writes it for every type, `exportHtmlDocument` (`export/html-document.ts`): the doctype, the policy `<meta>`, the title and the fonts, around the stylesheet and body each type renders. Only the canvas document asks for the viewport `<meta>`, which the deck's fit box needs to scale a page to a phone. Fonts are WOFF2 files base64'd into `@font-face` rules (`export/fonts.ts`). A doc embeds only the families it can draw in (`usedFamilies`, `export/doc/transform.ts`): its Normal's, in which `eigen-prose.css` draws the body with no other bundled family as its fallback, the monospace where code renders, and each bundled family its rendered body names, a font mark's style or a chart's SVG. A face is up to 0.6 MB of base64, so a plain doc's HTML is 1 MB where all six faces made it 2.2 MB, which WeasyPrint read on every PDF. A doc embeds `eigen-prose.css`, flattened once at load by `document/prose-css.ts`: WeasyPrint does not read CSS nesting, so nesting is expanded, `.dark` rules are dropped and theme variables become values. The only `var()` left is a doc's Normal (`--doc-*`), with Eigen's look as its fallback, which `.page` sets for a doc whose Normal is its own, its header and footer inside it ([DOCS.md](DOCS.md#a-doc-stores-its-normal-text-in-a-style-map-beside-its-page)). The font weights come from `font-weights.css`, rounded to the nearest multiple of 100 because WeasyPrint accepts no other weight: Heading 1 to 4 and table headers print at 500, Heading 5 and 6 at the body's 400, and bold at 600.

The doc node renderers (`export/doc/render.ts`) are pure and shared with the preview: `renderDocHtml` renders a body for both, with one node mapping, so quick look draws a list's start and type as the export does. They highlight with the backend's one lowlight (`document/lowlight.ts`), which the docx writer and reader share, so the main thread imports them lazily. A figure resolves its media name to a `data:` URI and, with none, keeps its `src`, so an image pasted as a `data:` URI draws; a missing image renders no `<img>`, and an external `src` is stripped by the sanitizer. So a figure with only an external `src` exports empty, with no warning, an open [ROADMAP](ROADMAP.md) row. A task item is rendered by hand, because the static renderer drops `checked`.

## The PDF prints the bands as running elements placed before the body

The PDF's HTML places every band before the body as a WeasyPrint running element (`position: running(header)`), and the head's CSS shows them in the `@top-center` and `@bottom-center` margin boxes over the text column, the page's `headerDistance` and `footerDistance` from the paper's edge, page 1's under `@page :first` when the page differs (`bandsCss`, `export/doc/transform.ts`). Before the body, because `element()` takes the element placed on its page or the last one placed before it: a footer placed after the body would print on the last page only. The `element()` rules stay in the head, which the sanitizer never sees: it strips `element(` from a body's CSS as a fetch. A page number renders empty in the PDF, a band's or the body's, and the head's `::after` draws `counter(page)` or `counter(pages)` (`PAGE_NUMBER_CSS`). WeasyPrint counts both in the body's flow as in a margin box, so the rule goes in every PDF's head, not only a banded doc's: a doc with no bands holds a page count in its body wherever its docx's `NUMPAGES` sat.

A margin box pushes nothing, so a band taller than its margin would print over the body, where Word and the editor move the body down. So `weasyprint-render.py` first lays out a probe of the bands alone (`band_margins`): the doc's HTML under a user stylesheet that hides the body and forces a second page, so page 1's bands and the other pages' both lay out, on two near-empty pages. A band needs its distance from the edge plus its height, as the editor's margin measures it; its last block has no space after (`PAGE_BAND_CLASS`, [DOCS.md](DOCS.md#a-header-and-a-footer-are-fragments-of-their-own-beside-the-body)), so a one-line header fits the 2 cm margin. The doc's one render then takes a user stylesheet that grows `@page :first` to page 1's need and `@page` to the other pages', `!important` because a user rule loses to the document's own, so a short letterhead keeps page 1's body high and a page that page 1's growth spills onto still clears its own header. The growth stops where the margins would leave the body less than half the page: a band taller than that runs over the body rather than leaving it a line per page. A doc without bands pays for no probe, as the script looks for `PAGE_BAND_CLASS` first. The probe reads WeasyPrint's layout boxes, which are not its public API, so an `AttributeError` or `ImportError` there grows no margin: a WeasyPrint upgrade that moves them prints a tall band over the body rather than failing every PDF export, docs, sheets and decks alike. Over the 257 corpus docx files whose import gets a band, each doc lays out once, where 187 laid out twice before the probe; the total time stays within 3 % (885 s to 907 s), as the probe costs about what the second layout cost a small doc, and the longest render stays near 33 s, inside the 60 s timeout. Seven print a band over the body, each one whose bands are taller than half the page, which without the cap stretched the worst from 44 pages to 64.

Browsers ignore `running()`, so the HTML download places the bands where the long page shows them: page 1's header before the body and the other pages' footer after it, a page number as its `#`, the body's too, as the drive preview shows it.

## The PDF prints a note at its page's foot, and the screen lists the notes after the body

A footnote ([DOCS.md](DOCS.md#a-footnote-is-an-inline-node-that-holds-its-notes-paragraphs)) renders two ways from `renderDocHtml`. The PDF writes it in place as the editor's spans (`pageFootnotes`), and the head's CSS (`PAGE_FOOTNOTES_CSS`, `export/doc/transform.ts`) floats it with WeasyPrint's `float: footnote` to the foot of the page its reference falls on, as Google prints notes: a superscript number in the text and at the note, the notes at 10 pt (`FOOTNOTE_LOOK`) under a 2-inch rule. The note inherits from its reference's paragraph, so its paragraphs and its marker set its look, and the note's own font sets no line, so a note in a title adds no title-sized line to the foot. The call keeps the size of the text it sits in. The rule is an SVG background, because WeasyPrint draws a footnote area's background at the image's own size and reads no `background-size`. In every PDF, a heading that holds a note labels its bookmark with its own text (`data-bookmark`), since WeasyPrint's label would end in the note's number.

A note floats whole to its reference's page, so a note taller than the page's text lost its lines past the foot, and WeasyPrint lays the notes out again for every page they fill: 4,000 one-line notes took 35 s and 10,000 ran past the 60 s timeout. So a PDF with more than `MAX_PAGE_NOTES` (1,500) notes, or with one note longer than a page (`notesFitPages`, `export/doc/transform.ts`: its paragraphs and characters at 10 pt in the tallest bundled face, a picture at its height, against the page's lines), lists every note after the body, as the HTML download does; 4,000 notes print so in 18 s.

Browsers ignore `float: footnote`, so the HTML download and the drive preview write each reference as a superscript number linking to its note in a list closing the body (`section.footnotes`), each note linking back at the end of its last paragraph, or after its last block, as Google's HTML download does. Both forms number the notes in document order, the order `footnotesInOrder` reads, and a nested note renders as its text (`flattenNestedFootnotes`). Only a doc with notes gets either stylesheet. A band holds no note: `readEigendocBands` drops one a peer forged.

## The doc renderers write the DOM the editor holds

A figure is an inline node, so it renders as a `span.figure` with a `span.figcaption`, which a paragraph can hold. A `<figure>` inside a `<p>` closes it in every HTML parser, the sanitizer's and WeasyPrint's, and the paragraph split around it gains margins the editor never draws. `span.figure` parses back with its caption and layout; the `<figure>` rule stays, because the editor's own copy still writes one. Both draw from the shared `.figure` box ([DOCS.md](DOCS.md#the-node-view-and-the-export-draw-one-figure-box)). A chart takes the same box with inline SVG in place of the image, never an `<img>`, because an SVG image can't reach the page's `@font-face` and its labels would fall back to another font ([CHARTS.md](CHARTS.md#a-docs-chart-draws-its-look-at-its-own-size)).

`withTrailingBreaks` (`export/doc/render.ts`) gives a paragraph, heading or code block the trailing `<br>` the editor has, in the export and the preview alike ([DOCS.md](DOCS.md#the-node-view-and-the-export-draw-one-figure-box)).

The static renderer nests a text's marks the other way round from the editor: it wraps the first mark innermost, where ProseMirror draws it outermost. Rendered as is, a link's own color would sit outside its `<a>`, and `.eigen-prose a` would draw the link color over it. `inEditorMarkOrder` (`document/doc-schema.ts`) hands the renderer the doc over a schema whose marks rank in reverse, so the export and the preview nest marks as the editor does: the `<a>` outermost, its color inside it.

## The PDF draws an equation as the SVG MathJax makes of it

The HTML download and the preview draw an equation as the MathML the editor holds, in the editor's span, without its LaTeX annotation, which no screen draws. WeasyPrint draws no MathML, so the PDF draws each one as an SVG that MathJax 4 (`@mathjax/src`) makes from that same MathML string. `renderEigendocExport` (`export/doc/transform.ts`) runs an async pass before the render: it walks the equations in document order, parses each distinct one and has `mathmlToSvg` (`export/math-svg.ts`) draw it once, and hands `renderDocHtml` the drawings keyed by stored string and display. The `equation` mapping looks each equation up by its own key, so a subtree the render skips, an equation the schema refuses in a code block, a figure or another equation but a Yjs update can hold, moves no drawing onto another equation.

- MathJax loads on the first equation, once per Worker, so an export with none never evaluates it. It loads a font range the first time a character needs one, so every equation goes through the promise API.
- Every glyph is a path of its own (`fontCache: 'none'`). A glyph cache would write each glyph's id in every equation's `<defs>`, and one HTML document would hold the same id many times. An inline equation is one SVG: MathJax's inline line breaks would split it into several around an element the sanitizer drops.
- The SVG goes through `sanitizeExportHtml` with the rest of the body, which keeps all of it but `focusable`. MathJax's `vertical-align` puts an inline one on the text's baseline. A displayed one (`span.math-svg[data-display]`, `printExtras`) takes its line as in the editor: a full-width box, centred, on the bottom of the line the paragraph's trailing `<br>` holds, so no empty line follows it. Hiding that `<br>` instead would hide a user's own break after text that follows the equation, since CSS's `+` skips text. MathJax breaks no equation into lines, so one wider than the column scales down to it, where Word and Google Docs wrap it.
- **Every render bounds its equations by element, every copy counted, because the sanitizer's jsdom and WeasyPrint pay per element, not per byte.** The bands and the body spend one budget (`renderEquations`), in the order the export writes them, so a header's equations print on every page as SVG too. jsdom runs in the Worker, which shares the API's address space ([DOCUMENT-TRANSFORMS.md](DOCUMENT-TRANSFORMS.md#one-child-runs-at-a-time)). The PDF draws at most 50,000 elements and 10 MB of SVG (`SVG_LIMIT`, `export/math-svg.ts`). 44,000 elements of empty fences are 1.2 MB, and take the Worker 0.56 GB and WeasyPrint 9 s; 6 times as many, which fit 10 MB, take 1.9 GB and 51 s. Glyph paths run about 390 bytes an element, so there the bytes bind first. One equation at the math bounds draws up to 4.1 MB of SVG, a row of 1,999 `⨌`, so the budget holds two. The HTML download and the preview, which a viewer's open runs, write at most 50,000 elements of MathML (`MATHML_LIMIT`, `export/doc/render.ts`), at 3 to 5 KB of jsdom each: one paragraph of 294,000 elements is 1.6 GB of preview, and 4.9 million elements 16 GB of download.
- A 1,000-equation paper of the 108 corpus equations draws about 21,700 SVG elements and 4.2 MB, in 8 s of WeasyPrint, and writes about 10,900 MathML elements, so it shows every equation. The PDF's pass stops calling MathJax at the first equation that does not fit, so it holds at most the budget plus that one drawing. `MAX_SVG_EQUATIONS` (1,000) bounds the MathJax calls, at 1 to 2 ms each over the corpus after about 0.12 s to load (measured on a warm file cache), and up to 0.6 s for a tree at the math bounds. From the first equation past a bound, the rest print as their linear text, `readStoredEquation`'s `text`, typed or from Word alike, as the search index reads them ([DOCS.md](DOCS.md#an-equations-text-is-its-linear-form-and-the-find-bar-skips-it)). Text costs no element.

The tests are in `apps/api/src/test/export/math-svg.test.ts`, the equations blocks of `doc-export.test.ts`, the preview's budget in `preview/eigendoc-render.test.ts`, and the WeasyPrint block of `document-export-route.test.ts`, which prints an equation through the Worker.

## An ordered list draws its first number and its marker inline

WeasyPrint reads `<ol start>` and `<ol type>` only as presentational hints, and the PDF render takes no hints, so every list would print from 1 in decimals. A stylesheet can't stand in for `type`: HTML matches the attribute case-blind, so `[type="a"]` matches an `A` list too, and Chrome reads no `s` flag to tell them apart. So the schema's ordered list (`EigenOrderedList`, `packages/lib/src/docs/eigendoc/nodes/ordered-list.ts`) writes both into its own `style`: `counter-reset: list-item <start − 1>` on a list that starts elsewhere, and `list-style-type` for a lettered or Roman one. The editor, quick look, the HTML and the PDF all render it, and it keeps `start` and `type`, which a paste reads back.

## A doc's docx is written from its JSON, with the editor's CSS values

`writeDocx` (`export/doc/docx/to-docx.ts`) writes the WordprocessingML by hand from the JSON `readEigendocFromDoc` returns, the reader's mirror in `export/doc/docx/`: `paragraphs.ts` the blocks and their properties, `runs.ts` the runs, marks and links, `numbering.ts` the lists, `tables.ts` the tables, `drawings.ts` the figures, `styles.ts` the styles, `fonts.ts` the font table and its embedded faces and `package.ts` the document's section, settings and note separators. It packages them with `writePackage` (`ooxml/opc.ts`, over `writeZip`), the way xlsx is written from the workbook and not from HTML. Fed the export HTML, a converter kept a doc's structure and lost almost every visual property ([PROPOSAL_DOCX.md](proposals/PROPOSAL_DOCX.md)). Every size, margin, color and border comes from `eigen-prose.css` through `proseValue` (`document/prose-css.ts`), so the editor's look lives in one file and the docx keeps the editor's spacing. `proseValue` throws when the CSS sets no such value, so a renamed rule fails the export tests instead of drifting. A `var(--doc-…, x)` reads as `x`: the CSS is Eigen's look, and the doc's own Normal reaches the writer as the style map.

No schema checked the CRDT's JSON, so the writer checks attrs where it uses them and never fails on structure: inline content where a block belongs is wrapped in a paragraph, and a nested block is hoisted out. A node or mark it has no mapping for throws, as the HTML export does, and `apps/api/src/test/export/doc/docx/to-docx.test.ts` exports a doc holding every node and mark of the schema, so a new node fails a test instead of vanishing from the docx. A comment mark writes nothing and its text stays: comments are not exported, an open [ROADMAP](ROADMAP.md) question. A page number writes Word's `PAGE` field and a page count its `NUMPAGES` field (`PAGE_NUMBER_FIELDS`, `ooxml/wordml.ts`) as a complex field, `w:fldChar` runs around the instruction and the result, as Word and LibreOffice write it: Google Docs leaves a `w:fldSimple` `PAGE` in the body blank. The field's runs take no marks (the editor keeps none on a page number) and the result caches 1, which Word, LibreOffice and Google Docs replace as they lay out the pages; the docx reader reads the field back as the node. Every zip entry carries the DOS epoch as its date, so one doc always exports to the same bytes.

An equation is Word's own math: the `m:oMath` that `writeOmml` writes from the tree `readStoredEquation` reads, beside the paragraph's runs rather than inside one. A displayed one is wrapped in `m:oMathPara` in a paragraph of its own, as Word's Change to Display leaves it, so it splits its paragraph as a block figure does: the pieces share the paragraph's margins, a heading's later pieces stay out of the navigator, and a list item's number stays on the first. LibreOffice draws an `m:oMathPara` that shares its paragraph with text inline. An empty equation stays an empty `m:oMath`, and the typed LaTeX stays behind, because OMML has no slot for it ([DOCS.md](DOCS.md#an-equation-is-an-inline-node-that-stores-its-mathml)).

A code block's language rides a hidden paragraph style of its own, `Code Block (<language>)` based on `Code Block` (`codeBlockStyle` in `apps/api/src/lib/ooxml/wordml.ts`), written only for a language lowlight knows. Word keeps a paragraph's style on a re-save, and LibreOffice keeps its name, so the reader reads the language back from the name. The style is `w:semiHidden` without `w:unhideWhenUsed`, which keeps it out of Word's style gallery once used. Google Docs drops every custom style, so a doc that went through it comes back with no language.

## A band is a docx part with relationships of its own

The header and the footer are parts of their own, `header1.xml` and `footer1.xml`, written by the body's block writer in the body's column, and page 1's beside them when the page differs, with `w:titlePg` in the section; a page-1 band the doc lacks is an empty part, as Word writes one. A part resolves the `r:id`s it uses through its own relationships part (`relsPathOf`, `ooxml/opc.ts`), so a header's image or link has its own relationship, while the image file is written once for the package (`officeImages`, `export/office-image.ts`). The `Package` walk carries the relationships of the part it writes (`pkg.part`, a `partRelationships`), and drawing ids stay the package's, so no two collide. A part's root declares the document's namespaces, `m:` included, as a band may hold an equation. The section's `w:header` and `w:footer` are the page's `headerDistance` and `footerDistance`, which a docx import reads back. A band's last block is written with no space after, as the editor and the PDF draw it (`PAGE_BAND_CLASS`) and as Word's Header and Footer styles have none, so a one-line footer stands one line high.

## A note is a footnote in Word's notes part

A footnote writes Word's `w:footnoteReference` run in the FootnoteReference style where it stands, and its note goes to `footnotes.xml`, numbered 1, 2, 3 as the body meets them, the order `footnotesInOrder` reads. The part opens with Word's two separators, notes -1 and 0, which `w:footnotePr` in the settings names, as Word writes them; a doc without notes writes neither. Each note is written by the body's block writer in the body's column, in the FootnoteText style, through the part's own relationships as a band is ([§ A band is a docx part](#a-band-is-a-docx-part-with-relationships-of-its-own)), so a link or an image in a note resolves; its first paragraph opens with Word's `w:footnoteRef` number and a space. A nested note is its text (`flattenNestedFootnotes`). FootnoteText is Word's own, 10 pt, single spaced with no space after (`FOOTNOTE_LOOK`, the PDF's note size), and FootnoteReference is superscript.

## Caps cross the docx as Word's toggles

The writer puts a `textStyle`'s caps on the run as `w:caps` or `w:smallCaps`, and the reader turns them back into the attribute, so the letters stay as typed both ways ([DOCS.md](DOCS.md#caps-are-an-attribute-of-the-fonts-mark-drawn-over-the-letters-as-typed)). Both are toggle properties (ECMA-376 §17.7.3), read as bold and italic are: a character style flips the paragraph style's, and the run's own setting wins. No node draws capitals, so a style's caps, a Title's say, become the mark on its runs.

## The docx embeds the faces a doc uses, its 600s in the Bold slot

The writer puts a `textStyle`'s font size on the run as `w:sz` and `w:szCs` in half points. The reader keeps a run's size where it differs from the one its node draws: the docx's own body size (Normal over the document defaults) or a heading's or a title's style. So a Word file with a 12 pt body, a quarter of the corpus, imports without a size on every run, its body at 12 pt as the doc's Normal, and its headings at the doc's heading sizes. Small is written as its look, 9 pt and a little spaced, and reads back as a 9 pt size. Both ways go through `readFontSize`, so a hostile `w:sz` lands in 1 to 400 pt ([DOCS.md](DOCS.md#a-font-size-is-a-number-in-points-on-the-fonts-mark)).

Word has four slots per family (Regular, Bold, Italic, Bold Italic) and reads no variable font, so the writer embeds static TrueType files that sit beside the variable WOFF2s in `packages/ui/src/assets/fonts/` (`DOCX_FONT_FILES` in `export/fonts.ts`). The editor draws bold at 600. So Inter's and JetBrains Mono's Bold slots hold their 600 files, renamed to Bold so the family stays one name that Word, an import and Google Docs all find. Source Serif 4's holds its 700, and Excalifont has a Regular only, from which Word synthesizes the rest.

Only the faces a doc's runs resolve to are embedded, with the body's Regular always among them, each whole and not subset, so a reader can type new characters. Each is obfuscated as ECMA-376 requires, its first 32 bytes XORed with a GUID key hashed from the face, so the bytes stay stable. MS Gothic, which draws the task checkboxes, joins the font table only with a task list and is not embedded.

## The docx line is a multiple of each font's own line height

CSS sets a line as a multiple of the font size. Word's `auto` line is a multiple of the font's own line height, `(usWinAscent + usWinDescent) / unitsPerEm` from its OS/2 table, and `atLeast` would be read as single spacing by Google Docs. So `autoLine` divides the CSS pitch by that height, and every style's line is the editor's pitch in Word. Word also scales an `auto` line with the tallest face in it, by that face's own line height, while the editor's unitless `line-height` scales with the largest size alone. So a larger size in the paragraph mark's family keeps the style's line, and a paragraph whose runs all draw in one family other than its paragraph mark's gets its line rescaled by that family's height (`familyLine`) when the runs' line is taller than the mark's, so Source Serif 4, JetBrains Mono and Excalifont keep the editor's pitch. Each family's height is its `EIGEN_FONTS` line (`fontLineHeight`, `packages/lib/src/constants/fonts.ts`), which `fonts.test.ts` checks against its TTF and the docx reader shares.

A paragraph's own format ([DOCS.md](DOCS.md#a-paragraphs-format-is-six-numbers-on-its-textblock)) goes on top of its style's and its container's: its line spacing as an `auto` line through `autoLine`, which comes to 240ths of the multiple for Inter, before and after in twips outside a list, quote or cell, which own the spacing of what they hold, and its indents as `w:ind`, the left one counted from the container's text, a negative first line as `w:hanging`. A list item's first paragraph takes its indent from the numbering level, so an indent set on it stays in the editor. `w:docDefaults` and the Normal style are the doc's Normal: its font, colour and size as the default run, its before, after and line spacing as Normal's, the line through `autoLine` in the Normal's font, as the headings' and the title's lines are, which draw in it too. Eigen's own, line spacing 1.4 and 11 pt after, is an `auto` 336 and 220. The styles are built per export on that Normal, so the writer's spacing and line decisions read the doc's. A paragraph in a list, a quote or a cell, and the Quote style, write a before of 0 when the Normal has one, as the editor draws none there. Spacing `eigen-prose.css` gives in em (a list's, a quote's, a figure's margin) is written at the 11 pt body's, where the editor scales it with the Normal's size.

## An Office image is a PNG or JPEG made from its source

Office for the web and Google's editors show no WebP, so a docx, pptx or xlsx never takes the WebP screen preview. `prepareOfficeMedia` (`export/media.ts`) re-encodes each image from its source file in the thumbnail Worker, by the rules of `encodeOfficeImage` (`export/office-image.ts`): at most 2560 px on the long side (`OFFICE_IMAGE_MAX_SIZE`), PNG for a lossless source (PNG, GIF, a VP8L WebP), JPEG for the rest, and PNG again for a source with alpha. The re-encode drops EXIF, GPS included. It is uncached and runs on the thumbnail semaphore uploads and previews share, which allows 4 workers. `collectExportMedia` loops over the images in sequence, so one export takes one image at a time and queues no more once the client disconnects. The Worker's width and height size a docx drawing, because a figure stores only its width, and place a pptx picture its box covers or contains.

An SVG goes in as itself, an `asvg:svgBlip` that Word, PowerPoint and LibreOffice draw, beside a PNG fallback for a reader without SVG. `withSvgFallbacks` (`export/office-image.ts`) draws that PNG in the transform process from the sanitized XML the `svgBlip` carries ([§ The sanitizer](#the-sanitizer-keeps-only-data-references-because-a-browser-fetches)), so the Office file shows what the PDF shows. sharp loads only for an Office file that holds an SVG, or a docx with a pasted image. One librsvg cannot read leaves the file, a docx keeping its caption, and so does one it cannot draw within 30 s. That timeout is sharp's own, so a slow SVG costs its image and not the export: a 310-byte filter chain held the one transform slot for 90 s. sharp reads physical units (`in`, `cm`, `mm`, `pt`, `pc`) at 72 dpi, so `cssSize` scales a side the root `<svg>` gives in one by 96/72, the size the HTML export draws.

A figure pasted with a `data:` src has no media file, and the main thread never reads the doc ([DOCUMENT-TRANSFORMS.md](DOCUMENT-TRANSFORMS.md)), so the transform process decodes each such src once (`pastedFigureMedia`, `export/doc/docx/drawings.ts`). A raster goes through `encodeOfficeImage` and the thumbnail Worker's own `sharpResize`, so it drops its EXIF and shrinks as a media file does; an SVG goes through `sanitizeExportMedia` and `withSvgFallbacks`. The writer names the item by its `src` (`figureMediaKey`), which no media name can equal, since a media name holds no `/`. Only a `;base64` src is read; a percent-encoded one writes only the caption.

A docs chart is a picture in the docx: its SVG beside the PNG `withSvgFallbacks` draws of it, at the chart's own width, its alt text the chart's title or "Chart", as its HTML's image has. The transform process draws it (`chartFigureMedia`, `export/doc/docx/drawings.ts`) through `chartSvg`, the painter the HTML export inlines, and sanitizes it as a pasted SVG. The writer names the item by a SHA-256 of that SVG, drawn under one gradient id since each SVG is a file of its own, so two charts that draw the same are one part, though their series ids differ; the name starts with `chart/`, which no media name or `data:` src does. A spec that doesn't parse draws nothing, so the chart writes its caption alone. A Word chart (`c:chart`) is not written, so Word can't edit the data, and a re-import reads the picture back as an SVG figure, not as a chart. The SVG's labels name the spec's font, which a reader draws them in where it has that font. The PNG draws them in the API image's copies of the bundled TTFs (`docker/api/Dockerfile`), since librsvg finds only system fonts, and the image's others, DejaVu and URW's, are wider than the faces the layout measures.

Observed in Word's render on 2026-10-08: a 1204×4 px divider drew 466.5 pt wide until its height became whole twips. So the writer rounds the height to whole twips itself. A figure with no media, an external `src` (a docx fetches nothing) or a media item without a size or fallback writes only its caption.

## The PDF starts a list below a wrapped figure

The editor draws a list beside a wrapped figure, narrowed to the room the float leaves ([DOCS.md](DOCS.md#the-node-view-and-the-export-draw-one-figure-box)), because the list is its own formatting context. WeasyPrint lays such a box out at its containing block's whole width and then moves it down past every float it doesn't fit beside (`avoid_collisions` in its `layout/float.py`); only a line box narrows. So the PDF starts the list below the figure. As a plain block the list would run beside the float, but with its markers under the image and every level at the float's edge. `doc-export.test.ts` pins the PDF's list below the figure, an open [ROADMAP](ROADMAP.md) gap.

## A wrapped figure is a floating one-cell table

A figure wrapped left or right becomes a borderless floating table of one cell holding the image and its caption, placed before its paragraph, its distances from the text the figure's float margin in `eigen-prose.css`. It is the one wrap that keeps the caption under the image in every reader, and its row cannot split, or Google Docs moves the caption to the next page. In a list or quote a left float starts at the container's text edge, clear of the bullet and the bar.

## The docx writes a figure's margin inside its paragraph's spacing

In the editor a paragraph's own margins collapse with its neighbours', and a figure's 0.75em margin sits inside the paragraph and never collapses. Word and LibreOffice collapse adjacent spacing to the larger, as CSS does, and have no inside margin. So the docx writer carries the figure's margin as an inset on its paragraphs, and `withInsets` writes the whole gap on the inset paragraph's side: the neighbour's inset, the two spacings collapsed, its own inset. The pieces a figure splits a paragraph into share its margins, the first taking the one above and the last the one below. A paragraph that holds only a wrapped figure keeps its line, as the editor's trailing break does. In a quote, a paragraph whose style isn't Quote (a figure's, its caption's, an item's clearing Spacer, a done task) draws the quote's bar itself at the quote's indent, so the bar runs unbroken past it.

A list item that holds a wrapped figure ends in a clearing break (`w:br w:clear="all"`) on a single-spaced Spacer paragraph, so the next item starts below the float, as in the editor. A nested item clears its own floats, so the item around it writes no second break. LibreOffice ignores the clear on an exact-height Spacer. Google Docs ignores the clear too, so the next item draws beside the float there (observed 2026-10-08), while Word and LibreOffice honour it. The cases are pinned in `apps/api/src/test/export/doc/docx/to-docx.test.ts`.

## Bullet lists share one numbering definition, and each ordered list has its own

Each ordered list gets its own `w:abstractNum` with its start in all nine levels, so two adjacent lists count separately. A list that stores no type numbers by depth in the editor ([DOCS.md](DOCS.md#a-lists-numbering-lives-on-the-list-so-restarting-it-splits-the-list)), so the writer reads its format from the same rules, `.eigen-prose ol`, then `.eigen-doc ol ol` and on (`untypedListFormat`, `document/looks.ts`), counting the numbered lists around it, a bullet list between them or not. The reader matches it the other way: a Word level that draws what an untyped list draws at its depth stores no type, so Google's and Word's 1. a. i. comes in untyped, and any other level keeps its type, a nested decimal one `'1'`. A bullet counts nothing, so bullet lists at one indent share one definition, which keeps `numbering.xml` small, and a bullet has no counter to restart. Word has nine levels, so a list or quote deeper still indents no further.

## A cell's fill is its w:shd, both ways

A cell's `backgroundColor` ([DOCS.md](DOCS.md#a-cells-fill-is-a-color-on-the-cell)) is its `w:shd` fill, and a header cell without one takes the header's grey from `.eigen-prose th`, so a cell's own fill wins. Word draws a fill per cell, so a vertical merge's covered cells write their merge's fill too. The reader keeps the fill a cell draws, its own, else its table style's first row's, else the table's, in any color: a fill is the cell's look and never marks a header. A header row is one with `w:tblHeader`, or a first row its table style fills. A header cell beside a body cell, which `w:tblHeader` can't mark, writes its plain paragraphs in a hidden Table Header style based on Normal (`STYLE_NAMES.TableHeader`), as a code block's language rides its style, and the reader reads a cell with one as a header; a header cell holding no plain paragraph, and one Google Docs re-saved, as it drops every custom style, comes back a body cell in the header's grey. Auto text on a dark cell draws white, as Word draws it, and light text keeps its color, since the cell draws the fill it sits on.

## A docx keeps every page break

A page break is a paragraph holding `w:br w:type="page"` wherever it stands, at the top level or in a list item, a task item, a quote or a table cell.

## Every export points root-relative links at the instance

A link's root-relative `href` means nothing outside Eigen, so the docx, the HTML and the PDF prefix it with the public origin (`getPublicOrigin`, none on a `localhost` dev server), and a protocol-relative one gets `https:`, since a downloaded file would open it as `file:`. One rule serves all three: `absoluteHref` in `apps/api/src/lib/export/doc/render.ts`, which the docx writer calls per link and `withAbsoluteLinks` applies to the JSON before the HTML render. The docx import reverses it, so an export edited in Word comes back with its links into Eigen: the import job carries the public origin, and `rootRelativeHref` (`apps/api/src/lib/import/doc/runs.ts`) turns a link into the instance root-relative again. It returns a path only when one `/` follows the origin, so `https://<origin>//other.host` stays absolute instead of becoming a protocol-relative link that leaves the instance.

## WeasyPrint fetches only data: URIs

PDF is the HTML document through WeasyPrint, run by `export/weasyprint-render.py` through its Python API rather than its CLI. That script hands WeasyPrint a URL fetcher that opens `data:` URIs and refuses everything else: http(s), `file:`, a plain or relative path, any other scheme. Export embeds every resource it needs as a `data:` URI, so any other reference came from a collaborator's CRDT string, and WeasyPrint would fetch it from the API host while it renders. WeasyPrint's default fetcher opens every one, from a nested `<image href>` in a `data:` SVG to an `<a rel="attachment">`, whose response, or the server file a plain path names, it embeds in the PDF. The fetcher is the boundary for the PDF; the sanitizer is not relied on for it, and `export-pdf-ssrf.test.ts` renders raw hostile bodies to prove it.

- `htmlToPdf` runs the script with the Python that imports WeasyPrint 68 or later: the one the `weasyprint` launcher's shebang names (a pip venv's, Homebrew's own, through `env` or `env -S` too), else `python3`. A pip launcher whose venv path is long or holds a space starts `#!/bin/sh`, so it counts as naming none. When neither imports a recent enough one, a PDF export answers 501. The probe is cached; a spawn that finds the cached interpreter gone, as after a Homebrew upgrade, probes once more. An import that runs past 5 s is killed, because the export routes set no request timeout, and is not cached, so the next export probes again.
- It runs under `python -I`, so a module in the working directory or on `PYTHONPATH` cannot load in its place. That also drops the user site, so a `pip install --user` WeasyPrint is not found: install it system-wide, in a venv or from the OS package.
- The script subclasses `URLFetcher`, which WeasyPrint 68 introduced, rather than pass `allowed_protocols={'data'}`: 68.0 takes the text before `://` as the scheme, so it refuses every `data:` URI.
- The Docker image pins WeasyPrint 70.0 from PyPI in a venv at `/opt/weasyprint`, so it renders with the engine development does. `docker/api/weasyprint-requirements.txt` pins every dependency by hash, for the amd64 and arm64 wheels, and its first line is the command that regenerates it. The build renders a one-line PDF through `weasyprint-render.py`, so a system library the image lacks fails the build instead of every PDF export. Debian 13 ships 62.3, which ignores flex `align-items` and width on the `.figure` box and prints a centred figure left-aligned, its caption squeezed beside it.
- The document has no base URL, so a relative link stays relative in the PDF instead of becoming a `file://` URL of the server's working directory.

## The sanitizer keeps only data: references, because a browser fetches

`sanitizeExportHtml` (`export/sanitize.ts`) is DOMPurify plus one rule. Every CSS `url(`, every `src`, `poster` and `background`, and every SVG `href` must open a `data:` URI with no fragment. A `url(` may also be fragment-only (`#id`), a reference into the same document, and so may an `href` on the elements that reference with one: `use`, the gradients, `pattern`, `filter`, `textPath` and `mpath`. An `image` or `feImage` loads its `href` as a file, so a fragment there names the document itself. `srcset` is dropped. A `url(` that opens anything else costs the whole attribute it is in, and in a `<style>` element the statement it is in. So do `@import`, the string forms of `image-set()`, `image()`, `cross-fade()` and `element()`, which fetch with no `url(`, and `attr()`, which can read an attribute as a URL: WeasyPrint fails the whole export on `attr(name url)`.

A browser that opens an HTML download fetches what the document names, from the reader's machine, which tells whoever wrote the reference who read it. A preview body is live DOM in the drive hero, the same beacon at every viewer ([PREVIEWS.md](PREVIEWS.md)). So the restriction runs inside the transform process on every assembled body, and every format inherits it: `exportHtmlDocument` sanitizes the body of every HTML and PDF document, and keeps a link's `target`, so a downloaded link opens in a new tab as it does in the editors. WeasyPrint ignores `target`. A `data:` URI passes as it came, whatever its type or payload: a browser fetches nothing from an SVG drawn as an image, librsvg draws one from its bytes, and WeasyPrint's fetcher opens nothing but `data:`. The exception is a fragment. Firefox loads a `data:` SVG named with one (`mask:url(data:…#m)`, `fill="url(data:…#p)"`, `<pattern href="data:…#g">`) as a document, not an image, and fetches what that document names, such as its `@import`. So a `data:` URI holding a `#` is refused wherever it stands. A real one never has one: export media is base64, and a `#` in a percent-encoded payload ends it anyway.

- The rule reads the `url(` token, in any case, never a `url(…)` pair. A quoted URL can hold a `)` or a quote, so a pair regex ends early on `url('http://host/a)')` and the CSS parser fetches it. Its function tokens and its statement split come from the mail rules (`packages/lib/src/core/mail/remote-content.ts`). The `url(` admissions differ: a message keeps only a raster image its parser inlined, an export any `data:` URI without a fragment, a same-document fragment and the preview's own URLs.
- Every attribute value is scanned, not only `style`: an SVG `fill`, `filter`, `mask`, `clip-path` or `marker-*` is CSS too.
- Backslashes go from `style` and `<style>` text before the scan. A CSS escape spells `url(` or `@import` invisibly to a regex (`\75 rl(`), but not to the parser that fetches. Any other attribute holding both a backslash and a `(` is dropped: an escape spells `url(` (`\75 rl(`) or a fragment (`url(data:…\23 p)`), and every fetch needs the literal `(` that opens a function.
- `<a href>` keeps its target, because docs and sheets carry real links and a browser follows one only on a click. A link is not inert to WeasyPrint: one with `rel="attachment"` is fetched and embedded in the PDF, which only the fetcher stops. jsdom names an SVG `<a>` in lowercase and an HTML one in uppercase, so the check ignores case.
- DOMPurify drops every `<use>`. A profile that admits `<svg>` keeps one whose every `href` is fragment-only, because matplotlib draws its text with `<use href="#glyph">`; any other `<use>` goes. Written as XML (`toXmlDocument`, SVG media), a `<use>` also needs every target to exist and hold no `<use>` of its own. Each reference draws its target again, so nested ones multiply: 1.2 KB of six levels of ten runs WeasyPrint into its 60 s kill. One level is what glyphs need, and it ends every cycle.
- DOMPurify's MathML profile drops `<none>`, the empty slot of a prescript, which breaks the `<mmultiscripts>` it is in. `KEEP_MATHML` keeps it for every HTML and PDF document and the doc preview; the namespace check still drops one outside a `<math>`.
- Only the whitespace a URL or CSS parser trims counts as whitespace. A non-breaking space before `#` or `data:` makes a relative path of the rest.
- Every token pattern runs in one pass, because a collaborator's string sizes the scan. Two whitespace runs that could trade characters around an empty match cost their square: 256 KB of spaces after a `url(` costs 26 s.
- The hooks are added and removed around each synchronous call, so they never leak to another DOMPurify user.
- A media preview serves an SVG as uploaded. A docx carries it as a part of its own, and WeasyPrint and librsvg draw its every `<use>`, so the transform process takes every `image/svg+xml` media item through `sanitizeExportMedia` before any arm embeds it, and writes it as XML, without the characters XML can't hold; a file with no `<svg>` in it is dropped. The main thread hands over the inlined bytes as they are, because sanitizing a big drawing holds jsdom for seconds. Every format takes an SVG of any size within the export's media cap: the export deadline, sharp's pixel limit and the PNG fallback's timeout ([§ An Office image](#an-office-image-is-a-png-or-jpeg-made-from-its-source)) bound the work.

A browser backs the rule up: every export response carries `EXPORT_CSP` (`export/sanitize.ts`), which allows `data:` images and fonts and inline styles and nothing else, and `exportHtmlDocument` writes it into every HTML download as a `<meta>` too, so it holds once the file is saved.

Previews pass the same function the exact set of their own preview URLs ([PREVIEWS.md](PREVIEWS.md)). The tests are in `apps/api/src/test/export/export-pdf-ssrf.test.ts`.

## A sheet export recalcs, and xlsx carries cells, charts and pictures

Export is the one read that recalcs a workbook nobody computed ([SHEETS.md § The editor computes on write](SHEETS.md#the-editor-computes-on-write-the-server-only-what-nobody-computed)), so an import whose recalc failed still exports values. A recalc failure exports the replayed values with a `recalc-failed` warning. A legacy workbook whose recalc outlasts the 120 s deadline fails the export, an accepted residual.

The HTML and PDF export and the Drive preview render the sheets whose tabs show, as Excel prints a workbook, while formulas and rules still read the hidden ones. A hidden row or column is left out of the table the same way, hidden by its key in `rowhidden` or `colhidden` whatever it holds, since the editor and the import store 0. The xlsx export writes every sheet, a hidden one hidden, with its tab colour.

`writeXlsx` (`export/sheets/xlsx/to-xlsx.ts`) writes the SpreadsheetML by hand, the reader's mirror in `export/sheets/xlsx/`: `package.ts` names the sheets and writes the workbook, `worksheet.ts` a sheet part around its grid, `cells.ts` the grid, `strings.ts` the shared strings and `styles.ts` the looks, each look and string interned once. Every part is declared before any is written. A sheet's rows reach the zip writer in batches of about 1 MB, deflated a batch at a time, so a sheet of millions of cells is never one string, and the shared strings and styles the sheets filled are written after them. A cell of a merge writes its own value, formula and stored borders, as Excel keeps them, so a formula reading a cell under a merge computes the same after a round trip. A link is an element of its own beside its cell's value: a web address passes `resolveWebLink`, the editor's gate, and is an external relationship, and a place in the workbook is a `location`, a whole range kept, labelled by the cell's text in `display`. Past Excel's limits, a text of 32,767 characters, a formula of 8,192, a number format of 255, 64,000 cell formats, 65,530 links a sheet or a cell past its grid, the writer cuts and counts a warning rather than failing the export. A sheet name Excel refuses (`History`, a forbidden character, a quote at an end, a clash in any case after the 31-character cut) is repaired and numbered as Excel numbers a copy, counted too; formulas naming it keep the name they had. A number format is written in Excel's case, `m` for a month. The bytes hold no timestamp, so one workbook always exports the same file. Inter is the workbook's default font ([TYPOGRAPHY.md](TYPOGRAPHY.md#the-xlsx-export-makes-inter-the-workbooks-default-font)). A column width is written in 256ths of Inter's digit, and each sheet's default column width and row height go into its `sheetFormatPr`, so Excel opens a column or row at the size Eigen draws it and the import reads back every pixel. A sheet's charts are its drawing part (`drawing.ts`), each a chart Excel can edit ([CHARTS.md](CHARTS.md#a-chart-goes-to-office-as-a-cchartspace-that-reads-back-as-the-same-spec)), and its conditional formats and validations its rules' slot (`rules.ts`). An imported chart sheet is a sheet without cells, so it exports as a worksheet holding its chart at A1. A pie is written without axes, as Excel's pie has none, so the axis settings its spec keeps for a change of type come back as the defaults. A pie's slice colours go with the points its cells resolve to, so a pie over a whole column, an area or more points than a chart draws writes none. A sheet's images go into the same drawing part as pictures, in one paint order with the charts ([§ An xlsx picture is anchored as Excel places a turned one](#an-xlsx-picture-is-anchored-as-excel-places-a-turned-one)). The class-styled HTML and the round-trip drifts: [SHEETS.md](SHEETS.md).

## The xlsx writer's gate is a round trip over the corpus

`bun apps/api/src/scripts/xlsx-audit.ts roundtrip <corpus dir...> --out <dir>` imports each file, writes it with `writeXlsx`, its pictures prepared as an export prepares them, imports the result again and compares the two imports key by key, a picture's media by its type and pixel size. Each file runs in a child process of its own under a time and memory cap. A difference the writer explains is listed in `LISTED`, each kind with its reason, as a sheet name Excel refuses is repaired; any other is unlisted. The run passes with no crash, no cut and no unlisted difference. A file the first import refuses is skipped, so a reader that newly refuses one is caught by `compare` of two corpus runs, not here.

## Canvas pages are the boxes the live canvas draws

A deck's HTML and PDF and a drawing's PDF are pages of compositor layers (`export/canvas/render.ts`), which the canvas previews share. It restates no geometry: `layerBoxCss`, `layerPrintCss`, `layerInnerHtml` and `backgroundCss` come from `packages/lib`, and each screen layer gets the box `element-layer.tsx` gives it live, each printed layer the same box laid out where it prints. So what a user sees is what prints. A screen page holds the scene at 1:1 and scales it once, because a layer's body is authored in scene pixels. A non-text layer sits in an `overflow="visible"` `<svg>`, because roughjs overshoots its box.

`canvasHtmlDocument` (`export/canvas/transform.ts`) wraps all three, with one `@page` rule, font block and reset, so they cannot drift. It embeds `canvas-text.css` for the list and link rules an inline style cannot reach.

Before layout, `sanitizeSceneHtml` filters every text box to `LIGHT_EDITOR_TAGS` (`packages/lib/src/core/html.ts`), the set the canvas mounts a body with. A `<table>` or `<style>` a peer wrote would otherwise be invisible live yet print. The document cannot forbid `<style>` instead, because it carries its own `@font-face` block.

## A deck prints each frame at its own width

A frame is the page, at the deck's slide size and physical width ([SLIDES.md](SLIDES.md#a-deck-has-a-physical-width-so-its-text-sizes-read-in-pt)), and an overhanging element is clipped as the canvas clips it. Every frame is 1920 wide, so a new deck's 960 pt page prints at 2/3, 338.67 × 190.5 mm for 16:9 as PowerPoint's widescreen, and a 10 in deck at 0.5: 960 by 540 px for 16:9 and 960 by 720 px for 4:3, which is 254 × 142.875 mm and 254 × 190.5 mm, Google's PDF sizes (`deckScale`, `export/canvas/render.ts`). The PDF document lays each slide out at 1:1 on a 1920 px `@page`, and `htmlToPdf` hands WeasyPrint that scale as its zoom, which prints it at the deck's width. Only the transform process reads the deck, so the export's result carries the zoom back to the main thread beside the document's bytes. The HTML download wraps each page in a `.page-fit` box that scales it to the viewport, so a deck reads on a phone, with a `@media` ladder first for a browser that cannot divide `100cqw` by a length. The PDF has no fit box, because WeasyPrint has no viewport. The `.page-fit` rules mirror `packages/ui/src/styles/globals.css`, since a standalone file cannot import it.

## A deck's pptx is written from the scene, one DrawingML shape per element

`writePptx` (`export/slides/pptx/to-pptx.ts`) writes the PresentationML by hand, from `package.ts` (the presentation, its master, layout and slides), `shapes.ts`, `lines.ts`, `pictures.ts` and `text.ts`, the way the docx is written from the JSON: a converter fed the export HTML would keep the text and lose the canvas's geometry. One frame is one slide, and `p:sldSz` is the deck's own width and its slide size's height at the deck's pt per px, so a 10 in deck writes Google's 9,144,000 by 5,143,500 EMU and a 13.33 in one PowerPoint's 12,192,000 by 6,858,000. A 10 in deck names its on-screen show type, `screen16x9` or `screen4x3`; any other width is the attribute's default, custom. A text size is the deck's pt to the hundredth (`sz`), so the 44 pt title a file brought in leaves as `sz="4400"`. Each element becomes the shape that draws it: a preset for a rectangle, ellipse, diamond or pie, a connector for a two-point line or arrow, a custom path for a path element's own commands, for more points and for a freehand stroke's outline, a picture with its cover or contain fit, and a text body for rich text, with its runs, lists and links. Every shape writes its own colors and fonts, so the theme only has to be valid. A gradient writes the nine OKLab samples the canvas paints from (`gradientStops`, `packages/lib/src/background/gradient.ts`), so a reader that blends in sRGB still draws Eigen's ramp. A link keeps its text's color, as `canvas-text.css` draws it.

`renderEigenslidesExport` (`export/slides/transform.ts`) runs `sanitizeSceneHtml` before it writes a pptx, the filter the HTML export runs ([§ Canvas pages](#canvas-pages-are-the-boxes-the-live-canvas-draws)). It is what keeps a `javascript:` link a peer wrote out of the file, because a pptx hyperlink is a relationship target the writer copies as it is. The pictures come from the Office media prep ([§ An Office image](#an-office-image-is-a-png-or-jpeg-made-from-its-source)). `apps/api/src/test/export/slides/pptx/to-pptx.test.ts` pins the writer, and `slides-export.test.ts` a whole export.

## A pptx draws what DrawingML can, and loses the rest

DrawingML has no sketch, no hatch and no paragraph border, so a few looks change on the way out:

- A hatched or rough fill is solid, and a rough outline is the plain one.
- A quote keeps its indent and its fade, but not its bar.
- An elbow arrow's rounded bends are square.
- An arrow label hides the shaft under it with a box in the slide's color, where the canvas cuts the shaft out. On a gradient or picture background there is no such color, so the shaft runs under the text, and over another shape the box covers that shape too.
- A pie's gradient spans the whole ellipse's box at its angle, where the canvas paints it across the slice's own box.
- A chart is the shapes Convert to shapes makes (`convertToShapes`), not a chart PowerPoint can edit: there is no chart part writer yet, an open [ROADMAP](ROADMAP.md) row.
- Fonts are written by name (Inter, Source Serif 4, JetBrains Mono, Excalifont) and not embedded, while the docx embeds them ([§ The docx embeds the faces](#the-docx-embeds-the-faces-a-doc-uses-its-600s-in-the-bold-slot)). PowerPoint for the web substitutes all four; Google Slides has the first three and substitutes Excalifont. Embedding them is an open [ROADMAP](ROADMAP.md) row.

## A drawing downloads its own SVG and prints as layers

A drawing's SVG is written in the open editor, not by the export route, because only a browser lays rich text out as the canvas does. The server has no layout engine, and the `<foreignObject>` the canvas's HTML would ride in is drawn by browsers alone, not by Illustrator, Inkscape, Figma, Office or Preview. So Vector's File › Download › SVG image runs `downloadCanvasImage` (`packages/ui/src/components/vector/canvas-image.ts`), and the route answers 400 to `svg`: Drive's Download and ⌘K offer a drawing as PDF only.

The same writer draws Download image, a row of every object menu that holds a chart or a canvas selection ([LAYOUT.md](LAYOUT.md#menus-draw-their-rows-in-one-order)): a chart in Docs, Sheets, Slides or Vector, and any selection in Slides or Vector. A single image's menu offers only Download original image, since a picture of a picture adds nothing. Viewers get the row too, because a download writes nothing.

`canvasImageScene` (`packages/lib/src/vector/canvas-image.ts`) is the one place the writer's input becomes the elements the image draws, and the background they draw on. A canvas passes its own elements as they are. They are the editor's own drawing, not clipboard input, so the 10,000-element cap a paste puts on a forged wire does not apply. A doc or a sheet has no elements, so it passes the chart item its copy writes, with the look and, from a sheet, the ranges read into inline data; that item becomes the one chart element a canvas paste would make of it, through the element reader. The whole drawing keeps its own background, a selection is transparent and a chart alone draws on white, as it does in a doc or on a sheet. A chart's file is named for its title (`chartImageName`), less the characters a file name can't hold, or "Chart"; a selection is "<file> – selection". `sceneToSvg` draws the elements. Images are the canvas's own media, the screen preview, inlined as `data:` URIs.

Each rich-text box is laid out again in a hidden copy of its layer, its own markup and style at its size under the app's `canvas-text.css`. Once `document.fonts.ready` resolves, `Range.getClientRects` reads where every character landed, and `richTextSvg` writes one positioned `<tspan>` per run of characters side by side on one baseline, each word on its own on a justified line, since no SVG reader stretches spaces. A list's number is text the copy carries where the browser draws its `::marker`. A disc is not: Chrome paints it as a circle from the font's rounded ascent (Blink's symbol-marker rect), which no DOM API reports, so `richTextSvg` restates that geometry; another browser's canvas draws its own disc, which the file does not follow. A quote's rule is a `<rect>`. In Chrome the file draws pixel for pixel what the canvas draws, for plain, mixed-style, linked, listed, centred, justified and quoted text in all four bundled faces; a rotated box differs only in antialiasing, under 0.5% of its ink.

The file embeds only the faces it draws in (`canvasImageFaces`, `fontFacesFor` in `constants/fonts.ts`): a box's measured runs, each in the face of its computed family and style, and every other element's labels, upright. Italic is a face of its own, so a drawing with no italic run carries no italic face; a family without one, Excalifont or JetBrains Mono, slants its upright face. Every bundled face is variable across its weights, so a weight never picks another file.

Right-to-left text and emoji are accepted limits: a run is written in logical order at its measured start, and an emoji names the run's family list, so a reader draws it in its own emoji font.

A drawing's PDF is a single compositor page sized to the content plus 10 px on each side, the margin `sceneToSvg` leaves for roughjs's overshoot. Rich text prints because it is an HTML div; WeasyPrint ignores `<foreignObject>`. A transparent drawing prints on white paper, because WeasyPrint has no canvas behind the page. The page is capped at 19,200 px a side (`MAX_PDF_PAGE_PX`, `export/weasyprint.ts`), the PDF's 200-inch limit, so a far-out element cannot make WeasyPrint lay out an unbounded sheet. Artwork past it is cut off. A sheet's PDF page has the same cap, and a taller sheet continues on the next page.

## WeasyPrint dictates how a layer references its paint

A gradient (`fill="url(#…)"`) or an image clip (`clip-path="url(#…)"`) stays an SVG attribute pointing at the element's own `<defs>`. WeasyPrint resolves `url(#id)` only within the same `<svg>`.

No transform sits above a PDF layer, and a layer's only transform is its rotation: `renderPrintPage` lays each layer out where it prints, its box minus the page's origin as `top` and `left` (`layerPrintCss`, beside the live canvas's `layerBoxCss`), and a deck scales through WeasyPrint's zoom, never a CSS `scale`. WeasyPrint 68 lays a page out ignoring transforms and cuts every line whose layout box passes the `@page` height, and it clips a translucent element to the page as its parent's transform maps it. A layer laid out at the scene origin and moved by a `translate` would lose a text box's lines wherever its layout box passed the page bottom: in a slide's lower half under a scale of 0.5, in a text box starting above a slide, in a drawing drawn above or left of the scene origin (`canvas-pdf.test.ts`).

An arrow's shaft is hidden under its label by a `<mask>`, because WeasyPrint ignores `clip-rule="evenodd"`. WeasyPrint applies a mask after drawing a node's children, so the reference goes on each shaft `<path>`, never a wrapping `<g>`. See `labelMask` and `maskShaft` in `packages/lib/src/vector/kinds/arrow-render.ts`.

## An import writes nothing until the transform succeeds

`importIntoDocument` imports into an open document (`/import`, `/import-from-drive`) and `convertToDocument` (`/convert`) creates one beside the source, both in `import/import-document.ts`. The transform converts bytes only and never sees an owner, mount or path. So a failed transform creates no document and mutates no Yjs state, and its 400 or 413 crosses the boundary unchanged. An xlsx comes back as snapshot JSON plus images, the JSON committed without parsing on a replace and decoded into new tabs on an insert ([SHEETS.md](SHEETS.md#an-imported-tab-arrives-as-an-addsheet-op-renamed-as-duplicate-names-a-copy)); a docx as a ready Yjs update, its page and images; a pptx as a ready Yjs update plus images. A convert refuses a file on its extension before it reads it, so a `.pptm` or a `.potx` never reaches the reader.

The route checks write before it buffers, but the job can queue for minutes, long enough for a share to be revoked. So `importIntoDocument` checks write again as the last await before the synchronous Yjs write, and a revoked writer gets a 403. `convertToDocument` checks write on the destination folder before it reads the source, so a reader pays for no transform, and needs no recheck, because `SharedDrive.create` checks write. A convert that fails after its create (quota another write spent) trashes the new document through `Drive.deletePath` and answers the failure; the trashed document sits in the owner's Trash, counted against quota, until it is purged ([SOFT-DELETE.md](SOFT-DELETE.md)). It takes no abort signal either: a page reload must not kill a minute of conversion, and the file appears through the drive SSE refresh.

## An Import… answers with what the file held that did not come over

Every reader counts what it leaves out or draws simpler as it reads, through one `lossCounter` (`document/transform/protocol.ts`), and returns the counts as warnings beside what it read. The runner logs them on the job's line. An Import… of any format answers with `importSummary` (`import/messages.ts`) of them, which the hook toasts: "2 tables and 1 SmartArt graphic were not imported; 5 shapes were simplified." It phrases every reader's codes from one table of nouns, so one kind reads alike whichever format met it: a docx's SmartArt and a deck's are both SmartArt graphics. A warning without a count, a failed recalc, says nothing. A Convert, of any format, answers only the new document's path and opens it without a summary: the document itself shows what is missing, a deck's placeholder boxes and a doc's chart lines among them.

## A replace saves a version first

An import into an open document takes a mode, `insert` or `replace` (`DocumentImportOptions`), in the upload's query, since its body is the file, and in the Drive pick's body beside the source. A docx only replaces, and an insert into a doc is a 400 before the transform: the file's page setup, Normal style and bands can't sit beside the doc's. Before a replace writes, `importIntoDocument` calls `saveVersion`, as a version restore does before its own write. A replace clears what the document held, its comments' anchors and a peer's pending edits included, and nothing else can bring that back: Ctrl+Z doesn't undo a server's write, and the newest automatic version can be up to 99 writes old. So the document as it was is one restore away in its version history. An insert saves none, because it writes only new records. A deck replace with a file that has no slides says so and saves nothing.

The version holds the container's `data.db`, not its media folder. A docx, pptx or xlsx import names its pictures with a random prefix per import (`xlsx-<uuid>-image-1.png`) and writes them beside the media already there, so a restored version draws its own pictures.

## Zip guards run before the parser inflates anything

The upload bound limits compressed bytes, and an inflated package can hold 200 MB of XML. So the docx, xlsx and pptx readers open the package with `openZip` (`ooxml/zip.ts`), which refuses a declared total past the byte cap before it inflates anything and inflates an entry no further than it declares, so a forged directory that declares a small size is refused too. Nothing else reads the upload. A file a reader can't read is a 400 in its format's words, and an encrypted package names the application that removes its password (`importError` and the words in `import/messages.ts`).

The xlsx reader (`import/sheets/`) reads the SpreadsheetML itself. Bun has no streaming XML, and a parsed tree costs about 100 times its text, so a sheet's grid, which can be the whole byte cap, is never one tree. `readInBatches` (`import/sheets/package.ts`) cuts `<sheetData>` into batches of whole rows of about 1 MB, each parsed behind the part's prolog and start tags, so prefixes bind and a DOCTYPE is still refused. The cut is checked, not trusted: a batch that won't parse, because a comment, CDATA or an instruction hid the cut, reads the part whole past the rows already read, under the budget below, and a part that won't parse whole is malformed XML, never a misread. The shared strings are read in batches too. The workbook, the styles, the theme and a sheet's part without its grid are each parsed whole, once.

What the reader parses is charged before it is parsed, against the read budget in `import/sheets/package.ts`, because a node costs its parse and its memory whatever it emits, and a 1 MB upload inflates to tens of millions of empty cells or strings. Every grid's and the shared strings' elements are counted in their bytes before the part's first batch, against `MAX_XLSX_ELEMENTS` together (16 million, a little over twice the corpus's most, 7.3 million, so the cheapest flood parses in seconds), the prolog's and start tags' elements again for every batch they are parsed in front of, and every reference of a validation's or a conditional format's sqref before it is parsed. A batch past `MAX_BATCH_BYTES` (12 MB) is refused: a batch ends at the first row or string past 1 MB, so it holds one long row or string whole, and the corpus's longest is a 2.5 MB row. A sheet's part past its grid, and a part read whole because its cut can't be checked, never passes through `openPackage`'s part cache, so it is charged its bytes and tags against a budget of its own with the package budget's values, `MAX_PACKAGE_XML_BYTES` and `MAX_PACKAGE_XML_TAGS` (32 MB and 1.5 million, together across the sheets). The workbook, styles, theme and relationships parts go through the part cache and its budget. Past any of these the import is a 413 "This spreadsheet is too large to import".

What the reader emits is charged against one budget as it reads, before it is built, so a range a file declares costs what it emits, never what it spans. `MAX_CELLS` counts every cell emitted: a value or a border, a rich string's run, a row's height or hidden flag, each cell of a merge, charged from its area before any is visited, a linked cell, a column's width, a conditional format's ranges per rule, a validated cell. A validation stops 1,000 rows and 100 columns past the cells. Each sheet's span, its rows by its columns and at least a default grid's, counts against the same cap, because recalc walks it. The grid recalc builds, at least 100 rows deep and 26 columns wide, has a budget of its own, `MAX_GRID_SLOTS`: a sheet holding A1 and XFD1 spans 16,384 cells but builds 1.6 million slots. A row or column past the grid's last, a cell past the cap, or a span past it is a 413 "Spreadsheet has too many cells"; any other cap a 413 "This spreadsheet is too large to import".

`MAX_TEXT` counts the text the reader writes: every value, display, rich-text run, number format, formula, link and rule text. A shared string counts once for every cell that shows it, because the snapshot spells it out per cell, so a 1 MB string in a thousand cells is a gigabyte. A shared formula's copies are translated before they are weighed, so they have a budget of their own, `MAX_SHARED_FORMULA_TEXT`. The caps sit in `import/sheets/from-xlsx.ts`.

Only what the file holds is walked, never the row or column numbers before it, and merges are never checked against each other: a merge over a cell an earlier one holds is dropped, as Excel repairs it, found through the cells already placed. Defined names are never read. A number format past Excel's 255 characters reads as General, and one numfmt can't parse keeps its code but displays General, tested once: numfmt parses it again on every display to throw. Cell formats that name more than 1,000 number formats, four times Excel's own allowance, are refused, since each costs its date test and canonical form. A shared formula past Excel's 8,192 characters is not translated into its copies, which keep their values: a translation costs about a hundred times its text.

Over 1,062 public workbooks (GOV.UK statistics, Zenodo data, and the test files of Apache POI, LibreOffice and other readers), the caps refuse 14. POI's 49609 is refused as unreadable, because its part names use backslashes, which `openZip` keeps verbatim. `apps/api/src/test/import/sheets/limits.test.ts` pins the bounds on small hostile files, one per class.

The docx reader opens its package with `openPackage` (`apps/api/src/lib/ooxml/opc.ts`), so it reads only through `openZip` too. It parses only the parts it needs (the content types, the document, its styles, numbering, theme, font table and notes, the final section's headers and footers, the settings when an even page's band is named, their relationships, a chart's part reached only by a chart relationship under `word/charts/` and of the chart content type, and SmartArt's own parts), never `webSettings.xml` or `comments.xml`, each once. A parsed XML tree costs many times its text (`apps/api/src/lib/core/xml.ts` gives the measured ratios) and per element, so 16 MB of empty paragraphs is 2.8 million elements and 3.5 GB, while the largest real document met holds 611,000 tags. So `openPackage` charges every part the reader parses, a chart's or SmartArt's included, against the package's parse budget before it inflates and before it parses ([DOCUMENT-TRANSFORMS.md](DOCUMENT-TRANSFORMS.md#a-packages-parts-have-a-parse-budget-before-the-memory-limit)). A part past it makes the whole import 413 "This document is too large to import", and the transform process's memory limit is the backstop past the budget. The budget's worst case is dear: 1.48 million empty paragraphs, just under its tags, peak at 2.2 GB in the reader before the output's weight refuses them. What the reader builds has caps of its own: `MAX_DOCX_PIECES` for the text pieces a run splits into past its first, about 600 bytes each before the output is weighed, so 4 million of them from 5.7 MB of XML cost 2.5 GB; `MAX_INLINE_NODES` per paragraph and the output's weight and text (below). The structural bounds (columns, table and quote nesting, list starts, style chains) sit beside the code they bound in `apps/api/src/lib/import/doc/`; a thousand nested tables overflowed a Worker thread's stack before the nesting cap. Past a cap the import is a 413 "This document is too large to import", and the import maps a stack overflow, in the reader or the Yjs conversion, to the same 413, as the transform process answers an import that runs out of memory ([DOCUMENT-TRANSFORMS.md](DOCUMENT-TRANSFORMS.md#out-of-memory-is-the-jobs-not-the-servers)); any other `RangeError`, as ProseMirror's schema and table checks throw, is a reader slip, logged and 400. `apps/api/src/test/import/doc/limits.test.ts` pins the bounds.

## An imported sheet is stored as computed

The transform runs `recalcSheets` and encodes the snapshot as computed, so no later read recalcs it. A recalc failure, formula ranges past the server's budget on what they index or read among them ([SHEETS.md](SHEETS.md#the-editor-computes-on-write-the-server-only-what-nobody-computed)), stores the parsed values uncomputed with a warning, and the first export recalcs them. The importer keeps these rules:

- `ct.fa` is always paired with `ct.t`, `'General'` when Excel reports no number format. Without an `fa`, date serials and percents render as raw numbers.
- A formula cell's `f` keeps its leading `=` (`=SUM(A1:A3)`), the form a sheet stores; the xlsx writer strips it. A function Excel added after 2007 is stored as `_xlfn.IFNA(…)`; the reader drops the prefix so the engine recomputes it, and the writer adds it back for the functions `ooxml/spreadsheetml.ts` lists, since Excel reads a bare `IFNA` as an unknown name.
- A number keeps no horizontal alignment unless its format names one, and `horizontal="general"` is none: the editor and the HTML and PDF export align a number or a date right by its type, a boolean or an error centred, as Excel does (`generalAlign`).
- A merged cell other than the anchor keeps the value the file holds under the merge, and the xlsx writer writes it back, so a formula reading it computes the same. Excel and the editor show the anchor's across the merge, and the editor tells the anchor by its `mc.rs`.
- A rich string keeps its runs as the editor stores them, `ct: { t: 'inlineStr', s }`, each with its font, a run Excel wrote without properties in its cell's. The runs are the text's one source, with no `v` or `m` beside them, so an edit in the editor leaves nothing stale; every reader of a value or a display, the formula engine, the conditional formats, the HTML export and the search index, reads a rich cell through `richText` (`engine/format.ts`). The runs are a copy per cell, so each is charged as a cell.
- Every imported sheet gets its `defaultColWidth` and `defaultRowHeight` from `sheetFormatPr`, Excel's own defaults when the file has none, so its unsized columns and rows keep Excel's pitch ([SHEETS.md](SHEETS.md#some-xlsx-round-trip-drifts-are-decisions)). A row at that default height stores no height of its own.
- A hidden sheet is the editor's `hide: 1`, and so is a very hidden one, which the editor can show again, and a workbook that hides every sheet shows its first, because Excel always shows one and the editor opens on a sheet it shows. A tab colour is the sheet's `color`.

## An xlsx chart comes in over the cells Excel draws it over

A chart Excel anchors on a worksheet comes in as a sheet chart ([SHEETS.md](SHEETS.md#a-chart-is-a-floating-record-whose-refs-name-sheets-by-id)) through `readChart` (`ooxml/ooxml-chart.ts`), a column, bar, line or pie chart, a 3-D one drawn flat, in the theme's colours. `placeDrawings` (`import/sheets/drawing.ts`) reads the sheet's drawing part once every sheet has its id, because a chart's refs may name any sheet. A ref names its sheet by the name the workbook writes, lower-cased as Excel compares names, the first sheet of a name winning, and becomes a ref by that sheet's id. Ranges come first, as Google Sheets saves a chart's caches empty. A ref ranges can't hold, a literal, a defined name, several areas, an area, or a sheet the workbook doesn't have, as an external workbook's, brings the whole chart in from its caches as inline data, which shows the file's numbers and follows no cell. A pie over more cells than a chart draws slices for reads its caches, as a ref it can't follow does, and is left out and counted only when they hold too many points too.

A two-cell anchor spans the same cells as in Excel, between its corners whichever comes first: each corner is its cell's place, walked through the sheet's own widths and heights with an unsized track at the sheet's default, plus its offset into the cell. The walk is `sheetColumnsWidth` and `sheetRowsHeight` (`packages/lib/src/sheets/defaults.ts`), the one the HTML and PDF export draw the overlay with, so an export puts the chart over the same cells. A one-cell anchor takes its size from its `xdr:ext`, and an absolute one its place too. The box is stored through `sheetFloatingBox`, the clamp every sheet writer uses, at angle 0, since the reader takes no rotation from the anchor. An `mc:AlternateContent` reads the branch in the drawing's vocabulary, so Excel 2016's charts (waterfall, funnel), whose choice is a `cx:chart`, fall back to their shape. Shapes in the drawing are not read; pictures are ([§ An xlsx picture comes in as a sheet image](#an-xlsx-picture-comes-in-as-a-sheet-image)).

A chart sheet is a sheet of its own, in its place among the tabs, with its name, hidden state and tab colour and no cells: the reader reads it as a worksheet without a grid. Its chart sits at the top left at its anchor's `xdr:ext`, or 977 × 638 px, Excel's chart sheet on its default page, when the anchor names no size. A chart sheet whose chart can't come in is an empty tab, so a workbook of chart sheets only still imports.

A chart part is read once however many anchors name it. Every chart placed is charged its part's `chartCost` and the tracks walked to place it against `MAX_XLSX_ELEMENTS`, since `readChart` builds every point a cache declares, and its spec's text against `MAX_TEXT`. Charts are placed after every grid is read, so a chart past the element budget is left out rather than refusing the workbook. A chart left out, one the reader can't draw, a part missing or damaged, one past the budget, or an Excel 2016 chart, counts toward a `charts-dropped` warning, and a conditional format the engine has no rule for, such as an icon set, or one over no range of the grid, toward `conditional-formats-dropped`.

## An xlsx picture is anchored as Excel places a turned one

`drawingOf` (`export/sheets/xlsx/drawing.ts`) writes each image as an `xdr:pic` in a two-cell anchor over the cells its box covers, the anchor a chart takes, so a picture and a chart stack in Excel as in the editor. The picture is the Office media prep's PNG or JPEG under `xl/media/`, an SVG beside its PNG as the `svgBlip`, one file however many sheets show it. A picture whose media the prep has none for, a missing file or a type sharp can't read, is left out and counted as `images-dropped`. Excel turns a picture, so `a:xfrm rot` carries the image's angle, clockwise as Eigen turns it, while a chart goes upright.

Excel and LibreOffice place a picture turned within 45° of a quarter turn (45° to 135°, 225° to 315°) by its box turned that quarter: the anchor and the `a:xfrm` hold the box with its sides swapped about its centre. Written unswapped, LibreOffice squeezes the turned picture into the upright box. `anchoredBox` (`ooxml/drawingml.ts`) is that swap, its own inverse, so the writer and the reader share it. A sideways box that would start left of A1 or above row 1 is moved onto the grid, since an anchor can't start before it.

## An xlsx picture comes in as a sheet image

`placeDrawings` (`import/sheets/drawing.ts`) reads a worksheet's `xdr:pic` anchors beside its charts, in file order, so one fractional paint index orders both. A two-cell, one-cell or absolute anchor gives the box as it gives a chart's, an `mc:AlternateContent` reads its branch in the drawing's vocabulary, and `a:xfrm rot` the angle, a sideways one turned back from its anchor through `anchoredBox`. An image's id is a fresh uuid, as the editor's are, so an insert beside the workbook's own images never collides.

The picture's part is its `svgBlip`'s, else its `a:blip`'s, read raw and never parsed. `pictureMediaPart` and `importMedia` (`import/image-types.ts`) are the pptx reader's rules, shared: only PNG, JPEG, GIF and SVG come in, since no browser or sharp draws EMF, WMF or TIFF, and each part is one media file named per import, as a docx's is. A picture of another type, a part that isn't there, one past `MAX_MEDIA_PARTS` (1,000) or past the upload cap in bytes, is left out and counted as `images-dropped`, as a chart past its budget is, rather than refusing the workbook. The anchor's tracks are charged against `MAX_XLSX_ELEMENTS` as a chart's are. The bytes cross back beside the snapshot, and the main thread writes them through Drive before the snapshot that names them, under the owner's quota, as a pptx import does. A picture in a group, a crop and a flip are not read.

## A docx import replaces the document

`readDocx` (`apps/api/src/lib/import/doc/from-docx.ts`) reads the WordprocessingML straight into a doc of the schema, with no HTML between, in the transform process; `docxToPmJson` gives the same doc as JSON, for the audit and the tests. An HTML converter between the file and the schema loses most of what Word shows (alignment, color, fonts, list numbers, image widths) and needs a sanitizer after it; reading the XML into the schema keeps the looks and leaves nothing to sanitize. The reader resolves styles through their chain and runs Word's list counters in document order, so a list keeps the numbers Word draws. A property Eigen has no home for (a paragraph's shading) leaves its text and drops its look, and light text on it takes the body color, or it would vanish on Eigen's paper: the gaps are a [ROADMAP](ROADMAP.md) row. Word comments are not read, and their text stays. Tracked changes come in accepted. The reader also recognises the writer's looks (`document/looks.ts`, which both share), so an export that Google Docs re-saved, which flattens Eigen's styles into direct formatting, still comes back with its quotes, code blocks, captions and done tasks. Heading 5 and 6 draw Google Docs' grey, and 6 its italic, so the reader drops that grey from their runs, as it drops a quote's. Word's Title and Subtitle styles, a name Word, LibreOffice and Google Docs share, become the title and the subtitle, which the writer writes in those built-in styles. The node draws their size, and the subtitle its grey, which the reader drops; a style's bold or italic stays a mark, as the title and subtitle draw neither. An italic mark in Heading 6 draws upright, as in Google Docs and Word, so the writer writes it as `<w:i w:val="0"/>` and the reader makes a run Word draws upright there the mark, and one Word draws italic plain text. Word's own Heading 6 style is not italic, so its plain runs come in as the mark. A Word page break splits its paragraph on the way in ([DOCS.md](DOCS.md#a-word-page-break-splits-its-paragraph-on-import)). Word's math comes in as equations: each `m:oMath` is an `equation` node holding `writeMathml(readOmml(…))` where it stands among the runs, and each `m:oMath` of an `m:oMathPara` a displayed one; an equation past a bound of the package comes in as the text of its `m:t`, Word's neighbouring runs one word and each object a word of its own, as Word cuts runs by style, and one in a code block or a caption is its linear text there, `readStoredEquation`'s `text`.

Word's notes come in as footnotes ([DOCS.md](DOCS.md#a-footnote-is-an-inline-node-that-holds-its-notes-paragraphs)): each `w:footnoteReference` becomes a `footnote` node holding its note's paragraphs, read where the reference stands (`readNote`, `import/doc/paragraphs.ts`) through the notes part's own relationships, as a band's are, so a link or an image in a note resolves. An endnote is a footnote too, numbered among them in document order, as Google Docs has no endnotes. The separators and the continuation notice no reference names are no notes, Word's number at the note and the space or tab after it go, and a note's heading, list, table or code comes in as its paragraphs, as the node holds paragraphs only. A note's paragraph draws in its style's look, as a heading does in its own, so Word's FootnoteText, 10 pt and single spaced, gives its runs no size mark and its paragraphs no format. A custom mark (`w:customMarkFollows`) drops the text it draws, a `*` say, the run's text up to a tab: Eigen numbers every note, so the reference shows its number. A reference to a note the file lacks keeps its text. A note is read once per depth however often it is referenced, in the body or in another note, and each reference holds a copy, charged past the first as the pieces no tag counts are (`chargePiece`), so 1,000 references in a note to a 1,000-paragraph note are a 413 in milliseconds. A note referenced inside a note is its text there (`flattenNestedFootnotes`), read at most two deep, so a note's text is the same whichever reference reads it first, and a reference back to a note being read goes. A note's numbered list, and a band's, counts on its own, as Eigen numbers them, so neither continues the body's count.

The JSON is checked against the schema block by block. A block the schema refuses keeps its text and equations as paragraphs, so a reader slip never fails an import.

The doc's page is the body's last `w:sectPr`, Word's document-level section, its size and margins read through `readPageSetup`, so a hostile `w:pgSz` clamps as a peer's write does. A size the section leaves out is the default A4, a margin Word's 1 in, so the page and the anchors placed in its column match what Word draws. A doc has one page, so an earlier section with another size or margins is dropped with a warning. A wrapped picture goes left or right by which half of the column its middle sits in, and Word gives its offset from the area `wp:positionH`'s `relativeFrom` names: the paper's edge for `page` and the left or inside margin, the column's end for the right or outside margin, and the column for the margin, the column and a character. A third of the corpus's anchored pictures are page- or margin-relative, and an offset from the paper's edge read from the column's would put a picture in a wide left margin on the right. The offset is kept on the paper first, so a hostile one decides nothing past its edge. The vertical position is not read: a figure stores no place on the page. `w:orient` is not read: Word draws the page `w` by `h` whatever it says. Images and tables import no wider than that page's text column.

The header and footer are the final section's: its default parts, and page 1's when the section has `w:titlePg`, which turns Different first page on. Its `w:pgMar` `w:header` and `w:footer` are the page's distances, read through `readPageSetup` and so held within the margins, and Word's 1.27 cm where it names none. A reference a section leaves out is the one an earlier section named, as Word inherits it. Each part is charged against the package's parse budget and read as the body is, through its own relationships, so a header's logo resolves. A doc has one header, so even pages' bands, which Word draws only with `w:evenAndOddHeaders` on, are dropped with a warning. A reference counts only through a header's or a footer's relationship. A band isn't paged, as a note isn't, so a page break in it goes; a space after on its last block goes, as a band's last block draws none; an anchored picture in it is a block figure, as a band holds no float, with a warning; and a node a band's schema leaves out is its text, with the body's flattening warning. What would cover or swamp the page drops, with a warning of its own: a picture anchored behind the text (`behindDoc`, a full-page letterhead or a background) and a VML picture, Word's picture watermark, which as block figures pushed whole pages of body away, and Word's text watermark, a VML shape whose text is its path. A band part that is missing or damaged is dropped with the same warning. A note reference in a band drops too, as a band's schema holds no note. `PAGE`, `NUMPAGES` and `SECTIONPAGES` fields, complex or simple and whatever their switches, become the page number node, `SECTIONPAGES` the page count, as a doc is one section, in the body too, and their cached digits go. The bands are weighed with the body, checked block by block as it is, and ride in the update in their own roots, each as its editor leaves it on open.

`commitEigendocImport` (`document/doc.ts`) clears the body and the header and footer fragments, applies the update and sets every page key and every key of the Normal in one transaction, so an import replaces rather than appends and leaves no header, page or Normal of the doc before it. The page and style keys are set on the live doc, never in the update: a key the transform's own doc sets is concurrent with the live one, and Yjs keeps whichever client id orders last.

Each image part becomes one media file through `importMedia` (`import/image-types.ts`), as a deck's and a workbook's pictures do: named `docx-<uuid>-image-1.png`, `docx-<uuid>-image-2.wmf`, … in the order met, the prefix drawn once per import, its extension from the part's content type, its bytes read when it is first named. A docx keeps every image type `IMAGE_EXTENSION_BY_MIME` (`ooxml/drawingml.ts`) names, where a slide and a sheet keep only those they draw, so a part declared as anything else never reaches the container. A part that isn't there is no picture. One whose bytes don't read, one past `MAX_MEDIA_PARTS` (1,000) or past the upload cap in bytes, which the job carries as `maxMediaBytes`, is left out and counted as `images-dropped`, as in a workbook, rather than refusing the document. WMF, EMF and BMP are kept under their own name though sharp reads none of them (`UNSHOWN_IMAGE_TYPES`). A browser draws a BMP, but the editor and quick look load every image through its sharp preview (`/file/:pathId/preview`), so all three show as a broken image with its alt text, which the user can delete, and the HTML, PDF and docx exports, which re-encode through sharp too, leave the picture out and keep its caption. The images are written through Drive as an upload is, with its write check, drive event and thumbnail, and before the update that names them: an open tab looks each name up once, as the update arrives. The images count toward the mount's quota at their inflated size, which the upload cap bounds: `saveDocImages` charges their total through `enforceMountQuota` before the first is written, a repeat import in full, as it overwrites nothing, and a conversion checks before it creates the document, so a 507 leaves nothing behind. A linked picture lives outside the file, so only its alt text comes in. A SmartArt graphic keeps its text, one paragraph per shape.

A chart comes in as a docs `chart` node through `readChart` (`ooxml/ooxml-chart.ts`), from the values the file caches, as a pptx's does: a column, bar, line or pie chart, a 3-D one drawn flat, its series in the theme's colours, or the chart's own where its `c:clrMapOvr` overrides the map. It is placed as a picture is: its `wp:extent` in px (a chart in a group or a canvas takes its own frame's `a:ext`), shrunk to the text column and to `CHART_MAX_SIDE` keeping its shape, an anchored one wrapped or aligned by `anchorLayout`, an inline one aligned by its paragraph, and a caption taken by the same rules, since the reader tests for either frame node (`isFigureFrameNode`). A chart the spec can't draw as Word does is a paragraph in its place with Slides' words for it, its kind and its title (`droppedChart`: "Scatter chart not imported"), and so is a missing or damaged part, as "Chart not imported". A part is read once however many drawings name it, and its elements and the points its caches declare (`chartCost`) are charged once against `MAX_DOCX_CHART_WORK` (`import/doc/package.ts`), because `readChart` builds every point a cache declares before the spec refuses them; a chart past it is the plain "Chart not imported", which costs only that chart. A band's schema holds no chart and Insert puts none in a note, so a chart in a header, a footer or a footnote, found and charged as the body's, keeps its title as text, the one `readChart` reads. Each chart that doesn't come in counts toward `charts-dropped`.

The import returns warnings beside the update: `blocks-flattened`, `images-unshown`, `images-dropped`, `graphics-dropped`, `charts-dropped`, `section-pages-dropped`, `even-bands-dropped`, `band-images-unanchored` and `band-content-dropped`, each with a count. The runner logs them on the job's line, and an Import… answers with their summary ([§ An Import… answers with what the file held that did not come over](#an-import-answers-with-what-the-file-held-that-did-not-come-over)).

A file the reader can't read is a 400 "Not a valid docx file", whether the zip is broken, the XML malformed or the reader slipped. An encrypted docx is an OLE file holding an `EncryptedPackage` stream, and gets its own 400, "This document is password-protected. Remove the password in Word and import it again." A cap is a 413 ([§ Zip guards](#zip-guards-run-before-the-parser-inflates-anything)).

## A docx paragraph keeps what it sets apart from its Normal

Most Word files set their body's line spacing and spacing in Normal: 583 files of the corpus have a 1.15 Normal, and Google Docs writes the same values again on every paragraph. Read as they stand, every paragraph would get a format and draw unlike typed text. So the reader takes the docx's Normal (docDefaults and the default paragraph style) as the doc's Normal (`createReader` in `import/doc/paragraphs.ts`): its font through the font map, its size, its before and after, and its `auto` line in that font's own line, single for any other rule. A paragraph (`readParagraph`) is compared with that Normal, and a heading, a title or a quote with its own style, whose look is the node's, and gets a value only where it differs; a run gets a font mark only for a font other than the Normal's, Inter included, and a size or colour mark only for one apart from the body's. A line spacing is an `auto` line as its multiple; `exact` and `atLeast` are heights in points, which read differently at each size, so they give none.

The writer writes the container's look as direct spacing: an item's and a quote's after, a table's margin on the block below it (or the larger margin of a list or quote the table ends, `BLOCK_MARGINS` in `looks.ts`, as a table holds no space after), no space above the first block. So the reader takes spacing only on a block outside any list, quote or cell. Under a table the editor adds a paragraph's space before, its own or the Normal's, which it draws as padding, to the table's margin, while a heading's style margin collapses with it to the larger; so the writer writes the two summed (`withBefore`) and the reader keeps only what passes the margin, and none where that is the style's or the Normal's (`formatOf` and `gapBelowTable` in `assemble.ts`). A quote placed into a list item has its lists renumbered by the numbered lists around the item, as a table's are (`numberWithin`), since each was read as a flow of its own. The writer also rescales the line of a paragraph all in one other family (`familyLine`), which the reader undoes with the same line heights, so an Eigen doc's paragraphs read back with no format. A paragraph a Word page break splits ([DOCS.md](DOCS.md#a-word-page-break-splits-its-paragraph-on-import)) keeps its space before on the first half and its space after on the last, where Word draws them. Indents are structure first: an indent nests a paragraph into a list item or a quote ([§ A docx import replaces the document](#a-docx-import-replaces-the-document)), so only the indent past the item's text is the paragraph's, an item's own indent holds its number, and a quote's paragraph keeps none. Every value is bounded through `readParagraphFormat`, as a peer's is.

## An imported doc is stored as the editor leaves it on open

The editor repairs some content the moment it loads: prosemirror-tables pads a row short of its table's columns, and on the next pass gives the new cells their column's width, and StarterKit's TrailingNode appends an empty paragraph to a doc that ends in anything else. Each repair is a Yjs update nobody typed, and two people opening a fresh import together write it twice. So the reader writes well-formed tables (`import/doc/tables.ts`): a row Word draws short of the grid ends in a cell over the columns it misses, with their widths, and a merge stops where a row leaves it out, so `fixTables` finds nothing to repair. A row stops at Word's 63 columns, its last cell holding the text of any past them: the widest row sets every row's width in the TableMap the editor builds for each table, and one row of 20,000 cells over 5,000 more cost 2.3 GB. A table that merges is split into tables of `MAX_MERGED_ROWS` (2,000) rows, a merge across the split starting again in the next: `findWidth`, under every TableMap, rescans the rows above each row after a rowspan, so 49,000 rows took 27 s to open, and a part now costs at most 0.9 s. Repairing them afterwards is no option on untrusted input: `fixTables`' transaction keeps a copy of the table for every repair, so 20,000 rows with one bad width each cost 3.4 GB and 6 s. `asOpened` (`import/doc/transform.ts`) is the safety net: it refuses a table whose repairs times rows pass `MAX_TABLE_REPAIRS` before any repair runs, runs `fixTables` once, refuses with a 413 a table a second pass would still repair (a repair can leave another, and the reader writes tables that need none), and ends the doc in a paragraph before `importDocxToEigendocUpdate` encodes the update. `apps/api/src/test/import/doc/tables.test.ts` expects `fixTables` to find nothing on ragged, colliding and mismatched tables, and `transform.test.ts` opens the stored doc with the editor's plugins and expects no change.

## A docx import is weighed by what it emits

The Yjs update costs memory per node and per mark, not per XML tag: 720,000 tags of marked tabs and breaks emit 3.6 million nodes and marks and cost 4.4 GB in the transform, which every import's limit has to hold. So after the reader walks the document and before anything is built from it, `sizeOf` (`import/doc/from-docx.ts`) counts each node and mark as one, a string attribute as one per 512 characters (the update spells a link's href out for every text node it marks) and every table's area, the slots its TableMap holds, as one per 64 (a slot costs about 16 bytes, which a span or a padded row fills at no node's cost). The same pass counts the text's characters and every string attribute's: one `w:t` compresses a gigabyte into a small upload, a link's href is spelled out again for every text node it marks, and the update holds every character, which a client opens in one WebSocket message of at most 128 MB. Past `MAX_DOCX_WEIGHT`, or past `MAX_DOCX_TEXT` characters (16 million, the corpus's most 511,898), the import is 413 "This document is too large to import". An equation's MathML is charged at the same rate as the reader writes it (`chargeMathml`, `import/doc/package.ts`), not at the weigh: a space in `m:t` writes 26 characters of MathML, so a 22 KB upload of spaces in equations would hold 400M characters by the time the weigh refuses it. The parse itself, which the weighing comes too late for, has the package's XML budget.

## A pptx import adds slides and leaves a box where it can't draw

`readPptx` (`apps/api/src/lib/import/slides/from-pptx.ts`) reads the PresentationML into the canvas's own elements in the transform process, and `importPptxToSlidesUpdate` (`import/slides/transform.ts`) encodes them as a Yjs update of frames and elements. One slide is one frame. A Convert makes the deck in the slide size nearest the file's `p:sldSz`, `SLIDE_SIZES[nearestSlideSize(cx, cy)]` (`packages/lib/src/vector/frames.ts`), and the update's `meta.slideSize` says which, so a 4:3 file makes a 4:3 deck and a 16:10 or A4 one is letterboxed, centred, into the nearer size. The update's `meta.slideWidth` is the width that keeps the file's pt per px: the file's own width when its shape matches, and wider when it is letterboxed between bands at the sides. That width is held to the 128 to 4032 pt a deck may have, and the shapes take the held width's pt per px, so a pt stays a pt: a slide over 42 in tall overhangs its 4:3 frame top and bottom, and a slide under an inch tall sits inside its frame. An insert passes the open deck's page, read from its `meta` with `readSlidePage`, and a file of another size is letterboxed into it, its text scaling with its shapes; the deck's `meta` stays as it was. A replace passes none, as a Convert does. Either way a text size is snapped to the half points of the deck's pt (`snapSlideFontSize`), so a 44 pt title reads 44 pt and not 44.000000001. A Convert and a replace write the update with `replaceSlidesInYjs`, its `meta` included; an insert writes it after the slide the user is on with `insertSlidesIntoYjs`, under fresh ids, so nothing in the open deck is rewritten and its undo and comments stay valid ([SLIDES.md](SLIDES.md#the-deck-writer-inserts-under-fresh-ids-and-only-a-replace-clears-the-deck)). Hidden slides come in too; speaker notes do not.

What the canvas has a kind for comes in as that kind: a rectangle, rounded rectangle, ellipse, diamond and pie, a straight line or connector (an arrow where it has a head), a PNG, JPEG, GIF or SVG picture, and each text body as a rich text box with its runs' fonts, sizes and colors. A layout's and master's shapes are copied beneath every slide that shows them, and groups are flattened. Any other shape comes in as editable paths ([§ A shape no kind draws is a path](#a-shape-no-kind-draws-is-a-path-from-its-drawingml-geometry)). A chart comes in as an Eigen chart through `readChart` (`ooxml/ooxml-chart.ts`), from the values the file caches: a column, bar, line or pie chart, a 3-D one drawn flat, with its series colours through the slide's colour map, or the chart's own where it overrides that, and its text in the chart's own text colour or else that map's text colour, so it reads on a dark theme. A chart the spec can't draw as the file does (area, scatter, doughnut, radar, bubble, stock, surface, pie of pie, a combo, a stacked line, a secondary, log or reversed value axis) leaves a box naming its kind as PowerPoint's Insert Chart does (`readChart`'s name) and its title. A chart the reader's work budget can no longer cover leaves the plain "Chart not imported" box, which costs only that graphic. A table, SmartArt graphic, embedded object or unreadable picture leaves a box saying what was there too, at its place, so the slide shows the gap instead of hiding it. Every box is see-through, a dashed outline and its label in the slide's text colour, so a title it overlaps stays readable. A pattern fill becomes its foreground color, a gradient keeps its first and last stop, and a picture fill on a shape is left out. These gaps are [ROADMAP](ROADMAP.md) rows.

Each loss is counted once per source shape, so a master's background is one loss however many slides show it, and the Import… summary counts them ([§ An Import… answers with what the file held that did not come over](#an-import-answers-with-what-the-file-held-that-did-not-come-over)). A file with no slides converts to a deck with none, which the Slides editor seeds on first open as it does a new one; An Import… of such a file writes nothing and answers "This presentation has no slides".

The pictures are named with a random prefix per import, so a second import of the same file into one deck overwrites none of the first's. An Import that fails after its pictures are saved, a revoked write or a closed tab, leaves them in the deck's media folder, counted against quota, as Eigen keeps a document's unused media. Untrusted bytes are bounded as for a docx: the reader parses only the presentation, slides, layouts, masters, themes, their relationships and the content types, never notes, diagrams or embeddings, and a chart's part reached only by a chart relationship under `ppt/charts/`, never its own relationships, each part it parses spending the package's one parse budget (`openPackage`, [DOCUMENT-TRANSFORMS.md](DOCUMENT-TRANSFORMS.md#a-packages-parts-have-a-parse-budget-before-the-memory-limit)), and caps the slides, the elements, the reader's work (one budget over the children it scans, the colours it resolves, the text it reads, the shapes it walks, each geometry's guides, commands, arcs, nesting outlines and simplifying passes, and each chart part's elements and the points its caches declare, for every colour map it is painted with), the pictures (by count, and by bytes at the upload cap the job carries) and the update's weight. Past a cap the import is a 413 "This presentation is too large to import". The caps live in `import/slides/`. A macro deck, template or slideshow saved under `.pptx` is refused by its content type with a message to save it as a `.pptx`.

## A shape no kind draws is a path from its DrawingML geometry

A pptx shape's outline is a preset, one of ECMA-376's 187 named shapes with adjust values, or a `custGeom`, its own path list, both written in DrawingML's guide formulas. The few presets a canvas kind draws, rectangle, rounded rectangle, ellipse, diamond and their flowchart twins, come in as that kind (`PRESET_KINDS`, `import/slides/preset-geometry.ts`), so they keep their corners and binding; a pie keeps its angles. Every other shape becomes canvas paths ([CANVAS.md](CANVAS.md#a-path-is-stored-in-its-unit-box)) at the shape's box, so a star, a block arrow, a map outline or a freeform drawing stays editable and recolorable. `customGeometry` (`custom-geometry.ts`) turns a `custGeom`, and `presetGeometry` a preset through its definition in Ecma's `presetShapeDefinitions.xml`, committed unchanged beside them with its NOTICE, into one path per way the geometry paints. `guides.ts` evaluates the formulas without `eval`, every result finite. The file is the spec's own, read once per process, so every preset draws as the spec defines it; upArrow, which the file lacks, is a named override in code.

The paths follow how PowerPoint and LibreOffice paint them. A shading path (`darken`, `lighten` and their `Less` forms, a can's top or a cube's side) fills in the shape's fill blended toward black or white, by LibreOffice's fractions. A filled path left open fills as if closed and strokes open, so it becomes a closed fill and an open line. Each subpath winds by how deep it nests among its path's others, so a contour inside another is a hole, as LibreOffice's even-odd fill draws it, on the canvas's nonzero fill and under its even-odd hatch alike. Its depth is found from a point on its first segment's curve, tested against the others' outlines, each curve cut into chords within 0.1% of the box, so a thin ring such as a donut's is still a hole: a chord's middle lies inside its curve, and ends and middles alone make a circle an octagon 7.6% inside it. Filled paths painting alike become one path element only while their boxes don't overlap: the export writes an element as one `a:path`, which LibreOffice fills even-odd, so a firewall's bricks concatenated onto its wall would come back as holes. Overlapping ones are elements of their own at the shape's box, in the file's order; a shape is 32 geometries at most, so 64 path elements at most with an open fill's line apart: past them an alike path concatenates overlapping or not, and one painting a new way leaves the shape only its text, counted as simplified. A flipped shape's points are mirrored across its box as they are read, before the caps measure the path, since a path, unlike a picture, can carry its mirror. The shape's text sits on top in a transparent box. One conversion is kept per geometry and size, so a layout's shape converts once for every slide that shows it.

A geometry past the canvas's path caps is simplified, dropping each point that lies within 0.1 to 0.4% of the box of the line its neighbours draw, and past them still, or past the reader's work budget, the shape keeps only its text and counts as simplified. Each stage, the arcs, the nesting and each simplifying pass, asks the budget before it begins, so a geometry it can't cover costs the deck nothing more. An open path's arrowheads, a bent or curved connector's, an arc's or an open freeform's, are lost and counted, since a path draws none; PowerPoint draws none on a closed one. Shadows, glows and 3-D are dropped as on every shape.
