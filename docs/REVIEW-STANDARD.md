# Review Standard

The bar every reviewer is held to, whether a subagent, an external LLM or a developer driving one. The goal is code that is clean, simple, stable and easy to read, and indistinguishable from the code around it in patterns, naming, comment density, how solutions are built and how the UX behaves.

- **Brief reviewers cold and unopinionated.** A reviewer reads [CODE-STANDARDS.md](CODE-STANDARDS.md) itself and judges against the written standards, not taste; an external, non-Claude reviewer reads [AGENTS.md](../AGENTS.md) too. Give it the task and the files, never the author's story of what was "addressed" or "accepted", and never tell it what not to flag; adjudicate its findings afterwards.
- **Clean is a result.** A review that finds nothing real says so plainly; that is as useful as a finding, and a reviewer never invents or inflates one to show work.
- **Review the blast radius, not the diff.** Trace the changed behavior through code the diff did not touch: other apps' entry points, SSE handlers, callers and callees of every changed function, the deploy files. Most escaped bugs live there.
- **Hunt absences, not only mistakes.** For every new seam ask: every cache, who invalidates it (SSE included)? every route, what validates and bounds its input, before which side effects? every fan-out or loop, what bounds it? every check-then-act, what closes the race? every path from user data, what contains it? every "fixed" bug class, are ALL its instances fixed? every promise in the docs, which code keeps it?
- **A page looks like its siblings.** Compare a new or changed screen with the screens beside it, by screenshot as well as code: the same section structure (a separator between sections, a header with its count and its action on the right, the same empty state), the same row and chip components, spacing and labels. Admin's team and user detail, or Mail's and Contacts' lists, read as one design. A difference needs a reason, and the reviewer names the side that moves.
- **The better design wins.** When two domains solve one problem differently, the review names which side moves: the worse one, even when it is the older, shipped code. A small fix to the older domain joins the same change.
- **A ruling is not an axiom.** A cleaner design found later replaces an earlier ruling, the owner's included, recorded with the evidence.
- **An audit finding is a lead, not a confirmed bug.** Check the design intent in the docs and tests before acting on it.
- **A patch is a finding.** A case covered with a special case, a second code path, a flag, a cache, a retry or in-memory state is reported as such, with the fix at the cause or the feature to drop ([CODE-STANDARDS.md § Code Philosophy](CODE-STANDARDS.md#code-philosophy)). The third fix on one mechanism within a week is a stop: before a fourth, name the shape of the pile and fix that. The shapes recur: a step that runs before the fact it needs is written, a second copy of the truth, a predicted cost where a cap would do, precision for a rare race, two paths for one job, code for an older build's data, a check on what our own typed code produced, scaffolding left after its job.
- **A rare edge case is not a bug by itself.** It is a must-fix only when it can crash or block the server, lose or corrupt stored data, or leak access; otherwise say how rare it is and what the user sees, and the default is to accept it.
- **Every touched file comes out better.** Fix broken windows, remove dead code and duplication, use the shared components and helpers ([SHARED-PRIMITIVES.md](SHARED-PRIMITIVES.md)) over hand-rolled logic, no over-engineering. Types come from `packages/lib/src/types/[domain].ts` (the leaves `@workspace/math` and `@workspace/formula` own their own), never redefined or declared at the wrong layer.
- **Signal over volume, both ways.** Report only real findings, each tried against a refutation first. But before merge run one recall-biased pass with the *Hunt absences* checklist over the whole branch: a cold reviewer that over-reports and gets pruned beats a polite one that misses, because what escapes per-unit reviews is mostly absences, half-fixed classes and bugs outside the blast radius.
