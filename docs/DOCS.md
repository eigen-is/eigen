# Docs

> **TLDR:** Docs is Eigen's word processor: rich text on a page that several people edit at once. A doc is a `.eigendoc` collab document whose truth is ProseMirror content held in a Yjs fragment, and one schema defines that content for the editor and for every server renderer. The schema is `packages/lib/src/docs/eigendoc/`, and the editor is `apps/docs/src/components/docs/`.

The editor is TipTap, a React wrapper around ProseMirror, the editing toolkit that models a document as a tree of nodes (paragraphs, a title and subtitle, headings, lists, tables, task lists, code blocks, images, charts, equations, page breaks, page numbers, footnotes) carrying marks (bold, color, font and size, comment). An image is a `figure` node, a chart a `chart` node in the same frame, and an equation an `equation` node. The app around it is a Drive-style file list plus one editor route, `/doc/$ownerId/$mountId/$pathId`.

On disk a doc is a container, a Drive folder named like a file (`Notes.eigendoc`), like every collab document ([COLLAB.md](COLLAB.md)). Its `data.db` holds the Yjs state, and the truth inside it is the `XmlFragment` named `default`, which y-prosemirror (the Yjs binding for ProseMirror) keeps in step with the editor. Beside it sit the page map, the style map holding the doc's Normal text and the header's and footer's own fragments. The same container holds the doc's images in `media/`, its comment threads in `chat/` and `comments.db` ([COMMENTS.md](COMMENTS.md)), and its version history.

The server never runs the editor, yet it renders the doc for the drive preview, the export formats and the search index, and writes it on a docx import. It reads the fragment as ProseMirror JSON (`readEigendocFromDoc`, [DOCUMENT-CONTENT-LAYER.md](DOCUMENT-CONTENT-LAYER.md)) and renders it with the same schema the editor uses. That shared schema is the one idea the app rests on: what the editor can write, the server can read.

The goal is parity with Word and Google Docs. A property the schema can't hold is a candidate to add to it, never something to flatten for good: the schema change is still asked, and before 1.0 it needs no migration path.

A figure names its image, and never holds bytes or a URL. The name is a file in the container's `media/` folder, resolved to a URL at render ([MEDIA-REFERENCES.md](MEDIA-REFERENCES.md)). A pending name, `pending:<uuid>`, stands in for an image whose upload has not landed yet. A panel is one of the right-side panes: comments, activity, and the figure, chart, table and equation properties.

The sections cover the schema, the title and subtitle, figures, the page, headers and footers, page numbers, footnotes, the open note, the panels, the menus, page breaks, equations, comments, the clipboard, what keeps content inside the page, table columns, fonts, sizes and caps, a paragraph's spacing and indents, list numbering, and word count. Four things in them surprise people:

- The side panels overlay the page instead of taking room from it, and the page slides and scales to stay clear ([§ The page keeps its width](#the-page-keeps-its-width-and-slides-then-scales-clear-of-a-panel)).
- A figure stores its width in the page's own pixels, so the on-screen scale never leaks into the document ([§ A figure stores a name and a width](#a-figure-stores-a-media-name-and-a-width-in-page-pixels)).
- Undo reverts only this tab's edits ([§ Undo is the Yjs binding's](#undo-is-the-yjs-bindings-and-reverts-only-this-tabs-edits)).
- A tab left open across a deploy that adds a node deletes that node for everyone ([§ A tab older than the schema](#a-tab-older-than-the-schema-deletes-the-nodes-it-does-not-know)).

## One schema serves the editor and every server renderer

`getDocExtensions` (`packages/lib/src/docs/eigendoc/extensions.ts`) is the schema. The server builds it once, on first use, in `apps/api/src/lib/document/doc-schema.ts`, and the drive preview (`apps/api/src/lib/preview/eigendoc-render.ts`) and the export (`apps/api/src/lib/export/doc/transform.ts`) render through one helper over it, `renderDocHtml` (`export/doc/render.ts`). The docx import (`apps/api/src/lib/import/doc/from-docx.ts`) checks what it reads against the same schema, `docSchema()`, as do the test fixtures. So a node the editor writes is a node the server can parse and render. A node only one side knew would vanish from every preview and export.

The editor leaves out the schema's `figure`, `chart` and `comment` and adds `Figure`, `Chart` and `CommentMark` (`apps/docs/src/components/docs/extensions/`), which extend the lib nodes with the node view and the click, menu and decoration behavior. It also swaps the schema's `table` for the same node configured to resize its columns ([§ A table column resizes by its border](#a-table-column-resizes-by-its-border-with-a-mouse-only)). The stored shape stays the lib's, because an extension adds behavior, not attributes.

The values and readers a page outside the editor draws a doc with live apart from the extensions under `nodes/`: `page.ts`, `normal-style.ts`, `paragraph-format.ts` and `bands.ts`. A top-level `Extension.create` or `Node.create` is a call the bundler keeps with its module, so one beside a reader the file preview imports put all of TipTap in the first load of Mail, Chat, Drive and Calendar.

The code block exists only when the caller passes `lowlight`, the syntax highlighter. The server's schema passes the backend's one (`apps/api/src/lib/document/lowlight.ts`), so the docx import reads a code block's language back only when lowlight knows it, and the docx writer writes only such a language. A test fixture that writes a stored doc's code block takes `docSchema()` for the same reason.

## A tab older than the schema deletes the nodes it does not know

The Yjs binding (`createNodeFromYElement` in `@tiptap/y-tiptap`) deletes any fragment element the tab's schema cannot build, and the delete syncs to everyone. So a tab left open across a deploy that adds a node deletes every instance of that node it receives, which is accepted before 1.0 under [ROADMAP.md](ROADMAP.md)'s no-backward-compatibility rule.

## Undo is the Yjs binding's and reverts only this tab's edits

The schema turns TipTap's own undo off (`undoRedo: false`), and y-prosemirror's undo plugin takes its place. It tracks only the changes this tab made, so ⌘Z never takes back a collaborator's typing. The toolbar reads its undo and redo state from that plugin (`yUndoPluginKey`).

The editor builds the plugin's `Y.UndoManager` itself (`createDocUndoManager`), over the `default` fragment, the page map and the style map, so ⌘Z also takes back a page setup change and an update of Normal text. The plugin applies its defaults (the binding's tracked origin, the delete filter that keeps a paragraph holding text when its insert is undone, `addToHistory: false` skipping capture) only to a manager it builds, so `createDocUndoManager` copies them. A page or Normal change is no editor transaction, so the toolbar's undo state catches up through the re-render the page change causes.

## A title and a subtitle are paragraphs marked by their type

Google Docs' and Word's Title and Subtitle are paragraph styles, so the schema's `title` and `subtitle` nodes (`packages/lib/src/docs/eigendoc/nodes/title.ts`) hold what a paragraph holds and render as `<p data-type="title">` and `<p data-type="subtitle">`. A `<p>` is how both write them in HTML, so the export, the search text and a paste into another app treat them as text. The `data-type` marks them rather than a class, because a web page's `p.title` would otherwise paste as a Title. A paste reads one only from the editor's own HTML, and from any other app it lands as the paragraph it was written as. Enter at the end of either starts Normal text, as at the end of a heading, because the schema's default block is the paragraph.

Their look is Google's: 26 pt for the title, 15 pt in the Heading 5 and 6 grey for the subtitle, both at the body's weight, set once in `eigen-prose.css`. The docx writer reads it from there into Word's built-in Title and Subtitle styles ([EXPORT.md](EXPORT.md#a-docs-docx-is-written-from-its-json-with-the-editors-css-values)). `PROSE_TEXTBLOCKS` (`@workspace/lib/docs/eigendoc`) names the textblocks that hold prose, which alignment and a paragraph's format apply to and which the server treats alike: the paragraph, the title, the subtitle and the heading. Format › Paragraph styles and the style picker list Title through Heading 6 from one table, `PARAGRAPH_STYLES` (`apps/docs/src/components/docs/paragraph-styles.ts`), in Google's order, through `paragraphStylesIn(schema)`, which keeps the styles the editor's schema holds: a band's lists no Title or Subtitle. Normal text is written by hand in each menu, and Quote in Format › Paragraph styles only, as neither is a style the picker lights from a node's type.

## A figure stores a media name and a width in page pixels

A figure is an inline, atomic node (`packages/lib/src/docs/eigendoc/nodes/figure.ts`): it sits in a paragraph, its contents are not editable, and it can be dragged. Its durable reference is `mediaName`. `src` is only for an external image, and the export strips that ([EXPORT.md](EXPORT.md#the-sanitizer-keeps-only-data-references-because-a-browser-fetches)). The other attributes are `alt`, `caption`, `alignment`, `layout` (block, wrapped left or right, or in front of or behind the text), `offsetX` and `offsetY` (a positioned figure's place in page px from its paragraph's padding box, kept while it is in the flow), `commentCardId` and `width`. The frame holds `layout` and the offsets, so a chart takes them too ([§ A figure in front of or behind the text](#a-figure-in-front-of-or-behind-the-text-sits-at-an-offset-from-its-paragraph)).

The browser starts a drag only from a press nobody prevented, selected figure included, so nothing on the figure itself prevents a press or takes focus from the editor. A drop that leaves the figure's own paragraph empty removes it (`figureDragOut` in the `Figure` extension). A cut keeps that empty paragraph, as Word and Google Docs do.

A figure stores its width and never its height, so the height always follows the image's own ratio. The width is in the page's layout pixels, measured with `clientWidth` on the page element, which a CSS `scale()` does not change. So a doc edited on a narrow, scaled-down page stores the same width as on a wide one, and a grip's drag divides the pointer's travel by the page's scale, measured as the grip is pressed. The node view (`apps/docs/src/components/docs/extensions/figure.tsx`) sets the width on the image's first load, capped at the text column (half of it for a wrapped image, the page map's paper for one in front of or behind the text), and a resize clamps between 100 px and that cap (`clampFigureWidth`, with the cap from `figureMaxWidth`). A switch to a wrap in the Image or Chart panel shrinks a wider figure to that half in the same write (`widthWithinLayout`), a chart keeping its shape, or nothing would wrap beside it. A layout or an alignment the renderers don't know, from a paste or a peer, parses as the default.

Shift and an arrow key resize a selected figure by 10 px, Right and Up wider, Left and Down narrower, with the same clamp. It is a keymap on the figure's node selection (`addKeyboardShortcuts` in the `Figure` extension), so the keys never leave the editor. Shift and an arrow would otherwise extend the selection, and on a text selection of the figure, the one Shift+ArrowRight from beside it makes, they still do. The Image panel's Width field writes through `updateFigure` with the same clamp too. It writes on Enter or a blur and drops its draft on Escape, unlike the canvas panels' `MergedNumberInput`, which writes on every keystroke and would snap a half-typed width to the 100 px floor. Docs shows and takes sizes in cm, never px: the field shows the width to 0.1 cm and a grip's readout on an image or a chart the size (`figureSize`, which `FigureFrame` hands `ObjectTransform`), and the Page setup dialog its margins to 0.01 cm, all through the one converter beside the page's unit math (`cmText`, `readCm`, `pxToMm`, `mmToPx` in `packages/lib/src/docs/eigendoc/page.ts`). Storage stays px, and the field writes only a changed value, so a stored 300 px, shown as 7.9 cm, doesn't become 298.6 px on a blur.

## A chart is a node of its own in the figure's frame

A chart is an inline atom like a figure (`packages/lib/src/docs/eigendoc/nodes/chart.ts`), and its data is a `ChartSpec` ([CHARTS.md](CHARTS.md)) stored as an attribute per part, `specChart` to `specData`, each JSON string kept as stored even when it doesn't parse. The Yjs binding writes only the attributes that changed and undoes them one by one, so a title in one tab and a series colour in another both stand, and ⌘Z of the title leaves the colour. The schema declares every part (`CHART_SPEC_PART_KEYS`) because a tab removes from a node it edits every attribute its schema lacks: a part added later would be lost on that chart's next edit in an older tab, so a later option nests inside a part instead ([CHARTS.md](CHARTS.md#a-stored-spec-grows-only-in-ways-an-older-build-keeps)). Its look (background and hatch, stroke, sketch, label color) is an attribute per field beside it, in a canvas chart's field names, unset reading as Google's flat look ([CHARTS.md](CHARTS.md#one-look-a-canvas-charts-own-fields-paints-a-chart-in-every-app)). It is a node of its own rather than a kind of figure, because every figure consumer reads a media name, and a chart has none. What the two share is the frame: the layout, alignment, caption and comment card attributes and their HTML (`nodes/figure-frame.ts`), and the node view's box, selection ring, grips, comment mark and caption (`FigureFrame` in `apps/docs/src/components/docs/extensions/figure-frame.tsx`).

A chart has no aspect ratio of its own, so it stores its height beside its width, both in page pixels, and a grip resizes it freely. Shift and an arrow resize an image, not a chart. Each side reads at most `CHART_MAX_SIDE`, 2112 px, Word's largest page of 22 inches, as no page's text area is larger: a peer or a pasted `span.chart` can set any size, and a side in the millions keeps the layout busy for seconds in every viewer and in the export. Insert › Chart places the sample chart at 600 × 371 px, shrunk to a narrower text column, flat with a random seed, and selects it, so its panel opens. The panel is the shared chart sections (`ChartSections`: the chart editor, then the look rows Labels, Fill, Stroke and Sketch), the figure's Layout rows and a caption. Every write goes through the doc's own undo manager as one step (`sealed`), and a title typed into the panel holds its step until the field is left (`holdCapture` on `PropertyGestureContext`). The caret stays in the field, out of the editor's keymap, so the panel hands ⌘Z and ⇧⌘Z to the doc's history (`PropertyHistoryContext`): the browser's own field undo would take a typed title back a character at a time, writing each one. The caption is a draft until the field is left, so ⌘Z in it is the field's own. Edit data, from the panel or a double-click, is the shared grid dialog, whose Save is one write.

Its HTML is `span.chart`, read ahead of the figure's `span.figure`, with the spec, size and look as data attributes and an `<img>` of the chart inside for an app that doesn't know the node. The parts are one JSON `data-chart` and the look one JSON `data-look`, each parsed once and only within the depth limit and a length bound, so a forged one pastes as the placeholder and stores nothing. The look's bound is the spec's byte limit. The parts' is twice it, since the attribute escapes every quote in their text again, and once parsed they are held to the byte limit itself, so a real chart near the limit still pastes. So a docs copy carries a chart through its own HTML back into Docs, and writes a chart item beside it for Sheets, Slides and Vector ([CLIPBOARD.md](CLIPBOARD.md#a-chart-travels-as-its-spec-with-the-numbers-inline)). A chart item from another app lands as a chart node at its copied size, a part a newer build added left out, as the schema has no attribute for it, capped at the text column with its shape kept, as a pasted `span.chart` is; a header, a footer and a footnote place none, as their Insert menus offer none. The HTML and PDF downloads and the preview draw it as inline SVG in the figure's `span.figure` instead, so its labels take the page's fonts. The docx writes it as a Word chart, with its caption, which a re-import reads back as the same chart and look ([CHARTS.md](CHARTS.md#a-chart-goes-to-office-as-a-cchartspace-that-reads-back-as-the-same-spec)). Search indexes its caption, titles, series and categories, and Word count only its caption, as for an image.

## The node view and the export draw one figure box

The editor, quick look and the HTML and PDF exports lay a doc out the same, block for block, and the docx writer takes its spacing from the same rules ([EXPORT.md](EXPORT.md#a-docs-docx-is-written-from-its-json-with-the-editors-css-values)). A figure gets that from one box: the `.figure` rules in `packages/ui/src/styles/eigen-prose.css`, which the node view's wrapper span and the export's `span.figure` both carry, with `data-layout` and `data-alignment`. A block figure is a full-width `inline-flex` at the bottom of its line, because the node is inline. A wrapped figure takes its float and its only margin from the same rules, and a chart's inline SVG its fit, never wider than the column with its height following, from `.figure svg`.

ProseMirror ends a textblock that is empty, or ends in a non-text node, with a `<br class="ProseMirror-trailingBreak">` (`addTextblockHacks` in prosemirror-view). It holds the caret: hidden, ArrowRight skips past the figure and typed text lands in the next block. So the box stays inline-level, a full-width box on the bottom of its line, and the break sits on the figure's line, where the caret expects it. The export writes the same `<br>` (`withTrailingBreaks` in `export/doc/render.ts`). A block-level wrapper would push the break onto a line of its own, an empty line under every figure. Because the box is the column's width, ProseMirror would take a click in the empty space beside the image as a click on the node and select it. So the `Figure` extension's `handleClickOn` puts the caret before the figure for a click left of the image, and after it for a click right of it. The image, its ring and its caption still select the node.

A list is its own formatting context (`ul, ol { display: flow-root }`), so beside a float it narrows as a whole and its markers sit clear of the float instead of under it. The context keeps its first and last items' margins in, where they collapsed with the list's own, so those go and a list and a nested one space as their margins say. These rules are Docs' own, under `.eigen-doc` (`DOC_PROSE_CLASS`), which the editor and its bands, quick look and the exports carry, and a mail or chat editor's prose doesn't, as Docs alone wraps figures. A list item that holds a wrapped figure is one too (`display: flow-root list-item`), so the next item starts below the float instead of drawing its number over it: the list's own context keeps its floats in, but lets them push its later items. WebKit reads no `flow-root list-item`, so it gets `contain: layout`. A task item keeps its flex, which contains a float already.

## A figure in front of or behind the text sits at an offset from its paragraph

The `front` and `behind` layouts take a figure or a chart out of the flow; the code calls such a figure positioned. It stays an inline atom in its paragraph, the anchor, and its box draws with `position: absolute` at `offsetX` and `offsetY` from the anchor's padding box, at `z-index: 1` over the text or `-1` under it. The rules live under `.eigen-doc` in `eigen-prose.css`, which gives every paragraph and heading `position: relative`. So the figure moves with its paragraph, as Word's Move with text does: text typed above pushes it down, and deleting the paragraph deletes it.

The offsets count from the padding box because it is the box CSS places an absolute child in. The paragraph's indent is its margin and its space before is its padding, so every renderer draws the figure with no indent math, and only the docx converts ([EXPORT.md](EXPORT.md#a-figure-in-front-of-or-behind-the-text-is-a-wrapnone-anchor-at-the-start-of-its-paragraph)). The cost: indenting the anchor, by Tab, the indent buttons or a list's nesting, moves the figure with it, where Word, counting from the text column, keeps it still ([ROADMAP.md](ROADMAP.md)).

`figureLayoutStyle` (`nodes/figure-frame.ts`) gives a positioned box its `left`, `top` and `width`, which the node view and the export's `renderFigureFrame` write inline. The width goes on the box, because an image's `max-width: 100%` inside an absolute box that shrinks to fit its content is cyclic. Within a layer, figures draw in document order: no stacking order is stored, so there is no Bring to front or Send to back ([ROADMAP.md](ROADMAP.md)). A positioned figure draws no caption, and the panels hide the field, though `caption` and `alignment` stay stored. The offsets stay stored when the figure goes back into the flow, so a switch back restores its place. An offset or a width reads within the largest paper (`MAX_PAPER_MM`), so a forged one can't stall the layout. Only Eigen's own `span.figure` parses as positioned: another app's `<figure>` or absolute `<img>` has no anchor to count from, so it pastes as a block.

The paragraph makes no stacking context, so both layers stack in the page's. The page is that context everywhere: the editor's page div and quick look's page carry `isolate`, and the export's `.page` carries `position: relative; z-index: 0`, as WeasyPrint ignores `isolation` ([EXPORT.md](EXPORT.md#a-figure-in-front-of-or-behind-the-text-prints-on-its-paragraphs-first-page)). A stacking context paints its own background below its negative layer, so a behind figure draws on the white paper at every scale. On `.ProseMirror` alone, a behind letterhead near the top would cover the header band's text in the editor but not on paper. Quick look's page also clips with `overflow: hidden`, so a box placed past the paper's edge is cut there.

After a change to the doc, `PositionedFigures` sets the body's `min-height` to reach the lowest positioned box (`growBody`), and again when an image loads, so the notes and the footer band draw below it. It reads layout, so it runs only while the plugin's state counts a positioned figure: a doc with none pays nothing.

## A positioned figure lives in the body only

A table cell, a note and a band hold no body paragraph to anchor on, and the PDF and the preview draw a note's paragraphs as spans, which hold no box. So a positioned figure there draws in line, as a block, in every editor and renderer. `PositionedFigures` resets one that lands in a table cell or a note in the body, and every one in a band's or a note's editor, to `block` (`BLOCK_ONLY_FIGURE_PARENTS`, and the extension's `blockOnly` option for a band's and a note's editor). It skips a viewer's tab, as `TableWidthClamp` does, since the server drops a viewer's writes, and a peer's transaction, which the peer's own tab resets. `renderDocHtml` draws one a forged doc holds there in line too (`withBodyOnlyPositions`, with a `band` option the export passes for a band part), and the docx writer writes it as a block. A note's Image panel and its Format › Image offer the layouts in the flow alone, and a band's offer none, as a band holds no float ([§ The properties panels follow the selection](#the-properties-panels-follow-the-selection-on-desktop-only)).

## The caret never rests before a positioned figure

A positioned figure draws elsewhere and takes no width on its line. Its `NodeViewWrapper` is the absolute box, and TipTap's own span around it stays in the flow as a zero-width inline at the line's start, which the caret beside it reads. ProseMirror still counts the atom as a position, so a caret before it would draw where the text starts, typed text would land before the atom, and ArrowLeft from after it would select an atom the user can't see. `PositionedFigures` (`apps/docs/src/components/docs/extensions/positioned-figure.ts`), which every docs editor registers, holds the rules:

- Positioned atoms lead their paragraph. An `appendTransaction` moves one found after other content to the end of the paragraph's leading run, as after a paste, a join or a drop, and the docx import places them first. It skips a peer's transaction and a viewer's tab, as the reset does.
- The caret rests after the run: an empty selection inside it moves past it. That spot is the paragraph's visual start.
- At the visual start, ArrowLeft goes to the end of the textblock above, and Backspace joins with it, as at a plain paragraph's start. Delete at the end of the textblock above joins forward. The join keeps each figure where it is drawn: its offsets are measured against the joined paragraph before the dispatch, and the join is one undo step. A join another way, a range delete or a paste, moves the run without measuring, so the figure jumps to the joined paragraph's top until it is dragged.
- Enter at the visual start splits before the run, so the empty paragraph goes above and the figure goes down with its text. Word does the same: splitting an anchor's paragraph attaches the anchor to the second paragraph. Enter anywhere else leaves the figure in the upper part.
- On a selected positioned figure, Escape and a plain arrow put the caret at its paragraph's visual start, Backspace and Delete delete it, and Shift and an arrow resize it, up to the paper.

A positioned figure is selected with the pointer or a finger only, and an arrow never nudges one, as a nudge on an atom the caret skips would trap the caret. Keyboard selection and nudging are a [ROADMAP.md](ROADMAP.md) row.

## A positioned figure moves by a pointer gesture, kept on the page map's paper

The browser's drag and drop moves an atom through the text, but a positioned figure's place is its offsets. So it moves by a pointer gesture on its node view instead (`startMove` in `FigureFrame`, `extensions/figure-frame.tsx`), with the browser's drag turned off. The gesture previews the offsets locally and commits once on pointer-up through `moveFigure`, the pointer's travel divided by the page's scale. A press on a front figure that isn't selected selects it, and the same gesture drags. A finger on one that isn't selected scrolls the page.

While a positioned figure is selected, its ring, grips, drag surface and comment mark draw in a sibling of the box, at the same place and `z-index: 2`, above both layers. The picture stays in its layer, and text over a behind figure never covers its grips. A behind figure under text is selected by a press where no line of its paragraph's text is: the paragraph's box lies over the whole figure, so a `mousedown` handler tests geometry, the elements under the pointer and the rects of the text's lines. Alt-click selects it over the text too. A phone has no Alt, so a behind figure fully under text can't be selected there.

The clamp reads the page map, never the screen (`offsetsOnPaper`). The anchor's place on the paper is the page map's margin plus its distance from the text column's edge, divided by the scale, and the box stays between the paper's edges and below the page's top. So a drag on a phone, whose page draws scaled, stores what a desktop would. A view without pages must keep that contract: stored offsets never depend on the screen, and such a view clamps the box into its column when it draws, writing nothing, so the stored place draws again with pages. The drop test in `positioned-figure.test.tsx` pins the clamp at the paper's edge with the column laid out at 360 px.

A drop re-anchors the figure on the body textblock under its box's top edge. A table, or a textblock that can't hold a figure such as a code block, keeps the current anchor. A new anchor is one transaction: it deletes the atom and inserts it at the end of the new paragraph's leading run, with offsets that keep it where it was dropped, its comment card kept and a node selection set on it, or the mapped selection would close the panel. A drop within its own paragraph writes the offsets alone, so it never moves the node. Two people who re-anchor the same figure at the same moment each delete and insert it, and Yjs keeps both inserts, so the doc holds it twice: a rare duplicate, accepted, with a [ROADMAP.md](ROADMAP.md) row. A west or north grip moves the offsets by the size change, so the opposite edge stays put (`useFigureResize` writes the size and the offsets in one commit).

A switch to front or behind, from the panel or Format › Image (`positionFigure`), writes the offsets that keep the figure where it is drawn and caps its width at the paper. It moves the atom to its paragraph's start only when it doesn't lead already, and then selects it again in the same transaction. A switch back into the flow moves nothing.

## An image renders from a pending name until its upload lands

An insert, a drop or a pasted image file writes the figure with the pending name `startUpload` returns, so the image shows on the next frame. When the upload settles, `swapFigureMediaName` rewrites every figure still holding that name to the real one, or removes the figure if the upload failed. A figure whose name never resolves shows `ImagePlaceholder`. The mechanics, and the sweep that clears a pending name a closed tab left behind, are in [MEDIA-REFERENCES.md](MEDIA-REFERENCES.md#a-new-upload-renders-from-a-pending-name).

A docx import (`apps/api/src/lib/import/import-document.ts`) saves every image to `media/` before it writes the update that names them. A tab looks up a name it lacks once (`useFolderLookup`, `packages/lib/src/core/drive/hooks/reads.ts`), as the update reaches it, and no event refetches the folder after that. So an image saved after the update spins until a reload, and on S3, where each save takes a round trip, it usually is.

## A doc stores its page in a page map beside its content

A doc's page size and margins live in the root `Y.Map` named `page` (`PAGE_ROOT`), one number in millimetres per key: `width`, `height`, `marginTop`, `marginRight`, `marginBottom` and `marginLeft`, and the header's and footer's `headerDistance` and `footerDistance` from the paper's edge, beside their `differentFirstPage` flag ([§ A header and a footer](#a-header-and-a-footer-are-fragments-of-their-own-beside-the-body)). Orientation is no key: a page wider than it is tall is landscape. One key per field lets two people change different margins and both keep their change. ProseMirror's top node can't hold the page, because y-prosemirror never syncs the doc node's attributes. An empty map or a missing key is the default page, A4 with 2 cm margins (`DEFAULT_PAGE_SETUP`, `packages/lib/src/docs/eigendoc/page.ts`). The root is in the doc's `yjsRoots` (`packages/lib/src/types/drive.ts`), so a version restore takes the page with it, and a version from before the map restores the default page.

**Every reader goes through `readPageSetup(map.toJSON())`**, because any peer can write the map. A key that is not a finite number reads as its default. The paper stays between 5 cm and 55.88 cm (Word's 22 in), so a forged size can't reach the layout math, WeasyPrint's `@page` or the docx unbounded. A negative margin reads as its size, and two opposite margins that leave less than 2.5 cm of text (`MIN_TEXT_MM`) shrink in proportion instead of resetting, so a near miss stays near. A band's distance reads between 0 and its margin as the margin reads, so a band never sits in the body's column; a missing one is Word's and Google's 1.27 cm. A pair within 1e-6 mm of the limit reads as it is, so a page read once reads the same again and the dialog accepts it; a stored value that reads as another, such as a shrunk margin, is written as the dialog showed it the next time OK writes the page.

One `PageSetup` in millimetres describes a page, and each surface takes the unit it needs: pixels at 96 dpi for layout math (`pagePx`), a width and padding for a page box on screen (`pageBoxStyle`), a stylesheet for a page that also prints (`pageStylesheet`) and twips for the docx (`pageTwips`). The editor observes the map (`useYMapRead`, `apps/docs/src/components/docs/hooks/use-y-map-read.ts`, which reads the style map too), and its page box, text column and slide-then-scale math follow it. Browser print follows too, through the editor's stylesheet. The server reads the page through `readEigendocPage` (`apps/api/src/lib/document/doc.ts`), beside the body, so quick look, the Drive thumbnail, the HTML and PDF exports and the docx draw it too ([EXPORT.md](EXPORT.md#every-format-but-xlsx-docx-and-pptx-is-one-html-document), [PREVIEWS.md](PREVIEWS.md#the-client-draws-the-body-as-live-dom)).

On screen the margins are the page box's padding. On paper the `@page` rule draws them, so the page must drop its padding and width in print, or the margins print twice. `pageStylesheet(setup, selector)` holds all three rules: the `@page` rule, the selector's width and padding, and the print reset. The editor renders it for `[data-document]` in a `<style>`, which also matches the clone browser print makes, and the export embeds it for `.page`. Quick look and the thumbnail never print, so they keep `pageBoxStyle` inline.

A margin change rewrites no content, so it stays one small undo step. A figure wider than the new column keeps its stored width and draws at the column's width (`max-width: 100%`). A table wider than the column shrinks at the next change to the doc that reaches a writer's open tab, where `TableWidthClamp` fits every table to the column, and stays shrunk when the column widens again.

File → **Page setup…** and Format → **Page orientation** open one dialog, Google Docs' Pages tab without Apply to, Page colour and Set as default: a doc has one page. It offers Google's eleven paper sizes. A page within 1 mm of one, either way round, shows as that paper (`matchPaperSize`), because Word stores a page in twips and never lands on Letter's 215.9 mm exactly. Any other size shows as a Custom entry nobody can pick. A margin `readPageSetup` would change shows an error and blocks OK, and a viewer sees the dialog read-only. OK writes only the keys the user changed in the dialog, in one transaction (`writePageSetup`, `apps/docs/src/components/docs/page-setup.ts`), so a collaborator's concurrent change to another key survives, and ⌘Z takes the change back as its own step ([§ Undo is the Yjs binding's](#undo-is-the-yjs-bindings-and-reverts-only-this-tabs-edits)).

## A doc stores its Normal text in a style map beside its page

A doc's Normal text is what unformatted text draws in: text with no font, size or colour mark, in a paragraph with no format of its own. It lives in the root `Y.Map` named `style` (`STYLE_ROOT`, `packages/lib/src/docs/eigendoc/normal-style.ts`), one key per field: `font` (a bundled font's name), `size` and `spaceBefore` and `spaceAfter` in points, `lineSpacing` as a paragraph's multiple, and `color` as a lowercase hex. An empty map is Eigen's own look, Inter at 11 pt, line spacing 1.4, nothing before, 11 pt after, in the body colour (`DEFAULT_NORMAL_STYLE`). It exists for the docx: about 42% of the corpus has a body size other than 11 pt and 63% a default line other than single, and without it every run and paragraph of such a file would need a mark or a format to keep its look. It is Google Docs' Normal text only, no other named style: headings, the title and the subtitle keep eigen-prose.css's own sizes and spacing, and inherit the Normal's font and colour, as Word's headings based on Normal do. The root is in the doc's `yjsRoots`, so a version restore takes it along, and a version from before it restores Eigen's look.

**Every reader goes through `readNormalStyle(map.toJSON())`**, as any peer writes the map and its values reach CSS: a size is read as a run's (`readFontSize`), the spacing as a paragraph's (`readParagraphFormat`), the font only from the bundled names and the colour only as a hex. A forged key reads as its default.

The page draws it as CSS custom properties, `--doc-font-family`, `--doc-font-size`, `--doc-line-height`, `--doc-space-before`, `--doc-space-after` and `--doc-color`, which `eigen-prose.css` reads with Eigen's own values as the fallbacks (`normalStyleProperties`). Only a value apart from Eigen's is set, so a doc that keeps Eigen's look renders exactly as one without the map. The editor sets them on `[data-document]`, so the body and the bands draw them; quick look and the Drive thumbnail on their page from the preview's `style`; the exports on `.page`, which holds the header and footer too, so the PDF's running bands inherit it in their margin boxes. The docx's header and footer parts share its `styles.xml`, so they draw in the Normal its `w:docDefaults` and Normal style write. A paragraph's own format and a run's marks still win, being set on the element itself. A paragraph's space before is padding, as a paragraph's own is, and a list, a quote, a table cell, the title and the subtitle draw none of it.

The toolbar reads unformatted text as the Normal: the font and the size a run without a mark draws in, and the line spacing an unset paragraph draws, which ticks Single, 1.15, 1.5 or Double when it is one (Eigen's own 1.4 is none). Custom spacing opens on it, and a size step steps from it, as `getDocExtensions` gives the font size extension a reader of the map. Format › Paragraph styles › Normal text › **Update 'Normal text' to match** (`updateNormalStyle`, `apps/docs/src/components/docs/normal-style.ts`) stores what the selection's first text and paragraph draw as the Normal: the first text's own font, size and colour (a caret's the ones it types with), writing only the keys that change, as one undo step of the body. It leaves the content as it is, as Google Docs does. A paragraph in a list, a quote or a cell draws its container's spacing, so there the Normal keeps its own, and so it does for a font or colour it can't hold, a pasted `rgb()` colour say. The item is offered only with the selection starting in a paragraph of the body: a heading's or a title's look is its own, and a band's ⌘Z is its own editor's, which could not take back a change to the body's undo.

## A header and a footer are fragments of their own, beside the body

A doc's header and footer live in four root `XmlFragment`s beside `default`: `header` and `footer` for every page, and `headerFirst` and `footerFirst` for page 1 when the page map's `differentFirstPage` is true (`BAND_ROOTS`, `packages/lib/src/docs/eigendoc/bands.ts`). Each is a band. They are in the doc's `yjsRoots`, so a version restore takes them along. `differentFirstPage` is a page key like the margins: `readPageSetup` reads it as true only when it is stored as true, and the Different first page box on a band's bar writes it through `writePageSetup`, so ⌘Z in the body takes it back. So do the bands' distances from the paper's edge ([§ A header and a footer are edited in place](#a-header-and-a-footer-are-edited-in-place-on-the-page)).

As nodes in the body, the bands would have to be skipped by select-all, delete, paste, find, word count, the preview's first blocks and the docx body walk. As fragments of their own, none of them sees a band. Each band is edited by a TipTap editor of its own, bound to its root through `Collaboration`'s `field`, with y-tiptap's default undo over that root alone, so ⌘Z in a band takes back only that band's typing.

## A band's schema leaves out nodes, never marks

The band editors build the schema without `BAND_EXCLUDED_NODES`: the page break, the title, the subtitle and the code block, none of which means anything in a header that repeats on every page, the footnote, whose note belongs to the body's text, and the chart, because the Chart panel and **Edit data** follow the body's editor only (the Insert menu greys **Chart** out for an editor whose schema has none). A paste parses into the band's schema, and the Yjs binding deletes one that a peer writes. Every mark stays, because a mark missing from the schema deletes the text that carries it ([§ A tab older than the schema](#a-tab-older-than-the-schema-deletes-the-nodes-it-does-not-know)). So the comment mark stays too, and a paste into a band drops its comment anchors instead (`cleanPastedHTML` with no cards). Comments, find and word count reach the body only. An equation stays in a band's schema, because Word allows its math in a header and a footer, and reaches a band through a paste or a Word file, where its panel edits it as in the body ([§ The properties panels](#the-properties-panels-follow-the-selection-on-desktop-only)).

## One factory builds the body's editor, every band's and the open note's

`docEditorOptions` and `useDocEditor` (`apps/docs/src/components/docs/doc-editor.ts`) build every docs editor: the schema, the figure, chart, equation and page-number node views, the table and `TableWidthClamp`, `AtomMarks`, the collaboration and its caret, copy, paste and drop, the sweep of pending images a closed tab left, and the font-name pass. `useBandEditors` keeps the four band editors for as long as the doc is open, all four on the page, a hidden one too. An editor binds to its root once its view first mounts, as y-prosemirror binds in a plugin view, so that is what lets a page-number preset write a band the page doesn't show and a logo uploading into a header resolve its pending name after the band was left. The sweep runs in a writer's editor only, once per root per open, because a viewer's deletion is dropped by the server. `useDocMedia`'s uploads take a getter of the editor they act on and read it again once the upload settles, because the body's editor is built anew when its comment handler changes. Every editor shares the one `cursor` awareness field, because y-prosemirror draws a remote caret only in the editor whose fragment the caret's position resolves in. A band prints in the body's text column, so the factory gives every editor's paste and `TableWidthClamp` the column from the page map. The open footnote's editor is a third target with no collaboration of its own ([§ One note at a time is open](#one-note-at-a-time-is-open-in-a-live-editor-under-the-text)): no root, no caret, no sweep and no font pass, which the body's editor runs over every note. An image put in a note settles in the body's editor (`uploadImage`'s `settle`), whose walk reaches every note, because the note's editor may hold another note by then. TipTap keeps an editor's editable flag across renders, so `useDocEditor` sets it from `editable` (the tab's write access) and `editing` (false for a band not being edited) before paint: a writer made a viewer while the doc is open no longer types into what the server drops, and a viewer made a writer can type, with no remount. An editor that stops taking edits turns a selected node into a caret, as a node view reads the flag only as it renders and an image would keep its grips ([ACL.md](ACL.md#share-propagation)).

## A header and a footer are edited in place, on the page

The page draws the header in its top margin, above the first block, and the footer in its bottom margin, after the last block: where page 1's header and the last page's footer are on paper. Each margin is a `PageBands` (`page-band.tsx`) holding its bands, each drawn by the band's own live editor from `useBandEditors`, so a collaborator's edit shows as it lands and the band reads in full, not dimmed. A band shows only when `bandHasContent` finds text, an equation with content, or another leaf node but a line break, because focusing an empty band leaves an empty paragraph behind. It sits its distance from the paper's edge, the page's `headerDistance` or `footerDistance`, 1.27 cm unless set, which `readPageSetup` holds within the margin, so the editor, the PDF and the docx place it alike with no clamp of their own. Its last block has no space after, as Word's Header and Footer styles have none, through the `PAGE_BAND_CLASS` rule in `eigen-prose.css` that the export's bands carry too, so a footer ends on its distance and a one-line header fits a 2 cm margin. The margin's negative margins pull it over the page's padding to the paper's edges, so a double-click anywhere in it lands on it, and its min-height gives the room back, so a band taller than its margin pushes the body down instead of covering it, as in Word.

A writer on a desktop or a tablet enters a band, as in Google Docs, by a double-click in a margin, by Insert › Page elements › Header or Footer, by Format › Headers and footers, or by a page-number preset, which writes the number and then enters its band. A single click does nothing, so a link in a band still follows. An empty margin shows a writer "Double-click to add a header" on hover, with a mouse only. Shown on hover, it can't push the body as a band does, so it sits at the band's distance where a line fits after it and moves toward the paper's edge where it doesn't, as at a 1 cm margin: it never covers the body. A viewer and a phone see the bands, with no way in.

The band being edited is one explicit `editingBand` state in `editor.tsx`, not the focused editor, because a menu takes focus when it opens. Only that band's editor is editable; the others draw as they print. It never hides while edited, even when emptied, and it gets Google's bar toward the body, across the paper with solid light-grey edges (the `border` and `muted` tokens, as Google's #dadce0 lines on #f8f9fa): its label, Different first page and Options (Header format… or Footer format…, page numbers, Page setup…, Remove header or footer). Header format… and Footer format… open one small dialog, Google's Headers and footers without Different odd & even, which a doc has no bands for: the header's centimetres from the top and the footer's from the bottom under Margins, and Different first page under Layout, the same key the bar's box writes. Its Apply writes through `writePageSetup`, one undo step of the body, and a distance past its margin shows an error and blocks Apply, as a margin does in Page setup. The bar takes its room in the margin like the band, so it never covers the body: the body moves down only by what the margin can't hold of the band and its bar. The toolbar and the Format and Insert menus take `activeEditor`, the band's editor while one is edited, through their one `editor` prop. So do the undo state, an inserted or replaced image, and the menus' clipboard commands. The undo state comes from the undo manager's own events (`useYjsUndoState`), because Y moves an undone step onto the redo stack after the transaction that undid it. A menu closing, by a pick, Esc or a press outside, hands focus to that editor rather than to its trigger (`keepEditorFocus`), unless a dialog it opened has it. So do the Image, Equation and table panels ([§ The properties panels](#the-properties-panels-follow-the-selection-on-desktop-only)). Insert › Equation is greyed out there: a band's equation comes from a paste or a Word file. Insert greys out, as Google greys Break, Bookmark and Equation, what the active editor can't hold (Chart, Equation, Horizontal rule, Page break, Table, Code block and Comment in a band or a note, per `InsertMenu`'s `held` and `inNote`), and the paragraph styles ask that editor's schema what to offer, because a command for a node the schema lacks throws. Comments, find and word count stay on the body: Comment is greyed out in a band, and ⌘F, a comment card and a comment search leave it.

The body is not dimmed while a band is edited, as in Google, and stays editable. A press in it leaves the band and puts the caret where it landed, as in Google. A press in another band moves the caret there, as a band is read-only until entered. A press anywhere else on the page or the grey around it keeps the caret in the band, because it would focus nothing and leave the band edited with Esc and typing reaching nothing. Esc, a key of the band editors' own keymap so the find bar and a dialog keep theirs, leaves and puts the caret back where it was in the body.

With Different first page ticked, a margin not being edited shows the band its end of the long page prints: page 1's header at the top, the other pages' footer at the bottom, as two headers stacked would read as one. While a band of that margin is edited both variants stack, each on its own bar: page 1's header at the top edge and the other pages' header next to the body, and at the bottom the other pages' footer and then page 1's. Ticking it keeps what was typed in the other pages' band, as Google keeps it for page 2 on, and moves the caret into page 1's new, empty band. A switch between the two in one place would hide what the user just typed, and the end of the long page is not always the last page.

A preset puts a right-aligned page number below what the band holds, or in place of an empty band, and leaves a band that has one as it is. A preset not on the first page turns Different first page on, numbers only the band of the other pages and takes the page number off the first page's bands, as Google's Show on first page off does. One on every page numbers the first page's band too when Different first page is on. A preset is two undo steps: the Different first page toggle is in the body's ⌘Z, the number in the band's (`page-numbers.tsx`).

Browser print hides the bands and quick look draws none ([ROADMAP.md](ROADMAP.md)). The server reads them through `readEigendocBands` (`apps/api/src/lib/document/doc.ts`), beside the body and the page: the PDF prints them on every page, the HTML download shows them where the long page does, and the docx writes them as Word's header and footer parts, which a docx import reads back ([EXPORT.md](EXPORT.md#the-pdf-prints-the-bands-as-running-elements-placed-before-the-body)).

## Print is the server's PDF, in a tab of its own

File › Print and ⌘P print the PDF export, as Google prints from a PDF, because only WeasyPrint lays a doc out in pages: browser print of the editor's one long page has no page to put a header, a footer or a page number on. `usePrintPdf` (`packages/lib/src/core/drive/hooks/use-print-pdf.ts`) opens a blank tab before its first await, because a popup blocker allows a new tab only inside the click or key press. It then fetches the export and points the tab at a blob URL of it, where the browser's PDF viewer prints. A hidden iframe would print with no tab, but Android Chrome can't print a PDF in one, Safari does it unreliably, and the page can't tell whether it printed. The blob URL lives until the tab closes, so a reload of the tab still finds the PDF. The hook polls for the close, as a tab that navigated away runs none of the opener's listeners.

The server prints what it has stored. So a tab that is offline or holds edits the server hasn't acknowledged ([COLLAB.md](COLLAB.md#unacknowledged-edits-guard-the-tab)) prints in the browser instead, through `printDocument`, and so do a blocked tab and a failed export, such as the 501 of a server without WeasyPrint ([EXPORT.md](EXPORT.md#weasyprint-fetches-only-data-uris)). A toast says the headers and footers are left out, and a tab opened for a PDF that failed closes again.

`EigenApp` binds ⌘P on the document to `printDocument`, for every app. The docs toolbar binds its own on `<html>`, which a keydown reaches before the document, and the hotkey stops the event there. Two bindings on one target would both fire, and the hotkey library's `replace` would drop the global one for good once the editor unmounts. `editor-toolbar.test.tsx` pins both.

## A page number is a field whose text is # and whose chip names its kind

The `pageNumber` node (`packages/lib/src/docs/eigendoc/nodes/page-number.ts`) is an inline atom whose `kind` is `page` or `pages`. `readPageNumberKind` reads it on parse and on render, so any other value is a page number. It is inline because Google's Page count goes anywhere text goes, the body included (Insert › Page elements › Page numbers › Page count). Its HTML is a `span[data-type="page-number"]` holding `#`, and `#` is also its text for a quoted comment anchor, a copy's text item and a plain-text copy, so no digit shows that a page never had; the search index reads nothing for it. That `#` is its `renderText` and what those callbacks name, never its `leafText`: Tiptap's input rules read the text before the caret through `leafText`, so a space typed after a field opening a paragraph would match the heading rule's `# ` and the heading would drop the field. The editor's node view (`apps/docs/src/components/docs/extensions/page-number.ts`), in the body and the bands alike, draws a grey chip that names its kind after the `#`, `#page` or `#pages`, as both kinds would show `#` alone, with the kind and what fills it in as its tooltip and the kind as its `aria-label`. The name is the chip's alone, and `print:hidden`, so the browser's own print, the offline fallback, shows `#` as the HTML download does. Word count counts no word for it. The PDF draws the page's number or the page count in its place, in the body as in a band ([EXPORT.md](EXPORT.md#the-pdf-prints-the-bands-as-running-elements-placed-before-the-body)), and the docx Word's `PAGE` or `NUMPAGES` field, which the import reads back as the node ([EXPORT.md](EXPORT.md#a-docs-docx-is-written-from-its-json-with-the-editors-css-values)).

## A footnote is an inline node that holds its note's paragraphs

The `footnote` node (`packages/lib/src/docs/eigendoc/nodes/footnote.ts`) is an inline atom whose content is the note, `paragraph+`. The note lives inside its reference, so a copy, a paste, a delete, an undo and a collaborator's edit carry it along. It stores no number: notes number 1, 2, 3 in document order, read by `footnoteNumbers` from a ProseMirror doc and by `footnotesInOrder` from stored JSON on the server, so both sides count alike. `AtomMarks` takes any mark off the reference, and the note's text keeps its own.

Its HTML is `span.footnote` with `data-type="footnote"`, holding one `span[data-type="footnote-paragraph"]` per paragraph (`FOOTNOTE_PARAGRAPH`). Spans, as the figure writes them, because a `<p>` inside the body's `<p>` closes it in every HTML parser, and a copied paragraph holding a note would paste as three. A paste reads the `data-type`, so a web page's own `span.footnote` stays text. The PDF writes the same spans and prints each note at the foot of its reference's page; the HTML download and the drive preview, which no browser pages, write a linked number and list the notes after the body ([EXPORT.md](EXPORT.md#the-pdf-prints-a-note-at-its-pages-foot-and-the-screen-lists-the-notes-after-the-body)). The docx writes Word's footnotes ([EXPORT.md](EXPORT.md#a-note-is-a-footnote-in-words-notes-part)), and its import reads Word's footnotes and endnotes back as the node ([EXPORT.md](EXPORT.md#a-docx-import-replaces-the-document)).

The schema can't refuse a note inside a note. The note holds the body's own paragraph, and a content expression names what a node admits, never what it leaves out. A paragraph type of the note's own would fork every reader of a paragraph, and a plugin that flattened a nested note would duplicate its text when two tabs flatten the same one at once. So `insertFootnote` refuses inside a note, and a paste and every renderer read a nested note through `flattenNestedFootnotes`: its paragraphs' inline content in its place, each after a space. `insertFootnote(tr)` puts the reference after the selection, which stays, as Word's and Google's insert keep a selected text, with one empty paragraph in the note and the caret after the reference. It returns the reference's position, or null inside a note, in a code block and in a schema without the node, a band's.

A plain-text copy leaves the note out (`renderText` is empty): the number is the doc's order, which a text serializer never sees, and the note's text would run into the sentence. The node is no leaf, so it has no `leafText` for Tiptap's input rules to read. They check a match against `textBetween`, which reads the note's text at its own positions inside the node, so text typed after a note never completes a rule with the note's last characters. The search index reads the note's text with the body's. A comment's quote, a copy's text item and word count leave it out, as Google's word count does, and a copy writes no item for an image in a note.

## One note at a time is open in a live editor, under the text

The reference draws as its number, a superscript the `Footnote` node view (`apps/docs/src/components/docs/extensions/footnote.ts`) reads from a node decoration that holds `footnoteNumbers`' number. A node view isn't redrawn when another note goes in before it, but its decorations are. The plugin maps the numbers through a change that leaves every note's node at its mapped position and inserts none, and walks the doc again otherwise; the notes keep their array while none moved, so the list under the text draws nothing again. The note's text is no DOM of the body's.

The notes show after the body's text, under a short rule, as Google's pageless document collects them at its end (`FootnoteList`, `apps/docs/src/components/docs/footnote-list.tsx`). Each is static HTML from the schema's serializer, so a doc with 133 notes isn't 133 editors, and its images resolve as the figure's node view's do. A press on a note, or on its reference, opens it: one live editor, the open note's, takes its place in the list. That editor lives as long as the doc, beside the bands', and holds whichever note is open. Its doc is `paragraph+`, so a pasted heading, list or table lands as paragraphs, and its schema is the body's otherwise, as a note crosses between the two as JSON and a node either schema lacked would throw.

The open note is one explicit state, as the band being edited is, because a menu takes focus when it opens (`useOpenNote`, `apps/docs/src/components/docs/hooks/use-open-note.ts`). The toolbar and the Format and Insert menus follow it through `activeEditor`, as they follow a band. A note's paragraphs draw at the footnote size (`FOOTNOTE_FONT_SIZE`), so the toolbar reads them against that Normal and its size box shows 10. Insert leaves out what a note can't hold (a chart, a rule, a page break, a table, a code block, an equation, a comment) and greys **Footnote**, which a band's schema and a code block refuse on their own. Opening a note leaves a band, and entering a band closes the note. Esc, a key of the note's editor, leaves it with the caret right after the reference; a press in the body leaves it with the caret where it landed. A press elsewhere on the page keeps the caret in the note. A viewer and a phone read the static notes, with no way in, as with the bands.

Insert › Page elements › Footnote and ⌘⌥F (`insertNote`) put the reference after the selection and open its note with the caret in it, as Google's do. ⌘⌥F asks the editor's host (`onInsert`), which inserts only where a note opens, so a phone's keyboard leaves no note nobody can edit. The menu item inserts once the menu has closed, as Insert › Equation does, so Radix hands no focus back to the trigger after the note took it. Find and replace left ⌘⌥F for ⇧⌘H ([IN_DOCUMENT_SEARCH.md](IN_DOCUMENT_SEARCH.md)).

## An open note forwards its edits by diff, anchored on its Yjs element

The note's editor has no collaboration. Each of its transactions forwards into the body by diff: the range where the note's paragraphs differ from the body's note replaces that range in the body (`forwardNote`), marked `NOTE_EDIT`. A diff rather than its steps, because TipTap replays a transaction a command captured without its meta, and the steps would land twice; a diff that finds nothing changes nothing. A forward also carries `preventAutolink`: the note's editor makes its own links, and the body's autolink would take the note's typing as typed after the body's words before the reference. Each body transaction pulls the body's note back the same way (`pullNote`, marked `NOTE_PULL`), so a peer's edit, an undo or Replace all moves the open note's caret with the text. A note that goes while the caret is in it, its reference deleted by a peer or by an undo, hands the caret to the body where the reference stood, or typing and ⇧⌘Z would reach nothing. It does so in the next frame: the pull runs inside the body's transaction, and a focus there draws a selection the DOM doesn't hold yet, which Chrome throws on, so the note's ⌘Z never returned and the browser's own undo ran on the body as well. The pull also hands the note the body's decorations inside it, the reference node view's `innerDecorations`, so the find bar's matches paint in the open note.

The open note is its footnote's Yjs element, beside its reference's position (`NoteAnchor`, `findNote`). This editor's own transactions map the position, and the element is the one the binding (`ySyncPluginKey.getState(state).binding.mapping`) maps to the node there: a split of the reference's paragraph here can give the note a new element, as `updateYFragment` keeps the old paragraph's elements for the half that matches more of it, and the mapped position follows. A peer's change or an undo, which y-prosemirror applies as a replace of the whole doc that no mapped position survives, reads the position back from the element, through a Yjs relative position on it; a deleted element is a note gone, never the neighbour its place now holds, and a note a split in another tab gave a new element closes. A relative position taken at the reference instead sat on the character before it, so a peer typing there closed the note and a peer deleting it opened the next one. Never a node, nor a node view's: y-tiptap builds every node anew on a peer's update, ProseMirror keeps the view of a node equal to the one it drew without calling its `update`, and a step that only changes marks or an attribute (AtomMarks after a Bold, an image's name landing) maps no position yet makes a new node. So the numbering checks each note's node, not its position alone, and the notes list keys each note by its element (`noteKey`), read from a reverse of the binding's mapping built once per doc state, as y-tiptap refills the mapping on every peer update, so the open note's editor never remounts, losing its focus, when a note goes in or out before it. Two notes alike never swap, which matching their text would. The note's content goes into its editor as it opens, before React mounts that editor in the list, as an image's node view mounting inside a layout effect makes React refuse its `flushSync`.

There is one history. ⌘Z in a note runs the body's undo, whose change pulls back into the note. The note's `undo` and `redo` commands mark their own transaction `preventDispatch`, as Collaboration's do, because the pull changes the note's state while the command runs and the command's transaction would land on a state it was not made from.

## The body never formats a note's text

In Google Docs, bold, a colour, a comment or Clear formatting across a reference leaves the note alone. ProseMirror's mark and block commands descend into an inline node's content, so `NoteFormatting` (in the same file) gives a note back as it was after a body transaction that left its text as it was and changed its marks or attributes. It goes first among the body's plugins, sees only the transaction a command dispatched, and leaves a transaction another plugin appended alone, so it and `AtomMarks` never undo each other. A changed text passes, so Replace all reaches the notes. The note's own forwarded edits, a peer's change, an undo, an upload's name landing in a note's image and the font-name pass are `NOTE_EDIT` or the binding's, and pass too. `canAnchorComment` reads no text inside a note, so a reference selected alone takes no comment, and a comment's quote leaves a note's text out (`textOutsideNotes`, which word count reads too).

A note pasted into a note leaves its text in its place: the note's editor reads its paste as the open note's content and flattens it with `flattenNestedFootnotes`. A band's schema has no note, and its paste drops one whole (`cleanPastedHTML`), or the note's paragraphs would land as the band's text.

## A link autolinks through a text walk that reads a note as one space

Typing a space or Enter after a URL links it, as TipTap's autolink does, but through the schema's own link (`EigenLink`, `packages/lib/src/docs/eigendoc/nodes/link.ts`), with TipTap's autolink configured off. TipTap's reads the paragraph with `textBetween`, which reads a footnote's note in its reference's place, so past a reference its offsets missed the doc's positions: " then example.com " typed after one linked "hen example". The walk takes each character beside its position and any other node as one space at its own, so a word never runs into a note and a link lands where its text is. The mark stays inclusive, as it is with TipTap's autolink on, so text typed at a link's end joins it. A transaction the Yjs binding applied, a peer's change or an undo, links nothing (`remote`, which the docs editors set to the binding's meta), as y-tiptap writes one as a replace of the whole doc and the doc's first textblock would gain a link its writer never made. A pull into the open note carries `preventAutolink` for the same reason. A typing rule takes nothing from a note either: a `>` typed after a reference whose note ends in `-` stays `>` (`footnote.test.ts` pins both).

## A page break is a dashed rule on screen and a new page on paper

The `pageBreak` node (`packages/lib/src/docs/eigendoc/nodes/page-break.ts`) is an atomic block with no content. It renders as `<div class="page-break">` and parses that div back when it holds no text, so a heading, table or `div` with text that carries the class keeps its content. `PAGE_BREAK_CLASS` holds the class, and `eigen-prose.css` draws and pages at the same class.

The **Insert** menu and Mod-Enter insert it the way the horizontal rule is inserted: the caret lands after it, on a new paragraph when the break ends the doc. Mid-paragraph the break splits it, and the caret waits at the start of the second half. Before a table or a rule the caret waits in a gap cursor instead, so the first Backspace selects the break and the second removes it, and the table stays. A gap cursor needs a closed block on both sides, so before a list or a quote, which open on a paragraph, the caret goes into its first paragraph. A selected image is an inline node with no room for a block beside it, so the break splits its paragraph after the image.

On selected table cells, or a selected node with no place for a break, Mod-Enter does nothing. StarterKit's hard break binds Mod-Enter too, so the node's shortcut runs at priority 101 to win, and it swallows the key where no break fits, because the hard break would empty a cell or replace the selected node. In a code block Mod-Enter still exits the block, and Shift-Enter stays the line break. `packages/lib/src/test/docs/eigendoc/nodes/page-break.test.ts` pins the keys.

Every screen surface draws it from `eigen-prose.css` as a dashed rule labeled "Page break": the editor, quick look, the Drive preview and the HTML download. Print and the PDF draw nothing and start a new page after it, and the docx writes a Word page break ([EXPORT.md](EXPORT.md#a-docx-keeps-every-page-break)). That rule is a top-level `@media print` block, because the export's CSS flattener (`flattenEigenProseCSS`) expands only plain nesting and would break an `@media` nested in `.eigen-prose`. Its `.tiptap .page-break` selector weighs the same as the flattened `.eigen-prose .page-break` and comes after it, so it wins in the PDF too. A selected page break or horizontal rule takes the shared selection ring (`.eigen-selection-ring` in `packages/ui/src/styles/globals.css`).

## A Word page break splits its paragraph on import

In Word a page break is a run inside a paragraph (`w:br w:type="page"`), and in a doc it is a block. So the docx reader (`apps/api/src/lib/import/doc/`) splits a paragraph at each break and sets the break between the halves. The halves keep the paragraph's style, so the break stands between two headings instead of inside one. A half that shows nothing (empty, spaces, a bookmark) gives no block, but one holding a non-breaking space stays, as Word draws it. Two breaks in a row stay two.

Inside a list item or a quote the break stays inside. It becomes a block of the item, the rest of a split item continues that item unnumbered, and the list keeps counting; a paragraph holding nothing but a break joins the item above and takes no number. Word counts on across a page, and a break pulled out of the list would cut it in two and restart the second half at 1. A break in a table cell is a page break inside the cell.

Word starts a page in two more ways, and both give a break. A paragraph with `w:pageBreakBefore`, its own or its style's, gets one before it. A section break that starts a page gets one after its paragraph: `nextPage`, `oddPage`, `evenPage`, or no type, which means `nextPage` (`PAGE_SECTION_TYPES`, `apps/api/src/lib/ooxml/wordml.ts`). A `continuous` or `nextColumn` section break gives none, and neither does the body's last section, which ends the document. A footnote or endnote isn't paged, so every break in a note is dropped.

Empty paragraphs import as blank lines, except a run of them that ends at a break, which is dropped (`isBlank` in `assemble.ts`). Eigen draws an empty line taller than Word, so the blank lines that fill out Word's page would push the break onto a blank page of its own. A blank list item, task item or rule stays. The cases are pinned in `apps/api/src/test/import/doc-import.test.ts`, `apps/api/src/test/import/doc/paragraphs.test.ts` and `apps/api/src/test/import/doc/assemble.test.ts`. The docx writer leaves out the blank lines before a page break the same way (`blocksOf` in `export/doc/docx/paragraphs.ts`): Word draws nothing there, but Google Docs and LibreOffice fit less on a page and push them onto a blank page before the break's own. The blank line a wrapped figure floats from stays, so the figure stays on its page.

## An equation is an inline node that stores its MathML

An equation is an inline, atomic node like the figure (`packages/lib/src/docs/eigendoc/nodes/equation.ts`), because Word keeps a displayed equation inside its paragraph and Google Docs has only inline ones. Its attributes are `mathml`, `display` and `commentCardId`. `mathml` is MathML in the dialect of `@workspace/math` ([MATH.md](MATH.md)), with the LaTeX a user typed as its `application/x-tex` annotation. `display` says the equation stands on its own line, and a renderer sets `display="block"` on the `<math>` it draws, since the package's writer never writes it. An empty string is an empty equation, which the editor draws as an empty dashed box. The editor draws an equation through its node view (`apps/docs/src/components/docs/extensions/equation.tsx`), which mounts the `<math>` that `drawnMath` writes from `readEquation`'s tree, centred on a line of its own when displayed, a paragraph's gap from the next. `drawnMath` draws Word's dotted box (`⬚`) in each empty required argument, a fraction's numerator or a root's body, and so does the panel's preview; the stored MathML and every export keep the argument empty. A script's base stays empty, since `{}^{14}C` empties it on purpose, as do a large operator's body, a fence and a table's cell. renderHTML, which writes a copy's HTML, puts the `<math>` in a span, because ProseMirror marks an atom `contenteditable="false"` on its outer element only, and browsers honour that attribute on HTML elements only: in an editor without the node view, the caret would enter a bare `<math>`'s tokens.

An equation, a figure, a chart, a page number or a footnote's reference carries no mark. A mark is its paragraph's to allow, so a bold or a colour over a range lands on the atom too, and the Yjs binding would drop it on reload. The editor's `AtomMarks` extension (`apps/docs/src/components/docs/extensions/atom-marks.ts`) takes any mark off one a transaction touched (`MARKLESS_ATOMS`), in the body's editor and in every band's. ProseMirror gives the caret the marks of the node before it, and an atom has none, so the same extension gives a caret right beside an atom the marks of the text around it (before the atom, else after), as stored marks: text typed after a bold run's equation stays bold, as in Google Docs.

The whole equation is one attribute, so two people editing one equation don't merge: the last write wins. The LaTeX rides only in the annotation, and Word's OMML has no slot for it ([MATH.md](MATH.md#a-word-equation-comes-back-as-drawn-not-as-built)), so a Word round trip keeps the equation's tree and loses what was typed. The docx import reads each Word equation into this node, one in an `m:oMathPara` with `display` set ([EXPORT.md](EXPORT.md#a-docx-import-replaces-the-document)).

## Every reader of an equation goes through readEquation

**No consumer mounts or parses the stored string itself**, because any peer can write it. `readEquation` parses only a string that starts with `<math`, as everything the writer writes does, so no prolog, DOCTYPE or entity reaches either parser, and refuses one longer than `MATH_LIMITS.mathmlLength` before parsing. It reads the tree with `readMathml` and writes it again with `writeMathml`, since the annotation counts toward no bound; an annotation the writer refuses is dropped and the tree kept. A tree past a bound shows its LaTeX as text, when the LaTeX is shorter than the size bound; anything else reads as an empty equation. So whatever a peer stored, `readEquation` returns MathML the writer wrote, and renderHTML mounts that, never the stored string.

The browser parses with `DOMParser`. The server has none, so `readStoredEquation` (`apps/api/src/lib/document/equation.ts`) passes Bun's parser, and a string either parser refuses reads as an empty equation. The HTML export and the drive preview draw the MathML without the annotation, which no screen draws, in the editor's `<span class="equation">`, so the one `eigen-prose.css` rule lays a displayed equation on a full-width line as the editor does and the trailing `<br>` adds no empty line under it. Their sanitizer keeps `<none>`, the empty slot of a prescript, which DOMPurify's MathML profile drops (`KEEP_MATHML`). A pasted `<math>`, Eigen's own or a web page's, is read and written the same way, lifting `display="block"`, and keeps its annotation only when `readLatex` reads it, since the panel edits that LaTeX and would open on an error nobody typed. One the package refuses pastes as nothing rather than as its tokens' scattered text. KaTeX, MathJax 2 (Word for the web's), MathJax 3 and Wikipedia put each equation on the page twice: as a `<math>` hidden for screen readers, and as drawn glyphs or an image. So `cleanPastedHTML` first replaces each drawing with its `<math>` (`unwrapRenderedMath`), or the glyphs would paste as text beside the equation, and Wikipedia's fallback `<img>` as a figure hotlinking its `src`. Only a `<math>` in the renderer's hidden holder, directly inside the drawing, counts. So a page's own element that carries a renderer's class keeps the rest of what it holds, and the pasted body is never replaced. MathJax 4 turns its hidden MathML off by default, as KaTeX's HTML-only output leaves it out, so such a page puts no `<math>` on the clipboard and its equations paste as their glyphs' text.

## An equation's text is its linear form, and the find bar skips it

Word count, a comment's quote, the text item of a docs copy, a plain-text copy and the search index read an equation as its linear form, the UnicodeMath line `writeText` writes (`x/2`, `x^2`, `∑_(i=1)^n`; [MATH.md](MATH.md#the-text-form-is-words-linear-format-written-only)), typed or not: the `text` of what `readEquation` reads, which every reader of an equation gets, so the server's index, the export past its budget and the docx import's caption or code block read it through `readStoredEquation` too. The first three read `readEquation(attrs).text` in their own leaf callback, as they name the figure there, and a comment on an empty equation quotes "Equation". The callback replaces every leaf's `leafText`, so a comment's quote and a copy's text item name a page number's `#` there too. The plain-text copy reads the node's `renderText`. The node has no `leafText`: Tiptap's input rules check their match against `textBetween`, which reads it, so a rule would replace an equation whose LaTeX is the rule's prefix (`light (`, an equation `c`, then `)` would give ©). The find bar matches text nodes only, and prosemirror-search reads any other leaf as one placeholder character, so it never finds an equation, a [ROADMAP](ROADMAP.md) row.

## An equation is edited as LaTeX in its panel, and a draft stays in the tab until it is written

Insert › Equation adds an empty equation at the caret, selects it and focuses the LaTeX field of the Equation panel, closing a comments or activity panel so the Equation panel gets the slot. It sits after Chart, where Google's Insert › Symbols › Equation sits, since Eigen's Insert menu has no Symbols submenu. The insert waits until the menu has closed: Radix hands the focus back to the menu's trigger on close, which would take it from the new field. It doesn't focus the editor either, since Tiptap's `focus()` focuses it a frame later, after the field. A phone has no right-side panel, so Insert › Equation is left out there, and Enter on a selected equation splits the paragraph before it, as on a figure. In a band being edited or an open note it is greyed out. In a code block the insert splits the block at the caret, as a horizontal rule or a table does there, and the equation takes a paragraph between the halves. A click or a right-click on an equation opens its panel too, and Enter on a selected one or a click on one already selected opens it with the field focused; an arrow that selects one opens nothing, since an equation sits in prose and its panel opening and closing would slide the page at each one passed (`use-selection-panel.ts`). ProseMirror dispatches no selection a click leaves unchanged, so the click on a selected equation is the node's `handleClickOn` (`extensions/equation.tsx`). Google edits an equation in place, as a structure; Eigen edits its LaTeX in the panel, by decision: the field is the editor, and no structural one is planned.

The field edits a draft, as the Image panel's fields do (`equation-properties-panel.tsx`). A keystroke or a menu item starts it; until then the field shows the equation as stored, a peer's write too. The preview draws the draft, or the equation as it stands while the draft doesn't parse. ⌘Enter (Ctrl+Enter) writes the draft and puts the caret after the equation, as Enter starts a new line, which the LaTeX reader takes as a space; a blur out of the field and its symbol menus writes it too, and so does the panel unmounting, which fires no blur (the comments panel taking the slot, a phone's width); Escape drops it. A draft that doesn't parse is never written: the field's description, not an alert, since half-typed LaTeX is an error at nearly every keystroke, shows the reader's message and marks the character where it stopped (`MathError.offset`). The panel shows the last equation the selection holds, as a node or as text (Shift and an arrow, or a drag), and a write is `writeMathml(readLatex(draft), draft)` as an attribute step on that equation alone, since a draft of one equation's LaTeX would replace the content of the others; a draft whose write finds no equation stays. An attribute step moves no position, so the selection stays. A draft that is back to the LaTeX it started from writes nothing. An equation from Word has no LaTeX, so its field starts from `writeLatex` of its tree, and a visit writes nothing, so it gains no annotation it never had. A draft that starts with `<math`, once trimmed, is MathML, parsed by `parseMathml` with the checks `readEquation` puts on a stored string, and written as its tree with its own LaTeX as the annotation when `readLatex` reads it, else `writeLatex` of the tree, so the field shows LaTeX from then on; one that can't be read shows its error and is never written.

**A draft is invisible to peers until it is written, and then the last writer wins**: the equation is one attribute ([§ An equation is an inline node](#an-equation-is-an-inline-node-that-stores-its-mathml)). A peer's write to the equation leaves a draft alone, and a peer's delete ends it. The Yjs binding then selects whatever node sits where the equation stood, so the panel tells them apart by node: a write makes a new node there, while a neighbour the delete moved there is one the document already held, which the binding reuses.

A command's name and a space, `\frac` then a space, become the command with a pair of braces per argument it takes in `LATEX_COMMANDS`, `\frac{}{}`, with the caret in the first braces; a command whose arguments already follow, `\frac {a}{b}`, keeps its space. There is no Tab between slots and no braces after `^` or `_`. The five symbol menus are Google's, item for item and named as Google names them (`equation-menus.ts`); a screen reader reads a symbol as its character and a template by a name in words, where Google's names are `leq` and `rbracelr`. Each item inserts its command at the field's caret, a symbol with a space after it so a letter typed next doesn't join its name, a template with the caret in its first slot past a base (`\frac{|}{}`, `x_{|}^{}`), and the field takes the focus back when the menu closes. The Style row's In line with text and On its own line (`EQUATION_STYLES`, which the equation's menu offers too) set `display` through `updateEquation`, on every equation the selection holds, as the Image panel's layout does on every figure.

## Every equation draws in STIX Two Math, with CSS for what Chrome leaves out

STIX Two Math (OFL, `packages/ui/src/assets/fonts/stix-two-math/`) is a face in `fonts.css`, and one `math` rule in `eigen-prose.css` draws every `<math>` in it, the editor's, the panel's and an export's. It is no `EIGEN_FONTS` name, since nobody sets text in it, and no export embeds it, a [ROADMAP](ROADMAP.md) row.

Chrome implements MathML Core, which leaves `columnalign` and `menclose` out, and WebKit centres an aligned table's cells too. So `eigen-prose.css` aligns an equations table's cells (`displaystyle="true"`) right and left by turns, as the writer's `columnalign` says, and a cases table's (`columnalign="left"`) left. Inside `@supports (display: block math)`, which Chrome passes and WebKit doesn't, it uses the `-webkit-` alignment values that Chrome's block-laid cells need and that break WebKit's row, and draws each `menclose` notation as a border or a background layer of its own, which WebKit and Firefox draw themselves. The exports embed `eigen-prose.css`: the HTML download needs the block in Chrome, while WeasyPrint skips an `@supports` rule and the PDF draws an equation as SVG, so the custom properties that compose the strike layers never reach it. The check stands in for "lays cells out as blocks and draws no `menclose`": Chrome passes it and WebKit fails it, Firefox is unchecked, and each browser release is a re-check. A browser that ships `display: math` falls into this block whether it needs it or not, a [ROADMAP](ROADMAP.md) row. Tailwind's reset takes away the padding both browsers give an `mtd`, so a matrix's columns would touch; `eigen-prose.css` puts MathML's `0.5ex 0.4em` back, but not between an equations table's cells, which meet at their alignment point; a cases table keeps it as its column gap.

## The page keeps its width and slides, then scales, clear of a panel

The page is centered in a scroll box. Its width never changes, so a line breaks in the same place on every screen, and the drive preview and the HTML export lay the doc out at the same width ([EXPORT.md](EXPORT.md#every-format-but-xlsx-docx-and-pptx-is-one-html-document)).

A panel is an absolute overlay on the right of the scroll box, so opening one never reflows the page. Only the text column has to stay clear of it: the page's right margin may tuck under. Below `PANEL_CLEAR_WIDTH_PX` the page slides left by its overlap with the panel, and scales down only once the space left of the page runs out. A screen narrower than the page scales it too. The scale is a CSS transform with a negative bottom margin that gives back the space the transform frees.

Laying the panel out as a flex sibling, the way sheets and slides do, would end the scroll box at the panel's edge. But the page would then re-center in the narrower box and jump on every open and close, which the slide-then-scale math exists to prevent.

## A side panel ends left of the page's scrollbar

The overlay sits in a wrapper with a stable scrollbar gutter (`scrollbar-gutter: stable`) and `overflow: hidden`. That gutter is as wide as the scroll box's scrollbar but draws none, and an absolute child ends where the gutter starts. So the panel stops left of the page's scrollbar, which stays visible and draggable, and its left edge lands where the slide math (`PANEL_INTRUSION_PX`) assumes it is. The wrapper ignores the pointer and the panel takes it back, so clicks around the panel reach the page. An overlay scrollbar has no gutter, so the panel still covers one.

## The properties panels follow the selection, on desktop only

Selecting a figure, a chart or a table opens its properties panel, for a user who can write, in the slot the comments and activity panels use, and so does an equation selected by a click, Insert › Equation or Enter, not by an arrow ([§ An equation is edited as LaTeX](#an-equation-is-edited-as-latex-in-its-panel-and-a-draft-stays-in-the-tab-until-it-is-written)). An open comments or activity panel keeps the slot, and moving the caret out of the figure, chart, equation or table closes the properties panel.

The panels follow `activeEditor`, the editor that has the selection: the band's being edited, the open note's, else the body's. `useSelectionPanel` reads that editor again when it changes, so a figure selected in the body shows no panel over a band. The Image, Equation and table panels write only through that editor's commands, so a change lands in the band or the note, and that editor's ⌘Z takes it back. A band's Image panel offers the alignment alone, which puts a pasted wrap on its own line: a band holds no float, as the docx import reads a header's anchored picture as a block ([EXPORT.md](EXPORT.md#a-docx-import-replaces-the-document)), and a wrap set there would come back a block. A note's offers the layouts in the flow, block and the wraps, as a note's figure draws in line ([§ A positioned figure lives in the body only](#a-positioned-figure-lives-in-the-body-only)). The Chart panel stays the body's, because it and **Edit data** write through the body's undo manager, so a note's chart opens none and a band holds no chart ([ROADMAP.md](ROADMAP.md)). A press in a panel keeps the band edited and the note open: the panel sits outside the scroll box whose press leaves them. A phone shows no right-side panels: comments and activity open as a pane that hides the editor ([COMMENTS.md](COMMENTS.md#the-pane-hides-the-editor-never-unmounts-it)), and the properties panels have no phone form. Format › Table holds the table panel's actions, and Format › Image the Image panel's Replace image and its layouts as a choice, so a phone reaches them there. The menu offers the layouts the panel offers, from the one list both read (`figureLayoutLooks`): none in a band, and those in the flow in a note. A chart's Edit data, caption and layout have no menu, so a phone can't reach them ([ROADMAP.md](ROADMAP.md)). The panel's button and the menu item open one Replace image picker, which `editor.tsx` owns.

So a write from the Image panel must keep the figure selected. TipTap's `updateAttributes` writes with `setNodeMarkup`, which replaces a leaf node, and the node selection maps to a text selection, which closes the panel. The figure node's `updateFigure` command and every write in the node view go through `setFigureAttributes` (`packages/lib/src/docs/eigendoc/nodes/figure-frame.ts`), which sets each attribute with `setNodeAttribute` instead, a step that moves no position. Such a write fires no `selectionUpdate` and `useEditor` re-renders on no transaction, so the panel reads the figure through `useEditorState`.

## An option sits in the menu Google Docs puts it in

Each option goes in the menu Google Docs uses for it, so a user coming from Google finds it where they look. ## A long selection's toolbar shows what its start holds

The toolbar lights a button when the whole selection carries the mark or sits in the block, and it reads that again on every transaction, a collaborator's keystroke or caret included. ## A comment anchors on text as a mark and on a figure, a chart or an equation as an attribute

A comment's card id rides the `comment` mark on text and the `commentCardId` attribute on a figure, a chart or an equation, because the Yjs binding keeps a mark only on text. A node anchors by attribute when its schema gives it `commentCardId`, so a page number, which has none, anchors no card, and `AtomMarks` strips the mark from it. `canAnchorComment` holds Insert › Comment, ⌘⌥M and the selection's right-click menu back from a selection with no text and no such node selected alone, as a page number selected alone. `nodeCommentCardId` reads either form, and `addCommentAnchor`, `removeCommentAnchors` and `selectCommentAnchor` in `extensions/comment-mark.ts` set, clear and select either. The decorations, the image's own menu and its corner mark are in [COMMENTS.md](COMMENTS.md#each-app-anchors-a-card-in-its-own-content). A commented equation is highlighted as text is and draws the image's corner mark too, in a strip of its own right of the glyphs, which the mark would cover. The mark opens its card, since a click on the equation itself selects it for its panel. Clear formatting keeps a card's anchor, and a link, as Google Docs' does: both marks are `clearable: false`, which TipTap's `unsetAllMarks` skips, and `clearNodes` leaves an atom's attributes alone. The `clearFormatting` command (`paragraph-format.ts`) runs both and is bound to ⌘\\ in the eigendoc schema, so the body and a band take the key; the toolbar button and Format › Clear formatting call it too.

## A table cell and an equation have right-click menus of their own

A right-click in a cell opens the table menu, about the cell under the pointer (`posAtCoords`), so a text selection there stays: Cut, Copy and Paste, Format › Table's rows (`tableMenuSections`), the comment rows, then Delete row, Delete column and Delete table, red and last, in `MenuSections`' order ([LAYOUT.md](LAYOUT.md#menus-draw-their-rows-in-one-order)). An equation's menu holds Cut and Copy, Edit equation, the panel's two Style options, the comment rows and Delete equation (`equation-menu-sections.tsx`). Edit equation opens the panel once the menu has closed, as Insert › Equation does, or the menu would take the focus back from its field; a phone, with no panel, gets no Edit equation. Each menu acts on the editor the cell or the equation sits in, the body's, the band's being edited or the open note's, so a band's table grows in the band. A viewer and a band not being edited keep the browser's menu, as their editor is read-only.

The table menu is an editor prop (`table.onContextMenu` in `docEditorOptions`), not a plugin, so it runs ahead of the comment mark's plugin: over a cell it takes in the rows of a highlight's card and the selection's Add comment, which would otherwise open menus of their own. A right-click inside the selection keeps it, so a cell selection merges; elsewhere the caret goes to the cell. An equation's right-click comes through its node view, as a figure's does, since ProseMirror never sees a node view's events. Paste has no clipboard event to read, so `pasteFromClipboard` reads `navigator.clipboard`, which asks the browser's permission, and hands its HTML, text and images to the editor's own paste in a synthetic one, so `handlePaste` and `cleanPastedHTML` run as on ⌘V.

## A docs copy with an image writes its items in order, and a docs paste reads its HTML

A copy or cut whose selection holds a figure writes the eigen clipboard payload, beside ProseMirror's own HTML and the plain text (`writeDocsClipboard`, `apps/docs/src/components/docs/clipboard.ts`). It runs in the editor's `handleDOMEvents`, before ProseMirror's own handler, because that handler deletes a cut's selection before any later listener could read it. So it makes the cut's delete itself. In document order the payload holds an image item per figure whose file resolves, and the text between them as a text item, a line per paragraph. A footnote's text and images are left out, as no part of the sentence around the reference. A selection with no resolvable figure writes no payload, and leaves the copy to ProseMirror unless it holds a title, a subtitle or an italic mark in Heading 6, whose look the copy writes inline ([§ Pasted content is fitted to the page](#pasted-content-is-fitted-to-the-page)). It decides that from the document, so a plain copy is never serialized twice. The payload is what lets another app (slides, sheets, a drawing) place the image ([CLIPBOARD.md](CLIPBOARD.md)).

Edit › Cut and Copy have no clipboard event of their own, so they fire `execCommand('cut')` and `execCommand('copy')`, and the editor's handlers write what ⌘X and ⌘C write. The browser sends the event to the element that holds the page's selection, and opening the menu leaves that selection in place, in Chrome, Firefox and WebKit alike. A read-only editor never puts its own selection on the page, so a viewer's right-clicked image is selected in the editor only: `runClipboardCommand` sets the page's selection to the editor's first, or the copy would go to the body and write nothing. The menu has no Paste, as reading the clipboard asks the browser's permission.

ProseMirror's own HTML writes a figure as spans, `span.figure` with a `span.figcaption`, the form the export writes. A `<figure>` inside a `<p>` closes the paragraph in every HTML parser, so a pasted copy would split its paragraph around the image.

On paste, a payload with an image item goes through `insertEigenItems`. A docs copy, whose HTML ProseMirror marked with `data-pm-slice`, pastes through that HTML, because a text item is plain and would drop the headings, lists and marks. First each figure takes the name its image item gives: a figure from another document's `media/` is re-uploaded into this one, and a figure with no item or a failed re-upload is removed, so none pastes broken. The re-uploads run at once, one per file, so an image pasted twice uploads once, and the paste lands when they have all settled. Any other payload, from slides or sheets, is placed item by item: a text item is plain and lands as typed, a paragraph per line, and beside text an image takes a paragraph of its own.

## Pasted content is fitted to the page

Content wider than the text column would overflow the page and the export. So the editor's `transformPastedHTML` (`cleanPastedHTML`, `apps/docs/src/components/docs/paste.ts`) caps every pasted image, chart and table at the text column's width, a chart keeping its shape. An image or a chart in front of or behind the text caps at the paper instead, and its horizontal offset stays on the paper, counted as if its paragraph started at the column's edge: the paragraph's indent isn't known at paste, so an indented anchor may overhang the paper by it until the figure is dragged. The cleaner also maps common desktop fonts onto the bundled families ([TYPOGRAPHY.md](TYPOGRAPHY.md#foreign-fonts-map-onto-the-bundled-ones)). Google Docs writes a size on every span, its body's 11 pt and a heading's own included. So the cleaner drops an 11 pt size, which the doc draws already, and every size in another app's heading, which draws at the doc's heading size; a copy from a ProseMirror editor, which marks it with `data-pm-slice`, keeps every size it carries, so an 11 pt run in a heading copied here pastes back at 11. That mark is any ProseMirror editor's, not Eigen's alone, which is fine: such an editor writes the sizes its runs carry, not its body's on every span. Heading 6 draws an italic mark upright, and Google Docs writes every run of its italic Heading 6 as `font-style: italic` and an upright one as `normal`, so in a heading `ITALIC_HEADING_LEVELS` (`@workspace/lib/docs/eigendoc`) names, the cleaner makes the upright run the mark and drops the italic. A copy writes the mark there as `<em style="font-style: normal">` (`writeDocsClipboard`), so Google Docs reads it upright too. A title and a subtitle draw their size and the subtitle's grey from `eigen-prose.css`, which a paste elsewhere doesn't carry. So the copy reads each one's font size, and its color where it differs from the one it inherits (the body's, a quote's grey), from the page with `getComputedStyle` and writes them inline on its `p`, and Google Docs and Word paste a 26 pt line, not 11 pt Normal text. The CSS stays the one place the look is spelled, and the `data-type` still pastes back here as the node. Word and web pages keep a heading's look in a `<style>` block or the browser's defaults, so their `<em>` and `<i>` in a Heading 6 are read by tag, not by look, and draw upright: an accepted gap, as italic inside a pasted Heading 6 is rare. A table pasted or grown past the column, a collaborator's included, is scaled back after every change by `TableWidthClamp` (`apps/docs/src/components/docs/extensions/table-width-clamp.ts`), which shrinks every column by the same factor with a 25 px floor. The clamp and the paste read the column from the page map, not the page on screen: a docx imported into an open doc, or a collaborator's change, brings the content and the page in one update, and the clamp runs before React draws the new page. It runs in a writer's tab only: the server drops a viewer's writes, so a viewer's tab would draw a table nobody else has.

## A table column resizes by its border, with a mouse only

A cell stores its column's width as `colwidth`, prosemirror-tables' attribute, which the docx and the PDF and HTML exports read. The editor's table is `EditorTable` (`apps/docs/src/components/docs/extensions/table.ts`), TipTap's `Table` with `resizable` on. The setting adds plugins and no attribute, so the stored doc and the server's schema are the same with it or without it, and it stays out of `getDocExtensions`, which the server builds headless.

A drag follows Google Docs: the border between two columns moves width from one to the other, so the table keeps its width, and each column stops at `MIN_TABLE_COLUMN_PX`. Only the table's right edge changes the table's width, up to the block the table sits in: the text column, or a list item or a cell inside it. prosemirror-tables' own drag sets one column's width, so a table that fills the text column could only grow, and `TableWidthClamp` would then shrink every column, the dragged one included. So `EditorTable` takes over the drag from mousedown to mouseup and keeps the rest of columnResizing: the hover that finds the border, the handle and the cursor. During a drag it takes the editor's mousemove and mouseleave ahead of columnResizing, so the hover never moves the handle. A collaborator may edit the doc during a drag, and y-tiptap applies every remote change as one replace of the whole document, which no mapped position survives. The table's node view does, so the drop finds the table from the DOM it dragged (`tableOf`) and reads it again: a table that moved or gained rows takes the dragged widths, a table whose column count changed keeps its own and draws them again, and a table deleted meanwhile takes nothing. A cell spanning both columns keeps its total and splits it anew. The first drag on a table stores every column's drawn width, because a column left without one would take whatever room the layout leaves it. A drag that ends where it started, a click, writes nothing. Only the primary button without control or command drags, as prosemirror-tables' `tableEditing` reads them, so macOS's control-click, its right-click, doesn't: another press on a border is swallowed, or columnResizing's own mousedown would start its drag and write the column's width. A drag whose mouseup was lost, outside the window or to a native menu, ends at the first move with no button down, where the last move with the button down left it. `TableWidthClamp` still caps at the text column, as an `appendTransaction` can't measure a table the view hasn't drawn yet, so a nested table pasted wider than its list item or cell is cut by `.tableWrapper`'s `overflow: hidden`.

The table draws through prosemirror-tables' `TableView`, not TipTap's. TipTap's never clears a column's width, so an undo that takes `colwidth` back to none left the dragged widths on screen.

A coarse pointer gets no resize. prosemirror-tables reads mouse events only, so a finger drags nothing, and a tap beside a border fires the compatibility mousedown that starts a drag, which swallows the caret and writes the column's width. So the handle has no touch variant.

Format › Table › Distribute columns and the table panel's button run `distributeColumns`, a command of `EditorTable`: every column gets one width, the table's own width split evenly, or the width of the block the table sits in when a column has none and the table draws at full width. A table whose columns already have that width is left as it is, so no empty undo step. `table.test.ts` in `apps/docs/src/test/components/docs/extensions/` drives drags through the plugins and pins the undo and the split, and `table-width-clamp.test.ts` beside it pins the clamp.

## A cell's fill is a color on the cell

`tableCell` and `tableHeader` carry `backgroundColor`, a lowercase `#rrggbb` (`packages/lib/src/docs/eigendoc/nodes/table-cell.ts`), drawn as the cell's `background-color` in the editor and every export and read back from a pasted cell's style, Google Docs' included. A peer or a paste can write any string, and it lands in a style and a docx's `w:shd`, so `readCellBackground` keeps only that form and reads anything else as none. The table panel's Fill row and Format › Table › Cell background color set it on every cell a selection holds; a header cell without one keeps the header's grey. The docx: [EXPORT.md](EXPORT.md#a-cells-fill-is-its-wshd-both-ways).

## A font is stored as its name

The `textStyle` mark stores a font's name, and renders it as a CSS stack. A doc that still holds a stack is collapsed to names by `normalizeFontFamilyMarks` when an editor with write access opens it, outside the undo history. The reasons are in [TYPOGRAPHY.md](TYPOGRAPHY.md#docs-and-the-canvas-store-a-font-name-never-a-css-stack).

## A font size is a number in points on the font's mark

A size is the `fontSize` attribute of the `textStyle` mark (`packages/lib/src/docs/eigendoc/nodes/font-size.ts`), in points, as Google Docs and Word store it. Text without one draws at the doc's Normal size ([§ A doc stores its Normal text](#a-doc-stores-its-normal-text-in-a-style-map-beside-its-page)), by default the body's 11 pt (`DOCUMENT_FONT_SIZE`, which `looks.test.ts` holds to `eigen-prose.css`, as it holds Small's 9 pt, `SMALL_FONT_SIZE`), and a heading, the title and the subtitle at their own. Every reader of the attribute goes through `readFontSize` (`@workspace/lib/constants/fonts`): the parse, the render, the docx reader and the docx writer. Any peer writes it, and y-prosemirror hands the stored value to `renderHTML` without a parse, so only a finite number is a size, and it lands on Google's 1 to 400 pt in Word's half points. A string or `NaN` renders no size at all. A paste reads `pt` and `px`; `em`, `rem`, a percentage or a keyword is relative to what the source drew around the text, so it gives none.

The toolbar's "− [11] +" between the font and Bold is `FontSizeStepper` (`@workspace/ui/components/media`), the one Sheets has too. It shows the size the selection draws at, read by `selectionFontSizes`, and stays empty for a mix, as Google's does. A heading's or a title's size lives in `eigen-prose.css` alone, so that reader takes it off the page with `getComputedStyle`. A typed size sets one size on the range (`applyFontSize`). A step, from the buttons, Format › Text › Size or ⌘⇧. and ⌘⇧,, moves every run a point from its own size (`stepFontSize`), so a mix stays a mix, as in Google Docs and Word.

## Small stays in the schema and leaves the menus

The `small` mark draws text at 9 pt, a little spaced. A size took its place, and no menu offers it. It stays in the schema because the Yjs binding deletes the text that holds a mark the schema lacks, the whole paragraph's run of text ([§ A tab older than the schema](#a-tab-older-than-the-schema-deletes-the-nodes-it-does-not-know)), and docx imports wrote it into stored docs. So it still renders as `<small>`, the toolbar reads it as 9 pt, and setting or stepping a size replaces it. The docx writer writes its look, and the reader reads that back as a 9 pt size.

## A paragraph's format is six numbers on its textblock

A paragraph, a heading, the title and the subtitle hold Word's and Google Docs' paragraph properties as attributes of their own (`EigenParagraphFormat`, `packages/lib/src/docs/eigendoc/nodes/paragraph-format.ts`, with its values and readers in `eigendoc/paragraph-format.ts`): `lineSpacing`, a multiple of the font's single line as both apps store it, and `spaceBefore`, `spaceAfter`, `indentLeft`, `indentRight` and `indentFirstLine` in points, a negative first line being a hanging indent. Null is the doc's own look, its Normal for a paragraph. A list keeps its structure: its items nest by level, not by an indent. Every reader goes through `readParagraphFormat`, the parse, the render and the docx reader and writer, because any peer writes the attributes and the Yjs binding hands them to `renderHTML` unparsed. Only a finite number is a value, within its bounds (line spacing 0.5 to 5, spacing 0 to 400 pt, an indent within Word's largest page) and at Word's step, a hundredth of a line or a twentieth of a point. The editor's commands also keep an indent within the doc's text column, which the page setup gives the extension (`textColumnWidth`, as `TableWidthClamp` takes it). `indentLeft` is where the body lines stand and `indentFirstLine` the first line's offset from them, as Word's `w:left` with `w:firstLine` or `w:hanging`, so the docx reader and writer map them one to one. Alignment is TipTap's `textAlign` beside them (`eigendoc/extensions.ts`), which writes `text-align` only for a non-default alignment, so null means left.

A list, a quote and a table cell own the spacing of what they hold. Only a textblock whose parent is the doc stores a space before or after: `setParagraphFormat` skips them elsewhere, the menu's Add and Remove space and Custom spacing's Before and After are disabled there, `eigen-prose.css` draws none for a paragraph there even if it stores one (it became an item after it was set, say), and the docx reader and writer leave it to the container. Line spacing and indents apply everywhere.

CSS draws a line spacing as `line-height` of the multiple times 1.21, Inter's single line (`DOCUMENT_LINE_RATIO`, Inter's `EIGEN_FONTS` line, which `fonts.test.ts` holds to the TTF), because `renderHTML` sees the attributes and not the fonts of the paragraph's runs. A paragraph in another font draws at the same pitch, and the docx writer scales its line by that font's own height so Word draws it alike ([EXPORT.md](EXPORT.md#the-docx-line-is-a-multiple-of-each-fonts-own-line-height)). Eigen's own look is declared in the same numbers, line spacing 1.4, nothing before and 11 pt after (`DOCUMENT_PARAGRAPH_FORMAT`), which `eigen-prose.css` draws as 1.694 and 11pt where the doc's Normal sets nothing, a paragraph after a paragraph without a margin above, and `looks.test.ts` holds the two together. Space before draws as `padding-top` with no margin above, so it adds to the space after the block above, as Word and Google Docs add the two, where CSS margins would collapse to the larger; it replaces a heading's own margin above.

The HTML carries each value twice, as CSS and as a `data-` attribute, and a paste reads the `data-` attribute only. Google Docs writes `line-height:1.38;margin-top:0;margin-bottom:0` on every paragraph, which would give every pasted paragraph a format typed text lacks; another app's paragraph CSS is its own look, so a paste takes the doc's, while a docs copy keeps its format.

Format › Line & paragraph spacing has Google's Single, 1.15, 1.5 and Double, ticked where every selected paragraph stores that value or draws it from the Normal, so none for Eigen's own 1.4. Add and Remove space before or after reads what the first selected paragraph draws, a heading's off the page, and adds Word's 12 pt. Custom spacing… and Format › Align and indent › Indentation options… open on what the first paragraph draws and write only the fields that changed, to every paragraph selected, so an unset paragraph keeps the doc's look. Indentation options' Left is `indentLeft`, where the body lines stand, as in Google Docs, and Hanging puts the first line that far left of them. Increase and Decrease indent (⌘] and ⌘[) move each paragraph to the next multiple of 1.27 cm, and in a list sink or lift the item instead, as Tab does; they always take the key, as ⌘[ is the browser's Back. A band's editor shares the schema, so a header's paragraphs take a format too. Clear formatting resets the six with the rest, as Google's does, because `clearNodes` gives every textblock it touches its default attributes. The icon row has no spacing or indent buttons: its breakpoints are measured widths, so a button would mean measuring the row again in a browser.

## Caps are an attribute of the font's mark, drawn over the letters as typed

All caps and small caps are the `caps` attribute of the `textStyle` mark (`packages/lib/src/docs/eigendoc/nodes/caps.ts`), `'all'` or `'small'`, beside the font's name. The typed letters never change: the editor and every export draw the capitals with CSS, `text-transform: uppercase` and `font-variant-caps: small-caps`. So search, a plain-text copy and toggling caps off all get back what was typed, as with Word's `w:caps` and `w:smallCaps`. One attribute holds both because Word's two properties exclude each other, and where a paste or a docx sets both, all caps wins, as Word draws it. Small caps are written as the longhand, because the `font-variant` shorthand would turn the ligatures the editor switches off back on.

Mod-Shift-A toggles all caps, as in Word. Small caps get no key: Word's Mod-Shift-K reaches the command palette, whose listener takes Mod+K with or without Shift (`use-palette-shortcuts.ts`).

## The PDF fakes small caps where the font has none

A browser fakes small caps in a font that has none, so the editor, quick look and the HTML download show them in every font. WeasyPrint fakes nothing: it draws `font-variant-caps` only from a font's own small-caps glyphs (the OpenType `smcp` feature), which of the bundled fonts only Source Serif 4's upright face has, marked `smallCaps` in the fonts table (`FONT_FILES`, `apps/api/src/lib/export/fonts.ts`). So the PDF's HTML fakes them itself: in Inter, JetBrains Mono, Excalifont and italic Source Serif 4, a small-caps run's lowercase letters are written as capitals in a span at 0.7em, the size Chromium and WebKit fake them at. Its capitals and everything else stay as typed. Upright Source Serif 4 keeps its real small caps. A run counts as italic under the italic mark, or in a blockquote while eigen-prose.css sets a quote in italic (`QUOTE_LOOK`, `apps/api/src/lib/document/looks.ts`). `renderDocHtml` does this behind its `smallCapsFont` option, the doc's Normal font that a run without a font mark draws in, which `renderEigendocExport` sets for the `pdf-html` format only, so the HTML download keeps the letters as typed. Word fakes small caps itself, so the docx shows them everywhere.

## A list's numbering lives on the list, so restarting it splits the list

An `orderedList` stores its style as `type` (`1`, `a`, `A`, `i` or `I`) and its first number as `start`; an item carries no number of its own. A list with no type numbers by depth, as Google's default 1. a. i. does: decimal, then lower-alpha inside a numbered list, lower-roman two deep, and round again, from `.eigen-doc`'s rules in `eigen-prose.css`, which a mail or chat editor doesn't take, as its sent HTML would number 1. 1. 1., which the docx writer reads too ([EXPORT.md](EXPORT.md#bullet-lists-share-one-numbering-definition-and-each-ordered-list-has-its-own)). A type the list stores is drawn on the list itself and wins, so a list set to 1. 2. 3. stays decimal at any depth, and decimal is stored as `'1'`. Numbered list ticks what an untyped list draws, read off the page. Format › Bullets and numbering › Numbered list sets `type`, and List options › Restart numbering sets `start` (`apps/docs/src/components/docs/list-numbering.ts`). Both act on the innermost list around the caret, and only when that list is numbered, so a bulleted list nested in a numbered one greys List options. A restart at the first item sets `start`; past it, the list is split before the item into two lists, the second with the new `start` and the same `type`, as Google does. The docx writer gives each list its own `w:num`, so two lists side by side import apart even when the second's numbers run on from the first's.

## Word count reads the editor's text, and its key belongs to the page

Tools › Word count counts the doc, and the selection out of it when there is one, as Google Docs does: words, characters, and characters excluding spaces (`countWords`, `apps/docs/src/components/docs/word-count.ts`). It reads ProseMirror's own text, so table cells, list items and figure and chart captions count, and alt text, comment threads, media names and footnotes don't, as in Google Docs; a reference ends the word before it. A word is a whitespace-separated token holding a letter or a digit. A character is a grapheme, and a line break is none. The dialog counts once as it opens, so a collaborator's typing never recounts the doc behind it. It shows no page count, because the editor draws one long page and the browser has no page to count ([ROADMAP.md](ROADMAP.md)).

A viewer counts too, so Mod-Shift-C is a document-level hotkey (`useHotkey` in the toolbar), not an editor keymap: ProseMirror runs no keydown handler while the editor is not editable.
