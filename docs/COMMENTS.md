# Comments

> **TLDR:** A comment is a card pinned to a piece of a document, with a chat thread under it for the replies. Docs, sheets, stickies, slides and vector share one comment model, and each app only decides how a card anchors to its content. Hooks live in `packages/lib/src/core/comments/`, components in `packages/ui/src/components/comments/` and `cards/`, the server side in `apps/api/src/lib/chat/`.

A user selects something in a document, such as a run of text, a cell, a shape or an image, and adds a comment. They see a card with a title, a description, a color and optional attachments, and under it a chat thread for the replies. A comment can be resolved and reopened, and assigned to a member of the document. In Docs, Sheets, Slides and Vector the comments column at the right lists them and opens one thread at a time; Stickies lists its activity in a column as wide as the comments list and opens a card in a dialog. A mouse resting on a comment shows its card. On a stickies board every card is a comment card.

Each app that shows comments is called a host. A host decides only where a card anchors, such as a mark on text in a doc or a list of card ids on a sheet cell. The shared hooks and components do the rest, so a change to comments lands in every app at once.

A comment is spread over three stores in the document's container, the Drive folder that holds one document, such as `Notes.eigendoc` ([STORAGE.md](STORAGE.md)). The card lives in the document's Y.Doc, the shared Yjs state every editor holds a copy of ([COLLAB.md](COLLAB.md)). The thread is a chat in the container's `chat/` folder ([CHAT.md](CHAT.md)). And `comments.db` keeps one index row per thread ([A comment lives in three stores](#a-comment-lives-in-three-stores)).

Four things surprise people:

- Text and color are collaborative Yjs state, but status and assignee are written by the server, which records the activity row and sends the notification ([A comment lives in three stores](#a-comment-lives-in-three-stores)).
- A delete strips the anchor and keeps the card, so whatever brings the anchor back, such as an undo or a version restore, brings the whole comment back ([A delete strips the anchor and keeps the card](#a-delete-strips-the-anchor-and-keeps-the-card)).
- A link to a deleted comment still opens it, as "This comment was deleted" with nothing that acts ([A deleted comment shows as deleted wherever it is reached](#a-deleted-comment-shows-as-deleted-wherever-it-is-reached)).
- On a phone the column hides the editor instead of unmounting it ([On a phone the column hides the editor, never unmounts it](#on-a-phone-the-column-hides-the-editor-never-unmounts-it)).

## A comment lives in three stores

The card (`CommentCard`, `packages/lib/src/types/comments.ts`) is an entry in a Y.Map on the document's Y.Doc: title, description, color, attachments, creator, and the name of its chat, which every card has. Stickies keeps its cards in the `tasks` map and every other app in `comments`. The thread is an `.eigenchat` in the container's `chat/` folder, linked from the card by `chatName`. Its hooks (`useComments`, `useResolveComment`, `useAssignComment`) live in the chat domain, because a thread is a chat room and chat's SSE events invalidate them, and `@workspace/lib/comments` re-exports them beside the card hooks. The index is `comments.db` beside `data.db`, one row per thread keyed by that chat name. So a container holds child items by design: its `chat/` threads, its `media/` folder, and each thread's own `media/`. A guard that refuses to create or copy under a container breaks comments and inline media.

Each fact lives where its writer is. Text, color and creator change in the editor, so they ride y-websocket like any other edit, reach peers live and need no REST route. Status and assignee go through the API, because a resolve or an assignment records an activity row and an assignment notifies someone, and the server has to do both. Reply count, last author and the search text are derived from the thread by the server on every message. So `comments.db` is not a cache: losing it loses every status and assignee.

## The card is sanitized where it is read

`readCards` (`hooks/use-comment-cards.ts`) is the one function every consumer of a card reads through. It sanitizes the description with `sanitizeCommentCardHtml`, the LightEditor allowlist plus task lists, and drops malformed attachments. Any peer can write raw values into the Y.Doc, and the description reaches `dangerouslySetInnerHTML` in every viewer. It skips a card without a string `chatName`, which no editor writes, so such a card shows nowhere while its bytes stay in the Y.Doc. That test is `isCommentCard`. A board shows a column's ids joined with the cards this read holds, so it never shows a card the read skipped, and a writer's open of the board gives such a card a thread ([STICKIES.md](STICKIES.md#a-writers-open-gives-a-card-without-a-thread-its-own)). The server's reader (`documentReferences`) throws on one instead, so a sweep of its document deletes nothing.

`useCommentCards` reads the map synchronously on mount. A host that mounts after sync must see its cards on the first render, or for one render a `?chat=` landing finds no card and reads as deleted or closes. It also keeps a card object's identity while its fields are unchanged, so memoized card components skip the re-render.

## Each app anchors a card in its own content

| App | Anchor |
|---|---|
| Docs | The `comment` mark on text (`cardId`, `data-comment-id` in HTML); an image's, a chart's, a text box's or an equation's `commentCardId` attribute |
| Sheets | `Cell.commentCardIds`, an array of card ids |
| Stickies | The card id in a column's `taskIds` |
| Slides, vector | `VectorElementBase.commentCardIds`, a JSON id string, because every stored canvas field is a scalar ([CANVAS.md](CANVAS.md#every-stored-field-is-a-scalar)) |

`useCreateCommentCard` creates the chat, then writes the card and runs the host's anchor callback inside one Y.Doc transaction, so in docs and stickies the card and its anchor are one undo step. The callback must be synchronous: anything it defers escapes the transaction. The canvas is the exception: it anchors once the card exists, as an untracked write, because its `comments` map is outside the undo scope ([CANVAS.md § One discrete op is one undo step](CANVAS.md#one-discrete-op-is-one-undo-step)).

A docs image, chart, text box or equation anchors through an attribute, not the mark, because the Yjs binding persists marks only on text: a mark on the node would vanish on reload and never reach a peer. `nodeCommentCardId` (`apps/docs/src/components/docs/extensions/comment-mark.ts`) reads either form, and everything outside the figure's node view goes through it: the active set, the decorations, scroll-to and delete. A text selection that spans a figure, a chart or an equation marks only the text. A new card's title starts as the selection's text (`commentAnchorText`). A figure reads as "Image", a chart as "Chart" and a text box as "Text box", so a comment on one alone has something to quote. An equation reads as its linear form (`x/2`), or "Equation" when empty, and a page number as `#`.

A cut image keeps its card, because the cut serializes the figure's `data-comment-id` like the mark and the card stays in the document's `comments` map. A paste keeps only the anchors that map holds: `cleanPastedHTML` (`apps/docs/src/components/docs/paste.ts`) strips every other `data-comment-id`, so content copied from another document arrives without anchors to cards this one lacks. A docs-to-docs paste of an image goes through the copy's HTML too, so in its own document a copied image keeps its card like copied text does. Pasted into a slide or a sheet, it arrives as an image item, which carries no card. A canvas paste clears `commentCardIds`, so a canvas copy starts without comments.

## A docs image opens its own menu and paints its own mark

ProseMirror never sees a right-click inside a node view, so the figure's node view hands it to the `Figure` extension's `onContextMenu`. The editor node-selects the figure and opens the image menu (**Download original image**, then the card's rows or **Add comment**) only when a row will render; otherwise the browser's menu shows. A commented figure or equation paints the canvas' `CommentIndicator` in its top-right corner, in the color a node decoration carries, resolved cards included, and only that mark opens the card: a click on the atom itself selects it. The node view re-renders on every update, because TipTap skips a decoration-only change and the color arrives as one. A chart's node view draws in the same frame (`FigureFrame`), so a chart does all of this too, with Download image in place of the original ([EXPORT.md](EXPORT.md#a-drawing-downloads-its-own-svg-and-prints-as-layers)). A table cell's and an equation's menus draw a card's rows the same way ([DOCS.md](DOCS.md#a-table-cell-and-an-equation-have-right-click-menus-of-their-own)).

## A delete strips the anchor and keeps the card

A delete takes the card's id out of the content and leaves the card, its thread and its index row where they are, until Delete history or a copy removes a thread nothing names ([Delete history and a copy remove a thread nothing names](#delete-history-and-a-copy-remove-a-thread-nothing-names)). The panel shows only active cards, the ones the host finds in use, so the deleted comment disappears from view. An undo or a version restore that brings the anchor back brings the whole comment back, thread included. A restore moves only the anchors and leaves the cards alone, because the `comments` map is not one of the document's declared `yjsRoots` ([COLLAB.md](COLLAB.md#a-version-restore-rewrites-an-open-document-in-one-transaction)).

The canvas also marks the card deleted with `deletedAt`, because on the canvas a card that no element anchors is a document-level comment, not an orphan: stripping the anchor alone would leave it in the panel. Its active set, `activeCommentCardIds` (`packages/lib/src/vector/comments.ts`), counts a card that an element anchors or that is not marked. So a card whose element was deleted stays in the panel as a document-level comment, and a deleted card whose element comes back, through an undo of the element's delete or a restore, shows again. It keeps its `deletedAt`, so it shows only while an element anchors it: once that element is deleted again, the card hides, as a comment on deleted text hides in docs. A card raised from the comments column is document-level from the start.

The canvas writes the mark and strips the id from every element that holds it in one untracked transaction (`deleteCommentCardInDoc`), and appends the id to its element after `createCard` resolves, untracked too. The comment map is outside the canvas undo scope, so a ⌘Z that moved only the anchor would bring back a card the user deleted, or turn a new comment into a document-level one. The append is idempotent, so a double submit lists the card once.

Stickies is the exception. Its `tasks` map is a declared root and in its undo scope. A delete removes the card from its column and from `tasks` in one transaction (`deleteCardFromBoard`), so one ⌘Z brings back the card and its place. A restore rewrites the cards too: a card added after the version drops off the board while its thread and row stay, and an edit made since to a card's text or color reverts. A link to such a card's thread still opens it as deleted, through its index row ([A deleted comment shows as deleted wherever it is reached](#a-deleted-comment-shows-as-deleted-wherever-it-is-reached)).

## A deleted comment shows as deleted wherever it is reached

A card is deleted when its host no longer uses it, or when its thread is gone from `chat/`, which the sweep does ([Delete history and a copy remove a thread nothing names](#delete-history-and-a-copy-remove-a-thread-nothing-names)). One rule says so, `useIsCardDeleted`, and the lifecycle hands it out as `isCardDeleted`. The card dialog, the pane and the comment menus read it, so a `?chat=` or `?card=` landing, a notification's link, an activity row and a comment search hit all open the same deleted state (`DeletedComment`): the title grayed and "This comment was deleted", with no thread, no description and nothing that acts. The menus keep only View and Delete. A resolve or an assignment on a gone thread would only get a 404, a reply has no thread to go to, and a card nothing anchors would otherwise open through a link as if it were live.

A comment whose card is gone from the map, such as a card deleted from its board, is deleted too. Its chat name still reaches it while `comments.db` holds its row, and it shows the row's `title`. The server writes that title only with a resolve or an assignment, so a card nobody resolved or assigned reads "Comment" ([ROADMAP.md](ROADMAP.md)). The open thread is the URL's `?chat=` ([The open thread is the URL's ?chat=](#the-open-thread-is-the-urls-chat)), and it resolves by name on every render: to the card that holds it, else to the row. So a card deleted from its board while its thread is open turns into the deleted state, rather than closing, and the bundle's `openChat` writes a name whether a card holds it or only a row does. Every host's activity row goes through it, and so does a search hit. A host that shows a card's anchor before it opens the card, such as docs, sheets or a canvas, passes its own `openCard`, and `openChat` hands it a card the name finds. A name with neither a card nor a row opens nothing, and a `?chat=` that names neither closes as the host closes a thread. A `?card=` link and a `card-added` or `card-moved` activity row carry only the card id, so for a card deleted from its board they open nothing ([ROADMAP.md](ROADMAP.md)).

Neither half decides early. The active set counts only once the host's `ready` is true, or every landing in docs would show the deleted state for the 200 ms before its first walk of the body. A `?chat=` also waits for the index rows, or a card deleted from its board would read as not found. A `?card=` landing names only a card, so it waits for the cards alone before it becomes that card's `?chat=`. A thread counts as gone only once the chat folder's refetch settled (`isChatMissing` on the media resolver, the twin of `isMediaMissing`), so a new comment whose thread the listing doesn't hold yet never flashes deleted. While it waits, the thread shows the loading line. The lifecycle reads the resolver, so the resolver has to sit above the editor that calls `useCommentLifecycle`. Every editor route renders `EigenDocEditorRoute`, which provides `MediaResolverProvider` around the editor, so no host provides its own.

The comments list shows only active cards, so it shows the deleted state only for a card whose thread went while the card stayed anchored, such as one another tab anchored again after the sweep, through an undo.

## Delete history and a copy remove a thread nothing names

A deleted comment's thread stays while something could bring its card back, which is any saved version. So nothing removes it on its own. Delete history, once the versions are gone, and a copy, on the copy, run the sweep that deletes unnamed media ([MEDIA-REFERENCES.md](MEDIA-REFERENCES.md#a-file-stays-until-delete-history-or-a-copy-and-then-only-while-the-state-names-it)), which also deletes a thread in `chat/` when no card in use names it and nobody created or wrote in it for 72 hours. A copy has no grace, but deletes only a thread it wrote itself, so a comment someone starts in it before its sweep runs stays. A card is in use when its host's active set holds it: anchored in docs and sheets, on the board in stickies, anchored or not marked deleted on the canvas. The server reads that rule through `documentReferences` (`apps/api/src/lib/document/references.ts`).

The thread goes first, through `Mount.deletePath`, and only then its row in `comments.db` and its `comment_mentions` rows (`CommentIndex.deleteRowsWithoutThread`), for every thread no longer in `chat/`. The mentions have no foreign key, so they go by name, and the search hit follows the row through the `comments_ad` trigger. The order matters: a thread that stays without its row heals as open and unassigned and loses its status, while a row whose thread went is harmless. No person can trash a thread on its own ([STORAGE.md](STORAGE.md#a-person-only-adds-new-files-and-threads-inside-a-document)), so a thread missing from `chat/` is gone for good, or in the trash with its whole document.

The card stays in the document's card map as dead bytes, because the sweep never writes the document. The activity rows that name the thread keep their entries ([FILE-HISTORY.md](FILE-HISTORY.md)).

A thread's last write is the newer of its own `createdAt` and the `updatedAt` of its `data.db` row. A write stamps that row when the database syncs, within 30 s, so a reply through a notification keeps the thread for another 72 hours, and a reply in the last seconds before a sweep may not. That is accepted: it takes a reply to a deleted comment's thread, untouched for 72 hours, within 30 s of Delete history. A database stays open for five idle minutes after any use, and on a disk mount its close stamps the row too, so a thread someone just read counts as written.

## A thread's own media go when no message names them

Inside each thread it keeps, the sweep runs again with the thread as the document: a file in the thread's `media/` goes when no message names it, a deleted message's included, and it is past the grace. `ChatRoom.deleteMessage` also deletes a deleted message's files itself ([CHAT.md](CHAT.md)), so a version of a thread can name an attachment that is gone. No screen restores a thread version.

## Card attachments are staged until Save

Attachments reuse chat's wire type, `ChatAttachment`: a string names a file in the container's `media/` folder, a reference points at a drive item. The form stages drafts locally and `useResolveCardAttachments` settles them on Save, so Cancel leaves nothing behind. A device file uploads into `media/`. A regular drive file is copied there, because the container's ACL must cover it for every collaborator, the same rule as chat ([CHAT.md § Attachments live in the room's media folder](CHAT.md#attachments-live-in-the-rooms-media-folder)). A container stays a reference. A failed upload aborts the save, so no card is half-attached. A container without a media folder hides the attachment controls.

Removing an attachment leaves its file in `media/` on purpose, like an inline image in a document, so an undo that puts the attachment back finds its file. A version restore does not bring a removed attachment back, because it keeps today's cards, except in stickies, whose cards are part of the board it restores. What a restore brings back is a card's anchor, and with it the card as it is today, attachments included. The sweep runs only once no version is left, or on a copy that has none, so it keeps the files the current state's cards in use hold. Attachments on the thread's messages are the chat's own and live in the chat's `media/`.

## A thread's index row is seeded at creation

`Drive.create` seeds the row when a chat is created inside a container's `chat/` folder (`seedCommentRow`). A standalone chat has no container and gets no row. `ensureComment` leaves a row that exists alone. Posting a message calls it too, so a thread that lost its row gets a new one on its first message. The frontend treats a missing row as open and unassigned (`matchesCommentFilter`), so a card shows before its row exists.

A status or assignee write answers 404 when the name has no row. Without that it would write an activity row and a notification while the card stayed open and unassigned. Both writes need write access, through the `SharedDrive` wrappers of `Drive.setCommentStatus` and `Drive.assignComment`.

## Every index write reaches the other clients

`ChatRoom.updateCommentIndex` wraps every write a message causes: it opens the index, runs the change, recomputes the search text and sends `CHAT_COMMENT_INDEX_UPDATED` to the owner's home and every effective member. `Drive.setCommentStatus` and `Drive.assignComment` send the same event through `broadcastCommentIndexUpdated` (`apps/api/src/lib/chat/sse-events.ts`), so a resolve or an assignment shows up live in every open tab. The seed at creation sends nothing; the creating client refetches the list itself in `useCreateCommentCard`. Cross-home delivery goes through the home relay ([SCALABILITY.md](SCALABILITY.md)).

## Search reads a recomputed tail of each thread

`recentText` holds the newest 8192 characters (`RECENT_TEXT_CAP`) of a thread's messages, and the FTS5 table `comments_fts` indexes it for the in-document find bar ([IN_DOCUMENT_SEARCH.md](IN_DOCUMENT_SEARCH.md#comment-threads-are-searched-on-the-server)). It is rebuilt from the live messages on every indexed write, not appended to, so a deleted message stops matching and an edit never matches twice. The chat reads the text right before it writes it, inside the comment index call, after the member lookup and the broadcast. So a post that waits on those never writes a text from before a later post. Two writes that both fall in the short read-and-write itself can still leave the older text, until the thread's next write. Whispers stay out of it and out of the index entirely. A built-in emote goes in as the third-person sentence a bystander reads (`searchableMessageText`), not its stored key, so a search for its words finds it. The people an emote names go in by name and email, looked up when the text is rebuilt, because a search finds a person by either ([CHAT.md](CHAT.md#emotes-are-stored-as-keys-and-phrased-per-viewer)). So a rename, or a thread whose text was built while the index held only emails, shows the new form only after the thread's next message, edit or delete. A failed lookup leaves the email alone and still writes the text and sends the update event. Text past the cap is not searchable; the full history lives in the thread's own `data.db`, out of reach of a query on `comments.db`. The FTS update trigger fires only when `recentText` changes, so status, count and assignee writes never re-index the body. The migrations are pinned in `apps/api/src/test/comments/`.

## Assignment is a member's email, set by the server

The assignee is a lowercased email that must belong to an effective member of the document, or the route answers 400. A real change records an `assigned` activity row. The assignee is left out of the watcher fan-out and gets a direct notification instead, unless they assigned themselves or have no account ([NOTIFICATION-CENTER.md](NOTIFICATION-CENTER.md), [ACTIVITY-ROWS.md](ACTIVITY-ROWS.md)). Picking the current assignee again, and unassigning, record no row and notify nobody.

The same assignments send a mail, under two server-wide flags ([SERVER-SETTINGS.md](SERVER-SETTINGS.md#the-notification-flags-gate-the-email-only)), because a guest rarely has Eigen open and one who never signed in has no bell. An address with no account counts as a guest: it gets the mail and no notification, as it has no home to hold one. The mail names the card title and links to the card with `?chat=`. A recipient off the mail domain goes through the guest login and returns to the card, because `buildAttachmentUrl` adds `?email=`, so a password user off the domain lands on the Guest tab, as with a share mail. The send is detached, so a slow mail relay does not hold the assign route.

The limit is one mail per person and document an hour (`assignMailWindow` in `apps/api/src/lib/drive/assignment-propagation.ts`). A notification folds a repeat on its tag, but a mail cannot, so working through a board would otherwise send a mail per card. Later cards in that document inside the hour reach the assignee only in the app: the bell, the toolbar badge in docs, sheets, slides and vector, and on a board the ring on their avatar (`CardTile`). An address with no account hears of them only when it signs in. The window lives in the API process, so a restart forgets it, and a `false` from `sendMail` frees it, so the next assignment retries.

The client posts the card title with every status and assignee write, and the server caches it in `title` for activity labels. It trusts the client the way the stickies card events do ([FILE-HISTORY.md](FILE-HISTORY.md)), and it lags a rename until the next action, so the UI never reads it and reads the card instead.

The toolbar badge counts the open, anchored comments assigned to you (`useAssignedCommentCount`). It is personal because a document-wide unresolved count would show every viewer the same red number, for threads that belong to someone else. `CardTile` marks the same thing on the card: its footer is muted, but the avatar of an open card assigned to you is not, and it has a ring in the app's color.

Mentions are recorded in `comment_mentions` on every message, and nothing reads them ([ROADMAP.md](ROADMAP.md)).

## One lifecycle bundle drives every host

`useCommentLifecycle` holds the card read, the server entries, create, update, resolve, assign, the card a delete is asked for and the deleted rule, and derives from the host's `?chat=` the open comment and whether the chat names nothing (`chatMissing`). It opens and closes nothing. `useCommentHost` (`packages/ui/src/components/comments/`) adds the opens, which write the URL, and hands the components the bundle (`CommentLifecycleBundle`): the comment menus, `CommentLifecycleDialogs`, `CommentCardDialog`, the comments column and the sheet's cell menu all take it. `mapName` picks `comments` or `tasks`, as `commentMapName` decides for a document type, the rule the server's reader uses too. Every host passes `ready` once its cards have synced and its active set is computed: docs after the first walk of the body, sheets once its workbook loaded and names its sheets, the canvas and stickies on `loaded`. A landing waits for it instead of resolving against an empty map, and opens the card in the state the host shows it in. It stays true through a disconnect, as `loaded` does ([COLLAB.md](COLLAB.md#the-client-gates-on-loaded-never-synced)): on live `synced` a dropped socket would hide the open card, close its thread and drop an edit in progress.

A delete from the edit form or `CommentContextMenu` asks first, in the `DeleteCommentDialog` that `CommentLifecycleDialogs` mounts, which then runs the host's delete and, when the card is the open one, closes it as the host closes a thread, since a host that keeps a deleted card would otherwise leave it open in its deleted state. The sheet's cell menu asks with the same `DeleteCommentDialog`, mounted in the sheet's dialog slot, which outlives the menu and passes `onCloseAutoFocus` so the focus goes back to the grid. Docs' image, table and equation menus ask in the bundle's dialog too: their `part="delete"` row hands the card id to the lifecycle's `requestDelete`.

`CommentLifecycleMenuItems` binds the shared rows (view, edit, color, assign, resolve or reopen, delete) to that bundle. It gates every write on `canWrite` in one place, and the host supplies only what its anchor decides: the item under the cursor, add and delete. So a new row lands in every app at once. It renders in `CommentContextMenu` (through `CommentLifecycleDialogs`, which every editor mounts), in the sheet's cell menu and in docs' image menu. Every row is a real menu item, so selecting one closes the host menu.

Adding a comment opens the form client-side; the server is touched only on Save. `CardForm` creates with concrete values (a trimmed title, a seeded color) and edits with a patch of the changed fields only, so an unchanged save writes nothing to the Y.Doc. An opened card is `CardDetail`, which hands its title, actions, body and edit form to the frame its host draws, so the card reads the same in any frame while each frame keeps its own save spinner and "Discard changes?". `CardDialog` is that frame on a board: editing happens in place inside it, never in a stacked dialog. The comments column is the other frame, which opens the edit form in a dialog of its own ([In Docs, Sheets, Slides and Vector, comments open in a column the URL names](#in-docs-sheets-slides-and-vector-comments-open-in-a-column-the-url-names)). Edit mode is pinned to a card id in the bundle, so opening another card lands in view mode.

## A visitor sees the cards as stored and nothing from the server

A visitor, someone with no login on a document a public link opens ([ACL.md § A public link opens a path to anyone without a login](ACL.md#a-public-link-opens-a-path-to-anyone-without-a-login)), loads the document's stored state and so reads every card as it is stored: its title, description, color, attachments, time and `creator`, the author's email address. The server's side is closed to them: the thread routes, the comment index and the member list all need a login. So `useCommentLifecycle` runs no index or member query when `useAuth()` has no user, `CommentThread` finds no chat for a card's name and shows the card without its replies, and `useCommentsColumn` and the Stickies board offer no Activity.

A reader without a socket, a visitor or someone signed in who reads only through a link, sees a card added or changed meanwhile within 30 s while the tab is visible, or when it is shown again ([COLLAB.md § Without a socket](COLLAB.md#without-a-socket-the-editor-shows-the-state-it-fetched)).

The deleted rule bends for the same reason as the missing replies. A visitor's listing has no `chat/` folder, so `useIsCardDeleted` counts only the host's use for them: otherwise every card would read as deleted, its thread missing.

The address in the card is accepted, since a card lives in the Y.Doc and a visitor gets the Y.Doc's stored state; [ROADMAP.md](ROADMAP.md) has the row for a card's author and content in the document.

## The open thread is the URL's ?chat=

In every host the open comment thread is the page's `?chat=`, the name a copied link writes (`getDriveShareUrl(path, { chat })`) and every editor route validates. `useCommentHost` reads it from the route's search itself (`useEigenDocEditorSearch`), so no editor hands it down. It is the one open state: the lifecycle takes it as `chat` and holds none of its own. While it is set, the open comment is the card that holds that chat name, else the index row ([A deleted comment shows as deleted wherever it is reached](#a-deleted-comment-shows-as-deleted-wherever-it-is-reached)). One source means a second notification click opens its comment because the URL changed, and a reload shows what the URL says, nothing it said before. A close that wrote the card's state directly would race the router and get the old `?chat=` written back.

`useCommentHost` writes `?panel=` and `?chat=` for every host, Stickies included, through one `useDetailHistory`, so a list and the thread it opened share one history entry. Opening from closed pushes an entry flagged as the detail's own, so a phone's back closes it; opening a thread from a list, such as an activity row, replaces. Closing a thread goes back to the list behind it by replace: the comments column's list, or a board's activity. With no list behind it, such as a board card opened by a click or a link, it closes through `useDetailHistory`'s close, back over its own push and by replace on a link. A delete of the open comment and a `?chat=` that names nothing, once the cards synced and the rows loaded, close the thread the same way. So on a board, Activity, then a card's row, then a delete leaves the one entry of the activity: one X closes it, and back after it opens nothing again. Back never lands on a gone comment; only forward can, where the not-found rule closes it again.

So every open goes through the host: a click on a row of the list, a mark, the hover card or a board card, an activity row, a search hit and the comment menu's Edit all write `?chat=`. A card link's `?card=`, which Drive's activity list and a card's notification write, becomes that card's `?chat=` by replace once the cards are ready, keeping the entry's state, and one that names no card is dropped by replace. Edit mode is pinned to the card id, so Edit lands in the form once the URL names the card. It ends when that card closes or another opens, such as on Back or a second link, so the card opens again in its view; while the form changed, such a navigation asks "Discard changes?" first ([FORMS.md](FORMS.md#a-page-form-with-unsaved-edits-asks-before-you-leave)). `CommentLifecycleDialogs` holds only the comment menu and the delete confirm; in Stickies the card opens in `CommentCardDialog`, which the board renders beside it.

## In Docs, Sheets, Slides and Vector, comments open in a column the URL names

`CommentsColumn` is a detail column ([LAYOUT.md](LAYOUT.md#a-detail-column-opens-at-the-right-under-the-bar-that-spans-the-screen)) with three levels: the comments list at `?panel=comments`, the activity at `?panel=activity` and one thread at `?chat=`. The list is `small`, the width of the properties panel it takes turns with, so switching between them keeps the right slot's width. A thread grows the column to `large`, because reading and writing a conversation needs the room ([LAYOUT.md](LAYOUT.md#a-side-column-is-small-medium-or-large) holds the widths). `?chat=` alone is a thread with the comments list behind it, which is what a copied link or a click on a comment's mark opens. A link opens straight at the thread's width and loads while the cards sync, one that names no comment lands on the list by replace, and a deleted one opens as deleted. Inside an open column the step between the list and a thread eases over 200 ms (`DetailColumn`'s width transition, instant with reduced motion), and each level is laid out at its own width from the first frame, so the column clips it as it grows or shrinks and no text rewraps; opening, closing and a phone are instant, since the column mounts at its width.

`useCommentsColumn` builds on `useCommentHost`, with the comments list behind a `?chat=` that names no list. The toolbar's comments and activity toggles open from closed with a push and close the column; a row opens its thread and `‹ Comments`, or `‹ Activity` from the activity, goes back by replace; X, Esc and a phone's back close the whole column, from a thread too, since Esc means close and `‹ Comments` is the way back. On a phone the list's own bar shows the same `‹ Comments` (or `‹ Activity`), which closes the column, since a phone has no X. A thread that closes lands on the list, so a delete does too.

A row of the comments list is a `CommentCardTile`, as the hover card and a board's drag overlay are, and shows the card's title. A host may add a prefix (`titlePrefixes`), which sheets uses for another sheet's name, as the only location left in the row. A card on several sheets counts as being on its first cell in tab order, so the prefix names where a click goes, even when the card is also on the open sheet. A title seeded from an anchor, such as `Cell B2`, stays as written when the anchor moves. `SortableCard` in stickies maps a card onto `CardTile` itself, because it takes flat props it can memoize.

The list stays mounted under a thread, invisible and at its own `small` width inside the `large` column, so its rows don't wrap again and `‹ Comments` finds its scroll. `CardDetail` hands the column null while no card is open, so list and thread share one tree. The thread gets a `fill` body and scrolls over its own reply box, its actions sit in the bar, and Edit opens the card's edit form in a dialog over the column. On a canvas the list's bar has **New comment** (`+`), which adds a document-level comment, anchored to no element, in `CardFormDialog`. Docs anchors every comment to its text and Sheets to a cell, so their bars have none: a comment comes from Insert › Comment or the selection's or cell's menu.

A thread a list or activity row opens reveals its anchor, and so does a `?chat=` landing, such as a notification's link or a reload: `useCommentsColumn` calls the same `reveal` once per landed card, as soon as the comment has loaded, which waits for the host's `ready`, leaving no room for growth since the column already has its thread width. An anchor that comes later, such as text a peer's undo brings back, moves nothing, so a reveal never takes the selection from someone already at work. A command-palette hit under **In comments** opens through the column's `openChat`, as an activity row does, so it reveals the same way and opens a closed column at the thread ([IN_DOCUMENT_SEARCH.md](IN_DOCUMENT_SEARCH.md#comment-threads-are-searched-on-the-server)). The anchor's own click, its corner mark or the hover card over it, moves nothing. Docs selects the anchor in the body, a text anchor as a caret at its start, without the focus, so the reply box keeps it and a text anchor shows by its highlight; it scrolls the page so the anchor's top sits as far below the view's top as the comment's colored block sits below the column's (`THREAD_BLOCK_TOP_PX`), even when it is already in view, smoothly unless the reader prefers reduced motion; ProseMirror's own scroll stays off. A click on the comment's own text opens its thread and leaves the caret where the click put it: a selected anchor would make the next keystroke replace the commented text. Sheets goes to the cell's tab, selects the cell and centers it through `revealSearchMatch`, so it stays in view as a thread narrows the grid; with the find bar open a jump can move its ring, and a hidden tab refuses the switch, so that thread opens without a jump. Slides goes to the element's slide and selects it, and the slide refits as the column grows. Vector selects the element and centers it at the current zoom in the canvas left of the column, once the column has its thread width, through ⌘F's `centerOn`, short of the `growPx` the column is about to grow by. It pans even when the element is already in view, and one larger than that area still gets its center there. A click focuses the thread's reply box as it opens; a landing or a reload doesn't, nor does forward to a thread a click opened and a close shut. After that the box takes the focus only after the user's own send or message edit, never on a peer's message or as the window comes back, so a reply never pulls the focus from the slide or the drawing. While the focus is in the column the canvas's keys and its undo stand down (`useFocusInDetail`), so Delete on Resolve or ⌘Z in the reply box leaves the drawing alone. Docs needs no such guard: its undo and its other editing keys are the editor's own keymaps, which hear a key only with the page focused. Sheets' cell keys are the workbook's own keydown, which skips a key from its right slot, so a letter, Delete, Enter or ⌘Z in the reply box never edits the selected cell, and its paste listener acts only with the grid focused.

In Docs the column lies over the page in the right slot the properties panels use, so the page moves only as far as it must to keep its text clear ([DOCS.md](DOCS.md#the-page-keeps-its-width-and-slides-then-scales-clear-of-a-panel)). On a phone it takes the screen while Docs' own `hidden` wrapper hides the editor, the one its outline pane shares. The extensions are built before the comment lifecycle, which needs the body's anchors (`useActiveComments(editor)`), so the comment mark's click and its ⌥⌘M toggle reach the column through refs.

In Sheets the column sits in the workbook's right slot, under the menu bar and beside the formula bar, the grid and the tabs, where it takes the image and chart panel's place while it is open ([SHEETS.md](SHEETS.md)). The grid measures its canvas again as the slot opens, closes and grows into a thread. On a phone `PhoneDetail` hides the workbook, which stays mounted.

Stickies keeps its card dialog, so it doesn't use `CommentsColumn`, which would draw a thread in the column. Its board draws the activity itself, a `small` `DetailColumn` at `?panel=activity` under the board's toolbar, and an activity row opens the card in the board's dialog, with the column left open behind it, both through `useCommentHost` ([STICKIES.md](STICKIES.md#the-board-reuses-the-comment-ui)).

## On a phone the column hides the editor, never unmounts it

Below the breakpoint the comments column, or a board's activity column, takes the whole screen. Docs hides the editor with its own `hidden` wrapper instead of `PhoneDetail`, because its outline pane shares that hide, and sheets, the canvas and the board hide theirs through `PhoneDetail`, never unmounting them, so node views, thumbnails, scroll position, selection and undo history survive a visit to the column. Two things follow:

- Anything that measures the editor skips a 0×0 box, since `display: none` measures zero. Docs' resize observer and figure view, the sheet engine and the canvas viewport all do.
- The find bar floats inside the hidden wrapper. Each host passes the column's `onSearchOpenChange` to `DocSearchProvider`, and the board its own close of the activity, so a search that opens on mobile (⌘F, a palette hit) closes the column.

On mobile the column skips its reveal: scrolling to a mark, a cell or an element would move a view nobody can see. On desktop each host reveals as its column says ([In Docs, Sheets, Slides and Vector, comments open in a column the URL names](#in-docs-sheets-slides-and-vector-comments-open-in-a-column-the-url-names)).

## A hover shows a comment's card, and the host draws it

Resting a mouse on a comment shows its card beside it, after a 300 ms pause that lets a quick pass go by. A click on the card opens the comment. An editor reports only "pointer over this card at this rect" or "pointer left", as `report(target)` or `report(null)`. A press reads as left, and so does a sheet's cell editor opening or a canvas mark unmounting, since no move or pointer leave comes then. The host, which already holds the cards and their entries, keeps that in `useCommentHover` and renders `CommentHoverCard`, so the hover hands no engine a thread list. Each host's state re-renders its editor twice per hover, which is accepted. The close waits a 150 ms grace after the pointer leaves, which a quick hand needs to reach the card. A slow one takes longer over the gap, or over the cell below a short anchor, so `CommentHoverCard` also holds the card while the pointer is between where it last was on the anchor and the card, as `enterCard` does on the card itself. Off that way, the grace runs as before, and back on the anchor the host's report takes over, which is why any report of a card releases the hold.

| App | What shows a card | Where the card opens |
|---|---|---|
| Docs | Highlighted text, and the corner mark of an image, a chart, a text box or an equation | Under it |
| Sheets | The whole cell, with its first card, unless the cell's link card is open, which the comment card would cover | Right of it |
| Slides, vector | An element's corner mark, with its first card | Right of it |

Stickies has no target, as its board draws the cards already. Resolved text gets no card, because its highlight is gone and nothing on the page says a comment sits there. A corner mark or a commented cell keeps its triangle when resolved, so it keeps its card. Docs reports from a React handler on a parent of `EditorContent` (`reportCommentHover`), because node views stop ProseMirror's events and draw their portals beside the editor's own div. A span that wraps reports the line under the pointer.

The card is a Radix `Popover` with a virtual anchor, because `HoverCard` has no Anchor part. It carries `role="tooltip"`, because `useDialogOpen` reads Radix's `role="dialog"` as a modal and stands down the document's keymaps. It takes no focus, so the editor keeps its caret: its content has Radix's `tabIndex` of -1, so a press on it is cancelled, or the thread its click opens would give the focus back to the card, gone by then. Radix still closes it on an outside press, a focus change and Escape, and the card stops that Escape, so it cancels no cell edit and closes no find bar. A deleted comment shows as deleted here too.

The rect is measured once. floating-ui tracks no scroll for a virtual anchor, so a wheel or a scroll anywhere closes the card rather than leaving it behind. A new anchor ref per target is what moves it, since Radix repositions only when the anchor's identity changes.

`enterCard` is a latch, not a cancel. The sheet's `document` mousemove reports "left" on every frame while the pointer is over the portaled card, so a cancel would last one frame and the 150 ms close would start again. While the latch holds, a report of "left" does nothing, and `leaveCard` clears it. A coarse pointer gets no card, because a tap emulates mouse events: a report of a card does nothing under `useIsCoarsePointer`.

Accepted edges:

- Sheets reports on every move, so after Escape or a wheel the next move over the same cell opens the card again after the pause. Docs and the canvas report only on entry, so they wait for the pointer to enter the target again.
- In sheets, a jump from the comments list with a cell editor open acts as a tab click does: to another tab it discards the uncommitted typing, and on the same tab the selection moves under the editor, which still commits to its own cell. `revealSearchMatch` is shared with the find bar, and the workbook's API tells a host nothing about an open editor.
- A pointer resting on the card keeps it open while a sheet's cell editor opens, as the latch holds.

## The filter lives on the surface it filters

The filter is session state, never persisted: `useCommentFilter` holds it in the host, so it survives closing the pane, and `matchesCommentFilter` (`packages/lib/src/core/comments/filter.ts`) applies it. In docs, sheets and the canvas it narrows only the pane or the column's list, so their `CommentFilterButton` is its only control. A toolbar menu would change state nobody can see while the pane is closed. Stickies filters the board itself, so its toolbar Filter menu (`CommentFilterMenuItems`) and its color-dot row drive one filter instance, and the board shows resolved cards by default.
