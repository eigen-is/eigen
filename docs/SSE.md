# Server-Sent Events (SSE)

> **TLDR:** The server tells open pages that data changed through an event stream. Every signed-in tab holds one, the stream of its user's own Home (`apps/api/src/lib/home/sse-stream.ts`, served by `apps/api/src/routes/sse.ts`), and `useSSE` (`packages/lib/src/core/sse/hooks/use-sse.ts`) hands each event to the domain handlers, which invalidate the TanStack Query cache so the page refetches. Not obvious from the code: an event carries only what invalidation needs, toasts come only from the notification center's event, a stream holds its Home and ends when that Home closes or its session ends, so the tab reconnects to the next one or stops hearing, and every stream announces the data epoch of the user's homes, an id that changes only when a restore replaces a home's data or an update replaces the code, so a tab reloads after either.

Every app mounts the stream once, in `EigenApp`'s provider stack ([LAYOUT.md](LAYOUT.md#every-app-is-eigenapp-around-appshell)), so a tab holds one stream whichever app it shows. It carries the changes that are not collab edits: a new mail, a renamed file, a chat message, a changed calendar event, a notification. A collab document's own edits travel on the document's socket instead ([COLLAB.md](COLLAB.md)). Read this doc before you add an event type ([§ A new domain adds four pieces](#a-new-domain-adds-four-pieces)).

## A stream belongs to one user's own Home

A user subscribes to their own Home's stream, never to another's. An action that touches another home reaches its users through the relay: `sendToHome` with a `broadcast` message, or `broadcastToOwnerAndMembers` for the owner and every member of a path, such as the people a folder is shared with or a team's members (`apps/api/src/lib/home/home-relay.ts`). The target Home then broadcasts to its own listeners. That keeps every stream on the server that owns its home, which is what sharding needs ([SCALABILITY.md](SCALABILITY.md)).

A home's first stream also starts its mail folder watchers, so a change another mail app makes reaches the open tab at once ([IMAP.md § Only the six standard folders have a watcher](IMAP.md#only-the-six-standard-folders-have-a-watcher)).

## A stream holds its Home and ends when it closes

A stream takes a hold on its Home when it opens (`Home.hold`), so a Home with an open tab never idles out, however long nobody sends a request. The release when the stream ends starts no fresh idle: a Home whose last request is long ago closes at once, and a tab that reconnects makes a request. A Home can still close under it, for a restore, a deletion or the shutdown. Then the hold's close callback ends the stream before the Home's parts close, because a stream left on a closed Home would go silent while the tab still looks connected. The browser's `EventSource` takes a stream that ends for a dropped connection and opens a new one, which reaches the next Home. A Home that is already closing refuses the hold with a 503, which the route answers, so a stream never opens on a Home it would not hear close.

Elysia calls a stream's `cancel` only when the client leaves, never when the stream closes itself. So `createSSEStream` has one teardown, which the cancel, the Home's close, the session's end and a failed send all run: it stops the keepalive, drops the listener and lets go of the hold. While the shutdown runs (`shutdownAllHomes`), `openHome` refuses every home with a 503, so a tab that reconnects builds no home again over the databases the shutdown closes. `apps/api/src/test/server/sse.test.ts` pins the hold, the end and the refusal.

## The keepalive keeps a proxy from closing the stream

The stream sends a keepalive at once when it opens and every 15 s after. The first one stops a proxy such as Apache from timing out a stream that has had nothing to say yet, and the later ones stop it from timing out a quiet one.

The keepalive is a named event with no data, `event: keepalive`, written by Elysia's `sse` helper. A browser never dispatches a named event to `onmessage`, so `useSSE` never sees it and every message it gets is an `SSEvent`. `apps/api/src/test/server/sse.test.ts` pins the bytes.

Every keepalive also reads the stream's session with `getSessionUser`, the read a collab socket's check starts with ([COLLAB.md](COLLAB.md#read-and-the-session-are-checked-at-open-and-every-15-s-write-on-every-message)), and a session that is gone or past its expiry ends the stream. So a sign-out, a revoked session, a password change that signs out the sessions and an admin's reset stop its events within 15 s, and a stream of another session stays. That table in COLLAB.md says which action ends which session. A read that throws is logged and leaves the stream, and the next keepalive asks again. `EventSource` takes the end for a dropped connection and reconnects: a browser with a new session's cookie reaches a new stream and notices nothing, and one with no session meets a 401, which `useSSE` retries as below until the tab reloads. `apps/api/src/test/server/sse.test.ts` pins it.

`useSSE` reconnects after a stream closes on an HTTP error such as a 502, or the 503 of a home a restore is replacing, which `EventSource` does not do on its own: from 1 s, doubling up to 30 s, with up to 20% jitter so a restarted server is not hit by every tab at once. While the tab holds a restart notice the delay stops at 5 s, because that server said it would be back within minutes and the tab should find the new version soon after it starts.

## Six tabs on plain http fill the browser's connections

Every signed-in tab holds one stream open (`useSSE`), and over plain http Chrome allows six connections per host. So on the dev stack a sixth Eigen tab's requests wait until another tab closes or reloads: Drive hangs on its root listing, a sheet stays blank. Behind Caddy, over HTTPS, HTTP/2 carries every request on one connection and the limit doesn't apply. When the dev app stalls for no reason, count the open tabs first.

## An event carries only what invalidation needs

An event holds ids, never display text or a domain object: a drive event its path's owner, mount, id and parent, a mail event its message and mailbox, and so on. The handler invalidates the queries those ids name and refetches the truth. A fat event would be a second copy of the data that drifts from the one the query returns. The shapes are in `packages/lib/src/types/sse.ts`. A whole-file contacts import sends one `contacts:changed` in place of one event per card, since a card change invalidates the whole list anyway ([CONTACTS.md](CONTACTS.md)).

The backend builds each event in `apps/api/src/lib/[domain]/sse-events.ts`. An event only the owner may see, such as mail's, goes out with `home.broadcast()`. A drive or chat event goes to everyone who can read its path, through `broadcastToOwnerAndMembers` ([§ A drive event reaches everyone who can read the path](#a-drive-event-reaches-everyone-who-can-read-the-path)). A drive event's callers pass a whole `DrivePath`, so `buildDriveEvent` picks its five ids: the path's name and its ACL, which lists the email of everyone it is shared with, never travel on the stream. The frontend handler is `packages/lib/src/core/[domain]/sse-handlers.ts`, and `handleSSEvent` (`packages/lib/src/core/sse/sse-handlers.ts`) hands every event to all of them. A test keyed by every `SSEventType` (`packages/lib/src/test/core/sse/sse-handlers.test.ts`) holds each type to a handler, so a type with no handler fails it.

## A drive event reaches everyone who can read the path

`Drive.emit` sends a drive event to the path's owner and relays it to every effective member of the path who may read it, through `broadcastToOwnerAndMembers`. The effective members are the people the path's own ACL or a folder above it is shared with, and on a team drive every member of the team (`Drive.getEffectiveMembers`). A folder's event also goes to the members of every path shared below it (`Drive.membersToTell`), because their Shared with me shows that path where it lives and a trash, restore or move of the folder sends no event for the paths below it. The members are read once for the event, so a sharee of both the folder and a path below it hears it once. They get the folder's ids, opaque to them, and nothing more. An ACL entry that grants only write, or nothing, gets no event, because its holder cannot list the folder the event names. Nobody signs in as a team, so a team Home has no listeners of its own, and the relay is how a team drive change reaches a tab. File-history, chat and comment-index events go the same way.

The members are read when the event goes out, from the same ACLs and team rows that grant access. So a sharee of a subfolder hears that subfolder's changes and nothing beside it, and a member who left the team or lost the share hears nothing more. A change that takes the path away from some of them reads the members first: a move tells the members of the old and the new place, and a trash tells those who could see the path before. Each tab then drops the path from the folder it still shows. The event is the same five ids, and it mostly names what the member's view already shows. A move out of a share is the exception: the old members get the moved path's new `parentId`, the opaque id of a folder they may not be able to read. It names nothing and opens nothing, because every fetch checks access, but it is an id they did not have. In a user's home the owner is one of the members, and still hears each event once.

A relayed event only refetches: `handleDriveSSEvent` raises no toast and adds nothing to the bell, the same as for the owner ([§ Toasts come only from the notification center](#toasts-come-only-from-the-notification-center)). A team calendar's event changes reach only the users it is shared with by name, not the team's members ([ROADMAP.md](ROADMAP.md)).

## A relayed drive event reads its members in one query

The relay reads the members from the path's ACL chain, looks their accounts up in one query, then pushes the event into each open home. A closed home costs nothing, because a broadcast never opens one. An unshared path in a user's home has its owner alone, so its event reads the path's folder chain and looks no account up (`Drive.membersToTell`).

Measured on an M1 Pro dev Mac that other test runs shared, so the numbers are noisy. For a team of 50 with a listener each, one event cost 0.5 to 1.0 ms, of which reading the members was about 0.5 ms. 500 uploads, eight at a time, took 2.0 to 3.0 s into a team folder and 2.1 s into a personal one. One member lookup per member had cost 3.4 ms per event. On an unshared personal folder an event costs about 0.09 ms more than a broadcast to the owner alone, the folder chain read.

## A burst of drive events refetches an open listing once

Every member's tab hears every item of a burst, such as 500 files dropped into a team folder or a trash of 500 items emptied. Each invalidation restarts the open listing's fetch, so that was 500 fetches per tab, and the tabs of one office share the server's per-IP rate limit (`rateLimit` in `apps/api/src/app.ts`). So `handleDriveSSEvent` splits every create, upload, rename, move, trash, restore and delete in two. What belongs to the one path happens at once: a renamed, moved or overwritten path's own detail is marked stale, because an open preview of an overwritten file must show the new bytes, and a trashed or deleted path's detail is dropped. Everything that lists paths refetches per owner once, 250 ms after the burst (`debouncePerOwner`): the folder and mime listings, the breadcrumbs, the search results and the history. The viewer's own lists of several owners' items, Shared by me, Shared with me, Recent and Watched, refetch once per burst too, keyed by the viewer. A trash list refetches only after a trash, restore or delete, because the sidebar's count keeps every drive's trash list on screen and an upload would refetch them all. That one refresh takes every listing of the owner rather than the folders the events named, which costs nothing extra, because only a query on screen refetches. A long upload never pauses 250 ms, so the listings also refetch every 1.5 s while it goes on, and a 2,000-photo upload fills an open folder as it goes rather than at the end. Mail, calendar and contacts use the same two numbers for their bursts. The ACL and file-history events are not collapsed.

The tab that made the change refreshes from its own mutation, without waiting. A write hook such as `useRenamePath` takes the item's `DrivePath` and invalidates exactly what that change stales (`invalidatePathRenamed` and its siblings in `packages/lib/src/core/drive/hooks/keys.ts`): the item's own drive and parent folder and the viewer's lists of several owners' items, never the folder of the view the action started in. A batch, such as a delete of 300 items, invalidates each folder, drive and list once, because every invalidation of a query on screen starts another fetch.

## A breadcrumb has its own key, so a folder's change reaches what is below it

A breadcrumb holds the name and the ACL of every folder above its path. So `driveKeys.breadcrumb` sits under the owner's `driveKeys.breadcrumbs` prefix, not under the path's own detail, and a rename, a move or an ACL change invalidates the whole prefix (`invalidateBreadcrumbs`): an open document shows the new name of a folder above it. A save or an overwrite, which changes no name, leaves the breadcrumbs alone.

## Toasts come only from the notification center

A domain handler never toasts. The toast comes from `notification:created`, which the notification center broadcasts after it writes the row, so a toast always has a row in the bell behind it ([NOTIFICATION-CENTER.md § Notifications and domain events are separate broadcasts](NOTIFICATION-CENTER.md#notifications-and-domain-events-are-separate-broadcasts), [NOTIFICATIONS.md](NOTIFICATIONS.md)).

## A backup job's event is only a nudge

`backup:job-updated` carries the job's id and its home's `ownerId`, nothing else. The job map in the API is the truth, and the admin pane refetches its job and artifact lists. An event for the org's `ownerId` refetches the server archive list, whose rows show the record a running upload rewrites. A home job's event goes to every admin, so a second admin watching the same pane follows along; a server backup's goes to the owner alone, who alone may see it ([BACKUP.md](BACKUP.md)).

## A restore reloads every tab of the home

A restore puts other data under every open tab of the home, and each tab's caches describe the home as it was. The data epoch (`apps/api/src/lib/home/data-epoch.ts`) marks that moment. It has three parts: the server's, a random id in `data/server/data-epoch` drawn on first use, then the commit the API image was built from (`EIGEN_COMMIT`), then the home's, from `data/server/home-data-epochs.json`. A per-home restore rotates the home's part once the new folder is whole, so no tab reloads onto the 503 of a restore still running. A failed install never rotates it. A failure after the rotation, in its save or in removing the restore's note, leaves it rotated, so the tabs reload once, which is accepted. A whole-server archive never holds either file (`SERVER_RUNTIME_FILES` in `apps/api/src/lib/config/paths.ts`), so after `./eigen restore` or `./eigen rollback` the server draws a new epoch and every tab reloads. A restart keeps both files and the commit. An update changes the commit, so every tab reloads onto the new code: a tab from before it never writes old structures to the new server. The price is that a tab drops whatever it had not saved, a collab edit the outage kept from syncing as well as text in a form or a comment box.

Every stream sends `home:data-epochs` when it opens and after every keepalive: the epoch of the user's own home and of each of their teams. `handleHomeSSEvent` (`packages/lib/src/core/home/sse-handlers.ts`) reloads through `reloadReplacedHome` when an epoch it holds changes. A home it has not heard of is new to it (a team joined), not replaced. One announcement covers every case with no push across homes. The restore closes the home, which ends its streams, and each reconnect meets the restore's 503 until it is done. So a tab hears the new epoch from the stream it opens after the restore, within `useSSE`'s retry delay: from 1 s, doubling up to 30 s, or up to 5 s while it holds a restart notice. A tab that was offline, or any tab after a whole-server restore, hears it on reconnect too. The keepalive's announcement is for a team: a member's stream is their own home's, which a restore of the team never closes.

## A reload for a restore starts the epochs over

A tab keeps its epochs in sessionStorage, so the next page it loads still holds them. `reloadReplacedHome` drops them before it reloads. An editor tab reloads when its collab socket names an epoch the restore replaced, which can come before its stream announces the new one, and the page that comes back takes the first epochs it hears as its own. So no page reloads twice for one restore. Stay on the leave prompt ends the asking, because the tab already holds the epoch it asked for.

## The owner and the team reload, a user with a share does not

The owner reloads in every app, and so does every member of a restored team, because those are the homes a stream announces. A user who only has something shared from the home keeps their tabs. Their open documents of it reload through the collab socket ([COLLAB.md](COLLAB.md#home-replacement-closes-every-socket)).

## The restart notice goes to every open stream

Before `./eigen update`, `rollback` or `restore` stops Eigen, the launcher tells the running API through the control socket, so every tab can warn its user to save first ([SELF-HOSTING.md § An update, rollback or restore warns the open tabs first](SELF-HOSTING.md#an-update-rollback-or-restore-warns-the-open-tabs-first)). The notice is in-memory state of the API process (`apps/api/src/lib/config/restart-notice.ts`): its reason (`update`, `rollback` or `demo-reset`, `RESTART_REASONS` in `packages/lib/src/types/sse.ts`; `./eigen restore` announces itself as a rollback, since to a user both put back data from before, and a demo box's hourly reset announces `demo-reset` five minutes ahead through `scripts/demo-reset.sh`, whose banner counts in minutes and seconds), when it was announced, its time and the operator's message. A restart of the process drops it, which is right, since that is the restart it announced.

`server:restart-notice` carries `msLeft` and `msSinceAnnounced`, counted when the event is sent, never a clock time, so a browser whose clock is off still shows the right times. Every stream sends it when it opens, with `notice: null` when there is none, so a tab that reconnects to the restarted server drops the banner it held. The keepalive never sends it: a stream ends with its Home, and the stream the tab opens next sends the notice of that moment, so a notice given or taken back while no Home had the tab's listener still reaches it. A change goes out at once to every loaded home's listeners through `broadcastToLoadedHomes` (`apps/api/src/lib/home/get-home.ts`). That is no push across homes: it reads no home's data, opens no home, and a home without a loaded instance has no open stream to tell.

The tab keeps the notice in a small store (`packages/lib/src/core/sse/restart-notice.ts`): `handleRestartNoticeSSEvent` turns `msLeft` into a deadline and `msSinceAnnounced` into the time it was announced (`heardAt`), both on the tab's own clock, and `useSSE` marks the stream down on an error and up when it opens. `RestartBanner`, which `AppShell` renders at the foot of every app, reads the store through `useRestartNotice`. A page without `EigenApp`, such as the blog, opens no stream, so its store stays empty and the banner shows nothing. The store is how a tab tells an update from a crash. A stream that drops while the tab holds a notice whose time has come is the restart, and the banner says Eigen is updating, or for a rollback that it is going back to an earlier version. A stream that drops with no notice shows nothing new. The banner shows `heardAt` as the time of the broadcast, so a tab that reloads still says when the notice came. A reconnect sends the notice again with fresh times. When its reason, message, deadline and announce time match the one held, give or take a few seconds, the tab keeps the one it holds. Without `msSinceAnnounced` the tab takes the time it first heard the notice. The banner is keyed by `heardAt`, which a repeat of the same notice keeps, so a reconnect keeps the status region a screen reader already knows. The first stream of the restarted server sends `notice: null`, which drops the banner, and after an update or rollback its new data epoch reloads the tab.

A notice whose restart has not come five minutes after its time (`RESTART_NOTICE_EXPIRY_MS`, which the CLI's usage quotes too) drops itself and tells the streams, for a launcher killed before it could take the notice back. The timer is fixed: a new notice starts it over, and nothing else holds it, such as a running backup. Each call of `./eigen restart-notice` gives up after ten seconds and says Eigen is not answering, because the launcher takes the notice back as it exits and a hung API must not hold that exit. `apps/api/src/test/cli/control.test.ts` and `apps/api/src/test/server/sse.test.ts` pin the routes, the expiry and the bytes after the keepalive.

## A new domain adds four pieces

1. The event type in `packages/lib/src/types/sse.ts`: its entry in `SSEventType` and its member of the `SSEvent` union.
2. A builder in `apps/api/src/lib/[domain]/sse-events.ts` that returns only ids.
3. `this.home.broadcast(buildEvent(...))` where the business logic changes the data, or `broadcastToOwnerAndMembers` when other users can read it.
4. A handler in `packages/lib/src/core/[domain]/sse-handlers.ts` that invalidates, with no toast, called from `handleSSEvent`, and a sample of the event in its test's table.
