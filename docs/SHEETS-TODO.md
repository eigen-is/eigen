## Package rulings

- **`packages/sheet` is English-only** (Reinder). There is no i18n layer and none is planned: no `locale()` lookup helper and no `en` string object. UI copy is a plain English literal at its call site, in the same bare-JSX style the menus use for `Cut`/`Copy`/`Paste`. The data tables live in named modules under `state/modules/`: `function-list.ts` (`FUNCTION_LIST`), `currencies.ts` (`CURRENCIES`), `format-presets.ts` (`numberMenuPresets`, `DATE_FORMAT_PRESETS`) and `fonts.ts` (`FONT_ARRAY`, `FONT_INDEX_BY_NAME`). Don't reintroduce a string table; if a string is shown twice in one file, a local `const` is the answer.
- **Backwards compatibility is not required** (Reinder): stored sheet JSON, the op wire shape and the in-memory shape are all free to change. Q11 below asks how far that goes for live data.
- **The op log stays, for now.** Whether sheets should keep its op log or become a real Yjs document with `Y.UndoManager` is researched in [PROPOSAL_SHEETS_YJS_WORKBOOK.md](proposals/PROPOSAL_SHEETS_YJS_WORKBOOK.md). ## Open questions: decide before building

These are choices, not tasks. Several read like settled rulings, but none was ever put to a human. Nothing below should be implemented until the question above it has an answer.

### Q1: When the editor can't calculate an imported formula, should it delete the number Excel put there?

**The problem.** Importing an Excel file brings in each formula *and* the number Excel last calculated for it. If our engine doesn't know a function the formula uses, we produce `#NAME?`. On the server we refuse to overwrite the imported number with that error. In the editor we don't: the moment anything upstream changes, the number is replaced by `#NAME?`, sent to every collaborator, and written into the saved document. **The original number is then gone for good.** Not hidden behind the error: destroyed.

The case for today's behavior is that "showing a number that no longer matches its inputs is a lie". That reasoning is sound as far as it goes, but it doesn't weigh the destructive half, and it reads like an assistant's judgement rather than yours.

**Options.**
- **A. Keep today's behavior.** Honest about staleness. But one keystroke permanently deletes data that came from the user's own Excel file.
- **B. Mirror the server's guard into the editor.** The imported number survives. But it can silently drift out of date, and it looks like a working formula when it isn't.
- **C. Keep the value and mark it.** Keep the number, flag the cell (corner marker plus a tooltip: "this value came from Excel and can't be recalculated here: FUNCTION isn't supported yet"). Nothing destroyed, nothing misrepresented. Costs a small piece of UI and somewhere to store the flag.
- **D. Fix the cause: add the missing functions.** The right long-term answer, now scoped (see [Formula engine](#formula-engine)): about eight common classics, three of which arrive free with a library upgrade.

C and D are not exclusive; C is the safe stopgap while D proceeds.

### Q2: How should `<`, `>`, `<=`, `>=` compare things?

**The problem.** Those four operators currently hand both values straight to JavaScript. JavaScript sorts text by character code, so `"Zebra" < "apple"` is TRUE for us and FALSE in Excel. It can't compare text against a number at all, so `"abc" > 1` is FALSE where Excel says TRUE (in Excel every piece of text ranks above every number). Excel and Google Sheets agree with each other on all of this. We match neither.

Note: on a blank cell, `A1>=0` returning TRUE is **correct**. It's `A1=0` returning FALSE that's wrong; Excel and Sheets both say TRUE there.

**Options.**
- **A. Implement Excel's rules.** One shared helper behind all six operators: a blank counts as `0` against a number and as empty text against text; numbers sort below text, text below TRUE/FALSE; text compares case-insensitively. Imported sheets then behave the way their author expected. Some formulas in existing Eigen documents will change answer on the next recalc. That's the point, but it is a change.
- **B. Leave it.** Any formula comparing text with `<`/`>`, or comparing a blank with `=`, keeps giving a wrong answer with no error shown. This is the silent-wrong-answer class, the hardest for a user to catch.
- **C. Fix only the blank-versus-zero mismatch in `=`.** Cheap, removes the visible inconsistency between `A1=0` and `A1>=0`, leaves text ordering wrong.

### Q3: What is the in-memory shortcut allowed to be?

**Settled by the cross-tab/cross-login requirement, recorded here so it isn't relitigated.** Today, pasting inside one spreadsheet doesn't really use the clipboard: the app remembers which cells you selected and copies them across in memory (`ctx.copyState` holds *coordinates only*; the fidelity comes from re-reading the live cells). That object cannot survive a second tab or a second login, so it cannot be the source of truth.

It can survive as a **cache**: a same-tab paste of a large range skips serialize/parse by checking that the clipboard payload's identity matches the cached one. The contract has to be *the clipboard payload alone is sufficient; the cache is an equal-output shortcut*, enforced by a test that runs both paths over the same range and asserts identical resulting sheet state. Without that test the cache drifts and the cross-tab path rots exactly as it has today.

The only open part: keep the cache, or drop it for one code path? Dropping it costs speed on big same-tab pastes and buys one less thing to keep in sync.

### Q4: Should a block of cells become its own kind of clipboard item?

**The problem.** The shared clipboard understands two things: a piece of text, and a picture. A block of cells is neither, so today it's squeezed into the text slot and only the visible values survive.

**Options.**
- **A. Add a "cells" kind.** Values, formulas, formats, colors, merges, row heights and column widths travel properly. Copying between two spreadsheet files finally works, and cross-tab copying stops losing things. Costs a new type every app must at least know to ignore, plus a size limit.
- **B. Keep squeezing it into text.** No work, but copying between two spreadsheet files stays lossy forever.
- **C. Hide it in the free-form `meta` bag.** Fastest to build, but this shortcut makes sizes and styles silently disappear between apps. Not recommended.

A is the only option that delivers the stated goal.

### Q5: How big is too big?

**The problem.** Carrying full detail (every cell's formula, format, color and border) makes the payload far larger than the plain text it replaces, and the transport is URI-encoded JSON inside an HTML attribute. Fifty thousand cells can reach several megabytes. Browsers have limits, and even below them a copy that pauses for a second feels broken.

**Options.**
- **A. No limit.** Small copies are perfect; a large copy may hang or fail silently on some browsers, intermittently and unreproducibly.
- **B. A limit, falling back to the simpler format above it.** Over the threshold, copy the plain table: values, formats, colors, widths, no formulas or validation rules. Copy is always fast and never fails, but a large copy silently loses formulas.
- **C. A limit, with a warning.** As B plus "this selection is large; formulas were not included", so the user can choose to copy in two halves.

C is the honest one. Measure a realistic large sheet before picking the number. (A side channel between tabs would raise the ceiling, but it only works in one browser profile, so it doesn't help across logins.)

### Q6: What happens to a picture when cells are copied to someone else's spreadsheet?

**The problem.** Pictures aren't stored in the clipboard. The clipboard stores a pointer saying "the picture lives over there, in that file", and the browser fetches it on paste, **as the pasting user**. That works for you. It breaks when a different person pastes, because they may have no permission to open the source file. The picture just disappears, with no explanation.

This is correct security behavior and must not be weakened by widening drive access. But it does mean a reference-only image is not a self-contained payload across logins.

**Options.**
- **A. Leave it.** Pictures arrive when you have access, vanish silently when you don't. Free and safe, but it looks like a bug and will be reported as one.
- **B. Leave it, but say so.** Same behavior plus "1 image could not be copied: you don't have access to the original." Still free, no longer looks broken.
- **C. Embed small pictures in the payload.** Below a size cap, carry the actual image data so it always pastes. Works for everyone, but the payload gets big, large pictures still fail (so you need B anyway), and it means a picture can leave a restricted file by being copied. Defensible (the copier could screenshot it), but it should be a decision, not an accident.

B now; C only if it's actually asked for.

### Q7: If a formula is pasted into a different file, what should it point at?

**The problem.** `=SUM(A1:A10)` means "the ten cells above me". `=Budget!B4` means "cell B4 on the sheet called Budget". Paste into a different file and there may be no sheet called Budget. This never comes up today, because a copy between files carries no formulas at all, only the numbers.

**Options.**
- **A. Carry formulas and shift them the way pasting normally does.** Relative references move correctly; references to a missing sheet go `#REF!`. Matches Excel and Google Sheets, and users already understand `#REF!`.
- **B. Formulas within one file, values everywhere else.** Never broken, never surprising, and quietly worse than the tool people are used to. They will notice.
- **C. Offer a choice.** "Paste values / paste formulas". Most control, most clicks, more to build. Worth having eventually regardless of the default.

A is what every spreadsheet user expects. Note this requires the payload to carry its **source anchor and sheet name**, so the target can recompute the offset.

### Q8: If cells are cut in one tab and pasted in another, should the originals disappear?

**The problem.** Cut means move, and moving needs two things: the cells appear in the new place, and they leave the old one. The clipboard only carries the first. The old tab has to be told to delete them, and it may be a different browser, a different machine, or a different person.

**Options.**
- **A. Across tabs, a cut behaves like a copy.** Simple, predictable, no half-finished moves. But a cut that doesn't remove isn't really a cut, and someone ends up with duplicates.
- **B. Delete the originals when the paste happens.** A real move, but only within one browser and login. Between two people it cannot work at all, and a half-applied move is worse than none.
- **C. Cut only moves where you cut it.** Within one tab, cut moves; anywhere else it copies and says so. Two behaviors, each easy to explain, and no data loss.

C is the honest one.

### Q9: How much should survive when cells are pasted into a document or a slide?

**The problem.** A range is a grid; a document flows and a slide is a free canvas. Neither has a natural home for column widths, conditional formatting and formulas. Something must be dropped. The question is how much.

**Options.**
- **A. Text only (roughly today).** Nothing surprising happens, and nothing useful arrives. Users rebuild the table by hand.
- **B. A real formatted table.** Documents already do this; extend it to slides. The common case ("put this table in the report") just works, and formulas become their displayed values, which is what people want there anyway. Costs a slides-side table renderer.
- **C. A picture of the table.** Looks exactly right, completely uneditable and unsearchable. Good as an option, bad as a default.

B, with C possibly offered later as an explicit "paste as image".

### Q11: Is "the sheet-JSON format is free to change" still true?

The range-keyed `dataVerification` rework is L-sized and justified by a parenthetical claiming a "dev-only carve-out". That phrase appears nowhere else in the repo, and "dev-only" is not true: eigen.is is live. The accurate framing is "migration allowed, no backwards-compatibility required", a different and more expensive promise. Confirm before anyone starts.

### Q13: Should a typed `5/1/2026` become a date, and in which order?

Typing `1/2/2026`, `31/12/2025` or `5 Jan 2026` into a cell keeps it as text; only ISO `2026-01-05` (and `2026-01-05 13:30`) becomes a date (`engine/format.ts` `parseCellInput`). Excel parses slash dates in the user's locale order; the repo writes dates day-month-year but spells en-US otherwise, so `1/2/2026` is ambiguous by design. Options: keep text (today), parse day-month-year only, or parse both when unambiguous (`13/12/2025`) and text otherwise. A formula result never goes through this path.

### Q12: Who opens an exported spreadsheet in real Excel, and when?

An agent can't do this; it needs a person with Excel or Google Sheets. It's a documented [verify-in-browser](../.claude/skills/verify-in-browser/SKILL.md) obligation. The rule exists because a library can write internal hyperlinks our own importer accepts and Google Sheets rejects. Either someone spends twenty minutes on it, or we consciously drop the rule for xlsx.

## Bugs

Verified, user-visible, bounded.

- [ ] **By-values checkboxes are silently ignored while a condition is active**: the checkbox list renders unconditionally (the `filter-by-value` section of `FilterMenu` in `FilterMenu.tsx`) but Confirm discards it when a condition is set (the Confirm button's `onClick`, "a selected condition takes precedence"). A user unticks values, picks a condition, hits Confirm, and the ticks do nothing. Disable or collapse the list while a condition is active. (There is no "Google-parity filter-menu redesign" to defer this to: no doc, no branch, no ticket.) **S**

- [ ] **Plain-text paste doesn't unquote TSV**: the plain-text arm of `pasteHandler` (`state/events/paste.ts`) splits on tabs and newlines and drops rows shorter than the first, so a quoted cell holding a newline, which Sheets' own ⌘C and Google write as `"two\nlines"`, lands split over two rows with its quotes. Read it with `parseTsv` (`@workspace/lib/clipboard`), as the chart Edit data grid does.

- [ ] **The export and preview clip text the grid lets overflow**: `render.ts` gives every `<td>` `overflow:hidden;white-space:nowrap`, so a long note in column A shows cut at A's edge in the HTML, PDF and preview, while the grid spills it over the empty cells beside it ([SHEETS.md](SHEETS.md#text-spills-into-empty-neighbours)). The server can't measure text, so it would size an inner box to the empty run beside the cell (the same blocker rule as `rowOverflowSpans`) and let the `<td>` overflow into it. **M**

- [ ] **A selection can't be moved or filled by touch**: the fill handle is a 6px square with a 14px grab area and the move band a 6px strip, both sized for a mouse, and there is no touch knob (see Closed / dropped). Nothing in the grid listens for touch on a selection, so a coarse pointer can select and scroll but cannot drag-fill or drag-move. Widening the same strips under `@media (pointer: coarse)` is the cheap half; it needs a real device to judge, because a wider band on touch also means a tap near a cell border starts a move-press instead of a selection, and the strips `preventDefault()` on mousedown. **M**

- [ ] **Two document-wide element lookups assume one workbook per page**: `rangeSetValue` in `formula-range.ts` (`.sheet-formula-text-lpar`) and `cellFocus` in `data-verification.ts` (`#sheet-dataVerification-dropdown-btn`) both query `document` and take the first hit; the ids are rendered inside the workbook subtree, so two mounts emit duplicates. The same mount would also duplicate the per-workbook ids nothing queries but assistive tech does: `sr-selection`, `sr-sheetFocus`, `shortcuts-heading` (`SheetOverlay/index.tsx`). **Latent today**: `SheetEditorInner` in `apps/sheets/src/components/sheets/editor.tsx` is the only `<Workbook>` mount in the repo, so nothing can hit this until a second one exists. There is no blocker: `refs.globalCache` is per-workbook (the `globalCache` ref in `Workbook/index.tsx`) and is already the argument these handlers receive, so one container field set at mount closes both from one place. **M**


- [ ] **Narrowing a column doesn't grow its wrapped rows**: a row fits its wrapped text when the cell is committed or Wrap is turned on (`updateCell` in `cell.ts`, `updateFormatCell` in `toolbar.ts`), but a column resize (`setColumnWidth`, the header drag) leaves the row heights alone, so the new extra lines are clipped until the cell is edited again. Google refits the rows. A commit also skips the fit when the cell's column and row both already have a size, so a row grown once by another cell stops growing, and when it does fit it sets the row to the committed cell's height alone, so a two-line cell committed beside a 36 pt one shrinks the row and clips the big one. Google fits the row to its tallest cell. **S**

- [ ] **A copied underline arrives as a bottom border, not an underline**: `getStyleByCell` renders `un` as `border-bottom: Npx solid <color>` (through `getFontStyleByCell` in `state/modules/cell.ts`) while its neighbor `cl` renders a real `text-decoration`, and the API's HTML export writes `text-decoration:underline` (`buildCellStyle` in `apps/api/src/lib/export/sheets/render.ts`). So copy an underlined cell and paste it in a second tab (which has no `ctx.copyState` and therefore goes through the foreign-HTML parser), and the cell arrives with `un` unset **and** a spurious bottom border, because `handlePaste` in `paste.ts` reads that `border-bottom` as a real border. Pasting into Excel or Google has the same drift. The fix is one line in `cell.ts`, but `getStyleByCell` also styles the in-cell editor (`SheetOverlay/InputBox.tsx`), so the editor's underline changes from a drawn border to a text decoration; screenshot it before merging. Symmetric gap worth doing at the same time: `un` has no inner-markup check (`cl` reads `<s>`), so a Google Sheets cell that carries its decoration on an inner `<span>` loses both. **S**

- [ ] **Undoing a delete or redoing an insert of an image or chart a peer deletes at once can end apart**: the undo or redo writes the whole object back, and a peer's concurrent delete removes it. Each live client applies its own batch first and the other's on arrival, so the object survives on the client that takes the delete first and is gone on the one that takes it last; the replay follows the log's order. `floatingWriteFilter` can't settle it: both writes are whole-object writes, not writes into a missing object. Fix shape: live clients apply batches in log order, step 1 of [PROPOSAL_SHEETS_YJS_WORKBOOK.md](proposals/PROPOSAL_SHEETS_YJS_WORKBOOK.md#what-to-do-first). **L**

- [ ] **A row or column op and a peer's concurrent edit to the sheet's metadata can end apart**: `sheetMetadataOps` (`state/utils/patch.ts`) ships every top-level field of the edited sheet whole with the op: `frozen`, `config` (row heights, column widths, hidden rows and columns, merges), conditional formats, validation. A peer's write to one of them at the same time survives on a client that takes the row op first and is overwritten on one that takes it last, and the replay follows the log's order, so live clients disagree until they reload. The batch itself applies everywhere and the grid sizes agree (`rowcol-ops.test.ts`). Fix shape: per-field metadata ops, so the op writes only the entries it shifted. Applying batches in log order (step 1 of the proposal) would make the clients agree, still losing one of the two edits. **M**

- [ ] **A copied sheet's formulas don't recalculate until the next open**: `copySheet` (`state/api/sheet.ts`) deep-clones the source, `calcChain` included, so the copy's chain still names the source sheet's id; and the copy has no `data` until it is visited, where `initSheetData` registers nothing. So a built formula map never learns the copy's formulas, and a rebuild from `calcChain` registers the source's cells instead: edit a precedent on the copy and its formulas keep their old values until `seedCalcChain` re-seeds at mount. A peer's copy is tracked (`applyOp` registers an added sheet's formulas), but only until the next rebuild. Fix shape: give the cloned chain the copy's id, and register a sheet's formulas wherever its `data` is first built. **S**

- [ ] **Conditional-format value coercion is inconsistent across rule types**: `equal "5"` matches the number 5 and the text `5`, `equal 5` matches only the number, `equal TRUE` matches no boolean cell; `top10` and `aboveAverage` count the text `5` and `TRUE` as numbers, and their apply pass styles a value-less style-only cell as 0 (pinned as characterization in `conditional-format-edges.test.ts`), where Excel ignores text, booleans and blanks; `greaterThan "abb"` never matches text. The 3-stop `colorGradation` midpoint is `Math.floor(mean)` while the xlsx exporter writes `percentile 50` for the same rule. One coercion rule for every branch is the fix, but it changes which cells light up in existing documents, so it needs the Q2 decision on comparison semantics first. **M**
- [ ] **Filter date conditions accept anything and silently match nothing**: both operand fields are an untyped `Input` shared by every condition (the `filter-by-condition` section of `FilterMenu` in `FilterMenu.tsx`); an unparseable date filters nothing rather than reporting an error (`buildFilterConditionMatcher` in `filter.ts`). A date picker is one possible fix, but Google Sheets itself uses a free-text field with relative-date presets, so the real defect is the silent failure. **S** for the error, **M** for a picker

- [ ] **A rich cell exports flat to HTML, PDF and the preview**: `getCellDisplay` (`export/sheets/render.ts`) writes the runs' joined text in the cell's own style, so a bold word in a sentence prints plain. The xlsx export keeps the runs. Fix direction: a styled span per run, its styles through the export's style registry as the cells' are. **M**

- [ ] **The cell editor shows a cell's strikethrough or underline over a run that turns it off**: the editor box draws the cell's `line-through` and underline border (`getStyleByCell`), and CSS draws a parent's decoration through a child span that says `none`. So a word un-struck in a struck cell looks struck while it is open. The commit and the canvas are right. Fix direction: the box leaves the decorations to its spans while a cell is open. **S**

- [ ] **A shortcut fires on the wrong letter outside QWERTY**: the cell editor's and the grid's shortcuts match through TanStack's `matchesKeyboardEvent` (`InputBox`, the Workbook's key handler, `handleGlobalKeyDown`), which falls back to the physical key even when the layout types another Latin letter. QWERTZ types y on the Z key, and the grid checks Mod+Z first, so Ctrl+Y undoes instead of redoing. Dvorak ⌘F lands on the Y key, so it redoes and blocks find. Dvorak ⌘P lands on the R key and fills right. Colemak ⌘S lands on the D key and fills down. Colemak types u on the I key, so ⌘U italicizes, in the grid and in the open editor alike. Dvorak types g on the U key, so ⌘G underlines in the grid. The chart and image panel's `undoChord` matches undo another way: by the typed letter only, with Ctrl or ⌘ on any platform, so the same keys undo there and not in the grid, or the other way round. Fix direction: one matcher for both that tries every shortcut's letter before any physical key, or the fix upstream. `SHEET_HOTKEYS` (`state/events/keyboard.ts`) already holds every letter shortcut, so that matcher has one table to try. **S**

- [ ] **A caret format doesn't reach IME input**: a format on a bare caret types only an `insertText` in its style (`typeStyledText`, `state/modules/inline-string.ts`), and a composition can't be cancelled, so Japanese or Chinese typed after ⌘B on a caret takes the style of the run beside it. **S**

### Decided, not defects

- **The cell-range picker stays put when the grid scrolls.** It is a portaled `position: fixed` dialog placed once at its cell, so scrolling moves the grid underneath it. Reinder confirmed this is the wanted behavior: a card that scrolls with the grid can ride off-screen entirely. Do not "fix" this into a scroll-tracking popup without asking.
- **The drag-to-move band reaches 2px inside the selection**, so a click in that 2px does not collapse a multi-cell selection to that cell. Deliberate: outward reach is 4px because that side steals clicks from the neighboring cell, so the grab has to come from the interior. Reinder chose 4/2 over 4/4.

## Clipboard: put sheets on the shared system

Goal: a sheets → sheets copy-paste must work **between browser tabs and between different user logins**, which means the complete payload has to live in the clipboard itself. The shared writer already produces exactly the right shape (real table HTML plus an Eigen metadata span in one `text/html` payload), and sheets already writes both. The gaps are on the read side and in the type model. See [CLIPBOARD.md](CLIPBOARD.md) and [PROPOSAL_COPY_PASTE.md](proposals/PROPOSAL_COPY_PASTE.md).

**Today, in one line:** sheets writes the eigen payload on every copy but can never read it back, because `onPaste` (`components/Workbook/index.tsx`) passes `COPY_ACTION_TABLE_MARKER` to `classifyPaste`, which suppresses the eigen flavors whenever the HTML contains `sheet-copy-action-table`, and sheets' own copy always emits it (`rangeValueToClipboard` in `state/modules/selection.ts`). Same-tab paste is served from `ctx.copyState` in memory, so it looks perfect. **Cross-tab paste is already broken**: the receiving tab has no `copyState`, the marker still suppresses the eigen read, and it falls through to the foreign-HTML parser, losing formulas, number formats, CF rules, data validation and hyperlinks.

Depends on **Q3**–**Q9**.

## Formula engine

- [ ] **IFERROR can't trap an unknown name or function**: `=IFERROR(LET(...),"")` and `=IFERROR(NOSUCHNAME,"fb")` yield `#NAME?` where Excel returns the fallback, because the unknown-function guard (`callFunction` in `evaluate-by-operator.ts`) and `_callVariable` (`parser.ts`) throw above the in-band conversion and unwind the whole parse. **This is not blocked on Q2.** Return the formulajs `#NAME?` singleton instead of throwing; every operator in `symbolOperators` (`evaluate-by-operator.ts`), the six comparisons included, already hands an Error operand through unchanged, so the in-band `#NAME?` reaches IFERROR like any other error. Trapping at the IFERROR call site is not an option: jison reduces bottom-up, so the inner call evaluates before IFERROR's own reduction. Not fixed alone, because the import path would lose data: `recalcSheets` (`engine/recalc.ts`) keeps Excel's cached value only when our result is an error, so once IFERROR traps our own `#NAME?`, an imported `=IFERROR(FILTER(…),"none")` or `=IFERROR(LET(…),"")` computes the fallback and overwrites the value Excel calculated. Pair it with a guard that keeps the cached value when the formula names a function the engine lacks, at import and in the editor (Q1). - [ ] **`T()` and `N()` are a syntax error**: a one-letter name before `(` lexes as a cell (`RELATIVE_CELL`), because the first `FUNCTION` lexer rule in `grammar-parser.ts` needs two characters, so `=T("a")` and `=N(5)` are `#ERROR!` where Excel gives `a` and 5. `text.test.ts` pins the `#ERROR!`. - [ ] **`&` binds tighter than `*` and `+`**: the grammar ranks `&` above the arithmetic operators (`%left '&'` after `*` `/` and `^`, `grammar-parser.jison`), while Excel ranks it below them, so `2*3&"x"` is `#VALUE!` where Excel gives `"6x"`, and `=1E308*10&"x"` is `#VALUE!`, not `#NUM!`.
