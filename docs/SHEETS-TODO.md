## Package rulings

- **`packages/sheet` is English-only** (Reinder). There is no i18n layer and none is planned: no `locale()` lookup helper and no `en` string object. UI copy is a plain English literal at its call site, in the same bare-JSX style the menus use for `Cut`/`Copy`/`Paste`. The data tables live in named modules under `state/modules/`: `function-list.ts` (`FUNCTION_LIST`), `currencies.ts` (`CURRENCIES`), `format-presets.ts` (`NUMBER_MENU_PRESETS`, `DATE_FORMAT_PRESETS`) and `fonts.ts` (`FONT_ARRAY`). Don't reintroduce a string table; if a string is shown twice in one file, a local `const` is the answer.
- **Backwards compatibility is not required** (Reinder): stored sheet JSON, the op wire shape and the in-memory shape are all free to change. That holds for live data too, as long as a document keeps its cells: data in a shape the build no longer reads is dropped where it is read, such as the per-cell validation rules of older builds.
- **The op log stays, for now.** Whether sheets should become a real Yjs document with `Y.UndoManager` is answered in [PROPOSAL_SHEETS_YJS_WORKBOOK.md](proposals/PROPOSAL_SHEETS_YJS_WORKBOOK.md): keep the op log, and build the Yjs version only with stable row and column ids, when the engine needs those anyway. ## Open questions: decide before building

These are choices, not tasks. Several read like settled rulings, but none was ever put to a human. Nothing below should be implemented until the question above it has an answer.

### Q2: How should `<`, `>`, `<=`, `>=` compare things?

**The problem.** Those four operators currently hand both values straight to JavaScript. JavaScript sorts text by character code, so `"Zebra" < "apple"` is TRUE for us and FALSE in Excel. It can't compare text against a number at all, so `"abc" > 1` is FALSE where Excel says TRUE (in Excel every piece of text ranks above every number). Excel and Google Sheets agree with each other on all of this. We match neither.

Note: on a blank cell, `A1>=0` returning TRUE is **correct**. It's `A1=0` returning FALSE that's wrong; Excel and Sheets both say TRUE there.

**Options.**
- **A. Implement Excel's rules.** One shared helper behind all six operators: a blank counts as `0` against a number and as empty text against text; numbers sort below text, text below TRUE/FALSE; text compares case-insensitively. Imported sheets then behave the way their author expected. Some formulas in existing Eigen documents will change answer on the next recalc. That's the point, but it is a change.
- **B. Leave it.** Any formula comparing text with `<`/`>`, or comparing a blank with `=`, keeps giving a wrong answer with no error shown. This is the silent-wrong-answer class, the hardest for a user to catch.
- **C. Fix only the blank-versus-zero mismatch in `=`.** Cheap, removes the visible inconsistency between `A1=0` and `A1>=0`, leaves text ordering wrong.

### Q3: What is the in-memory shortcut allowed to be?

**Settled by the cross-tab/cross-login requirement, recorded here so it isn't relitigated.** Today, pasting inside one spreadsheet doesn't really use the clipboard: the app remembers which cells you selected and copies them across in memory (`ctx.copyState` holds the copy's id and coordinates, no cells; the fidelity comes from re-reading the live cells). That object cannot survive a second tab or a second login, so it cannot be the source of truth.

It can survive as a **cache**: a same-tab paste of a large range skips serialize/parse by checking that the clipboard payload's identity matches the cached one. The contract has to be *the clipboard payload alone is sufficient; the cache is an equal-output shortcut*, enforced by a test that runs both paths over the same range and asserts identical resulting sheet state. Without that test the cache drifts and the cross-tab path rots exactly as it has today.

The only open part: keep the cache, or drop it for one code path? Dropping it costs speed on big same-tab pastes and buys one less thing to keep in sync.

### Q4: Should a block of cells become its own kind of clipboard item?

**The problem.** The shared clipboard carries text, pictures, canvas elements and charts. A block of cells is none of them, so today only the HTML table beside the payload carries it, and only the visible values survive.

**Options.**
- **A. Add a "cells" kind.** Values, formulas, formats, colors, merges, row heights and column widths travel properly. Copying between two spreadsheet files finally works, and cross-tab copying stops losing things. Costs a new type every app must at least know to ignore, plus a size limit.
- **B. Keep squeezing it into text.** No work, but copying between two spreadsheet files stays lossy forever.
- **C. Hide it in the free-form `meta` bag.** Fastest to build, but this shortcut makes sizes and styles silently disappear between apps. Not recommended.

A is the only option that delivers the stated goal.

### Q5: How big is too big?

**The problem.** Carrying full detail (every cell's formula, format, color and border) makes the payload far larger than the plain text it replaces, and the transport is URI-encoded JSON inside an HTML attribute. Fifty thousand cells can reach several megabytes. Browsers have limits, and even below them a copy that pauses for a second feels broken.

**Options.**
- **A. No limit.** Small copies are perfect; a large copy may hang or fail silently on some browsers, intermittently and unreproducibly.
- **B. A limit, falling back to the simpler format above it.** Over the threshold, copy the plain table: values, formats, colors, widths, no formulas or validation rules. Copy is always fast and never fails, but a large copy silently loses formulas.
- **C. A limit, with a warning.** As B plus "this selection is large; formulas were not included", so the user can choose to copy in two halves.

C is the honest one. Measure a realistic large sheet before picking the number. (A side channel between tabs would raise the ceiling, but it only works in one browser profile, so it doesn't help across logins.)

### Q6: What happens to a picture when cells are copied to someone else's spreadsheet?

**The problem.** Pictures aren't stored in the clipboard. The clipboard stores a pointer saying "the picture lives over there, in that file", and the browser fetches it on paste, **as the pasting user**. That works for you. It breaks when a different person pastes, because they may have no permission to open the source file. The picture just disappears, with no explanation.

This is correct security behavior and must not be weakened by widening drive access. But it does mean a reference-only image is not a self-contained payload across logins.

**Options.**
- **A. Leave it.** Pictures arrive when you have access, vanish silently when you don't. Free and safe, but it looks like a bug and will be reported as one.
- **B. Leave it, but say so.** Same behavior plus "1 image could not be copied: you don't have access to the original." Still free, no longer looks broken.
- **C. Embed small pictures in the payload.** Below a size cap, carry the actual image data so it always pastes. Works for everyone, but the payload gets big, large pictures still fail (so you need B anyway), and it means a picture can leave a restricted file by being copied. Defensible (the copier could screenshot it), but it should be a decision, not an accident.

B now; C only if it's actually asked for.

### Q7: If a formula is pasted into a different file, what should it point at?

**The problem.** `=SUM(A1:A10)` means "the ten cells above me". `=Budget!B4` means "cell B4 on the sheet called Budget". Paste into a different file and there may be no sheet called Budget. This never comes up today, because a copy between files carries no formulas at all, only the numbers.

**Options.**
- **A. Carry formulas and shift them the way pasting normally does.** Relative references move correctly; references to a missing sheet go `#REF!`. Matches Excel and Google Sheets, and users already understand `#REF!`.
- **B. Formulas within one file, values everywhere else.** Never broken, never surprising, and quietly worse than the tool people are used to. They will notice.
- **C. Offer a choice.** "Paste values / paste formulas". Most control, most clicks, more to build. Worth having eventually regardless of the default.

A is what every spreadsheet user expects. Note this requires the payload to carry its **source anchor and sheet name**, so the target can recompute the offset.

### Q8: If cells are cut in one tab and pasted in another, should the originals disappear?

**The problem.** Cut means move, and moving needs two things: the cells appear in the new place, and they leave the old one. The clipboard only carries the first. The old tab has to be told to delete them, and it may be a different browser, a different machine, or a different person.

**Options.**
- **A. Across tabs, a cut behaves like a copy.** Simple, predictable, no half-finished moves. But a cut that doesn't remove isn't really a cut, and someone ends up with duplicates.
- **B. Delete the originals when the paste happens.** A real move, but only within one browser and login. Between two people it cannot work at all, and a half-applied move is worse than none.
- **C. Cut only moves where you cut it.** Within one tab, cut moves; anywhere else it copies and says so. Two behaviors, each easy to explain, and no data loss.

C is the honest one.

### Q9: How much should survive when cells are pasted into a document or a slide?

**The problem.** A range is a grid; a document flows and a slide is a free canvas. Neither has a natural home for column widths, conditional formatting and formulas. Something must be dropped. The question is how much.

**Options.**
- **A. Text only (roughly today).** Nothing surprising happens, and nothing useful arrives. Users rebuild the table by hand.
- **B. A real formatted table.** Documents already do this; extend it to slides. The common case ("put this table in the report") just works, and formulas become their displayed values, which is what people want there anyway. Costs a slides-side table renderer.
- **C. A picture of the table.** Looks exactly right, completely uneditable and unsearchable. Good as an option, bad as a default.

B, with C possibly offered later as an explicit "paste as image".

### Q13: Should a typed `5/1/2026` become a date, and in which order?

Typing `1/2/2026`, `31/12/2025` or `5 Jan 2026` into a cell keeps it as text; only ISO `2026-01-05` (and `2026-01-05 13:30`) becomes a date (`engine/format.ts` `parseCellInput`). Excel parses slash dates in the user's locale order; the repo writes dates day-month-year but spells en-US otherwise, so `1/2/2026` is ambiguous by design. Options: keep text (today), parse day-month-year only, or parse both when unambiguous (`13/12/2025`) and text otherwise. A formula result never goes through this path.

### Q12: Who opens an exported spreadsheet in real Excel, and when?

An agent can't do this; it needs a person with Excel or Google Sheets. It's a documented [verify-in-browser](../.claude/skills/verify-in-browser/SKILL.md) obligation. The rule exists because a library can write internal hyperlinks our own importer accepts and Google Sheets rejects. Either someone spends twenty minutes on it, or we consciously drop the rule for xlsx.

### Decided, not defects

- **The cell-range picker stays put when the grid scrolls.** It is a portaled `position: fixed` dialog placed once at its cell, so scrolling moves the grid underneath it. Reinder confirmed this is the wanted behavior: a card that scrolls with the grid can ride off-screen entirely. Do not "fix" this into a scroll-tracking popup without asking.
- **The drag-to-move band reaches 2px inside the selection**, so a click in that 2px does not collapse a multi-cell selection to that cell. Deliberate: outward reach is 4px because that side steals clicks from the neighboring cell, so the grab has to come from the interior. Reinder chose 4/2 over 4/4.
- **Clear formatting also clears the diagonal border.** `handleClearFormat` deletes the cell's whole `"r_c"` border key, which is what clear formatting should do. Pinned by `clear-format.test.ts`.

## Clipboard: put sheets on the shared system

Goal: a sheets → sheets copy-paste must work **between browser tabs and between different user logins**, so the complete payload has to live in the clipboard itself. The shared writer already produces the right shape (real table HTML plus an Eigen metadata span in one `text/html` payload), and sheets already writes both. The gaps are on the read side and in the type model. Today a sheets paste skips its own payload and is served from `ctx.copyState`, so a paste in another tab falls through to the foreign-HTML parser and loses formulas, number formats, conditional formats, validation and links ([CLIPBOARD.md](CLIPBOARD.md#sheets-serves-its-own-copies-from-memory)). The design is in [PROPOSAL_COPY_PASTE.md](proposals/PROPOSAL_COPY_PASTE.md).

Depends on **Q3**–**Q9**.

- [ ] **Step 1: define `EigenClipboardGridItem`** in `packages/lib/src/types/clipboard.ts`, reusing `Cell` and `ConditionalFormatRule` from `packages/lib/src/sheets/types.ts`, already the shapes the frontend and the backend share and the wire type for ops, so no new type surface and no new dependency edge. Add a builder and a strict read-side validator next to `parseEigenJson` (`packages/lib/src/core/clipboard/clipboard.ts`): any web page can forge the wire, and a grid item is far more dangerous than a text item. Version it, and make the reader fall through to the HTML table on an unknown variant rather than throw. **Depends on Q4.** **M**
- [ ] **Step 2: producer.** A pure `rangeToGridItem(ctx, ranges)` in `packages/sheet/src/state/`, *beside* `copy`'s table builder, never inside it, wired into `onCopy` in `components/Workbook/index.tsx`. **Must not break, in either direction:**

- The visible `<table>` keeps going out on `text/html` verbatim: it is why pasting into Excel, Google Sheets, Numbers and email works. **`copy` stays the source of the outbound HTML and must not become a renderer of the grid item.** Two producers over one range can drift, but deriving the HTML from the JSON changes what Excel receives, which is the regression to avoid. Deriving it later stays possible; undoing it is not.
- The foreign-HTML parser (the HTML-table branch of `handlePaste`) survives byte for byte: it is why pasting *from* those apps works. The HTML-paste bugs in it, such as the underline under Bugs, stay open; the grid item only stops our own users hitting them.
- `hasRichHtmlBeyondMarker` keeps returning true for a sheets copy. Docs relies on it (`handlePaste` in `apps/docs/src/components/docs/doc-editor.ts`) to parse the sheets table into a real Tiptap table; without the HTML table, **sheets → docs would silently degrade to a paragraph of tab-separated text**. The most likely regression in the whole program.
- The `sheet-copy-action-table` marker lives once, as `COPY_ACTION_TABLE_MARKER` in `state/modules/clipboard.ts`; import it rather than retype it. It has **no backwards compatibility** with fortune-sheet's `fortune-copy-action-table`, a ruling: such HTML on a clipboard across a server update pastes through `readEigenClipboard` as tab-separated plain text.
- Don't widen drive ACLs to make cross-login image paste work. The 403 is correct behavior (**Q6**).

**Behavior changes to expect and test:** a grid item makes the copy-time snapshot authoritative, where a same-tab paste today lands the live cells, so "copy, edit the source, paste" changes meaning (arguably more correct, but different). And a payload copied before a deploy may be pasted after it, so the grid item has to tolerate two tabs on different builds.

## xlsx round-trip fidelity

Both sides already work on the raw SpreadsheetML: the import reads it itself (`apps/api/src/lib/import/sheets/`), and the export writes it by hand (`apps/api/src/lib/export/sheets/xlsx/`). Anything that needs raw XML extends tested code rather than adding a pass.

- [ ] **Validation `allowBlank` is dropped, so we are stricter than the source file**: the reader has the attribute on each `<dataValidation>`, but the rule has no field for it. Excel ticks "ignore blank" by default, so after import you can't clear a validated cell: Enter pops a warning and refuses the edit. Export hard-codes `allowBlank="1"` (`export/sheets/xlsx/rules.ts`), losing it the other way. One field on `DataValidationRule`, one guard in `validateCellData`, both converters. **S**
- [ ] **Validation error and prompt titles and custom error text are dropped**: deliberate, since `import/sheets/rules.ts` reads only the prompt and the editor words its own messages (`ValidationHint`, `describeValidationRule`). - [ ] **Style-only cells balloon `celldata`**: an imported cell with only a default font carries a `{fs, ff, fc}` entry, so ruled-but-blank regions grow `celldata`. Treating a default-font-only cell as empty would fix that, but it changes import output for every style-only cell, and the import golden. Product call, not a bug. **S**
- [ ] **Filter criteria don't round-trip**: the reader reads the filter's span and skips its `<filterColumn>`, and the export writes none. The condition model is editor-only (`FilterEntry.byCondition` in `state/types.ts`; lib's `Sheet` carries only `filterRange`), so importing criteria means promoting `filter` to the lib type, and recomputing `rowhidden` from the criteria at import. **M**
- [ ] **A reversed `autoFilter` ref imports a reversed filter**: the importer (`apps/api/src/lib/import/sheets/worksheet.ts`) stores the `ref` it gets from `parseA1Range` as it is, so a ref such as `D4:A1` gives a `filterRange` whose first row and column come after its last. `a1RangeRef` orders the two corners, and this read does not. - [ ] **Conditional-format `stopIfTrue` and the aboveAverage variants are lost**: the reader (`import/sheets/rules.ts`) reads none of `stopIfTrue`, `stdDev` or `equalAverage`. - [ ] **Aggregate conditional-format rules scope each range on its own**: `duplicateValue`, the top and bottom family and above and below average compute over one of the rule's `ranges` at a time (the per-range loop in `engine/conditional-format.ts`), while Excel computes them over the rule's whole `sqref`. A paste or a fill that leaves a hole in a rule splits its range and so changes the scope of these rules; check what Excel does. - [ ] **Excel outline groups aren't imported**: `packages/sheet` has no grouping model, header gutter or collapse control to import into, though the rows and columns the reader reads carry `outlineLevel`. A missing editor feature, not a converter gap. - [ ] **`googleMonthMinute` diverges from numfmt on two pathological formats** (`apps/api/src/lib/import/sheets/styles.ts`): the `_\x` three-character skip, where we consume two characters and leave the third to month re-casing, and the `B1`/`B2` calendar markers, where we push an adjacency breaker that numfmt matches first. The `_\x` case also re-cases a literal character in the stored format string. **S**
- [ ] **An imported custom row still auto-grows in the editor**: the reader keeps a custom row's height and drops the flag (`readGrid` in `apps/api/src/lib/import/sheets/cells.ts`), so typing wrapped text into it grows it where Excel would not. - [ ] **A one-line wrapped cell grows its row on import**: `estimateCellHeight` (`apps/api/src/lib/import/sheets/from-xlsx.ts`) puts one wrapped line at about 26 px, so a row that isn't custom grows past the 20 px default where LibreOffice keeps it at 20 px. - [ ] **A tick box doesn't reach xlsx**: `validationOf` (`apps/api/src/lib/export/sheets/xlsx/rules.ts`) maps no `checkbox` rule, as Excel's data validation has no tick box, so the export drops it. ## Formula engine

- [ ] **A range split by whitespace isn't a reference to the walker**: `=SUM(A1\n:A2)`, `A1\t:B2` and `A1:\nB2` evaluate as a range (3 for 1 and 2), but `walkFormulaRefs` (`engine/formula-shift.ts`) never hands them to its callback, so a row op leaves them unmoved and the dependency index lists no cell for them. The walker and the evaluator should read one grammar. **S**
- [ ] **A function name followed by a space reads as a cell**: in `LOG10 (A1)` the walker takes `LOG10` for a cell, so an insert writes `LOG11 (A2)`. The engine already answers `#ERROR!` for `=LOG10 (100)`, so it is minor. **S**

- [ ] **A formula's text result that reads as an error is stored as one**: `=A1` over a cell holding the text `#DIV/0!` (typed with an apostrophe), and `="#N/A"`, give the error where Excel gives the text. `inferType` (`engine/formula-engine.ts`) and the editor's `setCellValue` (`state/modules/cell.ts`) type a result by its value, and `execFunctionGroup` keeps only the value, so the next cell reads it as an error too. The parser already tells the two apart (`Parser.evaluate`'s `error` against its `result`); carry that type into the cache entry and the cell write. **S**
- [ ] **`ROW` and `COLUMN` are `#NAME?`**: formulajs's are Google's `(matrix, index)` forms, so the engine leaves them out (`LEFT_OUT` in `engine/parser/supported-formulas.ts`), and an imported number stays through a recompute. Excel's answer is the reference's position, which a function never sees: the parser hands it the cells' values (`callCellValue` and `callRangeValue` in `engine/parser/parser.ts`). The parser would hand these functions the reference itself, and the formula's own cell for `ROW()`, which also gives a conditional-format formula's bare `ROW()` its cell. An engine `ISREF` needs the same. **M**
- [ ] **`ROWS` of a cell holding `#REF!` is `#REF!`**: Excel says 1, as a cell has a size whatever it holds. The engine's `ROWS` and `COLUMNS` read a typed `#REF!` and a cell holding one alike, and a reference that is gone has no size, so telling them apart needs the reference, as `ROW` does. **S**
- [ ] **The D-functions answer 0 on clean data**: `DSUM(A1:B4,"Age",C1:C2)` over a plain table is 0 where Excel sums the matched rows, `DCOUNT` 0, `DAVERAGE` `#DIV/0!`. formulajs reads the database and the criteria as an array of columns, each headed by its field name, where a range arrives as an array of rows. Transpose both before the call, in an override per function. **S**
- [ ] **Array operators don't apply element by element**: the operators are scalar, so one over a range has no answer. `C2:C3+1` and `SUMPRODUCT(--(B2:B4>15))` are `#CALC!`, or keep the number they hold, where Excel computes them per cell ([SHEETS.md](SHEETS.md#recalc-keeps-what-it-cant-improve)). The check sits where the grammar calls the operator (`UNSUPPORTED_ARRAY_OPERATION`), so a function handed a range in a scalar parameter gets past it: `SUMPRODUCT(ISNUMBER(A1:A3))` is a silent 0. The operators in `engine/parser/evaluate-by-operator/operator/` would map over a range operand, with implicit intersection, scalar functions lifted over ranges and a cell budget. It shows in imported workbooks: a govuk fire statistics file sums `SUMPRODUCT(('Data - fatalities'!$A$2:$A$933=FIRE0503a_raw!$A$4:$F$4)*…)` per cell. In the corpus 2,386 of 433,648 formulas use one, in 11 of 168 files with formulas, 1,956 of them `SUMPRODUCT`. To build in the arrays step of the engine rewrite ([ROADMAP.md](ROADMAP.md), "Rewrite the Sheets formula engine in steps"), the owner on 11 Nov 2026. **M**
- [ ] **Comparison operators don't match Excel**: `<` `>` `<=` `>=` are raw JavaScript over `comparisonOperand` (`engine/parser/helper/number.ts`), so text sorts by code point and case-sensitively, and numbers never compare below text; `=` and `<>` treat a blank as `""` rather than `0`. One shared `compareValues` helper behind all six operators. **Depends on Q2.** **M**
- [ ] **`&` binds tighter than `*` and `+`**: the grammar ranks `&` above the arithmetic operators (`%left '&'` after `*`, `/` and `^`), while Excel ranks it below them, so `2*3&"x"` is `#VALUE!` where Excel gives `"6x"`. A precedence change in the hand-edited parse table of `grammar-parser.ts` and its `.jison` copy. **S**

Left unregistered, so `#NAME?` and an imported cell keeps Excel's value: `T.DIST` (formulajs implements the legacy `TDIST(x, df, tails)`, so a cumulative flag is `#NUM!`), `T.TEST` (ignores tails and type), `F.TEST` (0.614 on Microsoft's example, Excel 0.648). - [ ] **The `*IFS` criteria don't match Excel's**: `SUMIF(S)`, `COUNTIF(S)`, `AVERAGEIF(S)`, `MAXIFS` and `MINIFS` share formulajs's `lib/utils/criteria-eval`, which compares text case-sensitively and knows no wildcard but a lone `*`, so `COUNTIF(A1:A3,"a*")` is 0 and `COUNTIFS(A1:A3,"APPLE")` misses `apple`, where Excel matches both. A `TRUE` criterion matches no cell, where Excel matches the `TRUE` cells; `""` matches no cell, where Excel matches the blank cells and the empty texts; and a criterion that is a blank cell matches every cell in `SUMIFS`, `COUNTIF` and `MAXIFS` and none in `SUMIF`, where Excel reads it as 0. - [ ] **The `*IF` family's value ranges don't match Excel's**: formulajs's `SUMIFS`, `AVERAGEIF` and `AVERAGEIFS` give `#VALUE!` for a sum or average range that holds any text or error, where Excel skips the rows no criterion matches. `SUMIF` adds a matched text or error as a string: `SUMIF(A1:D1,"#N/A")` over two #N/A cells is `"0#N/A0#N/A0"`, where Excel gives #N/A. `MAXIFS` and `MINIFS` skip a matched error, where Excel hands it on. `COUNTIF` over one cell matches nothing, so `COUNTIF(B1,1)` is 0 with 1 in B1. `AVERAGEIFS` reads a criteria range down a column only, so a row range matches nothing. The engine's own `SUMIFS`, `AVERAGEIFS` and `COUNTIFS`, on the walk `extremeIfs` does for `MAXIFS`, fix all of it, together with the `*IFS` criteria row. **M**
- [ ] **A size check compares clamped ranges**: every range is clamped to its own sheet's grid (`callRangeValue` in `engine/parser/parser.ts`), so two ranges Excel sees as the same size arrive as different sizes when their sheets hold different row or column counts. - [ ] **The editor recalcs no volatile function on an edit**: `NOW`, `TODAY`, `RAND` and `RANDBETWEEN` compute when typed and keep that value, because a formula that reads no cell is nobody's dependent (`execFunctionGroup` in `state/modules/formula-exec.ts`). - [ ] **A date-typed formula result shows its serial in a mask-less cell**: `evaluate` returns an Excel serial for a Date result, and neither the editor (`execFunctionGroup` writes only the value, `state/modules/formula-exec.ts`) nor the server's write-back (`withResult` in `engine/recalc.ts`) gives a General cell a date format, so a fresh `=DATE(2026,1,5)` shows `46027` until the user formats it. - [ ] **formulajs parses ISO date strings as UTC** ([SHEETS.md](SHEETS.md#values-follow-excels-grid-and-calendar)): `DATEVALUE` and the serial-to-Date step inside `DAY`, `MONTH` and `YEAR` land on the day before west of Greenwich. Tests run in UTC and can't see it; the timezone pin in `parser/unit/helper/number.test.ts` shows the pattern. **S**

The space operator needs a production, not a lexer rule or a precedence entry, and `grammar-parser.ts` can't be regenerated ([SHEETS.md](SHEETS.md#the-engine-is-the-half-the-server-imports)), so it means a new grammar with a regeneration script, or hand-built states. **M**
- [ ] **A range that ends on a call is `#ERROR!`**: Excel reads `A1:INDEX(A1:B3,2,2)` as the range from A1 to the cell `INDEX` returns, so `=SUM(A1:INDEX(A1:B3,2,2))` sums A1:B2. The grammar's range rules join two cell references only (`grammar-parser.jison`), so the formula is `#ERROR!`, and so is `INDEX(…):B3`. The dependency walk already reads A1 and A1:B3 for it (`extractDependencies` in `engine/recalc.ts`). It needs a range production whose ends may be calls, and the reference form of `INDEX`, which the engine lacks. **M**
- [ ] **A 3-D reference is `#REF!`**: Excel reads `'First:Last'!B1` as B1 on every sheet from First to Last, so `=IF(SUM('I- User Parameters:O- BCR & Dashboard'!B1)=0,"OK","ERROR")` in the gov.uk Greener Minibus Tool is `OK`. The engine looks up a sheet named `First:Last`, finds none and answers `#REF!`, which a recompute stores over Excel's value, since `#REF!` is an answer (`cantEvaluate` in `engine/formula-engine.ts`). It needs a grammar form for a sheet span, the walker and the dependency index reading every sheet in it, and a row, column or sheet op shifting it. Until then, `cantEvaluate` could take it as no answer, so the stored value stays. **M**
- [ ] **An unquoted non-Latin sheet name is `#ERROR!`**: Excel writes a reference to a sheet such as `Лист1` without quotes, `=Лист1!A1`, but the grammar's `SHEET` rule (`grammar-parser.jison`) and `SIMPLE_SHEET_NAME` (`engine/parser/helper/cell.ts`) take only Latin letters, digits and `_` unquoted, so the formula is `#ERROR!` and records no dependency. `='Лист1'!A1` works. Check which other characters Excel leaves unquoted, such as a dot in `Sheet.1`, then widen both in one change, the grammar's two files included. **S**
- [ ] **Cross-sheet click-to-reference is dead**: `formulaCache.rangetosheet` (`FormulaCache` in `state/modules/formula-cache.ts`) is read in `formula-range.ts` but never assigned outside a test, so the sheet-name branch of `getRangetxt` (`state/modules/cell.ts`) is unreachable. Switching tabs cancels the composition anyway (`selectSheet` in `SheetItem.tsx` calls `cancelNormalSelected`). Either delete the field and its branches (**S**), or build the feature: the tab switch keeps an active composition instead of cancelling it, which touches focus, the range-highlight overlay and undo (**M–L**). Decide the feature first.
- [ ] **A running total filled down recalcs in quadratic time**: each cell adding the one above it, filled down 5,000 rows, takes 3.4 s to recalc, and the time grows with the square of the rows (`engine/dependency-index.ts`, `engine/recalc.ts`). The server stops at `SERVER_RECALC_BUDGET`, but the editor's engine has no budget, so the tab freezes. Profile it, then make that step linear. **S**
- [ ] **The sheet engine swallows an out-of-memory** ([DOCUMENT-TRANSFORMS.md](DOCUMENT-TRANSFORMS.md#out-of-memory-is-the-jobs-not-the-servers)): `isOutOfMemory` lives in `apps/api/src/lib/core/errors.ts`, which `packages/sheet` can't import, so its catches turn an out-of-memory into something else. `replaySheetsOps` (`engine/replay-ops.ts`) skips an op batch and silently truncates an export or preview, `recalcSheets` keeps old values, and `Parser.evaluate` and `inBand` return a formula error. Move `isOutOfMemory` to `packages/lib`, have the API import it, and rethrow it from each of those catches. **S**

### Functions

- [ ] **The index of `VLOOKUP` and `HLOOKUP` and the type of `MATCH` given a cell, a range or an array**: Excel answers `#REF!` for an error cell, a text that is no number, a 2-D range and a union, a 1-D range is one `#VALUE!` for the two lookups and `#REF!` for `MATCH`, and an array lifts only `MATCH`. ## Sync and undo

The op log, its order and how edits reach the undo stack ([SHEETS.md](SHEETS.md#every-tab-applies-the-batches-in-the-logs-order)).


- [ ] **Fold the op log while editors are connected**: the server compacts a workbook's log only when it closes (`closeAfterLinger` in `apps/api/src/lib/collab/collab-document.ts`), so a workbook some tab always has open never compacts, and every joiner and `readSheetsFromDoc` replays all of it. The cost is unmeasured. Trigger: joiners of a long-open sheet load measurably slower (measure at 100, 1,000 and 5,000 batches on the reference workbook). Then the server also compacts past a threshold while tabs are connected. A connected tab would load each fold as a new snapshot, which replays the whole log and empties its undo stacks ([SHEETS.md](SHEETS.md#a-new-snapshot-loads-into-the-mounted-grid)), so a live fold first needs a way for a tab to keep its grid and its undo through a fold of batches it holds. Then come the trigger in `CollabDocument` and the broadcast: each fold sends the whole snapshot, which on a large sheet and a slow link needs the ROADMAP row "Collab: large documents on slow connections". - [ ] **The open cell editor doesn't show a peer's write to its cell**: the editor loads its cell's text only when it opens ([SHEETS.md](SHEETS.md#enter-and-tab-commit-an-edit-and-move-on)), so it keeps showing that text while a peer's batch changes the cell, and Enter writes it over the peer's value. - [ ] **One user with two tabs open gives React a duplicate key**: the presence cursors are keyed by `userId` (`OverlayVisuals.tsx` in `components/SheetOverlay/`), so two tabs of one user render two cursors under one key. Key them by something each tab has of its own. **XS**

- [ ] **A batch recorded before a peer's row insert writes at the rows it recorded**: ops are not transformed ([SHEETS.md](SHEETS.md#every-tab-applies-the-batches-in-the-logs-order)). When the log puts a peer's insert first, a late batch's cell writes land on the cells that moved into place. A write into one field of a cell that is now empty is skipped alone, on every tab and in the replay, and the rest of the batch lands ([SHEETS.md](SHEETS.md#a-write-whose-parent-is-gone-is-skipped-alone)). - [ ] **A paste past the grid ships its growth as plain cell writes**: a paste that runs past the last row or column grows the grid (`roomFor` in `state/events/paste.ts`) and ships `add` writes on `data/N` with the sheet's new `row` and `column`, not a row or column insert. A marker inside the paste's own batch is no small change: `PatchOptions` holds one marker where a paste can grow rows and columns at once, `patchToOp` drops the `data` writes of a batch with a marker and puts the marker after the rest, and the undo through `undoRowCol` would have to restore the cells the paste wrote inside the old grid too. The case to pin is two peers inserting rows at once near the 10,000-row limit: each author applies its own insert first, and a joiner refuses the one the log puts second. Found in review and not reproduced yet; pin it over two tabs and a joiner through the log-order replay (`replayOps` in `components/Workbook/api.ts`). **S**

- [ ] **A row or column insert doesn't move a dropdown's range source**: a list rule that reads its options from cells keeps the reference as text in `value1`, such as `A2:A4`, and `applySheetsInsertRowCol` and `applySheetsDeleteRowCol` (`engine/rowcol.ts`) move a rule's ranges and a formula rule's text but not that text. Fix: shift `value1` and `value2` of a rule whose source is a reference through `functionStrChange`, on every sheet, and in `shiftEntries`. **S**
- [ ] **Two rules added at once at the rule cap leave the tabs apart until a reload**: on a sheet with 1,023 validation rules, or as many conditional formats, two peers each add one. Each tab keeps its own and drops the peer's as past the cap (`withinCap` in `packages/lib/src/sheets/yjs-ops.ts`), while a joiner keeps the one the log puts first. The two adds write different ids, so they commute and no tab applies the log again. Fix: a rule add that the cap could drop does not commute. **S**
- [ ] **A forged write inside `config` leaves tabs apart until a reload**: `opToPatchOnSheets` (`packages/lib/src/sheets/yjs-ops.ts`) drops a write that removes `config` or leaves it no map, but not a remove of one of its maps, such as `config.merge`, or a replace of `config` with `{}`. - [ ] **A batch whose added sheet lands renamed reads another tab by the old name**: an add whose name is taken takes the next free one, such as `Two (2)` (`legalSheetNames` in `applySheetsBatch`, `engine/replay-ops.ts`), but the formulas, rules and links the same batch writes still name `Two`, so they read the tab that holds the name.
