# Calendar

> **TLDR:** Each user, and each team that turns it on, has calendars of events in one SQLite database per Home. An event is kept as the iCalendar text that was written for it, plus Eigen's own `X-EIGEN-*` lines, and that text is the truth. Beside it the database keeps extracted fields such as title, start and end, so the app can query fast, and those can be rebuilt from the text at any time. The store is `apps/api/src/lib/calendar/`, the iCalendar reading and writing is `apps/api/src/lib/ical/`, the web app is `apps/calendar/`, and the CalDAV server has [CALDAV.md](CALDAV.md).

A user has one or more calendars, and each calendar holds events. A calendar can be shared with other users and with teams. A team can have calendars too, once an admin turns that on. Guests have no calendar.

An event gets in and out in four ways. The web app talks to the REST routes in `apps/api/src/routes/calendar.ts`. A calendar client such as Apple Calendar or Thunderbird syncs over CalDAV. An invitation travels between Eigen users directly, and to and from everyone else by mail. That mail format is iMIP (RFC 6047): a mail that carries a small iCalendar file. And a whole `.ics` file can be imported or exported.

All of it lives in one file per Home, `eigen.calendar/calendar.db`. A Home is the data folder of one user or one team ([STORAGE.md](STORAGE.md#a-home-is-loaded-on-demand-and-dropped-when-idle)), so there is one database per owner, not one per calendar. The calendars are rows in its `calendars` table.

The truth for an event is its iCalendar text (RFC 5545, the `.ics` format): a `VCALENDAR` wrapper with one `VEVENT` block per event inside. Eigen stores that text as it was written, plus its own `X-EIGEN-*` lines, in the `ics` column of a row in the `resources` table. A resource is one such stored file, the unit a CalDAV client reads and writes. It holds one series: an event with all its repeats. When someone changes a single occurrence of a series, iCalendar writes the changed occurrence as an extra `VEVENT`, called an override, and it lives in the same resource. Keeping the text as written means nothing a client sent is lost. A reminder setting or a property Eigen has never heard of goes back to that client unchanged on its next sync.

The text sits in a database column and not in `.ics` files on disk, for two reasons. One transaction writes the text together with everything derived from it, so a crash can't leave the two disagreeing. And only the API process opens the database, so there are no watchers and nothing to reconcile, unlike mail, where Dovecot changes the files too ([IMAP.md](IMAP.md)).

Parsing iCalendar text for every "what happens this week" would be slow. So each write also fills the `events` table: one row per `VEVENT` and one per cancelled occurrence, with the title, the start and end, the repeat rule and the guests as columns. The resource row has a few derived columns of its own. Together these are the projection. None of it is truth, because all of it can be thrown away and computed again from the stored text.

Two more terms come back in every section. A stamp is an `X-EIGEN-*` line Eigen adds to the text for a fact iCalendar has no field for, such as who created the event. A linked copy is the event an invitation puts in a guest's own calendar: an ordinary resource with a stamp that names the organizer's event.

The sections run in this order: how an event is stored and written, time zones, repeats, sharing and quota, invitations between Eigen users, invitations by mail, import and export. Four things in them surprise people:

- No client can write a stamp, and an invitation's link to its organizer is a stamp, never the `ORGANIZER` address ([§ Eigen's own facts ride as X-EIGEN- lines](#eigens-own-facts-ride-as-x-eigen--lines-no-client-can-write)).
- A web save patches only what moved, while a CalDAV PUT replaces the file ([§ A web save patches what moved](#a-web-save-patches-what-moved-and-a-caldav-put-replaces-the-file)).
- A repeat is expanded on every read and never stored ([§ Recurrence is expanded per read](#recurrence-is-expanded-per-read-never-stored)).
- An invitation by mail acts only for a sender our own mail server verified ([§ Inbound iMIP](#inbound-imip-acts-only-on-a-sender-our-own-mta-verified)).

## The stored bytes are the event, and every column is a projection

A resource row holds the bytes a client wrote, `VALARM` details and unknown properties included, and the SHA-256 of those bytes is its etag. A CalDAV GET serves them back verbatim ([CALDAV.md](CALDAV.md#get-serves-the-stored-bytes-and-put-answers-an-etag-only-for-bytes-it-kept)). How a resource and a calendar are named is in [CALDAV.md](CALDAV.md#eigen-names-what-it-creates-and-keeps-a-clients-name-as-written).

The `events` rows, `uid`, `etag` and `hasUnindexedRecurrence` are projected from the bytes each time a resource is written.

Some facts no VCALENDAR can hold live only in the database: a calendar's name, color, visibility, default flag, `shares`, `ctag` and `syncGen`, the `resource_tombstones` a sync delta reports as removals, and the recipient-side `shared_calendars`. See `schema.ts` and [DATABASE.md](DATABASE.md). Because the events themselves live in these rows, the database runs synchronous FULL ([DATABASE.md § A database that holds the truth runs synchronous FULL](DATABASE.md#a-database-that-holds-the-truth-runs-synchronous-full)).

## One resource holds one series

A resource holds one UID, the id iCalendar gives a series. Under it sit the master VEVENT, which carries the repeat rule, one override VEVENT per edited occurrence, and a VTIMEZONE, the definition of a time zone, for every TZID they name. A PUT carrying two UIDs is refused, or a second UID's overrides would hang off the first master.

Eigen cancels one occurrence with an `EXDATE` on the master, never with a `STATUS:CANCELLED` override. Thunderbird omits such an override from its next PUT, and the full replace would read that as "the client removed the exception" and bring the occurrence back. Cancelling a moved occurrence replaces its override with an `EXDATE` too, and the cancelled row keeps the override's id. Deleting an occurrence that is already cancelled changes nothing, whichever of the two spellings a client used, as a second delete of any row does. No screen shows a cancelled row, and a guest who could delete the organizer's cancellation would get the date back on their own copy.

## Eigen's own facts ride as `X-EIGEN-*` lines no client can write

iCalendar has no place for a row id, a creator, a color or an invitation link, so they ride inside the VEVENT as `X-EIGEN-*` properties, spelled once in `EIGEN` (`lib/ical/ical-parse.ts`):

| Line | Carries |
|---|---|
| `X-EIGEN-EVENT-ID` | the `events` row id, so an id survives each time the file is projected again |
| `X-EIGEN-CREATED-BY` | the user who first wrote the resource |
| `X-EIGEN-ORGANIZER-EVENT`, `-USER` | the invitation link on an attendee's copy ([§ A linked copy is an ordinary resource](#a-linked-copy-is-an-ordinary-resource-with-the-organizers-stamp)) |
| `X-EIGEN-COLOR` | the per-event color, the owner's own display choice, which no message carries |
| `X-EIGEN-IMPORTED-ORGANIZER` | the organizer an imported file named |
| `X-EIGEN-EXDATE` | beside each `EXDATE`: the exclusion's row id, SEQUENCE and message stamp |
| `X-EIGEN-GUEST-CUT` | on a guest's copy: the first date their "delete this and following" removed ([§ An RSVP names its scope](#an-rsvp-names-its-scope)) |

**An incoming stamp is never trusted.** `parseIcs` is the reader for bytes a stranger wrote, and its result type can't name an Eigen fact, so a forged one has nowhere to land. On a PUT, `restampResource` strips every Eigen property and parameter at every level, then copies the stamps back from the stored resource. It matches on UID plus recurrence key, never on the raw `RECURRENCE-ID` or `EXDATE` text, which clients rewrite between TZID, UTC and comma-joined forms. Only a resource nobody wrote before takes the caller's own stamps. Nothing that leaves the Home carries a stamp, except a CalDAV GET to the owner's own clients.

## Every write takes one lock and one function

bun:sqlite already makes a transaction atomic and serial. `Calendar.writeLock` exists for the async gaps between a check and its commit, such as the quota lookup, so a racing `If-Match` PUT loses inside the lock. Reads take no lock.

Every resource write ends in `Calendar.writeResource`. It takes a `PreparedResource` computed once (`resource-store.ts`), so the bytes the checks judged are the bytes that land. It checks `EVENT_MAX_BYTES` (5 MiB), then the Home's storage budget, then commits. The commit is one transaction: the ctag bump, the blob, a delete-and-reinsert of the resource's `events` rows, and clearing any tombstone at that uri. A throw anywhere leaves the old bytes and the old projection in place. `purgeResource` is the same in reverse.

`Calendar` holds what must be one per Home: the database, the lock and the byte counter. The domain logic is plain functions over it in the sibling modules. `Calendar` is the one entry point on purpose: routes and DAV call it, and the sibling modules take it as their first argument.

`moveEvent` re-homes a resource between two calendars of one Home in one transaction, so no window shows it in both. A lone occurrence can't be moved, a UID the target holds is a 409, and a uri the target holds becomes a fresh name. `deleteCalendar` deletes the calendar's tombstones itself, since no cascade reaches them and a calendar recreated at that id would inherit them.

## A web save patches what moved, and a CalDAV PUT replaces the file

The web form restates every field on every save. So `updateEvent` (`events.ts`) diffs the submitted times against the stored row, and `patchEvent` (`lib/ical/ical-component.ts`) writes only the properties that really changed. It compares what a property says, never how it is spelled, so the first web save of a client's event rewrites none of its lines: `LANGUAGE` on a title, an `ORGANIZER`'s `ROLE`, `ROLE=CHAIR` on an attendee, `CN` equal to the address, `INTERVAL=1` and an empty `LOCATION` all stay. It adds one line only, to an event with guests that names no `ORGANIZER` ([§ The organizer's writes fan out](#the-organizers-writes-fan-out-and-only-the-organizers)), and removes one only, the `ORGANIZER` of a VEVENT without guests, which RFC 5545 asks for; neither mails anybody. A title edit leaves a client's own `DTSTART` spelling, its `DURATION` and its VTIMEZONE alone. Each `ATTENDEE` line is patched in place, one parameter at a time, so `CUTYPE`, `RSVP` and every `X-` parameter a client set survive. A save that patches nothing writes nothing: no ctag moves, nothing is announced and no guest is mailed. A save only its owner sees, such as a color, a reminder or the same instants in another zone, writes and announces but mails no guest and moves no `SEQUENCE`: `propagateWrite` compares the file a guest would get before and after, its revision aside. A new override is compared with the occurrence its series yielded there, so recoloring one date is no message either. A repeating event's zone counts, because its rule steps in that zone's wall clock and a later occurrence can move an hour, so its guests hear it at the same `SEQUENCE`.

A CalDAV PUT replaces the whole resource, under the preconditions and the linked-copy rule in [CALDAV.md](CALDAV.md#a-put-is-judged-inside-the-write-lock).

Every VEVENT an edit changes gets its revision fields from `touch`, by the one rule in [§ A revision rises by one rule](#a-revision-rises-by-one-rule).

## A web write carries the etag its form holds

Two clients editing one event don't last-write-win. Every web write sends an etag: an update and a move in the body, a delete as a query parameter, and an override's creation in its body. A series and its overrides are one resource and so one etag, which is why a new override is judged against its master, and why one guest's reply stales every occurrence of the series. `assertEtag` (`events.ts`) judges inside `writeLock`, against the etag the write replaces, and a mismatch is a 412. The field is optional on the routes, so a script that loaded none writes unconditionally, and a call that crosses homes for a shared calendar passes it along. CalDAV never reaches these routes: it goes through `dav-store`. A move changes no bytes and so no etag, and a move elsewhere doesn't refuse a form opened before it.

A 412 reloads the events and tells the user (`onEtagWriteError`). `useEventDetailState` holds the clicked occurrence but hands the dialog the current list's copy, so a retry from the panel or its delete confirmation sends the reloaded etag. An occurrence that has left the list, because a save just truncated its series or it moved out of the view, stays on screen as clicked, so a running save keeps its dialog. Its writes stay refused until it is reopened, which is accepted as rare.

Edit event keeps what was typed and follows the rest. Its one state, `typed`, holds only what the user changed, and a field reads that, else the event as the list has it now. So a refetch moves the untouched fields, a clean form just follows the event, and no seed has to be kept in step. The times and the repeat are one entry, because a preset rule names the start's weekday and an end means nothing beside another event's start: changing one holds them all. The time zone isn't a field. The times are absolute, and the zone stays the event's. A guest list the user edited says who is on it, while each guest's reply stays the server's, so a second Save can't revert an RSVP.

The form's etag (`useHeldEtag`) is the event's when typing began, not the live one, so a Save over a change the user wasn't told about is refused even though the untouched fields already show it. With nothing typed, a Save answers to the event as it is. A refusal brings back the form, however deep the Save was behind the recurring choice or the move warning, and lets the etag move on once, to the event the toast says to check: the next Save sends the reloaded one, and a change after that reload is refused again. That Save overwrites a field typed here that also changed elsewhere. On a list edited here, a guest added elsewhere is dropped, and a guest removed elsewhere comes back with their old reply. The form can't show both values, and typing is what a refused Save must not lose.

A save of two writes takes the etag the first one answered: an update and then a move, or a truncate and then the new series. It keeps that etag if the second fails, so a retry isn't refused over its own first write. A move to another owner's calendar creates the copy before the delete is judged, so it first refuses, as a 412 would and with no writes, a form whose etag isn't the event's as this tab has it (`useRefuseStaleEvent`). In the rare race where the change hasn't reached this tab, the create succeeds and the delete is refused: the copy and the original both stay, nothing is lost, and the toast shows. Every redo copies the whole form again, so it may make a second copy and invite the guests a second time, as it does after a delete that failed for any other reason. That is accepted, because remembering the first copy lost everything changed after it.

## ical.js is the one serializer, and an edit touches only what it changes

`ICAL.Component.toString()` writes every resource, so folding, escaping and parameter quoting are ical.js's problem. It runs with one `bun patch` (`patches/`) holding two fixes that belong upstream, and each goes when a release carries it. `parse._parseParameters` looks for the `:` that ends the parameters only up to the next `;`, since a search to the end of the line per parameter grows with the square of the line. `Component.getTimeZoneByID` scans the root's VTIMEZONEs once and keeps the answer until the root's subcomponents change in number, since a scan per value costs values × siblings when a file names a zone it never defines. A swap that leaves the number the same keeps the old answer, which only a zone `Intl` knows can meet, and that resolves through `Intl` anyway ([§ A time resolves through Intl](#a-time-resolves-through-intl-before-the-files-own-vtimezone)).

Removing some of a list goes through `keepProperties` or `keepSubcomponents`, one rebuild of the list, because ical.js scans and splices the whole list per item it removes, and adding a component to a new parent removes it from the old one the same way. `importEvents` empties each VCALENDAR with `removeAllSubcomponents` for that reason. A rebuild needs a dense cache, so `parseCalendarStream` hydrates every component in order: ical.js caches by index, and a cache first written far along stays a sparse array, where each splice is slow. `buildResource` assembles a new VCALENDAR from rows, for a REST create and for an iMIP message about a whole series. Every other write edits the stored component in place, such as `applyEdits` and its one-edit call `patchEvent` in `ical-component.ts`, so every property Eigen didn't touch stays as the client wrote it. A property it does change is rewritten whole, so a retitled `SUMMARY` loses its `LANGUAGE`, and the form trims a title, so spaces around a client's title count as an edit. An `ORGANIZER` keeps its parameters until its address changes, its `CN` included.

A written `DTEND` removes the `DURATION` that stated the length before it, since RFC 5545 §3.6.1 allows one or the other. An end instant that falls in the second pass of a repeated hour can't be named in the stored zone's wall clock. It is written as a UTC `DTEND` beside the TZID `DTSTART`, which RFC 5545 allows, so the duration survives.

## Eigen writes a VTIMEZONE for every zone it names

Without a VTIMEZONE, strict parsers (ical.js included) read a TZID's wall times as floating (RFC 5545 §3.6.5). `vtimezone.ts` builds one from `Intl` offset data. A zone with a regular DST rule compresses to two open-ended RRULE observances, and an irregular one gets one observance per transition.

A definition a property still names is the client's own and is never rewritten. One nothing references any more is dropped. A TZID that is no IANA name, such as Outlook's `W. Europe Standard Time`, gets no block when the file defines none: the parser already maps it ([§ A time resolves through Intl](#a-time-resolves-through-intl-before-the-files-own-vtimezone)), and a block under the client's name would state Eigen's rules as theirs. New blocks go in front of the VEVENTs, because a client reads the file top to bottom and a TZID met before its definition is floating to it. `apps/api/src/test/ical/vtimezone.test.ts` checks the generator against `Intl`.

## Two readers, one trust rule

`parseIcs(text)` reads bytes a stranger wrote and can't hold a stamp ([§ Eigen's own facts ride as X-EIGEN- lines](#eigens-own-facts-ride-as-x-eigen--lines-no-client-can-write)). `projectResource(component)` reads a resource the store wrote and adds the stamps on top of the same projection.

`parseCalendarStream` is the one place a `.ics` becomes a component tree, stored or not, and `parseResource` is the same for a text that must hold one object. Before it builds a component it refuses a calendar nested past `MAX_NESTING` (8 levels, where RFC 5545 needs 3) with ical.js's own `ParserError`, so each caller's usual refusal answers: a PUT 403, an import 400, a preview 422, an invite card `null`. A resource stored past the limit by an older build still serves its bytes to GET, REPORT, the range read and export, because none of those parse it. A write to it is a 500. So is deleting one occurrence, which edits the file, while deleting the whole resource works.

A VEVENT the parser can't read is skipped and counted rather than failing the file. Each caller answers for its own surface: a PUT refuses the payload, the quick look counts it in `dropped`, an import in `failed`. Each VEVENT is wrapped in an `ICAL.Event` built with `{ exceptions: [] }`, which skips ical.js's scan for sibling exceptions. That scan is quadratic over a whole file: 20,000 events took 17 s.

## A time resolves through Intl before the file's own VTIMEZONE

A valid IANA TZID resolves through `Intl` even when the file defines a VTIMEZONE for it. That is the path the builder computes its wall times with, so identical bytes name one instant, and a repeated hour resolves to its first pass. A UTC value is exact. `Intl` reads a zone in any case, and `normalizeTimezone` answers with `Intl`'s own spelling, so the stored `timezone` holds one spelling per zone and the formatters kept per zone stop at the zone count. The bytes keep what the client wrote, and a TZID in another spelling gets no generated VTIMEZONE.

A TZID `Intl` doesn't know goes through `propTzid` (`ical-parse.ts`). It tries the Windows zone table first, because Outlook writes names like `W. Europe Standard Time` (`normalizeTimezone`, over the CLDR rows in `packages/lib/src/core/calendar/windows-zones.ts`). The table leaves out CLDR's `UTC` row, because the Windows name `UTC` is also Intl's, and the row turned a client's `UTC` into `Etc/GMT`, both in the stored zone and in the TZID a moved event was written with. Then it tries the `X-LIC-LOCATION` of the file's VTIMEZONE, where libical writes the IANA name beside a TZID no standard knows. When neither resolves, the stored `timezone` is `null`, and the file's own VTIMEZONE gives the parser its instants. Eigen reads that VTIMEZONE itself (`vtimezoneOffset`, `vtimezone.ts`), never through ical.js, because ical.js walks each observance's rule from its DTSTART, Outlook's 1601 included, so its cost follows whatever the file states. For each observance a yearly rule of one `BYMONTH` and one `BYDAY`, with or without `BYMONTHDAY`, and with or without a `BYHOUR`, `BYMINUTE` or `BYSECOND` that repeats the observance's start time as Lotus Notes writes, names one onset in the time's year and one in the year before, within its DTSTART and `UNTIL`, and an observance without a rule has its DTSTART as its one onset. The latest onset the time has passed gives the offset. That is the shape Outlook writes, and zone databases write for their current rules. A rule in any other shape, an `RDATE`, or more than 16 observances, and the whole zone reads as its first STANDARD's `TZOFFSETTO` all year. An hour the clock skips and an hour it repeats resolve as `Intl` resolves them, so a file zone and its IANA twin name one instant. Two observances of one kind without an `UNTIL` both stay in force, as ical.js reads them. A `DTSTAMP`, `CREATED` or `LAST-MODIFIED` a client wrote with a TZID reads the same way. A floating time maps its wall components through `Date.UTC`, never through the server's zone.

## Recurrence is expanded per read, never stored

An `RRULE` is stored as written and expanded in memory per query. An override is a VEVENT in the same resource, projected with `parentEventId` and `recurrenceDate`. An override keeps its stored occurrence key even after it moved, because the frontend sends that key back in a `scope='this'` RSVP.

A `UNTIL` ending in `Z` beside a zoned start is an instant (RFC 5545 §3.3.10), so `wallClockRule` (`wall-clock.ts`) moves it into the series' wall clock before the walk, and a cut writes one: `truncateRRule` ends a timed series one second before the cut day starts in its zone, which every client reads as the same day. Beside an all-day `DTSTART` RFC 5545 requires a `DATE` `UNTIL`, and strict clients refuse a datetime there, so an all-day series ends on the day before the cut as a date.

A range read (`occurrences.ts`) is bounded by its window, not by the size of the Home. It loads the single events overlapping the window, the masters starting before its end (a rule never steps back before DTSTART), and their overrides plus any override moved into the window.

The edit dialog opens on an occurrence but "All events in series" saves on the master. So `seriesEditFromOccurrence` (`packages/lib/src/core/calendar/calendar-utils.ts`) sends a delta. The master's times shift by what the user moved, and a text field travels only when retyped. So does the guest list: the master's own list with the guests the user added or removed, so a guest the opened date leaves out stays on the series. A series-wide text edit also reaches every override that still carried the master's old value; one that set its own keeps it.

## A RECURRENCE-ID names the original occurrence

An override's `RECURRENCE-ID` and an `EXDATE` both name the occurrence the series would have had, computed from the master VEVENT in its own DTSTART form, value type included. It is never the override's moved start, and never `VALUE=DATE` because the override was toggled to all day. Either would match no occurrence and orphan the override (RFC 5545 §3.8.4.4). The master is read from the file after its own patch, so an override that arrives in the message that moves the series names the new time.

A copy of one date holds no master to compute that instant from, so it keeps the organizer's own `RECURRENCE-ID`, and only its file does: no column holds it. It writes the line back in the zone the organizer wrote it in, never in the moved start's zone or all-day form, so the copy reads it back under the key it was filed under. A floating `RECURRENCE-ID` names no instant, so a copy keeps only the date it is written on. Every iMIP REPLY names its occurrence by what the stored file holds (`storedRecurrenceIds`), read before a delete erases it, and Google and Outlook match the answer to their occurrence by that instant. The relay gives a guest invited to one date the series' original slot in the series' zone, as a mailed REQUEST does, so the guest's answer and the organizer's next update find that date.

That key is provisional until the series arrives, because the copy's own file may not state the series' zone. A lone `RECURRENCE-ID` that names an instant and reaches a copy holding a timed master is keyed again in that master's zone (`occurrenceKey` in `invitations.ts`). So is each date of a copy of single dates when a timed series replaces it, by the instant its stored line names, so a date named in UTC keeps its row and answer.

## An occurrence is keyed by its wall-clock date in the series' zone

An occurrence key is a `YYYY-MM-DD` date. A range read also carries timestamps, so it stays on the reviving treaty, and the read hooks (`withOccurrenceDay`) put the key back from the `Date` the reviver makes of it. Expansion runs in wall-clock space, so an override must key to the same date to attach to its occurrence. **A timed `RECURRENCE-ID` or `EXDATE` names an instant (RFC 5545), and it keys on the day that instant falls on in the series' zone, whatever zone it is written in.** So an override an organizer names at 17:00 New York replaces the Auckland series' occurrence at 09:00 the next day, the one the guest would otherwise see twice. `recurrenceKeyOf` is that one rule for the projected row and for every edit of the file, and `apps/api/src/test/calendar/calendar-timezone.test.ts` pins the keying.

The series zone is the TZID of each UID's master DTSTART, and a timed master with none keeps its series in UTC. A `DATE` value keeps its date, and a floating one reads in the series' zone. An all-day series has no clock, so a timed value on it keys on the date it is written on, whatever its TZID. An occurrence a file holds without its master knows no zone but the one its `RECURRENCE-ID` is written in, UTC included, and keys in it whatever zone its DTSTART is restated in. A zone only the file defines keys in UTC, the form the copy writes the line back in.

Five edges are accepted:

- A series whose zone changes keys its overrides in the new zone, so one near midnight can land on the next or previous date.
- A previewed file whose override lost its UID shows that override on the date its `RECURRENCE-ID` is written in, and an import counts it as failed and drops it, since under the fresh UID it gets it has no master.
- A lone `RECURRENCE-ID` the organizer writes malformed (floating, a plain date on a timed event, or a TZID neither the file nor the zone database defines) is written back with a time Eigen picks, so when its series arrives the date may re-file a day off and the guest answers it again, and a REPLY names a line the organizer can't match.
- One organizer who writes two lone dates that fall on one key, one in UTC and one in a TZID, leaves the guest only one of them.
- A lone copy whose organizer restates one date between UTC and a TZID near midnight files that date twice.

Each `EXDATE` becomes a synthetic cancelled row. Its id and SEQUENCE come from the `X-EIGEN-EXDATE` stamp beside it, or the master's SEQUENCE when a client wrote the `EXDATE` itself. One occurrence is one row, however many forms name it.

An event ends at its `DTEND`, or at its `DURATION` when it names one, as Apple and Outlook both write. A timed VEVENT with neither is drawn as one hour, an all-day one as one day. A `DURATION` is added as plain seconds, because ical.js's own `endDate` steps month by month and takes as long as the number says. So a timed `P1D` across a clock change is 24 hours rather than the same wall time next day, an all-day one counts whole days, and an end past year 9999 is a VEVENT the parser can't read, since no `DTEND` could spell it.

## Expansion is bounded because it walks from DTSTART

`rrule.between` steps from DTSTART to the window on the shared event loop, and a rule with no next date walks on to rrule's last year, 9999, whatever the window. rrule takes no step limit. So the cost follows the numbers a rule states, and `recurrence-limits.ts` bounds them, before anything walks:

- A sub-daily rule is a 400 at the REST boundary. In a parsed `.ics` it is stripped from the projection, because refusing a whole file or invite over it is worse. A rule firing more than 24 times a day in daily words counts as sub-daily.
- A recurring DTSTART must fall between 1900 and 2200, and a window starting past 2200 has no repeats.
- A rule is tried once when its resource is stored (`isExpandableRrule`): from a start moved near 9999, keeping its weekday and leap phase in the series' wall clock, where the rule steps, with at least 28 years left per `INTERVAL`, rrule looks for one occurrence, and the walk ends at 9999. A rule with none, or one rrule refuses, is stripped like a sub-daily one, and a rule that names no `FREQ` is stripped wherever it is read, a mailed invitation included. A rule that has one costs the walk to it, up to about 15 ms for a rare date such as 29 February on a Monday stepped by the day. A rule with none costs about 25 ms when it steps by the day and about 5 ms otherwise. Only a stored series is tried: `parseIcs` reads a whole file for a look and walks nothing, and an override states no repeats of its own. The verdict is the stored row: a range read tries nothing and expands the rule it finds, so a row an older build stored reads as it did then.
- One expansion yields at most `MAX_OCCURRENCES` and covers at most five years, from the query's start or the series' own when that is later. The query's start moves back by one occurrence's length, so an occurrence that began before the window and still runs is in it, as a single event is. Only a series is cut: a single event and a moved occurrence answer for the whole window. So in a wider window, a series whose only occurrences lie past those five years is not found.

A stripped rule stays in the stored bytes. The event draws as one occurrence, and `hasUnindexedRecurrence` makes a CalDAV time-range query return it for every window, so a client that expands the rule itself misses nothing. An `RDATE` takes the same flag, and a `RANGE=THISANDFUTURE` override degrades to a single-instance edit.

## An all-day event is midnight UTC with an exclusive end

An all-day event's bounds are midnight UTC, and `endTime` is the day after the last day. The frontend reads the UTC date and never converts it. With an exclusive end, one invariant covers both kinds: `endTime < startTime` is a 400 over REST and a 403 on a PUT, and a zero-length event is legal. Inbound iMIP clamps a reversed interval to zero instead, because dropping an emailed invite is worse than showing it short.

The web dialogs hold a timed event as a date and an `hh:mm` per end, so a default end is computed from the start as a `Date` (`endAfter`), never by adding minutes to the time string: that wraps at midnight onto the start's date, and a new event made after 23:15 ended before it began. The New Event default starts at the wall clock's next quarter hour, and `bun test` runs in UTC, so a test of it pins the clock with `setSystemTime`.

`timezone` is nullable: only the web dialogs always set one. So `formatEventWhen` takes the fallback zone as a required argument. The browser passes `viewerTimeZone()`, the zone the grid draws in, so the detail dialog names the slot the grid shows. Invitation mail has no viewer and must not borrow the server's zone, so it renders a zone-less event in UTC and says so.

## Sharing is pushed, and team calendars are off by default

A share grants `free-busy` (time blocks only), `read` or `write`. When shares change, `share-propagation.ts` writes the calendar into each named recipient's `shared_calendars` ([ACL.md § Share Propagation](ACL.md#share-propagation)). A `free-busy` reader gets blocks with cancelled occurrences left out, so their existence doesn't leak.

A `TeamHome` starts with `{ calendar: { enabled: false } }`, and its `calendar` getter throws 404 until an admin enables it from the Admin app. Members get the team calendar in their `shared_calendars` at `read` on each `GET /calendar/:ownerId/shared`. A share on the team calendar upgrades them. While it is disabled, that sync removes the stale entries.

Two access rules guard a team home's calendars in `routes/calendar.ts`. Creating, changing and deleting one takes an org admin or the owner (`requireTeamAdmin`, since teams have no roles), because the admin sets a team calendar's shares. Any member may list them. Every event route takes the calendar share instead (`checkCalendarAccess`), so a member's `write` share is event-level. A non-team `ownerId` must be the caller's own.

REST bounds are never tighter than what a PUT may store. The ids Eigen mints cap at 512 characters, and every field a client spells caps at `EVENT_MAX_BYTES`, or an event a CalDAV client stored would be uneditable in the web app.

## Asking about another owner's calendar never opens a home it would create

Some reads take another owner's id before any permission exists: the share check behind every event route (`checkCalendarAccess`), `shared-with-me` and the signup reconciliation. They reach the owner through `calendarOf` in `home-relay.ts`, which checks that the owner's home folder exists before it opens the home. A user who never signed in has no folder yet. A guest's and an org's folders sit elsewhere, and their homes have no calendar. An id without a user has neither. All four answer as a calendar the caller may not see: 403 for an event or the access list, and `[]` for `shared-with-me`. So a caller can't tell which ids exist, and asking never creates a home folder that the backup would then pick up. A disabled team calendar still answers 404, because the team sync reads that 404 to remove stale entries.

## Calendar shares the home data budget

Calendar counts against the home data quota with mail and contacts ([QUOTA.md](QUOTA.md)). `Calendar.size()` answers from the in-memory `eventsBytes`, so a device sync costs no query per resource. Each commit reads its delta inside its transaction and applies it after, so a rolled-back write moves nothing. A rewrite is credited the bytes it replaces, so a shrinking edit is never refused. A move and a delete are not metered. An inbound invitation over budget is dropped while its mail still lands, because a fire-and-forget receiver has nobody to answer a 507 to.

## Every write is announced to every Home that sees the calendar

A change broadcasts a `calendar:*` event ([SSE.md](SSE.md)) to the owner's tabs and to each Home the calendar is shared with. A PUT of bytes already stored commits nothing and announces nothing, and neither does a web save that changes nothing. An import writes each series through the store, which announces nothing, and sends one `calendar:events-changed` when it ends if it wrote a series, even when a refusal stops it partway. Other requests' events go out at once meanwhile. The frontend hooks and the SSE handler that invalidates them are in `packages/lib/src/core/calendar/`.

## A linked copy is an ordinary resource with the organizer's stamp

An organizer's event with attendees puts a linked copy into each Eigen attendee's default calendar over the home relay, and mails everyone else an iMIP invitation (RFC 6047). Out is `invite-propagation.ts`, in is `invitations.ts`, mail is `imip.ts`. The copy is a resource whose VEVENTs carry `X-EIGEN-ORGANIZER-EVENT` and `X-EIGEN-ORGANIZER-USER`, projected to the indexed `organizerEventId` and `organizerUserId` columns. `findLinkedEvents` looks a copy up by that pair among its own VEVENTs only, a master or each date of a copy of single dates, because an override inherits the link and would otherwise answer for its series.

Only a trusted transport sets the link: the relay envelope, or a verified iMIP sender. `EventDataSchema` (`routes/calendar.ts`) has no field for the organizer, so a web save keeps the stored one whatever it posts back. An iMIP organizer has no Eigen id, so its `organizerUserId` is `external_<address>`, the way a team is `team_<id>`. `isExternalOwnerId` sends such an organizer's RSVP by mail instead of over the relay.

## An attendee may re-alarm a copy and nothing more

On a linked copy, a save keeps changes to reminders and color and drops the rest (`guestData`, `events.ts`), whether it edits the copy or sets one date apart. The edit dialog disables the same fields (`detailsDisabled`), so a save never drops them silently. The calendar select stays live, because moving the copy to another calendar is allowed.

Whether an event is somebody else's invitation is `isInvitationFromOthers` (`packages/lib/src/core/calendar/calendar-utils.ts`). It compares the stored organizer address with the Home user's, case-insensitively. A stored `ORGANIZER` alone means nothing: Apple Calendar and Thunderbird write the account's own address on every event they create with guests, and that event is the owner's own. The guard, `deleteEvent`, `rsvp()`, the inbound REPLY lookup, both calendar dialogs and each write that asks whether its actor organizes the series all use this one rule, read on the series' master. A CalDAV PUT reads the stamp instead ([CALDAV.md](CALDAV.md#a-put-is-judged-inside-the-write-lock)).

Both dialogs take the rule from one hook, `useIsInvitationFromOthers`. On a calendar another user shared, it compares with that owner's address, which `usePublicUser` resolves. Until that address arrives every event counts as an invitation, so none is briefly editable. A team Home has no address, so the hook asks for none, and on a team calendar the rule reads Eigen's organizer stamp (`organizerEventId`), as a CalDAV PUT does: an event a member organized carries only the member's address and stays the team's own.

## The organizer's writes fan out, and only the organizer's

A create or update with attendees diffs the old list against the new one, then adds, updates or cancels each copy. Only the organizer fans out, because a guest's own SEQUENCE bump would outrank the organizer's next update. An Eigen user gets a copy over the home relay. Anyone else, and any guest-role user, gets an iMIP mail and a share registry entry ([ACL.md § Share Registry](ACL.md#share-registry)). When that address signs up, reconciliation pulls from the organizer's Home the same messages an Eigen guest would have had: each series that lists them, and each occurrence that lists them while its series doesn't. An event somebody else organizes is skipped, by the rule a save uses ([§ An attendee may re-alarm a copy](#an-attendee-may-re-alarm-a-copy-and-nothing-more)), even one a client synced in with no link, and so is a cancelled series or date, whose guests' copies went with the cancel. The acting user's own address is skipped. So is the calendar owner's, when a collaborator with write access invites them: the event already sits in the owner's calendar, so the owner gets no copy and stays needs-action until they answer it.

The calendar's owner organizes its events, and an editor with a write share acts as the owner. A guest answers the `ORGANIZER`, and only that Home holds the event, so every message, by mail or over the relay, an invitation or a CANCEL, names the one organizer the event's file stores (`organizerOf` in `invite-propagation.ts`), and its mail goes out from that address. The iCalendar writer keeps that line. An organizer's create, edit or new date ends in one pass over every VEVENT of the file (`keepOrganizers`, `ical-component.ts`), so a VEVENT names an `ORGANIZER` exactly while it has guests, since RFC 5546 clients expect one on a group-scheduled event and RFC 5545 gives an event on one person's calendar none. A VEVENT that gains guests takes a copy of the line the file holds, else the saver's. So the line is written once, when the event first gets guests, and no later save rewrites it, nor does a save that changes nothing else write anything. The pass reads the whole file, so a date an older build stored with guests and no line gains it on the organizer's next save, even one that leaves that date alone. A request can't name an organizer: the routes' event schema has no field for one. An email reminder Eigen writes mails the `ORGANIZER` its VEVENT names at that moment, so one on a VEVENT without guests, or on a new event or date, whose line the pass adds after, is stored as a display alarm. A file that names none, such as one a client stored with guests and no line, is organized by the calendar's owner, and its next save writes the line. That mails nobody, since every message names the organizer anyway, so `guestView` (`events.ts`) leaves the `ORGANIZER` out of what it compares. A team has no address, so a team event names the member who first gave it guests, whoever saves or deletes it later, and its mail goes out from that member. An outside guest's reply to that member lands in the member's own Home and is lost ([ROADMAP.md](ROADMAP.md)).

When the organizer deletes or cancels an event, every copy gets a CANCEL, and a series' CANCEL reaches the guests of each of its dates too, since someone can be invited to one date only (`heldGuests`, `events.ts`). A cancelled series' later delete sends nothing more. When an attendee deletes, it is a decline, but only if their address is in the event's attendees. A file or a CalDAV client can hang any `ORGANIZER` on an event, and a decline would then reach a stranger. An organizer known only by address, as every organizer a PUT or a file names is, gets the decline as an iMIP REPLY.

A guest the web form adds is named by a name typed as `Name <address>`, else by the user's contact for that address. An address nobody knows is stored with no name and so no `CN`, and every reader shows the address: its local part is no name the person chose. The guest list counts the organizer as a guest, in the total and in the tally of replies alike, as Google Calendar does, so the parts add up to the whole. The organizer's reply is their own when the attendees list them, and accepted when they are listed only as organizer, since organizing an event is accepting it (`AttendeeList`, `attendee-list.tsx`).

## An occurrence message names the series

A guest holds one linked series, and an override on it inherits the series' link. So every message about one occurrence names the series' event id plus the occurrence key, never the override's own row id. The receiver attaches it as an exception of the guest's series, as it does an iMIP REQUEST with a `RECURRENCE-ID`. The `RECURRENCE-ID` names the original instant, which only the series knows once the override has moved.

Every override stores its whole guest list, on the organizer's side as on a guest's copy, because RFC 5546 clients read an override's `ATTENDEE` lines as its whole guest list, and a CalDAV client syncing the organizer's calendar shows what is stored. So every reader takes a date's own list: "This event" in the edit dialog sends the date's list as shown, a guest's answer for one date writes the series' list with that answer onto the date, and a date whose list is emptied has no guests, who get a CANCEL for it. A date still follows the series, as in Google and Outlook. A guest the organizer adds to or drops from the series joins or leaves every date's list in the same write (`followMaster`, `ical-component.ts`), which is a new revision of each date it changes, and a guest's answer for the whole series, by mail, over the relay or in their own copy, is their answer on every date (`updateAttendeeStatus`, `invitations.ts`), so only a later answer for one date sets that date apart. Every message about a series carries every override and every cancelled occurrence, or a copy would show a moved occurrence at its old slot. One sender, `invitationRequest`, builds it per Eigen guest, so an override whose list leaves that guest out travels to them as cancelled. Mailed guests share one file ([§ iMIP mail](#imip-mail-carries-the-projected-event-never-the-stored-bytes)), so such an override still reaches a mailed guest live. That is accepted: it takes an outside guest taken off one date of a series they stay on.

An older build stored a date the organizer changed with no `ATTENDEE` lines, because the date then had the series' guests. Such a date now reads as a date with no guests: a guest the series gains later joins it, but the guests it already had never come back on their own. So the organizer sees it without them, and their next change to the series tells every guest on this server that the date is cancelled, mails the other guests the date with nobody on it, and refuses a guest's answer for that one date. The organizer can give the date its guests again in the edit dialog with "This event". That is accepted, since no code reads what an older build wrote.

A series-wide edit of the title, description or location reaches each override that still carried the master's old value. Guests run the same rule, so a moved occurrence is renamed everywhere without a message of its own.

## An RSVP names its scope

`PUT .../events/:id/rsvp` takes `{status, scope?, recurrenceDate?, remove?}`:

| Scope | Effect |
|---|---|
| `all` (default) | the attendee's status on the whole copy |
| `this` + `recurrenceDate` | an override with that status; with `remove`, an exclusion and a decline |
| `this-and-following` + `remove` | the copy's rule is truncated and a series-wide decline goes out |
| `remove` alone | the copy is deleted, as a decline |

A copy without a rule has one occurrence, so `this` on it is `all`.

An answer the organizer's Home records is announced as an event update, whether it came over the relay or by mail, so the organizer's open tabs show it.

A guest's "delete this and following" truncates their copy's rule and records the first date it removed as `X-EIGEN-GUEST-CUT` on the copy's master, so the organizer's next update can't bring those dates back. The line is what marks the cut as the guest's: an `UNTIL` on the copy may be the organizer's own, and an organizer who lengthens a series reaches every guest who never cut it. The cut also drops the copy's moved and cancelled occurrences from that date on, and an update adds none back.

`constrainRRule` (`recurrence.ts`) holds an update to the cut by comparing days, never by walking the rule: a rule from 1900 that never fires walks to 9999 for seconds, inside the write lock. An organizer's `UNTIL` whose day in the series' wall clock falls before the cut stands. No end, a later `UNTIL` or a `COUNT` is cut at the cut by `truncateRRule`, in the incoming event's own form, so an all-day series gets a `DATE` `UNTIL`. A `COUNT` that ends before the cut is not walked to its last date, so the guest sees dates up to their cut that the organizer's series doesn't have, which is accepted. So are two more: an organizer who restates a cut series in another zone can bring back the one occurrence at the cut, and a series start moved past the guest's cut leaves their copy empty.

A copy that is one occurrence of a series the guest doesn't hold answers for that occurrence: its RSVP names the organizer's `RECURRENCE-ID`, so it lands on the organizer's override that holds that occurrence's guests.

## Every inbound REQUEST takes one locked decision

A REQUEST relayed from another Home ([SCALABILITY.md](SCALABILITY.md)) and one mailed over iMIP both go through `receiveRequest`, which takes one UID's events: a master and its exceptions, or one occurrence alone. They take one decision, `decideInboundRequest`, inside one hold of the write lock, and the copy is written at most once and the guest told once. The decision looks up the UID Home-wide, so two concurrent deliveries can't file two masters for one UID. A decision per event would write, announce and notify once per moved date.

The two transports differ only in what they hand it. A mail carries a file, and its link is the verified sender, `external_<address>` with the UID as the event. The relay message `calendar:request` carries the events a mail would, already parsed, and the link its envelope vouches for: the organizer's Home and event. It carries no reminder, no stamp and only the guest list, so a local copy never counts the organizer as an attendee, as a mailed file does. Every update carries the master and that guest's exceptions, as an invitation does. A guest who deleted their copy gets it back with the organizer's next update, by either transport, faded as declined, since a delete leaves nothing behind but the declined answer the organizer holds. A date the guest removed comes back the same way.

1. **Update.** A stored copy linked to an organizer takes the message, but only when the message names the link the copy holds, never just its address, so a co-attendee can't hijack it. Each event patches the stored file in place, and only an occurrence the copy lacks is added whole, so the guest's reminders, color, row ids, truncated rule and answers survive. A REQUEST for one occurrence attaches as an override, since a full update would collapse the series. The decision reads the copy's revisions once (`storedRevisions`), turns each occurrence key into at most one edit, the newest event winning where a message names a key twice, and `applyEdits` applies them in one pass over the file, so a series with thousands of exceptions costs one keying of its VEVENTs, not one per event.
2. **Adopt.** A stored master nobody linked is claimed when its own organizer address equals the verified sender. `X-EIGEN-IMPORTED-ORGANIZER` wins over the `ORGANIZER` line here. The resource keeps its row ids, and every VEVENT gains the link, the occurrences the message adds included, and the master the organizer. It takes the message's fields and guest list only where the message is newer than what it holds, by the ordering rule below.
3. **Create** in the default calendar, built whole in one write, only when the body's `ORGANIZER` is the sender. A REQUEST for one occurrence of a series this Home doesn't hold files as a standalone event that keeps its `RECURRENCE-ID`, the only record of which occurrence it answers for. An organizer sends each date a guest is invited to as its own message, so a REQUEST for another date of that series joins the same copy: one VEVENT per date and no master, the shape RFC 6638 gives an attendee of some instances only.

A relayed message naming this Home as its own organizer is dropped, because adopting it would make an event a linked copy of itself.

**A copy of single dates gives way to the series.** When the organizer later invites the guest to the whole series, the series is written over the copy's file in one write. The guest's reminders and color carry over, and each date the series lists as an exception keeps its row id and the guest's answer. A date it doesn't list becomes a plain occurrence of the series, and the series must still be newer than that date to replace the copy. A CANCEL for one date removes that date's VEVENT, since there is no series to exclude it from, and the last date takes the copy with it; a guest who deletes one date removes it the same way. A REQUEST that marks a date cancelled sets that date's own status, as one cancelling a whole series does on its master, and one cancelling a date the copy doesn't hold is dropped. Only an exception of a held series becomes an `EXDATE`.

## A revision rises by one rule

`touch` owns the revision fields, and `revisionAfter` (`ical-component.ts`) is their rule. `LAST-MODIFIED` is always now. An organizer's scheduling change to any item of a resource, such as a moved date, a guest-list change, a cancelled date or the series' times or rule, sets that item's `SEQUENCE` to the highest number the file holds plus one, a cancelled date's stamp included (RFC 5546 § 2.1.4). What reschedules an item is what `scheduleOf` reads, when it starts, how long it runs, whether it is all day, its status and its guests, and on a master a changed rule (`ruleMoved` in `patchVEvent`). The rule stays out of `scheduleOf` because a new override is compared with the occurrence its master yields there, and only the master states a rule. A title, a color or the same instants in another zone is none of it. A new override is compared with what its guests held there, its own VEVENT or the occurrence its master yields, so a date recolored or retitled keeps its number. One write raises every item it reschedules to that one number, and a cancelled date raises its series with it. The file's highest number is the bar because guests hold a date differently: a mailed client holds an unmoved date at the series' number and drops a message below it, while Eigen's own receiver holds no revision for an unmoved date and takes any message for it. A deleted series leaves no file to raise in, so `eraseStoredEvent` takes its CANCEL's number before the purge.

Who acts is one test, and each write's caller states it in its `WriteContext`. The Home's user organizes a series when they are its `ORGANIZER` or it names none, which is `isInvitationFromOthers` read on the series' master ([§ An attendee may re-alarm a copy](#an-attendee-may-re-alarm-a-copy-and-nothing-more)). A receiver never raises, because a number of its own would outrank the organizer's next update. It takes the `SEQUENCE` and `DTSTAMP` a message states for the item the message names, and a date it adds on its own, such as a guest's answer for one date or a date the guest restores, takes the revision the copy holds for that date, or the series' when it holds none. A guest's answer that the organizer's Home records is the guest's act, so it raises nothing either. On a guest's copy only a message moves `DTSTAMP`, because it orders the organizer's next message.

## Revisions are ordered, and a redelivery is applied as one

`isNewerRevision` (RFC 5546 § 2.1.5) compares SEQUENCE first, then `DTSTAMP`. The stored side is what the resource holds for that occurrence before the message touches it (`storedRevisions`); a cancelled one reads the stamp beside its `EXDATE`. A lower SEQUENCE always loses. At equal SEQUENCE an equal or newer stamp is applied, and so is a message when either side has no stamp. `DTSTAMP` has one-second resolution, so such a message is a redelivery, and a redelivery patches to nothing: no ctag moves and the user is told nothing twice. An occurrence the copy already holds is patched the same way, so a series redelivered with its moved and cancelled occurrences writes nothing either. The master is patched first, so a series rename reaches the overrides that carried the old title before each override's own event patches it. A stamp more than 24 hours ahead of the receiver's clock is clamped to now, or it would outrank every genuine update at the same SEQUENCE.

**A guest's answer on their own copy is theirs.** An answer the guest gave, accepted, declined or tentative, stands whatever a message says, because the organizer's list can lag behind a reply it hasn't read yet. Only a rescheduling asks again: a needs-action at a higher SEQUENCE than the copy holds for that date, or for the series when the copy holds no VEVENT for the date, resets the answer. A copy with no answer from the guest, or a pending one, takes the message's, so an answer the guest gave from another client lands once the organizer passes it on. On a copy the guest cut, a pending answer does not take the organizer's decline, because that decline is the cut's own echo and no answer to the dates the guest kept. A date removed from the copy holds no list, so a date that comes back takes the message's answer. That is accepted: a guest who removes a date while the organizer has not yet recorded their decline can get the date back on the organizer's next update. The copy's own VEVENT cancelled by its status is the organizer's word, not the guest's, so the answer it holds stands when the organizer restores it. `keepOwnAnswer` is that one rule for the series and for each date, on every path: an update, an adoption and a series replacing an occurrence copy.

A message over `EVENT_MAX_BYTES` or the storage budget is logged and dropped, because the mail it rode in on has landed and nobody is waiting for a 413 or a 507. A refused master files nothing, its occurrences included, because a new copy is one write. So is an answer to a series the organizer deleted while it travelled.

## iMIP mail carries the projected event, never the stored bytes

`imip.ts` composes REQUEST (with an "updated" banner for an update), CANCEL and REPLY. `serializeEventForImip` builds a fresh VCALENDAR from the rows, so no Eigen stamp can leak, and strips them anyway. So no color travels, by mail or over the relay, which names only the guests: a color is the organizer's own display choice, and a guest keeps their own on their copy. A series travels whole: one VCALENDAR with the master, an `EXDATE` per cancelled occurrence and an override per edited one (RFC 5546). A message about one occurrence carries that occurrence alone. Nothing in the file differs per guest, so a save builds it once, when its first mail goes out, and every mailed guest gets those bytes. Only the address, and the subject and banner of an update, differ. A local guest's notice has no file at all.

**No `VALARM` ever travels.** The organizer's reminders are their own, and an email reminder would ship as `ACTION:EMAIL` naming the organizer, so every guest's client would mail the organizer at the trigger. The `URL` stays, since guests seeing the link is the point. A REQUEST asks each guest to reply (`RSVP=TRUE`) and lists the organizer as an accepted attendee. A CANCEL carries `STATUS:CANCELLED` and lists as its attendees exactly the guests it goes to (RFC 5546 § 3.2.5), because a cancelled occurrence holds no guest list and a removed guest is no longer on the event's. A CANCEL for a moved occurrence carries its moved times, the slot the guests last saw, while its `RECURRENCE-ID` names the original. A CANCEL is a revision of its own: one for a date carries the number its exclusion was stamped with, and one for a deleted series the file's highest number plus one, taken before the purge leaves no file to raise it in. Both carry the time of the cancellation as their `DTSTAMP`, so no CANCEL repeats the last REQUEST's revision.

## Inbound iMIP acts only on a sender our own MTA verified

`Mail.mailboxDeliver` (`lib/mail/mail-domain.ts`) scans a delivered message for a `text/calendar` part after the INBOX append ([MAIL.md](MAIL.md)). It waits for the calendar, so a client reacting to the new-mail event already finds the change. A failure is only logged and never fails the delivery.

Every change binds to the `From:` address, so the delivery computes a verdict with `verifyImipSender` (`lib/mail/imip-auth.ts`). A sender is verified when the topmost `Authentication-Results` header stamped with our own authserv-id records a `dkim=pass` for a domain aligned with the `From:` domain. OpenDKIM prepends its result and strips older ones with our id (`docker/postfix/entrypoint.sh`), so a header below it is a stale hop or a forgery. Anything else fails closed and the invite stays a plain attachment, unparsed. An imported `.eml` never reaches the calendar, and an operator whose MTA writes no such header has automatic iMIP off. A calendar part past `IMIP_MAX_BYTES` (1 MiB) is skipped, since a scheduling message is far smaller than what a saved event, a CalDAV PUT or an `.ics` import may hold (`EVENT_MAX_BYTES`, 5 MiB). A message is acted on for its first `IMIP_MAX_EVENTS` (50) events only, since more is a mailed export, not a scheduling message. A REPLY answers its first `IMIP_MAX_REPLY_DATES` (5) dates of a series only, because a date counts only when the rule yields it, and checking that expands the series from its start to that date.

A REQUEST or CANCEL from the recipient's own address is dropped. It is their own mail coming back through a forward or a list, and acting on it would turn their own event into somebody else's copy. A REPLY from one's own address is still processed.

Its REQUEST events are grouped by UID, so the order a file lists them in doesn't matter, and each series takes the [locked decision](#every-inbound-request-takes-one-locked-decision) with `external_<sender>` as the organizer. CANCEL removes the copy, or one occurrence of it under the ordering rule. REPLY moves PARTSTAT on the organizer's master or on that occurrence's override, the master first whatever the file's order, because the series' answer is the sender's answer on every date. It only sets the sender's own status, only for an invited attendee, and never brings back an occurrence the organizer deleted. A date the rule doesn't yield is no occurrence, so a reply naming one is dropped rather than drawn as a new one. An `RDATE` date counts as none too, as it does in the expansion. A REPLY without DTSTART, which RFC 5546 allows, answers nothing and is logged: every event row needs a start, and no client is known to send one.

## The mail app draws an invite from the server's summary

`Mail.messageGet` summarizes each calendar part through the same parser into `Attachment.calendarInvite`, and `calendar-invite-widget.tsx` (`apps/mail/`) draws it inline instead of in the attachment list. A `null` summary is an unparseable file or a part past `IMIP_MAX_BYTES`, and draws as an error card.

## Import replays each series through putResource, as a device sync does

`Calendar.importEvents` (`transfer.ts`) takes a whole `.ics`, which must be UTF-8 (RFC 5545 §3.1). The event cap counts every VEVENT, not every master, because one master can hold 37,000 overrides inside `ICS_MAX_BYTES`. It is counted on the text before ical.js builds a tree, and again on what the parser returned. A file may spread one UID over several VCALENDAR objects, so VEVENTs are grouped by UID first. A TZID names the VTIMEZONE of the object its VEVENT came in, since two objects may define one name differently.

Each series is written as its own resource through `putResource`, the path a CalDAV PUT takes ([CALDAV.md](CALDAV.md#a-put-is-judged-inside-the-write-lock)), under a fresh `<uuid>.ics`. UID uniqueness is Home-wide for an import, and a UID any calendar of the Home already holds counts as `skipped`. The reason is scheduling: an inbound REQUEST (`decideInboundRequest`, `invitations.ts`) and a REPLY (`imip.ts`) find their event by UID across the whole Home and bind to the first master they meet. With two imported copies, row order decides which one is adopted or answered, and the other goes stale. A device's CalDAV PUT is checked against its own calendar alone, because a device sees one collection and RFC 4791 lets each calendar hold the same UID. The skip also makes a failed import retryable: a retry skips what landed and finishes the file. A written-bytes cap stops the run with a 413, because a VTIMEZONE the file defines once is copied into every series that names it. It counts each series before its put, since one the store refuses has cost its parse all the same.

**An import takes the scheduling out.** Every guest `ATTENDEE` is dropped, and the `ORGANIZER` becomes an inert `X-EIGEN-IMPORTED-ORGANIZER`. Otherwise the first edit would mail addresses the file's author chose, and a forged iMIP REPLY could match the event by UID. The imported organizer can still claim the event by sending a real invitation ([Adopt](#every-inbound-request-takes-one-locked-decision)).

## An import needs a target calendar

The file routes reach only the caller's own home and team homes, because only the home relay crosses into another user's Home. So a calendar another user shared is no target ([ROADMAP-POST-1.md](ROADMAP-POST-1.md)). An export takes `read` and an import `write`, and `free-busy` is no read here.

The "Import to Calendar" file action opens `ImportToCalendarPicker` (`packages/ui/src/components/calendar/`). It offers the viewer's own calendars, the team calendars they may write in, or a new one. `useImportToCalendar` deletes a new calendar again when it took no events. When that delete fails, the next try deletes it first, unless the user picks it from the list.

## Export splices the stored lines

`exportEvents` lifts the `VTIMEZONE` and `VEVENT` blocks out of each stored resource as text (`spliceBlocks`, `blocks.ts`) and drops every line with an Eigen name. It parses and re-serializes only a file whose zone clashes, below, because ical.js rewrites parameter quoting and order, and bytes Eigen only stored are not Eigen's to rewrite. The result is one VCALENDAR, never a concatenation, because many readers take only the first object of a stream. So one export holds one definition per TZID. An IANA or Windows name resolves through `Intl` whatever a file defines for it, so its first definition serves all. A name only the file explains, such as Outlook's `Customized Time Zone`, can mean another offset in another file. A file whose definition differs is the one thing an export rewrites: `withOwnZoneNames` gives its zones a name with a digest of their definition, and its references with them, or a re-import would move the time. Nothing bounds the size of a whole-calendar export ([ROADMAP.md](ROADMAP.md)).
