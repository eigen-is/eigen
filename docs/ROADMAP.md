# Roadmap

Open work on the road to a trustworthy 1.0, data integrity first. Status is what exists in code today; designs live in the `docs/proposals/PROPOSAL_*.md` file a row links. Work that waits until after 1.0, or for a trigger, is in [ROADMAP-POST-1.md](ROADMAP-POST-1.md). Each domain keeps its own backlog: [DOCS-TODO.md](DOCS-TODO.md), [CANVAS-TODO.md](CANVAS-TODO.md) (slides, vector, stickies), [SHEETS-TODO.md](SHEETS-TODO.md) and [CHARTS-TODO.md](CHARTS-TODO.md). Their data-loss and security bugs stay here, in P0 and P1.

**Before 0.5.0** comes first: 0.5.0 announces the open-source repository, and its section lists everything that ships before it. P0 to P2 hold the rest of the road to 1.0, most important first.

The page holds only open work: when work ships, its row or its done part goes in the same commit. A bug found is fixed, even outside the task; only one that needs the owner's yes, a product choice or more than a small unit gets a row instead, in the same commit, here or in its domain backlog, naming the file and function, the failure and the callers.

**No backward compatibility before 1.0.** A change to a persisted format is done outright: existing data is dropped or converted once, and migrations become mandatory from 1.0. Self-host tooling is never shimmed either: scripts, env files, Compose layouts and archive, snapshot and backup formats change outright, an old script is deleted, and running instances get a short note.

**Legend**: Effort: S / M / L / XL (rough T-shirt size). Frozen-format: flags a change to a persisted format (Yjs roots, DB schema, drive MIME values) that drops or converts existing data.

## Before 0.5.0: the open-source announcement

0.5.0 makes the repository public, so its first readers are self-hosters trying an install. They update and roll back without losing a file, nothing they type or upload gets lost, nobody keeps access they lost, and a backup leaves nothing readable to other users of the host. Within each table the rows are in order. The release itself then needs the intro paragraph in `CHANGELOG.md` that `bun run release publish` asks for.

### Update, roll back and back up without losing anything

| Item | Status in code | Effort | Frozen-format | Notes |
|---|---|---|---|---|
| **A wedged Docker daemon hangs a stop** | `api_cli` in `eigen` runs `docker compose exec` with no timeout, so `before_stop` and the restart notice wait for good on a daemon that stops answering, and `./eigen stop` never stops. | S | No | Bound the exec with a background job the launcher kills, in POSIX sh: macOS has no `timeout`. |
| **A per-home restore's database checks run on the API's event loop** | `verifyFolder`, `redateTrash` and `materializeMount` (`apps/api/src/lib/backup/materialize-mount.ts`) run synchronous SQLite work on the API's loop, so one large `quick_check` blocks every request for seconds. | M | No | Run the judge step in a transform process, with the job slot held. A new seam, so a short spec first. |
| **An update keeps only the api image of the release before** | SELF-HOSTING.md promises that an update keeps the previous release's images for `./eigen rollback`; demo.eigen.is kept only the api image. Then `prune_images` (`eigen`) can no longer find the old images by digest, and the dangling-only `docker image prune` it ends with removes them, against its own comment that no prune takes a digest-only image. - WebDAV and CalDAV conformance, the measured gaps first (litmus 0.17, cadaver, vdirsyncer 0.21):
  - `webdav/propfind.ts` answers allprop to every request (no prop selection, no 404 propstat, `Brief` ignored). Adopting the shared `lib/dav/propfind.ts` also brings in the dav multistatus builders and `encodePathSegment` (WebDAV hrefs return `%40` for `@`), so it needs a client round (Finder, Explorer, rclone, Mountain Duck).
  - DELETE, MOVE, COPY and PROPPATCH ignore `If-Match` and `If-None-Match` (RFC 7232 § 3.1: 412).
  - A PUT whose `If` names a bogus lock token answers 204, not 412 (`fail_cond_put`, `fail_complex_cond_put`).
  - A PROPPATCH response lists a prop once per operation.
  - `app.ts` advertises `DAV: 1, 2, 3, calendar-access, addressbook` and an `Allow` with `MOVE, COPY, LOCK, UNLOCK` on `/dav`, none of which that router implements.
  - CalDAV MKCOL creates nothing (vdirsyncer cannot create a calendar; MKCALENDAR works).
  - A PUT, MOVE or COPY already in flight lands after another user's LOCK: `handlePut` (`apps/api/src/lib/webdav/resource.ts`) checks the locks once, before it reads the body, and a create does the same. `resolveMoveCopy` (`apps/api/src/lib/webdav/move-copy.ts`) checks the destination's locks before `Drive.movePathOver` or `Drive.copyPathOver` writes, so a LOCK taken on it in between is not seen. Closing it needs a lock check at the moment the bytes or the row land, a layer crossing, so it is the owner's call. Rare.
  - A COPY of a file over a file checks the quota for the source's whole size, though the drive grows only by the difference: `checkedCopyTree` (`apps/api/src/lib/drive/drive.ts`) runs before `replaceOccupant`, so near the quota a COPY-save gets a 507 a PUT of the same bytes would pass. XS.

  - A `Depth: 0` lock on a folder stops a create in it, but not a DELETE or MOVE of one of its members: `handleDelete` and `resolveMoveCopy` (`apps/api/src/lib/webdav/move-copy.ts`) do not check the parent's own lock. XS.
