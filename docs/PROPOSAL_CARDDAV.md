# Proposal: CardDAV — contacts as vCard files + address-book sync

> **TLDR**: Add CardDAV (RFC 6352) so iOS/macOS Contacts, DAVx⁵, and Thunderbird sync Eigen contacts two-way, using the same Basic-auth app-password setup CalDAV already has. The enabling move (decided 2026-08-14): restructure contact storage to **mimic mail, not calendar** — one `.vcf` file per contact under `eigen.contacts/cards/`, files are the source of truth, and `contacts.db` becomes a rebuildable index the way `MailDB` indexes the maildir. That makes round-trip fidelity perfect by construction (a DAV GET returns the exact bytes a client PUT, unknown properties and all) and turns the contacts store into plain files you can grep, back up, and import anywhere. Existing contact books are **dropped, not migrated** (decided — they are seed-scale on eigen.is, and zero export code beats carrying a legacy path forever): a **v2 migration on `contacts.db`** drops the v1 tables and creates the index shape in place, the emptied book reseeds like a new account, and the existing avatar-cleanup pass sweeps the orphans. The protocol layer is a near-clone of `apps/api/src/lib/caldav/` minus its two hard parts (recurrence, VTIMEZONE): a `/dav/addressbooks/:ownerId/…` router, `addressbook-home-set` discovery, `addressbook-multiget`/`addressbook-query`/`sync-collection` REPORTs backed by the calendar's ctag + tombstone pattern, and content-hash ETags. Labels ride as `CATEGORIES` (membership truth moves into the file; the `labels` table keeps name + color). Photos ride as inline `PHOTO` (canonical in the file; `avatars/*.webp` becomes a derived cache). REST routes and the Contacts app are untouched. ~2–3 days for the storage relayout, ~3–4 days for the protocol surface plus a real-client verification day; the phases are sequential. Revised twice on 2026-08-14 after two independent review passes (the second: [PROPOSAL_CARDDAV_REVIEW.md](PROPOSAL_CARDDAV_REVIEW.md), every code claim re-verified before folding); all verified findings are folded in below.

## Goals

1. **Contacts sync to real devices.** Add an Eigen account to iOS/macOS Contacts, DAVx⁵ (Android), or Thunderbird and get two-way sync — create on the phone, it appears in the app; edit in the app, it lands on the phone. Same credential story as CalDAV/IMAP: Basic auth via `authenticateBasic` (`apps/api/src/lib/auth/protocol-auth.ts` — app password with primary-password fallback).
2. **Fidelity by construction.** A client's vCard survives Eigen untouched: unknown properties (`IMPP`, `URL`, `X-*`, extra `TEL` types Eigen doesn't model) round-trip because the stored file *is* the DAV resource. No regenerate-and-pray serializer.
3. **Contacts become portable files.** `eigen.contacts/cards/*.vcf` on disk mirrors what `eigen.mail/Maildir` did for mail: standard format, greppable, restorable, exportable with `cp`.
4. **CalDAV-grade incremental sync.** `sync-collection` (RFC 6578) with ctag + tombstones, copied from the calendar implementation, so clients pull deltas, not full books.

## Non-goals

- **Team or shared address books.** Contacts are per-Home personal data today and CalDAV is `requireSelf`-only too (`caldav-router.ts:36`); the layout leaves room (`cards/` is one book, siblings possible) but v1 ships exactly one book per user.
- **A global address list.** Team-member suggestions stay REST-side (`useContactSuggestions`); exposing the org directory over CardDAV is a different feature with different ACL questions.
- **Multiple address books, MKADDRESSBOOK.** One fixed book named "Contacts"; MKADDRESSBOOK/MKCOL → 403.
- **Native vCard 4.0 storage.** The book is 3.0 on disk and on the wire (what iOS and DAVx⁵ speak against this server, and every client accepts); 4.0 PUTs are transcoded to 3.0 at the seam — see Design § 2. Storing 4.0 verbatim was reviewed and rejected: Thunderbird 102+ PUTs 4.0 by default while ignoring `supported-address-data` (Mozilla bug 1692760), and 4.0 bytes served verbatim corrupt the iOS view (iOS reads only the 3.0 `PHOTO;ENCODING=b` form).
- **Exotic query collations.** `addressbook-query` gets real server-side filtering (Design § 4 — the earlier full-set-superset stance was reversed on second review: RFC 6352 § 8.6 requires match-only responses, and clients treat every returned card as a match). What stays out: collations beyond the RFC-required `i;ascii-casemap`/`i;unicode-casemap`, rejected with `CARDDAV:supported-collation`.
- **Full RFC 6352 conformance claims.** v1 is a deliberate interoperability subset: no WebDAV ACL surface beyond the auth gate, no `expand-property` REPORT, and `supported-report-set` advertises exactly what exists — nothing more.
- **Mapping Apple group vCards to labels.** Apple's Contacts creates groups as separate `X-ADDRESSBOOKSERVER-KIND:group` cards; v1 stores them verbatim (fidelity) but hides them from the app's contact list. Label mapping for them is deferred; DAVx⁵'s default per-contact `CATEGORIES` mode maps to labels in v1. Known cosmetic consequence: an Apple-created group card renders as a blank contact in DAVx⁵'s CATEGORIES mode and in Thunderbird (Mozilla bug 1807394) — set that expectation in CONTACTS.md and the release note.
- **Fetching remote `PHOTO;VALUE=URI` images.** Kept verbatim in the file, never fetched server-side (SSRF), no thumbnail.

## Current state (recap)

**Contacts is DB-canonical.** `apps/api/src/lib/contacts/` stores structured rows in `eigen.contacts/contacts.db` (`db-config.ts`, version 1): `contacts` (firstName, lastName, eigenId, `data` JSON with email[]/phone[]/company/jobTitle/address[]/birthday/notes/avatar — `schema.ts:5-16`), `labels` (name + color), and a junction table. The `Contacts` class (`contacts.ts:48`) does CRUD + SSE, seeds "yourself" and optionally the org owner on init (`:67-109`), guards self-deletion (`:156-163`), and pushes profile changes through the home relay when you edit your own card (`:166-181`). Avatars are webp thumbnails in `eigen.contacts/avatars/` written by `uploadAvatar` (`:291-309`), referenced by URL string in `contact.avatar`. REST surface: `apps/api/src/routes/contacts.ts:42-168`. No `uri`, no `etag`, no tombstones, no raw-format storage — none of the DAV plumbing exists on this domain yet.

**CalDAV is the protocol template.** `apps/api/src/lib/caldav/` (~1.5k lines) serves RFC 4791 at `/dav/calendars/:ownerId/…`: thin Elysia router (`caldav-router.ts`), discovery chain `PROPFIND /dav/` → `current-user-principal` → principal props with `calendar-home-set` (`discovery.ts`, `xml-builder.ts:66-71`), collection PROPFIND, PROPPATCH, GET/PUT/DELETE with `If-Match`/`If-None-Match` ETag preconditions (`resource.ts:35-45`), and REPORTs including `sync-collection` with `urn:eigen:sync:<ctag>` tokens and the RFC 6578 invalid-token error that forces a clean full resync (`report.ts:126-167`, `:143`). The calendar schema carries the sync bookkeeping this proposal copies: per-collection `ctag` (`calendar/schema.ts:11`), per-resource `etag` (`:37`) + `eventCtag` (`:46`), and an `event_tombstones` table `{uri, deletedAtCtag}` (`:59-69`). URI comes from the request path, UID from the payload (`resource.ts:85-101`). Client setup is manual-URL today — there is no `/.well-known/caldav` anywhere in the API.

**Mail is the storage template.** `MaildirStore` (`apps/api/src/lib/mail/maildir-store.ts`) treats files under `eigen.mail/Maildir` as the source of truth and `MailDB` as a rebuildable index, reconciled by `syncMailbox` (`:248`) under a one-slot semaphore so a reconcile never straddles a mutation's fs+db pair (`:26-28`). It fs-watches the maildir (`:55-66`) because an out-of-process writer (Postfix) delivers into it — a reason contacts don't have.

**Format-freeze context.** eigen.is is live and storage formats are generally frozen, but Reinder ruled (2026-08-14) that contacts are exempt: the storage format may change freely **and existing contact data may be dropped** where that keeps the code clean. Contact books on eigen.is today are essentially the auto-seeded rows (`addYourself` + org owner) plus a handful of manual entries, and re-adding those is cheaper than carrying a row-to-vCard export path forever. Dropping still needs a mechanism, though — populated `contacts.db` files exist on eigen.is, so the cleanup rides a normal v2 schema upgrade (see Design § 1).

**Verified sharp edges (second review).** Code facts, independently re-verified, that shaped this revision: the REST contact update is an unconditional full-projection replacement — no version or etag anywhere, and absent fields are *erased* because the whole `data` blob is rebuilt (`routes/contacts.ts:72-83`, `contacts.ts:165-200`); the avatar endpoint is staging-only (file in, URL out, no contact id — the app uploads before the contact even exists); `labels.name` has no uniqueness constraint and every consumer resolves labels by id, so name-keyed `CATEGORIES` resolution would be non-deterministic; `LocalFilesystem.write` writes straight to the final path and **no fsync exists anywhere in the API** — the maildir message writers are the repo's only temp+rename precedent (`maildir-store.ts:529-533`); `ManagedDatabase.config.currentVersion` is dead metadata — nothing rejects a DB *newer* than the binary, so a rollback after a destructive migration opens the wrong schema silently (`managed-database.ts:125-154`); the CalDAV sync handler accepts any token that ends in a number, including one *ahead* of the current ctag, and answers it with an empty delta plus a **lower** token — permanently stalling that client (`report.ts:139-166`); and the calendar's insert-only, never-pruned tombstones can emit one href as both 200 and 404 in a single sync response, where the 404 wins on in-order clients, which then delete a live event (`calendar.ts:438-458` — a live calendar bug this design must not inherit). Deployment: both Caddyfiles already own `/.well-known/caldav` as a method-agnostic redirect (`Caddyfile:57-59`, `docker/static/Caddyfile:54-56`); neither has a carddav twin.

## Alternatives considered

1. **DB stays canonical, vCards regenerated on GET** — rejected. Lossy by construction: the first Eigen-side edit after a phone sync strips every property Eigen doesn't model, and two-way sync then propagates the damage back to the client's address book. A server that corrupts client data on round-trip is worse than no server.
2. **DB canonical + raw vCard sidecar column** — workable, but the merge discipline ("regenerate owned properties, splice unknown ones from the sidecar") is fiddly, and the reasons calendar needs DB-canonical rows — time-range queries, recurrence expansion, iMIP cross-linking — don't exist for contacts. It also keeps contacts locked inside SQLite instead of making them portable files. (Review note: the calendar schema's `icsBlob` column looks like this model but is dead — never written, never read; CalDAV GET regenerates ICS via `eventsToIcs` (`caldav/resource.ts:11`), so calendar actually lives with alternative 1's lossiness today. Fine for events, which Eigen models completely; fatal for contacts, which it doesn't.)
3. **Files as truth, index DB derived (the mail model)** — **chosen** (directed by Reinder). Fidelity is free, the storage story matches mail, and the index keeps list/search/labels fast. Cost: a one-time storage relayout, priced in Phase 1 — and with the data-drop ruling, no migration at all.

## Design

### 1 — Storage relayout: `cards/` + rebuildable index (Phase 1)

```
eigen.contacts/
  cards/<contactId>.vcf    ← source of truth, one vCard per contact
  avatars/<contactId>.webp ← derived thumbnail cache (web UI)
  contacts.db              ← rebuildable index + sync bookkeeping
```

- **Cleaned by a v2 upgrade, in place** (`db-config.ts`): eigen.is homes already carry `contacts.db` files with data, so the cleanup goes through the machinery built for exactly this — `CONTACTS_DB_CONFIG` bumps to `currentVersion: 2`, and the v2 migration drops the v1 tables/indexes and creates the new index shape. `ManagedDatabase` applies pending migrations sequentially on first open (`managed-database.ts:128-152`), so existing homes upgrade the moment they load contacts, the emptied book reseeds through the normal fresh-account path (`contacts.ts:82-106`), and the avatar-cleanup pass already in `init` (`:108`) sweeps the now-orphaned webp files. The v1 migration block stays verbatim (fresh homes run v1 then v2 — one empty-table create/drop at home creation, harmless); `schema.ts` describes only the new shape, as the pattern already has it. No new filename, no filesystem special-casing.
- **Index schema**: `contacts` becomes an index of the files — keeps `id` (now a pure random app PK — REST identity and avatar-cache key), `firstName`/`lastName` (sort), `eigenId`, `data` JSON (parsed projection for fast list), `updatedAt`; gains `uri` (the sanitized client-chosen resource name, canonically unique, doubling as the filename `cards/<uri>` — split from `id` because CardDAV resource names are arbitrary client input and must not become REST identities), `etag` (SHA-256 hex of the file bytes), `cardCtag` (**NOT NULL** — the book ctag at the card's last change, stamped on every create, update, label/photo rewrite, and reconciled file change; this is the column that answers "which cards changed after token N", which earlier drafts forgot entirely, and the NOT NULL matters because the calendar's nullable `eventCtag` leaves legacy rows permanently invisible to sync), `mtime` + `size` (the reconcile fast path), `uid` (vCard UID, unique per book, immutable on update), and `isGroup` (hides `KIND:group` cards from the app). The `data` projection stores the **avatar URL string only, never photo bytes** — base64 `PHOTO` payloads stay in the files and must never leak into the index or the list response. New: a one-row `book` table carrying `ctag` plus a `syncGen` rebuild-generation stamp (see the reconcile bullet), and `contact_tombstones` `{uri, deletedAtCtag}` — the calendar pattern (`calendar/schema.ts:11`, `:59-69`) with one fix: `putCard` clears any tombstone for a URI it re-creates, so delete-then-recreate never lists one href as both a 200 and a 404 in a single sync response (RFC 6578 forbids duplicate member URLs; the calendar's insert-only tombstones carry the same latent bug and can take the same one-line fix as a broken-window follow-up). `labels` and the junction table keep their shape; the junction becomes derived data, rebuilt from each card's `CATEGORIES` on parse. Honest contract (revised on second review): `contacts.db` is **index plus authoritative sync/label metadata**, not a fully disposable cache — card projections, etags, and category-name membership rebuild from `cards/` alone; label ids/colors, the ctag, `syncGen`, and tombstones are authoritative in the DB, live in backups, and any rebuild that loses them rotates `syncGen`.
- **Etag = content hash.** The resource is the bytes, so the etag is a hash of the bytes — simpler and more honest than the calendar's field-hash `computeEtag`, and it makes reconcile trivially able to detect out-of-band file edits.
- **Atomic, fail-closed writes** (added on second review). Every card write goes temp file → fsync → rename into `cards/` — the maildir delivery pattern (`maildir-store.ts:529-533`); `LocalFilesystem.write` alone writes straight to the final path and nothing in the API fsyncs today, so contacts sets that precedent — then one SQLite transaction commits index row + label links + `cardCtag` + book ctag + tombstone changes together. If the DB step fails after a successful rename, the book fails closed: a targeted reconcile of that uri must succeed before further reads or writes are served. Label fan-outs need no journal — membership is derived from the files, so a crash mid-fan-out self-heals at the next reconcile (unprocessed files still carry the old name, which simply re-creates that label) and the rename can be retried.
- **Reconcile on open, no watchers.** `reconcileIndex()` runs at init: list `cards/` and compare **mtime + size** against values stored in the index — the clean case (always, in practice) is one directory listing plus stats, zero file reads, zero parses. Only entries whose stat drifted get read, hashed, and re-parsed; rows whose file vanished get tombstoned; `ctag` bumps only if something actually changed. A stat-only pass cannot see a same-size, timestamp-preserving replacement (a selective `cp -p` restore), so a full-rehash `rebuildIndex()` mode exists too — it runs when the index is missing or fails integrity checks and can be requested explicitly after manual disk surgery; routine opens stay stat-only. Unlike mail there is **no out-of-process writer** (Postfix is why mail fs-watches), so no watchers — every in-process mutation updates file + index together under a one-slot `Semaphore`, exactly `MaildirStore.storeLock`'s job (`maildir-store.ts:26-28`). Tombstone loss (an index rebuilt from `cards/` alone) cannot be papered over with ctags — a rebuilt book restarts its counter, old numeric tokens still parse (`report.ts:139-146` rejects only malformed tokens), and clients would be told "nothing changed" while deletions from the gap became permanent ghosts. So sync-tokens carry the generation: `urn:eigen:sync:<syncGen>-<ctag>`, with `syncGen` stamped fresh on every from-scratch rebuild. A token with a stale generation gets the RFC 6578 `valid-sync-token` error (as a 412, sabre-style), forcing the full comparison that heals ghost deletions — degraded to a full resync, never wrong. Thunderbird's invalid-token recovery is checked explicitly in the real-client gate (its fix targeted HTTP 400; sabre uses 412, ownCloud 403).

### 2 — vCard parse/serialize (Phase 1)

`apps/api/src/lib/carddav/vcard-parse.ts` + `vcard-serialize.ts`, mirroring the scope and hand-rolled style of `ical-parse.ts`/`ical-serialize.ts` (same content-line grammar: unfolding, parameters, escaping — no new dependency).

- **Parse** → structured `Contact` projection for the index: `N`/`FN` → firstName/lastName (prefer `N`, fall back to splitting `FN`), `EMAIL`/`TEL` → arrays, `ORG`/`TITLE`, `ADR` components → `Address`, `BDAY` → birthday, `NOTE` → notes, `CATEGORIES` → labels, `UID`, `X-EIGEN-ID` → eigenId, `KIND`/`X-ADDRESSBOOKSERVER-KIND` → isGroup. Parse is for the *index*; the file keeps everything.
- **Serialize** is a value-keyed merge over a content-line AST, not wholesale property replacement (revised on second review: Eigen's projection is untyped — `email: string[]`, `phone: string[]`, reduced addresses — so regenerating every owned line would strip the `TYPE`/`PREF` parameters a phone put there, even with correct group handling). The contract: parse the existing file into ordered content lines; for multi-value owned properties (`EMAIL`/`TEL`/`ADR`), diff by value — an unchanged value keeps its original line byte-for-byte (parameters, `item1.`-style group prefix, position), a removed value drops its line plus same-group X-props (never orphan an `item1.X-ABLabel`), an added value appends a minimal new line; single-value owned properties (`N`/`FN`/`ORG`/`TITLE`/`BDAY`/`NOTE`/`CATEGORIES`/`PHOTO`) rewrite in place, keeping the original group and unrelated parameters. Net effect: a name-only web edit leaves every typed `TEL`/`EMAIL`/`ADR` line untouched; editing one specific value costs that one line's parameters — the honest limit of an untyped projection. `CATEGORIES` values are comma/backslash-escaped per RFC. A contact created in the app gets a minimal clean vCard 3.0 with `UID` + `X-EIGEN-ID`.
- **4.0 → 3.0 transcode at the PUT seam** (decided after review): Thunderbird 102+ PUTs `VERSION:4.0` regardless of what the server advertises, and 4.0 bytes served verbatim lose the photo on iOS. So a 4.0 PUT is converted to 3.0 before storage — properties carried over verbatim where the grammar allows, `PHOTO` data-URIs rewritten to `ENCODING=b` form — and the response carries the etag of the stored 3.0 bytes, so honest clients re-converge on the next fetch. The verbatim-bytes contract thus holds exactly for 3.0 clients (iOS, DAVx⁵ — the traffic that matters) and semantically for 4.0 ones. Rejecting 4.0 with the RFC 6352 `supported-address-data` precondition was the compliant alternative, but "add Eigen to Thunderbird and your new cards bounce" is not a shippable default.
- **`X-EIGEN-ID` linkage with a specced rematch.** The eigenId ↔ user link rides as an X-property. Clients are *supposed* to round-trip unknown properties but some strip them, so a rematch rule runs in both `putCard` and `reconcileIndex` whenever a card lacks the property (this is new machinery — no backend email-matching exists today; `getMe` keys purely on eigenId, `contacts.ts:358-366`): if the card's parsed emails contain the **account owner's email** (case-insensitive, exact), restore the self-link in the index and rewrite the property into the file. Only the owner's own address is matched — never other users' emails, so no cross-user inference. The guard matters because `getMe` self-heals by seeding a fresh card when no eigenId row exists: without the rematch, a phone edit that strips the property would strand the real card *and* mint a duplicate skeleton "me" on the next profile load. Residual gap, accepted: a single client edit that strips the property and changes the email in one go loses the link until the user re-saves their profile. Trust rule (hardening, on second review): the property is client-writable bytes, so the *index* accepts it only when it equals the account owner's own id, and at most one row per book carries the indexed self-link — a second self-claiming card indexes as a plain contact. Forged or foreign values stay verbatim in the file and drive nothing (verified: `eigenId` is only ever compared against `home.user.id` — `contacts.ts:322-325` — and its entire FE surface is one hide-delete check). Self-guards and `getMe` key on the indexed link, which only the server assigns; that is the server-owned invariant the review asked for, without inventing a reserved URI.

### 3 — `Contacts` class refit: same shape, conditional writes (Phase 1)

`addContact`/`updateContact`/`deleteContact`/`getContacts`/`getContactById`/`getMe` and the label methods keep their signatures and the app UIs are untouched — but the earlier **zero-line REST claim is revised** (second review): today's REST update is an unconditional full-projection replacement with no version anywhere, and absent fields are *erased* because the whole `data` blob is rebuilt (`routes/contacts.ts:72-83`, `contacts.ts:165-200`). Tolerable while the web forms were the only writer; a data-loss path the moment a phone writes concurrently — a stale form silently reverts a phone edit, then syncs the reversion back out. So the `Contact` projection gains `etag`, REST update/delete require the expected etag, evaluated inside the same mutation lock as the write, and a mismatch returns 412 — surfaced through the standard hook error path ("This contact changed elsewhere") with a list/detail invalidation so the form reloads. Internally every write becomes merge-serialize → atomic file write (§ 1) → one index transaction (row + etag + `cardCtag` + book ctag) → SSE; deletes remove the file, tombstone the uri, bump the ctag. `init`'s two seeds also become independently idempotent (verified gap: one emptiness check wraps both today, so a crash between self-card and owner-card permanently skips the owner — `contacts.ts:82-105`).

New DAV-facing methods (so the protocol handlers stay as thin as `caldav/resource.ts`): `listCards()`, `getCardBytes(uri)`, `putCard(uri, bytes, { ifMatch, ifNoneMatch })` (sanitize name → parse/validate → **evaluate preconditions inside the semaphore** → write → index → ctag → SSE), `deleteCard(uri, { ifMatch })`. Preconditions must not be checked handler-side the way `caldav/resource.ts:35-45` does — that code is race-free only because nothing awaits between check and write, a property an async file write loses. Here two racing `If-Match` PUTs serialize through the semaphore and the loser gets a typed precondition-failed result, mapped to 412 by the handler. `putCard` also accepts exactly one vCard per body (contacts have no multi-component excuse like recurrence — anything else is a 400) and treats `UID` as immutable: a PUT to an existing uri carrying a different UID gets 412 `CARDDAV:no-uid-conflict`. `putCard` on your own card still fires the profile push `updateContact` does today (`contacts.ts:166-181`), but the own-email guarantee (silently prepending your account email) stays app-side only — rewriting a client's payload would break the verbatim-bytes contract, and the `X-EIGEN-ID`/email rematch keeps the link alive without it. `deleteCard` on your own card → 403, mirroring `deleteContact` (`:156-163`).

**Photos:** inline `PHOTO` in the file is canonical. A DAV PUT with an inline photo gets decoded and thumbnailed via the existing `generateImagePreview` pipeline into the cache; the app side keeps `uploadAvatar` exactly as it is — a pure staging endpoint (verified: it takes only a file and returns a URL; the app uploads before the contact even exists) — and the `PHOTO` rewrite happens where the staged URL is consumed, in `addContact`/`updateContact`, which read the staged webp and embed it. Staged orphans are swept by `cleanupAvatarImages` as today. Cache files are named `<contactId>-<hash8>.webp` (first 8 chars of the photo hash), so a changed photo changes the URL — preserving the natural cache-busting today's random filenames give against the route's 15-minute cache headers (`routes/contacts.ts:157`), with `cleanupAvatarImages` sweeping superseded files as it already does. `contact.avatar` stays a URL string for the FE, now always pointing at the derived cache. Remote-URI photos: verbatim in file, ignored by the cache (see Non-goals).

**Quota:** `Contacts.size()` today sums only `avatars/` (`contacts.ts:111-119`); under files-as-truth the bulk moves to `cards/`, so `size()` sums both, and `putCard` enforces the contacts quota before writing — otherwise DAV PUT is an unmetered ingest path bounded only by the per-card cap.

**SSE under bulk sync:** an initial device sync PUTs hundreds of cards, each broadcasting a contact event and triggering a full-list refetch. Accepted for v1 at contact-book scale (TanStack coalesces refetches), with a named fallback if real-device testing shows churn: a trailing-edge debounce (~1s) of contact SSE during DAV write bursts.

### 4 — CardDAV protocol surface (Phase 2)

`apps/api/src/lib/carddav/` mirroring `caldav/` file-for-file, mounted in `app.ts` next to `caldavRouter`:

- **Router** at `/dav/addressbooks/:ownerId/…` — `authenticateBasic` + `requireSelf` on every route, wildcard path parsing, ~150 lines like `caldav-router.ts`.
- **Discovery**: add the `CARD` namespace (`urn:ietf:params:xml:ns:carddav`) to the shared `xml-builder.ts` `NS` string and extend `principalProps` with `<CARD:addressbook-home-set>/dav/addressbooks/:userId/</CARD:addressbook-home-set>` — one principal serves both protocols; clients only read the props they know. Book collection props: `<CARD:addressbook/>` resourcetype, displayname "Contacts", `getctag`, `sync-token`, `supported-address-data` (vCard 3.0), `max-resource-size`, and `supported-report-set` — macOS Contacts keys on the last to choose `sync-collection` and is documented not to fall back when it's missing (the CalDAV template lacks it entirely; adding it for calendars is a cheap broken-window follow-up). **OPTIONS matters too and lives outside the cloned directory**: the capability headers are built in `app.ts:38-45` and attached by the root `onRequest` hook, which prefix-matches `/dav` — so `/dav/addressbooks/…` would silently inherit the calendar-only `DAV: '1, 2, 3, calendar-access'` today. Fix: one combined header for the whole `/dav` tree, `DAV: 1, 2, 3, calendar-access, addressbook` (the sabre/Radicale shape — clients check for the `addressbook` token before trusting the account). The 401 realm is also path-derived (`app.ts:140`, `Basic realm="Eigen CalDAV"`); it becomes the protocol-neutral `"Eigen DAV"` — clients key stored credentials on host, not realm, so nothing re-prompts.
- **Resources**: GET returns the stored bytes verbatim (`text/vcard; charset=utf-8`, quoted etag); PUT validates by parsing but stores the bytes untouched (after the 4.0 transcode, § 2); `If-Match`/`If-None-Match` evaluate inside the mutation semaphore (§ 3). Resource name from the path, UID from the payload — but **not** "per the CalDAV precedent": there the URI only ever lands in a DB column (`resource.ts:85-101`), here it becomes a filename, so the threat model changed. Names are sanitized before any filesystem or index use (the AGENTS.md path rule): must match `[A-Za-z0-9._@-]{1,200}`, must end `.vcf`, no leading dot (rejects `.`/`..` outright), and compared/stored in one canonical form (NFC, case-insensitive uniqueness) so case- or normalization-colliding names can't alias one file on APFS. The router accepts exactly one decoded resource segment — extra segments and malformed percent-encoding are 400s. A PUT whose UID already exists under a different resource name → 412 with `CARDDAV:no-uid-conflict` (RFC 6352 § 6.3.2), never a raw constraint 500. Oversize PUTs: the book advertises `CARDDAV:max-resource-size` (5 MiB — DAVx⁵ does not downscale Android photos, and it retries a bare 413 silently forever) and rejects with the `max-resource-size` precondition element.
- **REPORTs**: `addressbook-multiget` (hrefs → etag + `CARD:address-data` per card; hrefs are **percent-decoded** before matching and **percent-encoded** on every emission, as the WebDAV layer already does (`webdav/xml.ts:53`) — the CalDAV template skips both and survives only because its URIs are server-generated, while card names are client-chosen). `addressbook-query` with **real server-side filtering** (reversed on second review — RFC 6352 § 8.6 requires match-only responses, and clients treat every returned card as a match): the filter grammar (`prop-filter`, `param-filter`, `is-not-defined`, `text-match` with negation and match types, `anyof`/`allof`), the two required collations, and the `limit` element, evaluated in-memory over parsed cards — books are small and queries rare, so this stays off every hot path; unsupported collations → `CARDDAV:supported-collation`, unevaluable filters → `CARDDAV:supported-filter`, never a superset. Partial `address-data` (a requested property subset) is honored for query and multiget by projecting the content-line AST plus the mandatory skeleton. `sync-collection` from `report.ts:126-167` with the generation-stamped tokens from § 1, where a token whose ctag is *ahead* of the current book also counts as stale (verified: the calendar handler answers a post-rebuild future token with an empty delta and a **lower** token, permanently stalling that client), and tombstone 404-rows. Bounds on all of it: REPORT bodies capped (1 MiB), multiget hrefs capped (500), query results capped server-side — beyond the cap, an error, never unbounded response assembly.
- **Well-known** (corrected on second review — this already exists for CalDAV): both Caddyfiles own a method-agnostic `handle /.well-known/caldav { redir /dav/ 301 }` (`Caddyfile:57-59`, `docker/static/Caddyfile:54-56`), so discovery is **edge-owned**. The change is the twin `carddav` block in both files — no API route at all, and API tests keep probing `/dav/` directly. Pre-existing quirk, noted not fixed: the exact-path matcher misses a trailing-slash variant, which falls through to the SPA — the same behaviour CalDAV has today, and no known client probes it.

### 5 — Labels ↔ CATEGORIES

Membership truth moves into the file (`CATEGORIES:Friends,Work`) — otherwise the junction table and the file are two sources of one fact and every DAV rewrite risks drift. The `labels` table remains the *definition* store (id, name, **color** — color has no vCard home). Consequences, all mechanical: parse rebuilds the junction from `CATEGORIES`, auto-creating unknown label names via a conflict-safe upsert keyed on the **normalized name** (NFC, trimmed, case-folded — enforced unique in the v2 schema; verified that `labels.name` has no constraint today and duplicates are creatable via REST, which would make name-keyed resolution non-deterministic) with a deterministic color (hash of the normalized name into `EIGEN_COLORS`). A DAV write that creates a label **emits the label SSE event too** (verified: label and contact caches invalidate separately — a contact event alone leaves the app's label list stale), and REST `addLabel`/`updateLabel` gain the same uniqueness check (duplicate normalized name → 409); label rename rewrites `CATEGORIES` in member files (their etags change — correct, clients must re-fetch); label delete removes the category from member files; app-side label assignment is just another owned-property edit through the serializer.

## Performance invariants

The avatar chain is genuinely hot — `useResolvedUser` sits behind nearly every rendered avatar in every app and reads the full contact list (`packages/lib/src/core/public/hooks/use-resolved-user.ts:15`) — and home init is latency-sensitive. The files-as-truth design must not leak file I/O or payload weight into those paths:

- **REST reads never touch `.vcf` files.** `getContacts`/`getContactById`/suggestions serve from the SQLite index exactly as they serve from tables today — same query count, same shapes (plus one cheap `etag` string for conditional writes, already in the row). Files are opened only on writes and on DAV GET/multiget/query — the requests whose payload *is* the card; query filtering runs in-memory over a small book on a rare request, never on an app path.
- **No photo bytes in the index, list responses, or SSE events — ever.** The index `data` projection carries the avatar URL string; base64 `PHOTO` blobs live only in the files. This is the one place the design could silently multiply the `useContacts()` payload by ~1000×, so it's an invariant, not a preference.
- **Parsing and hashing happen at write time only.** Etag, projection, label links, and the thumbnail are computed when a card changes (rare, human-initiated) and stored; no request-time recomputation anywhere.
- **Reconcile's clean case is stat-only.** One directory listing + mtime/size comparison on home open — no reads, no hashes, no parses unless something actually drifted. At contact-book scale that is sub-millisecond noise next to what home init already does.
- **DAV sync answers come from the index.** `sync-collection` and PROPFIND Depth:1 are pure SQLite (uris, etags, tombstones); only multiget/GET stream file bytes, and those are the requests whose payload *is* the file.
- **Avatar serving is byte-identical to today**: small cached webp + the existing 15-minute cache headers; thumbnail generation stays per-write and bounded by the 5 MiB PUT cap plus sharp's dimension and input-pixel limits.

## Risks and caveats

- **The deploy resets every user's contact book** to the seeded state — decided, not accidental. eigen.is books are seed-scale today; anyone with manual entries re-adds them (or syncs them back from a phone once CardDAV is live). Say so in the release note.
- **Index/file divergence** is the structural risk of any files+index design. The atomic write protocol plus the semaphore make in-process pairs safe; fail-closed + targeted reconcile covers the residual DB-failure window; reconcile-on-open and the explicit `rebuildIndex()` mode catch out-of-band edits. Worst degradation is a `syncGen` rotation → clients full-resync.
- **Sync-token invalidation on rebuild** — deliberate and safe: a fresh `syncGen` forces the full-resync path that heals ghost deletions (RFC 6578 defines the recovery). A pathological reconcile loop would make clients re-download the book repeatedly; the ctag only bumps and the generation only rotates when something actually drifted.
- **Clients that strip `X-EIGEN-ID`** downgrade the self-link to the account-email rematch (§ 2); only an edit that strips the property *and* changes the email in one go loses the link, and the `getMe` reseed guard prevents the duplicate-me card that would otherwise mint. Acceptable: the link only powers profile-push and self-guards.
- **Label renames fan out** file rewrites + etag bumps across every member card; fine at contact-book scale.
- **`PROPFIND` prop-list permissiveness** (returning the fixed superset regardless of the request body) is inherited from CalDAV — it has survived real clients there, but a new client that chokes on unrequested props would need the proper prop-filtering both protocols currently skip.

## Decisions (2026-08-14)

1. **Files as truth, mail model** — directed by Reinder mid-review; the fidelity and portability arguments close the case. The calendar's DB-canonical + `icsBlob` model stays calendar-only.
2. **Existing contact data is dropped, not migrated** (Reinder, 2026-08-14) — and the drop rides the normal `ManagedDatabase` upgrade: a v2 migration on `contacts.db` drops the v1 tables and creates the index shape in place, then the book reseeds like a new account. No export code, no new filename, no init-time filesystem special-casing — eigen.is homes with populated v1 files clean themselves on first open.
3. **`CATEGORIES` is label-membership truth**; the `labels` table keeps definitions (color). One fact, one home.
4. **Inline `PHOTO` is canonical**, `avatars/*.webp` demoted to derived cache.
5. **One address book, vCard 3.0 on disk, `requireSelf`-only** — matching CalDAV's current scope; 4.0 PUTs transcode to 3.0 at the seam (decided after review — rejecting them breaks Thunderbird's default, storing them verbatim corrupts the iOS view). The second review re-raised rejecting 4.0 outright; the transcode stands — converting accepted input to the advertised format with an honest new etag is legitimate DAV behaviour, and Thunderbird-by-default matters more than byte purity for a version we don't advertise.
6. **No fs-watchers** — contacts have no out-of-process writer; reconcile-on-open covers manual disk surgery.
7. **First independent review folded in** (2026-08-14) — resource-name allowlist before any filesystem use, generation-stamped sync tokens, preconditions under the mutation semaphore, a specced account-email rematch with a `getMe` reseed guard, 5 MiB `max-resource-size` with the RFC precondition, grouped-property-safe serialization, tombstone-clear on re-create, quota over `cards/`.
8. **Second independent review folded in** (2026-08-14, [PROPOSAL_CARDDAV_REVIEW.md](PROPOSAL_CARDDAV_REVIEW.md), every code claim re-verified before merging) — per-card `cardCtag`; the value-keyed merge contract; the `id`/`uri` split; conditional REST writes (the zero-line claim was revised); atomic fail-closed writes; real `addressbook-query` filtering (the superset stance was reversed); `contacts.db` re-scoped as index + authoritative metadata; the `X-EIGEN-ID` trust rule; edge-owned well-known (Caddy already owns the CalDAV twin); the combined `/dav` OPTIONS header + neutral realm; request bounds; idempotent seeding; the `ManagedDatabase` future-version guard. **Rejected from that review, with reasons**: 3.0-only PUT rejection (the transcode stands, see 5) and storing files under app ids — a rebuild from files must reproduce client hrefs, and verbatim bytes can't embed the uri, so the sanitized uri stays the filename while the identity split it argued for is adopted in the index.
