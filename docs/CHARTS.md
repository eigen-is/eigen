# Charts

> **TLDR:** A chart is one stored description, a `ChartSpec`: its type, titles, legend, axes, colors and data. One pure layout turns it into ordinary canvas elements plus lines of text, and one painter draws those as plain SVG, so a chart looks the same live, in a preview and in every export. The spec, its reader and the layout are `packages/lib/src/charts/` with the types in `packages/lib/src/types/chart.ts`; the canvas kind and its painter are `packages/lib/src/vector/kinds/chart.ts` and `chart-render.ts`; the shared editor and the Edit data dialog are `packages/ui/src/components/charts/`.

Before changing how a chart draws or reads, look at how the big libraries do it: clones of Chart.js, d3-axis, d3-scale, ECharts, Observable Plot, Recharts, uPlot and Vega-Lite sit in the gitignored `.superpowers/corpus/charts-src/`, and [CHART-DRAWING-RESEARCH.md](CHART-DRAWING-RESEARCH.md) compares their layout choices.

A chart is a column, bar, line or pie chart, in Google's and Excel's names: a column chart has vertical bars, a bar chart horizontal ones. Its `ChartSpec` holds the presentation (title, legend position, axis titles, value-axis min and max, gridlines, stacking, colors, font) and the data: categories along one axis and one or more series of values. It is eight parts, each a record ([§ A spec is eight parts](#a-spec-is-eight-parts-each-a-record)). A canvas element of kind `chart`, in Vector and Slides, stores it as a JSON string per part, `specChart` to `specData` ([CANVAS.md](CANVAS.md)), a docs `chart` node as an attribute per part ([§ A doc's chart](#a-docs-chart-draws-its-look-at-its-own-size)), and a sheet's `SheetChart` as a field per part with each keyed part a record of entries ([§ A sheet chart reads its ranges](#a-sheet-chart-reads-its-ranges-and-its-panel-adds-googles-setup)). On a canvas and in a doc, Insert → Chart places one with sample data, the properties panel edits its presentation, and Edit data its numbers ([§ One chart editor edits a spec](#one-chart-editor-edits-a-spec-and-the-host-writes-it)).

The data is inline or a range. Inline data is the numbers themselves, inside the spec. Range data names cells of a sheet (a `CellRangeRef`: sheet id, first and last row, first and last column), which only a sheet can resolve. A canvas has no sheet, so it draws only inline data.

A chart's look is the rest of how it draws: its background and the hatch of its bars and slices, the stroke of its axes, the width of its line series, its sketch and its label color. It is a set of fields beside the spec, in a canvas chart element's own field names, so a doc's chart, a sheet's chart and a canvas chart store it the same way ([§ One look, a canvas chart's own fields](#one-look-a-canvas-charts-own-fields-paints-a-chart-in-every-app)).

The layout, `layoutChart`, takes the spec, the resolved data, a box and a paint (the look as the painter reads it), and returns shapes and labels in the box's own coordinates. The shapes are real canvas elements: rectangles for bars and legend swatches, lines for gridlines, baselines and line series, ellipses for markers and the pie kind for slices. The labels are lines of text with a position, font, size, weight, color and turn. The painter, `renderChartSvg`, draws the shapes through their own kinds and the labels as SVG `<text>`.

Six things surprise people:

- An edit never writes back the spec this build read. It applies a change onto the spec as stored, so a key from a newer build survives ([§ An edit is a change](#an-edit-is-a-change-applied-onto-the-spec-as-stored)).
- A canvas keeps each part of a chart's spec exactly as stored, even one that doesn't parse ([§ A canvas keeps the spec as stored](#a-canvas-keeps-the-spec-as-stored-and-draws-a-placeholder-for-one-it-cant-draw)).
- A chart's labels are SVG text, never rich text, because WeasyPrint ignores `foreignObject` ([§ The painter draws each shape with its own kind](#the-painter-draws-each-shape-with-its-own-kind-and-the-labels-as-svg-text)).
- Label widths come from a committed table, not from a browser ([§ Text widths come from a committed table](#text-widths-come-from-a-committed-table-generated-from-the-bundled-fonts)).
- Past 200 points a chart's data draws flat whatever its sketch ([§ Past 200 points the data draws flat](#past-200-points-the-data-draws-flat-and-the-rest-keeps-the-sketch)).
- A crowded data label hides rather than moves, where Office lets labels overlap ([§ A series' data labels](#a-series-data-labels-show-its-values-in-their-own-format-and-a-crowded-one-hides)).

## A spec is eight parts, each a record

A `ChartSpec` (`types/chart.ts`) is eight parts. Each is a record, so a later option nests inside one and an older build keeps it ([§ A stored spec grows](#a-stored-spec-grows-only-in-ways-an-older-build-keeps)).

| Part | Holds |
|---|---|
| `chart` | `type`, `blanks`, `fontFamily` |
| `title` | `text` |
| `legend` | `position` |
| `axes` | an axis per id: `kind`, `title.text`, `visible`, `gridlines.visible`, `labels.format`, `scale.min`, `scale.max`, `scale.reversed` |
| `plots` | a plot type's options, by type: `stacking` |
| `series` | a series' style, by its id: `plot`, `yAxis`, `color`, `line.smooth`, `marker.visible`, `labels.visible` |
| `points` | a point's style, by series id and index: `color` |
| `data` | `source`, `categories`, and `series`, each `{ id, name, values }` |

The axis ids are fixed, never minted: `x` is the category axis, `y` the value axis, `x2` and `y2` the second pair. A bar chart's `x` runs up its side. This build draws `x` and `y`, and keeps the other two as stored.

Style lives apart from the data and is keyed by series id, so deleting a series moves no other series' style. A series' `plot` and `yAxis` say which type and axis it draws in; this build draws every series in the chart's type on `y`. A pie's slices are its first series' points, so a slice color is `points.<id>.<index>.color`. A point's key is its index as a canonical decimal under the point limit (`chartPointIndex`), and any other key is ignored.

`CHART_SPEC_PARTS` (`types/chart.ts`) lists the parts once, with how deep Sheets splits each. The codec in `charts/spec.ts` reads and writes a chart stored as a field per part, `specChart` to `specData`. On a canvas and in a doc each part is a JSON string. On Sheets `axes`, `plots`, `series` and `points` are records with an entry per axis, plot type, series or point, keyed by the entry's path joined by `/` (`specPoints['s-1/3']`), so two peers who edit two entries both keep their edit. A point's key splits at its last `/`, since an id holds none. An entry key that is no such path (`'s-1/3/4'`, `'s-1/1e3'`, an id outside the grammar) is ignored, and so is an entry that doesn't parse. A part that doesn't parse reads as missing, and a keyed part as empty. `chartSpecWrites` and `sheetChartSpecWrites` apply a change and return only the parts, or on Sheets the entries, whose text it changed: a remove of what isn't stored writes nothing, and nor does a set to the stored value, so it can't undo a peer's edit of another entry in that part. Sheets never gets a keyed record whole, nor an entry key the reader ignores. Writing `series` or `points` drops the entries of a series `data` no longer names, so a deleted series' style goes with the next edit of its part. `newChartSpecParts` and `newSheetChartSpecParts` write a new or pasted chart's parts with every keyed part present, empty if need be: on Sheets a recipe that made the record and set an entry in it would ship the record whole, and two peers' first entries would collide. They take a spec, or the texts a copy carries (`chartSpecTexts`), which they keep as they came, a newer build's part too.

## readChartSpec reads a stored chart as stored and as resolved

Everything that reads what a stored chart says goes through `readChartSpec` (`packages/lib/src/charts/spec.ts`), because a stored chart is written by any collaborator or a paste. It takes a host's record of parts, so the byte limit is measured on what peers store. It returns two things. `stored` is the JSON as parsed and unvalidated, every key in place, known to this build or not: writers apply their change onto it. `spec` is the resolved view: validated, defaults filled, known keys only. Search, exports, the layout and the editors read `spec` only. `parseChartSpec` reads one spec string, as the OOXML reader builds one, when only `spec` is wanted.

Broken structure (no `chart` part, an unknown `chart.type`, no data, a series that is not a list, a bad series id, a range outside Excel's grid) or a hard limit resolves `spec` as `null`, which draws the placeholder, while `stored` is kept. Past the byte limit both are empty. A part past the depth limit, or one that is no JSON object, is missing, a keyed part empty, and the other parts still read. A broken, missing or unknown presentation value reads its default instead, so a field a build adds never turns a chart stored without it into a placeholder. An unknown axis `kind` reads its id's (`x` category, `y` value), an unknown series `plot` draws in the chart's type, and a series on an axis this build doesn't draw draws on `y`. `spec` holds the axes this build draws, `x` and `y`; a style for every series in `data`, defaults filled; and points only for those series. A style or a point keyed by a series `data` doesn't name stays in `stored` only. Text is cut to 200 characters and loses what XML can't hold, because every label ends up in SVG.

## An edit is a change applied onto the spec as stored

An editor never writes the spec it resolved. It hands its host a `ChartSpecChange` (`types/chart.ts`): ops that set, remove or move a value at a path into the stored spec. `applyChartSpecChange` applies the ops onto `stored` and returns the spec to write. So a tab on an older build that edits the title keeps a key a newer build stored, such as a log axis, and an enum value it doesn't know, such as a new legend position: it reads its default but is never written back.

- Each editor row emits the op for the field it edits: the title row sets `title.text`, the min row `axes.y.scale.min`, a series color `series.<id>.color`. No diff runs per keystroke.
- An array is a leaf, set whole. A list of records with ids (`data.series`) is laid over the stored list by id, so a series keeps the keys a newer build stored on it.
- A set makes the records along its path. Every record the writer makes or copies has no prototype, and an op whose path names `__proto__`, `constructor` or `prototype` is dropped, since `stored` is whatever a peer wrote.
- A move takes what is at `from` to `path`, and nothing at `from` leaves nothing at `path`, so a list of moves remaps indexes. `chartPointMoves` makes the list for every stored point, under any series id, for a remap that keeps the order, a row op's or Edit data's: the moves down run from the lowest target, the moves up from the highest, so none lands on a point still to move. Each point moves whole, keys this build doesn't know included.

Each host applies the change onto the stored spec it has at that moment. Sheets applies it inside the recipe onto the chart as the workbook then stores it, so a panel that rendered before a peer's edit keeps it when the panel's change sets another field. A series color sets one series' `color` and a slice color one point's, so neither touches another series or slice. A canvas and a doc apply it onto the element or node as last rendered. Edit data is the one editor that diffs (`chartSpecChange`), [§ Edit data](#edit-data-is-a-grid-over-inline-data-and-save-is-one-write).

Structural writers walk `stored` too. A row op and a copied sheet (`mapChartRefs`, `packages/sheet/src/engine/chart-data.ts`) move every record shaped as a `CellRangeRef` on `data` or on one of its series, under any key, so a ref a newer build stores moves as well, even in a chart this build can't draw. A row op along the categories also moves every stored series' points, in a chart this build can't draw too, since the ref they run along is found by shape on `data` as the refs are ([SHEETS.md](SHEETS.md#chart-refs-shift-with-rows-and-columns-and-an-undone-delete-ships-them)). Nothing deeper is walked, since no ref lives there. A copy to a host without cells (`inlineChartSpec`) reads the known ranges into numbers and leaves out every other ref, which would name cells the host doesn't have.

## Every series has an id that follows it

Each series in `data.series` has an `id`, unique in its chart, of 1 to 64 letters, digits, `-` or `_`, and never `__proto__`, `constructor` or `prototype`. A missing, malformed or repeated id resolves the spec as `null`. The id is what a change lays a series over by and what its style and points are keyed by, so a series keeps what is stored on it across a delete or a reorder of the ones before it. Eigen mints `s-` and ten characters of nanoid (`newChartSeriesId`) for a new column in Edit data and for a series a sheet's Setup or typed range adds past the previous ones. Setup keeps the id at each index, so switching rows and columns keeps the first series' id and its style. The sample numbers its series `s-1` to `s-3`. The OOXML reader takes Office's `c16:uniqueId` without its GUID's braces where it is a valid id no series before took, else `x-` and the `c:idx`, else that and the series' place. The writer writes no id, so a chart read back from Office has `x-` ids.

## A stored spec grows only in ways an older build keeps

A build keeps what it doesn't know, so a newer field must be one an older build can carry without misreading:

- A record grows by a key. A scalar never becomes a record. A new collection is a record keyed by id or index, never an array that grows by position.
- The positional arrays a build rebuilds are `data.categories` and each series' `values`. Per-point data that must run parallel to the values (a scatter's x, a bubble's sizes) is a sibling array in its `data.series` item. Edit data opens read-only when `data` or a series holds a key this build doesn't read (`holdsUnknownChartData`), so it never rebuilds the values without the array beside them. A sheet's Setup and typed range leave such data as it is: the panel shows their rows disabled, with Edit data's notice to reload.
- An enum may gain members. An older build keeps the stored value and draws its key's default; an unknown chart type draws the placeholder, and an unknown series `plot` draws in the chart's type.
- A value's type and unit never change. A changed meaning is a new sibling key with a precedence rule. A number's unit is in its name (`widthPx`, `holePercent`) unless it is an axis value, a count or a base.
- Every cell ref lives in `data`, shaped as a `CellRangeRef`, which never grows a field, so a row op moves it by its shape.

The font, `chart.fontFamily`, is a presentation field like the others: one of the bundled Eigen fonts, read through the canvas's own font reader, and Inter (`DEFAULT_CHART_FONT`) when it is missing or anything else. Only a bundled font has a width table and an `@font-face` an export can embed. It lives in the spec rather than on a canvas element because a document or a sheet has no element, so a chart keeps its font wherever it goes.

A series or slice color (`series.<id>.color`, `points.<id>.<index>.color`) of `null` is automatic: it draws in `chartColor(i)`, the palette color at its index, which the layout resolves on every draw. A missing color, or one that isn't a color token, reads as `null`. Charts made in Eigen store `null` (the sample, a new series or row in Edit data, a Sheets insert), so a palette change reaches them; a picked color stores its hex. As with Google's Auto, deleting a series shifts the automatic colors of the series after it, since their indexes change. `chartColor` is the shared accent palette in the order calendars and labels hand it out (`EIGEN_ACCENT_COLORS_SHUFFLED`, `constants/colors.ts`, where the order's rule is written and `colors.test.ts` pins it). It has seventeen colors, so the grid's twelve series never repeat one, and it starts at pink, Eigen's accent ([LAYOUT.md § Pink is Eigen's accent color](LAYOUT.md#pink-is-eigens-accent-color)). A new deck's title slide opens on pink, so a chart's first automatic series on it draws in the slide's own color. The same module owns the sample chart, `sampleChartSpec`, which Insert → Chart starts from: the share of light per equal 100 nm bin from 300 to 1000 nm for the Sun, a bulb (2700 K) and a hot star, from Planck's law. It is one dataset for every type because the Type switch keeps the data, and a pie draws the Sun. It carries axis titles, with the unit in the value axis's title, and no axis format. A Sheets insert starts from `defaultChartSpec` instead, so a chart of a selection never inherits the sample's titles.

`plots.<type>.stacking` is Excel's grouping, for column and bar charts: `'none'`, `'stacked'` or `'percent'`. Any other value reads `'none'`. Column and bar each keep their own, and switching Type between them carries it. Under `'percent'` the value axis's min and max are shares, 1 for 100%.

Each axis has `visible` and `scale.reversed`, both read as Google's look when missing. Only `x`'s `scale.reversed` is drawn, edited and written; `y`'s is read and kept, and the value axis always runs from its minimum (`minMax`). A hidden axis draws no labels and no line, as Excel's `c:delete`; its title and the gridlines are fields of their own and stay. With gridlines on, the line at zero stays as a gridline, as Office keeps its 0 line; with them off a hidden category axis draws nothing there. An imported axis reads as hidden under `c:delete` and under `c:tickLblPos none` alike, though Office keeps the axis line for `none`: `visible` is one bit, so a `none` axis loses its line. A reversed category axis runs the other way from Google's: a bar chart's from the bottom up, which is Excel's default, and a column or line chart's from the right. The whole axis turns, bands included, so inside each category the first series sits where the axis starts, as Excel draws it. Reversing the data would turn the categories but not the series inside each band, and an xlsx chart's ranges can't be read backwards anyway. The writer mirrors the reader: `c:orientation` is `maxMin` when `(type === 'bar') !== reversed` and `minMax` otherwise, with the value axis crossing at that end so it stays where Eigen draws it, and a hidden axis is `c:delete`, so a `c:tickLblPos none` axis comes back deleted ([§ A chart goes to Office as a c:chartSpace](#a-chart-goes-to-office-as-a-cchartspace-that-reads-back-as-the-same-spec)).

## Hard limits bound what every peer lays out

Every peer lays out and paints whatever is stored, so the limits bound one chart's cost. They are constants in `charts/limits.ts`.

| Limit | Value | Over it |
|---|---|---|
| Serialized spec, or every `spec…` key of a record of parts summed | 64 KiB | the spec reads as `null`, and `stored` as empty |
| Nesting of `[` and `{` in one stored string | 32 levels | the spec reads as `null`, and `stored` as empty; on a record of parts, that part or entry is missing |
| Series | 32 | `null` |
| Points (all inline values, or categories) | 2,000 | `null` |
| One label | 200 characters | cut |
| A doc's or a sheet's box side | 2112 px (`CHART_MAX_SIDE`, Word's largest page) | clamped, since a larger side runs the layout for seconds in every viewer |
| Inline data the Edit data grid edits | 12 series, 200 categories and 2,000 cells | `exceedsInlineGridLimits` answers true, and the grid opens read-only |

The depth limit guards the writers. Every writer serializes `stored` with `JSON.stringify`, and V8's recurses: it throws at about 8,000 levels, which a forged spec reaches in 16 KB. Bun's engine doesn't throw, so only a browser shows it. The reader counts the brackets outside strings in one pass before it parses. A string past the limit reads as empty: the chart draws the placeholder, no editor opens, and a row op or a copied sheet leaves it as stored.

On a record of parts the byte limit is one sum over the name and text of every key that starts `spec` and a capital, a newer build's parts included, and on Sheets each entry's key and text. It is measured in UTF-8 before anything parses, and the count stops at the limit, so a forged `specPoints` of a million entries costs about 6,000 measured ones. Only the measuring stops: listing a record's keys still walks every one. The canvas read counts while it lists an element's keys and stops both at the limit. On Sheets `MAX_CHART_SPEC_ENTRIES` bounds the walk: a chart's keys and its records' keys summed, a third of the byte limit since the shortest entry a build writes is three bytes. `floatingWriteFilter` drops a write past it, and the snapshot decode and `normalizeSheetConfig` leave out a chart past it ([SHEETS.md](SHEETS.md#a-chart-is-a-floating-record-whose-refs-name-sheets-by-id)).

## A canvas keeps the spec as stored, and draws a placeholder for one it can't draw

The chart kind's `read` keeps each part's string as it came, never re-serialized from the parsed spec, and also keeps a string under any other key that starts `spec` and a capital, a part a newer build added. Every copy carries such a part, and each part's text as stored: Duplicate, the `elements` item and the paste write store a chart's prefixed keys beside `ELEMENT_FIELDS` (`storedElementFields`), and the chart item carries them as texts. Past the byte limit, summed over all those keys, the read stops: every part reads as `''` and no newer part is kept. The reader's repairs live only in the scene anyway ([CANVAS.md § The reader is the trust boundary](CANVAS.md#the-reader-is-the-trust-boundary)), and an edit applies its change onto the parts as stored and writes only the parts it changed ([§ An edit is a change](#an-edit-is-a-change-applied-onto-the-spec-as-stored)), so a spec this build can't read, such as one with a field from a newer build, stays recoverable. Since every part is its own field, two peers who edit two parts both keep their edit, and ⌘Z of one edit leaves a peer's edit of another part.

A spec that doesn't parse, and a spec with range data, draws a placeholder: a dashed box in the gray a picture with no file draws, and one centered line, "This chart can't be shown", ellipsized to the box or left out when the box is too small. `layoutChartMessage` lays that line out the way the layout's own messages are laid out.

## A chart is laid out as canvas elements plus labels

`layoutChart` (`charts/layout.ts`) is pure and synchronous, so the server and the live canvas run the same code. Its shapes are the canvas's own element types rather than a chart-only drawing, so a bar paints exactly as a rectangle with the same fields, with the host's roughness and hatch. Each shape's id is `${chartId}:${key}` (`c1:bar:0:2`, `c1:gridline:3`), which keeps the ids and every id derived from them unique on a page, and its seed is derived from the chart's seed and the key, so the jitter is the same on every redraw and differs per shape.

Shapes come in paint order: background, gridlines, bars or slices, lines, markers, baseline, legend swatches. Every shape has opacity 100 except the gridlines, which are faint. The chart's own opacity is its layer's, as for every element.

A label's `y` is the top of its line, not its baseline, so a renderer adds its font's baseline offset and a text box could take it as its top. A turned label turns about `(x, y)`.

The look is Google's defaults: text scaled to the box, title on top in bold, legend on top for column, bar and line and none for a pie, light gridlines, no tick marks, zero-based bars. The category axis is one band per category, end to end, as in Office and Google, and a line's points sit at the band centers. A category's bars fill 61.8% of its band (`BAR_GROUP_WIDTH`, Google's group width), centered: side by side they split it, stacked they take it whole. Stacked bars sum positives and negatives apart. A 100% stack (`'percent'`) plots each value as its share of its category's absolute sum, as Excel and Observable Plot do, so a category's positives and negatives together span 100%, and its ticks read as percents whatever the axis's or the source cells' number format. A category that sums to zero draws no bar. A line's value axis takes in zero when the line is flat or its smallest value is under 5/6 of its largest, so the spread passes a sixth: 50, 70 and 100 tick from 0, while 90, 95 and 100 fit their data with nice ends. Data below zero mirrors it. That is Excel's rule, which LibreOffice's `ScaleAutomatism` mirrors. Google's look fits the data instead; Eigen takes Excel's so a line imported from Excel keeps its scale. A pinned min or max still sets its end. All zeros draw an axis from 0 to 1, and so does a span too small for a tick step (under 1e-300). Value ticks come from a port of d3-array's tick algorithm (`charts/ticks.ts`), spaced by pixels and never more than 20 (`MAX_TICK_COUNT`), however long the axis, because a peer sets the box. d3 takes the count as a hint and can return half as many again, so an axis over 20 asks again for fewer, which steps up to the next nice step. A bar chart's value axis then asks for as many as its widest pair of labels has room for until they stop touching. Two is the fewest it asks for, and d3 can answer two with four, while turned category names can squeeze a column chart's axis below its count. So on either value axis a last pass hides every other tick label until none touch, Vega's parity rule, counting from zero's label so an axis that crosses zero still names it, and every tick keeps its gridline. A tick label carries as many decimals as the step, and reads in scientific notation (`5E-21`, `1.0E100`) past six decimals or from a step of 1e15, so tiny ticks stay distinct and a huge value leaves the plot its room. A value axis with a number format (`axes.y.labels.format`) draws its ticks in that format instead, through `numberDisplay` (`charts/number-display.ts`), the formatter the sheet writes its cells with, in every host. The format then decides the decimals and the step doesn't, as Excel draws them and as d3-format and Chart.js let a format's own precision win, so `0%` over a 0.5% step repeats labels. Without an axis format the layout takes `sourceFormat`, the values' own format a host passes: a sheet chart passes its first value cell's, and General when that cell has none, so its ticks read as the grid shows the cells (`renderSheetChartSvg`). Docs and canvases pass nothing. A pinned min or max too close to its partner to tick gives way to the data's domain. Category labels turn -45° when upright ones would touch, then ellipsize. A bar chart's category names are centered on their bands, so where the bands are thinner than a line they start half a line in from the plot's ends, which keeps the end names off the title or legend above and the value labels below. A hidden axis gives its labels' room to the plot, and a hidden category axis draws no baseline, since the baseline is that axis's line. A column or line chart's end tick labels overhang the plot by half a line, so the plot keeps that half line at the top, and at the bottom when no category names sit there, off the axis title and a bottom legend. A legend past its room, 30% of the height on top or bottom and the height below the title on a side, drops the entries that don't fit and ends with "+N" counting them. A pie labels each slice of 5% or more with its name and share, beside the slice and without leader lines. Small neighbours near 12 or 6 o'clock would put their labels on one line, so labels are placed largest slice first, as Highcharts ranks its data labels, and one that would touch a label already placed is left out: the biggest slices keep theirs. No data, a pie with a negative value or a box too small for a plot draws one centered message instead. No data means no series, no categories or every value blank, whatever the blanks setting, and for a pie also nothing positive. The tests in `packages/lib/src/test/charts/` pin each of these, a file per part of the layout (`cartesian.test.ts`, `legend.test.ts`, `pie.test.ts`).

## A series' data labels show its values in their own format, and a crowded one hides

A column, bar or line series with `labels.visible` draws each value it plots as a label, as Google's and Excel's data labels do. Missing reads false, so every chart stored before the key existed lays out exactly as before, and the sample, Insert → Chart and a new series in Edit data start without labels, as Google's and Excel's defaults do. A pie ignores the key and keeps it, so a Type switch to pie and back keeps the labels; it labels its slices with name and share whatever the key says, because reading the key there would turn off every stored pie's labels.

The text is the raw value in the values' own format: the axis format, else `sourceFormat`, else General, which is Excel's source-linked default. A 100% stack labels the raw value, not its share, as Excel's `c:showVal` does, and skips the axis format, which formats shares: a chart imported before data labels can store an unlinked `0.0%` there, which would draw 1234 as 123400.0%, so its labels read `sourceFormat`, else General. A blank gets no label, even one plotted as zero. The label is drawn in the chart's label color, inside a dark segment too, since Office's default does the same; an Office file that sets white labels draws dark in Eigen.

The position follows the kind, as ECharts and Recharts place theirs, half an em from the mark: past a clustered bar's end, below or left of it for a negative value; centered in a stacked or 100% segment; above a line's point whatever its sign. A stacked segment too small for its label shows none, Eigen's own rule, where Excel lets the text spill. Labels past the marks need room the plot keeps only when one shows: a line and a half-em above a column or line chart, which takes in the end tick's half-line overhang rather than adding to it, a line below for negative columns, and the widest label's width right or left of a bar chart. Labels are the first thing to give: a box too small for a plot with them draws the plot without them, not the too-small message.

Crowded labels hide, never move, as Highcharts' do: the label of the bigger bar or segment keeps its place, and on a line the first series'. ECharts hides only a pie's by default, and Excel and LibreOffice let labels overlap, so a crowded imported chart shows fewer labels than Office. A label that leaves the plot frame grown by its reserved room hides too, which keeps it off the tick labels and category names outside that frame. Each label is measured once, and past `MAX_SKETCH_POINTS` plotted points a chart draws none, which bounds the collision pass to 200 labels; no labelled corpus chart has more than 100 points. `cartesian.test.ts` pins each rule. The labels are ordinary labels of the layout, so every renderer draws them and Convert to shapes turns them into text boxes.

## The painter draws each shape with its own kind and the labels as SVG text

`renderChartSvg` (`vector/kinds/chart-render.ts`) wraps each shape in its own translate group and calls that kind's `render`, so a chart's bar and a drawn rectangle with the same fields are the same SVG by construction. It imports the four shape kinds one by one: the registry imports the chart kind, so reaching the shapes through `ELEMENT_KINDS` would be an import cycle. The charts modules reach `vector/` only through modules that import no kind, such as `vector/points.ts` for the stored point list, so the chart kind imports the charts barrel. Code outside `vector/` reaches the painter through `@workspace/lib/vector`, never its own module: a kind's module as the first way into the kinds evaluates the registry before that kind, and `test/vector/kinds/cycle.test.ts` pins the charts and eigendoc barrels as entries.

The labels go through `svgTextLine` (`vector/kinds/render-utils.ts`), the one helper that turns a line of text into SVG `<text>`; an arrow's label draws through it too. Plain SVG text is what lets a chart print: WeasyPrint ignores `foreignObject`, so rich text would vanish from a PDF. A bold label is drawn at weight 600, the weight of Inter's and JetBrains Mono's bundled bold faces.

A document or a sheet has no element, so it draws through `renderChartSpecSvg` (`@workspace/lib/vector`, safe on the server): the same painter in the look the chart stores, and in `FLAT_CHART_LOOK` (`charts/look.ts`) when it is given none. That is Google's flat look: near-black text in the spec's font, a mid gray for the baseline and the faint gridlines, line width 2 (Google's series width), roughness 0, solid marks and no background, so the chart sits on the page. It takes the parsed spec, `null` drawing the placeholder, and for a sheet the resolved range data or why there is none: `'ref'` draws `#REF!` and `'too-many-points'` draws "Too much data for a chart", one centered line without the dashed box. Inline data needs nothing passed; range data with nothing passed draws the placeholder. It returns a complete `<svg>` the size of the box, which a document's HTML inlines and a sheet overlays.

The placeholder draws its line in Inter, since a spec that doesn't parse names no font.

So previews and exports need nothing for charts. The editor's downloaded SVG, the Download image a chart's menu offers in every app, the PDF page, a deck's HTML and the preview all draw the chart through the kind, and the export sanitizer keeps every shape and label; `apps/api/src/test/export/chart-export.test.ts` proves it. The downloaded SVG embeds the faces `canvasImageFaces` collects, and each kind answers for its own elements (`fontFamilies`), so the chart kind gives the font its labels draw in without the writer asking for charts by type. A placeholder adds none, so its line falls back to the viewer's fonts unless another element embeds Inter. The live canvas loads nothing extra: the app's `@font-face` rules load a face the first time SVG text uses it.

## A doc's chart draws its look at its own size

A docs `chart` node stores the spec, an attribute per part, beside a width, a height and its look, and draws it through `renderChartSpecSvg` everywhere: the node view at its size, and the server's HTML, PDF and preview as inline SVG in the figure's box ([DOCS.md](DOCS.md#a-chart-is-a-node-of-its-own-in-the-figures-frame)). Its labels draw in the spec's font, Inter for a chart Insert → Chart places, and the Chart panel's Font row changes it: the node view's inline SVG takes the face from the app's `@font-face` rules and the export's from the HTML's embedded fonts. A doc has no sheet, so its charts hold inline data, and anything else draws the placeholder. Search reads the node through `chartSearchText` (`charts/resolve.ts`), the text the canvas kind indexes too. The docx writes it as a Word chart ([§ A chart goes to Office as a c:chartSpace](#a-chart-goes-to-office-as-a-cchartspace-that-reads-back-as-the-same-spec)).

Insert → Chart places a flat chart, as Google's is, with a random `seed`. The sketch is a pure function of the seed, so a sketch picked later jitters the same in the editor, the export and a copy.

Every drawing of a doc's chart (`chartSvg`) takes a fresh id. A gradient background writes a `<linearGradient>` whose id derives from the chart's id, and a page holds many charts, so a fixed id would let one chart paint with another's gradient.

## One look, a canvas chart's own fields, paints a chart in every app

A chart's look is `ChartLook` (`types/chart.ts`): the canvas chart element's `fill`, `color`, `strokeColor`, `strokeWidth`, `seriesStrokeWidth`, `strokeStyle`, `roughness` and `seed`, listed once in `CHART_LOOK_FIELDS`. A canvas chart is its element, so it follows its host's style table like any shape: rough and hatched in Vector, flat and solid in Slides. A doc's chart stores the same fields as attributes of its node, and a sheet's chart as fields of its `SheetChart` record, one each, so a peer's stroke edit and another's sketch edit merge instead of one overwriting the other. `readChartLook` (`charts/look.ts`) reads a doc's, a sheet's or a clipboard item's look through the canvas reader's own validators, and a missing field reads flat, so a chart written before the look existed draws as it did. `chartPaintOf` turns any look into the painter's `ChartPaint`, the one map in all four apps. Opacity is a canvas layer's, not the look's. The font is not part of the look but the spec's, so Insert → Chart writes the host table's font into the new spec: Excalifont in Vector, Inter in Slides.

| Look field | What it paints |
|---|---|
| `fill` | The background, always solid; its hatch style is the fill style of the bars, slices and legend swatches |
| `strokeColor`, `strokeStyle` | The axes and gridlines, not a border |
| `strokeWidth` | The axes and gridlines, markers, and the outline of a hatched bar or swatch. A bar narrows by its outline across its band, so bars side by side meet outline to outline instead of overlapping, and a bar thinner than two outlines draws a thinner one |
| `seriesStrokeWidth` | A line series. Unset, it is `strokeWidth`, so a chart made in Eigen draws its series at its stroke and the Stroke row's width moves both; only an Office import sets it ([§ A chart's look goes to Office](#a-charts-look-goes-to-office-as-far-as-a-chart-part-paints-it-and-reads-back-the-same-in-all-three-formats)) |
| `color` | Every label |
| `roughness`, `seed` | Every shape |

A bar, a slice or a legend swatch with a solid fill draws no outline, as Google's do. A hatched one (hachure, cross-hatch or zigzag) is outlined in its own series or slice color, since a hatch is strokes inside an outline and reads as unfinished without it. The painter derives this from the fill style at draw time, so switching the style writes nothing else. A hatched slice's edge is 1px wide. Its hatch draws inside a clip of its own outline, as every canvas shape's does (`drawableToSvg`): roughjs strokes a hatch past the edge, a zigzag by about 3px at any size, which shows on a legend swatch. Series and slice colors are in the spec, automatic or picked ([§ readChartSpec](#readchartspec-reads-a-stored-chart-as-stored-and-as-resolved)).

`PaintSections` (`packages/ui/src/components/properties-panel/`) is the one panel section that edits a look: the Labels color, the Fill with its hatch Style, the Stroke and the Sketch. No row edits `seriesStrokeWidth`, so a chart imported from Office keeps its series width while the Stroke row changes its axes. The canvas panel shows it for every selection, merging each row across it, and adds the Labels row for charts alone; the Docs and Sheets chart panels show it for the selected chart, through `ChartSections`. A shape's hatch row shows only while it has a fill, since a hatch fills its body, but a chart's shows without a background, since its hatch is its bars'.

## Past 200 points the data draws flat, and the rest keeps the sketch

A rough or hatched mark costs about 20 times a flat one. Every viewer draws what a peer stores, a doc's chart is drawn again for its export and every copy's `<img>`, and the box can be 2112 px a side. At 2000 × 1200, cross-hatched, 200 points take 35 to 55 ms and 1.5 to 3.8 MB of SVG on the server, and 400 points 70 to 110 ms and 3 to 7.5 MB, which the browser then parses and paints. So past `MAX_SKETCH_POINTS` (200, `charts/layout.ts`) the data marks (bars, slices, lines and markers) draw with roughness 0 and solid, and so without outlines, while the background, gridlines, axes and legend keep the sketch. A chart counts its points as the values it plots (`chartPointCount`): a pie its first series, any other type every series. It is the painter's rule, so every app draws the same, and the panel's Sketch section says so when it applies (`isSketchCapped`).

## Convert to shapes unpacks the painter's own layout

Convert to shapes, a row in the canvas object menu and a button in the chart's panel section for a selection of one chart that draws, replaces the chart with what it draws. `chartToElements` (`vector/kinds/chart-convert.ts`) reads the same layout the painter draws (`chartElementLayout` in `chart-render.ts`), so each converted shape is the element that drew it: same kind, fields and seed, so no jitter or hatch rerolls. Each shape's center turns about the chart's center, the chart's angle is added to its own, and its opacity is multiplied by the chart's. Each label becomes a rich-text box in the label's font, sized by `measureLabel` plus half an em of slack, since its kerning-free width can run short and a wrapped label would take two lines, one line high at the font's own line height so the baseline lands where the SVG text put it, and aligned by its anchor. A turned label turns about its anchor but an element turns about its center, so the box's center is turned instead. A chart that draws its placeholder converts to nothing, and the row is hidden. The kind answers through `toShapes`, read by `convertToShapes`, so the menu never asks for a chart by type.

`replaceElementInDoc` (`packages/ui/src/components/vector/hooks/element-writes.ts`) deletes the chart and writes the shapes in one transaction, at keys between the chart's index and the next one above it, so they keep the chart's place in the stacking order. Both run it through `convertElementToShapes` as one sealed undo step, so one ⌘Z brings the chart back, and selects the shapes, since the canvas has no groups to put them in. An arrow bound to the chart keeps its endpoints and loses its binding, as on a delete. The action is one way and has no ⌘K entry, because the palette has no canvas element actions.

The converted labels are rich text, each its own layer. The live canvas, a preview and the PDF mount a rich-text layer as HTML, and the downloaded SVG writes it as SVG text the browser measured ([EXPORT.md](EXPORT.md#a-drawing-downloads-its-own-svg-and-prints-as-layers)), so all of them draw the labels.

## One chart editor edits a spec, and the host writes it

`ChartEditor` (`packages/ui/src/components/charts/`) is Google's Customise rows over one `ChartSpec`: type, stacking (Google's None, Standard and 100%), titles, legend, font, each axis's Show axis box, the category axis's Reverse axis order box, the value axis's min, max and gridlines, and a color per series or per pie slice. A color row says Automatic while its color is `null`, with the palette color in its swatch and no swatch marked in its picker, so a click on that palette color is a visible pick; a picked color's popover has an Automatic row (the shared `ColorRow`'s `automatic` prop) that writes `null` back in one change. The Font row is the canvas text box's `FontRow`, so a chart offers the same fonts as a text box. It takes a spec and the spec as stored, hands back a change of the fields a row edits, and knows nothing of where the chart lives, so any surface that stores a spec can mount it. On a canvas the chart kind's panel section is this editor, shown for exactly one selected chart, because a spec doesn't merge across charts the way a color does. Each change is one write of the element's parts it changed, applied onto them as stored. A host that edits one chart record, a doc's chart or a sheet's, mounts `ChartSections` instead: this editor, then `PaintSections` over the record's look. Its children land at the end of the Chart section, where Edit data sits, so Sheets puts its data range there. The canvas panel builds the same order from the chart kind's section and its own merged paint rows, so a chart reads alike in every app.

A typed title writes on every keystroke inside the host's gesture (`PropertyGestureContext`), so the title is one undo step and peers see it as it is typed. A range chart's categories and series names are only known to the sheet that resolves them, so its host passes them in (`categories`, `seriesNames`, one per series in the spec) to name the pie slices and the series rows; without them the slices and series go by number. A range series whose values ref is null draws nothing, so it has no row, and a pie with none left has no slice rows. A bar chart lies on its side, so its Horizontal axis rows edit the value axis and its Vertical axis rows the category axis, Reverse axis order among them. A box writes on its click, one undo step. Show axis is one box where Google has Show labels and Show axis line, because `visible` hides both. Each box is a `PropertyCheckbox`, Google's words beside it, and its accessible name leads with its section ("Horizontal axis: Show axis"), since both sections have one. A min at or past the max is not written, because the reader would drop both and the field would snap back. Under a 100% stack the min and max are shares of the whole, as Excel's `c:min` and `c:max` are (1 is 100%), so the editor shows and takes them as percents: a typed 100 stores 1, and a typed 33.3 stores 0.333 (rounded to 15 digits, past the division's float noise). Switching Stacking to or from 100% sets min and max back to automatic in the same change, since a raw max of 100 would read as 10,000% and a share of 1 as a raw 1. Switching Type between bar and any other type sets the category axis back to Google's direction in the same change: an Excel bar chart reads as reversed, which would turn it as a column chart right to left. Switching between column and bar sets the new type's stacking to the old one's. One Data labels box tops the Series section while a series draws, as Google keeps it under Customize › Series: it is checked when every drawn series shows labels, shows a minus when only some do, as an imported file can store, and a click sets every drawn series on, or all off when checked. A per-series box can come later without a format change. On Sheets the click writes the entry of each series it changes, each that series' whole style, so it races a peer's concurrent edit of any of those series and the last write wins. Markers and smooth lines are in the spec and the layout but not in the editor, as on Google's insert surface.

## Edit data is a grid over inline data, and Save is one write

`ChartDataDialog` shows inline data as a small sheet: categories down column A, series across row 1, and the empty top-left cell. It edits a draft, so Save is one write of the spec and one undo step, and Cancel leaves the chart as it was. Save hands the change from the grid as it opened to the grid as it is (`chartSpecChange`, a diff of leaves, arrays whole), applied onto the chart as it is at Save, so a peer's title, series color or slice color written while the dialog was open stands. A series' style isn't in the data, so Save never writes it. Each row carries the index it opened at, so Save also moves every stored point with its row, as a row op does: a deleted row's points go, and the rows after it keep theirs, a peer's slice color, a point past the rows and a series the data doesn't name among them. A cell keeps what was typed, so a value that isn't a number stays on screen, flagged, and Save waits for it. A new series or row is automatic.

The grid stops at 12 series, 200 categories and 2,000 cells in total, since a full 12 × 200 grid would be past the 2,000-point limit that makes a spec unreadable (`fitsInlineGrid`). A chart past those limits, written outside the grid, opens read-only as a plain table rather than as thousands of cells. So does a chart whose data or a series holds a key this build doesn't read ([§ A stored spec grows](#a-stored-spec-grows-only-in-ways-an-older-build-keeps)). On a canvas and in a doc the dialog opens from the panel's Edit data button and from a double-click on the chart ([CANVAS.md § A kind is one registry entry](CANVAS.md#a-kind-is-one-registry-entry)). `ChartEditor` shows that button for inline data and owns its dialog, except in Docs, which passes `onEditData` because `editor.tsx` opens the one dialog for both. A double-click mounts `InlineChartDataDialog`, open at once, which closes itself when the chart's data is no longer inline, as after a peer deletes the chart.

## Edit data looks and types like Eigen Sheets

The grid is drawn to look like a sheet, so a user who knows Sheets knows it. Its sizes come from `@workspace/lib/sheets` (`SHEET_DEFAULT_COL_WIDTH`, `SHEET_ROW_HEADER_WIDTH` and their siblings) and its colors from the `--sheet-*` variables in ui's `globals.css`, the ones Sheets' canvas reads, on a light-pinned `.eigen-paper` as the workbook is. It is its own component rather than an embedded Workbook; what embedding would take is a [CHARTS-TODO](CHARTS-TODO.md) row (Edit data: embed the Sheets grid).

Like a sheet, it fills the dialog with empty cells and opens on A1: every column a series can go in, B to M, and rows two views past the scroll position, more as it scrolls, up to the 200th category. Typing in an empty cell adds a category or a series, those between as gaps, and an empty commit adds nothing. A value past the 2,000-value total is left out, and the grid says so. A row or column header selects the whole row or column, and Delete removes it; Delete on cells clears them to gaps.

The keys are Sheets' keys: arrows move and Shift extends, typing replaces the cell, Enter and Tab commit and move down or right, F2, Enter and a double-click edit in place, and Escape cancels the edit. One `<input>` sits on the active cell and keeps the focus, invisible until a cell opens, as Sheets' own cell input does. That is what makes a canvas host stand down: its clipboard listeners bail on a focused input (`isTypingTarget`). Radix hears Escape on the document before the input does, so the dialog's `onEscapeKeyDown` lets an open cell editor (`[data-cell-editor][data-editing]`) take it, and only a second Escape closes the dialog.

⌘C writes the selection as TSV and an HTML table (`@workspace/lib/clipboard`'s `table.ts`, the helpers Sheets' copy uses too). ⌘V fills from the active cell and grows the grid to fit, up to the limits, and says how many rows and columns it pasted when some fell outside. A paste reads TSV when the plain text has a tab, and otherwise an HTML table if there is one, then the plain text's lines: a Docs table's `text/plain` is its cells on lines of their own, which would land down one column. A1 is the category axis title, the header of the categories column as in Google, typed, pasted and cleared like any cell; Save writes the title only when A1 changed, so a peer's title change made while the dialog was open stands. A `<br>` in an HTML table cell is a line break in it, as Google's HTML marks one. A paste past the limits is cut to one row and column more than the grid holds before it fills, so a million rows cost no more than 202. Numbers read as Sheets shows them in the `en` convention: grouped (`1,234`), after a currency symbol (`$1,234.00`) or a percent (`12%` is 0.12, rounded as the editor's percents are), over a plain decimal with an optional exponent; anything else, `0x10` among it, is flagged. While a cell is open, a single value pastes into it as typed text.

## Text widths come from a committed table generated from the bundled fonts

The layout needs a label's width to reserve room for the value-axis labels, the legend and turned or ellipsized category labels, and it runs where there is no DOM. `measureLabel` (`vector/text-width.ts`) sums advance widths in the spec's font from `vector/text-width-data.ts`: one table per Eigen font, regular and bold, for Basic Latin and Latin-1, with an em fallback for every other character. It ignores kerning, so it runs slightly off a browser's measurement, which is why widths only reserve room and placement goes through `text-anchor`.

The table is generated from the static TTFs a docx embeds: `bun apps/api/src/scripts/chart-text-widths.ts`, rerun after a font changes. Inter's and JetBrains Mono's bold TTFs are weight 600, the weight a bold label draws at. Source Serif's is 700, so its bold widths run slightly wide of the 600 the app's variable face draws, which only reserves extra room. Excalifont has only a regular face, so its bold width is its regular width and the browser fakes the bold. The demo seeder sizes its labels with the same function.

## A sheet chart reads its ranges, and its panel adds Google's Setup

A sheet keeps its charts beside its cells as `SheetChart` records, floating objects like its images and in one paint order with them, which can turn about their center, and a chart there usually holds range data, which the sheet resolves from its cells when it draws. The editor's overlay and the export draw it through `renderSheetChartSvg`, `renderChartSpecSvg` with the sheet's resolved data, its number formats and the look the record stores. Insert → Chart stores only a random seed, so a new chart is flat, as Google's is, and charts the selected cells, and selecting it shows `ChartSections` with Google's Setup (the data range, Switch rows/columns, headers and labels) at the end of the Chart section, or Edit data for an inline chart. Its sketch note counts the resolved data's points. How the sheet stores, shifts, draws and exports charts: [SHEETS.md § Images and charts are floating records](SHEETS.md#images-and-charts-are-floating-records-in-one-paint-order) and the sections after it.

## A chart goes to Office as a c:chartSpace that reads back as the same spec

`writeChart` (`apps/api/src/lib/ooxml/ooxml-chart-writer.ts`) writes a spec as a DrawingML chart part, the `c:chartSpace` that xlsx, docx and pptx files share, and `readChart` (`ooxml/ooxml-chart.ts`) is its inverse, which the three importers run. All three exports write one, so Excel, Word and PowerPoint see a chart they draw, not a picture. `ooxml-chart-writer.test.ts` writes every kind and option and reads back the same spec. The reader takes the plot area's category axis as `x` and its value axis as `y`, and refuses a chart with more than one of either, a log value axis or a value axis that runs `maxMin`; the group's grouping as its type's `plots` entry; and a pie's `c:dPt`s as its first series' points. The writer writes `x` and `y` as `c:axId` 1 and 2, and each slice as a `c:dPt`. Range data is written as refs by the names the workbook writes its sheets under, each with a cache of what the cells show, so Excel draws before it recalculates. In an xlsx, inline data is written as literals; a docx or pptx writes it into a workbook of its own ([below](#a-docx-or-pptx-chart-carries-its-numbers-in-a-workbook-of-its-own)). A bar or column chart's `c:gapWidth` leaves the bars `BAR_GROUP_WIDTH` of their category, as Eigen draws them: Office's gap is a share of one bar's width, so it is 62 for bars stacked or alone and grows with each series side by side, up to the 500 `ST_GapAmount` allows. Past eight series side by side Office draws the bars a little wider than Eigen does. The reader ignores `c:gapWidth`, since the spec has no bar width. The xlsx export places each sheet chart as a two-cell anchor over the cells its box covers (`sheetTrackAt`, the inverse of the import's walk), so a re-import lands it on the same pixels.

A docs or Slides chart is a part of its own, `word/charts/chartN.xml` or `ppt/charts/chartN.xml`, shown by a `w:drawing` or a `p:graphicFrame` whose `a:graphicData` names it ([EXPORT.md](EXPORT.md#a-docs-docx-is-written-from-its-json-with-the-editors-css-values)). All three writers add a chart's part through `addOfficeChart` (`export/office-chart.ts`), which numbers, writes and relates it and counts what it leaves out or draws plainer, and every host shows one through `chartGraphicXml`, whose `c:chart` declares the `c:` and `r:` prefixes itself, as Office writes it, so no host part has to and none can forget them. A spec that doesn't parse, or a docs or Slides chart holding range data, which only a sheet can read, writes no part and counts as `charts-dropped`. The docx and pptx imports read the chart back with the same kind, series, values, title and options, its series ids by place.

## A docx or pptx chart carries its numbers in a workbook of its own

Desktop Word and PowerPoint keep a chart's data in an xlsx embedded beside its part, and their Edit Data opens it. A doc's or a deck's chart holds inline data, so `addOfficeChart` writes that workbook as desktop Office, python-pptx and Aspose do: `embeddings/Microsoft_Excel_WorksheetN.xlsx` beside the chart's part, related from the part's own relationships as a `package`, named by `c:externalData` after its `c:txPr` with `c:autoUpdate` 0, and the package's `xlsx` Default content type, written only when a chart is. Its sheet, `Sheet1`, is laid out as Office lays one out: the series names along row 1 from B, the categories down A from row 2, each series' values down its own column, A1 empty, a value in the number format its cache carries and a gap no cell. `embeddedChartSheet` lays the cells out and the writer's refs name them, both in `ooxml-chart-writer.ts` from the one spec, so a ref and its cache can't disagree: each series' `c:tx` is a `c:strRef` to its name's cell, its `c:cat` a `c:strRef` over the categories and its `c:val` a `c:numRef` over its values, each with its cache. A range holds a cell at least, so no categories or no values go as an empty literal. Our own `writeXlsx` writes the workbook, so it is the file an xlsx export would be.

The imports read the caches, as they read any docx's or pptx's chart, and never open the workbook. The spec's limits bound it: 32 series and 2,000 points, each label 200 characters, so a workbook holds at most 4,032 cells, about 4 KB deflated for a sample chart. Edit Data works in desktop Word and PowerPoint as far as the format goes, since it is the one they write, but it is unverified in them: LibreOffice Calc and our own xlsx import read every cell a ref names as its cache holds it, and LibreOffice draws the charts. The check in desktop Office is a [CHARTS-TODO](CHARTS-TODO.md) row. An xlsx's charts name the workbook's own cells and embed nothing.

An automatic color is written as the palette color at its place, so Excel and Google show Eigen's colors rather than their theme's. The reader reads a series or slice color equal to `chartColor(i)` back as automatic, so the round trip keeps `null`, and a file from elsewhere that happens to use that color draws the same either way. Hidden rows are plotted (`c:plotVisOnly` 0), since the sheet reads hidden cells like any other. A pie has no axes in Office, so its axis titles and the axis settings only a Type switch shows come back as a new pie's. Its value format goes with its values instead, as each literal's or cache's `c:formatCode`, which the reader takes when there is no value axis, and its gridlines read as its type's.

A labelled series writes a `c:dLbls` of its own with `c:showVal` on, in `Group_DLbls` order, and an unlabelled one writes none, so a chart without labels writes the bytes it always did. The labels state Eigen's position (`outEnd` clustered, `ctr` stacked, since Office refuses `outEnd` there, and `t` on a line, since Excel's line default is elsewhere) and, when the spec has one, the values' format unlinked: for range data Excel would otherwise read each cell's own format, where Eigen draws every label in one. The reader takes a series' own `c:dLbls`, else its group's, and shows labels when `c:showVal` is on and `c:delete` is not; `isOnElement` reads a missing `c:showVal` as undefined, so the reader tests for true. It reads no position, label format, text style, name, category or percent label, and no per-point `c:dLbl`, so a nudged, retyped or deleted point label reads as its series' label, and those losses stay silent, as `c:gapWidth`'s are: the import summary has no row for them.

A 100% stack's value axis formats shares, so its own format is never the values'. The writer always writes `0%` unlinked on a 100% value axis, so Excel reads its 0 to 1 as percents whatever the stored format, which goes on the value cache and the labels' `c:numFmt`. The reader takes a 100% stack's format from its values whatever its axis says: in a docx or pptx the first series' value cache, and in an xlsx none, since the cells carry it. So a pptx whose cells hold shares in `0%` labels them 25%, as PowerPoint does, and an Eigen 100% chart storing `#,##0` comes back with it. No Office frame turns or fades a chart, so a rotated chart is written upright and a faded one opaque, and either counts as `charts-simplified`.

## A chart's look goes to Office as far as a chart part paints it, and reads back the same in all three formats

The writer maps the look onto the part: the background as `c:chartSpace`'s `c:spPr`, the label color as its `c:txPr`, the stroke's color and width as every axis and gridline's line, and a line series' width, `seriesStrokeWidth` or else the stroke's, as each line series' `a:ln`. `readChartPartLook` (`ooxml/ooxml-chart.ts`) is its mirror, and the docx, xlsx and pptx imports all store what it reads, so the look round-trips the same way in every format. A field the part doesn't state reads as Office draws it, the automatic look of chart style 2, as LibreOffice's oox chart importer reads it too: a label in the theme's `tx1`, which keeps a dark slide's chart text light; the background in the theme's `bg1` in a docx or an xlsx, and none in a pptx, where PowerPoint shows the slide through; and every line 0.75 pt of `tx1` at a 75% tint, but a line series 2.25 pt. The look has one series width, so it reads the first series' line. Office draws a line series three times as wide as its axes, so one stroke for both would draw an imported line chart's series at the axes' 1 px: that is why the series width is a field of its own. A column, bar or pie chart reads none. Many parts state none of it: Excel 2007 and 2010, openpyxl and LibreOffice write charts without a `c:spPr`. So a chart made in Office comes in with the look Office shows, and a re-import of Eigen's own part reads what the first import stored, since the writer always states all four fields. An axis Office draws no line along still shows its gridlines, so the stroke is the gridlines' line then. A pie has no axis line, so its stroke reads flat. A hatch, a dashed stroke and the sketch draw plain, and a gradient background draws as its middle color. Each chart so simplified counts once as `charts-simplified` (`chartLookSimplified`, [EXPORT.md](EXPORT.md#every-office-writer-counts-what-it-leaves-out)). The reader mirrors the gradient, reading a gradient as its middle color and a pattern as its foreground: an Office user gets a chart they can restyle rather than a picture of the look, the owner's ruling for all three formats. `c:spPr` can hold a dash, a pattern and a gradient, and mapping them is an open [CHARTS-TODO](CHARTS-TODO.md) row.

Eigen sizes a chart's text by its box (`chartFontSize` in `charts/context.ts`, the title `CHART_TITLE_SCALE` times it), and Office sizes it in points whatever the frame, at 10 pt when the part says nothing. So the part writes Eigen's sizes as `sz`, and its line widths, through `ChartFrame`: the box Eigen lays the chart out in and the EMU one of its px is in the file. A docx chart wider than the column shrinks to it, its text and lines with it, and `sz` stays within the 1 to 4000 pt Office accepts. A slide's px is half a page's, so a part without sizes draws a small Slides chart's labels at twice Eigen's size, and Office squeezes its plot to a strip. The reader divides a line's width by the same scale, so a stroke reads back in the host's px.

## A chart copies between apps with its numbers inline

⌘C on a chart in Sheets, Docs, Slides or Vector puts one chart item on the shared clipboard: the chart's parts as stored, its look and its box, which every host pastes as a live chart it can edit, not a picture ([CLIPBOARD.md](CLIPBOARD.md#a-chart-travels-as-its-spec-with-the-numbers-inline)). The data must be inline, since only the sheet a chart came from can read its ranges. So a sheet chart is read into inline data as it is copied, and only a paste back into the workbook it came from keeps its ranges ([SHEETS.md](SHEETS.md#a-selected-chart-copies-itself-not-the-cells-behind-it)). A doc's schema has no attribute for a newer build's part, so a paste into Docs leaves it out. The font travels in the spec, so a Vector chart pasted into Docs keeps Excalifont and its sketch. The copy writes the source cells' number format on `axes.y.labels.format`, so a percent column copied from Sheets ticks as 25% in Docs, Slides and Vector too.
