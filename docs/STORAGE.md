# Storage and Mounts

> **TLDR:** A Home is the per-owner object that holds an owner's databases and domain services (`apps/api/src/lib/home/`). Drive stores files through Mounts (`apps/api/src/lib/mount/`). A Mount is one storage root of an owner's Drive, with its own settings in the home's `settings.json`: a user has a default one, and a team has one per team drive. It is a `metadata.db` paths table over one storage backend, `local`, `local-key` or `s3` (`apps/api/src/lib/storage/`). Four things are not obvious from the code. On `local` a storage key is the name path, so every key-derived write holds the tree lock, one reader/writer lock over the mount's whole tree, and every rename takes it exclusively. Every storage read has a 30 s idle deadline, and a gone object answers 410 where an outage answers 503. Containers name users by email only, so they survive copy and restore anywhere. Folder sizes are a lazy cache, so a plain listing can write.

Drive is the file tree under every app. The Drive app shows it, WebDAV serves it to desktop clients ([WEBDAV.md](WEBDAV.md)), and every doc, sheet, deck, drawing, stickies board and chat lives in it as a container: a folder named like a file, such as `Notes.eigendoc`, that holds the document's databases and media ([ARCHITECTURE.md § Eigen file types](ARCHITECTURE.md#eigen-file-types)). A request reaches a file through four layers: the route, `SharedDrive`, which checks access when the caller is not the owner ([ACL.md](ACL.md)), `Drive`, which spans the owner's mounts, and the `Mount` ([ARCHITECTURE.md § Drive Architecture](ARCHITECTURE.md#drive-architecture)).

The idea underneath is that the mount's paths table is the tree and the backend holds only bytes. A row gives a file its name, its parent, its type and its sharing. The storage key is derived from the row: the name path on `local`, the id on the other two backends ([§ A mount is a paths table](#a-mount-is-a-paths-table-over-one-of-three-backends)).

Drive's **Recent files** page lists the paths a user lately opened or was notified about, wherever they live. Each user's own home keeps only which path and when, and every load asks each path's owner whether the user may still see it, so a name is always current and a lost file never shows ([§ Recent files stores only which path and when](#recent-files-stores-only-which-path-and-when)).

## A Home is loaded on demand and dropped when idle

`getHome(ownerId)` (`apps/api/src/lib/home/get-home.ts`) builds the Home on first use and caches it. A Home closes when nothing holds it and its last request is longer ago than its idle time (5 min for a user, 30 for a team). A request is a `getHome`, and the Home keeps its time (`Home.touch`). A hold pauses the closing, and a release only checks the rule again (`Home.closeWhenIdle`): it never starts a fresh idle, so a holder that comes and goes, such as an upload that retries on a failing bucket, never keeps a Home open. So when the last tab closes, its stream lets go, and a Home whose last request is long ago closes at once. A socket's document lingers a minute first and holds the Home meanwhile, so that Home closes when the linger ends. A tab that reconnects calls `getHome`, which is a request. `openHome` is `getHome` without the request, for background work such as a backup, which holds the Home while it captures like any other holder: a Home nobody requested closes when the capture lets go. Reading a part such as `home.drive` is no request either, so code that keeps a Home across long awaits holds it (`withHomeHeld`). Whatever may outlast the idle calls `hold()`: a backup capture, an open event stream ([SSE.md](SSE.md#a-stream-holds-its-home-and-ends-when-it-closes)), a collab socket ([COLLAB.md](COLLAB.md#home-replacement-closes-every-socket)), a collab document while it lingers ([COLLAB.md](COLLAB.md#a-document-lingers-after-the-last-unsubscribe)), a live WebDAV lock ([WEBDAV.md](WEBDAV.md#locks-live-in-memory)), an s3 upload on the wire ([SYNC.md](SYNC.md#an-upload-on-its-way-holds-its-home)) and a long request. A long request is one that switches off the server's idle timeout, such as a Drive copy, convert, export or import, a calendar, contacts or mail import and a WebDAV COPY, or a Drive upload or a WebDAV PUT, whose body streams in. It runs inside `withHomeHeld` (on `Home`, with forwarders on `Drive` and `SharedDrive`), which holds every Home it works in from its access check until it answers, the target Home of a copy into another owner's drive included. An upload or a PUT checks write access first, so a user who may not write never holds another owner's Home. An import from another owner's file holds that owner's Home while it reads the file. Without the hold, a request that outlasts the idle with nothing else touching that Home finds its databases closed under it, a 500. A holder that must stop when the Home closes anyway, such as a stream, passes a callback that the close runs before the parts close. A closing Home refuses a new hold with a 503, because that holder would never hear the close. A team home gets the longer idle (`TEAM_HOME_IDLE_MS` overrides it), because no event stream holds it, only a socket on one of its documents. `evictHome` closes one on purpose (user deletion, backup restore). A team home closes itself when an admin gives one of its drives new storage or switches one on or off (`TeamHome.updateMount`), because a Mount binds its storage when it opens: the next request opens the home on the saved settings, and its open documents save their edits as they close and their tabs reconnect. A new name or quota reaches the live mount and keeps the home. `shutdownAllHomes` all of them at exit, and while it runs `openHome` refuses every home with a 503, so nothing builds one again during the shutdown.

| Home | Folder | Services |
|---|---|---|
| `UserHome` | `data/home/{userId}/` | Drive, Mail, Contacts, Calendar, Notifications |
| `TeamHome` | `data/team/{teamId}/` | Drive, Calendar ([ORGANISATIONS-AND-TEAMS.md](ORGANISATIONS-AND-TEAMS.md)) |
| `OrgHome` | `data/org/{orgId}/` | Only its filesystem |
| `GuestHome` | `data/guest/{userId}/` | Drive, Notifications ([GUEST-ACCESS.md](GUEST-ACCESS.md)) |

A getter for a part the Home lacks, such as `mail` on a guest's or `notifications` on a team's, throws `ApiError(404)`, so a route that reaches for it answers 404 instead of crashing. Code that may meet any kind of home checks first, through `hasCalendar` or `instanceof TeamHome`. A notice goes through `Home.notify`, which drops it on a home without a notification center. The home relay hands a team's notices to its members instead.

A Home serves its own owner. Another owner's data goes through `home-relay.ts` ([SCALABILITY.md](SCALABILITY.md)).

## Every owner's data lives under one folder

```
data/home/{userId}/
├── settings.json
├── mounts/
│   ├── shared.db           paths others shared into this home (ACL.md), and Recent files
│   └── {mountId}/          metadata.db, data/, thumbs/, tmp/, staging/ (s3 only)
├── eigen.mail/             mail.db, Maildir/
├── eigen.contacts/         contacts.db, avatars/
├── eigen.calendar/         calendar.db
└── eigen.notifications/    notifications.db
```

The names come from `PATHS` in `apps/api/src/lib/config/paths.ts`. Mail, Contacts and Calendar reach their folders through `home.fs`, a `LocalFilesystem` with the atomic and durable write family those domains need. Contacts and calendar events live as BLOBs in their databases, with columns projected from them ([CONTACTS.md](CONTACTS.md), [CALENDAR.md](CALENDAR.md)). `staging/` sits outside `tmp/` so the stale-temp sweep can never purge an upload the bucket has not acknowledged ([SYNC.md](SYNC.md)). A JSON file such as `settings.json` is written through `writeAtomic`, which stages a dotted `.tmp-` copy beside it and renames it over. A crash between the two leaves the copy, so `Home.init` sweeps the home's root of copies older than a day (`STALE_TEMP_MAX_AGE_MS`) before it loads the settings; a younger one may be a write still in flight.

## Containers name users by email, never by id

A container (`.eigendoc`, `.eigenchat` and their siblings) is the portable unit. It is copied, moved and version-restored as a self-contained set of files. So its databases reference users by email only: chat authors, comment authors, assignees and mentions. Home-level databases (`metadata.db`, `contacts.db`, `calendar.db`, `notifications.db`) sit beside their owner and may hold user ids. Because containers carry no ids, a copy or a backup restore keeps every user reference intact on any server and in any id space.

## A mount is a paths table over one of three backends

Every Drive row lives in the mount's `paths` table (`apps/api/src/lib/mount/schema.ts`). The bytes live in a `StorageBackend` (`apps/api/src/lib/storage/types.ts`):

| Type | Where a file's bytes live |
|---|---|
| `local` | `data/` under the file's name path, so the tree on disk mirrors Drive |
| `local-key` | `data/{id}.{ext}`, flat |
| `s3` | `{prefix}/{id}.{ext}` in a bucket: a plain file is PUT in its request, a container database is written behind by the upload queue ([SYNC.md](SYNC.md)) |

An id key never moves, so on `local-key` and `s3` a rename, a move or a trash changes only the row. On `local` the same operations rename files and directories on disk. That difference drives the [tree lock](#on-local-a-key-is-a-name-path-so-renames-lock-the-whole-tree) and the `.trash/` directory ([SOFT-DELETE.md](SOFT-DELETE.md#only-local-moves-bytes-into-trash)).

A name check compares as the unique index on names does, with SQLite's `LOWER()`, which folds ASCII only. A case-insensitive disk such as APFS also treats non-ASCII case pairs as one file, so on `local` a non-ASCII name is compared under `foldName` too (`apps/api/src/lib/mount/names.ts`). An ASCII name whose stored twin is not ASCII, such as `strasse` beside `straße`, still passes the table, and the disk check of the write catches it ([SOFT-DELETE.md](SOFT-DELETE.md#on-local-the-bytes-move-first-and-what-is-on-disk-decides-after-a-crash)).

`read()` returns a `StorageFile`, a lazy `BunFile` or `S3File` that holds no bytes yet. A local file goes into a `Response` as is, which keeps serving zero-copy. An `S3File` goes in as `file.stream()`, since it takes no `ResponseInit` options. Both local backends resolve every key through `resolveWithinBase` (`apps/api/src/lib/core/path-utils.ts`), and `S3Storage` validates key segments, so no key escapes its base.

No write makes a `parentId` loop, so only a hand edit of `metadata.db` can make one. A backup leaves such rows out of its archive. The walks of the tree don't guard against one, so a request that touches it hangs instead of answering 500, and a walk that never awaits, such as `collectDescendantIds`, holds the whole API with it.

No write puts a row more than 256 levels below its mount's root either (`MAX_FOLDER_DEPTH` in `apps/api/src/lib/mount/names.ts`). A create, move, copy or restore checks it in the transaction of its row write, beside the trash check (`targetFolderErrorInTx`), counting the target folder's depth plus the levels the moved row's subtree adds; a copy writes row by row, so its first row past the limit fails it and the half-built copy is removed. A tree already deeper stays readable but takes no new row past the limit.

A file's `mimeType` is set when it is created: the web upload stores what the browser sent, and a WebDAV create derives it from the name (`Bun.file(name).type`). A rename, from the web app or a WebDAV MOVE, keeps it in step with the name: when the new name's derived type differs from the old name's and is not `application/octet-stream`, which is Bun's answer for a name it doesn't know, the same row write sets it (`Drive.changePlace`). So `photo.bin` renamed to `photo.png` gets its icon and preview and shows under All images, and a rename to an unknown or missing extension keeps the type. The thumbnail and the search text were made for the old type, so the rename makes both again as an overwrite does: it hands the thumbnail to the mount's background jobs and marks the row for the reindexer. The thumbnail job downloads the bytes itself (`thumbnailInBackground`), so a rename of a large file on `s3` answers at once, and a failed download only logs, after the rename, its history row and its sharing push are done. The ETag is the content hash and does not change. Folders and Eigen documents are never retyped, as their type is what they are. Nothing converts existing rows: a file renamed before this keeps its old type until its extension changes again.

## A local write lands whole, by a rename out of `tmp/`

`LocalStorage.write` (`apps/api/src/lib/storage/local-storage.ts`), the one write of both local backends, never writes into the file at its key. It writes the bytes to a side file in the mount's `tmp/`, fsyncs it, and renames it over the key. A reader that has the file open keeps the old bytes to their end, and one that opens it after the rename gets the new ones, so no reader sees a short or mixed file and none needs a lock for that. A process killed during a write leaves the key as it was and a side file in `tmp/`, which the stale-temp sweep removes at the first `Mount.init` an hour or more after the write; a failed write removes its own. The rename needs `tmp/` and `data/` on one filesystem, which they are as two folders of the mount's own folder. `apps/api/src/test/storage/storage.test.ts` pins this.

One local file is still written in place: on `local-key` a document's database is the stored file itself, which SQLite opens and writes ([§ Every storage read has a 30 s idle deadline](#every-storage-read-has-a-30-s-idle-deadline)).

## Writes to one row serialize on its path lock

A write to an existing row runs under `Mount.withPathLock(pathId)`: an overwrite, a rename or move, a trash, a restore or a permanent delete from the trash, a version snapshot on the container, the chat restore. That delete locks the item it deletes, so what lies under a deleted folder goes without its own lock. A row a document owns goes without its own lock too: a version prune and Delete history run under the container's lock, and a sweep of a document's parts takes no path lock. The path locks and the tree lock below belong to the mount's folder, not to a `Mount` object, so a backup's own `Mount` of a disabled mount and the one the next home builds after an enable wait for each other. A create has no row to lock yet. On `local` it takes a path lock on its folder and name instead (`withCreateLock`), because two creates of one name would write to one name path: the second waits, finds the first one's row and answers 409 before it writes. Off `local` each create writes to its own id key, and the partial unique index on `(parentId, LOWER(name))` over untrashed rows closes the race between two creates of one name. The loser gets a 409 and removes the object it wrote. Off `local` no lock keeps a folder's permanent delete out of a create, so the foreign key on `parentId` refuses a row under a deleted folder: that create answers 404 and removes its object too. A move or a restore into a folder deleted meanwhile answers the same 404 (`rethrowPathWriteError`). So does one into a folder trashed meanwhile, which that folder's permanent delete would take with it: the move or restore checks every folder from its target up to the root in the transaction of its row write (`targetFolderErrorInTx`). A rename or move on `local` checks its target name again under the exclusive tree lock, and what is on disk there ([SOFT-DELETE.md](SOFT-DELETE.md#on-local-the-bytes-move-first-and-what-is-on-disk-decides-after-a-crash)), before its disk rename, which would replace a sibling's bytes at the target. A create checks its name under the shared tree lock, right before its write, and on `local` what is on disk at its key, so one queued behind a rename, move or restore that took the name answers 409 and writes nothing.

## On `local` a key is a name path, so renames lock the whole tree

`LocalStorage.write` makes any missing folder above its key. So a save that resolved its key before a folder rename would rebuild the old folder and orphan the save. A `local` mount therefore has one reader/writer lock over its whole tree (`Mount.withTreeShared` / `withTreeExclusive`, `apps/api/src/utils/rw-lock.ts`). On `s3` and `local-key` both methods pass straight through.

- **Shared:** every write whose key comes from the paths table, from the key resolution through the storage call and the row write, so the row and the bytes agree. That covers file writes and creates, folder creates and a managed database's sync.
- **Exclusive:** every storage rename of a file or a directory and every removal of a row and its bytes: rename and move, trash, restore, folder delete and file delete.

A file delete is exclusive because a create of the same name writes the same key as soon as the row is gone. A delete beside it would unlink the new file's bytes, and an overwrite still running would write over them and then find no row. So on `local` no row disappears during an overwrite, whose shared lock runs from its key through its commit. Off `local` the tree lock is no lock, and a file or folder delete can take the row during an overwrite. The key is that row's alone, so `commitOverwrite` removes the object it wrote and answers 404. A file delete on `local` waits for the shared holders in flight and the later ones wait for it, as for a trash: those holders copy bytes already on this server, so the wait is a disk copy at most.

Waiters are served in arrival order. A rename queued behind a stream of saves runs after the saves in flight and before the saves that arrive after it. The lock order is path lock, then document-db slot, then tree lock. A path's `acl:` chain (`Drive.runInOrder`) comes before all three. Only an ACL change (`updateACLDelta`) and a removal (`removePath`: a trash, a failed copy's cleanup, the source of a WebDAV move over a file) run in it, each holding its item's chain while it takes its mount locks. A create's lock on its name is taken right before the tree lock, and its holder takes no slot, so a version snapshot at a tick or a close takes one while it holds the slot: it waits on the create lock of its `versions/` folder or its snapshot file. That is the only path lock a slot holder waits on. The snapshot only try-locks its container, so a slot holder never waits on a row's path lock. A tree-lock holder takes no further lock, because a shared region inside a shared region deadlocks once an exclusive is queued. A reader that holds a container database takes no path lock while it holds, because a close under that lock waits for it ([DATABASE.md](DATABASE.md#a-reader-holds-a-container-database-only-while-it-runs)). Most reads take no lock, and one that races a move answers a transient 404, a document-db open a 503. A Drive copy and the download of a document or a version into a temp file read under the shared tree lock. A backup's copy of a plain file holds the shared tree lock until the file is open and takes no path lock ([BACKUP.md](BACKUP.md#a-home-archive-holds-every-database-file-and-auth-row)). `apps/api/src/test/storage/overwrite-ancestor-move.test.ts` pins the races.

## Every storage read has a 30 s idle deadline

Bun's `S3Client` takes no timeout and no signal, and gives up on a silent request only after about 360 s. Eigen's own bound is `STORAGE_TIMEOUT_MS` (30 s, `apps/api/src/lib/storage/deadline.ts`). `S3Storage` races `exists`, `size`, `list` and `delete` against it. An `exists` or `size` that times out or fails answers 503, and only a missing key is `false` or `null`. A timed-out `delete` returns `false` like any failed delete.

Every storage read the server consumes itself runs through `streamStorageFile`, the storage form of the one stream loop `consumeStream`. A read that delivers no byte for 30 s is cancelled with a 503.

On a warm local file `consumeStream` never gives up the event loop. One kind of read relies on that: on `local-key` a document's database is the stored file, and SQLite writes it in place from the event loop, at a checkpoint. A Drive copy of an open document and the raw copy of a closed one for a version or a backup read that file as bytes, so a turn of the loop during the read could let a checkpoint in and tear the copy. Every other local file lands by a rename ([§ A local write lands whole](#a-local-write-lands-whole-by-a-rename-out-of-tmp)), so its readers could yield. The cost of not yielding is that a read holds the API for its length ([ROADMAP.md](ROADMAP.md)). Only the backup passes `yields`, which gives a turn every 2 MB, and only for a plain drive file, never for a document's database.

Most reads also pass the mount's `downloads` signal. `closeAllDatabases` and `Drive.destruct` abort it first, so no teardown waits on a stalled download or extraction read. Copy and version snapshots read without it, because a close-time snapshot runs after that abort.

A file served to a client (`/download`, `/embed`, WebDAV GET) is the exception. Its stream goes straight into the Response, so a stalled body there is bounded only by the server's 200 s `idleTimeout`. It holds no lock and no Home while it waits.

## A mount's background jobs end before its databases close

A mount runs some work that no request waits for: the thumbnail after an upload or an overwrite, and the purge of expired trash that `Mount.init` starts ([SOFT-DELETE.md](SOFT-DELETE.md#expired-trash-is-purged-only-when-a-home-loads)). Each one starts through `Mount.runInBackground`, which keeps it in one set and logs its failure. `closeAllDatabases` aborts the `downloads` signal, closes the reindex queue and then waits for that set (`Mount.backgroundDone`) before any database closes, so a job that runs by then never writes to a `metadata.db` its Home has closed. A request still in flight after that wait can start one more job, which then fails against the closed database and is logged. It loses no data, so it is accepted. A job is not guarded one by one: whatever a mount starts in the background goes into the set, and `init` leaves no timer behind.

A long job reads the `downloads` signal to stop early, as the purge does between two items. A short one, such as a thumbnail, is only waited for. The wait has no deadline of its own: the thumbnail worker's timeout bounds a thumbnail, and the storage deadline bounds each delete of a purge. The reindex queue keeps its own close with a deadline, because an extract can hang. `apps/api/src/test/mount/mount-background.test.ts` pins this.

## An S3 read tries three times before it answers 503

Hetzner Object Storage sheds load with a 503 `SlowDown`, and the same request a second later succeeds. Bun's `S3Client` never retries a read (its `retry` covers only multipart parts), so one throttled HEAD failed a whole docx export. `retryStorageRead` (`apps/api/src/lib/storage/deadline.ts`) gives `exists`, `size`, `list` and every `streamStorageFile` GET three attempts, about 200 ms and then 800 ms apart, with jitter. It retries a throttle, a 5xx, a refused or closed connection, and Bun's `UnknownError`, which is all a HEAD reports for any status but 200 and 404, a 403 included. A missing key and a definite refusal (`NoSuchKey`, `AccessDenied` in a GET body) fail at once. Writes are not retried: a whole-object PUT could be replayed, but the upload queue has its own backoff and orphan accounting, and on a versioned bucket each replay adds a version. Retrying the direct PUTs is in [ROADMAP.md](ROADMAP.md).

A HEAD and a list share one deadline over all their attempts: `storageRead` runs them inside the 30 s of `withStorageDeadline`, whose signal stops a wait when it fires. Each GET attempt has its own idle deadline, and a GET that stalled into it is not retried, so a GET whose attempts each fail late can take up to three deadlines. A GET retries only while no byte has reached the caller, since a second GET would hand it the first bytes again, and the mount's `downloads` signal stops its wait. The last failure keeps its 503. `apps/api/src/test/storage/s3-read-retry.test.ts` pins this.

## A gone object answers 410, an outage 503

Only the GET body tells a missing object from a sick bucket: `NoSuchKey` on S3, `ENOENT` on disk (`isMissingObjectCause`). `Mount.downloadKeyToTemp` answers that with 410 (`storageGone`), every other storage failure with 503, and a local one (the `tmp/` write or rename) with 500, so a full disk does not read as an outage. A 410 tells the client to stop retrying. The collab tab retries a 503 or a 500 ([COLLAB.md](COLLAB.md#each-close-code-tells-the-tab-what-to-do)), an HTTP client only a 503.

A container database's open reads the freshest copy first: the crash temp, then the staged copy of an unacknowledged upload, then the stored object ([SYNC.md](SYNC.md)). So a 410 means no copy exists anywhere, and a version restore is the way back. On a `local-key` mount the open does not GET but stats `data.db`, and answers 410 only on `ENOENT`.

## Creating a container is all or nothing

`Drive.create` (`apps/api/src/lib/drive/drive.ts`) creates the container folder, then provisions it (`ChatRoom.create` or `CollabDocument.create`, plus the comment row a card chat seeds). When provisioning throws, `mount.deletePath` removes the row and the error propagates. That delete sends no SSE, because the row was never announced. On a remote mount it cancels the container's queued uploads, so a staged PUT cannot bring the object back. The name is free again, so an immediate retry with the same name starts clean. A rollback that itself fails is logged and the container stays: a row nobody has seen, which holds the name and fails every open. No scan finds it: the orphaned-container scan is open work in the "Data integrity + verified backups" row of [ROADMAP.md](ROADMAP.md).

The stem passes the mount's name rule (`validateName`, `apps/api/src/lib/mount/names.ts`) before the extension goes on, so an empty stem cannot become a nameless `.eigendoc`. Names are stored NFC. Every dedup (copy, upload, chat `dedupeName`, trash restore) compares in NFC, and `getUniqueFileName` trims the stem so the ` (n)` suffix still fits the 255-byte limit.

## A create that timed out may still have landed

Slow storage can make a create look failed when it is not: the request times out or answers 503 while the server keeps writing, and the row lands seconds later. So the two create hooks (`useCreateDriveItem` and `useCreateChatRoom`) post through `createWithReconcile` (`packages/lib/src/core/drive/reconcile-create.ts`) with a 15 s timeout.

Before posting, the hook lists the folder once and keeps the ids it sees. After an abort, a network error or a 5xx it polls that listing for the name it sent. A row matches when it has that name and an id the snapshot did not hold. That means created by this request or by a concurrent create of the same name, with no clock on either side. A same-name sibling that existed before is in the snapshot, so it never passes for ours. A match resolves the mutation as a success, and a miss throws `CreateUnconfirmedError`, whose message is the toast.

- A 4xx is never reconciled: it is the server's definitive no (409 duplicate name).
- A failed snapshot skips reconcile, since there is no honest anchor.
- The chat wizard can create without a parent. The route then resolves the lazily created `chats` folder, which no client endpoint names, so the hook polls the mount's chat listing instead.
- A chat create through `dedupeName` lets the server suffix the name (`Name (2)`), so no poll could find it. It passes no `expectedName` and runs no polls. An indeterminate failure still becomes `CreateUnconfirmedError`, so a chat that may well exist reads as slow storage rather than a raw timeout.

`packages/lib/src/test/core/drive/reconcile-create.test.ts` pins the contract.

## Folder sizes are a lazy cache, so a listing can write

A folder row caches its recursive size in `paths.size`, and `NULL` means stale. A mutation does not recompute. It NULLs the whole ancestor chain (`invalidateSizesFrom`, or `invalidateAncestorsOf` for a content write). That runs once the mutation has committed, so a failure there is logged and leaves a stale total, never a 500 for a write that happened. The next read that hydrates the folder (`toDrivePath`) recomputes the subtree bottom-up in one transaction and writes the totals back, reusing every descendant total still cached.

So a GET can write, which matters for any read-replica idea. The first listing after a large move or delete pays the recompute, and every later read is a column read. A trashed item hangs under the mount root and is left out of the totals ([SOFT-DELETE.md](SOFT-DELETE.md)).

## Version snapshots live inside the container

A container that opts in (collab documents and chats, the `snapshot` key in their database config) keeps file-level snapshots of its `data.db` in `<container>/versions/<iso-ts>.db` (`apps/api/src/lib/versioning/`). `ManagedDatabase` takes one every 100 writes and on close, and each snapshot prunes by the retention policy. The policy (`DEFAULT_RETENTION`) keeps the newest version in each of the 24 most recent hours, 7 days, 4 weeks and 12 months that hold one, so at most 47. Each tier counts the hours or days the document was edited in, not the clock's, so a document worked on in bursts keeps an hourly trail of its sessions. A bucket is the version's own time divided by the interval, so the buckets never shift, and the prune after every snapshot never swaps a finished hour's version for a newer one. A database adopted from a crash temp ([SYNC.md](SYNC.md#a-crash-temp-is-adopted-and-re-synced)) owes its close a snapshot even with no new write, because the fresh connection counts no change for the recovered tail.

- A manual save and the pre-restore snapshot block on the container's path lock, because an explicit user action must never skip. They flush first, then read the live db, or with none open what an unclean shutdown left (the crash temp, or on `local-key` a stored file with its `-wal`, which the read folds in), then the staged copy, then the stored object (`stageManagedDbCopy`). A backup reads in the same order.
- The timer and close path try-locks and skips when the lock is held (`trySnapshotContainerDataDb`). It runs inside a close that a lock holder may be waiting on, and a skip loses one history entry, never bytes. A tick that skipped tries again on the next one. It reads the staged copy first, then the live db, then the stored object: the sync just before it staged those bytes, and reusing the copy saves a second `VACUUM INTO`. A close's snapshot never reads the crash temp, because that close removes it.
- A restore first copies the chosen snapshot to a temp file, since the pre-restore snapshot prunes and could delete it. It then replays the snapshot into the live Y.Doc for a collab document ([COLLAB.md](COLLAB.md#a-version-restore-rewrites-an-open-document-in-one-transaction)) or overwrites the chat's `data.db` bytes under the same row (`replaceContainerDataDb`): one slot call waits for a chat request still reading the db, closes it, removes its crash temp and writes the bytes, through the upload queue on `s3` and as a fresh file on `local-key`, whose `-wal` and `-shm` go with the old one. No lock is held across the steps.

A version keeps the media it names: as long as a saved version names a file, a restore can bring it back, so nothing deletes a file while versions exist. Only Delete history and a copy run the sweep that frees the rest ([MEDIA-REFERENCES.md](MEDIA-REFERENCES.md#a-file-stays-until-delete-history-or-a-copy-and-then-only-while-the-state-names-it)).

## Delete history deletes the versions and then sweeps at once

Delete history (`DELETE /drive/:ownerId/:mountId/file/:pathId/versions`, `Drive.deleteVersions`) deletes the `versions/` folder of the document and of each comment thread in its `chat/`, each under the path lock its snapshots take, so no version lands in a folder while it goes. Only an owner of the drive may (`requireDriveOwner`), as for a delete forever in the trash, because nothing brings a version back: a shared editor gets 403. The document's history gets a `versions-deleted` entry, as a restore gets `version-restored` ([FILE-HISTORY.md](FILE-HISTORY.md)). Then it sweeps the document at once, open or not, so what only the versions named goes in the same request, except the media and threads of the last 72 hours ([MEDIA-REFERENCES.md](MEDIA-REFERENCES.md#the-sweep-reads-the-state-once-and-deletes-nothing-more-after-a-failure)). A document only ever shrinks this way: no sweep runs on its own.

## A person only adds new files and threads inside a document

A document's parts, such as its `data.db` and `comments.db`, its `versions/` folder and each version in it, its comment threads and the files in its `media/`, change only with the whole document. A database renamed or trashed on its own breaks the document, a version moved out leaves a gap in its history, and a thread trashed on its own would leave the sweep a thread that is neither live nor gone. So a person never renames, moves, trashes or overwrites anything inside a document, the owner included, and that covers an existing file in `media/` too, since the document's versions name it. Server code that removes a part, such as `ChatRoom.deleteMessage` with a deleted message's attachments or the sweep, deletes it for good through the mount instead.

A person adds only two things inside a document: a file directly into the `media/` folder directly under a document, such as an image pasted into a doc or a chat attachment, and a thread directly into a collab document's `chat/`. Any other add is refused, such as a folder, a file beside `data.db` or anything in `versions/`, so nothing a person makes can take the name of a database or of `versions/`. Only something new is added: an existing path is never moved into a document, its `media/` and `chat/` included, because it could never leave again and nothing in the document names it, so the next sweep would delete it. A thread is a document itself, so its own `media/` takes attachments by the same rule. Outside documents nothing is checked.

`refuseDocumentWrite` (`apps/api/src/lib/drive/acl.ts`) is the one rule, a pure function over a breadcrumb, and every refusal is the same `423` with one message, the status WebDAV answers for a write it refuses. `Drive` applies it on the lookup each write already does: `personParent` for a write that adds a new child, such as a create, an upload or a copy, and `personPath` for a write that changes a path, such as a rename, a trash, new bytes or WebDAV dead properties. A move changes a path, so it also checks the path as it would sit in its new folder (`personMoveTarget`). So no route or protocol has a second check to forget, and WebDAV refuses with the lock and access checks first. Every call names its user.

A copy writes a whole new document, its databases, `media/` and `chat/` included, which the rule refuses to a person. So a copy applies the rule once, to the destination folder, and then writes the tree through `Mount.copyPath`. Server code that builds a document part by part, such as the demo seed, writes through the mount. `apps/api/src/test/drive/container-write-guard.test.ts` and `apps/api/src/test/webdav/container-guard.test.ts` pin the rule.


## Copy goes anywhere, a move stays in its mount

One writer makes every copy (`copyPath` in `apps/api/src/lib/mount/copy.ts`), whether it stays in its mount or lands in another mount or another owner's drive. It lists the whole source tree first (`listCopy`) and writes only that list. A walk that listed each folder as it reached it would copy its own output: a move of the target into the source while the copy runs, or two copies in opposite directions between two drives, would feed it new folders until the disk filled. The target's mount writes the list and reads each file through the source's mount, so a copy that stays in its mount is the case where both are one. That is why a copy is the same wherever it lands: every path it makes gets a `copied` history row naming its source, a document is marked for the search reindexer, and open tabs and watchers hear of it once, for its top, when it is whole. The copy route calls `Drive.copyPath` on the source's drive, which hands the path to the target's `Drive.receiveCopy`, so the drive that gets the copy checks, lists and writes it. WebDAV COPY calls `Drive.copyPathOver`, which stays in one mount. A byte copy of a container is a valid independent document, because its internal children reference each other by name, not by path id. The listing flushes each document's open `data.db` and `comments.db` first, so the copy has the latest edits and comments, and leaves `versions/` behind, so the copy starts with a clean history. A copied file keeps the source's media facts and its thumbnail, which is copied and never made again, so a source without one gives a copy without one. `originalName` and the WebDAV dead properties stay with the source.

A copy writes every part of a document as bytes, and then sweeps each document it made with no grace (`sweepCopy`). So the copy holds what its state names and nothing else, such as no image only a version named and no thread of a deleted comment, while the source keeps everything ([MEDIA-REFERENCES.md](MEDIA-REFERENCES.md#a-file-stays-until-delete-history-or-a-copy-and-then-only-while-the-state-names-it)). The sweep deletes only a part the copy wrote: the writer returns the id of every path it made and of each document among them. A listing of the target folder shows the copy while it lands, so an image, a comment or a document someone adds to it before the sweep runs stays. A sweep that fails only logs and leaves the copy whole, as the copy itself succeeded.

The copy route (`POST /drive/:ownerId/:mountId/path/:pathId/copy`) only parses and calls `Drive.copyPath`, which holds the source's home and passes the path on. The target's `Drive.receiveCopy` holds its own home and gives the copy a free name. `Drive.copyPathOver` takes the name as given instead, because a WebDAV COPY names its destination: what holds that name is replaced only after every check, so a refused COPY leaves it. A folder or document in the way goes to the trash before the copy is written, so a create that takes the freed name in between makes the COPY a 409 and leaves it in the trash, where it can be restored. A file under a file is kept and takes the bytes, as `Drive.movePathOver` does for a WebDAV MOVE, and anything else goes to the trash ([WEBDAV.md](WEBDAV.md#an-overwrite-keeps-a-file-under-a-file-and-trashes-anything-else)).

Every free name picked before a create (a copy, an upload, a trash restore, a chat the wizard names) goes through `withFreeName` (`apps/api/src/lib/drive/naming.ts`). In one step with no `await` in it, it reads the folder's names, skips the names of the creates still running in that folder, and reserves the name it picks in one map keyed by owner, mount and folder id. The step can be one because the mount reads its SQLite table synchronously (`Mount.hasLiveChild`, `Mount.liveChildNames`), so no other create lands between the read and the reservation. The reservation lasts until the create ends, and by then its row is in the folder for the next read to see. So creates of one name into one folder at once each get their own name, however many there are, and a name trashed, moved or deleted is free again at once, even while other creates run. Nothing retries and nothing waits: a reservation is a set entry, not a lock, so uploads and copies into one folder all run in parallel. A create that fails gives its name back.

An upload in the web app also stores the name it came with, before any numbering, as `details.originalName` (`finalizeUpload`). That name counts only inside a document, such as a chat's or a doc's `media/`, where nobody sees or renames the stored name: two `photo.png` attachments both show and download as `photo.png`. Every other file downloads and attaches to mail under the name Drive shows, whatever `originalName` its row carries (`downloadName` in `apps/api/src/lib/drive/serve-file.ts`, which reads the breadcrumb only for a row that has the field). So a rename or a move never has to clear it, and a create that keeps its name, such as a WebDAV PUT, stores none.

One map is enough because the API is one process. It holds the data dir's instance lock (`holdInstanceLock`), so every upload and copy on the server passes through that map. A writer that names its item itself, such as a new folder, a WebDAV MKCOL, PUT or LOCK ([WEBDAV.md](WEBDAV.md#put-stages-the-body-before-the-row)), a rename or a move, reserves nothing and answers 409 when the name is taken (`nameTakenError`). It can still take a name a create reserved, and then the reserving create gets that 409 instead: an upload in the web app that races a WebDAV PUT for one name can be a 409, not a numbered file. The losing create leaves no bytes: on `local` its create lock makes it fail before the write, and elsewhere it fails before the write or removes the object it wrote. A copy of a folder into its own subtree is a 409 from the route and from WebDAV alike, as RFC 4918 asks. A move makes the same check inside `Mount.updatePath`, in one synchronous transaction with the row write, so two opposite moves cannot form a cycle between check and write. A cycle would spin every recursive walk over the tree.

Both entries run the same checks before anything is written (`checkedCopyTree`), so a REST copy and a WebDAV COPY meet the same ones. Every copy must fit the target's free space (`enforceMountQuota`, 507), counted by `copySize` over the listed tree, so without the `versions/` of each document inside, since the copy leaves those behind. A file must also fit the per-file upload cap (`enforceMaxUploadSize`, 413), as an upload must ([QUOTA.md](QUOTA.md#507-is-a-full-budget-413-a-file-too-large)). Each check runs once per copy. `SharedDrive` checks the access: read on the source in `copyPath` and `copyPathOver`, read and write on the target folder in `receiveCopy`, and write on it in `copyPathOver`, whose WebDAV handler has resolved the folder under read access. So a folder shared write-only takes no copy. The target's `Drive` checks the rest, against its own owner's limits. Write access and the document rule come before the source is listed, so a copy the folder refuses flushes no document and reads no limit of the target's owner.

A folder or document copy creates its top folder first and then copies the children, so a child that fails, such as one whose bytes are gone, would leave a half-built tree, and every retry another. So a copy that throws removes its top folder (`deleteFailedCopy` in `apps/api/src/lib/drive/trash.ts`) before the error goes on. Nothing is kept first, because the source is untouched. Others can put their own paths in the half-built folder while the copy runs, as a listing of the target shows it. The walk records every path it creates, and `deleteFailedCopy` deletes the folder for good only when everything in it is one of those and nobody shared any of it since. It skips the trash then, because trashed bytes still count against the target's quota and a writer copying into another owner's folder cannot empty that owner's trash, so every failed retry would fill a stranger's drive. Anything else in the folder sends it to the trash like any delete, so a file someone moved or uploaded there can be restored. The check and the delete are not one step, so a create that passed its folder check before the cleanup began can still land and be deleted for good with the folder, an edge case the owner accepted. Either way the cleanup takes the lock, WebDAV-lock and document handling of `Drive.deletePath`. A crash mid-copy still leaves the partial tree, which the owner accepted too.

The copy route and WebDAV COPY send nothing while a deep tree copies, so both lift the server's 200 s `idleTimeout` for their request (`server.timeout(request, 0)`). Otherwise the client would see an empty reply and retry into a duplicate tree.

The client copies, moves, trashes or permanently deletes a batch with one route call per item, all at once (`settleEach` in `packages/lib/src/core/drive/hooks/writes.ts`). When only part of it goes through, the hook throws `PartialBatchError` with what went through (for a copy, the new copies) and the items that failed, and a dialog such as the move picker stays open on the failed ones, so a retry sends only those. An item sent again would go wrong: the route gives each copy a free name, so a source would land a second time, a moved item would get a new modified time and history entry, and a trashed one answers 404. `useCopyToMediaFolder`, for a document's or a chat's media, shows that error's toast and returns the copies that landed, so the editor still inserts them. The error's message ends with the first failure's reason. When every item fails, the hook throws the first server error instead, so the toast says why, a card's Save stops, and a yes/no dialog closes on a refusal as it does for one item.

A move never crosses mounts. It would change the row's owner, mount and id, and that breaks shares, links and history.

## Recent files stores only which path and when

The list lives in the `recent_paths` table of the user's own `shared.db` (`apps/api/src/lib/drive/shared-schema.ts`, schema version 2 in `db-config.ts`): one row per owner, mount and path, with `lastActivityAt` in seconds. It holds no name, type or reason. A stored name would go stale on a rename and would keep showing a file the user lost access to, so a load reads everything else from the path's owner. `apps/api/src/lib/drive/recent.ts` is the only file that reads or writes the table. `shared.db` is already in every backup, so the table needed no registration. A team home gets the empty table and nothing writes to it. A guest home can collect rows from notifications, and nothing reads them, because the route refuses a guest.

## The server records an open where it already serves one

Two things write a row: an open and a notification ([§ A notification about a path adds it too](#a-notification-about-a-path-adds-it-too)). An open is recorded in the three routes that serve one, once the open has succeeded:

| Open | Route | Recorded |
|---|---|---|
| A document in its editor | The collab socket's open (`routes/collab.ts`) | After the subscribe and the read check that follows it |
| A plain file in the inline editor | `GET /editor/:ownerId/:mountId/:pathId/content` (`routes/editor.ts`) | After `getEditableContent` answers, unless a folder above is a document (`recordOpenedUnlessInDocument`) |
| A chat | `GET /chat/:ownerId/:mountId/:chatId/messages` (`routes/chat.ts`) | For the first page only, and never for a comment thread's chat (`containerPath`) |

Each ends in `recordOpened`, which pushes a `drive:recent-open` message to the user's own home through `sendToHome`, and that home calls `Drive.touchRecent`. The push is fire-and-forget with a catch that logs, so a failed write never fails the open, and it does nothing for a guest. The server records opens because it already serves them: a client report would need a route, a hook in three apps and a body the server has to check. `GET /collab/.../info` records nothing, though every editor reads it, because its query refetches on focus and on someone else's rename or ACL change, so a document nobody looks at would keep moving up. A preview reads other routes and records nothing. Opening a folder records nothing either, because clicking through folders would fill the list with ones the user only passed through.

So the time means "last had it open". A socket that reconnects after sleep, an inline editor that refetches, or a chat that fetches its first page again after a new message moves the path up again. The chat app's index route opens the first chat by itself, so visiting the app counts as opening that chat.

## A notification about a path adds it too

`Home.notify` writes the bell row and then moves the path its tag names to the top of the recipient's list ([NOTIFICATION-CENTER.md § A notification about a path puts it in Recent](NOTIFICATION-CENTER.md#a-notification-about-a-path-puts-it-in-recent)). Without it, a document someone just shared would not appear until the user had opened it, which is the case the page most needs to serve. The two rows are separate, so dismissing the notification leaves the path in the list.

What else reaches the list follows from these two writers, and is accepted:

- An upload, a WebDAV edit or a rename counts only when the user also opens the path or is notified about it.
- A team file appears only when it involves the user. Nearly everyone is in the default team, so every edit would make the list a feed of the whole company.
- A colleague editing a document they shared doesn't bring it up unless the user watches it.
- A file with no editor, such as a PDF or an image, appears only when a notification names it, since a preview records nothing.
- A folder appears when a notification names it, such as a burst of uploads into a watched folder.
- The table started empty, with no backfill.

## Each write trims the table to 200 rows

`touchRecent` upserts the row and deletes all but the newest 200 in one transaction. So the table needs no scheduled cleanup, no age limit and, at that size, no index on the time. The page shows at most 100. The other 100 rows are its reserve: when too few of the newest rows are still visible, the load reads those instead ([§ A load asks each owner whether the user may still see the path](#a-load-asks-each-owner-whether-the-user-may-still-see-the-path)). A bulk trash of watched files writes a hidden row per file, because each trash notifies the watcher. Two hundred or more push the older rows out for good, which is accepted.

## A load asks each owner whether the user may still see the path

`GET /drive/:ownerId/recent` (`requireSelf`, `requireNonGuest`) runs `aggregateRecents` (`apps/api/src/lib/drive/aggregate.ts`). It takes the newest 100 rows, groups them by owner, reads the user's team memberships once, and asks every owner at once through `pullVisiblePaths`, which runs on `pullFromEach` ([SCALABILITY.md § Reads across many homes go through pullFromEach](SCALABILITY.md#reads-across-many-homes-go-through-pullfromeach)). The user's own home is asked the same way. When fewer than 100 rows come back visible, it asks again for the next 100. It merges, sorts by `lastActivityAt` and returns at most 100, each a current `DrivePath` with its `lastActivityAt`.

`Drive.getVisiblePaths` answers on the owner's side, with one batched `getBreadcrumbs` per mount. It does its own access check and only the relay calls it, so it has no `SharedDrive` wrapper ([ARCHITECTURE.md § Drive Architecture](ARCHITECTURE.md#drive-architecture)). **Shared with me** asks through the same two functions ([ACL.md](ACL.md#shared-with-me-reads-each-path-from-its-owner)). `getVisiblePaths` leaves a row out when:

| Left out | Why |
|---|---|
| The owner has no such mount | It is disabled, removed or failed to start. `Drive.getMount` would throw and lose that owner's other rows |
| The breadcrumb is empty | The path was deleted for good |
| Its `parentId` is null | It is a mount root, such as Drive home, which would otherwise rank first |
| `isTrashedChain` | It is in the trash. A trash ends a sharee's access, but the owner and team members can still read it |
| `isInsideDocument` | It is a part of a document, such as a chat's attachment |
| `canReadFromAncestors` fails | The user lost access |

## A breadcrumb ends with the path itself

`isInsideDocument` (`apps/api/src/lib/drive/acl.ts`) checks `chain.slice(0, -1)`, because a breadcrumb runs from the mount root down to the path and includes the path. A check of the whole chain would find the document type on the path itself and hide every document and chat from the list. `refuseDocumentWrite` uses the same function for a change to a path, for the same reason ([§ A person only adds new files and threads inside a document](#a-person-only-adds-new-files-and-threads-inside-a-document)). The test "a document and a chat, and nothing inside a document" in `apps/api/src/test/drive/recent.test.ts` pins it.

## A read never deletes a Recent row

A row the load leaves out stays in the table. At this level a failed lookup looks the same as a missing file, and a brief error must not wipe someone's history. So a hidden row comes back when the access or the file does, after a new share or a restore, and otherwise falls off through the trim. **Shared with me** keeps its rows the same way, and only a revoke deletes one ([ACL.md](ACL.md#shared-with-me-reads-each-path-from-its-owner)).

## The Recent files page reads at most once a minute

`useRecentPaths` (`packages/lib/src/core/drive/hooks/`) has a one-minute stale time and no live updates, because every refetch reads every owner in the list. An open doesn't touch the page's query, so a file just opened shows on the first visit after that minute. The page (`apps/drive/src/routes/_auth.recent.tsx`) is read-only like Watched, since its rows belong to many owners, and a click shows a path's details and activity in the detail panel. It keeps its own sort, starting at Modified newest first under the column label "Last activity", and never writes the shared view preference, which could otherwise open it alphabetically. `RecentFilesSidebarItem` puts the one page directly below Drive in the sidebar of Drive and the document apps, and in a section of its own in Chat's, Calendar's, Mail's and Contacts' sidebars. Chat's and Calendar's hide it from a guest. Mail's and Contacts' have no guest check, because a guest never reaches those apps: the app switcher leaves them out, and `requireNonGuest` guards their API routes ([GUEST-ACCESS.md § The guest frontend is a narrower shell](GUEST-ACCESS.md#the-guest-frontend-is-a-narrower-shell)). One page serves every app, since the list is most useful across types and Chat has no list view of its own.

## Slow operations log in production too

`time()` (`apps/api/src/utils/timing.ts`) logs a `[timing]` line for a wrapped operation past 100 ms, and a `ManagedDatabase` logs `Synced` after each push to storage. Both stay on in production, by the owner's choice: they are how a slow request or a stuck sync shows in the logs. Don't gate them behind an environment check.
